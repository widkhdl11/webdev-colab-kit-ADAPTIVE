# UX 명세 — 무엇이 언제 보이는지 먼저, 그다음 시안 (경로 조건 규칙)

> 2026-10-22 사용자 지시로 만들었다. 시안은 상태 하나만 담는다. 그래서 「무엇이 언제 보이는지」를
> 정하지 않고 시안부터 그리면 모든 요소가 항상 보이는 화면이 나온다(팬꾹 정돈 시범에서 세 화면
> 위반 20건). 경로 다섯째 줄(`docs/ux/**`)은 브리프를 쓰는 순간 건드리는 파일이 `docs/ux/pages/`
> 라서 넣었다 — 앞의 넷만 있으면 이 단계에서는 규칙이 읽히지 않는다.

이 규칙은 design-drafting.md 의 「판단」보다 **먼저** 본다. 이 규칙의 승인 없이 시안을 만들지 않는다.
design-drafting.md 가 같은 확인을 자기 쪽에서도 직접 한다 — 규칙이 읽히는 순서에 기대지 않는다.

## 1. 언제 켜지나

다음 중 하나라도 이번 diff 에 있으면 켠다.

- 새 화면
- 새 흐름(화면 사이 이동이 새로 생기거나 바뀜)
- 요소가 보이는 조건(상태)의 변경
- 입력 항목·단계 수의 변경
- 여러 화면을 동시에 바꾸는 작업

색·간격·radius·카드 모양만 바꾸는 diff 에는 켜지지 않는다. **애매하면 켠다** — 브리프 8줄은 싸다.

## 2. 산출물

`projects/<이름>/docs/ux/pages/<경로슬러그>.md` 한 파일.

- 경로슬러그: 라우트 경로의 `/` 를 `-` 로 바꾼다. `/guide/fan` → `guide-fan`, `/` → `home`.
  동적 구간은 대괄호를 뺀 이름으로(`/gifts/[orderNo]` → `gifts-orderNo`).
- frontmatter 는 `status: draft | approved` 하나. 기계는 아직 읽지 않는다.
- 빈 양식: `docs/references/ux-page-template.md` 를 복사해 쓴다.

## 3. 파일 구조

- `## 페이지 브리프` 8줄: 목적 / 주 사용자·부 사용자 / 사용자가 와서 하려는 일 / 방문 빈도 /
  페이지 유형(문서형·목록형·작업형·상세형·관리형 중 하나, 둘이면 주·부) / 같은 유형의 다른 페이지 /
  이 페이지만의 특이점 / 바꾸면 안 되는 것
- `## 상태표`: 상태 이름(코드 식별자 + 화면 표기) / 조건 / 보이는 요소 / 가능한 동작 / 다음 상태.
  이름은 `docs/ux/states.md` 에 있는 것을 쓰고, 없으면 「제안」으로 표시한다.
- `## 요소 목록`: 요소 / 보이는 상태 / 정상 경로·예외 경로 / 근거(유형 규칙 번호)
- `## 적용한 규칙`: principles.md·<유형>-pages.md 에서 적용한 항목 번호, 벗어난 항목과 이유
- `## 스펙 참조`: 기능 규칙은 다시 쓰지 않고 `docs/specs/<slug>.md` 의 INV·S 번호로 가리킨다.
  스펙이 없는 기능은 「스펙 없음」.

## 4. 판정 기준 문서

- `projects/<이름>/docs/ux/principles.md`
- `projects/<이름>/docs/ux/<유형>-pages.md` — 파일 이름의 유형은 영문으로: 문서형 `document`,
  목록형 `list`, 작업형 `task`, 상세형 `detail`, 관리형 `admin` (예: `list-pages.md`)
- `projects/<이름>/docs/ux/states.md`

**하나라도 없으면 멈추지 말고** 「UX 기준 문서 없음: <경로>」를 보고하고 작성할지 묻는다.
게이트는 막지 않는다. 답을 기다리는 동안 그 답에 의존하지 않는 일(브리프 초안·역진단)은 계속 한다.
유형 문서의 빈 양식은 `docs/references/ux-type-rules-template.md`.

## 5. 승인

브리프·상태표·요소 목록을 보여주고 승인받은 뒤 `status: approved` 로 바꾼다.
그다음에야 design-drafting.md 의 「판단」(새 방향인가, 반복인가)으로 넘어간다.
양식을 채워 보여주는 절차는 `page-brief` 스킬이 맡는다.

## 6. 기존 화면을 고칠 때

- 슬러그 파일이 있으면 그 파일을 기준으로 바뀌는 차이만 적고 갱신한다.
- 없으면 코드를 읽고 **현재 상태를 먼저 쓴 뒤**(역진단) 바꿀 것을 적는다. 지금 모습을 적지 않고
  바꿀 것만 쓰면 무엇이 바뀌는지 승인하는 사람이 대조할 수 없다.

## 7. design-drafting.md 와의 관계

이 규칙이 먼저다. 이 규칙이 켜진 작업은 승인된 UX 명세 없이 시안을 만들지 않는다.
시안은 명세 상태표의 상태마다 한 장이고, 구현 뒤에는 ux-reviewer 가 ui-reviewer 보다 먼저 돈다
(없어질 요소의 시각 기준을 재는 일을 막는다).
