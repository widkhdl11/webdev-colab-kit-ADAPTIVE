# TDD 규칙 (스펙이 있는 기능)

- projects/<이름>/docs/specs/에 해당 기능의 approved 스펙이 있으면: 구현 전에 시나리오를 테스트로 먼저 작성한다
- 테스트 설명문에 INV ID를 포함한다 (spec-coverage 게이트가 추적한다)
- 테스트 작성 → 실행해서 실패(red)를 출력으로 보여준다 → 구현 → 통과(green) 순서.
  구현 후 끼워 맞춘 테스트는 알리바이지 검증이 아니다
- 검증 대상 자체를 모킹하지 않는다. 불변식마다 실패 경로 테스트를 반드시 포함한다
- 네트워크 의존 통합 테스트(실제 Supabase 등 외부에 붙는 INV 검증)는 기본 `npm test`에서 분리한다 —
  별도 `test:integration` 스크립트 + 전용 vitest config, 테스트는 `projects/<이름>/tests/` 에 둔다.
  게이트가 `npm test`를 돌리므로, 통합 테스트가 기본 run에 있으면 프로젝트 일시정지·네트워크 장애 시 게이트가
  비결정적으로 실패한다. 기본 test는 오프라인 유닛만. (spec-coverage는 tests/도 스캔하므로 INV 커버리지엔 무관)

## green 이 무엇을 증명하는가 (2026-08-10 retro — 4세션 연속 재발)

"알리바이지 검증이 아니다"는 위에 이미 적혀 있었는데도 네 세션 연속 나왔다. 이름이 아니라 **확인 절차**가 없었다.

- **불변식 테스트는 강제 지점을 무력화해 빨간불을 본 뒤에야 green 으로 친다.** 가드를 지우거나 상수를 바꿔도
  전부 통과하면 그 테스트는 아무것도 붙들고 있지 않다. 실제 사례: `safeSourceUrl` 의 정리 로직을 통째로 지워도
  통과 · `width="0" height="300"` 은 비율 가드가 대신 잡고 있어 정수 검사를 풀어도 통과 ·
  `MAX_RATIO` 를 10→100 으로 바꿔도 전부 통과(상수가 테스트로 고정돼 있지 않았다).
- **부재만 확인하는 단언은 절반이다.** "없을 때 안 넣는다"를 봤으면 "있을 때 넣는다"도 본다 —
  안 그러면 그 줄을 통째로 지워도 통과한다.
- **문자열 매칭은 자리를 고정하지 못한다.** `toContain("원문 제목")`·`/<\/div><article/` 는 사이에 무엇이
  끼어들어도 통과한다. 구조를 검증할 거면 DOM(`querySelector`·`nextElementSibling`)으로 본다.
- **소스 텍스트를 정규식으로 훑는 것은 테스트가 아니다.** 함수를 한 번도 부르지 않으므로 주석 두 줄만 지워도
  빨간불이 되고, 반대로 동작을 바꿔도 통과한다. 실제로 호출해서 결과를 본다.
- 변이를 만들 때 **타입 단언(`as never` 등)으로 바꾸는 건 변이가 아니다** — 동작이 그대로다. 가드를 실제로 지운다.

## 유닛이 다 green 인 것과 동작하는 것은 다르다 (같은 retro)

- 외부(네트워크·DB·모델)에 붙거나 화면에 나오는 기능은 **리뷰 파견 전에 실제로 한 번 돌린다.**
  더미 데이터는 "잘 되는 모습"만 보여준다. 유닛이 전부 green 인 상태에서 실행 한 번이 잡은 것들:
  키 하나가 없을 때 라우트 500(유닛 250개 green) · 요약 0건·태그 0건·본문 0건 ·
  "아래는 원문입니다" 아래가 빈칸 · 재수집이 직전 주기에 추출한 본문을 덮어씀(고친 뒤 9→42건).
- `workspace/review.md` 에 사인오프를 적을 때 **실행 근거 한 줄**을 같이 남긴다 —
  돌린 명령 + 결과 숫자(예: `npm run ingest → 수집 42 · 요약 7 · 실패 0`).
  안 돌렸으면 안 돌렸다고 적는다. 적을 게 없는 것과 안 적은 것은 다르다.
