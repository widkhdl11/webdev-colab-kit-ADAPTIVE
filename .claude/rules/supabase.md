# Supabase 연동 규칙 (데이터 계층 — 킷 공통)

프로젝트 무관 범용 규칙만 여기 둔다. 프로젝트 고유 격리·테넌시·도메인 규칙은
projects/<이름> 스코프 파일로 분리한다 (예: supabase-wama.md).

- **service_role 키는 클라이언트에 절대 노출 금지.** 브라우저 번들에는 anon 키만. 서버 전용
  키가 필요한 연산은 RPC/서버 측에 둔다. (게이트 NO_HARDCODED_SECRET가 1차로 잡지만 배치도 규칙)
- **쿼리·RPC 응답은 신뢰 경계 밖.** shared/api는 반환값을 그대로 도메인에 넘기지 말고 경계에서
  파싱·검증한다 (스마트 컨스트럭터로 도메인 값 객체 생성).
- **인가는 클라이언트 필터가 아니라 RLS로.** 클라이언트의 `.eq(...)` 필터는 UX용일 뿐 인가가 아니다 —
  민감 데이터는 필터를 빼도 새지 않아야 한다. (테넌시·소유권 정책의 구체는 프로젝트 스코프 규칙에서)
- 이 파일은 범용 연결/호출 어댑터만 — 도메인 개념(도메인 규칙·로직)은 여기 두지 않는다
  (그건 entities/features). shared 규칙과 동일: 도메인 지식 유입 금지.

## 마이그레이션 (projects/<이름>/supabase/migrations/*.sql)

- **한 번만 도는 것과 여러 번 돌아도 되는 것을 한 파일에 섞지 않는다.** `scripts/apply-migrations.mjs` 는
  `--all` 을 주면 폴더의 `.sql` 을 이름순으로 전부 다시 적용하고, 새 DB·리셋에서는 실제로 그렇게 써야 한다.
  그 파일에 **조건 없는 `update`/`delete`/`truncate`** 가 남아 있으면 그때 데이터가 날아간다.
  일회성 데이터 정정은 파일에 넣지 말고 손으로 한 번 실행한 뒤 "언제 무엇을 했는지"만 주석으로 남긴다.
  다시 돌려도 결과가 같은 문장(`add column if not exists` 류)은 그대로 둔다.
  근거: `0003` 에 조건 없는 `set summary = null` 을 넣었고, 다음에 `0004` 를 추가해 전부 돌렸으면
  요약 92건이 사라지고 전액 재과금될 상태였다 (2026-08-10 리뷰에서 발견).
- 기존 테이블을 다시 만들지 않는다 — `create table`·`drop` 은 최초 파일에만.
