# 킥오프 — 요구를 함께 구체화하기

목표: 사용자 머릿속 그림을 PRODUCT.md로 옮긴다. 한 번에 다 정하지 말고 대화로 점진적으로.
PRODUCT.md = 제품 정의+스코프 문서(프로젝트당 1개, 스코프 변경 시에만 갱신, 갱신엔 사용자 동의 필수).

## 절차

0. 프로젝트 이름을 정한다(소문자·숫자·하이픈) → projects/<이름>/ 생성 → 루트 ACTIVE에 그 이름 한 줄 기록
   → projects/<이름>/workspace/·projects/<이름>/docs/ 폴더 생성. (이후 프로젝트 문서는 전부 이 아래에 쓴다)
1. 첫 설명으로 projects/<이름>/docs/PRODUCT.md 초안 작성 (빈 항목 포함). 이미 아는 것을 다시 묻지 않는다
2. 질문은 "안 물으면 잘못 만들 확률이 높은 것"만, 한 번에 3개 이하, 선택지 제시
3. 영역 순서: ①목적/대상 ②필수·비범위 ③페이지 ④기술 ⑤디자인
4. ④기술의 규칙: 언어(TS)·아키텍처(FSD)·검증 체계는 하네스 전제 — 묻지 않고 고지한다.
   묻는 것은 프리셋 안의 여지뿐: 렌더링(정적/SPA), 데이터 계층(없음/Supabase),
   배포(안 함/정적 호스팅/Vercel). 기본값 제안 + 근거 + 이견 확인 형식으로.
   답은 PRODUCT.md 기술 결정에 기록하고 setup의 입력이 된다
5. 답이 나올 때마다 PRODUCT.md 즉시 갱신, 변경분을 보여준다
6. "모르겠다/알아서" → 권고안 제시, 동의 후 "(가정)" 표시로 기록
7. 트레이드오프가 있던 결정은 projects/<이름>/workspace/DECISIONS.md에 한 줄 기록
8. 엔티티/데이터를 도출하면 docs/references/modeling-checklist.md를 **얕게** 훑는다 —
   8개 질문을 다 쏟지 말고, 필드를 스캔해 걸릴 것 같은 것만 **플래그만** 찍는다
   (예: "학생-학년이 시간에 따라 변함 → 스펙 필요"). 결제·인증·권한·동시성처럼 어기면
   사고 나는 기능, 또는 시변·파생 상태에 걸린 필드는: 구현 전 /spec 고지 + PRODUCT.md 해당
   항목에 "(스펙 필요: …)" 표시
9. 마무리: PRODUCT.md 요약 → "이대로 시작할까요?" → 동의 후 setup 스킬 제안

## 금지

- 심문 금지. 질문 총량 10개 초과 시 남은 건 가정 처리 + 기록
- PRODUCT.md 없이 구현 시작 금지
- 파일보다 인터뷰를 먼저 하지 않는다. 첫 행동은 "이름 + 한 줄 정의"를 받아 projects/<이름>/docs/PRODUCT.md 를 만드는 것. 그 전에 목적·기능·페이지 질문 금지 (이름을 모르면 '이름과 한 줄'만 물어 즉시 생성 — 이건 인터뷰가 아니라 파일 착수다). 생성 후 모든 질문은 파일 편집(변경분 표시)으로 한다.
