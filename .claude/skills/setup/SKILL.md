# 셋업 — 이 프로젝트에 맞는 하네스 구성 + 프로젝트 골격
목표: PRODUCT.md의 결정에서 파생되는 프로젝트 고유 구성만 추가한다. 기본 구성은 건드리지 않는다.

## 절차
1. projects/<이름>/docs/PRODUCT.md와 projects/<이름>/workspace/DECISIONS.md를 읽고 프로젝트 고유 요소를 추린다
2. 각 요소에 "구성 추가가 필요한가"를 아래 기준으로 판정
3. 추가할 것을 근거와 함께 제안 — 항목마다 "왜 기본 구성으로 부족한가" 한 줄 필수
4. 항목별로 사용자 승인 (일괄 승인 요청 금지). 승인된 것만 생성
5. **스캐폴딩·설치 전에 기술 스택을 문서로 합의한다.** projects/<이름>/docs/tech-stack.md 를
   `status: draft` 로 만든다 — 하네스 전제(TS·FSD·빌드·테스트)는 '확정'으로 고지, 프로젝트가
   고르는 것(UI 프레임워크·렌더링·배포 등)은 선택지+추천으로. 사용자가 확인·수락하면 `status: approved`
   로 바꾸고 그에 맞게 package.json 을 맞춘다. **approved 전에는 scaffold/npm install 금지**
   (혼자 스택을 정해 설치하지 않는다).
   - **아키텍처 프로파일**: docs/references/architectures/ 에 검증된 구조가 있으면(예: vite-fsd·nextjs-fsd)
     tech-stack.md에서 거기서 고르게 제시한다 — 구조·게이트 함의·기본 libs가 딸려온다(매번 재발명 금지).
     새로 검증된 구조를 만들면 프로파일 파일로 **학습·추가**한다(하나씩 축적).
   - **새 스택을 채택했으면 반드시**
     [architectures/README.md](../../../docs/references/architectures/README.md) 의
     "새 프로파일을 추가할 때" 체크리스트를 돌린다 — 게이트는 전역인데 "화면이 어디 사는가"는
     스택마다 다르다. 안 맞으면 **강제가 조용히 사라지거나(막아야 할 걸 안 막음)
     엉뚱한 프로젝트가 과차단된다.** 둘 다 실패로 보이지 않아서, 찾지 않으면 모른다.
6. `node scripts/scaffold.mjs <프로젝트명>` 실행(루트 ACTIVE의 프로젝트 이름으로 → projects/<프로젝트명>/ 골격 생성)
   → 승인된 tech-stack.md 대로 package.json 조정(프레임워크 등) → `node gates/run-gates.mjs`로 골격 검증
7. 생성 결과 보고 + 새 스킬/rules 인식을 위해 세션 재시작이 필요할 수 있음을 안내

## 생성 판정 기준 (미달이면 만들지 않는 것이 정답)
- 규칙은 적용 대상(경로)에 붙는다. 역할별 규칙 사본 금지 — 진실이 갈라진다
- **rules**: 특정 경로에서만 유효한 규칙이 3개 이상 모일 때만 (paths 스코프 가능해야)
- **서브에이전트**: 컨텍스트 격리·권한 격리·병렬성 중 1개 이상 충족할 때만.
  "역할이 있으면 좋겠다"는 근거가 아니다. 기존 리뷰어 프롬프트 보강이 우선.
  정의 파일 품질 요건: 임무 한 문장 / tools 최소셋 / 출력 형식 명시 /
  규칙은 본문에 복사하지 말고 rules·docs 포인터로
  - **tools 최소셋 = "역할이 성립하는 데 필요한 것"이지 "적을수록 좋은 것"이 아니다.**
    tools 는 화이트리스트라 안 적은 도구는 이미 다 막혀 있다(금지 목록을 따로 적을 필요 없음).
    **MCP 도구는 `mcp__<서버>__<도구>` 풀네임으로 명시해야 하며, 부모 세션에 연결돼 있어도
    서브에이전트로 상속되지 않는다.** description 에 전제("Playwright 연결 시에만 위임")를 쓰는 것과
    실제 권한을 주는 것은 별개 — 전제만 쓰면 위임해도 아무것도 못 하는 빈 껍데기가 되고,
    **위임해보기 전에는 드러나지 않는다.**
    본문에도 "필요한 도구가 안 보이면 시도하지 말고 '미연결'로 보고하고 끝낸다"를 넣어 실패를 조용하지 않게.
    (허용된 도구를 *어디까지* 쓰는지는 tools 로 표현 못 하므로 본문 산문으로 — 예: design-drafter 의
    "산출물은 mockups/ 아래", "design-rules.md 갱신은 본체가 한다")
- **게이트 규칙**: 정적 검사로 표현 가능한 고유 금지 패턴이 있을 때.
  gates/는 보호 파일 — 제안만 하고 사용자가 반영
  - **스택·아키텍처에 따라 달라지는 규칙은 가정을 코드에 숨기지 말고 먼저 판정하고 분기한다**
    (`isNextProject()` 처럼 설정 파일 존재로 판정 — 폴더 이름 추측 금지).
    분기의 기본값은 "스택 전용 규칙을 적용하지 않음" — 새 스택이 들어와도 잘못 막지는 않게.
    못 막는 구멍은 프로파일 문서 "게이트 함의"에 적는다. 상세: architectures/README.md
- **스킬**: 3회 이상 반복될 다단계 절차가 예상될 때만
- **조건부 서브 후보**: 스펙 쓰는 프로젝트 → spec-auditor / 세션이 많이 쌓이는
  장기 프로젝트 → doc-drift-auditor. 탐색용 서브는 만들지 않는다 (내장 Explore 사용)
