# 회고 — "뭐가 틀렸나"가 아니라 "무엇이 바뀌어야 같은 실수가 안 나나"
## 절차
1. 게이트 실패·리뷰 지적·사용자 피드백을 훑되, **빈도가 아니라 종류로 거른다** (핵심 판별):
   - **규칙의 부재(구조적 빈칸)** = 도메인 무관하게 재발하는, 물어볼 자리가 하네스에 없던 것.
     → **1회라도 교훈.** 하네스를 고친다. (예: "필드가 시간에 따라 변하는지 물을 국면이 없음")
   - **판단의 실수·재량적 예외** = 특정 상황의 잘못된/일회성 판단, 또는 사용자가 의도한 예외("이번만").
     → **몇 번이든 교훈 아님.** 인스턴스만 고치고 하네스는 둔다. (예: "이번 순서 착오")
   - 반영하는 규칙은 **"이미 참인 원칙의 기계화"이거나 "구조적 빈칸"** 이어야 한다. 개별 판단의
     결과를 규칙으로 박지 않는다 — 과적합은 사용자(오케스트레이터)의 예외 낼 권리를 뺏는다.
2. 교훈마다: 패턴 / 근거(어디서 몇 번) / 제안(반영 위치)
3. 반영 위치 우선순위 (싼 층으로 내려보내는 압력):
   ① permissions.deny — 선언으로 되면 최선 (0코드)
   ② 게이트 — 정적 검사 가능하면 (0토큰, 100% 강제. gates/는 보호 파일 — 제안만)
   ③ rules/조건부 문서 — 특정 경로·상황에만 필요한 규칙
   ④ CLAUDE.md — "어기면 협업이 깨지는" 수준일 때만 (상시 고정비)
   ※ 안내 문서(가이드) 축: 빈칸이 "이 국면에서 이걸 물어봤어야 했다"류면 강제 사다리 대신
     해당 국면의 안내 문서를 두껍게 한다 — 스펙 쓰다 발견한 빈칸 → docs/references/spec-template.md(정본),
     데이터 모델 함정 → docs/references/modeling-checklist.md. 특정 프로젝트 사본이 아니라 정본을 고친다
     (다음 프로젝트가 같은 빈칸에 다시 안 빠지게). 프로젝트가 쌓일수록 이 문서들이 두꺼워지는 게 정상.
4. 사용자 승인 후에만 반영. docs/LESSONS.md 기록은 승인 후 사용자 확인 하에
5. CLAUDE.md가 40줄을 넘보면 기존 규칙의 강등(③으로 이동)을 함께 제안
6. **미결 백로그(docs/references/harness-backlog.md)를 훑는다** — 각 항목의 승격 트리거가
   충족됐으면 사다리대로 승격 제안. 반영되면 항목을 `- [x]`로 졸업시키고 LESSONS.md로 옮긴다
