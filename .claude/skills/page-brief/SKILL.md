# 페이지 브리프 — 양식을 채워 보여 주고 고친다

빈 질문을 던지지 않는다. **추천값이 채워진 초안**을 먼저 보여 주고, 사용자는 틀린 칸만 고친다.
(이유: 처음부터 답을 쓰는 것보다 틀린 곳을 고르는 편이 쉽다 — design-interview 와 같은 방식이다)

## 언제 쓰나 (경계)
- **쓴다**: 새 화면, 새 흐름, 요소가 보이는 조건(상태)의 변경, 입력 항목·단계 수의 변경,
  여러 화면을 동시에 바꾸는 작업. 기준은 `.claude/rules/ux-spec.md` 1절.
- **안 쓴다**: 색·간격·radius·카드 모양만 바꾸는 작업. 시각 취향(색·톤·밀도)은 design-interview 의 몫이다.
- 애매하면 쓴다 — 브리프 8줄은 싸다.

## 절차
1. **초안을 만든다.** 산출물은 `projects/<이름>/docs/ux/pages/<경로슬러그>.md`,
   빈 양식은 `docs/references/ux-page-template.md`. 구조는 `.claude/rules/ux-spec.md` 3절을 따른다.
   - 페이지 유형은 추천 하나와 근거 한 줄을 같이 적는다.
   - 상태표는 `docs/ux/states.md` 와 코드(있으면)에서 뽑는다. states.md 에 없는 상태는 「제안」으로 표시한다.
   - 기존 화면이면 코드를 읽어 **지금 모습을 먼저** 적고, 바꿀 것은 그 아래에 차이로 적는다.
   - 판정 기준 문서(`docs/ux/principles.md`·`<유형>-pages.md`·`states.md`)가 없으면
     「UX 기준 문서 없음: <경로>」를 같이 보고하고 작성할지 묻는다. 초안 작성은 멈추지 않는다.
2. **보여 주고 틀린 칸을 고쳐 달라고 한다.** 브리프·상태표·요소 목록 세 덩어리를 보여 준다.
   2회차부터는 매번 「이 정도면 시안·구현에 충분합니다. 승인할까요?」를 명시한다.
3. **승인되면** frontmatter 를 `status: approved` 로 바꾼다. 「제안」 상태가 있으면
   `docs/ux/states.md` 에 올릴지 같은 턴에 묻는다.
4. **기능 규칙은 명세에 쓰지 않는다.** 「스펙 참조」에 `docs/specs/<slug>.md` 의 INV·S 번호만 적는다.
   위험 표면(인증·결제·권한·동시성)에 닿는데 스펙이 없으면 /spec 을 먼저 권한다.

## 다음 단계로 연결
```
page-brief (이 스킬, UX 명세 승인)
  → .claude/rules/design-drafting.md 의 「판단」 (새 방향인가, 반복인가)
     ├ 새 방향: design-interview → design-drafter(상태마다 시안 한 장) → checkpoint
     └ 반복:    바로 구현
  → 구현 → ux-reviewer → (시각 변경이면) ui-reviewer
```

## 금지
- 시각 취향(색·톤·밀도) 질문 — design-interview 의 몫이다.
- 승인 전에 `status: approved` 로 바꾸기, 승인 전에 시안이나 구현으로 넘어가기.
- 코드에 없는 상태를 명세에 지어 넣고 「지금 모습」이라고 적기 — 지금 모습과 바꿀 것을 섞지 않는다.
