# Phase A — 정적 파악

**목표**: 파일에 쓰여 있는 것만으로 harness의 워크플로우와 참조 문서를 완성한다.
**소요**: 주말 하루
**필요한 것**: 레포 파일뿐. 실행 로그 · Langfuse 불필요.
**산출물**: 워크플로우 그림 1장 + 보조 그림 3장 + 단계 문서 + `ARCHITECTURE.md`

---

## 원칙

이 작업의 최대 위험은 **에이전트가 그럴듯한 서사를 지어내는 것**이다. "내 harness 설명해줘"라고 물으면 매끄러운 답이 나오고, 모르니까 물어본 것이므로 검증할 수단이 없다.

그래서 모든 문서에 근거 등급을 표시한다.

| 표기                     | 의미                               |
| ------------------------ | ---------------------------------- |
| `[CONFIRMED: path:line]` | 파일에 그렇게 쓰여 있음            |
| `[INFERRED]`             | 읽고 추론함. Phase B에서 검증 대상 |

**등급은 이 둘뿐이다.** 다른 라벨을 쓰지 않는다. `[INFERRED]`가 많이 나오는 게 정상이고 정직한 상태다. 그 목록이 그대로 Phase B의 작업 큐가 된다.

확인된 것과 추정이 섞인 문서는 아예 없는 것보다 나쁘다. 나중에 그 문서를 근거로 판단하다가 틀리고, 어디서 틀렸는지 못 찾는다.

---

## A-0. 준비

```bash
git checkout -b docs/architecture-map
mkdir -p docs/{reference,stages,diagrams}
```

브랜치를 파는 이유: 이 작업은 문서만 건드리는데, 진행하다 보면 harness 코드를 고치고 싶어진다. 그러면 분리가 안 된다. **발견한 문제는 `findings.md`에 적기만 하고 고치지 않는다.**

## A-1. 추출 스크립트 작성

`[CONFIRMED]` 등급 정보는 전부 기계가 뽑을 수 있다. 손으로 쓰면 코드가 바뀔 때 즉시 stale해지므로, 이 층은 항상 생성물이어야 한다.

```
Write a Node script at scripts/extract-harness.mjs that inventories this
repository's agent configuration. It must READ ONLY — never modify anything.

Scan and collect:
1. Skills — every SKILL.md. Extract: name, full description text (verbatim,
   do not summarize — the description IS the trigger condition), allowed-tools
   if present, file path, line count, and paths of any reference files it
   points to.
2. Commands — every file under .claude/commands/ (or the equivalent path in
   this repo). Extract: name, description, referenced skills or agents.
3. Subagents — name, description, tool restrictions, which files they are
   allowed to write.
4. Hooks — event name, matcher, command, and the file it is configured in.
5. Rules — every rules file. Extract: path scope, load condition, size.
6. Graph — read graph.mjs and report the node types, edge kinds, and the
   propagation rules it implements.

Output docs/reference/inventory.json plus one markdown file per category
under docs/reference/.

Rules:
- Do not infer or guess. If a field is absent, write null — never fill it in.
- Do not editorialize. No "this skill is useful for..." commentary.
- Every markdown file must start with: "Generated by
  scripts/extract-harness.mjs. Do not edit by hand."

First: explore the repo and show me the actual directory layout and one
example of each file type you found. Then stop and wait for my confirmation
before writing the script.
```

> **마지막 문단이 핵심.** 구조를 모르는 상태에서 스크립트부터 짜게 하면 경로를 지어낸다. 반드시 구조 확인 → 승인 → 작성 순서로.

## A-2. 실행 + 정합성 검사

```
Run scripts/extract-harness.mjs, then cross-check docs/reference/ for
internal consistency and write docs/findings.md:

- Skills, subagents, or commands that nothing else references
- Documents a stage claims to read that no stage writes (phantom reference)
- Documents a stage writes that no stage reads (orphan)
- Hooks pointing at files that do not exist
- Gate conditions referencing state that nothing sets
- Skills whose description is under 30 words (weak trigger condition)
- Two or more skills whose descriptions overlap enough to both fire on the
  same request

Evidence for each finding. No fixes yet — I want the full list.
```

실측 없이도 여기서 상당수가 잡힌다. 고아 스킬, 유령 참조, 깨진 hook, 트리거 충돌은 전부 정적 검사로 나온다.

## A-4. 워크플로우 그림 ← 첫 산출물

```
Use archify to create a workflow diagram of this harness's main execution
path, based on docs/reference/.

Constraints:
- 8 to 12 nodes maximum. If you have more, group them — do not add edges.
- One primary happy path, clearly dominant. Branches and failure paths
  secondary.
- Mark every gate explicitly as a distinct node shape or lane.
- Put supporting detail in node cards, not in additional edges.
- Node labels must use the canonical terms from GLOSSARY.md.

Ground rules:
- Every node must correspond to something in docs/reference/.
- Mark each node [CONFIRMED: path:line] or [INFERRED] in its card.
- If a step exists in my head but not in the artifacts, do NOT draw it —
  list it separately as "unverified steps" after the diagram.

Save the JSON IR to docs/diagrams/00-workflow.workflow.json and the HTML
alongside it. Validate before delivering.
```

**여기까지가 최소 목표.** 8~12 노드 제약은 반드시 지킨다. 그 이상이면 아무도 읽지 않는다.

1200×630 공유 카드가 나오므로 `webdev-collab-kit` README 최상단에 바로 박을 수 있다. 인터랙티브 HTML은 GitHub Pages에 올려 링크한다.

## A-5. 보조 그림

한 번에 하나씩. 순서는 값어치 순.

### 문서 흐름 (권장 1순위)

"이 문서가 어디서 만들어져서 어디서 읽히는지"는 현재 머릿속에만, 그것도 부분적으로만 있다. 그림으로 그리면 A-2에서 나온 고아 · 유령이 시각적으로 확인된다.

```
Use archify to create a data-flow diagram of documents in this harness.
Nodes: every document created or read (SPEC.md, PLAN.md, HANDOFF.md,
_cross-cutting.md, GLOSSARY.md, sealed invariant files, etc.)
Edges: which stage writes it, which stages read it.
Mark sealed documents distinctly, and mark where hash verification occurs.
Use docs/findings.md to mark orphans and phantom references — these must be
visually distinct.
Save to docs/diagrams/03-doc-flow.dataflow.json.
```

### 게이트 상태

```
Use archify to create a lifecycle diagram of gate-mode: every state, the
events that transition between them, retry paths, and terminal outcomes.
Derive states from the rules files and graph.mjs, not from assumption.
Save to docs/diagrams/02-gate.lifecycle.json.
```

### 계층 구성

```
Use archify to create an architecture diagram of the five context layers
(CLAUDE.md, rules, skills, subagents, hooks). Show what loads always vs
conditionally, and the load trigger for each conditional layer.
Save to docs/diagrams/04-layers.architecture.json.
```

> **시퀀스 다이어그램은 Phase A에 없다.** 실제 호출 순서가 필요하므로 Phase B로 넘어간다.

## A-6. 단계 문서

**그림이 나온 뒤에 쓴다.** 그림을 먼저 그려야 단계 경계가 정해지고, 그 경계가 문서 분할을 결정한다. 반대로 하면 문서가 임의로 쪼개진다.

워크플로우 노드 하나 = 문서 하나.

```
For each node in docs/diagrams/00-workflow.workflow.json, write
docs/stages/NN-<name>.md using exactly this template:

# NN. <Stage name>

## Purpose
One sentence: why this stage exists and what breaks without it.

## Entry condition
What must be true to enter. Cite the file and line that enforces it.

## What it does
Numbered steps.

## Skills and tools
| name | when | evidence |
Evidence must be [CONFIRMED: path:line] or [INFERRED]. No other labels.

## Documents read
| document | purpose | required? |

## Documents written
| document | ownership | consumed by |

## Gate
Condition, pass path, fail path.

## Failure path
Where control goes when this stage cannot complete.

## Exit condition
What must be true to move on.

## Unverified
Anything you could not confirm from files. Be explicit — do not leave this
section empty just to look complete.

Write ONE file first and show it to me. Do not batch.
```

> **`Do not batch`를 반드시 넣는다.** 한 번에 다 쓰게 하면 템플릿만 채운 껍데기가 나온다. 첫 장을 보고 템플릿을 조정한 뒤 나머지를 진행한다.

템플릿에서 `Entry condition` · `Failure path` · `Exit condition` · `Unverified` 네 항목이 특히 중요하다. 앞의 셋은 단계 경계를 명확히 하고, 마지막은 모르는 것을 모른다고 남긴다. 적어두지 않으면 그 자리가 침묵으로 메워지고 나중에 아는 것과 구분되지 않는다.

## A-7. 진입점

```
Write docs/ARCHITECTURE.md as the entry point:
- Embed the workflow diagram (link to the HTML, inline the share card PNG)
- One paragraph: what this harness is for and what problem it solves
- A table linking each stage number to its docs/stages/ file
- Links to the other diagrams with one line each on what they answer
- A "Known gaps" section pulling the top items from findings.md
- A "Unverified claims" section collecting every [INFERRED] from the stage docs

Target: someone who has never seen this repo understands the shape in two
minutes. No marketing language. Under 150 lines.
```

마지막 두 섹션이 Phase B의 작업 목록이 된다.

## 산출 구조

```
docs/
  ARCHITECTURE.md              # 진입점
  findings.md                  # 정합성 검사 결과
  diagrams/
    00-workflow.workflow.json      ← 커밋 (소스)
    00-workflow.workflow.html      ← 산출물
    02-gate.lifecycle.json/.html
    03-doc-flow.dataflow.json/.html
    04-layers.architecture.json/.html
  stages/
    01-intake.md
    02-spec.md
    ...
  reference/                   # 전부 자동 생성
    inventory.json
    skills.md
    subagents.md
    hooks.md
    commands.md
scripts/
  extract-harness.mjs
```

**`.json`을 반드시 커밋한다.** archify IR이 소스이고 HTML은 산출물이다. 커밋해두면 나중에 `archify compare`로 커밋 간 구조 변화를 diff할 수 있다.

## 중단 신호

에이전트가 **"이 단계는 아마 이렇게 동작할 것"**이라고 매끄럽게 쓰기 시작하면 거기서 멈춘다. 그 지점이 이 작업 전체를 무효화한다.

의심되면:

```
Re-read the last document you wrote. For every claim, give me the exact file
path and line number that supports it. If you cannot produce one, move that
claim to the Unverified section.
```
