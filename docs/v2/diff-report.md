### 판정 근거 (갈린 것만)

**D1 — `qa` 글롭이 `.test.tsx` 를 못 잡는다. 1차가 맞다.**
`gates/graph-stop.mjs:32-43` 의 `globToRegex` 를 파일로 복사해 실행:

src/**/*.test.ts  vs  src/features/content-render/ui/article-body.test.tsx -> false
```
signal 의 테스트 9개 중 **3개가 `.tsx`** 다 (`article-body` · `mark-read-on-view` · `article-view`).
2차는 [05-qa.md](stages/05-qa.md) `Unverified` 에서 테스트 파일 탐지 정규식을 의심하긴 했으나 `spec-coverage` 쪽만 봤고, **`qa` 노드의 produces 글롭은 검사하지 않았다.** 명백한 누락이다.

**D2 — `schema-designer` 늘 통과. 1차가 맞다.**
`src/entities/*/model.ts` 는 signal 의 `src/entities/article/model/types.ts` 를 잡지 못한다(실측: false). `supabase/` 디렉터리도 없다.
→ 매칭 0개 → `gateBlocked` 가 막을 대상이 없어 **무조건 clean**.
2차는 [03-design.md](stages/03-design.md) 에서 이 노드를 다뤘지만 "절차 문서가 없다"까지만 갔고 글롭 매칭을 실측하지 않았다.

**D3·D4 — `execution-graph.html`(루트 15KB) 과 `tech-stack.md`. 1차가 맞다.**
`execution-graph.html` 을 언급하는 레포 파일: 1차 자신의 산출물 2개뿐, 실제 하네스에서는 **0건**.
`tech-stack.md` 는 `graph.mjs` 의 어느 `produces` 에도 없다(확인: grep 0건).
2차가 놓친 이유는 명확하다 — 고아 검사 대상 목록을 `docs/references/` · `.claude/rules/` · 루트 몇 개로 **손으로 한정**했고 `execution-graph.html` 과 프로젝트 문서를 넣지 않았다.

**D6 — 스킬 설명 충돌. 1차가 맞다. 2차의 방법이 틀렸다.**
2차는 어절 Jaccard 최댓값 0.086 을 근거로 "충돌 0건"이라고 결론지었다. **측정 도구가 질문에 맞지 않았다.**
충돌은 어휘가 겹치는 문제가 아니라 **어떤 말에 걸리느냐가 겹치는** 문제다. `checkpoint`("페이지를 처음 만들기 시작할 때")와
`design-interview`("새 시각 방향의 화면을 만들기 전")는 "새 페이지 만들어줘" 한 문장에 둘 다 성립하고,
**서로를 배제하는 문구가 어느 쪽에도 없다.** 순서를 정하는 것은 설명이 아니라 `.claude/rules/design-drafting.md` 라는 별도 문서다.
2차는 [findings.md](findings.md) F-06 에서 임계값의 근거가 없다는 것을 `[INFERRED]` 로 표시하긴 했으나, **표시하고도 "0건"이라는 결론은 내렸다.** 표시가 결론을 막지 못했다.

**D7 — qa-classifier 예시 경로. 1차가 틀렸다.**
```
projects/wama/supabase/migrations/0007_exam.sql      EXISTS
projects/wama/docs/specs/auth-isolation.md           EXISTS
```
1차는 "둘 다 존재하지 않는다(wama 시절 예시로 보인다)"라고 썼다. **두 파일은 지금 이 레포에 있다.**
원인은 프로젝트 상대경로를 레포 루트 기준으로 판정한 것 — §R6 에서 고친 추출기 결함과 **원인이 정확히 같다**.
도구를 고쳤더니 같은 자리에서 1차의 오탐이 드러났다.

**D8 — `deploy` 심각도. 2차가 맞다.**
1차는 "`deploy` 는 **구조상 clean이 될 수 없다**"고 썼다. 이건 거짓이다.
`gates/graph-stop.mjs:259-262` 가 프론티어에 사인오프 노드가 오면 **무엇을 써야 하는지 basis 해시까지 출력**한다.
절차 **문서**가 없는 것은 사실이지만(양쪽 일치), 그것과 "구조상 불가능"은 다르다. 2차의 중간이 옳다.

**D9 — 프론트매터 볼 게 없으면 통과. 2차가 맞다.**
`gates/graph-stop.mjs:153` — `if (files.length === 0) return true;`. 같은 파일의 `exists_nonempty`(167행)는 0개면 거짓이다.
볼 파일이 없을 때의 동작이 **서로 반대**라, `design-rules.md` 가 아예 없어도 `page-designer` 가 clean 이 된다.
1차는 이 파일을 여러 번 인용했지만 이 비대칭은 지적하지 않았다.

**D13 — 검사 항목 해석이 갈렸다. 둘 다 참이다.**
검사 항목은 "아무것도 참조하지 않는 스킬·서브에이전트·커맨드"였다.
- 1차: **누가 이 스킬을 부르나**(inbound) → `goal`·`status`·`scaffold` 는 `README.md` 한 줄뿐, CLAUDE.md 에 없음
- 2차: **이 스킬이 무엇을 참조하나**(outbound) → 10개 전부 최소 1개 파일 참조 → 0건

한국어로는 2차의 읽기가 문법에 맞지만, **실제로 쓸모 있는 건 1차 쪽이다** — 도달 불가능한 스킬이 실제 문제다.
최종본에는 **둘 다** 담는 게 맞다. (검증: `goal` 은 `README.md:31` 단 1곳, `status`·`scaffold` 도 같은 줄)

프롬프트는 "워크플로우 노드 하나 = 문서 하나"라고 했다. 두 결과 모두 자기 워크플로우 그림의 노드를 따랐으므로

**7장 + [runtime.md](runtime.md) 로 결정됐다** — 그래프 노드와의 1:1 을 지키면서 실행 주체 4종을 한곳에 모으는 절충이다(§7 ②).

| **R2-3 루트기준표기** | 17 | 마크다운 링크가 루트 기준 → 렌더러에서 `docs/stages/CLAUDE.md` 로 해석됨. **1차와 똑같은 사고의 남은 것** |

① [CONFIRMED: .claude/skills/spec/SKILL.md:1-5]   ← 루트 기준 경로 + 다중 줄 표기

```

**즉 1차의 실제 잔여 결함은 29건이다.** 수정을 했지만 완결됐는지 확인할 방법이 없었던 것 — 검사기가 없었기 때문이다.

## 6. 두 결과 모두 못 잡는 것 — 내 검사기의 한계

정직하게 적는다. `check-docs.mjs` 는 **범위 안의 틀린 줄 번호를 잡지 못한다.**

1차는 F1·F2·F3 의 근거로 `README.md:26` 을 **세 번** 인용했다. 실제 내용은 **31행**에 있다:

```
26:  디자인 국면 (새 방향일 때만 — 이미 승인된 방향의 반복 화면은 건너뛰고 바로 구현):
31:  슬래시 전용: /goal(세션 목표) /status(브리핑) /scaffold(...)
```

`README.md` 는 60줄이므로 `#L26` 은 범위 안이고 링크도 열린다 → **검사기가 통과시킨다.**
이런 건 잡을 방법이 하나뿐인데, §R5 의 표본 출력(`sed -n '<n>p'`)뿐이고, 그건 전수가 아니라 표본이다.
**2차의 인용에도 같은 종류의 오차가 남아 있을 수 있다.** 확인된 것은 표본 5건×9회 = 45건뿐이다.

두 번째 한계도 이 문서를 쓰다가 드러났다 — **검사기는 인용과 "인용의 예시"를 구별 못 한다.**
위 §5 표에 1차의 깨진 태그를 예시로 적었더니 검사기가 그걸 실제 인용으로 읽고 2건을 실패시켰다.
펜스 블록으로 옮겨 회피했지만, 근본적으로는 문맥을 모르는 도구의 한계다. 3건의 `부재` 오탐도 같은 종류다.

프롬프트 A-8 이 "최종본을 어느 쪽으로 확정할지는 사용자가 정한다. 임의로 병합하지 않는다"고 했으므로, 병합하지 않았다.
정해야 할 것은 셋이다.

**① findings 최종본 — 병합 완료** ✅ (2026-08-09, 사용자 결정)
[findings.md](findings.md) 가 이제 1차·2차 병합본이다. 1차에서 D1~D6 을 `F-11`~`F-16` 으로 가져오고,

**D7(1차 오탐)은 채택하지 않고** "확인했으나 결함이 아닌 것" 절에 이유와 함께 남겼다.
심각도는 2차의 기준 하나로 다시 매겼고, 1차와 등급이 갈린 3건(F-11 · F-14 · F-15)은 그 자리에 이유를 적었다.
결과: 16항목 중 결함 13건 — 높음 2 · 중간 7 · 낮음 6.

**② 단계 문서 구조 — 7장 + `runtime.md` 로 결정** ✅ (2026-08-09, 사용자 결정)
[stages/](stages/) 7장은 그래프 노드와 1:1 로 유지하고, 1차가 별도 장으로 뒀던 **실행 주체 4종**

1차의 11장 구조는 찾기는 쉬웠지만 그 4장에 `Entry condition`·`Exit condition` 같은 단계 양식이 맞지 않았다 —

**③ 1차 잔여 링크 29건 — 고치지 않기로 했다** ✅ (2026-08-09, 사용자 결정)
