# 작업: ADAPTIVE 하네스에 결정층(decision layer) 추가 — v3.3

> **받은 그대로 둔 기록이다. 지금 도는 규칙은 `docs/references/decision-layer.md`(v3.4)다.**
> 아래에서 한 줄이 그 문서와 어긋난다 — `escalate` 는 "그대로 멈춘다"가 아니라 보류로 올리고
> 그 답에 의존하지 않는 일은 계속 한다. 실행을 실제로 막는 것은 게이트뿐이다.

## 전제

- v3.2(docs/workspace 경계 재정비) 위에서 작업한다. 이 작업이 의존하는 v3.2 산출물: `docs/references/docs-contract.md`(기계가 docs에서 파싱하는 규약의 전체 목록), 경계 검사 a·b, `gates/lib/read-spec.mjs`, LESSONS의 "v3.2 정의" 항목.
- 시작 전에 `git tag`로 v3.2 태그 존재를 확인하고, 없으면 보고만 하고 진행한다(태그는 사용자가 단다).
- 새 브랜치에서 진행한다(`v3.3-decision-layer`). merge 조건은 말미의 완료 기준 전부 충족.
- 작업 전에 이 지시 전체, 킷 루트 CLAUDE.md, docs-contract.md, LESSONS.md의 v3.2 항목 5건을 읽는다.

## 해결하려는 문제

현재 하네스는 **검증**은 자동화했지만 **결정**은 자동화하지 못했다. gate가 결과 조건을 검사하고 prober가 QA를 수행하지만, spec이 다루지 않은 잔결정(간격, 문구, 정렬, 사소한 구조 선택 등)이 나타나면 에이전트는 결정할 권한이 없어 실행을 멈추고 사람에게 묻는다. 그 결과:

1. **실행이 사람의 가용 시간에 묶인다.** 사용자가 자리를 비우면 실행이 멈춘 채 대기하고, 사용자는 실행이 도는 동안 지켜보며 기다린다. 실제 구현 소모 시간은 적은데 경과 시간은 몇 주가 된다(signal 프로젝트 실측).
2. **같은 개입이 반복된다.** 개입에서 내린 판단이 기록되지 않아 다음 사이클·다음 페이지에서 같은 질문과 수정 요청이 다시 발생한다.
3. **지시 → 결과 → 피드백 → 재지시 왕복이 과다하다.** 피드백이 반만 반영되어 왕복이 한 번 더 돌거나, 페이지 1의 지적이 페이지 2~N에서 반복 발견된다.

## 의도

개입을 금지하는 것이 아니라 **개입의 형태를 바꾼다.**

- 실행 중 사람을 기다리는 **동기 개입**을, 실행 완주 후 리포트를 읽는 **비동기 검토**로 바꾼다. 실행은 사람의 부재와 무관하게 끝까지 돈다.
- 사람의 판단 1회가 그 자리에서 소멸하지 않고 **정책 규칙으로 축적**되어 같은 종류의 개입이 재발하지 않게 한다.
- 확인의 층위를 **결정 하나하나(인스턴스)에서 규칙(방향)으로 올린다.** 사람이 통제하는 것은 방향이고, 방향은 유한한 규칙으로 표현되며, 규칙은 사이클을 거듭할수록 줄어든다.
- 사람에게 남기는 것은 되돌리기 비싼 결정, 취향 판단, 그리고 위임 범위가 넓어진 지점의 확인뿐이며, 그마저도 실행을 멈추지 않고 모아서 받는다.

## 성공 기준

- 실행 사이클 중 `auto-decide` 등급 결정으로 인한 정지: **0회**.
- 사이클 리포트의 지표 — `HUMAN` 개입 건수, `NEW` 결정 건수 — 가 사이클을 거듭할수록 **감소 추세**.
- 사용자가 자리를 비워도 실행은 보류 항목만 쌓은 채 완주하고, 사용자는 자기 시간에 리포트 하나로 검토를 끝낸다.
- 같은 유형의 피드백을 두 번 말하는 일이 없다(2회 반복 시 규칙으로 승격되므로).
- 사용자가 리포트에서 봐야 하는 것은 네 종류뿐이다: 보류 항목 / provisional 규칙 / 디자인 방향 빈칸 / 구조 변경 요약. 나머지는 읽지 않아도 실행에 영향이 없다.

2. 계획을 보고한다. 계획에 반드시 포함할 것:
   - **첫 항목은 사이클 정의다** (0절). 무엇이 사이클을 열고 닫는지가 정해지기 전에는 로그·리포트·승격 루프의 단위가 없다.
   - 파일 목록과 각 한 줄 용도
   - **각 산출물의 docs/workspace 분류**와 그 판정 근거(v3.2 판별 질문: "하네스를 바꿔도 표기만 바꿔 살아남나 / 버리고 재계산하나")
   - **docs-contract.md에 등재할 항목** — 기계가 새로 파싱하게 되는 자리 전부
   - 이 스펙이 기존 아키텍처와 충돌하는 지점 목록. **반드시 포함**: CLAUDE.md·AGENTS.md의 규칙 문장 셋(아래 "제약"의 예외 조항 참조)
   - **기준선을 지금 만들지 미룰지의 판단** (3절)
   - **`read-policy` 의 실패 방향과 그 근거** (1절)
   - **scope 어휘 → 노드 매핑이 신규 개념이라는 명시** (1절)
   - auto-pass 재시도 한도, PENDING 상한 N의 제안값
   - **4단계 분할 계획.** 각 단계가 독립적으로 merge 가능하고 그 자체로 가치가 있어야 한다:
     - **0: 두 벌 동기화 검사** (백로그 #20). A가 CLAUDE.md·AGENTS.md를 고치므로 그 전에 있어야 한다
     - A: 정책 파일 + 결정 로그 + 리포트 + 후보 대장 + 규칙 문장 수정. gate·훅 변경 없음(에이전트 규약만). 실행 흐름은 현행 유지
     - B: gate auto_pass/escalation + PENDING + Stop 훅 조정 + (판단에 따라) 기준선
     - C: 승격 루프(provisional) + 디자인 방향 빈칸 + 템플릿 변경 + 계약서 등재 마무리
     - A 완료 후 dry run으로 결정 로그·리포트가 실제로 나오는지 먼저 확인하고 B로 간다
3. 승인 대상은 이 계획뿐이며, 승인 후에는 추가 질문 없이 끝까지 구현한다. 단 계획에 없던 충돌이 구현 중 발견되면 임의 해석하지 말고 충돌 목록에 추가해 보고한 뒤 계속한다.

## 구축할 것

### 0. 사이클 — 로그·리포트·승격의 단위

**사이클 = 사용자 지시 하나.** 세션과 다른 축이다. 한 세션에 사이클이 여럿 있을 수 있고, 한 사이클이 여러 세션에 걸칠 수도 있다.

- **여는 것은 계획 승인이다.** 구현 전 계획을 보고하고 사용자가 동의하는 그 시점에 `cycle-id`를 발급해 workspace에 기록한다. 발급자를 따로 만들지 않는다 — 이 승인은 이미 하네스가 요구하는 절차이고(5절 규칙 문장 수정 후에도 유지된다), 그 자리가 곧 사이클의 시작이다.
  - **kickoff에 얹지 않는다.** kickoff은 "무엇을 만들지가 아직 합의되지 않은 상태"를 푸는 인터뷰라 프로젝트 생애에 사실상 한 번 돈다. 두 번째 지시부터는 kickoff이 돌지 않으므로 발급자가 될 수 없다.
- **닫는 것은 Stop 훅이다.** 매 턴 그래프 상태를 갱신하는 그 자리에서 종료 조건을 판정하고, 충족되면 사이클을 닫고 리포트를 발행한다. 종료 조건 셋:
  1. 프론티어의 모든 노드가 보류 항목에 의존한다 (DAG로 기계 판정. "대부분" 같은 비율 표현을 쓰지 않는다)
  2. 그래프 종단에 도달했다
  3. 사용자가 중단을 선언했다
  - 1·2는 기계가 판정한다. 3은 사용자의 말이 신호이며, 턴 종료와 구분되지 않으므로 기계가 추측하지 않는다.
- **wrap-up은 세션 축 그대로 둔다.** 사이클 경계와 섞지 않는다. wrap-up이 사이클을 닫으면, 한 세션에 지시가 셋일 때 어느 사이클을 닫는지 정해지지 않고, 사이클이 세션을 넘을 때는 미완 사이클의 리포트가 나간다.
- `cycle-id`는 세션을 넘어 이어진다. 다음 세션의 브리핑이 열린 사이클을 알 수 있어야 한다.

### 1. 결정 정책 — 결정 권한의 단일 출처

**두 층으로 둔다.**

- **킷 레벨** (`docs/references/policy/` 아래): 프로젝트와 무관한 사용자의 판단 성향. 초기 시드 규칙:
  - 트레이드오프가 크지 않으면 당장 단순한 선택보다 확장 가능성을 열어두는 선택을 한다.
  - 파일 처리 시 원본 정보(파일명 등)를 보존하는 쪽을 기본값으로 한다.
  - 한 방향 기능(예: 업로드)을 만들면 대칭 기능(다운로드)의 확장을 막지 않는 구조로 만든다.
- **프로젝트 레벨** (`projects/<이름>/docs/policy/` 아래): 그 프로젝트에서 승격된 규칙.
- 정확한 경로는 계획 단계에서 docs-contract.md와 대조해 확정한다.

**규칙 하나 = 파일 하나.** frontmatter에 기계가 읽는 필드를 두고, 본문에 규칙 서술을 둔다.

```yaml
---
id: <규칙 식별자>
scope: <중립 어휘 하나>
status: confirmed | provisional
last_applied: <cycle-id 또는 비움>
---

규칙 본문. 산문으로 자유롭게 쓴다.
```

- **본문은 파싱하지 않는다. 통째로 주입한다.** 기계가 읽는 것은 frontmatter 네 필드뿐이다.
- 이 형태를 고른 이유는 v3.2의 교훈이다 — 산문 속 파싱은 형식을 등재해도 frontmatter 파싱보다 오독 표면이 넓다(LESSONS 2026-09-02, docs-contract 5절). 이 레포가 안전하다고 판정한 형식은 frontmatter 하나뿐이다.
- 읽기 경로는 `gates/lib/read-policy.mjs` 하나로 모으고 `gates/lib/read-spec.mjs`와 같은 구조로 둔다. docs-contract에 스펙과 나란히 등재한다.

**`read-policy`의 실패 방향.** read-spec이 물려주는 것은 파싱 코드가 아니라 실패 방향이다 — "모르는 값은 항상 더 엄격한 쪽으로 떨어진다. throw 하지 않는다." 그런데 스펙의 논리가 그대로 옮겨지지 않는다: 못 읽는 규칙을 **버리면** auto-decide가 근거 없이 진행하고, **살리면** 틀린 근거로 자동 적용된다. 둘 다 나쁘다.

> **그래서 셋째 방향을 쓴다 — 못 읽는 규칙은 버리되, 그 규칙의 scope에 속하는 결정을 `escalate`로 올린다.**
> 근거 없이 진행하지도, 틀린 근거로 진행하지도 않는다. throw는 하지 않는다(오타 하나로 게이트가 죽으면 사람이 그 파일을 지워서 우회한다).

**`scope` 어휘 — 하네스 중립.**

- 값은 노드 이름이 아니라 중립 어휘다(예: `ui` · `data-model` · `api` · `copy`). 최종 목록은 계획에서 확정한다.
- **노드 이름을 쓰지 않는 이유**: 프로젝트 `docs/` 는 하네스를 바꿔도 그대로 넘어가는 폴더인데, 노드 이름은 하네스 토폴로지라 살아남지 않는다. CLAUDE.md의 분류 조항이 금지하는 "노드 글롭"이 이것이다. 현행 경계 검사 b는 문자열 목록에 노드 이름이 없어 **이 위반을 잡지 못한다** — 검사를 통과해도 위반이므로 사람이 지킨다.
- 어휘 목록은 docs-contract에 등재한다(`surfaces` 어휘와 같은 자리·같은 실패 방향).
- **어휘 → 노드 매핑은 킷이 가진다**(graph.mjs 또는 별도 매핑 파일. 위치는 계획에서 확정).
  - **이것은 신규 개념이다.** `surfaces`에는 이런 매핑이 없다 — surfaces는 "그 표면을 커버하는 approved 스펙이 있나"만 보고 노드로 옮기지 않는다. "surfaces와 같은 처리"는 어휘 등재·실패 방향까지만 선례가 있고, 매핑은 v3.3이 처음 만든다. 계획에 그렇게 적는다.

**되돌리기 비용 기준의 두 등급:**

- `auto-decide`: 되돌리기 싼 결정(간격, 문구, 정렬 순서, 네이밍, 사소한 컴포넌트 구조, 에러 메시지, 기본값). 에이전트는 정책 규칙에 따라 스스로 결정하고, 로그에 남기고, 계속 진행한다. 사람에게 묻지 않는다.
- `escalate`: 되돌리기 비싼 결정. 단독 결정 금지, PENDING으로.
  - DB 스키마, 인증 방식, 외부 API/라이브러리 선택, 데이터 모델 변경
  - sealed invariant에 닿는 것, 비용/과금 영향
  - **시각 정체성** — 새 시각 방향은 언제나 escalate다(7절)
  - 못 읽는 규칙이 걸린 scope (위 실패 방향)
  - **하네스가 사람 승인을 요구하는 상태 변경 전부**: spec status 전환(approved 등), design-rules status, 사인오프, checkpoint 통과. 이것들은 auto-decide 문구가 아무리 강해도 auto-decide 대상이 아니다.

**규칙의 주입과 위생:**

- 각 노드 컨텍스트에는 그 노드에 매핑된 scope의 규칙만 주입한다. 정책 전체 주입 금지.
- **시각 정체성 규칙 금지 조항** (7절 참조): 색·타입·간격 리듬·모션·레이아웃 성격에 관한 규칙은 킷 레벨에 둘 수 없고, 프로젝트 레벨에서도 정책 파일이 아니라 design-rules.md가 출처다. 정책 파일에 허용되는 UI 관련 규칙은 UX 패턴(폼 검증, 로딩 상태, 에러 문구 톤, 빈 상태 처리)까지다.

### 2. 결정 로그 — 사이클 단위 (`workspace/logs/DECISION_LOG.<cycle-id>.md`)

에이전트는 자신이 내린 결정을 한 줄씩 기록한다:

```
| id | node | 결정 내용 | 이유 | 기각한 대안 | 적용 규칙 id 또는 NEW / HUMAN |
```

- 정책 규칙 적용 결정은 규칙 id, 커버 규칙이 없는 결정은 `NEW`, 사람 개입은 `HUMAN`.
- **기록 하한**: 실재하는 대안이 있었고 기각 이유를 한 줄로 쓸 수 있는 결정만 기록한다. 그 미만의 미시 선택(변수명 등)은 기록하지 않는다. 로그가 검토 불가능한 크기가 되면 비동기 검토가 다시 병목이 된다.
- 로그는 사이클 산출물이다. 검토 후 보관/폐기하며 이후 에이전트 컨텍스트에 주입하지 않는다. 다음 사이클로 넘어가는 것은 승격된 규칙뿐이다.

### 3. gate 확장 — 정지 없는 auto-pass / escalation

기존 결과 조건 시맨틱을 유지한 채 필드 두 개를 추가한다.

- `auto_pass_conditions`: 전부 통과 시 사람 없이 다음 노드로 진행.
- `escalation_conditions`: 같은 prober 실패 2회 반복, dirty-flag의 sealed invariant 도달, 스코프 밖 파일 수정, `escalate` 등급 결정 조우.

**핵심 동작:**

- escalation은 실행을 멈추지 **않는다.** 항목은 사이클의 `workspace/PENDING.md`에 들어가고, 의존하지 않는 나머지 작업은 계속 진행한다.
- **PENDING은 `GATE_KIND`에 카테고리를 더하는 일이다.** Stop 훅에는 이미 같은 모양의 장치가 있다 — `downgradeReason()`이 "그래프가 처방한 상태에서 비롯된 실패"를 안내로 낮추고 턴을 끝내게 하되, 노드는 dirty로 두고 하류를 계속 막는다. PENDING도 같은 자리를 쓴다.
  - 다만 현행 두 kind(`completion`·`precondition`)는 **owner 노드의 상태를 보고** 낮출지 정한다. PENDING은 owner 상태와 무관하게 낮춰야 하므로 **세 번째 kind**가 된다. 기존 두 분기는 손대지 않고 분기 하나를 더한다.
- 조기 종료 판정은 0절의 종료 조건을 쓴다.
- auto-pass 범위의 gate 실패는 실패 출력을 포함해 자동 재시도하고, 재시도 한도(계획에서 정한 값)를 넘긴 뒤에만 escalation한다.
- **기준선**: 사이클 시작 시점의 기존 게이트 실패는 신규 위반으로 세지 않는다. auto_pass_conditions는 신규 위반 0으로 판정한다.
  - **지금 만들지는 계획에서 정한다.** 현재 게이트는 통과 중이고(신규 위반 0 = 전체 0) tsc도 두 프로젝트 다 통과라, 기준선이 없어도 auto-pass가 성립한다. 실패가 하나도 없는 상태에서 만들면 그 장치가 작동하는지 확인할 실물이 없다 — "위반 0건이라는 보고와 검사가 아예 안 돌았다는 것은 겉이 같다"(LESSONS 2026-09-02).
  - 지금 만든다면 **위반을 일부러 심어 기준선이 그것을 걸러내는 것을 보는 항목**이 검사에 있어야 한다. 그 항목을 못 만들면 C 이후로 미룬다.

### 4. 사이클 리포트 — 사이클 종료 시 발행, 비동기 검토용

순서대로. 1~4번이 사용자가 봐야 하는 전부이고, 5~7번은 참고용이다.

1. **보류 목록** — 사람 결정 대기 항목.
2. **provisional 규칙** — 이번 사이클에 자동 승격된 규칙 목록. 각 항목에 근거가 된 2건의 원문과 "뒤집기" 한 줄 방법을 병기. (6절)
3. **디자인 방향 빈칸** — design-rules.md에 근거가 없어 임시 선택한 UI 결정 목록. (7절)
4. **구조 변경 요약** — 아키텍처·데이터 모델·페이지 구성의 변화. 사용자가 실행에 개입하지 않고도 시스템 파악 상태를 유지하기 위한 섹션.
5. **NEW 결정** — 항목별로 이유·기각 대안 포함.
6. **정책 적용 결정** — 규칙 id별 건수의 접힌 요약만.
7. **지표** — `HUMAN` 건수, `NEW` 건수, PENDING 건수(상한 N 대비), provisional 뒤집기 건수.

### 5. 피드백 처리 규약

사용자가 리포트나 실물을 보고 피드백을 주면:

1. **체크리스트 변환**: 날것 피드백을 항목별 체크리스트로 변환하고, 수정 사이클의 `auto_pass_conditions`에 추가한다. 전 항목 통과 전에는 결과를 사람에게 제시하지 않는다.
2. **즉시 일반화**: 피드백 항목마다 "이것이 적용되는 프로젝트 내 다른 지점 전부"를 스스로 찾아 같은 수정 사이클에서 함께 적용한다.

### 6. 승격 루프 — 침묵-동의 방식

1. 사용자가 리포트에서 뒤집을 결정을 표시하면, 뒤집기를 dirty-flag 부분 재작업으로 적용한다.
2. 뒤집기·`HUMAN` 개입·피드백 중 같은 유형이 누적 **2회 이상**이면 **자동 승격하되 `provisional` 태그를 단다.** 다음 리포트 2번 섹션에 노출하고, 사용자가 뒤집지 않으면 그다음 사이클에 `confirmed`로, 뒤집으면 파일 삭제 + 부분 재작업. 기계 검증 가능한 유형은 prober 체크리스트 항목으로 승격한다.
   - **승격 후보 대장** (`workspace/DECISION_CANDIDATES.md`): 1회 발생한 유형과 그 원문을 기록하고, 로그와 달리 **사이클을 넘어 유지**한다. 2회 도달 시 승격하고 대장에서 제거한다. 이 대장이 없으면 사이클 1의 1회와 사이클 2의 1회를 합산할 수 없어 승격이 같은 사이클 안에서만 동작한다.
3. **provisional 규칙의 한계**: escalate 범주와 시각 정체성(7절)에는 적용될 수 없다. 이 두 영역에서는 반복이 몇 회든 자동 승격이 일어나지 않고, 승격 후보로만 제시한다.
4. 1회짜리는 승격하지 않는다.
5. 정책 위생: 유사 규칙은 넓은 규칙 하나로 병합 제안, N사이클 미적용 규칙(`last_applied` 기준)은 삭제 후보로 표시해 승인받는다. 노드별 주입 시 지시 준수율을 떨어뜨리지 않는 총량을 유지한다.

### 7. 디자인 수렴 방지

배경: 규칙은 본성상 수렴시키고, 방향이 비면 모델 기본값이 채운다. UX는 수렴해도 되지만 UI(시각 정체성)는 프로젝트마다 달라야 한다.

1. **새 시각 방향은 언제나 `escalate`다.** design-rules.md로 커버되지 않는 새 레이아웃 언어는 auto-decide 대상이 아니며, 현행 절차(design-interview → 시안 → checkpoint)가 그대로 적용된다. 이 절차를 규정하는 규칙 문장은 5절 수정 대상에서 **제외**한다.
2. **"디자인 방향 빈칸"은 승인된 방향 안의 빠진 범주에만 해당한다.** 이미 승인된 design-rules를 물려받는 화면에서, 그 문서가 다루지 않은 세부(예: 승인된 카드 언어 안에서 빈 상태의 여백)를 만났을 때다. UI 관련 auto-decide는 반드시 design-rules.md의 항목을 인용하고, 인용할 항목이 없으면 기본값으로 메우지 말고 임시 선택 + 리포트 3번 섹션에 올린다.
3. 사용자가 빈칸에 방향을 주면 그 방향은 정책 파일이 아니라 **design-rules.md에 추가**된다. 이후 같은 범주는 자동이 된다.
4. design-rules 템플릿(`docs/references/`의 정본과 각 프로젝트의 것)에 **"방향" 섹션**을 요구한다: 컨셉·무드·레퍼런스·하지 말 것. 이 섹션이 비어 있으면 UI 구현 직전 단계에서 빈칸으로 보고한다.
5. 1절의 시각 정체성 규칙 금지 조항이 이 절의 집행 수단이다.

### 8. v3.2 정합

1. **산출물 분류** (판정 근거는 v3.2 판별 질문):
   - 정책 규칙 파일(킷/프로젝트) → docs 계층. 사람 판단의 기록이며 잃으면 복원 불가.
   - 결정 로그, PENDING, 사이클 리포트, cycle-id 기록 → workspace. 사이클 산출물.
   - 승격 후보 대장 → workspace. 사이클을 넘어 유지되지만 하네스가 재계산하는 값이다.
   - 정확한 경로는 계획 단계에서 docs-contract.md와 대조해 제안.
2. **docs-contract 등재**: 정책 파일은 기계가 파싱하므로(frontmatter 네 필드) 그 필드 셋과 `scope` 어휘 목록, 그리고 design-rules "방향" 섹션의 구조를 docs-contract.md에 등재한다. 미등재 파싱 금지 규칙과 경계 검사 b를 우회하지 않는다 — 검사 b가 새 파일에 걸리면 예외를 뚫지 말고 분류가 틀린 것으로 보고 다시 판정한다.
3. 프로젝트 docs에 하네스 참조가 새로 생기지 않아야 한다(검사 b 상시 통과). **검사 b 통과가 위반 없음을 뜻하지 않는다** — 노드 이름은 검사 목록에 없어 잡히지 않으므로, 정책 파일의 `scope` 값이 중립 어휘인지는 사람이 확인한다.
4. 이전 리허설(`check-handover-rehearsal.mjs`)도 계속 3/3이어야 한다 — 프로젝트 레벨 정책 규칙이 docs에 있으니 리허설 R2에 그 복원도 추가한다.

## 제약

- **추가만 한다.** 기존 동작(DAG 오케스트레이션, gate 결과 조건, dirty-flag, sealed invariant, prober, model routing, docs/workspace 분리, docs-contract, 경계 검사)은 위 섹션이 명시적으로 확장하는 경우 외에 변경 금지.
- **예외 — CLAUDE.md·AGENTS.md의 규칙 문장은 수정 대상이다.** 이 셋은 auto-decide와 정면으로 부딪히므로 새 문서에만 답을 적으면 두 규칙이 동시에 존재하게 된다. 계획에 **문장 단위 수정안**을 포함한다.

  | 현행 조항 | 수정 방향 |
  |---|---|
  | "불확실하면 진행하지 말고 물어라. 추측 코드가 질문보다 비싸다" | 등급별 분기 — `auto-decide`는 정책 근거로 결정하고 진행, `escalate`는 그대로 멈춘다 |
  | "구현 전: 무엇을 어디에 만들지 한 문단 요약 → 동의 → 시작" | **사이클 시작의 계획 승인으로만 유지**한다(0절의 발급 시점). 사이클 안의 개별 결정에는 적용하지 않는다 |
  | "새 시각 방향(첫 화면·새 레이아웃) → design-interview → 시안 → checkpoint" | **유지.** 시각 정체성은 escalate이므로 이 절차는 그대로 산다 |

  두 파일은 같은 내용의 두 벌이라 **양쪽을 함께 고친다.** 동기화 검사가 없는 채로 두 벌을 고치면 어긋난 것을 아무도 모른다 — 그래서 0단계가 A보다 앞이다.
- 스킬·규칙 문서를 고칠 때는 `.claude/` 와 `.agents/` 두 벌 모두 고친다.
- 새 문서는 기존 하네스 문서와 같은 한국어로 작성한다. 파일명·필드명·태그(`auto-decide`, `escalate`, `NEW`, `HUMAN`, `provisional`, `confirmed` 등)는 영어 유지.
- 어떤 에이전트 컨텍스트에도 로그 전체·정책 전체를 주입하지 않는다.
- 보호 파일(게이트·훅·LESSONS 등)은 킷 규칙대로: 적용 전 실패 / 적용 후 통과 검사 스크립트를 동봉한 패치로 제출하고 사용자가 적용한다. 검사 스크립트에는 v3.2 교훈 ②·④를 적용한다 — 프로브를 심어 검사가 실제로 그 경로를 밟았음을 확인하고, 각도가 다른 검사를 둘 이상 둔다.
- 단계별 커밋 분리. 시작 시 미커밋 작업 트리가 있으면 먼저 보고한다(v3.2 교훈 ⑤).

## 완료 기준

1. 실제 프로젝트(signal2)의 구현 단계 사이클 하나를 dry run했을 때:
   - 계획 승인 시점에 `cycle-id`가 발급되어 workspace에 기록된다
   - 태그 달린 결정 로그와 4절 형식의 사이클 리포트가 생성된다
   - `auto-decide` 결정으로 인한 정지 0회
   - 보류 항목이 실행을 막지 않고 PENDING에 수집된다
   - 종료 조건 1(프론티어 전부 보류 의존)이 기계로 판정되어 Stop 훅이 사이클을 닫고 리포트를 발행한다
2. 피드백 체크리스트가 수정 사이클의 auto_pass 조건으로 들어가 동작한다.
3. 승격 루프: 2회 반복된 결정 유형이 provisional로 정책 파일에 들어가고, 다음 리포트에 노출되며, 뒤집기로 삭제 + 재작업이 일어난다. escalate 범주와 시각 정체성에서는 자동 승격이 일어나지 않음을 프로브로 확인한다.
4. 디자인 방향 빈칸: 승인된 design-rules에 근거 없는 UI 결정이 리포트 3번 섹션에 올라오고, 방향을 주면 design-rules.md에 추가되는 것을 확인한다. 새 시각 방향은 빈칸이 아니라 escalate로 떨어지는 것을 프로브로 확인한다.
5. `read-policy`의 실패 방향 확인: 어휘 밖 값이 든 규칙 파일을 심으면 그 규칙이 버려지고 해당 scope의 결정이 escalate로 올라간다. 지우면 다시 통과한다.
6. 두 벌 동기화 검사가 CLAUDE.md↔AGENTS.md, `.claude/skills/`↔`.agents/skills/`의 어긋남을 잡는다. 한쪽만 고친 상태를 심어 잡히는 것을 본다.
7. 기존 검사 전부 통과: run-gates(신규 위반 0), check-read-spec 8/8, check-docs-boundary 7/7, check-handover-rehearsal(R2에 정책 복원 추가 후) 전부 통과.
8. docs-contract.md에 새 파싱 규약이 전부 등재되어 있고, 킷 문서에 v3.3 정의 한 줄이 있다: "이 버전부터 auto-decide 등급 결정은 실행을 멈추지 않으며, 사람의 판단은 provisional 규칙으로 축적된다."
