# 하네스 설계도 — 구조·루프 조건·작업 순서의 정본

> 지위: 이 문서는 하네스의 목표 구조와 보강 순서의 정본이다.
> 백로그·대기열 문서에서 ①~⑤, "필터", "책임 표", "판단 지점" 같은 용어가
> 가리키는 것은 이 문서의 정의다.
> 갱신 규칙: 구조나 순서를 바꾸는 결정이 있을 때만 사람이 갱신한다.

---

## 1. 목표 구조 (파이프라인 관점)

작업 하나가 지나가는 경로와, 그 경로를 지탱하는 기록 파일 두 개.

```
                          ┌─────────────[책임 표]──────────────┐
                          │ (검사 항목 목록)                    │
                          ↓ 표대로 검사                         │ 기준 밖 결함 승격
                                                               │ (사람 승인 필수)
[방향 결정] → [생성 루프] → [필터] ──(통과 상위만)──→ [승인] ──┘
  사람           ①~④        게이트                      사람
    ↑                                                    
    └──[LESSONS]←── 루프가 작업 중 발견을 즉시 기록 ──────┘
        다음 작업 시작 시 읽음
```

- **방향 결정** (사람): 무엇을 만들지 정하고 스펙·판정 기준을 쓴다.
- **생성 루프**: 설계·구현·테스트를 에이전트가 반복한다. 아래 ①~④가
  이 루프가 실제로 도는 조건이다.
- **필터** (게이트): 책임 표에 적힌 항목을 자동 검사하고, 통과분 중
  상위만 사람에게 올린다. 검사 내용의 출처는 책임 표뿐이다.
- **승인** (사람): 내보낼지 판단한다. 판단 중 발견한 "표에 없는 결함"은
  책임 표 승격 후보로 올린다 (사람 승인 후 표에 추가).
- **요청량 제한**: 필터 통과분과 승격 후보 모두 사람에게 올라가는
  개수에 상한을 둔다. 사람에게 오는 판단 요청의 총량을 제한하는 장치다.

기록 파일 두 개는 성격이 다르다:

| | LESSONS | 책임 표 |
|---|---|---|
| 내용 | 환경 특이사항 (예: 새 테이블 insert는 RLS 정책 없이는 401) | 검사 항목 목록 (노드↔스킬 바인딩에서 확장) |
| 쓰는 쪽 | 루프 (발견한 그 턴에 즉시) | 승인 (사람 승인을 거쳐서만) |
| 읽는 쪽 | 다음 작업의 에이전트 | 필터 (매 검사마다) |
| 추가 절차가 다른 이유 | 틀려도 다음 실행이 교정한다 | 틀리면 필터가 영구히 잘못 검사한다 |

## 2. 생성 루프의 조건 ①~⑤ — 정의와 판정

루프가 "에이전트가 만들고, 스스로 확인하고, 스스로 고치는" 반복이 되기 위한
조건. 번호는 백로그·대기열 문서에서 이 정의를 가리킨다.

### ① 실행 — 있음
에이전트가 코드 수정 후 typecheck·lint·테스트를 스스로 돌리고, 통과 전에는
완료 보고를 하지 않는다. 게이트로 강제되어 있다.
- 판정: 실행 없이 완료 보고하는 경로가 게이트에 막히는가. **현재 통과.**

### ② 관측 — 있음 (2026-09-15)
브라우저에서만 보이는 실패(콘솔 에러, 실패한 네트워크 요청)를 에이전트가
터미널에서 읽을 수 있게 하는 스크립트. Playwright 기반, 입력은 URL(필요 시
클릭할 요소), 출력은 콘솔 로그·실패 요청·스크린샷 경로. 판정은 하지 않는다
(판정용 QA는 별도, 이것은 수시 확인용이므로 가볍고 빨라야 한다).
- 판정: 페이지에서 발생한 401 같은 실패가 사람 개입 없이 에이전트의
  터미널 출력에 나타나는가. **현재 통과** — `node scripts/probe.mjs <URL>`.
  첫 실전 실행에서 서버 컴포넌트의 `fetch failed`와 그것이 만든 500을
  한 번에 집어냈다(2026-09-15).
- 1순위였던 이유: ②가 없으면 루프의 자가 수정이 돌지 않고, 돌지 않는 루프는
  ③④를 갖춰도 의미가 없다.
- 남은 것: 클릭 경로가 깊어지면 `--click`을 여러 번 주는 것으로는 부족해진다.
  그때 무엇이 필요한지는 ③·④와 같이 실전 투입 뒤에 정한다.

### ③ 왕복 속도 — 만들 것 (2순위)
수정 한 번마다 확인해도 부담 없는, 초 단위의 좁은 범위 확인 명령.
(예: 해당 테스트 파일만, 해당 페이지만.) 실패 메시지는 원인을 가리키게
작성한다 (상태 코드만이 아니라 응답 본문 포함).
- 판정: 방금 만진 것만 확인하는 명령이 있고 초 단위에 끝나는가.
  실패 메시지만 읽고 다음 수정 방향을 정할 수 있는가.
- 확인이 느리면 에이전트는 수정 여러 번을 묶어 한 번만 확인하게 되고,
  어긋난 코드 위에 다음 코드를 쌓는 구간이 길어진다.

### ④ 실험 공간 — 만들 것 (3순위)
망가뜨려도 명령 하나로 초기 상태 복구가 보장되는 로컬 환경.
로컬 DB + seed 스크립트 + 리셋 명령. 복구가 보장되면 마이그레이션
작성·실행·실패·재작성까지 에이전트에게 맡길 수 있다.
- 판정: 리셋 명령 하나로 초기 상태(스키마 + seed 데이터)로 돌아가는가.
- ④가 없으면 DB 작업이 "사람이 직접" 지점으로 루프 안에 남는다.

### ⑤ 지식 축적 — 있음
예상과 다르게 동작한 지점을 발견한 그 턴에 LESSONS에 한 줄 기록한다.
회고 때 몰아 쓰면 세션이 끊겼을 때 유실되므로 기록 시점이 규칙이다.
- 판정: 이번 세션의 발견이 기록되어 다음 세션이 같은 시행착오를
  반복하지 않는가. **파일은 있음. 기록 시점 준수는 계속 확인.**

②→③→④ 순서의 근거: ②가 없으면 루프가 안 돌고, 루프가 안 도는 상태에서
속도(③)는 의미가 없으며, 확인이 느린 상태에서 허용 범위(④)만 넓히면
느린 왕복이 많아질 뿐이다.

## 3. 작업 순서 — 닫힌 목록과 대기열

### 투입 전 (닫힌 목록, 순서 고정)

1. report-dashboard 제작 — 완료 (transitions.jsonl·바인딩 파일·그래프 밖 표기 포함)
2. 계약 테스트 규약 — 완료
   - 규칙 등재 — check-report.mjs가 1호. 부품(스킬·훅·게이트 스크립트) 수정은
     merge 전 자기 계약 테스트 재통과가 조건. 신규 부품은 계약 테스트 없이 등록 불가.
   - 배선 — node-skills.json의 `contract`가 배선을 들고 있다. 값은 검사 경로 /
     `none: <사유>` / `pending: <백로그 항목 조각>` 셋 중 하나이고 `null`은 금지다.
     `contract`가 경로인 스킬은 그 디렉터리가 바뀐 턴에 검사가 자동으로 돌고,
     `pending`인 스킬을 고친 턴에는 게이트가 막는다(미루기는 손대기 전까지만 유효하다).
     형식 정본은 docs/references/docs-contract.md 8절.
3. 대시보드 UI 개편 — 완료
4. ② probe 제작 — 완료. scripts/probe.mjs(관측만 하고 판정하지 않는다) +
   계약 테스트 scripts/check-probe.mjs
5. 실전 투입 — 다음

이 목록에는 항목을 추가하지 않는다. 새 아이디어는 대기열로 보낸다.

### 투입 후 (대기열 — 순서는 착공 신호가 정한다)

| 항목 | 착공 신호 |
|---|---|
| ③ 왕복 속도 | transitions.jsonl의 노드별 체류 시간 집계가 ③ 부족을 가리킬 때 |
| ④ 실험 공간 | 위 집계가 ④ 부족을 가리킬 때 (③과 동일 데이터로 판단) |
| 라이프사이클 뷰 | ③·④ 우선순위 판단을 위해 집계가 필요해지는 시점 (집계 = 이 뷰) |
| 책임 표 승격 고리 | 같은 종류의 기준 밖 결함이 사람에게 두 번째 도달할 때 |
| report-brief | 보고 피로가 실측될 때 |
| 에이전트 평가 (고정 과제 세트) | 다음 하네스 대수술 직전 (수술 전후 비교가 목적).<br>과제 세트 정의는 투입 직후, 투입한 작업 중 대표를 박제 |
| LESSONS 관리 규칙 (정제·폐기) | 세션 시작 로딩이 실측으로 무거워지거나,<br>틀린 기록이 오답을 만든 사례가 나올 때 |

대기열 항목은 착공 신호가 오기 전에 만들지 않는다. 신호 없이 만드는 것은
문제가 확인되지 않은 곳에 장치부터 세우는 것이다.

## 4. 전체 완성 판정

구조가 목표대로 작동하는지는 다음 두 문장으로 판정한다.

1. 작업 하나(예: 게시글에 좋아요 기능 추가)가 사람 개입 정확히 두 번
   (방향 결정 한 번, 승인 한 번)으로 끝난다. 세 번째 개입이 발생하면
   그 지점이 다음 보강 대상이다.
2. 같은 종류의 기준 밖 결함이 사람에게 두 번 도달하지 않는다.
   두 번 도달하면 책임 표 승격 고리의 고장이다.

## 5. 용어

- **파이프라인**: 작업 하나가 지나가는 처리 순서 (graph.mjs의 노드들).
  지나가는 것은 작업/데이터다.
- **라이프사이클**: 일 하나가 시작부터 끝까지 거치는 국면.
  지나가는 것은 일/프로젝트다. 킷 수리는 파이프라인 밖의 일이며,
  대시보드에서 "그래프 밖"으로 표기한다.
- **판단 지점**: 사람이 판단에 책임을 지는 두 곳 (방향 결정, 승인).
  생성 비용이 떨어져도 판단 비용은 떨어지지 않으므로, 하네스의 목표는
  이 두 지점의 판단을 (a) 적게 (필터·요청량 제한), (b) 싸게 (비교 자료·
  판정 결과 표시) 만드는 것이다.
- **기준 밖 결함**: 책임 표에 없어서 필터가 잡지 못하고 승인까지 올라온
  결함. 없앨 수는 없고, 승격 고리로 "한 번만 겪는 것"으로 만든다.
