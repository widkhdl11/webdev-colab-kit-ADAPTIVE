판정 레이어는 보호 파일이라 직접 못 고친다. 아래를 직접 적용하고, 판정기로 확인하면 된다.

**이미 적용된 것이 있다.** 이 패치가 요구하는 것 중 판정 레이어 밖의 변경(`scripts/check-hooks.mjs`)은
그쪽이 보호 파일이 아니라 그대로 반영했다. 남은 것은 판정 파일 둘뿐이다.

```

run-gates.patched.mjs      →  <판정 폴더>/run-gates.mjs
```


**적용 전에는 실패하고 적용 후에는 통과한다.** 실측한 적용 전 결과:

```
✗ A1 · 패치가 적용됐다 — spec-coverage.mjs 에 DUP_SCENARIO 검사가 없다 — 미적용

✓ B2 · 검사기가 --wiring-only 를 안다
✓ B3 · 지금 훅 배선이 성하다
✓ B4 · 심은 위반(상대 경로 훅)을 잡는다 — 실패로 신고했다

3/5 통과   (종료 코드 1)
```

**A3·B4 는 위반을 일부러 심어 잡히는 것을 본다.** 「위반 0건」이라는 보고와 검사가 아예 안 돈
것은 겉이 같기 때문이다. A3 은 승인된 스펙에 시나리오 줄 하나를 복사해 넣고 게이트가 그 번호를
이름으로 대며 죽는지 보고 원상복구한다. B4 는 상대 경로 훅이 든 가짜 저장소를 만들어 검사기를
거기서 돌린다 — 진짜 `settings.json` 은 안 건드린다.

## A. 시나리오 ID 유일성 (`spec-coverage.mjs`)

### 무슨 일이 있었나

`write-authorization.md` 에 `S14` 가 **두 번** 있었다. 하나는 INV-Z13(프로필 가시성), 하나는
INV-Z12(판정 함수 노출)를 가리켰다.

시나리오 번호는 테스트 이름에 담기는 규약이고(`INV-Z13 ④-1 (S16): …`), 사람이 「그 시나리오에
검사가 있나」를 확인할 때 쓰는 **유일한 손잡이**다. 번호가 겹치면 그 확인이 두 계약을 뭉갠다 —
한쪽 검사를 지워도 「S14 검사가 있다」는 결과가 그대로 나온다.

**기계는 끝까지 몰랐다.** `spec-coverage` 는 `INV-[A-Z0-9]+` 만 세고 시나리오 번호는 안 본다.
리뷰어 둘이 독립적으로 지적해서 잡혔다.

### 무엇이 달라지나

승인된 스펙 파일마다 `- S<숫자>…` 로 시작하는 줄의 번호를 세고, **한 파일 안에서 겹치면**
그 번호를 이름으로 대며 종료 코드 2 로 죽는다.

- **커버리지는 요구하지 않는다.** 시나리오는 불변식 하나를 여러 각도에서 쪼갠 것이라 개수가
  판단이다. 「시나리오마다 테스트」를 강제하면 반대 절반을 한 검사에 묶는 것이 위반이 된다.
- **`approved` 만 본다.** 초안에서 번호가 겹치는 것은 쓰는 중이고, 승인되는 순간 — 그 번호가
  계약의 손잡이가 되는 순간 — 걸린다.
- **인용은 안 센다.** 줄 맨 앞의 `- S…` 만 정의로 본다(불변식 앵커와 같은 규칙).

### 지금 저장소에서 미리 돌려 본 결과

같은 구조를 임시 폴더에 만들어 패치본을 그대로 돌렸다:

```
① 깨끗한 상태     → 종료코드 0
② 중복을 심은 상태 → 종료코드 2
   [spec-coverage/DUP_SCENARIO] …/write-authorization.md — 시나리오 S1 가 2 번 나온다.
③ 원상복구        → 같다
```

정규식이 실제 스펙 열둘에서 뽑는 번호도 확인했다 — `S7-1` 같은 하이픈 번호를 놓치지 않고,
`Supabase` 같은 낱말을 시나리오로 오인하지 않는다.

### 등재

`docs/references/docs-contract.md` 2절에 **먼저 등재했다**(그 문서의 자체 규칙이다 — 거기 없는
파싱을 게이트에 추가할 수 없다). 등재 이력에 「강제하는 게이트는 이 패치에 있다」고 적혀 있으니,
적용하면 그 줄도 같이 고쳐 주기 바란다.

## B. 훅 배선을 게이트로 올린다 (`run-gates.mjs`)

### 무슨 일이 있었나

2026-09-06 에 훅 일곱이 통째로 죽어 있었다. 명령이 상대 경로였고, 세션 작업 폴더가
`projects/<이름>` 으로 옮겨가자 Node 가 파일을 못 찾았다.

**훅 실패는 non-blocking 이라 도구는 그대로 실행된다.** 시크릿·보호 파일·위험 명령 차단과
편집 게이트와 Stop 훅이 한꺼번에 조용히 꺼졌는데 겉모습이 똑같았다. 화면에 뜬 오류 줄을
사람이 알아봐서 잡혔고, **그것 말고는 알아차릴 방법이 없었다.**

### 무엇이 달라지나

전체 게이트 실행(`--quick` 아님)에서 `scripts/check-hooks.mjs --wiring-only` 를 돌리고,
실패하면 그 줄을 `[hooks/WIRING]` 으로 게이트 오류에 올린다.

- **`--wiring-only` 로 부른다.** 그냥 부르면 검사기가 훅 프로세스를 오십 번 넘게 띄운다.
  느린 게이트는 결국 빠지고, 그러면 이 자리를 다시 아무도 안 보게 된다.
- **`--quick` 에는 안 넣는다.** `settings.json` 은 보호 파일이라 편집으로 바뀌지 않는다.
- **검사기가 없거나 못 돌면 ⚠ 로 건너뛴다.** 부분 적용 상태가 편집을 막지 않게.

`scripts/check-hooks.mjs` 쪽 변경은 **이미 반영했다**(보호 파일이 아니다):

| 무엇 | 왜 |
|---|---|
| `--wiring-only` 모드 | 정적 판정만 — 배선·등록·파싱 |
| 배선 검사 + 심은-위반 프로브 | 훅 명령의 스크립트 경로가 절대 경로이고 실제로 있는가 |
| `hookScriptName()` | 파일명 뽑기가 `split("/").pop()` 이라 **따옴표 친 절대 경로에서 깨져 있었다** — 훅 셋이 멀쩡히 도는데 "등록 안 됨"으로 보고했다 |

## 부분 적용 조합 — 넷 다 확인했다

패치가 파일 둘을 고치므로 한쪽만 붙은 상태가 실제로 생길 수 있다. **어느 조합에서도 안전하게
실패한다** — 둘은 서로를 안 부르고 각자 검사를 하나씩 더할 뿐이다.

| A(spec-coverage) | B(run-gates) | 그때 무슨 일이 | 위험한가 |
|---|---|---|---|
| ✗ | ✗ | 지금 상태. 시나리오 번호도 훅 배선도 아무도 안 본다 | 아니오(오늘까지의 상태) |
| ✓ | ✗ | 시나리오 번호만 본다. 훅 배선은 계속 사람이 기억해야 잡힌다 | 아니오 |
| ✗ | ✓ | 훅 배선만 본다. 시나리오 번호는 계속 리뷰어가 잡아야 한다 | 아니오 |
| ✓ | ✓ | 의도한 상태 | — |

**B 에는 조합이 하나 더 있다** — `scripts/check-hooks.mjs` 가 낡아서 `--wiring-only` 를 모르는
경우다. 그때 검사기는 그 인자를 무시하고 **전체 모드로 돌아** 훅 프로세스를 오십 개 띄운다.
느려지지만 판정은 맞고, 게이트가 틀린 답을 내지는 않는다. 판정기의 **B2** 가 이 조합을 잡는다.
이 저장소에서는 이미 반영돼 있어 해당 없다.
