# 불변식 커버 판정이 프로젝트를 안 가른다 (보호 파일 1개)

## 무슨 일이 났나

`study-mate` 의 인증 스펙을 `approved` 로 올렸다. 그 스펙에는 불변식이 넷 있고 테스트는
**하나도 없다.** 그런데 추적성 게이트가 통과했다.

원인:

- 게이트는 `projects/*/docs/specs` 에서 승인된 스펙의 INV id 를 모으고,
  `projects/*/src` · `projects/*/tests` 의 테스트 파일을 **전부 한 덩어리 문자열로 합친 뒤**
  그 안에 id 문자열이 있는지 본다.
- **INV id 는 스펙 파일 안에서만 고유하다.** 프로젝트가 다르면 같은 id(`INV-A1` …)를 쓰는 것이
  정상이다.
- 그래서 `wama/tests/inv/auth-isolation.integration.test.ts` 가 자기 프로젝트의 `INV-A1`~`A4` 를
  검증하는데, 그 문자열이 `study-mate` 의 `INV-A1`~`A4` 까지 덮었다.

실측:

```
study-mate 의 INV-A1 을 참조하는 테스트:
    projects/wama/tests/inv/auth-isolation.integration.test.ts
(A2·A3·A4 도 같다)
```

**"승인된 스펙은 불변식마다 그것을 참조하는 테스트가 요구된다"는 이 저장소의 핵심 약속인데,
프로젝트가 둘 이상이면 그 약속이 조용히 사라진다.** 프로젝트가 하나뿐일 때는 드러날 수 없다.

## 무엇을 고치나

판정의 키에 프로젝트를 붙이고, 테스트 본문도 프로젝트별로 나눠 본다. 스펙을 읽는 방식도
테스트를 찾는 방식도 그대로다 — 바뀌는 것은 **누구의 테스트가 누구의 불변식을 덮는가**뿐이다.

## 사용자가 붙일 것 — `gates/spec-coverage.mjs` 세 자리

### ① 지도를 만들기 직전에 헬퍼 둘을 더한다

**찾을 것**:

```js
const invToSpec = new Map();
```

**바꿀 것**:

```js
// INV id 는 스펙 파일 안에서만 고유하다. 프로젝트가 둘 이상이면 다른 프로젝트가 같은 id
// (INV-A1 등)를 쓰는 것이 정상이라, 테스트를 전부 한 덩어리로 합쳐 이름만 찾으면 **남의
// 프로젝트 테스트가 내 불변식을 덮는다.** 2026-09-04 에 실제로 그랬다 — 새 프로젝트의 승인된
// 스펙 불변식 넷이 테스트 0개인 채로 다른 프로젝트의 동명 테스트에 덮여 통과했다.
// 그래서 키에 프로젝트를 붙이고, 테스트 본문도 프로젝트별로 나눠 본다.
const projectOf = (p) => {
  const m = relative(ROOT, p).split("\\").join("/").match(/^projects\/([^/]+)\//);
  return m ? m[1] : "";
};
const KEY = (proj, inv) => `${proj}\u0000${inv}`;
const invToSpec = new Map();
```

### ② 지도에 넣을 때 키에 프로젝트를 붙인다

**찾을 것** (한 줄):

```js
  for (const m of src.matchAll(/^[ \t]*-[ \t]+(INV-[A-Z0-9]+)[ \t]*:/gm)) invToSpec.set(m[1], relative(ROOT, f));
```

**바꿀 것**:

```js
  for (const m of src.matchAll(/^[ \t]*-[ \t]+(INV-[A-Z0-9]+)[ \t]*:/gm)) invToSpec.set(KEY(projectOf(f), m[1]), relative(ROOT, f));
```

### ③ 테스트 본문을 프로젝트별로 나눠 대조한다

**찾을 것**:

```js
const testText = testFiles.map((f) => stripComments(readFileSync(f, "utf-8"))).join("\n");

const missing = [...invToSpec.entries()].filter(([inv]) => !testText.includes(inv));
if (missing.length > 0) {
  for (const [inv, spec] of missing)
    console.error(`[spec-coverage/MISSING_TEST] ${spec} — ${inv}를 검증하는 테스트가 없다. 구현 전에 테스트부터 (rules/tdd.md)`);
```

**바꿀 것**:

```js
const textByProject = new Map();
for (const f of testFiles) {
  const k = projectOf(f);
  textByProject.set(k, (textByProject.get(k) ?? "") + "\n" + stripComments(readFileSync(f, "utf-8")));
}

const missing = [...invToSpec.entries()].filter(([key]) => {
  const [proj, inv] = key.split("\u0000");
  return !(textByProject.get(proj) ?? "").includes(inv);
});
if (missing.length > 0) {
  for (const [key, spec] of missing)
    console.error(`[spec-coverage/MISSING_TEST] ${spec} — ${key.split("\u0000")[1]}를 검증하는 테스트가 없다. 구현 전에 테스트부터 (rules/tdd.md)`);
```

(그 아래 `process.exit(2); }` 는 그대로 둔다.)

## 판정 — 코드를 안 읽고 확인하는 법

```
node scripts/check-inv-scope.mjs
```

| | 무엇 | 붙기 전 | 붙은 뒤 |
|---|---|---|---|
| A | 내 프로젝트에 테스트가 없으면 남의 동명 테스트로 덮이지 않는다 | **실패** | 통과 |
| B | 자기 프로젝트 테스트가 참조하면 통과한다 | 통과 | 통과 |
| C | 패치를 적용한 **사본**에서 A 가 통과하고 B 도 유지된다 | 통과 | (생략) |

**붙기 전 2/3 → 붙은 뒤 3/3 · exit 0** 이면 붙은 것이다.

- **B 가 A 와 각도가 다르다.** 이 패치는 게이트를 **조이는** 변경이라 실패 방향이 과차단이다.
  A 만 보면 "전부 막는" 고장난 패치도 초록불이다.
- **C 가 핵심이다.** 보호 파일이라 붙기 전에는 A 를 통과시킬 수 없다. C 는 패치를 적용한 사본을
  임시 폴더에 만들어 같은 판정을 돌린다 — 검사가 들고 있는 치환과 이 문서의 치환이 같다.
- 픽스처는 프로젝트 둘을 만든다. 한쪽에 승인된 스펙(`INV-A1`)이 있고 테스트는 없고,
  다른 쪽에 같은 id 를 참조하는 테스트가 있다. 그게 이 결함의 최소 재현이다.

## 붙인 뒤 무엇이 달라지나 — 미리 알 것

**`spec-coverage` 가 실패하기 시작한다.** `study-mate` 의 승인된 인증 스펙에 불변식이 넷 있고
그 프로젝트에는 테스트가 없기 때문이다. **이건 결함이 아니라 방벽이 처음으로 제대로 도는 것이다.**

- `spec-coverage` 는 "끝내기 전에 있어야 한다" 성격의 게이트라 **턴을 막지 않는다.**
  안내로 낮춰지고, `spec` 노드가 dirty 가 되어 그 아래(구현·검증·리뷰·배포)가 닫힌다.
- 프론티어가 `review` 에서 `spec` 으로 돌아온다. 지금 그래프가 `review` 를 가리키는 것은
  **거짓말이다** — 승인된 계약의 불변식 넷이 검증되지 않았는데 검증 단계를 지났다고 말하고 있다.
- 푸는 방법은 하나뿐이다: `study-mate` 에 `INV-A1`~`A4` 를 참조하는 테스트를 쓴다.
  인증을 구현할 때 그 테스트를 먼저 쓰면 된다.

## 부분 적용 조합

파일 둘을 고친다. `scripts/check-inv-scope.mjs` 는 보호 파일이 아니라 **커밋으로 먼저** 들어가고,
`gates/spec-coverage.mjs` 만 사용자가 붙인다.

| 조합 | 상태 | 무슨 일이 일어나나 |
|---|---|---|
| ① 둘 다 없음 | 패치 전 | 구멍이 열린 채다. 프로젝트가 둘 이상이면 불변식 커버가 이름만 맞으면 통과한다 |
| ② `scripts/` 만 | **이 커밋 직후** | 검사가 2/3 로 실패한다(exit 2). 이 검사를 부르는 훅이 없으므로 **턴을 막지 않는다.** 손으로 돌렸을 때만 빨간불이고, 그게 "게이트를 붙여라"라는 뜻이다 |
| ③ `gates/` 만 | 이 커밋을 받기 전에 게이트만 고쳤을 때 | 구멍은 닫힌다. 닫혔다는 근거만 없다 |
| ④ 둘 다 | 패치 후 | 검사 3/3 · exit 0. `spec-coverage` 는 study-mate 때문에 실패하기 시작한다(위 참조) |

**어느 조합에서도 안전하게 실패한다.** ③ 이 위험하지 않은 이유는 이 패치가 게이트를 **조이는**
변경이라서다 — 잘못 붙으면 과차단으로 드러나고, 과차단은 조용하지 않다.

## 막혔을 때 빠져나오는 길

```
node --check gates/spec-coverage.mjs     # 문법만 본다
git checkout gates/spec-coverage.mjs     # 패치 전으로 되돌린다(커밋 전이라면)
```

패치를 붙인 뒤 `spec-coverage` 실패가 부담스러우면, 되돌리는 것 말고 **스펙을 `parked` 로
내리는 길**도 있다 — 그러면 그 스펙의 불변식은 요구되지 않는다. 다만 `parked` 는 그 표면을
커버하지 않으므로, 인증 코드를 쓰려면 다시 `approved` 로 올려야 하고 그때 테스트가 요구된다.
