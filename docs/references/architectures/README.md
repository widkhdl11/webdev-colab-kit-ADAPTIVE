# 아키텍처 프로파일 — 정본

검증된 프로젝트 구조를 하나씩 쌓아두는 곳. setup에서 하나를 고르면 폴더 구조·게이트 함의·기본 libs가
딸려온다(매번 재발명 금지). 프로젝트가 쌓일수록 이 폴더가 두꺼워지는 게 정상이다.

- [vite-fsd.md](./vite-fsd.md) — 킷 기본형. SPA, 화면은 `src/pages`
- [nextjs-fsd.md](./nextjs-fsd.md) — Next App Router. 화면은 `src/app`, `pages` 레이어 없음

---

## 게이트가 스택을 가정할 때의 규칙 (새 프로파일을 추가하기 전에 반드시 읽는다)

게이트는 전역이다. **모든 프로젝트가 같은 판정 코드를 지나간다.** 그런데 "화면이 어디 사는가",
"진입점이 무엇인가", "무엇이 부트스트랩인가"는 **스택마다 다르다.** 이 둘이 만나는 자리가
이 킷에서 가장 조용히 깨지는 지점이다.

### 이미 한 번 겪은 일

`design/BEFORE_UI`는 "화면 = `src/pages`·`src/widgets`"라는 가정을 코드에 **숨긴 채** 박아뒀다.
Vite 프로젝트만 있을 때는 맞는 말이었다. Next(App Router)를 들이자 화면이 `src/app`으로 옮겨갔고,
게이트는 **아무 소리 없이 통과했다** — 막아야 할 것을 안 막는 상태가 실패로 보이지 않았다.
반대로 고치면서 `src/app` 규칙을 전역에 걸 뻔했는데, 그러면 이번엔 Vite 프로젝트가
근거 없는 예외("라우트 화면 1장은 스켈레톤")를 뒤집어쓴다. **양쪽 다 조용한 오작동이다.**

### 그래서 지키는 것

1. **스택마다 갈리는 규칙은 가정을 코드에 숨기지 말고, 먼저 판정하고 분기한다.**
   게이트 안에 판정 함수를 두고(`isNextProject()` 같은), 규칙은 그걸 통해서만 갈라진다.
   판정 근거는 **설정 파일 존재 여부**처럼 확실한 것으로 (`next.config.*`).
   추측(폴더 이름이 이러니까 Next겠지)으로 갈라내지 않는다.
2. **분기의 기본값은 "가정을 적용하지 않음"이다.** 판정에 실패하면 스택 전용 규칙을 걸지 않고
   공통 규칙만 적용한다. 새 스택이 들어와도 **잘못 막지는 않는다**(못 막는 건 아래 3으로 잡는다).
3. **못 막는 구멍은 프로파일 문서의 "게이트 함의"에 적는다.** 게이트가 커버하지 못하는 것을
   적어두지 않으면, 그 스택을 쓰는 다음 세션은 게이트 통과를 "안전하다"로 읽는다.
   각 프로파일 문서의 그 절은 **선택이 아니라 필수**다.
4. **규칙에 예외를 둘 땐 그 예외가 어느 스택의 사정에서 나왔는지 주석에 남긴다.**
   ("App Router는 `page.*` 없이는 404라서" 처럼) 근거 없는 예외는 다음 사람이 지우지도 지키지도 못한다.

### 새 프로파일을 추가할 때 (setup에서 새 스택을 채택했을 때)

`gates/run-gates.mjs`를 훑으며 아래를 확인하고, 결과를 새 프로파일 문서의 "게이트 함의"에 적는다.
게이트는 보호 파일이라 **수정은 제안만** 하고 사용자가 반영한다.

- [ ] **화면 판정** — `design/BEFORE_UI`가 이 스택의 화면 파일을 트리거로 보는가?
      (못 보면 강제가 통째로 사라진다. 조용히 통과하므로 안 찾으면 모른다)
- [ ] **레이어 판정** — FSD 레이어 이름·경로가 이 스택과 충돌하지 않는가?
      (예: Next Pages Router의 `src/pages`는 FSD `pages` 레이어와 이름이 겹친다)
- [ ] **부트스트랩 파일** — 진입점·프로바이더·전역 스타일이 "화면"으로 오인되지 않는가?
      (오인하면 프로젝트 시작 단계에서 과차단된다)
- [ ] **타입체크·테스트 실행** — 게이트가 부르는 명령(`tsc --noEmit`, `npm test`)이 이 스택에서 그대로 도는가?
      (Next처럼 빌드 전제가 있으면 우회가 필요할 수 있다 — nextjs-fsd의 `next-env.d.ts` 수동 생성 사례)
- [ ] **보안 게이트** — 이 스택의 관용구가 금지 패턴에 걸리는가? 걸린다면 대안을 스펙에서 정한다
- [ ] 위에서 스택별 분기가 필요해졌다면 **판정 함수를 통해 갈라지게** 제안한다(위 1번)

### 아직 안 한 것 (다음에 손댈 때 같이)

지금은 스택 판정이 `isNextProject()` 하나로 흩어져 있다. 스택이 셋 이상 되면
`projectProfile(projDir) → "nextjs-fsd" | "vite-fsd" | ...` 하나로 모으고, 스택별로 갈리는 규칙은
전부 그걸 통하게 하는 편이 낫다. 덧붙여 **게이트 요약 줄에 판정된 프로파일을 찍으면**
("2개 프로젝트: signal=nextjs-fsd, wama=vite-fsd") 가정이 매 실행마다 눈에 보여서,
오판정이 조용히 지나가지 않는다. 스택이 셋째로 늘어날 때 승격 검토.
