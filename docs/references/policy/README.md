# 결정 정책 — 규칙 하나 = 파일 하나

여기 있는 것은 **사용자의 판단 성향**이다. 되돌리기 싼 결정을 사람에게 묻지 않고 내릴 때
그 근거가 되는 문장들이고, 근거로 쓸 규칙이 없으면 결정하지 않고 보류로 올린다.

이 폴더는 킷 레벨이다 — 어느 프로젝트에서나 같은 성향. 프로젝트에서 승격된 규칙은
`projects/<이름>/docs/policy/` 에 따로 쌓인다.

## 형식

```yaml
---
id: open-for-extension          # 파일명과 같게 둔다
scope: [data-model, api]        # 이 규칙이 근거가 되는 영역
status: confirmed               # confirmed | provisional
last_applied: signal2-20260903-1  # 마지막으로 이 규칙을 근거로 쓴 사이클. 처음엔 비운다
---

규칙 본문. 산문으로 자유롭게 쓴다.
```

**기계가 읽는 것은 frontmatter 네 필드뿐이고, 본문은 파싱하지 않는다.** 본문은 통째로
읽는 쪽에 넘어간다. 본문에서 값을 긁어내는 규약을 새로 만들지 않는다 — 형식을 문서에
등재해도 산문 속 파싱은 frontmatter 파싱보다 오독 표면이 넓다(docs/LESSONS.md 2026-09-02).

어휘와 실패 방향의 정본은 `docs/references/docs-contract.md` 다.

## 왜 파일 하나에 규칙 하나인가

한 파일에 규칙을 여럿 담으면 "어느 규칙이 어느 영역에 붙는가"를 본문에서 다시 갈라야 하고,
그 순간 본문이 파싱 대상이 된다. 파일을 나누면 그 갈라내기를 파일 시스템이 한다.

그리고 규칙은 지워지기도 한다 — 사용자가 뒤집으면 파일 하나를 지우면 끝이고, 한 파일 안의
한 블록을 도려내는 것보다 되돌리기 쉽다.

## 규칙을 늘리는 방법

여기에 손으로 쓰지 않는다. 같은 판단이 두 번 반복되면 `provisional` 로 자동 승격되고,
사용자가 뒤집지 않으면 `confirmed` 가 된다. 1회짜리는 승격하지 않는다.

아래 세 개만 예외다 — 사용자가 직접 준 시드다.

## 총량

규칙이 늘어나면 각 결정 자리에 주입되는 양이 늘고, 어느 지점부터는 지시가 묽어져
규칙이 있으나 마나가 된다. 그래서 위생 규칙이 둘 있다.

- 비슷한 규칙 여럿은 넓은 규칙 하나로 병합을 제안한다.
- 오랫동안 `last_applied` 가 갱신되지 않은 규칙은 삭제 후보로 올린다.

둘 다 제안이고, 지우는 것은 사용자가 정한다.
