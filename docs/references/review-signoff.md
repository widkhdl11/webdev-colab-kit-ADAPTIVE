# review 사인오프 — 표면별 리뷰어와 `reviewers:` 규약

CLAUDE.md 에서 내려온 문서다(2026-09-04). 상시 들고 있을 이유가 약한 이유는 하나다 —
`review` 가 프론티어가 되면 graph-stop 이 매 턴 무엇이 모자란지 찍어준다. 즉 이 문서를
읽어야 하는 국면에 트리거가 기계로 존재한다.

## 무엇을 기록하나

리뷰어 통과 = 그래프의 `review` 노드를 clean 으로 만드는 것이다. 통과하면
`workspace/review.md` 에 네 줄을 기록한다.

```yaml
project: <프로젝트명>
status: passed
basis: <해시>                      # graph-stop 이 매 턴 화면에 찍어준다
reviewers: [실제로 돌린 리뷰어]
```

구현이 바뀌면 basis 불일치로 review 가 자동으로 낡는다(재리뷰 강제).
review 가 dirty 인 동안 `deploy` 는 차단된다.

## `reviewers:` 가 필수인 이유

basis 해시는 graph-stop 이 화면에 찍어주는 값이라, **그것만 검사하면 리뷰를 돌린 것과
두 줄을 적은 것이 구분되지 않는다.**

그리고 risk-surface 게이트가 코드에서 `auth`·`payment`·`authz` 를 감지했는데 `reviewers` 에
security-reviewer 가 없으면 사인오프를 거부한다 — 파견 판단은 모델에게 있지만, 보안 표면을
그냥 지나친 기록은 기계가 잡는다.

ux-reviewer 도 실제로 돌렸으면 `reviewers:` 에 적는다. 이것을 요구하는 게이트는 없다 —
위의 security-reviewer 필수 판정만 기계가 본다.

얕은 qa(테스트)는 매 턴 자동 clean 이고, 깊은 리뷰는 이 기능-완성 마일스톤에만 파견한다
(잦은 리뷰 방지).

## 시험을 언제 어디까지 돌리나 (2026-10-12 사용자 지시)

- **구현·리뷰 반영 중에는 관련 시험만 돌린다.** 관련 시험은 바꾼 모듈을 import 하는 시험과
  바꾼 DB 테이블을 건드리는 시험 전부다. 좁게 고르지 않는다.
- **전체 통합 시험은 묶음 사인오프 때 한 번 돌린다.** 문제집(여러 묶음) 끝까지 미루지 않는다.
  그 명령과 결과 숫자를 review.md 「실행 근거」에 적는다.
- 변이(강제 장치를 지워 빨간불 보기)는 이 규칙과 별개다. 범위를 줄이지 않는다.

이유: 구현 한 번 61분 가운데 통합 전체 실행이 10분이었고, 바꾼 곳과 관계없는 시험까지 돌았다.
대신 다른 기능을 건드린 회귀는 사인오프 때 드러난다 — 그래서 사인오프의 전체 실행은 건너뛰지 않는다.
지시 양식: [subagent-brief.md](subagent-brief.md).

## 리뷰가 잡은 회귀를 어디까지 고치나 (2026-09-17 사용자 지시)

> **이번 diff 가 만든 회귀는 diff 이전 동작으로 되돌리는 것까지가 범위다.**
> 그 과정에서 드러난 기존 결함은 백로그로 보낸다. 근본 수정은 별도 요청으로 받는다.

이 문장이 없어서 한 번 넘어갔다. 2026-09-16 에 좋아요가 조회수를 클릭마다 부풀리는 회귀를
리뷰가 잡았는데, 되돌리는 것(집계 호출을 원래 자리로)과 근본을 고치는 것(조회수가 무엇을
세는 숫자인지 다시 정하기)이 구별되지 않아 **스펙 하나와 기능 하나가 요청 밖에서 만들어졌다.**

가르는 기준은 하나다. **diff 이전에도 있던 동작이면 기존 결함이고, 이 diff 가 만들었으면
회귀다.** 위 사례에서 「그리는 코드가 조회수를 올린다」는 diff 이전부터 있었고, 이 diff 는
그것을 **반복 가능하게** 만들었을 뿐이다 — 되돌릴 범위는 그 반복이지 구조가 아니다.

선택지를 사용자에게 올릴 때 **「지금 안 고친다」를 빼지 않는다.** 고치는 방법만 늘어놓으면
고르는 사람에게 범위를 좁힐 자리가 없다.

## 표면별 리뷰어

리뷰어 하나하나가 특정 표면에 붙어 있다. 닿지 않은 표면의 리뷰어는 읽을 것이 없어
지적도 못 한다 — 파견하지 않는다.

| 리뷰어 | 언제 파견하나 |
|---|---|
| `security-reviewer` | 사용자 입력·인가·시크릿·세션을 만진 diff 에 |
| `ux-reviewer` | 상태·노출·입력 구조가 바뀐 diff 에(UX 명세가 있는 화면만). 파견 순서는 ui-reviewer 앞 — 없어질 요소의 시각 기준을 재는 일을 막는다 |
| `ui-reviewer` | 승인된 design-rules 에서 벗어나는 시각 변경에(새 컴포넌트·레이아웃·토큰) |
| `code-reviewer` | 도메인 로직·상태 관리가 바뀐 diff 에 |
| `test-auditor` | 스펙 INV 를 검증하는 테스트를 새로 쓴 뒤에("이 테스트를 지워도 잘못된 구현이 통과하나") |

→ 통과하면 review 마커를 기록한다. **어느 리뷰어를 왜 뺐는지는 한 줄로 알린다** —
뺀 판단도 보고 대상이다.
