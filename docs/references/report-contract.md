# 진행 기록 계약 — 대시보드가 읽고 쓰는 파일 전부

`projects/<이름>/report/` 아래 파일들의 스키마와 기록 규칙이다. 여기 없는 필드를 읽거나 쓰는
코드를 추가하려면 이 문서에 먼저 등재한다.

## 왜 `docs-contract.md` 가 아니라 여기인가

`docs-contract.md` 는 **프로젝트 `docs/` 에서 기계가 읽는 것**의 목록이다. 그 폴더는 하네스를
바꿔도 그대로 넘어가는 프로젝트 지식이고, 그래서 그 문서는 다음 하네스에 해석 명세로 함께 간다.

`report/` 는 그 반대다. 노드 이름·전환 이력·툴 호출 기록은 **이 하네스가 어떻게 굴러갔는지**의
기록이라, 하네스를 바꾸면 버리고 새 하네스가 자기 모양으로 다시 만든다. 그것을 `docs-contract`
안에 넣으면 그 문서가 "다음 하네스에 넘길 것"과 "지금 하네스의 사정"을 같이 들고 있게 되고,
그 순간 그 문서의 전제가 깨진다.

그래서 규약은 여기 두고, `docs-contract.md` 5절에서 이 문서를 가리킨다.

**이 문서가 정하는 것은 파일에 들어가는 값이지 화면에 찍히는 글자가 아니다.** 화면이 쓰는 말은
`docs/references/devtool-ui-standards.md` 8절이 따로 정한다 — 예를 들어 여기서 「체류 시간」이라
부르는 것을 화면은 「걸린 시간」으로 적는다. 다만 파일에 그 글자로 들어 있는 값
(`status` 의 `승인 대기`, `result` 의 `통과`·`반려`, 노드 이름)은 화면에서도 그대로 쓴다.

## 1. `workflow.json` — 워크플로우 구조

거의 변하지 않는다. `graph.mjs` 선언에서 `scripts/export-workflow.mjs` 가 파생한다.
**손으로 고치지 않는다** — 선언과 어긋나면 계약 테스트가 잡는다.

```json
{
  "nodes": [{ "id": "design/page-designer", "label": "page-designer", "kind": "child",
              "parent": "design", "skills": ["checkpoint", "design-interview"] }],
  "edges": [{ "from": "product", "to": "spec" }],
  "skills": [{ "name": "checkpoint", "nodes": ["design/page-designer"] }]
}
```

`kind` 어휘 넷:

| 값 | 무엇 |
|---|---|
| `root` | 상류가 없는 노드 |
| `step` | 보통 노드 |
| `aggregate` | 자식이 있는 노드. 자기 산출물 없이 자식이 모두 clean 이라야 clean |
| `child` | `aggregate` 의 자식. `parent` 필드를 갖는다 |

엣지 방향은 상류 → 하류다. 자식은 부모로 들어간다(자식이 clean 이라야 부모가 clean).

`skills` 는 노드마다 하나, 그리고 파일 최상위에 목록으로 하나 — **같은 바인딩을 두 방향에서 본
것이다.** 노드 쪽은 지도가 읽고, 목록 쪽은 사이드바가 읽는다. 출처는 하나뿐이다:
`docs/references/node-skills.json`(형식은 docs-contract 8절). 어느 쪽도 손으로 쓰지 않는다.
최상위 `skills[].nodes` 에는 `"all"` 이 그대로 들어간다 — 그 스킬은 사이드바에서 「상시」로 묶인다.

## 2. `state.json` — 현재 위치 (덮어쓰기)

```json
{
  "session_id": "문자열",
  "current_node": "workflow.json 의 노드 id 중 하나, 또는 null (제품 그래프 밖)",
  "task": "스펙/task 식별자",
  "now": "사람이 읽는 한 줄. 80자 이내",
  "since": "ISO8601 — 이 상태가 시작된 시각",
  "blockers": [{ "id": "문자열", "label": "사람 입력 대기 항목" }],
  "skill": "지금 실행 중인 스킬 이름, 없으면 null",
  "delay_reason": "지금 항목이 오래 걸리는 이유 한 줄(80자 이내), 없으면 null",
  "off_graph": "current_node 가 null 일 때만 — 무슨 작업인지 한 줄"
}
```

- 필수 필드는 여덟(`session_id`·`current_node`·`task`·`now`·`since`·`blockers`·`skill`·`delay_reason`).
  `off_graph` 만 조건부다(아래).
- `now` 는 **80자 이내 한 줄**이다. 산문 보고를 쓰는 자리가 아니다 — 넘으면 기록이 거부된다.
- `current_node` 가 `workflow.json` 에 없는 값이면 위반이다.
- **`current_node` 는 `null` 일 수 있다 = 제품 그래프 밖의 일을 하는 중.** 킷(`scripts/` ·
  `.claude/` · `docs/references/`)을 고치는 것처럼 어느 노드의 산출물도 아닌 작업이 그렇다.
  그럴 때 지도에서는 아무 상자도 빛나지 않고, 상단에 `off_graph` 의 한 줄이 뜬다.
  **`null` 이면 `off_graph` 가 필수이고, 노드가 있으면 `off_graph` 는 금지다** — 빈칸으로 두면
  「그래프 밖」과 「안 적었다」가 구별되지 않는다.

  왜 노드 이름을 하나 골라 적지 않나: 그러면 지도가 틀린 상자를 빛낸다. 2026-09-14 에 실제로
  그랬다 — 킷 작업을 하면서 `qa` 라고 적었고, 같은 시각 그래프는 「전부 clean, 프론티어 없음」
  이었다. 모른다고 말할 자리가 없으면 아무 값이나 들어가고, 그 값은 틀렸다는 신호를 어디에도
  안 남긴다.
- `blockers` 가 비어 있지 않으면 화면은 그 노드를 「사람 입력 대기」로 구분해 그린다.
- `skill` 은 **언제나 있는 필드**다. 안 쓰는 중이면 `null` 이다 — 빠뜨림과 구별해야 해서
  없는 것은 위반이다. 값이 있으면 바인딩에 있는 이름이어야 하고, 화면은 그 스킬을 초록으로
  칠한다. **앞 상태에서 물려받지 않는다** — 안 주면 「스킬을 안 쓰는 중」이다. 물려받게 하면
  끝난 스킬이 화면에서 계속 초록으로 남고, 그건 틀렸다는 신호가 아무 데도 안 뜨는 종류다.
- 노드 상자의 색 우선순위는 **사람 입력 대기 > 스킬 실행 중 > 그냥 여기** 다. 대기가 제일 위인
  이유는 셋 중 그것만이 사람이 해야 할 일이기 때문이다.
- **`delay_reason` 은 지금 항목의 체류가 임계(11절)를 넘은 뒤 에이전트가 적는 자기 신고다.**
  `skill` 과 같이 **언제나 있는 필드**이고 안 적었으면 `null` 이다.
  - 쓰는 시점: 임계를 넘은 뒤 첫 `state.json` 갱신. 80자 이내 한 줄이고, 넘으면 기록이 거부된다.
  - **항목이 바뀌면 `null` 로 돌아간다.** 사람이 지우는 것에 맡기지 않고 `report-note.mjs` 가
    직전 전환의 `item` 과 비교해 기계로 되돌린다.
  - **이 값은 판정 근거가 아니라 대조용이다.** 화면은 이것을 기계 집계 다섯 옆에 나란히 놓을
    뿐이고, "무엇 때문에 늦었다"는 결론을 내리지 않는다. 대조는 사람이 한다.

## 3. `transitions.jsonl` — 전환 이력 (한 줄씩 덧붙이기)

```json
{ "at": "ISO8601", "from_node": "문자열|null", "to_node": "노드 id|null", "task": "식별자",
  "now": "한 줄", "result": "문자열|null", "item": "요청 항목 label|null",
  "blockers": [{ "id": "문자열", "label": "사람 입력 대기 항목" }] }
```

- `from_node` 는 첫 전환에서만 `null` 이다. `to_node` 는 `null` 일 수 있다(그래프 밖 구간).
- `result` 는 **task 가 끝나는 전환에만** 채운다(`통과` · `반려` · `실패` 같은 값). 그 외에는 `null`.
  「직전에 무엇이 끝났나」의 유일한 출처가 이 필드다 — 활동 기록으로 완료를 추측하지 않는다.
- `now` 에도 80자 제한이 그대로 적용된다.
- `item` 은 이 전환이 속한 **요청 항목의 label** 이다. 요청의 `items` 에 없는 값이면
  「요청 밖 작업」이고, 그 판별은 여기서 하지 않는다 — 요청 기록과 대조해야 알 수 있어서
  요청 층이 한다. 항목과 무관한 전환(그래프 밖 작업 등)은 `null`.
- `blockers` 는 **그 시점의 `state.blockers` 사본**이다. `state.json` 은 덮어쓰기라 과거가 남지
  않아서, "blocker 가 언제 생겨서 언제 풀렸나"를 계산할 자리가 이 이력밖에 없다. 빈 배열에서
  비지 않은 배열로 바뀐 줄이 발생이고, 그 반대가 해소다.
  - **필드가 아예 없는 줄은 이 필드가 생기기 전(2026-09-15 이전)의 기록이다.** 빈 배열(= blocker
    없음)과 다르므로 스키마가 요구하지 않고, 화면은 그런 구간을 「0분」이 아니라 「기록 없음」으로
    구분해 그린다. 모르는 것이 0 으로 보이면 그건 틀렸다는 신호가 안 뜨는 종류다.
- `result` 가 정확히 `실패` · `반려` 인 줄만 지연 진단의 「검사 실패 반복」으로 센다. `result` 는
  자유 문자열이라 부분 일치로 세면 「반려 아님」 같은 값까지 걸린다 — 어휘를 늘리려면 여기에 먼저 적는다.
- 노드별 체류 시간은 이 줄들의 `at` 간격에서 계산한다. 마지막 줄은 지금 시각까지로 친다.
- **비어 있는 과거를 나중에 채워 넣지 않는다.** 2026-09-15~17 은 기록이 멈춰 있던 구간이고
  (전환 0건), 그 구간은 그대로 둔다. 「기록 없음」이 정직한 상태다 — 기억으로 복원한 줄은
  실제 체류 시간이 아니라 **나중에 지어낸 숫자**이고, 한 번 섞이면 어느 줄이 측정이고 어느
  줄이 추정인지 다시 갈라낼 방법이 없다. 하네스의 판정(왕복 속도·개입 횟수)이 그 숫자를
  근거로 쓰므로, 지어낸 값 하나가 판정 전체를 못 믿을 것으로 만든다.
- **`at` 은 뒤로 가지 않는다.** 앞 줄보다 이른 시각은 기록이 거부된다. 뒤로 가면 「마지막
  전환」의 뜻이 둘로 갈린다 — 짝 검사는 파일의 마지막 줄을 보고, 화면은 시간순으로 정렬한
  마지막 줄을 본다. 둘이 다른 줄을 가리키면 어느 쪽도 못 믿는다.
- **줄과 줄은 이어져야 한다.** 첫 줄의 `from_node` 는 `null` 이고, 그 뒤로는 `from_node` 가
  앞 줄의 `to_node` 와 **정확히 같아야** 한다 — `null` 끼리도 그대로 비교한다. 그래프 밖
  구간이 이어지는 것은 정상이고, 「qa 에 도착했는데 다음 줄이 아무 데서도 출발 안 함」은 끊김이다. 이것이 「이력 한가운데가 끊긴 것」을 잡는 유일한 검사다 —
  짝 검사는 마지막 한 줄만 보므로 가운데의 끊김을 그냥 통과시킨다.
- 그래서 **현재 위치의 출처는 `state.json` 이 아니라 이 파일이다.** 다음 줄의 `from_node` 는
  `state.current_node` 가 아니라 **마지막 전환 줄의 `to_node`** 에서 온다. `state.json` 만
  지워진 상태(둘 다 커밋 대상이 아니라 흔한 모양)에서 state 를 근거로 삼으면 `from_node` 가
  `null` 인 줄이 한가운데에 붙는데, 그 줄은 마지막 줄과 state 가 정확히 맞아떨어져서
  짝 검사를 통과한다.

## 4. 기록 시점과 **쌍 규칙**

기록하는 시점은 셋뿐이다: **노드 전환 · task 시작/종료 · blocker 발생/해소.** 그 외에는 기록하지 않는다.

> `state.json` 을 쓰는 시점마다 `transitions.jsonl` 에도 한 줄을 쓴다.
> 두 기록은 **항상 쌍으로** 이뤄지며, 한쪽만 기록되는 코드 경로가 있어서는 안 된다.

이 규칙을 사람의 주의력에 맡기지 않는 방법이 둘이다.

1. **쓰는 자리를 하나로 둔다.** `scripts/report-note.mjs` 의 함수 하나가 두 파일을 같이 쓴다.
   다른 자리에서 `state.json` 을 쓰지 않는다는 것을 계약 테스트가 검사한다.
2. **깨진 짝을 판정할 수 있게 만든다.** `state.current_node` 는 마지막 전환의 `to_node` 와 같아야
   하고, `state.since` 는 마지막 전환의 `at` 과 같아야 한다. 다르면 한쪽만 기록된 것이다.

어겼을 때 무슨 일이 일어나나: 화면은 멀쩡해 보이는데 체류 시간과 「직전 완료」가 조용히 틀린다.
에러가 아니라 **그럴듯한 화면**이 나오므로, 보고 있어도 모른다.

### 누가 기록하나 — 노드는 기계가, 의미는 사람이 (2026-09-17)

기록에는 경로가 둘 있고, **각자 책임지는 필드가 다르다.**

| 경로 | 언제 | 채우는 것 |
|---|---|---|
| Stop 훅 (`scripts/turn-transition.mjs`) | 턴이 끝날 때마다 | `to_node` 만. 위치가 바뀌었을 때만 한 줄 |
| 손 기록 (`scripts/report-note.mjs`) | 사람/에이전트가 부를 때 | `task`·`now`·`item`·`result` 같은 의미 필드 |

훅이 쓰는 줄의 `task`·`now` 는 **지어내지 않는다** — 마지막 손 기록의 값을 그대로 싣는다.
`item` 은 마지막 전환 줄에서 물려받고, `result` 는 언제나 `null` 이다(무엇이 끝났는지는
훅이 알 수 없다). 손 기록이 한 번도 없으면 `task: "기록-없음"` 이 들어간다 —
그 자리는 스키마가 빈 값을 허용하지 않아서 비워 둘 수 없다.

**쓰기는 여전히 한 자리다.** 훅도 `report-note.mjs` 의 `note()` 를 부른다. 위의 1번 규칙은
그대로 살아 있다.

**주 노드 규칙.** 한 턴에 여러 노드의 산출물이 바뀌면(스펙을 고치면서 구현도 고친다)
**위상 순서상 가장 뒤**를 그 턴의 위치로 적는다. 상류를 적으면 이미 지나온 자리에
머무는 것으로 보인다.

**같은 노드에 머무는 턴은 줄을 안 늘린다.** 체류 시간은 줄과 줄 **사이**라서, 한 노드 안에서
열 번 고쳤다고 열 줄이 생기면 그 노드의 체류가 0초 열 개로 쪼개진다.

**제품이 그대로고 킷만 고친 턴**은 `to_node: null` 로 적고 `state.off_graph` 에 무슨 파일을
고쳤는지 채운다(활동 기록에서 뽑는다). 뽑지 못하면 `"미기재"` 로 남고, 그 값이 남아 있으면
다음 턴에 게이트가 사유 한 줄을 요구한다.

#### `turn-hashes.json` — 대조용 메모 (사람이 읽는 파일이 아니다)

```json
{ "at": "ISO8601", "hashes": { "노드 id": "해시|null" } }
```

턴과 턴 사이를 비교하려고 훅이 남기는 스냅샷이다. **기록이 아니다** — 지우면 다음 턴에
다시 생기고, 그 한 턴만 전환이 안 적힌다. 이 파일이 따로 필요한 이유는 `HANDOFF.md` 의
해시가 「마지막으로 clean 이 됐을 때」의 값이어서, 그것과 대조하면 dirty 인 동안 아무것도
안 고친 턴까지 「바뀐 것」으로 잡히기 때문이다.

### 항목마다 전환 줄 하나 — `통과` 와 `done` 은 쌍이다 (2026-09-17)

요청 항목(`request.json` 의 `items`)을 닫을 때는 **두 자리를 같이** 적는다.

1. 그 항목으로 전환 한 줄: `--item "<label>" --result 통과`
2. 항목 자체: `report-request.mjs --done <id>`

한쪽만 남으면 화면의 `n/m` 과 이력이 서로 다른 말을 하고, 어느 쪽이 맞는지 아무도 모른다.
**`반려`·`실패` 는 쌍을 요구하지 않는다** — 그렇게 끝난 항목은 닫힌 것이 아니다.

요청이 열려 있는 동안 그래프 안 전환의 `item` 은 비울 수 없다. 요청 밖 작업이면 `items` 에
없는 이름을 적는다 — `null` 은 「밖」이 아니라 「잊었다」이고, 그 줄의 시간은 어느 항목의
체류에도 안 들어간다.

이 셋(어휘·쌍·`item` 빈칸)은 `scripts/lib/record-rules.mjs` 가 판정하고 게이트가 막는다.
`result` 어휘의 코드 쪽 정본도 그 파일의 `RESULT_VOCAB` 다 — 늘리려면 여기 3절과 그 상수를
같이 고친다.

## 5. `activity.jsonl` — 활동 기록 (훅이 덧붙이기)

```json
{ "at": "ISO8601", "tool": "툴 이름", "target": "대상 경로 또는 명령 (200자로 자름)", "session_id": "문자열" }
```

- `.claude/hooks/report-activity.mjs` 가 PostToolUse 에서 쓴다. **모델 컨텍스트에는 아무것도 넣지 않는다.**
- 날이 바뀌면 어제치가 `activity-<YYYY-MM-DD>.jsonl` 로 옮겨진다. 화면은 `activity.jsonl` 만 읽는다.
- 이 훅은 실패해도 조용히 끝낸다(exit 0). 관찰하려고 넣은 것이 관찰 대상을 망가뜨리면 안 된다.
- 훅이 안 붙어 있으면 이 파일은 빈 채로 있고, 1·2층만으로 대시보드는 그대로 돈다.

## 6. `request.json` — 현재 요청 하나 (덮어쓰기)

```json
{
  "task": "state.json·transitions.jsonl 의 task 와 같은 식별자",
  "request": "사람이 시킨 문장 원문. 요약·재해석 금지",
  "goal": "이 요청의 목표(왜) 한 줄, 없으면 null",
  "source": "spec | manual",
  "spec_path": "source 가 spec 이면 스펙 경로, 아니면 null",
  "items": [{ "id": "문자열", "label": "문자열", "done": false }],
  "status": "진행 중 | 승인 대기 | 완료 | 중단",
  "status_reason": "승인 대기·중단이면 사유, 아니면 null",
  "started_at": "ISO8601",
  "ended_at": "ISO8601 | null"
}
```

### `goal` — "왜"는 "무엇"과 다른 칸이다

`request` 는 사람이 시킨 문장("무엇")이고 `goal` 은 그것을 왜 하는지다. 스펙이나 `Intent.md` 에
목표 절이 있으면 거기서 옮기고, 없으면 시작할 때 사람이 말한 한 줄을 적는다.

**요청 문장에서 지어내지 않는다.** 스펙에도 없고 사람도 말하지 않았으면 `null` 이고, 화면은
「기록 없음」으로 그린다. 지어내면 화면이 사람이 말한 적 없는 목표를 사람의 목표로 보여 주는데,
그건 틀렸다는 신호가 아무 데도 안 뜨는 종류다.

`goal` 도 `skill`·`delay_reason` 과 같이 **언제나 있는 필드**다(모르면 `null`).

### 범위는 시작 시점에 얼어붙는다 — 이 규약의 핵심

> 요청을 시작할 때 `items` 를 기록하고, **그 뒤로 `items` 는 `done` 말고 아무것도 바뀌지 않는다.**

**배열의 순서도 함께 얼어붙는다.** `items` 의 순서 = 시작 시점에 정한 작업 순서이고, 화면의
단계 띠가 그 순서를 그대로 그린다. 진행 중 재배열하면 띠는 "무엇을 어떤 순서로 하기로 했나"를
더는 말해 주지 않는다 — 그래서 기록 스크립트가 재배열도 거부한다(`done` 만 바꿀 수 있다).
순서에 확신이 없으면 질문 목록에 올리되 기록은 한다. 순서 없는 기록은 없다.

시작 후 새로 생긴 일은 항목에 추가하지 않는다. 전환의 `item` 에 `items` 에 없는 이름을 적으면
그것이 곧 「요청 밖 작업」이고, 화면이 그렇게 분류한다.

**파생 판별은 판단이 아니라 「시작 목록에 있었나」의 기계 대조다.** 시작 후 목록을 고칠 수
있으면 "요청 밖으로 나갔나"라는 질문 자체가 성립하지 않는다 — 나간 것을 목록에 넣는 순간
안 나간 것이 되기 때문이다. 기록 스크립트가 변경 시도를 거부한다.

### `items` 의 출처

| `source` | 어디서 오나 |
|---|---|
| `spec` | 스펙의 **불변식 정의 앵커**(`- INV-…:`, docs-contract 2절). 스크립트가 옮긴다 |
| `manual` | 시작 시 사람/에이전트가 요청 문장을 항목으로 쪼개 적는다 |

불변식을 쓰고 시나리오를 안 쓰는 이유: 시나리오는 한 불변식을 여러 각도로 쪼갠 것이라 개수가
작성자의 판단이다. 진행률의 분모가 판단에 따라 흔들리면 그 숫자를 못 믿는다.

### 기록 시점

- 요청 시작 시 `request.json` 작성
- 항목 완료 시 그 `item.done` 갱신
- 스킬 실행 시작·종료 시 `state.skill` 갱신
- 승인 대기 발생 시 `status`·`status_reason` 갱신 (`blockers` 와 함께)
- 요청 완료·중단 시 `status`·`ended_at` 갱신 후 이력으로 옮긴다

요청이 완료·중단되면 `request.json` 내용을 그대로 한 줄 덧붙이고 `request.json` 은 지운다.

## 8. `subagents.jsonl` — 서브에이전트 (훅이 덧붙이기)

```json
{ "at": "ISO8601", "event": "start | end", "agent": "에이전트 이름", "brief": "지시문 첫 줄 80자" }
```

- `.claude/hooks/report-subagent.mjs` 가 쓴다. **모델 컨텍스트에는 아무것도 넣지 않는다.**
- `start` 뒤에 `end` 가 없는 것이 실행 중이다.
- `brief` 는 지시문 첫 줄을 자른 것이다. **요약하지 않는다** — 요약하려면 모델을 불러야 하고,
  그러면 화면에 LLM 이 끼어든다.
- **등록된 에이전트 목록의 출처는 `.claude/agents/` 의 실제 파일이다.** `workflow.json` 의
  `agents` 로 실려 나온다. 화면 코드에도 스크립트에도 이름을 박지 않는다 — 박으면 에이전트를
  더한 사람이 그 목록을 안 고쳐서 화면에서만 조용히 빠진다.

## 11. `config.json` — 프로젝트별 임계값

```json
{ "dwell_threshold_min": 30, "activity_gap_min": 10 }
```

| 키 | 뜻 | 기본 |
|---|---|---|
| `dwell_threshold_min` | 한 항목에 이만큼(분) 넘게 머물면 「임계 초과」 | 30 |
| `activity_gap_min` | 활동 기록이 이만큼(분) 이상 끊기면 「활동 공백」 | 10 |

- 파일이 없거나 값이 숫자가 아니거나 0 이하면 **그 칸만** 기본값으로 돌아간다. 기본값의 출처는
  `report/render.mjs` 의 `DEFAULT_REPORT_CONFIG` 하나뿐이다 — 두 벌 두면 화면과 검사가 다른
  기본값을 쓴다.
- **임계는 고정값 하나다.** 항목별·노드별 임계, 예상 시간 추정, 자동 학습은 하지 않는다.
  추정한 값과 실제가 어긋나면 화면이 틀린 것을 자신 있게 말하게 된다. 필요해지면 대기열로.

### 왜 `docs-contract.md` 가 아니라 여기인가

이 임계값은 프로젝트 지식이 아니라 **이 대시보드의 사정**이다. 하네스를 바꾸면 화면과 함께
버려진다. 그래서 `report/` 의 다른 파일과 같은 자리에 등재한다(이 문서 맨 위의 이유가 그대로
적용된다). `docs-contract.md` 5절이 이 문서를 가리킨다.
