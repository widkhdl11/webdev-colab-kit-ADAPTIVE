# 대기열 — 대시보드 라이프사이클 층 (task 여정 뷰)

**착공 조건: 실전 투입 후, ③(왕복 속도)·④(실험 공간)의 우선순위를 정하려고
`transitions.jsonl` 집계가 필요해지는 시점.** 그 전에는 실행하지 않는다.

①~⑤의 정의와 이 항목이 대기열 어디에 있는지는 `docs/references/harness-design.md` 가 정본이다.

집계를 일회성 스크립트로 만들지 말고 이 뷰로 만들어 두 일을 하나로 합친다 —
같은 계산을 두 번 구현하면 화면과 보고서가 다른 숫자를 말하게 된다.

---

## 목표

기존 지도가 「지금 어느 노드에 있나」(현재)를 보여준다면, 이 층은 「task 하나가 전체 여정 중
어디까지 왔고 어디에 오래 머물렀나」(여정)를 보여준다.

**새 기록은 만들지 않는다.** `transitions.jsonl` 의 집계만으로 그린다.
LLM 비관여 제1 제약은 이 층에도 그대로 적용된다.

## 데이터

- 입력은 `transitions.jsonl` 하나. 기록 스키마 변경 없음, 새 필드 없음.
- 집계 단위: `task` 필드로 전환들을 묶는다.
- 렌더 로직이 계산하는 값:
  - task 별 지나온 노드 순서와 각 노드 체류 시간 (연속한 `at` 의 차이)
  - 역방향 전환 횟수 (뒤 노드 → 앞 노드로 되돌아간 것 = 반려 왕복)
  - `result` 가 채워진 전환의 위치와 값 (통과/반려/실패)
  - 진행 중 여부 (`state.json` 의 `task` 와 대조)
- 집계는 순수 함수로 분리해 node 단위 테스트가 가능해야 한다.
- **파생 데이터 파일을 만들지 않는다.** 집계 결과를 파일로 저장하는 순간 원본과 어긋날 수 있는
  사본이 생긴다. 원본은 하나다.

## 렌더링

- 위치: 워크플로우 지도 아래, 활동 피드 위.
- task 한 줄 = 가로 진행 막대.
  - 지나온 노드 구간을 순서대로 이어 그린다. 구간 폭은 체류 시간에 비례하되 **최소 폭을
    보장한다**(짧은 구간도 라벨이 읽히게).
  - 각 구간에 노드명과 체류 시간을 표기한다.
  - **역방향 전환은 색이 아니라 표시로** 나타낸다(구간 사이 되돌아감 표기 + 횟수).
    상태를 색으로만 구분하지 않는다는 기존 규칙이 이 층에도 적용된다.
  - `result` 의 실패·반려가 기록된 지점을 라벨로 표시한다.
  - 진행 중 task 는 마지막 구간이 열린 상태 + 「진행 중」 라벨.
  - `current_node` 가 `null` 이었던 구간은 **「그래프 밖 작업」** 구간으로 구분해 그린다.
- 완료된 task 는 기본 접힘 (최근 N개만 표시, 펼치기 제공).
- **노드별 합산 요약을 층 상단에** 표시한다: 전체 task 를 합산한 노드별 체류 시간을 큰 순서로.
  이 수치가 ③·④ 우선순위 결정의 근거 데이터다.
- 기존 접근성 기준(대비 4.5:1, 글자 크기, 키보드 순회, 1024px 폭)을 그대로 적용한다.

## 경계 — 하지 않는 것

- **기록 경로 무변경**: 훅 · `state.json` · `transitions.jsonl` 쓰기 코드를 건드리지 않는다.
- **해석·권고 없음**: 「qa 가 병목입니다」 같은 문장을 만들지 않는다. 수치와 표시만.
  판단은 사람이 한다.
- **예측 없음**: 남은 시간 추정, 완료 예상 시각 등을 계산하지 않는다.

## 완성 판정 — `scripts/check-report.mjs` 프로브 추가

1. 가짜 `transitions.jsonl`(task 2개, 역방향 전환 1회, `result` 채워진 줄 포함)을 주면
   task 별 막대에 노드 순서와 체류 시간이 렌더된다
2. 역방향 전환이 되돌아감 표기로 나타난다 (색 제거 상태에서도 구분 가능)
3. 노드별 합산 체류 시간 요약이 표시되고, 수기 계산 값과 일치한다
4. `current_node` null 구간이 「그래프 밖 작업」으로 표시된다
5. 집계 함수가 순수 함수이며 node 단위 테스트를 통과한다
6. 이 작업 후 `report/` 에 새 데이터 파일이 없다 (파생 사본 없음 확인)
7. `index.html` 의 외부 CDN 참조 수가 그대로다

검사 통과 후 실제 쌓인 `transitions.jsonl` 로 드라이런하고, 노드별 합산 수치를
③·④ 순서 결정 자료로 백로그에 기록한다.

## 착공할 때 먼저 물어야 하는 것 — 지금 답이 없는 것들

착공 시점에 임의로 정하지 말고 사용자에게 묻는다.

1. ~~③·④가 무엇인가~~ — **답이 왔다.** `harness-design.md` 2절에 정의돼 있다.
   ③은 「수정 한 번마다 확인해도 부담 없는 초 단위 확인 명령」, ④는 「명령 하나로 초기 상태
   복구가 보장되는 로컬 환경」이다. 그래서 집계가 가리켜야 하는 것도 정해졌다 —
   **어느 노드에 오래 머무는가**가 ③ 부족(확인이 느려 왕복을 묶는다)인지 ④ 부족(복구가 안 돼
   사람이 직접 하는 구간이 남는다)인지를 사람이 판단할 수 있는 수치여야 한다.
2. **접근성 기준의 정본이 어디인가.** 「대비 4.5:1 · 글자 크기 · 키보드 순회 · 1024px 폭」을
   기존 기준이라고 했는데, 대시보드는 제품이 아니라 개발 도구라 `design-rules.md` 가 적용되지
   않는다. 이 기준을 어디에 적어 둘지 정해야 재판정이 가능하다.
3. **「최근 N개」의 N.** 그리고 접힘의 기준이 개수인지 기간인지.
