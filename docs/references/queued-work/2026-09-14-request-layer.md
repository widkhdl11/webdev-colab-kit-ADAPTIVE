# 진행 예정 — 대시보드 정보 모델 개편 (요청 층 · 범위 고정 · 서브에이전트 칸)

> 이 문서는 사용자가 넘긴 프롬프트 전문과, **착수 전에 답이 필요한 것들**을 담는다.
> 대기열이 아니다 — 「투입 전 닫힌 목록」의 3번(대시보드 UI 개편)의 상위 변경이고,
> 착공 신호는 아래 「막는 것」이 풀리는 것이다.
> ①~⑤·「필터」·「책임 표」의 정의는 `docs/references/harness-design.md` 가 정본이다.

---

## 착수를 막는 것 — UI 개편 프롬프트가 이 레포에 없다

넘겨주신 프롬프트가 **「UI 개편 프롬프트의 기준 절」을 두 번 참조**한다.

- 「UI 개편의 렌더 규칙(Mermaid 제거, 노드 클릭 시 스킬 패널, 접근성 기준)은 그대로 유효」
- 「접근성·가독성 기준은 UI 개편 프롬프트의 기준 절을 그대로 적용한다」

**그 문서가 이 레포에 없고, 이 세션에도 온 적이 없다.** 2026-09-14 에 한 UI 개편은 그
프롬프트 없이 진행한 것이라 세 가지가 어긋나 있다.

| 그 프롬프트가 요구하는 것 | 지금 만들어진 것 |
|---|---|
| Mermaid 제거 | `index.html` 이 Mermaid CDN 하나를 쓴다. 유일한 외부 의존이다 |
| 노드 클릭 시 스킬 패널 | 사이드바에 스킬을 상시 나열한다. 지도 노드는 클릭이 안 된다 |
| 접근성 기준 절 | 대비·글자 크기·키보드 순회·폭의 기준이 어디에도 적혀 있지 않다 |

**Mermaid 제거는 가벼운 변경이 아니다.** 지금은 노드·엣지 배치를 Mermaid 가 계산한다.
빼면 그 배치를 직접 그려야 하고(노드 아홉·엣지 아홉·집계 노드의 자식 상자 포함),
CDN 이 0개가 되는 대신 렌더 코드가 늘어난다. 완성 판정 10번의 「CDN 0」이 이것을 전제한다 —
즉 그 프롬프트를 안 받은 채로 이 작업을 하면 10번을 통과할 수 없다.

→ **UI 개편 프롬프트 전문이 필요하다.** 받기 전에는 이 작업을 시작하지 않는다.

## 확인한 사실 셋 (조사 완료)

### 1. 스펙에 「결과 조건」 절이 없다 — items 출처를 정해야 한다

프롬프트는 `source: "spec"` 일 때 `items = 스펙의 결과 조건 목록` 이라고 한다.
실제 스펙(`projects/study-mate/docs/specs/*.md`)의 절은 넷이다:

```
## 불변식        INV-<접두><번호>  — 어기면 사고가 나는 규칙
## 시나리오      S<번호>           — 각 불변식을 검증하는 Given/When/Then
## 신뢰 경계
## 비범위
```

**「결과 조건」이라는 이름의 절은 없다.** 파싱은 둘 다 가능하다 — `docs-contract.md` 2절이
INV 정의 앵커와 시나리오 ID 를 이미 기계가 읽는 형식으로 등재해 뒀다.

그래서 정할 것은 파싱 가능 여부가 아니라 **무엇을 항목으로 볼 것인가**다.

| 후보 | 항목의 뜻 | 개수(auth-session 기준) |
|---|---|---|
| 불변식(INV) | 「이 규칙이 지켜지게 만들었나」 | 보통 5~10개 |
| 시나리오(S) | 「이 경우를 검증했나」 | INV 보다 많다(각 INV 를 여러 각도로 쪼갠다) |

**불변식을 권한다.** 요청 층은 「내가 시킨 것 대비 어디까지 왔나」에 답하는 자리인데,
시나리오는 한 불변식을 여러 각도로 쪼갠 것이라 개수가 판단이다 — 진행률의 분모가
판단에 따라 흔들리면 그 숫자를 못 믿는다.

### 2. 서브에이전트 호출은 지금 훅에 안 잡힌다 — 이유는 확인됐다

`activity.jsonl` 89줄에 서브에이전트 호출이 한 줄도 없다(Bash 44 · Write 15 · Edit 15).
2026-09-14 세션에서 `code-reviewer` 를 실제로 파견했는데도 없다.

**원인은 훅이 죽은 것이 아니라 matcher 다.** `settings.json` 의 배선이

```
"matcher": "Edit|Write|MultiEdit|Bash|PowerShell"
```

이고 서브에이전트를 띄우는 툴이 그 목록에 없다. 즉 훅 코드는 멀쩡하고 **배선만 좁다.**

→ 고치려면 matcher 를 넓혀야 하고, 그건 `settings.json` 이라 사용자가 직접 반영한다.
`start`/`end` 를 어느 이벤트로 잡을지(PreToolUse + PostToolUse 인지, PostToolUse +
SubagentStop 인지)와 훅 입력의 필드명은 **실제 입력을 한 번 받아 봐야 확정된다.**
프롬프트도 「확인이 안 되면 추측하지 말라」고 했으므로, 배선을 넓힌 뒤 raw 입력을 한 번
찍어 보고 그 다음에 스키마를 고정한다.

### 3. 서브에이전트 목록의 출처는 있다 — 하드코딩 불필요

`.claude/agents/` 에 정의 파일 일곱이 있다: `code-reviewer` · `design-drafter` ·
`qa-classifier` · `security-reviewer` · `style-scout` · `test-auditor` · `ui-reviewer`.
`export-workflow.mjs` 가 이 폴더를 읽어 `workflow.json` 에 실으면 된다 —
노드↔스킬 바인딩과 같은 방식이고, 화면 코드에 목록이 들어가지 않는다.

---

## 답이 필요한 것 (질문 목록)

1. **UI 개편 프롬프트 전문** — 위 「막는 것」. 특히 접근성 기준 절의 실제 수치.
2. **`source: "spec"` 의 items 를 불변식으로 볼지 시나리오로 볼지.** 위 표 참고. 불변식을 권한다.
3. **`item` 을 `transitions.jsonl` 에 더하는 것이 스키마 변경이다.** 라이프사이클 층 프롬프트는
   「기록 스키마 변경 없음, 새 필드 없음」을 전제로 쓰여 있다. 이 작업이 `item` 을 더하면 그
   전제가 깨진다 — 대기열 문서를 같이 고칠지, 라이프사이클 층이 `item` 을 무시하게 둘지.
4. **`request.json` 이 프로젝트 하나에 하나인가.** 「현재 요청 하나, 덮어쓰기」인데, 킷 작업과
   제품 작업이 동시에 열리면 어느 쪽이 현재 요청인지 규칙이 없다. 지금은 그래프 밖 작업을
   `current_node: null` 로 적고 있어서 둘이 겹칠 수 있다.

## 프롬프트 전문

```
# 목표

대시보드에 요청 층과 서브에이전트 칸을 추가하고, 화면을 아래 순서로 재구성한다.
1. 요청 층 — 진행 중인 요청, 항목 진행률, 현재 항목, 파생 작업, 대기 사유
2. 서브에이전트 칸 — 등록된 서브에이전트 목록과 실행 상태
3. 파이프라인 지도 — 기존 (UI 개편 규칙 적용)
4. 활동 피드 — 기존
(라이프사이클 층은 대기열 그대로. 이 작업에서 만들지 않는다.)

LLM 비관여 제1 제약은 유지된다. 새 기록은 메인 에이전트의 규약 기록과
hook 자동 기록으로만 만든다.

# 핵심 규칙 — 요청 범위는 시작 시점에 고정된다

- 요청 하나를 시작할 때 항목 목록(items)을 기록하고, 이후 items 는 바꾸지 않는다.
- 시작 후 새로 생긴 일은 items 에 추가하지 않는다. 작업 줄에 items 에 없는
  항목명을 적으면 그것이 곧 파생 작업이며, 대시보드가 파생으로 분류한다.
- 파생 작업의 판별은 사람이나 에이전트의 판단이 아니라 "시작 목록에 있었나"의
  기계 대조다. 기록 스크립트는 시작 후 items 변경 시도를 거부한다.

# 데이터 — 요청 기록

report/request.json (현재 요청 하나, 덮어쓰기):
{
  "task": string,                 // state.json·transitions.jsonl 의 task 와 동일 식별자
  "request": string,              // 사람이 시킨 문장 원문. 요약·재해석 금지
  "source": "spec" | "manual",    // items 의 출처
  "spec_path": string | null,     // source 가 spec 이면 스펙 파일 경로
  "items": [{ "id": string, "label": string, "done": boolean }],  // 시작 시 고정
  "status": "진행 중" | "승인 대기" | "완료" | "중단",
  "status_reason": string | null, // 승인 대기·중단 사유. 예: "결제 중 새 스펙 발견"
  "started_at": ISO8601,
  "ended_at": ISO8601 | null
}

items 의 출처 규칙:
- 스펙이 있는 작업: items = 스펙의 결과 조건 목록. 결과 조건이 파싱 가능한
  형식이면 스크립트가 옮기고, 아니면 시작 시 에이전트가 옮겨 적는다.
  (파싱 가능 여부를 확인해 보고하고, 애매하면 질문 목록에 올려라.)
- 스펙이 없는 작업(작은 수정, 킷 작업): 시작 시 에이전트가 요청 문장을 항목으로
  분해해 기록한다. 이 목록은 시작 직후 대시보드에 그대로 보인다.

report/requests-history.jsonl: 요청이 완료·중단될 때 request.json 내용을
한 줄 append 하고 request.json 을 초기화한다. (이후 라이프사이클 층의 입력)

transitions.jsonl 에 필드 추가:
  "item": string | null   // 이 전환이 속한 항목의 label. items 에 없는 값이면 파생.
                          // 그래프 밖 작업이나 항목과 무관한 전환은 null.

state.json 의 now 는 그대로 상세 한 줄(80자 이내)이고, 화면은 "현재 항목 — now"
형태로 조합해 표시한다. now 에 항목명을 중복해 적지 않는다.

기록 시점 (기존 규칙에 추가):
- 요청 시작 시 request.json 작성 (kickoff 또는 스펙 시작 시점)
- 항목 완료 시 해당 item 의 done 갱신
- 승인 대기 발생 시 status·status_reason 갱신 (blockers 와 함께)
- 요청 완료·중단 시 status·ended_at 갱신 후 history 로 이동
이 규약을 docs-contract 에 등재하고 kickoff 문서에 요약을 추가한다.

# 데이터 — 서브에이전트 기록 (hook 자동, 토큰 0)

report/subagents.jsonl: hook 이 append.
  { "at": ISO8601, "event": "start" | "end", "agent": string,
    "brief": string }   // 시작 시 지시문의 첫 줄, 80자 이내. end 는 빈 문자열 가능
- 서브에이전트 호출은 툴 호출이므로 해당 툴의 PreToolUse(start)와
  SubagentStop 또는 PostToolUse(end) hook 으로 잡는다. hook 입력에서
  서브에이전트 종류와 지시문을 뽑되, 필드명은 실제 hook 입력을 확인해 정한다.
  확인이 안 되면 추측하지 말고 질문 목록에 올려라.
- 등록된 서브에이전트 목록의 출처는 하네스의 에이전트 정의(실제 파일)다.
  스크립트나 화면 코드 안에 목록을 하드코딩하지 않는다.
- 기존 hook 설정은 병합, 덮어쓰기 금지.

# 렌더링

요청 층 (화면 최상단):
- 요청 문장 원문, status.
- 항목 진행: "n/m 완료" + 항목 목록(완료 여부 표시). 현재 항목은 강조 + now.
- 파생 작업: transitions 의 item 이 items 에 없는 것들을 항목명별로 묶어
  체류 시간 합계와 함께 별도 구역에 표시. 제목은 "요청 밖 작업".
  파생이 없으면 구역을 비우지 말고 "없음"을 표시한다.
- 승인 대기·중단이면 status_reason 을 요청 층 최상단에 표시하고
  파이프라인 지도의 대기 표시와 연동한다.
- 완료 직후에는 history 의 마지막 요청을 "완료 — <request>" 로 짧게 표시하고,
  새 요청이 시작되면 교체한다.

서브에이전트 칸:
- 등록된 서브에이전트를 전부 나열. 실행 중이면 색 + "작업 중" 라벨 + brief +
  경과 시간, 아니면 저채도 + "대기". 상태는 색과 라벨 이중 표기.
- start 후 end 가 없는 항목이 실행 중이다. 경과 시간을 표시한다.

접근성·가독성 기준은 UI 개편 프롬프트의 기준 절을 그대로 적용한다.

# 경계 (하지 않는 것)

- 파생 작업을 평가하지 않는다. "불필요", "범위 이탈" 같은 판정 문구 금지.
  파생 항목과 체류 시간을 보여줄 뿐이고, 판단은 사람이 한다.
- request 필드의 사람 문장을 요약하거나 고쳐 쓰지 않는다.
- 렌더 경로에 LLM 호출 없음. 서브에이전트 brief 를 모델로 요약하지 않는다
  (지시문 첫 줄을 자르기만 한다).
- 라이프사이클 층은 만들지 않는다 (대기열 유지).
- 보호 파일·게이트 무변경.

# 완성 판정 — check-report.mjs 프로브 추가

1. request.json 스키마 검증 통과. items 는 1개 이상.
2. 시작 후 items 를 바꾸려는 기록 시도가 스크립트에서 거부된다.
3. transitions 에 items 에 없는 item 을 가진 줄을 넣으면 요청 층의
   "요청 밖 작업" 구역에 그 항목과 체류 시간이 표시된다.
4. item 의 done 을 갱신하면 "n/m 완료" 표시가 바뀐다.
5. status 를 "승인 대기" + status_reason 으로 바꾸면 요청 층 최상단에
   사유가 표시된다.
6. 가짜 hook 입력으로 start·end 를 넣으면 subagents.jsonl 에 두 줄이 append 되고,
   렌더가 실행 중 ↔ 대기 표시를 바꾼다 (렌더 함수 순수 함수로 node 테스트).
7. 요청 완료 처리 시 requests-history.jsonl 에 한 줄 append 되고
   request.json 이 초기화된다.
8. 스펙이 있는 task 로 시작하면 source 가 spec 이고 items 가 스펙 결과 조건과
   일치한다 (파싱 가능한 경우. 불가하면 그 사실을 보고하고 질문 목록에).
9. 서브에이전트 목록이 에이전트 정의 파일과 일치한다 (하드코딩 없음 확인).
10. 기존 프로브 전부 유지: CDN 0, hook 병합 보존, now 80자, 전환 쌍 기록.

검사 통과 후 study-mate 에서 스펙 있는 작업 1건과 스펙 없는 작업 1건으로
드라이런하고, 요청 층이 "어디까지 했고 요청 밖으로 나갔나"를 5초 안에 읽히게
보여주는지 사람이 확인한다. 발견 사항은 백로그에 등재한다.
확신이 없는 결정은 임의로 정하지 말고 질문 목록에 올려라.
```
