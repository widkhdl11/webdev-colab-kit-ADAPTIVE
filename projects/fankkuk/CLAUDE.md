## 화면 문구 규칙

경로는 `projects/fankkuk/` 기준이다. 이 규칙의 본체는 이 파일(CLAUDE.md)이다 — AGENTS.md 에는 Codex 가 여기를 읽으라는 한 줄만 둔다. 작성 원칙은 여기, 서비스 용어의 의미와 대표 표기는 `docs/copy/glossary.md`에 둔다. 같은 규칙을 양쪽에 복사하지 않는다.

### 쓰기 전에: 자리·대상·사실 확인

1. 사용자에게 보이는 문구를 만들거나 고치기 전에 용어집의 관련 항목을 읽는다. 먼저 **누가 읽는지, 어디에 표시되는지, 어떤 상태에서 보이는지, 무엇을 이해하거나 해야 하는지** 확인한다. JSX·버튼·알림·오류·이메일·안내 문서에 같은 기준을 적용한다.
2. 최근 사용자의 명시적 수정 지시를 반영한다. 과거 문구·시안·용어집 예시와 다르면 관련 기준도 함께 갱신한다. 새로 만든 제안본 전체를 승인된 문구로 간주하지 않는다. 화면별 반영 여부는 작업 기록에 남기며 문체 규칙으로 삼지 않는다.
3. 정책·권리·비용·기한·개인정보 공개 범위는 확정된 기준과 실제 동작을 대조한다. 둘이 다르면 문구로 한쪽을 임의 확정하지 않고 해당 차이를 보고한다. 그 차이에 의존하지 않는 문구 수정은 계속한다.

### 문구의 역할에 맞게 쓴다

| 역할 | 작성 기준 | 예시 |
| --- | --- | --- |
| 페이지·구역 제목 | 담긴 내용이나 수행할 작업을 짧게 쓴다. 순서·분위기만 나타내는 이름을 피한다. | 선택 입력 사항 · 상자 선택 |
| 입력 라벨 | 입력할 값의 이름을 쓴다. 선택 사항은 표시한다. | 휴대폰 번호 · 가입 경로 (선택) |
| 조건·한도 | 비교·확인하기 쉽게 항목으로 쓴다. 불필요하게 문장으로 늘리지 않는다. | 배송비 포함 · 한 번에 최대 10개 |
| 상태·배지 | 현재 확인된 상태를 짧게 쓴다. 긴 원인 설명은 분리한다. | 승인 대기 · 결제 완료 · 주소 확인 필요 |
| 버튼·링크 | 실행할 행동이나 이동할 곳을 쓴다. ‘~하기’를 억지로 붙이지 않는다. | 저장 · 주소 변경 · 선물 보내기 · 고객센터 |
| 사실·결과·제한 | 중립적인 ‘~습니다’를 기본으로 한다. | 인증 요청을 보냈습니다. |
| 행동 요청 | 필요한 행동을 직접 ‘~해 주세요’로 안내한다. | 카카오톡에서 인증을 진행해 주세요. |
| 확인 질문 | 사용자가 선택한 행동을 확인한다. 거절·동의를 유도하지 않는다. | 답장을 삭제할까요? |
| 환영·브랜드 인사·개인 답장 | 자연스러운 해요체를 허용한다. 과한 친근함·감정 추측을 피한다. | 반가워요 · 잘 받았어요, 고마워요 |
| 약관·방침 | 정의된 용어와 ‘~합니다’ 문체를 유지한다. 의미가 우선이다. | 회사 · 회원 · 환불합니다 |

4. 화면 전체를 한 말투로 통일하지 않는다. 같은 화면에서도 제목·설명·질문·개인 답장의 역할을 구분한다. ‘받았어요’처럼 의미가 명확한 사용자 확인 버튼은 자연스러운 표현을 유지할 수 있다.
5. 한 문구에는 한 가지 핵심을 담는다. 제목·본문·단계에서 같은 내용을 반복하지 않는다. 긴 절차는 행동 순서로, 조건이 여러 개면 항목별로 나눈다. 중요한 조건을 줄이거나 접기 안으로 숨겨 짧게 만들지 않는다.
6. 한자어·일상어로 기계적으로 나누지 않는다. ‘배송지·환불·반송·주소 변경’처럼 익숙하고 정확한 서비스 용어를 쓴다. ‘환불합니다’를 반드시 ‘돌려드려요’로 풀지 않는다. 번역투·불필요한 존칭·감탄사·이모티콘을 피한다.
7. 라벨은 주변 제목·값과 함께 읽어 명확하면 된다. 모든 라벨에 대상·원인·해결법을 넣지 않는다. 주체가 헷갈리는 문장에는 ‘팬꾹’, ‘팬’, ‘크리에이터’를 명시한다.

### 사이트가 확인한 사실만 말한다

8. 등록·결제·승인·발송·입고·수령을 구분한다. 등록일을 발송일로, 결제 완료를 배송 완료로, 환불 대상을 환불 완료로 쓰지 않는다. 기한은 무엇을 기준으로 언제까지인지 명확히 한다.
9. 시스템에 응답이 없다는 이유로 ‘고민하고 있어요’라고 쓰지 않는다. 팔로우 취소 시 ‘슬퍼하실 거예요’처럼 타인의 감정을 추측하거나 선택에 부담을 주지 않는다. 확인된 근거 없이 안전·비공개·처리 시점을 보장하지 않는다.
10. 선택에 필요한 비용·한도·취소 결과·공개 범위·예외는 남긴다. ‘주소 비공개’라면 누구에게 비공개인지, ‘검수 포함’이라면 어떤 검수인지 구분한다. 필요한 안내가 기존 화면에 없으면 누락을 알리고 반영안을 제시한다. 문구 수정만으로 새 기능·입력·노출 조건을 만들지는 않는다.
11. 오류는 확인된 문제와 가능한 다음 행동을 쓴다. 원인을 모르면 추측하지 않는다. 빈 결과·처리 실패·권한 부족을 같은 오류로 묶지 않으며, 재시도로 해결되지 않는 문제에 ‘잠시 후 다시 시도’를 자동으로 붙이지 않는다. 내부 진단 정보는 사용자 안내와 분리한다.

### 용어·공통 문구 관리

12. 같은 개념의 대표 표기는 용어집에 맞춘다. 코드 식별자를 직역하지 않는다. 자연스러운 조사·활용과 상태/행동의 차이는 허용한다(상태 ‘수락 대기’, 버튼 ‘받기’). 용어집의 문장 예시는 복제 의무가 아니다.
13. 기존 개념의 쉬운 이름·라벨 개선은 근거를 남기고 진행한다. 여러 화면에서 반복할 새 서비스 용어는 용어집도 갱신한다. 새로운 정책·권한·비용·상태의 의미를 결정해야 할 때만 그 결정을 요청한다. 단어 하나가 없다는 이유로 문구 작업 전체를 멈추지 않는다.
14. 공통 문구는 기존 상수를 재사용한다. 정확성·가독성 문제가 발견되면 상수와 관련 문서를 함께 수정하고 사용처를 확인한다. 서로 다른 조건의 문장을 하나의 상수로 강제하지 않는다. 원문 그대로 유지할 필요가 있는 외부 제공 문장은 그 근거와 적용 범위를 명시한다.
15. 약관·방침은 단어 치환으로 권리·의무·예외·기한을 바꾸지 않는다. 기술 용어도 처리 방식을 정확히 설명하는 데 필요하면 사용한다. 운영자 진단·로그에는 사용자용 말투를 강제하지 않으며, 내부 오류를 화면에 그대로 노출하지 않는다.

### 수정 후 확인

16. 수정한 문구를 제목·값·버튼·성공/실패 상태와 함께 읽는다. 변수, 수치, 금액, 날짜, 조건, 동의의 의미가 보존됐는지 확인한다. 메뉴·버튼을 인용한 안내는 실제 이름과 맞춘다.
17. `npm run copy:lint`는 용어집 9절의 제한된 표현을 찾는 보조 검사다. 통과가 정확성·가독성 검토를 대신하지 않는다. 커밋 전 실행하고, 실패하면 실제 위반인지 확인한다. 문맥상 올바른 표현까지 막는 규칙은 이유를 남겨 기준을 고치고 재검사한다. 검사를 끄거나 문장을 의미 없이 바꾸어 통과시키지 않는다.
18. 고정 상수의 검사 제외는 그 문장의 정확성을 보장하지 않는다. 검토에 해당 상수의 실제 문구와 사용처를 포함한다. 검사 기준을 바꾸면 잘못된 표현은 실패하고 허용한 표현은 통과하는지 함께 확인한다.
