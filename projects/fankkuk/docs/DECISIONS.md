## 2026-10-01 — 요금: 단일 요금 → 상자마다 구간 요금

- 결정: 배송비를 포함한 한 금액을 상자마다 받는다. 소형(세 변 합 100cm·5kg 이하) 6,900원, 중형(세 변 합 100cm·10kg 이하) 8,900원. 크기와 무게 중 큰 쪽 구간. 중형을 넘으면 받지 않는다.
- 도착 실측이 신고 구간보다 크면 차액을 따로 결제 요청한다. 7일 안에 안 내면 반송하고, 실측이 작아도 환불하지 않는다.
- 기록은 배송비(구간 택배 원가)·서비스료(나머지)로 나눠 저장한다 — 부가세 분리(D-03)와 환불(반송 때 배송비 칸만)이 이 칸을 쓴다. 택배 원가는 계약 전 가정값(소형 4,000·중형 5,000).
- 이유: 검수와 송장이 상자 단위로 일어나므로 값도 상자 단위로 받는다. 「검수가 빠진 요금은 없다」는 그대로다.
- 출처: 결정 카드 d7(상자마다)·d8(빈칸 네 개 추천대로).

## 2026-10-01 — 화면 폭 거부 · 사이트 구성과 기능 다섯 개 추가

- 사용자가 메인 화면을 거부했다: 「저렇게 좁은 화면이 아니라 일반 사이트같은 사이즈로 생각했는데」, 「애초에 모든 페이지 시안을 보여주고 시작해야지」. 상담의 「모바일 우선」을 PC에서도 최대 480px로 옮긴 것이 원인이다. 색·모양은 그대로 두고 폭만 다시 잡는다(PC 본문 최대 1200px).
- 사용자가 사이트 구성을 직접 줬다(헤더 로그인·회원가입과 선물 상태 아이콘, 랜딩 → 메인, 네비 다섯, 내 정보 셋). 그중 제품 정의에 없던 크리에이터 찾기·팔로우·공지사항·고객센터·헤더 선물 아이콘을 첫 출시 필수에 넣었다 — 사용자 「넣어」.

## 2026-10-02 — 승인을 기다리지 않고 보낸다 · 거절되면 반송비를 빼고 환불

- 결정: 팬은 결제 직후 사무실 주소를 받아 바로 보낸다. 크리에이터 승인은 출고 전에만 있으면 된다(송장 출력 = 주소 열기는 여전히 승인 뒤에만). 거절·7일 자동 반려된 선물은 팬에게 반송하고, 결제 금액에서 반송 택배비(배송비 칸)를 뺀 금액(서비스료·상품 대금 칸)을 환불한다. 이 사실은 보내기 전(선물 보내기 화면)에 알린다.
- 이유: 사용자 「승인 기다리고 보내는게 아니라 걍 보낼 수 있게. 승인은 우리쪽에서 보내기 전에만」 — 팬이 승인을 기다리는 시간을 없앤다. 대신 거절될 선물이 사무실로 들어오는 비용은 환불에서 뺀다. 환불 계산은 질문 답 「반송 택배비만 빼고 환불」(추천안).
- 대체: 승인 서명 스펙 INV-S9(승인 전 사무실 주소 비공개) → 「결제 끝난 주문에만, 거절·반려·취소 주문엔 비공개」. 결제 스펙 INV-M8 의 「입고 뒤 거절·반려 → 배송비 칸만」(가정이었음).
- 그대로인 것: 크리에이터 주소는 승인 + 검수 완료 뒤 송장 출력 때만 열린다(INV-P4). 입고 전 거절은 전액 환불. 검수 불합격·차액 미납 반송은 배송비 칸만.

## 2026-10-02 — 검수에 걸려 반송하면 검수비·반송비 모두 차감

- 결정: 검수에서 추적 장치 등 보낼 수 없는 물품이 나오거나 실측이 중형을 넘어 반송하면, 서비스료(검수비)와 배송비 칸(반송 택배비)을 모두 빼고 상품 대금 칸만 환불한다(지금은 상품 대금이 0 이라 환불 없음). 결제 전에 알린다.
- 이유: 사용자 「검수에 걸렸다는 건 gps 같은게 있었다는 것, 검수비를 차감해야」 — 팬의 위반이라 비용을 팬이 부담. 질문 답 「검수비+반송비 모두 차감」(추천안). 중형 초과 실측은 같은 「검수 불합격」으로 묶여 있어 함께 바뀐다.
- 대체: 결제 스펙 INV-M8 「입고 뒤 검수 불합격 반송 → 배송비 칸만」.

## 2026-10-02 — DB 표 구성과 임시 로그인: 시험 계정 + 간단 로그인

- 결정: 로컬 DB에 시험 계정 셋(팬·크리에이터·운영자)을 심고 아이디·비밀번호 로그인 화면 하나만 붙인다. 로그인은 실제 방식(로그인한 사람 ID로 DB가 거른다)이고, 가입 화면·카카오 본인 확인은 계정 스펙 때 더한다.
- 표 열 개(계정·크리에이터·주문·상자·결제·승인 요청·주소 열람 기록·팔로우·공지·문의). 화면은 표를 직접 읽지 못하고 DB 함수가 보여도 되는 칸만 돌려준다. 돈·상태를 바꾸는 쓰기는 앱 서버 키로만. 실명·주소·전화번호 표는 이번에 만들지 않는다.
- 이유: 카카오 본인 확인은 딜러사 계약 전이라 계정 전체를 먼저 만들면 반쪽이 되고 DB 연결이 늦어진다. 로그인 방식은 실제와 같아 나중에 버리는 코드가 없다.
- 출처: 결정 카드 d9 「추천대로 진행」(A).

## 2026-10-02 — 로그인 유지: Supabase 공식 라이브러리 + 로그인 규칙 일곱 줄

- 결정: 로그인 쿠키 저장·만료 갱신은 `@supabase/ssr`에 맡긴다. 로그인 규칙(`docs/specs/session-login.md` INV-L1~L7)을 승인한다 — 토큰은 스크립트가 못 읽는 쿠키에만, 서버는 요청마다 사람을 다시 확인, 쓰기에는 확인한 ID만, 관리자 키는 서버 전용, 실패 안내는 하나, 시험 계정은 운영에서 막음, 로그아웃은 서버 세션까지 끝냄.
- 이유: 토큰 갱신과 동시 요청 처리를 직접 짜면 틀렸을 때 조용히 로그아웃되거나 만료 토큰이 통과한다. 공식 라이브러리는 study-mate 에서 이미 쓴다.
- 출처: 결정 카드 d10 「추천대로 진행」.

## 2026-10-02 — 내 정보: 연락처는 개인정보 구역에, 이메일은 확인한 주소에만

- 결정: 내 정보의 이메일·휴대폰·알림은 칸을 만들어 실제로 저장한다(카드 d11). 이메일·휴대폰은 개인정보 구역에 두고, 휴대폰은 암호화하지 않되 화면에는 가운데를 가려서만 보인다. 이메일은 바꾸면 확인 메일의 링크를 눌러야 새 주소가 된다(카드 d12).
- 이유: 배송 소식을 이메일로 보내므로 오타나 남의 주소로 가면 안 된다. 휴대폰은 알림톡 발송에 서버가 수시로 읽어야 해서 주소처럼 잠그지 않는다 — 법상 저장 암호화 의무 대상(고유식별정보·비밀번호·생체정보)도 아니다(운영 전 처리방침 작성 때 재확인).
- 주소는 지금 방식 유지: 「번호처럼 두면 안 되나」를 검토했고, 주소는 승인 건 출력 때만 필요하며 「승인 없이는 우리도 못 연다」가 제품 약속이라 브라우저 암호화·복호화 함수 구조를 그대로 둔다.
- 남은 것: 개정 스펙(my-account INV-A1~A8)과 메일 라이브러리 nodemailer 추가는 카드 d13 승인 대기.

## 2026-10-02 — 회원가입: 확인된 번호 하나에 계정 하나, 카카오 연결 전엔 로컬만 가짜 확인

- 결정: 번호 하나에 계정 하나, 가입 이메일도 확인 메일, 카카오 연결 전에는 로컬만 가짜 본인 확인이고 운영 가입은 막는다(카드 d14 「됐다」→ 추천대로). 스펙 signup(INV-U1~U11).
- 이유: 휴대폰 번호는 알림톡이 가는 곳이라 확인하지 않은 번호로 계정이 생기면 남에게 선물 소식이 간다. 운영에서 가짜가 켜질 길은 두지 않는다 — 설정 하나 잘못 넣어 아무 번호로 가입되는 일이 없게.
- 리뷰 뒤 더한 것: 본인 확인 번호표는 그것을 받은 브라우저의 쿠키에만 둔다(남이 번호표를 가져가도 못 쓴다).

## 2026-10-03 — 크리에이터 메인, 크리에이터도 선물 보내기(크리에이터에게·자기 팬에게)

- 결정: 셋 다 연다 — 크리에이터 메인 화면, 크리에이터 → 다른 크리에이터, 크리에이터 → 자기 팬(카드 d15 「셋 다」, 추천은 앞의 둘이었다).
- 이유: 크리에이터 로그인 뒤 승인 요청만 바로 나와 「본론부터 들어가는」 느낌이었다. 크리에이터도 팬에게, 가끔은 다른 크리에이터에게 선물을 보낸다.

## 2026-10-10 — 정책 문제집 메모로 정한 것 A~C (카드 d59 일부)

- 추적기 판정은 검수 기록의 새 칸(「추적기」·「추적기 아님」)으로 남긴다. 블루투스·RF 반응이 있으면 판정이 꼭 있어야 하고, 반응이 없으면 비어 있다. 판정 칸에는 기본값이 없다 — 직원이 열어 보고 고르지 않으면 기록이 저장되지 않는다.
- 추적기 상자의 결론 값은 처음 이름(보관)을 그대로 쓰고 뜻만 「추적기 반송」으로 바꿨다. 환불·대표 취소가 이 값을 「검수에 걸린 상자」로 읽고 있어, 값을 바꾸면 돈 처리(B9)가 같이 바뀌기 때문이다. 화면에는 「추적기 반송」으로 보인다. 알림 종류 코드(hold·hold_fan)도 그대로다.
- 추적기 상자는 검수 완료 스캔에서 바로 반송 대기로 가므로, 같은 주문의 다른 상자는 다른 검수 반송(금속·금지 물품)과 똑같이 된다 — 이미 승인된 주문은 나머지 상자가 출고되고, 승인 전 주문은 검수 결과가 「반송」이 돼 더 승인할 수 없다. 전에는 보관 중인 상자를 세지 않아 승인 전 주문도 나머지 상자를 승인할 수 있었다(168시간 뒤 반송 대기로 바뀌면 같아졌다). 근거: 「기존 검수 불합격 규칙 그대로」.
- 크리에이터 알림 이름은 「돌려보내는 선물」, 본문은 「검수를 통과하지 못해 보낸 분에게 돌려보내는 상자가 있어요」. 확인을 부탁하는 말과 「추적」이라는 말은 쓰지 않는다(본문 규칙 INV-N1 — 검수 결과의 세부를 넣지 않는다). 팬 알림에서는 「168시간 뒤」만 뺐다. 운영자 알림 목록의 이름은 「추적기 반송」(운영자는 내부 사정을 안다).
- 이미 보관 중이던 상자를 옮기는 처리는 마이그레이션에 넣지 않았다 — 배포 전이라 운영 DB 에 보관 상자가 없고 로컬 DB 도 0개였다(2026-10-12 다시 셈). 한 번짜리 데이터 정정은 마이그레이션에 넣지 않는다. 자동 처리의 「보관 + 168시간」 단계는 대상이 없어 아무 일도 하지 않지만, 큰 자동 처리 함수를 다시 쓰는 위험에 비해 얻는 것이 없어 그대로 두었다(BACKLOG).
- 「추적기 아님」으로 통과·반송한 상자에는 추적기 알림이 가지 않는다. 반송이면 다른 검수 반송과 같다.
- 실측 구간은 상자를 불러올 때 신고 구간이 골라진 채 열린다. 그 값은 「실측 기록」을 눌러야 저장된다 — 누르지 않고 검수 완료 스캔을 하면 지금처럼 거부된다(D5 「화면만」). 버튼을 누르지 않아도 자동으로 저장되게 하는 것은 저장 규칙을 바꾸는 일이라 하지 않았다.
- 약관 제10조(검수와 보낼 수 없는 물품)의 보관 두 줄을 「위치 추적 장치로 확인된 상자는 보관 없이 돌려보내고 크리에이터와 보낸 분에게 알린다 · 추적 장치가 아니라고 확인한 물품은 다른 물품과 같이 처리한다」로 고쳤다(시행일 전).

### D12 반영 때 정한 세부 (2026-10-12)

- 크리에이터 열람 기록 응답은 시각·주문번호·몇 번째 출력·돌려받은 줄인지 넷뿐이다. 거부 줄은 사유와 상관없이 전부 뺐다 — 결정 문장이 「열린 줄과 지운 줄만」이라 대표 본인의 거부(횟수 다 씀·승인 없음 등)와 주소 주인 불일치 거부도 크리에이터에게 가지 않는다. 화면의 「누가」 칸과 「이번 달」의 거부 숫자도 뺐다(숫자는 승인·주소 열림·재출력 셋).
- 팬의 몫 열람 기록도 같은 모양 — 연 줄과 지운 줄만, 「누가」 칸 없음.
- 운영자 내부 기록은 관리자 왼쪽 메뉴 「관리」 묶음의 새 화면 「주소 열람 기록」(/admin/access-log)에 둔다. 팬 선물과 역조공 몫의 연 줄·거부 줄을 최근 순 200줄, 줄마다 선물 종류·주문번호·누가(대표/대표 아님 + 닉네임)·결과·비고. 대표와 직원 모두 본다(운영자 확인과 같은 기준). 계정 id 는 싣지 않는다(admin-console INV-K8). 자동 처리 현황의 「승인 서명 없이 열린 주소」 경보가 「열람 기록에서 확인해 주세요」라고 안내하던 자리가 이 화면이다.
- C1 문구 「권한이 없는 계정이라 열리지 않았어요」는 이 관리자 화면의 거부 사유로 남는다. 출고 화면에서 직원이 누를 때 나오는 「송장 출력은 대표만 할 수 있어요」는 그대로 둔다 — 할 일을 알려 주는 안내라 바꿀 까닭이 없다.
- 약관 제15조·개인정보 처리방침 8절의 열람 기록 문장을 「주소가 열린 기록을 전부 보고, 거부된 시도와 출력한 사람의 기록은 회사 안에서만 보관」으로 고쳤다. 시행 전이라 동의 판(TERMS_VERSIONS)은 올리지 않았다. 소개·첫 화면의 「누가 열었는지」 문구와 소개 화면의 예시 표 「연 사람」 칸도 뺐다.
- 주소 주인이 달라(봉인 속 크리에이터·역조공은 봉인 속 주문번호) 송장에 쓰지 않은 출력은 기존 「출력 실패」와 같은 돌려주기로 처리한다 — 출력 함수가 그 연 줄을 돌려받고(조건·상자당 2번 한도 그대로), 답은 여전히 거부이며 거부 줄은 운영자 내부 기록에 남는다. 크리에이터·팬 기록에 그 줄은 「출력 실패」, 다음 송장은 첫 출력, 이번 달 재출력에 세지 않는다(리뷰: 송장이 안 나왔는데 「첫 출력」으로 보이고 실제 첫 송장이 「재출력 2번째」였다). 관리자 기록은 앱이 한 번에 200줄(ADMIN_ACCESS_LOG_LIMIT)을 넘겨 읽고, 크리에이터 기록 화면의 늘 「열림」이던 결과 칸은 뺐다(마이그레이션 20261012000008).
- DB 는 일반 마이그레이션 20261012000007_access_log_internal.sql 하나 — 읽기 함수 넷(크리에이터 기록·이번 달 숫자·팬 몫 기록·운영자 내부 기록)이 공개 스키마 표만 읽어 개인정보 구역 패치가 필요 없었다. 기록 표와 쓰는 함수는 그대로다.

### E4 반영 때 정한 세부 (2026-10-12)

- 팔로워 목록 한 줄은 계정 ID(등록에 넘길 값)와 닉네임 둘뿐이다. 로그인 아이디도 싣지 않았다 — 팬에게 하는 안내가 「닉네임을 볼 수 있어요」라서 그 말보다 많이 보이지 않게 했다.
- 목록 순서는 최근에 팔로우한 팬부터. 같은 닉네임이 둘이면 얼굴 색으로만 갈린다.
- 팬 안내는 문구 둘을 한 곳에 두고 쓴다. 팔로우하는 자리(크리에이터 찾기 목록 위·크리에이터 페이지의 선물 보내기 칸·선물 보내기의 「먼저 팔로우」 띠·메인 새 크리에이터 칸·함께한 기록의 보내기 단추 밑)에는 「팔로우하면 크리에이터가 내 닉네임을 볼 수 있어요.」, 이미 팔로우한 팬이 보는 「팔로우한 크리에이터」 화면에는 「팔로우한 크리에이터는 내 닉네임을 볼 수 있어요.」. 로그인하지 않은 사람에게는 띄우지 않는다.
- 아이디 찾기와 그 횟수 제한(10분 30번)은 함께 없앴다 — 막던 것(아이디를 넣어 보며 팔로워를 모으기)이 이제는 목록으로 그냥 보이는 정보다. 횟수 기록 표는 나중 마이그레이션에서 표를 지우지 않는 규칙 때문에 남겼다(BACKLOG).
- 체크된 줄은 design-rules 의 「체크된 항목」 면(옅은 코랄, 글자 진한 코랄)을 쓰고, 상자 크기 고르기는 체크한 줄에만 펼친다. 10명을 고르면 남은 체크 칸이 잠긴다.
- 약관 제12조·개인정보 처리방침(팔로우 항목의 목적, 크리에이터에게 보이는 것)의 문장을 「팔로워 목록에는 팬의 닉네임만」으로 고쳤다. 시행 전이라 동의 판은 올리지 않았다.
- 차단은 지금 규칙(decline-block — 역조공과 상관없다) 그대로라 차단한 팬도 목록에 있고 보낼 수 있다.
- (리뷰 반영) 보낸 역조공 목록도 같은 기준으로 팬 로그인 아이디를 뺐다 — 크리에이터는 받는 팬을 닉네임으로만 본다(INV-R8 문장 고침, 마이그레이션 20261012000010). 약관 제12조·처리방침·안내서 E-12·문제집도 같이. 등록은 받는 팬의 팔로우 줄을 잠근 뒤 판정해 끊기와 겹쳐도 끊긴 뒤 상태로 거부한다(INV-R1). 크리에이터 페이지 「선물 보내기」 칸의 연달은 두 줄은 「팔로우한 크리에이터에게만 보낼 수 있어요. 팔로우하면 내 닉네임이 보여요.」 한 줄로 합쳤다(로그인하지 않은 사람에게는 앞 문장만). 10명을 고른 뒤 남은 체크 칸은 흐리게만 하고 포커스는 남긴다(design-rules 2절).

## 2026-10-12 (2) — 문제집 D 메모 추가 답 (사용자가 메모마다 단 답)

- 블루투스 제품 크리에이터 확인(D3 ②): 블루투스·RF 반응이지만 직원이 추적기가 아니라고 판정한 상자는 바로 통과시키지 않고 크리에이터에게 받을지 묻는다(받기 / 돌려보내기). 168시간 안에 답이 없으면 반송. 추적기는 지금처럼 바로 반송. 사용자 D3 「응 그렇게하자」(메모의 추천 ② 와 기한·기본값 추천). D2 의 「(가) 직원 판정으로 통과」는 직원 판정 단계로 남고, 그 뒤 크리에이터 확인이 붙는다.
- 거절 알림 문구(D11): 알림도 화면(C2)과 같이 거절했다는 뜻을 전한다 — 직접 거절·차단 거절은 C2 의 거절 문구, 7일 자동 반려는 「기간이 지나 반려됐어요」. 결제 금액을 돌려준다는 안내는 그대로. 사용자 D11 「거절됐다고는 전달해도 된다고 바꿨던거 같아」(C2 「크리에이터가 나를 피한다는 정보 정도는 괜찮아」). 차단 거절과 직접 거절은 계속 같은 문구.
- 미확인 상자 주인 확인(D14·D9): 주인 확인은 운송장 번호 대조로 한다(지금 「내 물건 찾기」와 같은 방식). 운송장 번호를 모르는 사람만 예외로 직원이 확인을 도와 처리한다. 원 송장에 주소·닉네임이 있으면 연락, 없으면 물품 보관소(미확인 물품 페이지)에 올려 연락을 받는다. 주인이 확인되면 반송비를 결제하거나 착불로 보낸다. 사용자 D14 「운송장 번호 확인으로 할 수 있으면 그렇게 하자 … 모르는 사람만 예외적으로 확인을 도와줘서」, D9. 물품 보관소의 구매 영수증 확인은 예외 처리 때만. 게시판 세부는 BACKLOG 그대로.
- 그대로인 것: D2·D5·D7·D10·D12·E4·E7 은 이미 만든 것과 같다. D4·D13 은 동작 변경 없음 — 문제 해설만 고친다.
- 역조공(E) 남은 메모: 역조공은 합포장 중계로 바꾸기로 했고(d57·d58) 설계는 나중이다. 남은 E 메모는 합포장 설계 때 다시 본다(사용자 「대답하다가 다른 방식으로 바꾸기로 했던 게 생각나서 하다가 말았어」).

### D3 ② · D11 문구 반영 때 정한 세부 (2026-10-12)

- 검수 결론에 「크리에이터 확인」을 새로 두었다. 블루투스·RF 반응이 있고 「추적기 아님」으로 판정한 상자는 결론이 「크리에이터 확인」 또는 「반송」 둘뿐이다 — 「통과」는 고를 수 없다. 반응이 없는 상자와 역조공에는 「크리에이터 확인」이 없다. 받으면 그대로 출고되므로 실측 기록 규칙(통과와 같음)을 그대로 건다.
- 확인 대기 상자의 상태는 옛 「보관」 값을 다시 쓴다(이제 「크리에이터 확인 대기」). 추적기 반송 뒤로 보관 상자가 생기지 않아 비어 있었고, 「검수 완료 + 168시간 → 반송 대기」 자동 처리 단계가 이미 그 값에 붙어 있다. 사무실 「들어온 상자」 목록에서는 검수 탭에 둔다(검수 결론이 아직 나지 않았다).
- 168시간은 검수 완료 스캔(크리에이터에게 묻는 순간)부터 센다. 기한이 지나면 자동 처리 전이라도 답을 받지 않는다(승인 기한과 같은 방식).
- 크리에이터 답 화면: 「승인·받은 선물」의 가운데 탭 「확인할 선물」. 답을 기다리는 상자가 있을 때만 보이고, 그때는 이 화면을 열면 그 탭이 먼저 열린다 — 알림 링크는 물음표 없는 고정 경로 규칙(INV-N9) 때문에 이 화면 자체로 온다. 줄마다 보낸 팬 닉네임·상자 순번·품목·주문번호·잡힌 신호(블루투스/무선 RF)·남은 기간, 버튼은 「받기」·「돌려보내기」 + 확인 창. 서명·주소는 없다 — 받기는 상자를 통과시킬 뿐이고 주소는 지금처럼 승인 서명 뒤 송장 출력 때만 열린다. 한 번 정하면 바꿀 수 없다.
- 크리에이터 알림 「확인할 선물」(creator_check)은 상자마다 한 번, 끌 수 없다(같은 주문의 두 번째 확인 대기 상자도 따로 묻는 것이라 알림도 따로 간다 — 리뷰 반영 때 「주문마다 한 번」에서 고침. 주문마다 한 번이면 두 번째 상자에는 알림이 안 가는데 직원 화면은 「알림이 갔어요」라고 보였다). 본문은 「받을지 정해 주실 상자가 있어요 · 7일 안에 정하지 않으면 보낸 분에게 돌려보내요」 — 보낸 팬·잡힌 신호는 쓰지 않는다(INV-N1). 기한이 지나 돌려보낼 때 크리에이터에게 따로 알리지 않는다.
- 팬에게는 묻는 동안 알리지 않는다(주문은 「검수하고 있어요」로 보인다). 크리에이터가 돌려보내거나 기한이 지나면 추적기 반송과 같은 「돌려보낼 상자」(hold_fan) — 「검수를 통과하지 못한 상자」라고만 쓰고 크리에이터가 돌려보냈다는 것은 쓰지 않는다. 확인 창에서 크리에이터에게도 그렇게 알린다.
- 묻는 동안의 주문(금속 반송 규칙과 맞춤): 확인 대기 상자는 주문 단계 계산에서 「검수 중」으로 센다 — 답이 나기 전에는 주문이 검수 단계에 머물고 검수 결과도 비어 있다. 다른 상자는 지금처럼 상자마다 진행한다.
  - 승인된 주문: 다른 상자는 확인을 기다리지 않고 출고된다. 받으면 그 상자도 출고, 돌려보내면 금속 반송과 같다(주문 검수 결과 「반송」, 그 상자 상품 대금 칸 환불).
  - 승인 전 주문: 승인 요청은 그대로 열려 있어 크리에이터가 승인·거절할 수 있다. 확인 대기 상자는 받기와 승인이 둘 다 있어야 출고된다. 돌려보내면 금속 반송과 같이 검수 결과가 「반송」이 돼 더 승인할 수 없다.
  - 묻는 사이 주문이 끝나면(거절·7일 반려·대표 취소) 질문은 닫히고 상자는 검수 완료 상자와 같이 바로 반송 대기로 간다. 이 상자는 검수 불합격이 아니라 끝난 주문의 상자라 환불은 「입고 뒤 거절·반려·취소」 줄 그대로다(돌려보낸 상자·기한 지난 상자만 검수 불합격 줄). 팬 「돌려보낼 상자」 알림도 가지 않는다.
- 돈 처리는 새 규칙 없이 기존 검수 불합격 줄을 쓴다 — 진행 중 주문은 주문 검수 결과 「반송」으로 이미 같은 줄을 타고, 끝난 주문의 상자 몫 계산에서 「검수에 걸림(0)」에 크리에이터가 돌려보냈거나 기한이 지난 상자를 더했다.
- 확인 대기 상자의 차액 결제는 막지 않는다 — 받으면 출고되는 상자라 미리 낼 수 있어야 한다. 낸 뒤 돌려보내면 금속 반송과 같은 돈 처리다(전에는 「보관」 상자의 차액을 막았다).
- 크리에이터 메인 카드·머리글의 「승인 대기 N건」에는 확인할 선물 수를 더하지 않았다(BACKLOG).
- 리뷰 반영 때 정한 세부: 자동 처리가 기한 지남으로 닫은 상자에 답하면 「이미 답한 상자」가 아니라 「기한이 지나 돌려보내는 상자」로 답한다(크리에이터가 답한 적이 없다). 나갈 수 없게 된 상자(차액 기한 지남 등)는 「확인할 선물」 목록에서 뺀다 — 답해도 「끝남」이 나는 상자다. 답 저장이 잠그는 사이 겹치면 「잠시 뒤 다시 시도해 주세요」(409)로 답한다. 검수 기록 표도 「추적기 아님」이면 크리에이터 확인·반송만 받는다(전에는 함수만 막았다).
- 거절 알림 문구(D11): 직접 거절·차단 거절·차단 뒤 결제는 「크리에이터가 선물을 원하지 않아요」(화면의 「OO님이 선물을 원하지 않아요」와 같은 문구 조각을 쓰고, 알림에는 크리에이터 이름을 넣지 않는다), 7일 반려는 「보내신 선물이 기간이 지나 반려됐어요」, 둘 다 「결제 금액은 돌려드려요」. 어느 문구인지는 알림을 꺼낼 때 DB 가 주문 상태(거절 / 기간 지남)로 정한다 — 앱이 넘기는 값이 아니고, 차단 표시는 읽지 않아 차단 거절도 직접 거절과 같은 값이다. 갈래 값이 없는 줄(새 앱 + 옛 DB)은 보내지 않고 건너뛴다. 설정 화면 이름 「전해지지 못한 선물」은 그대로 두었다.

- 그래서 추가분 2의 「답장 스토리용 세로 카드」(답장 공유에서 X용/스토리용 고르기)는 하지 않는다. 스토리 세로 카드(1080×1920)는 정사각 공지 이미지를 세로로 옮긴 크리에이터 홍보 이미지이고, 「내 팬꾹 꾸미기」의 공지 이미지 세 크기 중 하나다. 팬의 답장 공유 카드(정사각·X 가로, gift-reply INV-G9)는 그대로 둔다.
- 감사 답장: 사용자 「선물을 받고 "OO님에게 감사의 메세지를 전해보세요!" 하고 짧게 보내거나 정해진 문구를 선택해서 보낼 수 있게 한다」 — 이미 정해진 문구 다섯 중 하나 + 선택 한 줄(80자)로 되어 있다. 답장 창 제목만 「{닉네임}님에게 감사의 메시지를 전해 보세요!」로 바꿨다.

## 2026-10-14 — 홍보 카드(공지 이미지) 구성: 직접 부탁 문구 빼고 크리에이터 프로필로

- 공지 이미지 세 크기(정사각·스토리 세로·가로)에 같은 구성을 쓴다. 지금 정사각 공지 이미지(「선물은 팬꾹으로 받아요 · 승인한 선물만 받습니다」)도 이 구성으로 바꾼다.
- 프로필 배경사진은 새 칸이다 — 프로필 사진 올리기와 같은 처리(EXIF 제거·다시 굽기)를 따른다.

## 2026-10-14 — 「내 팬꾹 꾸미기」·홍보 카드 시안 승인 (카드 d82 「추천대로」)

- 휴대폰 미리보기는 편집 칸 위에 붙고 접을 수 있게(B안). 프로필 배경사진은 홍보 카드와 링크 페이지 맨 위 둘 다에 쓴다. 스토리 카드는 시안대로. 메뉴는 「관리」 묶음 주소 관리 위. 디자인 기준 10절.
- 범위: 출시 때 할 것(함께한 크리에이터 표시·링크 이름 선점·사전 신청)과 답장 스탬프는 이번에도 만들지 않는다.

## 2026-10-14 — 「내 팬꾹 꾸미기」 구현에서 정한 것

- 홍보 카드(공지 이미지)는 로그인 없이 열리는 공개 주소 `/api/notice/{id}?size=square|story|wide` 로 바꿨다 — 「링크 복사」로 남에게 줄 수 있어야 하고, 스펙의 「공개 화면」에 공지 이미지가 들어 있다. 링크용 아이디가 없거나 확인 전이면 404. 내용은 공개 칸뿐(INV-E7·E10).
- 배경사진·심볼은 프로필 사진과 같은 공개 읽기 저장소(creator-photos — 2026-10-11 ⑫ 의 유일한 예외)에, 서버만 쓴다. 배경사진 긴 변 1280, 심볼 512 정사각.

## 2026-10-14 — 로그인·가입 화면, 주소 입력 시점

- 로그인·회원가입은 모달로 바꾸지 않고 지금처럼 페이지로 둔다(사용자 「페이지로 하자 우선」). 가입은 세 단계라 모달에 담으면 휴대폰에서 전체 화면을 덮고, 메일 확인·비밀번호 재설정·로그인 만료가 들어올 주소가 어차피 필요하다.
- 가입할 때는 주소를 받지 않는다. 가입 뒤 설정에서 등록하거나, 승인(팬은 역조공 받기)을 누를 때 등록 전이면 「주소를 입력해 주세요」, 등록돼 있으면 「주소를 확인해 주세요」 창을 띄워 확인·수정하게 한다(사용자 지시). 확인 창에 무엇을 보여 줄지는 카드 d83 에서 「이름표와 날짜만」으로 정했다(사용자 「추천대로」).
- 이름표는 자유 입력이 아니라 집·작업실·사무실·기타 넷 중에서 고른다 — 자유 입력이면 「역삼동 집」처럼 주소가 평문으로 DB 에 남을 수 있다. DB 칸도 이 넷만 받는다(구현 선택, 되돌리기 싸다).
- 주소 없는 승인은 DB 승인 함수가 「주소 없음」으로 거부한다. 승인 창에서 주소를 처음 등록하면 주소 서명과 승인 서명을 따로 받는다 — 둘을 한 서명으로 묶으면 주소 보호·승인 서명 스펙을 함께 바꿔야 해서 이번에는 하지 않았다.
- 팬은 지금처럼 역조공마다 주소를 새로 입력하고 계정에 저장하지 않는다(사용자 「추천대로」).
- 사이드바 재편은 사용자가 나머지를 확인해 알려 주기로 했다. 그동안 정한 것: 합포장은 메뉴에 「준비 중」으로만 두고 설계는 배포 뒤로, 이름은 지금처럼 「역조공」= 크리에이터가 자기 팬에게, 다른 크리에이터에게는 「선물」(사용자 「추천대로」).
- 크리에이터 사이드바는 시안 v19 A안으로 간다(카드 d84, 사용자 「A로 하자」) — 받기·보내기·내 팬꾹으로 묶고, 「팬에게 보내기」 아래 「몇 명에게」「합포장(준비 중)」을 늘 펼쳐 둔다. 접힌 사이드바에서는 하위를 숨긴다. design-rules 11절.

## 2026-10-14 — 로그인 뒤 본문 폭을 v18 이전으로

- 로그인 뒤 목록·관리 화면의 본문 글 폭을 최대 1200 으로 되돌렸다(v18 시안은 1440). 사용자: 「내가 넓히라고 했던건 푸터 뿐이었어」 — v18 반영 때 시안의 1440 이 따로 묻지 않은 채 같이 들어왔다. 안쪽 여백 40 과 사이드바를 뺀 남은 영역의 가운데에 두는 것은 그대로다. design-rules 00절.
- 이어서 사용자: 「기본은 원래대로하고, 넓은 너비가 필요한 섹션만 넓게」 — 넓어야 하는 구간만 최대 1360 으로 펼친다. 어느 구간을 넓힐지는 정해 진행했다(되돌리기 싸다, 클래스 하나): 카드가 여러 열로 늘어나는 격자 둘(크리에이터 찾기·팔로우한 크리에이터)과 칸이 많은 열람 기록 표. 제목·설명·검색창·탭·안내 판은 1200 에 둔다 — 글줄이 너무 길어지면 읽기 어렵기 때문이다.

## 2026-10-15 — 하늘색·고양이 로고로 브랜드 교체 (카드 d86)

- 색은 시안 v20 C안(흰 바탕 · 옅은 하늘 사이드바 · 하늘색 버튼)으로 간다. 사용자: 「응 일단 이렇게 하자」. 기준은 design-rules 000절.
- 로고는 사용자가 붙여 넣은 그림(하늘색 상자 안 흰 고양이)을 그대로 옮겨 쓴다. 사용자: 「로고 나중에 하고 일단 지금 내가 붙여넣은걸로하자」 — 로고 디자인은 나중에 다시 본다.
  로고 안 남색(눈)은 로고 안에서만 허용하고, 로고 하늘색은 사이트 하늘색과 맞추지 않고 원본대로 둔다(추천안, 사용자 「그래 일단 그걸로 가자」).
- 하늘색은 흰 바탕 대비 1.7:1 이라 면에만 쓴다. 글자·선택 테두리·초점 테두리는 짙은 회색이다 — 선택·초점 표시는 3:1 이 업계 기준(WCAG 1.4.11)이라서다. 하늘색 버튼 위 글자도 흰색 대신 짙은 회색이다(8.8:1).
- 시안은 랜딩 구간 제목을 하늘 그라데이션 글자로 칠했지만, 32px 큰 글자 기준 3:1 에도 못 미쳐 실제 화면에서는 강조 낱말 아래 형광펜 띠로 바꿨다.
- 리뷰 뒤 정리(스스로 정함, 되돌리기 쌈): 체크박스·라디오 켜짐 색을 하늘색에서 짙은 회색으로 — 켜진 칸이 흰 바탕과 1.7:1 이라 선택 표시 3:1 기준(위 줄과 같은 근거)에 못 미친다. 「보낸 내역」 두 화면의 탭은 페이지 제목 아래로 — 페이지 머리는 늘 본문 맨 앞(00절).
- 열람 기록 표도 1200 으로 되돌렸다(2026-10-15). 사용자: 「열람 기록 표도 꼭 필요한 부분은 아닌 것 같은데」. 넓은 구간은 카드 격자 둘만 남는다. design-rules 00절.

## 2026-10-15 — 추가 요청 3 중 스스로 정한 것

- 사이드바는 처음에 펼친다(사용자 「기본은 open」). 저장값이 생긴 뒤에는 그 값을 따르므로 페이지를 옮겨도 유지된다. 이전 「1024 이하 기본 접힘」은 버렸다.
- 아이디·닉네임 미리 확인은 입력을 멈춘 뒤 0.4초에 자동으로 묻고(업계 표준), 한 접속 주소당 1분 30번을 넘으면 1분 쉰다(판단 — 사람이 타이핑으로 넘기기 어려운 수, 긁기는 막는 수). 버벅이면 버튼 방식으로 바꾼다(사용자 조건).
- 닉네임 경계는 내 정보의 1~12자를 그대로 쓰고, 계정마다 다르게(대소문자·앞뒤 공백 무시) 했다. 금칙어 필터는 태그·팬덤 이름과 같은 것. signup INV-U13·U14.
- 화면 구성 원칙(단계별·좌우 카드 지양)은 design-rules 0000절에 적었다. 지금 화면 중 어긋나는 후보(카드 좌우 나열 24곳 중 한 줄로 바꿀 후보·판단 필요)는 따로 뽑아 두었고, 고치는 것은 시안 단계에서 같이 본다.

## 2026-10-15 — 추가 요청 3 정할 것 다섯 (카드 d87 「추천대로」)

1. 무통장 입금은 주문마다 입금 전용 계좌를 내 주는 방식(토스 가상계좌, 지금 계약 그대로) — 업계 표준. 입금되면 자동 확인, 입금 기한 24시간(지나면 주문 취소), 환불은 팬이 환불 계좌를 한 번 입력.
2. 선물 이름(20자)·내용(200자)은 보낸 팬 본인만 본다. 선물 상세·보낸 선물 목록에 나온다.
3. 크리에이터 퍼스널 컬러는 크리에이터 페이지 배경 띠·프로필 사진 테두리에만, 팬컬러는 팬덤 뱃지 색에만. 색은 자유, 그 위 글자는 대비로 검정·흰색 자동.
4. 팬 프로필(사진·소개·배경)은 본인과 그 팬의 승인 요청을 받은 크리에이터에게만. 사진은 공개 저장소에 두지 않고 잠깐만 열리는 주소로.
5. 선물 보낸 뒤 화면은 상자별 진행 상태 한 줄만. 송장번호는 원하는 사람만 상자 상세에서. 팬꾹이 요청한 조치(늦은 도착·받는 주소 없이 온 상자·추가 결제)만 새 「추가 조치」 페이지에 카드로, 사이드바·홈에 「해야 할 일 N건」. 팬 선물·역조공 둘 다.

## 2026-10-15 — 무통장 입금은 일단 뺀다 (사용자)

- 사용자: 「무통장 입금은 일단 빼줘. 토스페이먼츠로 심사 요청했고, 신용카드, 체크카드, 계좌이체, 간편결제로 삼성페이, SSG Pay, 페이코, L.Pay, 카카오페이, 네이버페이, 토스페이, 애플페이를 신청했다.」

- 같이 빠질 뻔한 것: 관리자 결제 목록의 역조공 줄 크리에이터 공개 이름 수정은 무통장 마이그레이션 안에 있었다 — 새 마이그레이션 20261015000011 로 따로 살렸다.

## 2026-10-15 — 로그인 후 본문 폭을 내용 종류별로 (카드 d89)

- ④ 팬 주소: **저장으로 바꿈** — 팬도 크리에이터처럼 가입 때는 받지 않고 설정에서 등록해 두고 계속 쓴다. 반송·역조공 때 등록 전이면 「주소를 입력해 주세요」, 등록돼 있으면 「주소를 확인해 주세요」 창(크리에이터와 같은 흐름, 업계 표준 — 쇼핑몰 배송지). 2026-10-14 「팬은 역조공마다 새로 입력하고 저장하지 않는다」와 같은 날 규칙 4 「송장 출력 후 삭제」를 뒤집는다(사용자 「추천대로」, 사용자는 처음부터 저장으로 알고 있었다). 처리방침에 팬 주소 보관(지우거나 탈퇴할 때까지)을 적는다. BACKLOG 「팬 주소 저장 선택」은 이걸로 닫는다.
- ⑤ 개봉 조건 추가: 탐지기 반응이 있는 상자 + **추적기로 판정된 적이 있는 팬**의 상자(어느 크리에이터에게 보낸 것이든)는 반응과 상관없이 연다. 등록 화면에 미리 알리지 않는다(걸린 팬에게만 뜨면 표시된 사실이 드러난다). 크리에이터 화면에는 아무것도 보이지 않고 검수 화면에만 개봉 사유. 「처음 보내는 팬 + 전자기기」는 열지 않는다 (사용자 「처음팬이어도 굳이 열지 않는다. 열어보는 것은 탐지기에 걸린것과, 과거 걸렸던 이력이 있는 사람만 연다」 → 기준 「추천대로」).
- ② 고침(같은 날, 스펙 초안 뒤) — 반송 주소는 「보낸 주소로 받기」 없이 **등록 주소 확인 창 하나**: 등록 주소가 뜨고 「바꾸기」 또는 그대로 「확인」을 눌러야 반송이 나간다. 등록 전이면 그 자리에서 입력. 확인하지 않으면 14일 재알림·30일 처분은 그대로. 사용자: 「반송 직전에 입력한 주소가 있으면 뜨게하고, 원하면 바꿀 수도 있게해. 안바꿀거면 선택·확인 하게 해서 진행하게하고」. 그 앞에 사용자가 파생 질문이 계속 생긴다며 정책이 복잡한 것 아니냐고 물었고, 「사람이 답할 때까지 멈춰 있는 상태」가 아홉 개로 늘어난 것이 원인이라고 답했다.

## 2026-10-17 — 팬의 「제가 보낸 게 아니에요」를 없앤다

- 바꾼 곳: inbound-address-code INV-C8·S8·S9c, notifications INV-N14 표, action-center, 용어집 not_mine 행.

## 2026-10-17 — 크리에이터 카드 C안(가운데 정렬) · 작은 뱃지·칩 · 같은 모양 유지 (카드 d103)

- 이유: 페이지 61개가 모두 요청마다 새로 그리는 페이지이고 로딩 화면이 0개라, Next.js 는 누른 뒤 서버 응답이 올 때까지 화면을 멈춰 두었다(공식 문서 「Dynamic routes without loading.tsx」). 로딩 화면이 있으면 Next 가 그 화면을 미리 받아 두어 누르는 즉시 바뀐다.
- 버린 안: 페이지를 통째로 미리 받기(prefetch={true}) — 미리 받은 화면을 최대 5분 그대로 보여 줘 선물 상태·승인 대기가 몇 분 전 값으로 보일 수 있다.

## 2026-10-18 — 링크에 마우스를 올리면 그 페이지를 통째로 미리 받기 (30초)
