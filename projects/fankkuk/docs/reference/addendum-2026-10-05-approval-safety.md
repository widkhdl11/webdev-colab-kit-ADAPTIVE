# 팬꾹 추가분 3 — 승인 후 주소 노출 경로 차단과 악성 요청 방어 (2026-10-05)

이 문서는 기존 design-source.md·decisions.md·kickoff 요청, 추가분 1(`addendum-2026-10-02-screens.md`), 추가분 2(`addendum-2026-10-02-creators-sponsorship.md`)에 **더하는 내용만** 담는다. 겹치는 부분이 있으면 이 문서의 "1. 바뀌는 것"이 우선하고, 그 밖에는 앞 문서들이 정본이다.

넣는 곳: `projects/fankkuk/docs/reference/addendum-2026-10-05-approval-safety.md`

번호 규칙: 추가분 2가 불변식 31, 요청 항목 24, 결정 D-16, 기능 F-15까지 썼으므로 이 문서는 불변식 32, 요청 항목 25, 결정 D-17, 기능 F-16부터 붙인다. 네 쪽 문서 번호가 다르면 이 부분만 맞춘다.

## 0. 이 문서가 답하는 질문

1. 크리에이터가 누군지 모르는 사람의 요청을 습관적으로 승인하면, 승인으로 풀린 주소가 요청자에게 노출되는가?
2. 악성 코드가 담긴 승인 요청을 보내 승인을 받으면, 풀린 주소값을 악성 유저가 받아 볼 수 있는가?

답: 둘 다 설계상 경로가 없다. 승인은 "팬꾹 사무실에서 송장을 출력할 때 주소를 열어도 된다"는 허락이고, 주소는 송장 출력 함수 안에서만 풀려 택배사 API와 프린터로만 나간다. 요청자가 바꿀 수 있는 건 주문 내용뿐이고 결과가 나가는 곳은 바꿀 수 없다. 이 문서는 그 전제가 구현에서 깨지지 않게 하는 조건과, 모르는 사람을 승인할 때 남는 실제 위험(상자 속 추적 장치)에 대한 보완을 정한다.

## 1. 앞 문서에서 바뀌는 것

| 항목 | 앞 문서 | 변경 |
| --- | --- | --- |
| 크리에이터 설정의 주소 표시 | 주소 등록·재등록 | 등록한 주소 전체를 다시 보여주지 않는다. 앞부분만 표시(예: "서울 강남구 ○○로 ****"). 수정은 새로 입력하는 방식만 |
| 송장 출력 | 승인 토큰 확인 후 출력 | 보내는 사람 칸을 팬꾹 사무실 주소·전화로 고정. 팬 이름·연락처는 송장 어디에도 들어가지 않음 |
| 송장 품목 칸 | 팬이 입력한 물품 종류 | 등록 화면의 정해진 품목 목록 값만 사용. 팬의 자유 입력(한마디 등)은 송장에 들어가지 않음 |
| 승인 화면 | 팬 닉네임, 물품 종류, 승인·거절 | + "처음 보내는 팬이에요" 표시, + 승인 버튼 위 안내 두 줄(F-17) |
| 개봉 검수 조건 | 신고 불일치, 밀봉 깨짐 등 | + 위험 신호 기반 개봉(F-18) |
| 크리에이터 설정 | 추가분 1·2 항목 | + "처음 보내는 팬의 선물은 항상 열어서 확인" 켜기(기본값 꺼짐) |
| 팬에게 보이는 날짜 | 단계별 시각 | 날짜 단위까지만. 시각은 보여주지 않음 |
| 이미지 업로드 | EXIF 제거 | + SVG 금지, 허용 형식 JPEG·PNG·WebP만, 서버에서 다시 인코딩해 저장 |

## 2. 새 기능 상세

### F-16. 승인 후 주소를 보는 대상과 막는 조건

| 대상 | 주소를 보나 | 조건 |
| --- | --- | --- |
| 요청한 사람(팬) | 보지 않음 | 팬 화면에는 사무실 주소와 단계 이름만. 운송장 번호 비공개. 날짜 단위까지만 |
| 팬꾹 서버 | 송장 출력 순간에만 복호화, 즉시 폐기 | 승인 토큰 + 격리된 복호화 함수(불변식 5) |
| 대표 계정 | 라벨 종이로 봄 | 출력 기록이 크리에이터 열람 로그에 남음 |
| 택배사·기사 | 봄 | 배송에 필요. 어느 배송 서비스나 같음 |
| 크리에이터 본인 화면 | 앞부분만 | 화면에 주소 원문이 없으면 다른 결함(XSS 등)이 생겨도 화면에서 가져갈 것이 없음 |
| 상자 안 추적 장치 | 도착 후 위치를 보낼 수 있음 | 검수가 막아야 하는 실제 위험(F-18) |

송장의 "보내는 사람"을 팬꾹으로 고정하는 이유:

1. 택배사의 배송 완료 문자·배송 문제 연락이 보내는 사람에게 가므로, 팬이 보내는 사람이면 배송 진행이 팬에게 전달된다.
2. 배송 실패·수취 거부 시 반송이 보내는 사람에게 가므로, 팬이 보내는 사람이면 상자가 팬에게 돌아가며 그 과정에서 배송지 정보가 노출될 수 있다.
3. 보내는 사람이 팬꾹이면 반송은 사무실로 오고, 사무실에서 팬의 원 송장 주소로 다시 처리한다(앞 문서의 반송 규칙 그대로).

### F-17. 승인 화면 안내와 사칭 연락 방지

승인 버튼 바로 위 고정 문구:

> 승인해도 보내는 분에게 주소는 보이지 않아요.
> 상자는 팬꾹이 추적 장치 검수를 거쳐 보내 드려요.

처음 보내는 팬 표시: 이 크리에이터에게 처음 요청하는 팬이면 승인 요청 카드에 "처음 보내는 팬이에요"를 표시한다. 팬의 다른 크리에이터 이용 이력은 보여주지 않는다.

사칭 연락 방지:

1. 크리에이터 가입 완료 화면, 설정 화면, 알림톡 하단에 "팬꾹은 채팅·메일·전화로 주소를 묻지 않아요. 주소를 다시 알려 달라는 연락은 팬꾹이 아닙니다"를 표시한다.
2. 주소 재등록은 크리에이터가 설정 화면에서 직접 하는 방법만 있다. 팬꾹 운영자가 주소 재등록을 요청하는 링크를 보내는 경로를 만들지 않는다.
3. 배송 실패로 주소 확인이 필요한 경우에도 알림은 "설정에서 주소를 다시 확인해 주세요"만 보내고 링크를 넣지 않는다. 크리에이터가 앱·사이트를 직접 열어 들어가게 한다.

### F-18. 모르는 사람 승인에 대한 보완: 위험 신호 기반 개봉 검수

승인이 형식이 되면 위험은 상자 내용물로 몰린다. 아래 조건에 해당하는 상자는 밀봉·신고 여부와 상관없이 개봉 검수로 돌린다. 요금은 같다(단일 요금 원칙 유지).

| 신호 | 처리 | 크리에이터에게 보이는 것 |
| --- | --- | --- |
| 처음 보내는 팬 + 전자기기 신고 | 개봉 검수 | "처음 보내는 팬이에요" |
| 가입 7일 안 계정이 24시간 안에 크리에이터 3명 이상에게 요청 | 운영자 확인 대기 + 개봉 검수 | 표시 없음 |
| 다른 크리에이터들에게 2회 이상 차단된 계정 | 개봉 검수 | 표시 없음(차단 이력은 팬 개인정보라 공개하지 않음, 팬꾹 내부에서만 사용) |
| 크리에이터가 "처음 보내는 팬의 선물은 항상 열어서 확인"을 켬 | 처음 보내는 팬의 상자는 전부 개봉 | 설정 화면에 켜짐 표시 |

수치(7일, 3명, 24시간, 2회)는 설정값으로 두고 운영하며 조정한다. 관리자 검수 화면에는 개봉 사유를 "위험 신호: {사유}"로 표시한다.

### F-19. 악성 요청 방어 (구현 조건)

악성 유저가 노릴 수 있는 경로와 막는 조건:

| 시도 | 막히는 이유 | 지켜야 할 조건 |
| --- | --- | --- |
| 승인 후 주소를 응답으로 받기 | 복호화 결과는 택배사 API 호출과 라벨 출력에만 쓰이고 즉시 폐기 | 송장 출력 함수가 주소를 응답·로그·에러·DB·분석 도구 어디에도 남기지 않음 |
| 요청 내용에 스크립트를 넣어 크리에이터 화면에서 실행(XSS) | 화면은 입력값을 글자로만 표시 | 1. 사용자 입력을 HTML로 그리지 않음(`dangerouslySetInnerHTML` 금지, 마크다운 렌더링 금지) 2. CSP(콘텐츠 보안 정책)로 인라인·외부 스크립트 차단 3. SVG 업로드 금지 |
| XSS가 성공했을 때 크리에이터 화면에서 주소 훔치기 | 화면에 주소 원문이 없음 | 크리에이터 설정에서도 주소 앞부분만 표시. 주소를 반환하는 API 자체가 없음 |
| 주문 정보를 조작해 다른 주문의 주소를 열게 하기 | 승인 서명 원문에 주문번호가 들어 있고 서버가 대조 | 송장 출력 함수의 입력은 주문번호 + 승인 토큰뿐. 둘이 맞지 않으면 거부(불변식 11) |
| 결과를 받을 외부 주소(웹훅·콜백)를 넣기 | 사용자가 지정하는 외부 전송 주소가 없음 | 사용자 입력 URL로 서버가 데이터를 보내는 기능을 만들지 않음 |
| 채널 링크에 내부 주소를 넣어 서버가 읽게 하기(서버 측 요청 위조) | 채널 확인 때 서버가 요청하는 곳은 허용 도메인뿐 | 서버의 외부 요청은 허용 도메인 목록(지원 플랫폼, 택배사 API, 카카오, 국세청, PG)으로만. 리다이렉트를 따라갈 때도 목록 검사 |
| 물품명에 긴 문자열·특수 문자를 넣어 송장·라벨 깨뜨리기 | 송장 품목은 정해진 목록 값 | 자유 입력은 송장·라벨·알림톡 어디에도 들어가지 않음 |
| 한마디·답장에 링크를 넣어 피싱 | 링크가 눌리지 않음 | 사용자 입력 텍스트의 URL을 자동 링크로 만들지 않음 |
| 이미지 파일에 다른 형식을 숨겨 올리기 | 서버가 다시 인코딩 | 허용 형식 JPEG·PNG·WebP만, 확장자가 아니라 파일 내용으로 형식 판별, 서버에서 다시 인코딩해 저장 |

## 3. 봉인 불변식 추가 (32~39)

32. 송장의 보내는 사람 칸은 항상 팬꾹 사무실 주소·전화다. 팬의 이름·주소·연락처는 송장·라벨·택배사 API 요청 어디에도 들어가지 않는다.
33. 주소 원문(크리에이터 본인 주소 포함)을 반환하는 API·화면은 없다. 크리에이터 설정은 주소 앞부분만 표시하고, 수정은 새로 입력하는 방식만 있다.
34. 사용자 입력은 HTML·마크다운으로 렌더링하지 않는다. `dangerouslySetInnerHTML`을 쓰지 않는다. 사용자 입력 텍스트의 URL을 자동 링크로 만들지 않는다.
35. 응답 헤더에 CSP를 적용해 인라인 스크립트와 허용 목록 밖 스크립트를 차단한다.
36. 이미지 업로드는 JPEG·PNG·WebP만 허용하고, 파일 내용으로 형식을 판별하며, 서버에서 다시 인코딩하고 EXIF를 제거해 저장한다. SVG는 받지 않는다.
37. 서버가 외부로 보내는 요청은 허용 도메인 목록(지원 플랫폼, 택배사 API, 카카오, 국세청, PG, 알림 발송)으로만 나간다. 사용자 입력 URL로 서버가 데이터를 보내는 기능은 없다. 리다이렉트도 목록을 검사한다.
38. 송장 품목·라벨·알림톡 본문에는 정해진 목록 값과 고정 문구만 들어간다. 팬의 자유 입력(한마디, 답장 추가 문장, 팬덤 이름 제외)은 들어가지 않는다.
39. 팬꾹은 크리에이터에게 채팅·메일·알림으로 주소 입력 링크를 보내지 않는다. 주소 재등록은 크리에이터가 설정 화면에 직접 들어가서 하는 방법만 있다.

## 4. 요청 항목 추가 (25~28)

25. 송장 발행 규칙(F-16): 보내는 사람 고정, 품목 칸은 목록 값만, 택배사 API 요청 본문 검사로 팬 정보 0건 확인.
26. 승인 화면 보강(F-17): 처음 보내는 팬 표시, 승인 버튼 위 안내 두 줄, 사칭 연락 안내 문구(가입 완료·설정·알림톡 하단), 링크 없는 주소 확인 알림.
27. 위험 신호 기반 개봉 검수(F-18): 신호 계산(처음 보내는 팬 + 전자기기, 신규 계정 다수 요청, 차단 이력), 설정값, 관리자 검수 화면의 개봉 사유 표시, 크리에이터 설정 "처음 보내는 팬 선물 항상 열어서 확인".
28. 악성 요청 방어(F-19): CSP 헤더, 이미지 업로드 검증·재인코딩, 서버 외부 요청 허용 목록, 크리에이터 주소 앞부분 표시, 자동 링크 없음.

배포 전 검사 게이트에 추가: 불변식 32~39 계약 테스트.

1. 송장 생성 결과와 택배사 API 요청 본문에 팬 이름·연락처 0건.
2. 모든 API 응답에서 주소 원문 패턴 0건(크리에이터 본인 계정으로 호출한 응답 포함).
3. 코드 검색으로 `dangerouslySetInnerHTML` 0건, 사용자 입력 렌더링 경로에 마크다운 렌더러 0건.
4. 응답 헤더에 CSP 존재.
5. SVG 업로드·확장자 위장 파일 업로드 거부, 저장된 이미지에 EXIF 0건.
6. 허용 목록 밖 도메인·내부 IP(`127.0.0.1`, `169.254.169.254`, 사설 대역)로의 서버 요청 시도가 차단됨.
7. 한마디에 `<script>`·`javascript:`·URL을 넣은 요청이 크리에이터 화면에서 글자 그대로 보이고 실행·링크되지 않음.

구현 순서: 25·28은 송장 출력(기존 항목 6)과 같은 단계에서, 26은 크리에이터 화면 단계에서, 27은 검수 단계에서 함께 구현한다.

## 5. 완료 판정 추가

1. 악성 요청 시나리오: 한마디에 스크립트와 피싱 링크를 넣은 요청 등록 → 크리에이터 승인 화면에 글자 그대로 표시, 실행·링크 없음 → 승인 → 출고 → 요청자 계정의 모든 화면·API 응답에서 크리에이터 주소 0건, 운송장 번호 0건, 시각 정보 0건.
2. 송장 시나리오: 출력된 라벨의 보내는 사람이 팬꾹 사무실, 품목이 목록 값, 팬 정보 0건.
3. 위험 신호 시나리오: 신규 계정으로 크리에이터 3명에게 24시간 안에 요청 → 운영자 확인 대기 + 개봉 검수로 표시 → 크리에이터 화면에는 신호 표시 없음.
4. 크리에이터 본인 화면: 설정에서 주소가 앞부분만 보이고, 주소를 반환하는 API 호출 경로가 없음.

## 6. 결정 기록 추가 (decisions.md에 이어 붙임)

### D-17. 승인은 주소를 요청자에게 여는 것이 아니라 송장 출력을 허락하는 것이다

- 결정: 승인 후에도 요청자는 사무실 주소와 단계 이름만 본다. 주소는 송장 출력 함수 안에서만 풀리고 택배사·프린터로만 나간다. 송장의 보내는 사람은 팬꾹으로 고정한다.
- 이유: 크리에이터는 누군지 모르는 요청도 습관적으로 승인할 수 있다. 승인의 의미를 "주소 공개"가 아니라 "팬꾹이 처리해도 된다"로 고정해야 습관적 승인이 주소 노출로 이어지지 않는다. 보내는 사람이 팬이면 택배사 연락과 반송이 팬에게 간다.

### D-18. 모르는 사람 승인의 위험은 상자 내용물로 보고 위험 신호 기반 개봉으로 막는다

- 결정: 처음 보내는 팬 + 전자기기, 신규 계정 다수 요청, 차단 이력 계정의 상자는 개봉 검수. 요금은 같다. 크리에이터에게는 "처음 보내는 팬" 표시만 보이고 차단 이력은 보이지 않는다.
- 이유: 승인이 형식이 되면 실제 위험은 추적 장치다. 차단 이력은 팬 개인정보라 공개하지 않고 팬꾹 내부 판단에만 쓴다.
- 버린 대안: 크리에이터에게 팬의 차단 이력 공개(팬 프라이버시 침해, 낙인), 처음 보내는 팬 전부 개봉(노동 증가, 크리에이터 선택 옵션으로만 둠).

### D-19. 주소 원문은 크리에이터 본인 화면에도 다시 보여주지 않는다

- 결정: 주소는 등록 시 브라우저에서 암호화되고, 이후 어떤 화면·API도 원문을 반환하지 않는다. 크리에이터 설정은 앞부분만 표시하고 수정은 새로 입력한다.
- 이유: 화면에 주소 원문이 있으면 XSS 같은 다른 결함이 하나만 생겨도 그 화면에서 주소가 새어 나간다. 원문이 화면에 없으면 다른 결함이 생겨도 가져갈 것이 없다.

### D-20. 사용자 입력은 글자로만 다루고, 서버의 외부 요청은 허용 목록으로만

- 결정: 사용자 입력을 HTML·마크다운으로 그리지 않고, URL을 자동 링크로 만들지 않고, CSP를 적용하고, SVG를 받지 않는다. 서버의 외부 요청은 허용 도메인 목록으로만 나가고, 사용자가 지정한 외부 주소로 데이터를 보내는 기능을 만들지 않는다.
- 이유: 악성 요청이 노릴 수 있는 경로는 크리에이터 화면에서 코드 실행(XSS)과 서버가 엉뚱한 곳에 요청하게 만들기(서버 측 요청 위조)다. 두 경로를 구조로 닫는다.
