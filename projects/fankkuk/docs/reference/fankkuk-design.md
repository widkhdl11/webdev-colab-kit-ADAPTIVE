# 팬꾹(fankkuk) 설계 정리 — 팬 선물 배송 대행 서비스

2026-09-30 · Howlyn

## 서비스 개요와 팬심 대비 차별점

팬이 보낸 선물을 사무실에서 받아 크리에이터에게 실명·주소 없이 전달하는 대행 서비스다. 팬심(선물 중개 서비스, 2026-09-18 실명·닉네임 유출 사고)의 대체를 목표로 하며, 운영 우선순위는 1. 보안 2. 속도 3. 상태 확인이다. 핵심 무기는 필수 검수·비복호화·승인 시스템·직원 최소 노출 네 가지이고, 여기에 사용자 경험(상태 확인 화면·디자인)을 더한다.

| 항목 | 팬심 | 이 서비스 |
| --- | --- | --- |
| 주소 보관 | 서버가 평문 조회 가능 (후기 화면에 실명 컬럼이 섞여 유출) | 크리에이터 승인 없이는 서버도 복호화 불가 |
| 승인 | 없음, 도착하면 발송 | 팬 등록 시점에 크리에이터 승인, 건별 |
| 열람 기록 | 비공개 | 복호화 로그를 크리에이터에게 전부 공개 |
| 검수 | 불명 | 필수: 전 건 원 송장 제거 + 겉면 탐지, 조건부 개봉. 단일 요금에 포함 |
| 광고 문구 | — | 메인: "크리에이터가 승인한 선물만 배송" / 크리에이터 화면: "승인 없이는 저희도 주소를 열 수 없습니다" |

초기 공급자(크리에이터) 확보는 이번 설계 범위에서 제외했다. 사무실은 선릉의 지인 사무실을 쓴다(임대료 0~일부 부담, 택배 수십 개 수령 가능). 서울 강남권에서 집하된 택배는 그날 밤 경기 남부 허브로 들어가므로 속도는 경기 남부 임대와 같다.

## 보안 구조: 크리에이터 승인 키 분할(C 구조)

DB와 서버 키를 모두 탈취당해도 크리에이터 기기 없이는 주소가 열리지 않는다. 사고 한 번의 피해를 전원에서 1명으로 제한하는 것이 목적이다.

1. 크리에이터가 주소를 등록하면 브라우저에서 무작위 데이터 키로 주소를 암호화한다. 서버는 암호문만 받는다.
2. 데이터 키를 두 조각으로 나눈다. 한 조각은 서버, 다른 조각은 크리에이터 기기의 passkey(WebAuthn, 지문·얼굴 인증) 아래에 둔다. (승인 수단을 카카오 인증서 서명으로 바꾼 뒤의 변형은 "승인 인증 방법" 절 참고 — 기기 조각 대신 KMS 격리 + 승인 토큰 조건으로 보장한다.)
3. 팬이 선물을 등록하면 크리에이터에게 승인 요청이 간다. 승인 토큰은 주문번호 한 건에만 묶인다.
4. 송장 출력 순간에만 두 조각을 합쳐 그 건의 주소를 복호화하고, 택배사 API 호출 후 평문을 즉시 폐기한다.
5. 복호화마다 언제·어느 주문·누가 출력했는지 기록하고 크리에이터 화면에 표시한다. 승인 횟수와 복호화 횟수가 다르면 이상 신호다.

| 공격 지점 | 테이블 분리만(A) | 승인 키 분할(C) |
| --- | --- | --- |
| DB 통째로 탈취 | 전원 주소 노출 | 암호문만, 0명 |
| 서버 키 탈취 | 전원 노출 | 기기 조각 없음, 0명 |
| 크리에이터 기기 해킹 | 본인 1명 | 본인 1명 |
| 승인 피싱 | (해당 없음) | 승인한 주문 1건 |
| 서버 침투 후 복호화 순간 가로채기 | 이미 전원 노출 | 승인이 일어난 건만 한 건씩 |

남는 위험은 마지막 줄이다. 복호화를 송장 출력 전용 격리 함수에서만 하고, 그 함수의 출력을 프린터 명령 하나로 제한하며, 승인 횟수와 복호화 횟수를 매일 대조한다.

**배포 규칙 (에이전트로 개발할 때 필수)**

1. 실명·주소·연락처는 별도 스키마(`pii`)에 두고 PostgREST 노출 목록에서 뺀다. public 테이블에는 `creator_id`와 닉네임만 둔다.
2. 배포 전 anon·일반 유저 권한으로 모든 공개 엔드포인트를 호출해 응답에 `real_name`·`address`·`phone` 필드나 전화번호·주소 패턴이 있으면 배포를 실패시킨다.
3. `pii` 스키마를 건드리는 마이그레이션은 에이전트가 자동 적용하지 못하게 하고 사람이 직접 적용한다.
4. 새 테이블 RLS 강제, Storage public 버킷 금지를 기본값으로 둔다.
5. 비밀번호 로그인·2차 비밀번호를 만들지 않는다. 승인은 카카오 인증서 서명 또는 패스키뿐이다(다음 절). 끌 수 있는 보안 옵션은 만들지 않는다. "전체 승인" 버튼은 만들지 않는다.

광고 문구의 범위: "승인 없이는 저희도 못 엽니다"는 참, "절대 유출되지 않습니다"는 거짓이다. C는 "회사가 털려도 안전"을 만들지 "크리에이터가 털려도 안전"을 만들지는 않는다.

## 승인 인증 방법: 카카오톡 인증서 서명 기본, 패스키 예비

승인은 "크리에이터가 이 주문 한 건의 수령을 허락했다"는 전자서명이다. 기본 수단은 카카오톡 인증 서비스 전자서명이고, 웹 + 패스키(WebAuthn)는 크리에이터가 원할 때 등록하는 예비 수단이다. 결정 이유와 버린 대안은 `fankkuk-decisions.md` D-01에 있다.

| 수단 | 역할 | 쓰는 경우 | 복구 |
| --- | --- | --- | --- |
| 카카오톡 인증서 서명 | 기본 | 카카오 인증서를 가진 모든 크리에이터 | 카카오가 재발급 처리 |
| 웹 + 패스키 | 예비 | 카카오 장애 시, 국내 통신사 번호·국내 계좌가 없어 인증서 발급이 안 되는 크리에이터 | 본인 인증 + 대기 시간 + 기존 연락처 알림 후 재등록 |
| 알림톡 버튼 클릭만 | 쓰지 않음 | — | — |
| 웹 2차 비밀번호 | 쓰지 않음 | — | — |

**승인 흐름 (카카오 인증서 기준)**

1. 팬이 선물을 등록하면 서버가 승인 요청을 만든다. 서명 원문은 `주문번호 + 요청 생성 시각 + 팬 닉네임 해시`이고, 주소·선물 내용은 들어가지 않는다.
2. 크리에이터에게 알림톡이 간다. 본문은 "승인 요청이 도착했습니다"뿐이고 선물 내용·보낸 사람·주소는 없다.
3. 크리에이터가 팬꾹 승인 화면에서 내용(팬 닉네임, 물품 종류)을 확인하고 "승인"을 누르면 카카오톡 인증서 서명 요청이 카톡 안에서 뜬다. 지문·얼굴 또는 인증서 비밀번호로 서명한다.
4. 서버는 돌려받은 서명 원문이 1번에서 보낸 원문과 같은지 비교하고, 서명 값을 직접 검증한다. 같은 서명은 두 번 처리하지 않는다.
5. 검증을 통과하면 그 주문번호에 승인 토큰이 묶인다. 이 토큰이 있어야만 송장 출력 서버 액션이 복호화를 시도한다.

**승인 모듈 구조** — 가운데만 교체 가능하게 만든다.

| 단계 | 하는 일 | 방식별 차이 |
| --- | --- | --- |
| 승인 요청 생성 | 주문번호로 서명 원문·요청 ID 생성, 알림 발송 | 없음 |
| 본인 확인 결과 수신 | 카카오 서명 검증 또는 패스키 assertion 검증 | 여기만 다름 |
| 승인 처리 | 승인 토큰 발급, 주문 상태 변경, 로그 | 없음 |

**비복호화와의 관계 — 정직하게 적어야 하는 부분**

앞 절의 C 구조는 "크리에이터 기기가 키 조각을 들고 있어서 서버 혼자서는 수학적으로 복호화가 불가능"한 구조였다. 카카오 인증서 서명은 키 조각이 아니라 "허락했다는 증거"라서, 서명을 기본 수단으로 두면 보장 방식이 바뀐다.

| | 패스키 키 분할(C) | 카카오 서명 + 격리 복호화 |
| --- | --- | --- |
| 서버 혼자 복호화 | 불가능(키 조각이 없음) | 정책상 불가(승인 토큰 없이는 복호화 함수가 KMS에 요청하지 않음) |
| DB + 서버 전체 탈취 시 | 암호문만, 0명 | 복호화 키가 KMS에 따로 있으면 암호문만. 키까지 같은 서버에 있으면 전원 노출 |
| 광고 문구 | "승인 없이는 저희도 열 수 없습니다" | "승인 없이는 저희 시스템이 열지 않습니다" |

그래서 카카오 서명을 기본으로 가려면 복호화 키를 Supabase DB·앱 서버와 분리된 곳(클라우드 KMS 또는 Supabase Vault 같은 별도 비밀 저장소)에 두고, 송장 출력 함수만 그 키에 접근하며, 접근 조건에 "유효한 승인 토큰 + 주문번호 일치"를 건다. 이러면 DB가 털려도 암호문만 나가고, 앱 서버가 털려도 승인이 없는 건은 열리지 않는다. 남는 위험은 앱 서버 침투 후 승인이 일어난 건을 한 건씩 가로채는 것으로, C 구조와 같다.

패스키 예비 수단을 쓰는 크리에이터만 C 구조(키 조각 보유)로 두는 것도 가능하지만, 두 구조를 동시에 유지하면 복호화 함수가 두 갈래가 되어 검사 표면이 넓어진다. 초기에는 "카카오 서명 + KMS 격리" 한 구조로 통일하고, 패스키도 승인 증거(assertion)로만 쓴다.

**보안 규칙 (구현 시 게이트로 검사)**

1. 서명 원문에 주문번호를 포함해 서명 하나가 주문 하나에만 쓰이게 한다.
2. 서버가 받은 서명 원문과 보낸 원문을 비교하고, 서명 값 검증은 서버에서 직접 한다.
3. 한 번 처리한 서명은 다시 받아도 처리하지 않는다(요청 ID 단위 멱등).
4. 서명 원문·알림 본문·로그에 주소를 넣지 않는다.
5. 링크를 누르는 것만으로 승인되는 경로를 만들지 않는다.
6. 예비 수단(패스키)은 기본 수단과 같은 보안 수준이어야 한다. 이보다 약한 승인 경로를 추가하지 않는다.
7. 승인 기능은 "승인 요청 생성 → 본인 확인 결과 수신 → 승인 처리" 세 단계로 나누고 가운데만 교체 가능하게 만든다.
8. 카카오 인증 API 호출은 등록된 고정 IP에서만 나간다.
9. 패스키 복구는 본인 인증 + 대기 시간 + 기존 연락처 알림을 거친다. 이메일 링크만으로 재등록되는 경로는 만들지 않는다.
10. 복호화 키는 앱 서버·DB와 분리된 비밀 저장소에 두고, 송장 출력 함수만 접근한다.

## 업무 프로세스

승인을 팬 등록 시점으로 당기면 도착 당일 출고가 가능해 하루가 준다. 사무실 주소는 승인 후에만 팬에게 보이므로 미등록 도착과 거절 후 도착이 거의 사라진다.

흐름(8단계, 결정 1개):

1. 팬 등록 — 팬이 사이트에서 선물을 등록하면 주문번호(예: FC-7K3M9)가 생긴다.
2. 크리에이터 승인? — 승인이면 팬에게 사무실 주소가 공개된다. 거절이면 팬에게 발송 중단 안내가 가고 주소는 주어지지 않는다.
3. 팬이 사무실로 발송 — 받는 사람 이름란에 주문번호를 적고, 사이트에 택배 송장번호를 입력한다.
4. 입고 스캔·내부 라벨 — 원 송장 바코드 스캔으로 주문번호를 확정하고 내부 QR 라벨을 출력·부착한다.
5. 원 송장 제거·탐지 — 원 송장을 떼어 파쇄하고 겉면 탐지를 한다. 불합격이면 착불 반송.
6. 송장 출력(복호화) — 대표 계정에서만, 여기서만 복호화가 일어난다.
7. 집하·배송.

거절이면 팬에게 발송 중단을 안내하고 주소를 주지 않는다. 검수 불합격은 팬의 원 송장 주소로 착불 반송한다. 송장 출력은 대표 계정에서만 하고, 여기서만 복호화가 일어난다.

| 단계 | 팬이 보는 것 | 크리에이터가 보는 것 |
| --- | --- | --- |
| 등록 | 주문번호 | 승인 요청(팬 닉네임, 팬이 입력한 물품 종류) |
| 승인 | 승인 여부, 사무실 주소 | 승인 완료 |
| 입고 | 도착 시각 | 도착 시각 |
| 검수 | 통과·반송 | 통과·반송 |
| 출고 | 출고 시각, 예상 도착일 | 출고 시각, 택배 조회 링크 |
| 배송중·수령 | 배송 단계만(택배사 API 중계) | 상세 추적 |

팬에게 운송장 번호는 절대 보여주지 않는다. 택배사 조회 페이지에 번호를 넣으면 수령지 일부가 나온다. 검수 사진은 손이 많이 가서 넣지 않고 상태만 보여준다.

**속도를 올리는 방법**

| 방법 | 효과 | 비용 |
| --- | --- | --- |
| 사전 승인(팬 등록 시점) | 승인 대기 0, 도착 당일 출고 | 0원 |
| 서울 강남권(선릉) 집하 | 당일 집하분이 그날 밤 경기 남부 허브 입고, 허브 인근 임대와 같음 | 0원 |
| 집하 마감 후 도착분을 직접 대리점·터미널에 반입 | 마감을 몇 시간 늦춤 | 이동 시간 |
| 익일 보장 상품(우체국 익일특급 등) 옵션 | 다음 날 배달 보장 | 건당 추가 요금, 팬 선택 |
| 수도권 당일 퀵 옵션 | 도착 당일 수령 | 건당 1.5~3만원, 팬 선택 |
| 크리에이터의 자동 승인 팬 목록 | 승인 대기 0 | 0원 |

참고: 팬심도 "오후 4시 이전 도착 시 당일 발송"이라 구조상 더 빠르지 않다. 빨라지는 지점은 집하 마감 시간(선릉 건물 집하 시각이 4시보다 늦으면)과 토요일 집하 택배사 사용뿐이다. 차별점은 속도가 아니라 상태 표시·승인·검수다.

## 예외 상황 처리

모든 예외는 착불 반송 + 7일 보관 + 크리에이터 주소 비복호화로 통일한다. 반송은 팬의 원 송장 주소로만 가고, 그 주소는 반송 후 폐기한다.

| 상황 | 처리 | 반송비 |
| --- | --- | --- |
| 미등록 도착(보내기 버튼 안 누름) | 보류 선반에 두고 "미확인 입고" 목록에 도착일·발신인 이름 일부만 올린다. 팬이 뒤늦게 등록하며 "내 물건 찾기"로 매칭한다. 7일 안에 매칭 안 되면 착불 반송 | 팬 |
| 검수 불합격 | 금지 품목(음식·액체·배터리 등)은 착불 반송. 트래커 발견 시에는 반송하지 않고 보관, 크리에이터에게 통보, 신고 여부는 크리에이터가 결정. 증거를 팬에게 돌려주지 않는다 | 팬 |
| 장기 미승인 | 등록 시 알림 → 도착 시 재알림 → 3일 후 재알림 → 7일 후 자동 반려·반송. 등록 화면에 그 크리에이터의 평균 승인 시간을 보여줘 팬이 판단하게 한다 | 팬 |
| 거절 | 팬에게 "크리에이터가 수령하지 않습니다"만 알린다(이유 비공개). 아직 안 보냈으면 발송 중단 안내, 이미 도착했으면 착불 반송. 크리에이터가 그 팬을 차단하면 이후 등록 자체가 막힌다 | 팬 |
| 한 팬이 상자 여러 개 | 등록 시 상자 수를 입력받아 FC-001-1, FC-001-2로 나눈다. 승인은 FC-001 하나로 묶는다 | — |
| 두 팬이 같은 주문번호를 적음 | 송장번호로 갈라진다. 송장번호도 없으면 미확인 입고 | — |
| 승인 전에 상자가 먼저 옴 | 입고까지 정상 처리하고 출고 목록에는 뜨지 않는다. 7일 규칙 적용 | — |

**여러 팬 → 한 크리에이터 매칭**: 매칭 단위는 크리에이터가 아니라 등록 건이다. 등록마다 주문번호가 생기고 승인·상자·송장이 전부 그 번호에 묶인다. 입고 시 매칭 키는 두 개(받는 사람 이름란의 주문번호, 팬이 입력한 택배 송장번호)라서 하나를 빼먹어도 다른 하나로 잡는다.

## 검수 정의와 단일 요금

검수는 필수이고 요금은 하나다. 검수 없는 요금을 두면 크리에이터가 개봉 검수를 켜는 것이 "내 팬에게 돈을 더 받는 결정"이 되어 아무도 안 켠다. 대신 개봉은 전수가 아니라 조건부로 해서 노동을 늘리지 않는다. 팬의 원 송장에는 팬의 이름·주소·전화가 있어 그대로 보내면 반대 방향 유출이 되므로 원 송장 제거는 어떤 경우에도 빠지지 않는다.

| 대상 | 처리 | 건당 시간 | 막는 것 |
| --- | --- | --- | --- |
| 모든 상자 | 원 송장 제거·파쇄 → 블루투스 스캔(폰 앱) → RF 탐지 → 금속 탐지 → 내부 라벨 | 1~2분 | 팬 신상 노출, 켜진 트래커·카메라 |
| 조건에 걸린 상자만 | 개봉 → 육안 확인 → RF 탐지(분리형이면 배터리 제거 후) → 서비스 박스로 재포장 | 5~10분 + 박스 500~1,000원 | 절전 트래커, 금지 품목, 위험물 |

개봉 여부와 무관하게 요금은 같다. 팬은 "검수 포함 요금"만 본다. 팬이 등록할 때 "전자기기 또는 금속 제품이 들어 있나요?"에 답하게 하고, 금속 탐지 결과와 대조해 개봉 여부를 정한다.

| 팬 신고 | 금속 탐지 | 처리 |
| --- | --- | --- |
| 없음 | 반응 없음 | 통과 |
| 없음 | 반응 있음 | 신고와 다르므로 개봉 |
| 전자기기 있음 | 반응 있음 | 정품 밀봉이 온전하면 통과, 밀봉이 깨졌거나 재포장 흔적이 있으면 개봉. 중고·개봉품 전자기기는 금지 품목 |
| 금속 제품 있음(텀블러 등) | 반응 있음 | 통과 |
| 크기·무게가 신고와 다름 | — | 개봉 또는 착불 반송 |

크리에이터 쪽 옵션은 "내 팬 대신 내가 부담" 스위치 하나만 남긴다. 팬이 추가 요금을 보는 옵션은 없다. 크기·무게 한도는 세 변 합 100cm·10kg이고, 냉장·냉동·음식·액체·배터리 단품·현금·중고 전자기기는 금지한다. 한계는 사실대로 적는다: 절전 상태 장치나 금속 제품 안에 숨긴 장치는 겉면 탐지로 발견되지 않을 수 있고, 개봉 검수도 모든 장치를 보장하지 않는다. 검수 기록(장비·시간·반응·담당자)은 건마다 시스템에 남긴다.

탐지 장비 초기 구성: 블루투스 태그 탐지 앱(0원) + 입문 RF 탐지기(2~6만원) + 저가 휴대용 금속 탐지기(3~5만원). 물량이 붙으면 중급 RF 탐지기(15~25만원)로 올린다.

## 내부 QR 시스템

사람이 읽고 판단하고 입력하는 지점을 없애고, 모든 이동을 "스캔 → 시스템이 허용해야 다음 단계"로 바꾼다. 특별한 기계는 없고 PC 한 대 + USB 2D 스캐너 + 라벨 프린터로 30만원 안쪽이다.

**장비**

| 장비 | 역할 | 주의 | 비용 |
| --- | --- | --- | --- |
| 2D 바코드 스캐너(USB) | 원 송장 바코드(1D)와 내부 QR(2D)을 읽어 키보드 입력처럼 문자 + Enter를 보낸다 | 1D 전용(레이저식)은 QR을 못 읽음 | 3~8만원 |
| 열전사 라벨 프린터 | 내부 라벨과 택배 송장 출력 | 100×150mm 송장 규격 지원 모델(BIXOLON SLP-TX 계열, Zebra ZD 계열 등) | 15~30만원 |
| 라벨 용지 | 내부 라벨용 소형, 송장용 100×150 | 택배사 계약 시 송장 용지 규격을 맞춘다 | 소모품 |
| 선반 슬롯 번호 스티커 | 상자 위치 고정 | — | 스티커 값 |

처음 몇 주는 스마트폰 카메라(html5-qrcode 등)로 0원 시작이 가능하다. 원 송장 1D 바코드는 폰 카메라가 잘 못 읽어서 물량이 붙으면 USB 스캐너로 간다.

**소프트웨어 네 조각**

1. QR 발급: 주문번호 문자열(예: FC-7K3M9)을 그대로 QR로 만든다(npm `qrcode`). QR 안에 주소·이름·URL을 넣지 않는다.
2. 라벨 출력: 관리자 페이지의 라벨 미리보기 화면에 CSS `@page { size: 60mm 40mm }`를 지정하고 `window.print()`를 호출한다. 기본 프린터를 라벨 프린터로 두면 브라우저 인쇄로 나온다. 택배 송장은 택배사 API가 주는 라벨 이미지를 100×150 규격에 출력한다.
3. 스캔 입력: 작업 화면에 항상 포커스가 가 있는 입력창을 하나 둔다. 스캐너가 코드 + Enter를 보내면 onSubmit이 실행된다.
4. 서버 상태 확인: 스캔된 코드와 작업 모드(입고·검수·출고)를 서버 액션으로 보낸다. 서버가 아래 전환표로 허용 여부를 정하고, 화면은 성공이면 초록, 실패면 빨강 + 경고음.

**서버가 지키는 상태 전환표** — 이 표가 곧 코드다.

| 현재 상태 | 스캔한 것 | 작업 화면 | 허용 시 다음 상태 | 거부 조건 |
| --- | --- | --- | --- | --- |
| 등록·승인 | 원 송장 바코드 | 입고 | 입고 완료, 내부 라벨 출력 | 송장번호가 어느 주문과도 안 맞음 → 미확인 입고 |
| 입고 완료 | 내부 QR | 입고 | 라벨 부착 확인 | 직전 출력 라벨과 다른 주문번호 |
| 라벨 부착 확인 | 내부 QR | 검수 | 검수 완료 또는 반송 대기 | 없음 |
| 검수 완료 | 내부 QR | 출고 | 송장 출력(복호화 1회) | 승인 토큰 없음, 거절됨, 검수 미완료 |
| 송장 출력 | 송장 바코드 | 출고 | 출고 확정 | 송장번호가 이 주문의 것이 아님 |

**막히는 사고**

| 사고 | 막는 장치 |
| --- | --- |
| 다른 주문번호로 매칭 | 원 송장 바코드 스캔만 허용, 수동 입력 금지 |
| 라벨을 붙이다 상자가 섞임 | 1상자 1스캔 1라벨 즉시 부착, 부착 확인 스캔 전에는 다음 상자 스캔 거부 |
| 미승인·거절 건 출고 | 전환표 4행의 거부 조건 |
| 송장을 다른 상자에 붙임 | 내부 QR 스캔 → 그 건 송장 1장만 출력 → 부착 후 송장 바코드 재스캔으로 짝 확인 |
| 같은 크리에이터의 두 상자가 바뀜 | 위 짝 확인으로 잡힘 |

송장 출력 권한은 대표 계정 하나에만 둔다. 직원 계정에는 출력 메뉴가 없고, 직원은 입고 스캔·탐지·재포장까지만 한다. 원 송장은 입고 즉시 떼서 파쇄한다. 전환표 4행의 "송장 출력" 서버 액션은 C 구조의 복호화 자리이므로 에이전트 결과를 직접 읽고 승인 확인·로그 기록이 들어 있는지 확인한 뒤 배포한다.

만드는 시간: 상태 컬럼 + 전환 검사 서버 액션 하루, 라벨 미리보기 반나절, 스캔 입력창 + 모드별 화면 하루, 택배사 API 연동 후 송장 출력 하루.

## 수익 모델과 손익분기

초기 수익은 팬이 건당 내는 검수·전달 수수료 하나로 시작하고, 자체 상품 판매는 물량이 생긴 뒤 위탁 방식으로 붙인다. 크리에이터는 무료, 현금 후원 중개는 초기 제외다.

| 모델 | 돈을 내는 쪽 | 장점 | 단점 | 시점 |
| --- | --- | --- | --- | --- |
| 건당 검수·전달 수수료 | 팬 | 재고 없음, 검수가 곧 상품 | 건수에 비례해서만 늘어남 | 처음부터 |
| 자체 상품 판매(위탁 큐레이션 몰) | 팬 | 마진 10~30%, 자체 상품은 개봉 검수 불필요 | 재고·CS·불량 책임(팬심 가습기 불량 사례) | 물량 생긴 뒤 |
| 크리에이터 월 구독 | 크리에이터 | 고정 수입 | 희소한 쪽에 과금 → 유입 감소 | 하지 않음 |
| 현금 후원 중개 수수료 | 팬 | 단가 큼 | 전자금융·원천징수·정산 의무 | 초기 제외 |
| 소속사 B2B 요금 | 소속사 | 한 계약에 크리에이터 여러 명 | 영업 필요 | 공급자 확보 이후 |

**건당 단가 (대략)**

| 항목 | 비용 |
| --- | --- |
| 택배비(일반 요금) | 3,500~4,000원, 계약 후 2,500~3,000원 |
| 포장재·라벨 | 500원 안팎 |
| PG 수수료(붙일 경우) | 결제액의 3% |
| 검수 인건비 | 초기 본인 0원, 이후 건당 1,000~1,500원 |

팬에게 "배송비 실비 + 검수·전달 서비스료 5,000원"(합계 8,500~9,000원)을 단일 요금으로 받는다. 검수 없는 요금을 두지 않아 비교 대상이 없게 한다. 건당 마진은 5,000 − 포장재 500 − PG 수수료 약 270 = 약 4,200원이다. 가격은 팬심과 같거나 조금 높게 잡고 "검수 포함"을 명시한다. 팬은 크리에이터를 따라 옮기지 가격 때문에 옮기지 않으므로 싸게 잡으면 마진만 준다.

**손익분기**

1. 고정비를 월 30만원으로 잡는다(선릉 사무실 임대료 0 + 인프라·기타 30). 임대료를 일부 부담하면 그만큼 더한다.
2. 건당 마진 4,200원이면 72건/월, 하루 2~3건이 손익분기다.
3. 택배 계약으로 배송비가 내려가도 실비 항목이라 마진은 그대로이고, 대신 팬 부담 총액이 1,000원 준다.

하루 2~3건이면 5% 시나리오(하루 10건)에서도 흑자다. 임대료가 월 50만원 생기면 손익분기는 하루 6~7건으로 올라간다.

## 팬심 기준 수익 추정

팬심 선물 물량의 10%를 가져오면 월 매출 540만원 안팎, 고정비를 빼고 월 220만원 안팎이 남는다. 30%를 가져와야 월 마진 700만원대가 되며, 팬심의 연매출 규모는 배송 수수료가 아니라 자체 상품 판매·메시지 과금에서 나온다.

**팬심(일리오) 공개 수치**

2024년 이후 매출은 공개 자료가 없다. 30% 성장을 그대로 적용하면 2025년 약 20억원대이나, 혁신의숲 요약은 2025년 매출을 전년 대비 거의 변동 없음으로 표시하고 있어 15~25억원 사이로 본다(추정).

**건당 매출 역산 — 배송 수수료로는 이 매출이 안 나온다**

1. 2022년 선물 건수를 연 4.5만 건(2021년 3.5만 건 × 1.3)으로 잡는다.
2. 11.2억원 ÷ 4.5만 건 = 건당 약 25,000원이다.
3. 배송·검수 수수료는 건당 3,000~5,000원 수준이므로, 팬심 매출의 대부분은 팬심 안에서 파는 자체 상품 판매액과 메시지 과금이다. 순수 대행 수수료 매출은 연 2~3억원 안팎으로 추정한다.

즉 팬심을 "배송 대행 회사"로 보고 매출을 따라가면 틀린다. 대행 수수료만으로는 연 2~3억원이 상한이고, 그 이상은 자체 상품·메시지 과금이 만든다.

**이 서비스가 가져올 수 있는 물량 시나리오 (2026년 팬심 선물 물량을 하루 200건, 연 7만 건으로 추정)**

| 시나리오 | 점유율 | 하루 건수 | 월 매출(팬 결제액, 건당 9,000원) | 월 마진(건당 4,200원) | 고정비 30만원 차감 후 |
| --- | --- | --- | --- | --- | --- |
| 소극적 | 5% | 10건 | 270만원 | 126만원 | +96만원 |
| 유출 사고 반사 이익 | 15% | 30건 | 810만원 | 378만원 | +348만원 |
| 팬심 대체 | 30% | 60건 | 1,620만원 | 756만원 | +726만원 |

하루 200건은 2021년 하루 100건에 2023년 성장률 30~40%를 3년 적용한 추정치다. 실제는 이보다 낮을 수 있고, 팬심 탈퇴 크리에이터가 많아진 지금은 점유율이 위 표보다 빨리 오를 수 있다.

**읽는 법**

1. 5% 시나리오도 임대료가 없으면 월 96만원 흑자다. 혼자 검수·송장 부착을 하는 구간이다.
2. 15% 시나리오가 손익분기(하루 2~3건)를 크게 넘어 직원 1명을 둘 수 있는 첫 구간이다. 이 구간부터 직원 1명 검수와 택배 계약이 필요하다.
3. 30% 시나리오라도 월 마진 726만원이라, 대행 수수료만으로는 1인 사업 수준을 넘지 못한다. 그 위로 가려면 팬심처럼 자체 상품(위탁) 마진을 붙여야 하고, 그때 건당 매출이 5,000원에서 10,000원대로 오른다.

요약하면: 팬심 물량 15%를 가져오면 월 마진 348만원 안팎, 30%면 726만원이다. 배송 대행만으로 팬심 매출을 따라갈 수는 없고, 팬심 매출의 대부분은 자체 상품 판매다.

**노동 최소화(하루 30건 기준)**

사람 손이 꼭 가는 물리 작업은 약 80분(입고 스캔·원 송장 제거 20분, 겉면 탐지 20분, 내부 라벨 10분, 출고 스캔·송장 20분, 집하 10분). 나머지는 자동화한다: PG 결제(계좌이체 정산 수작업 제거), 상태 화면이 CS 대신, 팬 입력 송장번호를 택배사 API로 조회해 "내일 도착 예정 N건" 아침 알림, 처리 시간대를 집하 1시간 반 전 하루 1회로 고정, 7일 자동 반려·리마인드·반송 라벨 자동. 물리 작업까지 넘기려면 월 50만원 아르바이트 + 대표 폰 원격 승인(알바가 내부 QR 스캔 → 대표 폰 지문 승인 → 사무실 프린터 출력).

## 카카오 인증·알림톡 계약과 심사 절차 계획

카카오 인증 서비스는 카카오와 직접 계약하지 않고 딜러사(공식 대행사)를 통해 계약한다. 딜러사 계약을 개발 초반에 해서 테스트 API 키로 개발하고, 이용기관 등록 심사는 출시 직전에 요청한다(D-05). 알림톡은 카카오톡 비즈니스 채널 + 알림톡 발송 대행사 계약이 별도로 필요하다.

**계약·심사 일정표**

| 순서 | 시점 | 할 일 | 완료 조건 | 담당 |
| --- | --- | --- | --- | --- |
| 1 | 개발 초기 | 배포 구조와 고정 IP 방법 정하기. Vercel 서버리스는 고정 IP가 없으므로 카카오 API 호출만 고정 IP를 가진 경로(소형 VM, 또는 고정 IP가 되는 프록시)로 보낸다 | 카카오 API 호출이 나갈 고정 IP가 정해져 있다 | 본인 |

**이용기관 심사 신청 전 확인 목록**

1. 팬꾹 사이트가 실제 도메인으로 접속되고 서비스 내용이 보인다.
2. 이용약관과 개인정보처리방침 페이지가 있다.
3. 사이트 하단에 사업자 정보(상호 네오코드, 사업자등록번호, 고객센터)가 표시된다.
4. 카카오 디벨로퍼스 앱이 사업자 정보로 비즈 앱 전환되어 있고, 앱 이름·서비스 정보가 사이트와 일치한다.
5. 카카오톡 비즈니스 채널 전환이 완료되어 있다.
6. 기관명·이용기관 로고·고객센터 연락처·알림톡 헤더 이미지가 확정되어 있다.
7. API 접근 허용 IP로 등록할 고정 IP가 준비되어 있다.

**개발이 심사를 기다리지 않게 하는 방법**

1. 본인 확인 단계를 교체 가능하게 만들었으므로, 테스트 키 환경에서는 딜러사 테스트 서명으로, 운영 전환 전까지는 패스키로 전 흐름을 돌릴 수 있다.
2. 알림톡 템플릿 승인 전에는 같은 본문을 이메일로 보내는 발송 어댑터로 대체한다. 알림 모듈도 "알림 생성 → 채널 발송" 두 단계로 나눠 채널만 교체한다.
3. 고정 IP 경로는 1번 항목에서 먼저 정해야 한다. 나중에 정하면 배포 구조를 다시 짜게 된다.

## 초기 비용과 남은 결정 사항

고정비는 임대료 없이 월 30만원 안팎이고, 시작 전에 반드시 드는 항목은 신고·검수 장비·인프라뿐이다. 결제·본인인증·외부 보안진단은 초기에 대체 방식으로 미룰 수 있지만, 미룬 만큼 본인 시간으로 메운다.

| 항목 | 대략 비용 | 미룰 수 있나 |
| --- | --- | --- |
| 사무실(선릉 지인 사무실) | 0~일부 부담 | 사용 승낙서·집하 시간·보관 선반 확인 후 사용 |
| 사업자등록 + 통신판매업 신고 | 무료 + 등록면허세 연 4~5만원 | 불가 |
| 이용약관·개인정보처리방침 | 템플릿 0원, 변호사 검토 수십만원 | 문서는 불가, 검토는 미룰 수 있음 |
| 결제(PG) | 초기 0~수만원 + 결제액 3% | 처음부터 붙인다(정산 수작업 제거) |
| 본인인증(휴대폰) | 건당 수십 원 + 계약 심사 | 방송 채널 인증 코드로 대체 |
| 인프라(Supabase·Vercel·도메인) | 월 0~5만원 | 불가 |
| 검수 장비(RF 탐지기·금속 탐지기·포장재) | 10~20만원 일회성 | 불가 |
| 스캐너·라벨 프린터 | 20~40만원 일회성 | 폰 카메라로 몇 주 대체 가능 |
| 택배 계약 | 물량 적으면 일반 요금, 계약 시 건당 1,000원 절감 | 물량 생긴 뒤 |
| 외부 취약점 진단 | 정식 수백만원 | 자동 스캐너 + 지인 리뷰로 대체, 크리에이터 늘면 필수 |

**법적 대비(유료 검수를 놓쳤을 때)**: 문구는 방법과 한계를 사실대로, 건마다 검수 기록, 경과실 배상 한도 정액(예: 검수 수수료의 10배 또는 10만원 중 큰 금액), 팬의 전자기기 신고 의무 조항, 영업배상책임보험 검토. 고의·중과실 면책은 약관규제법상 무효. 약관 문안과 한도 숫자는 변호사 검토 1회.

**세금**: 부가세(팬에게 받은 돈 전체, 배송비 포함)와 종합소득세 두 가지. 크리에이터에게 돈을 지급하지 않으므로 원천징수 없음. "팬 대신 부담" 옵션·소속사 B2B를 위해 일반과세자 등록 권장(간이과세자는 세금계산서 발급 제한). 매출은 PG로 자동 집계, 택배사 세금계산서 수취, 첫 부가세 신고 전 세무사 상담 1회.

**시간 비용**

1. 검수는 사람이 상자를 열어야 하므로 사무실에 누군가 상주해야 한다. 초기에 직접 하면 개발 시간이 그만큼 준다.
2. 계좌이체 정산은 입금 확인·환불이 전부 수작업이고 건수에 비례해 는다.
3. C 구조 설계와 배포 전 자동 검사는 사람이 만들어야 한다. 설계 포함 1~2주로 본다.

**아직 정하지 않은 것**

- [ ] 사용자 경험: 팬 3개·크리에이터 3개·관리자 3개 화면의 흐름과 디자인 설계, 상태 화면이 CS를 대신하도록
