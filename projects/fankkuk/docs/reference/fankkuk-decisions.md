# 팬꾹 — 결정 기록과 착수 전 작업 목록

작성일: 2026-10-01
용도: 하네스에 넣는 프로젝트 지식 문서. 결정의 이유와 버린 대안을 기록하고, 구현 시 지켜야 할 보안 규칙과 착수 전 작업 순서를 전달한다.

## 1. 서비스 개요

- 한 줄 설명: 팬이 크리에이터에게 보내는 선물을 받아 검수한 뒤, 크리에이터 주소를 노출하지 않고 재배송하는 대행 서비스.
- 서비스 이름: 팬꾹 (개발 중 가칭, 출시 전 최종 확정. 대안 후보: 팬덕)
- 운영 우선순위: 1. 보안 2. 속도(하루라도 빠른 배송) 3. 정보성(현재 배송 상태 확인)
- 핵심 무기 다섯 가지:
  1. 필수 검수
  2. 비복호화 (크리에이터 승인 없이는 서비스도 주소를 복호화할 수 없음)
  3. 승인 시스템 (크리에이터가 승인한 선물만 배송)
  4. 직원 최소 노출
  5. 사용자 친화적 사이트 (UX·디자인·상태 확인)
- 상태 단계: 등록 → 승인 → 입고 → 검수 → 출고 → 배송중 → 수령

## 2. 결정 기록

### D-01. 승인 방식: 카카오톡 인증서 서명을 기본, 웹 + 패스키를 예비로 둔다

- 결정: 크리에이터 승인은 카카오톡 인증 서비스 전자서명으로 받는다. 웹 + 패스키는 크리에이터가 원할 때만 등록하는 예비 수단으로 둔다.
- 이유:
  1. 카카오톡 안에서 서명이 끝나서 브라우저로 넘어가는 단계가 없다.
  2. 카카오 인증서는 이미 발급받은 사람이 많아 처음 쓰는 부담이 작다.
  3. 휴대폰 분실·교체 시 재발급을 카카오가 처리하므로 복구 절차를 직접 설계할 필요가 없다.
  4. 카카오 계정 비밀번호가 유출되어도 인증서는 본인 휴대폰 + 비밀번호(또는 생체 인증) 없이 쓸 수 없다.
  5. 이용기관 등록 심사가 짧고(딜러사 안내 기준 최대 3영업일), 딜러사 테스트 키로 개발을 먼저 진행할 수 있다.
- 예비 수단이 필요한 이유:
  1. 카카오 장애 시 승인 전체가 멈추는 것을 막는다.
  2. 카카오 인증서를 발급받을 수 없는 크리에이터(국내 통신사 번호·국내 계좌 없음)를 지원한다.
- 버린 대안:
  - 웹 + 패스키를 기본으로: 카카오톡 인앱 브라우저에서 동작이 불안정할 수 있고, 복구 경로를 직접 설계해야 하며, 나중에 카톡 인증서로 바꾸면 크리에이터 전원이 재설정해야 한다.
  - 크리에이터 전용 어플: 개발·스토어 심사로 출시가 늦어지고, 생체 인증 승인은 패스키로도 가능하며, 알림을 꺼두면 푸시가 닿지 않는다. 크리에이터 승인 건수와 관리 기능 요구가 늘면 재검토한다.
  - 웹 2차 비밀번호: 서버 DB 유출 시 6자리 비밀번호는 쉽게 풀리고, 피싱·비밀번호 재사용에 약하다. 예비 수단으로도 쓰지 않는다 (승인 경로 중 가장 약한 것이 전체 보안 수준이 되기 때문).
  - 알림톡 버튼 클릭만으로 승인: 카톡이 열린 휴대폰만 있으면 누구나 승인할 수 있다.

### D-02. 알림은 카카오 알림톡으로 보낸다

- 결정: 승인 요청·배송 상태 알림은 카카오 알림톡으로 보낸다.
- 이유: 거의 모든 사용자에게 닿고, 사용자가 따로 설치하거나 허용할 것이 없다.
- 제약: 알림 본문에 선물 내용·보낸 사람·주소를 넣지 않는다. 알림은 "요청이 왔다"는 사실만 전달한다.
- 이후 검토: 사용자가 늘면 비용 절감용으로 웹 푸시를 보조로 추가한다.

### D-03. 결제는 대행 수수료 구조로 설계한다

- 결정: 팬꾹의 매출은 검수·전달 수수료로 잡히도록 설계한다. 크리에이터는 무료.
- 이유: 사업자가 일반과세자라 매출에 부가세 10%가 붙는다. 선물 금액까지 매출로 잡히면 실제 수익 대비 세금·신고 부담이 크게 늘어난다.
- 제약: 대신 구매 기능을 넣을 경우 상품 대금과 대행 수수료를 결제·영수증·DB에서 분리한다.
- 미확정: 부가세 신고 기준은 세무사 확인 후 확정한다.

### D-04. 사업자는 기존 개인사업자 네오코드를 그대로 쓴다

- 결정: 새 사업자를 만들지 않고 기존 네오코드(일반과세자)를 사용한다. 팬꾹은 서비스 이름으로 쓴다.
- 이유: 사업자번호를 유지하면 기존 계약·등록을 바꿀 필요가 없고, 폐업 후 같은 종류의 사업을 다시 시작하면 창업 감면 대상이 아닌 경우가 많다.
- 할 일: 출시 전에 업종 추가 정정 신고를 한다. 상호 변경은 선택.
- 참고: 통신판매업자는 사이트 하단에 사업장 주소를 공개해야 하므로, 집 주소 대신 다른 주소 사용을 검토한다.

### D-05. 카카오 이용기관 심사는 출시에 맞춰 요청하고, 딜러사 계약은 개발 초반에 한다

- 결정: 딜러사 계약을 먼저 해서 테스트 API 키로 서명 흐름을 개발하고, 이용기관 등록 심사는 출시 직전에 요청한다.
- 이유: 기관 심사 자체는 짧고, 계약과 개발을 동시에 진행하면 출시 일정이 늦어지지 않는다.

## 3. 구현 시 지켜야 할 보안 규칙

1. 승인 서명의 원문에는 선물 요청 ID를 포함해서, 서명 하나가 선물 하나에만 쓰이게 한다.
2. 서버는 받은 서명 원문이 보낸 원문과 같은지 비교한다. 서명 값 검증은 서버에서 직접 구현한다.
3. 한 번 처리한 서명은 다시 받아도 처리하지 않는다.
4. 서명 원문·알림 본문·로그에 주소를 넣지 않는다.
5. 링크를 누르는 것만으로 승인되는 경로를 만들지 않는다.
6. 예비 승인 수단(패스키)은 기본 수단과 같은 보안 수준이어야 한다. 이보다 약한 승인 경로를 추가하지 않는다.
7. 승인 기능은 "승인 요청 생성 → 본인 확인 결과 수신 → 승인 처리" 세 단계로 나누고, 가운데 본인 확인 부분만 방식별로 교체할 수 있게 만든다.
8. 카카오 인증 API는 등록된 IP에서만 호출을 받으므로, 해당 호출은 고정 IP를 가진 경로로만 나간다.
9. 패스키 예비 수단의 복구는 본인 인증 + 대기 시간 + 기존 연락처 알림을 거쳐야 한다. 이메일 링크만으로 재등록되는 경로는 만들지 않는다.

## 4. 착수 전 작업 순서

| 순서 | 시점 | 할 일 | 완료 조건 |
|---|---|---|---|
| 1 | 개발 초기 | 배포 구조와 고정 IP 방법 정하기 | 카카오 API 호출이 나갈 고정 IP가 정해져 있다 |
| 2 | 개발 초기 | 딜러사 2~3곳 문의 후 계약 | 기간·건당 요금·묶음 서명 상품 여부를 확인했고, 테스트 API 키를 받았다 |
| 3 | 개발 중 | 서명 승인 흐름 개발 | 3장 보안 규칙 1~5가 테스트로 검증된다 |
| 4 | 개발 중 | 결제·주문 구조 설계 | 상품 대금과 수수료가 분리되어 있고, 세무사 확인을 받았다 |
| 5 | 출시 2~3주 전 | 사업자·채널·디자인 준비 | 업종 추가 정정 신고 완료, 비즈니스 채널 전환 완료, 로고·알림톡 헤더 이미지 확정 |
| 6 | 출시 직전 | 이용기관 등록 심사 요청 | 심사 승인 후 운영 환경으로 전환했다 |

## 5. 이용기관 심사 신청 전 확인 목록

1. 팬꾹 사이트가 실제 주소로 접속되고 서비스 내용이 보인다.
2. 이용약관과 개인정보처리방침 페이지가 있다.
3. 사이트 하단에 사업자 정보(상호, 사업자등록번호, 고객센터)가 표시된다.
4. 카카오 디벨로퍼스 앱(카카오 API 사용을 위한 등록 단위, 휴대폰 어플 아님)이 사업자 정보로 비즈 앱 전환되어 있고, 앱 이름·서비스 정보가 사이트와 일치한다.
5. 카카오톡 비즈니스 채널 전환이 완료되어 있다.
6. 기관명·이용기관 로고·고객센터 연락처·알림톡 헤더 이미지가 확정되어 있다 (등록 후 변경은 딜러사를 통해서만 가능).
7. API 접근 허용 IP로 등록할 고정 IP가 준비되어 있다.

## 6. 아직 확인되지 않은 것

| 항목 | 확인 방법 |
|---|---|
| 딜러사 계약~운영 전환 실제 기간 | 딜러사 문의 |
| 서명 1건당 요금 | 딜러사 요금표 |
| 여러 건을 한 번에 서명하는 상품 여부 | 딜러사 문의 |
| 부가세 신고 기준 (대행 수수료 구조) | 세무사 확인 |
| 카카오톡 인앱 브라우저에서 패스키 동작 여부 | 아이폰·안드로이드 실기기 테스트 |
| 서비스 이름 최종 확정 (팬꾹 / 팬덕) | 팬심 이용 경험자 5~10명 반응 확인 |
