## 2. 새 기능 상세

### F-10. 크리에이터 범위 확장 (1차)

크리에이터 종류별 차이와 대응:

| | 실시간 방송인(치지직·SOOP·트위치) | 유튜버 | 인스타 인플루언서 |
| --- | --- | --- | --- |
| 팬 선물 문화 | 가장 강함 | 중간 | 상대적으로 약함 |
| 주소 노출 위험 | 팬 선물 | 팬 선물 + 협찬품 | 협찬품이 많음 |
| 링크를 넣는 곳 | 방송국 공지, 채널 설명 | 채널 설명, 커뮤니티 탭 | 프로필 링크 한 칸(링크 모음 서비스 안) |
| 팬이 자랑하는 곳 | X, 방송 채팅 | X, 댓글 | 인스타 스토리 |
| 기념일 | 방송 시작일, 생일 | 채널 개설일 | 생일, 활동 시작일 |

변경 사항:

1. 용어 통일: 화면·문구·문서에서 "방송인·스트리머·BJ"는 "크리에이터"로, "방송 기념일"은 "활동 기념일"로, "구독자·팔로워"는 "팬"으로 쓴다. 팬·구독자·팔로워 중 세 플랫폼 모두에서 쓰이는 말은 "팬"이고, 구독자·팔로워는 플랫폼이 붙인 숫자 단위라 관계를 부르는 말로는 약하다.
2. 인스타 스토리용 세로 공유 카드: 답장 공유(F-5)에서 "X용" / "스토리용"을 고른다. 스토리용은 1080×1920, 크리에이터 프로필 사진·닉네임·답장 문구·날짜·팬꾹 로고. 인스타는 팬이 스토리에 크리에이터를 태그하고 크리에이터가 다시 공유하는 흐름이 흔해서 이 카드가 그 흐름에 맞는다. 팬꾹이 인스타 계정을 자동으로 태그하지는 않는다(팬이 직접 태그).
3. 링크 모음 서비스 대응: 인스타 인플루언서는 프로필 링크 한 칸을 여러 링크를 모아 주는 서비스에 쓰는 경우가 많다. 팬꾹 링크가 그 안에 들어가도 미리보기(OG 이미지·제목·설명)가 정상으로 보이는지 대표 서비스 2~3곳에서 확인한다.
4. 팬덤 이름 설정: 크리에이터 설정에 "팬을 부르는 이름"(선택, 10자). 링크 페이지 감사 문장이 "보내주시는 마음 늘 감사해요" → "{팬덤 이름} 여러분의 마음 늘 감사해요"로 바뀐다. 답장 고정 문구 일부에도 쓸 수 있다. 문구 자체는 고정 템플릿이라 불변식 21(자유 문장 금지)과 충돌하지 않는다. 입력값에는 금칙어 검사(욕설, 다른 크리에이터 이름, 팬꾹 사칭 단어)를 건다.
5. 기념일 이름 예시를 "생일, 활동 시작일, 채널 개설일"로 바꾼다(F-6).

### F-11. 활동 채널 링크와 크리에이터 확인 뱃지 (1차)

목적: 1. 가짜 페이지 차단. 누군가 유명 크리에이터 행세를 하며 페이지를 만들면 팬 선물이 엉뚱한 사람에게 간다. 채널 확인을 마친 계정만 선물을 받게 해서 이 경로를 막는다. 2. 팬이 진짜 그 사람 페이지인지 한눈에 판단한다. 3. 팬이 아이콘을 눌러 크리에이터 채널로 바로 이동한다.

등록과 확인 순서:

1. 크리에이터가 설정에서 플랫폼을 고르고 채널 주소를 붙여 넣는다. 지원 플랫폼: 유튜브, 치지직, SOOP, 트위치, 인스타그램, X, 틱톡. 목록 밖의 임의 주소를 넣는 칸은 없다.
2. 플랫폼마다 주소 형식을 검사한다(예: 유튜브 `youtube.com/@핸들`, 인스타 `instagram.com/계정`). 형식이 맞지 않으면 저장하지 않는다.
3. 팬꾹이 확인 코드(예: `FANKKUK-7K3M9`)를 보여주고, 크리에이터는 채널 설명란이나 프로필 소개에 잠시 넣은 뒤 "확인 요청"을 누른다.
4. 설명란을 자동으로 읽을 수 있는 플랫폼은 시스템이 확인한다. 자동으로 읽기 어려운 플랫폼(인스타그램 등)은 운영자 확인 대기 목록(F-12)으로 간다. 어느 플랫폼을 자동으로 할지는 구현 단계에서 각 플랫폼의 공개 API·약관을 확인해 정한다(escalate 아님, 자동 결정. 단 약관상 수집 금지인 곳은 운영자 확인으로).
5. 확인되면 그 채널이 링크 페이지 아이콘 줄에 나타나고, 뱃지에 그 플랫폼이 추가된다. 채널 하나 이상 확인되면 "선물 받기"가 켜진다.
6. 크리에이터는 아이콘 순서를 정한다. 맨 앞 채널이 미리보기의 대표 플랫폼이 된다.
7. 확인이 끝나면 "설명란의 확인 코드는 지워도 됩니다"를 안내한다.

뱃지 규칙:

| 항목 | 규칙 |
| --- | --- |
| 무엇을 말하나 | "이 계정이 그 채널의 주인이다"만. 뱃지를 누르면 "유튜브 채널 소유 확인 · 2026.10.12" |
| 쓰지 않는 말 | 공식, 안전한 크리에이터, 인증된 사람, 검증된 크리에이터 |
| 모양 | 확인 아이콘 + 확인된 플랫폼 아이콘들. 색만으로 구분하지 않는다 |
| 한 채널 한 계정 | 같은 플랫폼·같은 핸들은 한 계정에만 "확인됨"으로 존재. 다른 계정이 같은 채널을 확인 시도하면 기존 계정에 알리고 운영자 확인으로 넘긴다 |
| 재확인 | 닉네임·채널 주소를 바꿀 때 다시 확인. 90일마다 채널이 존재하는지 자동 확인(코드 재검사 아님) |
| 내려가는 경우 | 채널 삭제, 재확인 실패, 다른 계정이 같은 채널을 운영자 확인으로 가져감. 확인된 채널이 0개가 되면 "선물 받기"가 꺼지고 크리에이터에게 알림. 이미 승인된 건은 그대로 처리 |

아이콘 링크 규칙:

| 항목 | 규칙 |
| --- | --- |
| 보이는 링크 | 확인 끝난 채널만 |
| 누를 때 | 새 탭, `rel="noopener noreferrer"` |
| 아이콘 | 각 플랫폼이 공개한 공식 아이콘을 브랜드 가이드대로. 색·모양 변형 금지 |
| 길게 누르기·마우스 올리기 | "@핸들 · {확인 날짜} 확인" |
| 크리에이터 안내 | 공개 활동 채널만 등록, 개인 계정은 넣지 않기. 주소·핸들을 바꾸면 다시 확인 필요 |

팬에게 보이는 방식:

| 화면 | 표시 |
| --- | --- |
| 선물 링크 페이지 | 닉네임 옆 확인 아이콘, 아래 활동 채널 아이콘 줄 |
| 링크 미리보기 | 닉네임 옆 확인 아이콘 |
| 팬 등록 화면 | "{닉네임}님의 {플랫폼들} 채널 소유가 확인된 페이지예요" |
| 확인 안 된 페이지 | 페이지는 보이지만 선물 보내기 없음, "아직 채널 확인 전인 페이지예요" |
| 함께한 시간 화면 | 상단 프로필 옆 확인 아이콘 |

데이터: `creator_channels`(크리에이터, 플랫폼, 주소, 핸들, 확인 코드, 확인 방법 auto/manual, 확인한 운영자, 확인 시각, 마지막 재확인 시각, 상태 pending/verified/failed/duplicate/removed, 표시 순서). (플랫폼, 핸들)에 "verified 상태에서 유일" 조건.

완료 조건:

1. 채널 확인 전 크리에이터의 링크 페이지에 선물 보내기 버튼이 없고, 등록 API도 거부한다.
2. 확인된 채널만 아이콘으로 보이고, 누르면 새 탭으로 그 채널이 열린다.
3. 같은 채널을 두 번째 계정이 확인 시도하면 자동 확인되지 않고 운영자 대기로 간다.
4. 지원 플랫폼 밖 주소나 형식이 틀린 주소는 저장되지 않는다.
5. 채널이 삭제된 것으로 재확인되면 아이콘이 내려가고, 확인 채널이 0개면 선물 받기가 꺼진다.

### F-12. 운영자 "크리에이터 확인" 화면 (1차, 관리자 화면 4번째)

목적: 자동 확인이 안 되는 플랫폼과 중복 확인 시도를 운영자가 직접 처리한다. 운영자(대표 계정)만 접근.

| 칸 | 내용 |
| --- | --- |
| 크리에이터 | 팬꾹 닉네임, 가입일 |
| 링크 | 플랫폼 아이콘 + 주소. 누르면 새 탭 |
| 확인 코드 | 이 크리에이터에게 준 코드 |
| 상태 | 자동 확인됨 / 운영자 확인 대기 / 확인 실패 / 다른 계정과 중복 |
| 동작 | 확인 / 거절(사유 선택: 코드 없음, 채널 없음, 개인 계정, 사칭 의심, 기타) / 보류 |
| 기록 | 누가 언제 어떤 동작을 했는지 |

규칙:

1. 대기 목록은 오래된 순.
2. 중복 건은 두 계정과 두 확인 시각을 나란히 보여준다. 기존 계정의 확인을 내리는 동작은 확인 대화상자를 한 번 더 거친다.
3. 거절하면 크리에이터에게 사유가 고정 문구로 간다.
4. 동작 기록은 지우거나 고칠 수 없다.

### F-13. 협찬품 (2차. 1차에는 데이터 칸만)

목적: 인플루언서가 실제로 주소를 가장 많이 내주는 상대는 협찬 브랜드다(브랜드 담당자, 대행사, 택배 기사까지 퍼짐). 같은 구조(주소 대신 링크, 승인한 것만, 열람 기록)로 협찬품도 받는다.

핵심: 협찬은 팬 선물 버튼 옆의 선택지가 아니다. 크리에이터가 만들어 브랜드에 주는 **협찬 링크로만** 들어온다. 팬이 "협찬"을 골라 우회하는 경로를 막기 위해서다.

| 항목 | 팬 선물 | 협찬품 |
| --- | --- | --- |
| 들어오는 길 | 크리에이터 선물 링크 | 크리에이터가 브랜드별로 만든 협찬 링크 |
| 보내는 사람 | 개인 계정 | 사업자 계정(F-14) |
| 승인 | 건마다 크리에이터 승인 | 협찬 링크를 만든 것이 승인. 링크에 상자 수 상한·유효 기간(7·30·90일) |
| 검수 | 원 송장 제거 + 겉면 탐지, 조건부 개봉 | 원 송장 제거 + 겉면 탐지만. 개봉하지 않는다(언박싱 촬영용 원래 포장 유지). 반응이 나오면 크리에이터에게 "열어서 확인할까요?"를 묻고 답을 기다림 |
| 금지 품목 | 냉장·냉동·음식·액체 | 냉장·냉동만. 상온 밀봉 식품·음료·화장품 허용(사업자가 보낸 새 상품 조건). 팬 경로 금지 품목은 그대로 |
| 요금 | 팬이 박스당 | 브랜드 결제, 세금계산서 발행. 단가·월 정산 여부는 미정 |
| 보내는 쪽이 보는 상태 | 등록~수령 | 등록 → 입고 → 확인 → 출고 → 배송중 → 수령 + 수령 날짜. 주소·운송장 없음 |
| 크리에이터 반응 | 감사 답장, 함께한 시간 | 수령 확인만 |
| 링크 페이지 집계 | "N명의 팬" 숫자에 포함 | 포함하지 않음 |
| 반송 | 팬 착불 | 브랜드 사업장 주소, 브랜드 부담 |
| 크리에이터에게 남는 것 | 열람 기록 | 열람 기록 + 협찬 수령 내역(브랜드·날짜·품목) 엑셀 내려받기 |

협찬 한 건의 흐름:

1. 크리에이터가 "협찬 링크 관리"에서 브랜드 이름, 상자 수 상한, 유효 기간을 정해 링크를 만들고 브랜드 담당자에게 준다.
2. 브랜드가 링크로 들어와 사업자 계정에 로그인한다. 처음이면 사업자 확인(F-14)을 거친다.
3. 브랜드가 상자 수·구간·품목을 입력하고 결제한다. 이때 사무실 주소가 보인다.
4. 사무실 도착 → 입고 스캔(내부 라벨에 "협찬" 표시) → 겉면 탐지. 반응이 없으면 원래 포장 그대로 출고. 반응이 있으면 크리에이터 확인 대기.
5. 출고 시 송장 출력 서버 액션은 승인 토큰 대신 협찬 링크 유효성(켜짐, 상한 미초과, 기간 내)을 확인한다. 복호화·로그 규칙은 팬 선물과 같다.
6. 크리에이터가 수령 확인을 누른다. 누르지 않으면 택배사 배송 완료 날짜를 수령 날짜로 쓴다.
7. 브랜드 협찬 현황에 수령 날짜, 크리에이터 협찬 수령 내역에 한 줄이 쌓인다.

크리에이터 쪽 화면:

| 화면 | 내용 |
| --- | --- |
| 협찬 링크 관리(2차 새 화면) | 링크 만들기, 링크별 사용 현황(등록 상자 수 / 상한), 링크 즉시 끄기 |
| 승인·받은 선물(기존 화면에 탭) | "팬 선물" / "협찬품" 탭. 협찬품은 수령 확인만. 겉면 탐지 반응 건에 "열어서 확인할까요?" |
| 협찬 수령 내역(설정 안 메뉴) | 브랜드·날짜·품목 목록, 엑셀 내려받기, "광고 표시와 세무 판단은 크리에이터 몫" 안내 |

관리자 화면 차이:

| 단계 | 팬 선물 | 협찬품 |
| --- | --- | --- |
| 입고 | 원 송장 → 주문 매칭 | 같음 + 내부 라벨 "협찬" |
| 검수 | 겉면 탐지 + 조건부 개봉 | 겉면 탐지만. 개봉 버튼 없음, 반응 시 "크리에이터 확인 대기" |
| 출고 | 승인 토큰 확인 | 협찬 링크 유효성 확인 |
| 반송 | 팬 착불 | 브랜드 사업장, 브랜드 부담 |

정해야 할 것(2차 착수 전):

1. 협찬 요금: 팬 선물보다 높게 받을지, 월 정산을 열지. 인플루언서·브랜드 몇 곳에 묻고 정한다.
2. 세금계산서 발행 방법: PG 자동 발행 지원 여부, 아니면 전자세금계산서 발행 서비스 연동. PG 계약 때 함께 확인.
3. 2차 착수 조건: 인플루언서 사용자가 생기고, 그들에게 "협찬품도 팬꾹으로 받겠는가, 브랜드가 박스당 얼마까지 낼 것 같은가"를 확인한 뒤.

### F-14. 사업자 계정·사업자 확인·사업자 화면 (2차. 1차에는 데이터 칸만)

국세청 API:

- 공공데이터포털 "국세청_사업자등록정보 진위확인 및 상태조회 서비스". 무료, 개발·운영 자동 승인, 한 번에 100건·하루 100만 건, 국세청 정보와 30분 주기 동기화, 신규 개업자는 반영까지 1~2일.
- 진위확인: 사업자번호 + 대표자명 + 개업일자가 국세청 정보와 맞는지.
- 상태조회: 사업자번호로 영업 상태(계속·휴업·폐업), 과세유형, 폐업일자.
- 호출 방식: REST, JSON 본문 `b_no`에 사업자번호 배열, POST. 예: `https://api.odcloud.kr/api/nts-businessman/v1/status?serviceKey=...`
- 고정 IP 제한 없음(카카오 인증과 달리 별도 아웃바운드 경로 불필요).
- 이 API로 확인되는 것: 번호가 실재하고 영업 중이며 대표자 정보가 맞다. 확인 안 되는 것: 등록하는 사람이 그 회사 사람이다, 실제로 협찬 계약을 했다.

사업자 확인 순서:

1. 협찬 링크: 크리에이터가 브랜드와 이야기한 뒤에만 주므로 가장 강한 확인이다.
2. 진위확인 + 상태조회: 맞지 않거나 휴업·폐업이면 가입을 막는다.
3. 이름 대조: 확인된 상호와 협찬 링크의 브랜드 이름이 크게 다르면 크리에이터에게 "이 회사가 맞나요?"를 묻는다. 대행사일 수 있어 막지는 않는다.
4. 결제·세금계산서: 그 사업자 명의 결제, 그 번호로 세금계산서 발행. 남의 번호로 가입할 동기를 줄인다.
5. 월 1회 재확인: 등록 사업자 전체를 100건씩 묶어 상태조회. 휴업·폐업으로 바뀌면 새 협찬 등록 차단.
6. 신규 개업으로 조회가 안 되면 거절 대신 "확인 대기" 상태로 두고 하루 뒤 자동 재조회.

구현 규칙: API 호출은 서버에서만, 인증키(serviceKey)는 클라이언트에 내려보내지 않는다. 조회 결과(상태, 과세유형, 조회 시각)를 `businesses`에 저장하고 같은 번호를 매번 다시 묻지 않는다.

사업자 화면 4개:

| 화면 | 하는 일 | 보이는 것 | 보이지 않는 것 |
| --- | --- | --- | --- |
| 가입·사업자 확인 | 사업자번호·대표자명·개업일자 → 진위확인·상태조회 → 담당자 이름·회사 이메일·연락처 | 확인 결과(상호, 과세유형, 영업 상태) | — |

| 협찬 현황 | 크리에이터별·캠페인별로 묶어 단계 확인 | 단계, 수령 날짜 | 운송장, 주소, 다른 브랜드 협찬, 팬 선물 정보 |

브랜드와 대행사는 나누지 않는다. 대행사도 하나의 사업자 계정이고, 협찬 링크마다 브랜드 이름이 적혀 있어 한 계정에서 여러 브랜드를 보낼 수 있다. 같은 회사 담당자 여러 명이 쓰는 팀원 기능은 백로그.

담당자 연락처는 크리에이터에게 보여주지 않는다. 팬꾹이 연락 창구가 되면 반대로 크리에이터 연락처를 요구하는 경로가 생길 수 있다.

계정 종류 분리(1차부터 적용):

1. 가입 때 "개인 계정(팬·크리에이터)"과 "사업자 계정"을 고른다. 한 계정이 둘을 겸하지 않는다. 브랜드 담당자가 개인적으로 팬이면 개인 계정을 따로 만든다.

## 3. 봉인 불변식 추가 (24~31)

24. 크리에이터는 확인된 채널이 1개 이상일 때만 선물 등록을 받을 수 있다. 확인 채널이 0개면 링크 페이지에 선물 보내기가 없고 등록 API도 거부한다.
25. 링크 페이지에 공개되는 채널 링크는 확인된 채널뿐이며, 지원 플랫폼 목록 밖의 임의 URL을 저장·표시하는 경로는 없다. 외부 링크는 새 탭과 `rel="noopener noreferrer"`로 연다.
26. (플랫폼, 핸들)은 한 계정에만 verified 상태로 존재한다. 중복 확인 시도는 자동 확인되지 않고 운영자 확인으로 간다.
27. 뱃지·확인 문구는 확인한 사실(채널 소유, 사업자 등록·영업 상태)만 말한다. "공식", "안전한", "인증된 크리에이터", "검증된" 같은 문구를 쓰지 않는다.
28. 계정 종류(personal / business)는 하나의 계정에 하나다. business 계정은 팬 선물 등록에, personal 계정은 협찬 등록에 접근할 수 없다(RLS + 계약 테스트).
29. 협찬 등록은 유효한 협찬 링크(켜짐, 상자 수 상한 미초과, 유효 기간 내)로만 가능하다. 팬 선물 화면에 "협찬" 선택지는 없다.
30. 사업자 계정은 크리에이터 주소·연락처·운송장·팬 정보·다른 사업자의 협찬 정보를 어떤 화면·API로도 조회할 수 없다. 크리에이터는 사업자 담당자 연락처를 팬꾹에서 볼 수 없다.
31. 국세청 API 인증키와 카카오 인증 키 등 외부 API 인증키는 서버 환경 변수에만 있고 클라이언트 번들에 포함되지 않는다(배포 전 검사로 번들 검색).

## 7. 결정 기록 추가 (decisions.md에 이어 붙임)

### D-11. 대상을 크리에이터 전체로 넓히고 이름은 팬꾹을 유지한다

- 결정: 방송인·유튜버·인스타 인플루언서를 모두 대상으로 한다. 이름은 팬꾹 그대로, 서비스 안 호칭은 "팬"으로 통일한다.
- 이유: 팬·구독자·팔로워 중 세 플랫폼 모두에서 쓰이는 말은 "팬"이다. 구독자·팔로워는 플랫폼이 붙인 숫자 단위이고, 선물을 보내는 사람은 스스로를 팬이라고 생각한다. 방송 전용 느낌은 이름이 아니라 방송에만 맞춰진 단어·기능에서 생기므로 그것을 바꾼다.
- 보완: 플랫폼별 호칭 차이는 크리에이터가 정하는 팬덤 이름으로 살린다.
- 버린 대안: 더 넓은 이름으로 변경(팬 선물 쪽 정체성이 흐려지고 지금 바꿀 이유가 약함).

### D-12. 크리에이터는 채널 확인 후에만 선물을 받는다

- 결정: 활동 채널을 확인 코드로 검증하고, 확인 채널이 1개 이상일 때만 선물 받기를 켠다. 확인된 채널만 링크 페이지 아이콘으로 공개한다.
- 이유: 유명 크리에이터 행세를 하는 가짜 페이지로 팬 선물이 엉뚱한 사람에게 가는 것을 막는다. 확인 뱃지는 꾸밈이 아니라 보안 장치다.
- 보완: 자동 확인이 안 되는 플랫폼은 운영자 확인 화면에서 처리한다.
- 버린 대안: 확인 없이 선물 받기 허용, 임의 링크 입력 허용(남의 채널이나 피싱 사이트로 보내는 경로가 생김), "공식·인증" 같은 넓은 보증 문구.

### D-13. 협찬품은 협찬 링크로만 받는다

- 결정: 협찬은 크리에이터가 브랜드별로 만든 협찬 링크로만 등록된다. 링크를 만든 것이 승인이고, 상자 수 상한과 유효 기간이 있다. 상자는 열지 않고 겉면 탐지만 하며, 상온 밀봉 식품·화장품은 협찬 경로에서만 허용한다.
- 이유: 팬 선물 버튼 옆에 "협찬"을 두면 팬이 협찬인 척 우회할 수 있다. 인플루언서는 원래 포장 그대로 여는 콘텐츠를 찍으므로 개봉하면 안 된다. 사업자 인증된 발신자라 추적 장치 동기가 낮다.
- 범위: 2차. 1차에는 데이터 칸만.

### D-14. 사업자는 국세청 API로 확인하고, 계정 종류를 처음부터 나눈다

- 결정: 공공데이터포털 국세청 진위확인·상태조회 API로 사업자번호의 실재·영업 상태·대표자 정보 일치를 확인하고, 월 1회 재확인한다. 계정은 personal / business로 나누고 한 계정이 겸하지 않는다.
- 이유: API는 무료·자동 승인이고 고정 IP 제한이 없다. 다만 등록자가 그 회사 사람인지는 증명하지 못하므로 협찬 링크를 첫 번째 확인으로 두고 API는 두 번째 확인으로 쓴다. 계정을 겸하면 "협찬인 척하는 팬", "팬인 척하는 브랜드"가 생긴다.

### D-15. 사업자 계정은 크리에이터·직원에게만 다르게 보이고, 팬에게는 보이지 않는다

- 결정: 크리에이터에게는 "확인된 사업자" 뱃지와 상호·사업자번호 일부·영업 상태·확인 날짜·담당자 이름을 보여준다. 담당자 연락처는 보여주지 않는다. 일반 팬에게는 어디에도 보이지 않고 링크 페이지 집계에도 포함하지 않는다.
- 이유: 크리에이터가 진짜 브랜드인지 한눈에 판단하게 한다. 팬꾹이 연락 창구가 되면 크리에이터 연락처를 요구하는 경로가 생긴다.

### D-16. 사이트 소개는 "크리에이터"와 "팬"으로, 협찬은 준비 중 표시

- 결정: 첫 문구 "주소는 숨기고, 마음은 받으세요". 대상별 소개를 크리에이터·팬·브랜드로 나누고, 브랜드 쪽은 2차 출시 전까지 "준비 중"과 출시 알림 신청으로만 둔다.
- 이유: 특정 플랫폼 단어를 쓰면 방송 전용 서비스로 보인다. 없는 기능을 있는 것처럼 쓰면 표시광고법 위반 소지가 있다.
