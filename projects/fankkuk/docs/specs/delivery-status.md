# 배송 현황 표시 스펙

팬꾹이 상자를 내보낸 뒤 받는 쪽이 받을 때까지를 단계 네 개로 보여 준다. 배송 조회 서비스(웹훅)를 붙이기 전이라
택배사의 실제 위치는 모른다 — 송장 출력·출고 날짜·받는 쪽 확인과 지금 시각만으로 단계를 정한다.
팬 선물(팬 → 크리에이터)과 선물함(크리에이터 → 팬)이 같은 단계를 쓴다.

어기면 생기는 사고: 송장번호로 택배사 조회를 하면 「○○대리점」 줄에서 받는 사람의 지역이 드러난다. 받지 않은 선물을 「도착했어요」로
확정해 보여 주거나, 날짜로 짐작한 도착을 확인된 도착처럼 보여 준다. 웹훅을 붙일 때 화면을 다시 짜야 한다.

용어
- **송장 출력**: 사무실이 그 상자의 출고 송장을 출력한 것(주문 상태 송장 출력, 선물함 신청의 송장 출력 시각).
- **출고**: 사무실이 택배사에 넘긴 것(출고 확정 시각). 날짜는 서울 날짜로 센다.
- **받는 쪽 확인**: 팬 선물은 크리에이터의 「받았어요」(답장과 함께 남긴 것 포함 — gift-reply INV-G2), 선물함은 받는 팬의 「받았어요」.

## 불변식

- INV-DS1: 단계는 넷이고 문구는 결정문 그대로다 — 「팬꾹에서 보냈어요」(송장 출력부터) → 「보통 1~2일 안에 도착해요」(출고한 서울 날짜의 다음 날 0시부터)
  → 「도착했어요」(받는 쪽 확인) / 확인이 없으면 출고 + 3일(서울 날짜) 0시부터 「도착했어요(예상)」을 흐리게. 송장 출력도 출고도 없으면 배송 단계가 없다.
  단계는 저장하지 않는다 — 원천(송장 출력 여부·출고 날·받는 쪽 확인)과 화면을 그리는 서버의 지금 시각으로 한 곳(순수 함수)에서 계산한다.
  날짜 경계(다음 날 = 1, 예상 도착 = 3)는 설정값 하나씩이다.
  (강제 위치: 단계 계산 함수 · 화면은 그 결과만 그린다)
  위반 시: 같은 상자가 화면마다 다른 단계로 보이거나, 시각 경계가 시간대(UTC)로 어긋난다.
- INV-DS2: 「도착했어요」(확정)는 받는 쪽 확인으로만 된다. 날짜가 아무리 지나도 확인이 없으면 「도착했어요(예상)」이고, 확정과 구별되게 흐리게 보인다
  (팬 선물 상세의 단계 막대에서도 수령 칸을 끝난 칸으로 칠하지 않는다). 받는 쪽 확인은 출고 뒤에만 남길 수 있고, 두 번·동시에 눌러도 기록은 하나다.
  (강제 위치: 단계 계산 함수 · DB — 팬 선물은 gift-reply INV-G1·G2, 선물함은 받았어요 저장 함수의 줄 잠금 + 비어 있을 때만 씀)
  위반 시: 받지 않은 선물을 받은 것처럼 알린다.
- INV-DS3: 송장번호와 배송 이력의 노출 범위.
  ① 팬 화면·팬이 받는 응답에는 팬꾹이 발송한 송장번호가 어느 단계에서도 없다(팬 선물의 크리에이터행, 선물함의 팬행 모두). 팬이 사무실로 보낼 때 직접 넣은 자기 송장번호는 여기 해당하지 않는다(inbound-address-code INV-C7).
  ② 크리에이터 화면에는 자기 선물(자기 주소로 가는 상자)의 송장번호만 낼 수 있다. 선물함에서 팬에게 가는 송장번호는 크리에이터에게도 내지 않는다
     — 「자기 선물」이 아니고, 그 번호로 택배사 조회를 하면 팬의 지역·수령인이 드러난다.
  ③ 배송 이력의 대리점·터미널명, 기사 이름·전화, 배달 지역, 수령인은 팬·크리에이터 화면과 그 화면이 받는 응답 어디에도 내지 않는다. 단계 계산의 입력에는 이 칸이 없다.
  ④ 외부 조회 페이지(택배사·조회 서비스) 링크를 팬·크리에이터 화면에 두지 않는다 — 팬꾹 화면에서 단계만 보인다.
  (강제 위치: DB 읽기 함수가 돌려주는 칸 · 읽기 응답 꼴 검사(정해진 칸만) · 단계 계산 입력의 형)
  위반 시: 받는 사람의 지역·이름이 상대에게 드러난다(address-protection 의 목적이 무너진다).
- INV-DS4: 단계를 어디서 정할지는 설정값 하나(estimate | webhook)로 바뀐다. webhook 이면 날짜가 아니라 택배사 상태(집하·배송 중·배달 완료)로 정하고 화면 구조는 그대로다.
  택배사 상태는 웹훅 수신(INV-DS7~DS10)이 저장하고, 설정값은 DB 의 값 하나다(INV-DS11). estimate 에서는 택배사 상태 칸이 와도 쓰지 않는다.
  (강제 위치: 설정 파일 · 단계 계산 함수)
  위반 시: 웹훅을 붙일 때 화면마다 고쳐야 하고, 한쪽만 바뀐 채 남는다.
- INV-DS5: 설정값이 estimate 인 동안(웹훅 연결 전)에는 「배송 완료」를 쓰는 기준 넷 — 헤더 선물 아이콘의 체크, 선물함 신청의 delivered, 팬 주소 사본 삭제 시점, 탈퇴 가능 기준 — 이
  지금대로 출고 기준이다. 「도착했어요」(확정·예상)는 화면 단계일 뿐 이 넷을 바꾸지 않는다. 헤더 아이콘·상태 문구는 「배송 완료」 대신 「발송 완료」라고 쓴다(배달 완료를 모르기 때문).
  (강제 위치: 헤더 아이콘 판정 · DB — 받았어요 저장 함수는 신청 상태를 바꾸지 않는다)
  위반 시: 확인되지 않은 배달 완료를 근거로 주소를 지우거나 탈퇴를 허용한다.
- INV-DS6: 선물함(크리에이터 → 팬)도 INV-DS1~DS3 의 같은 단계를 쓴다. 받는 쪽은 팬이다 — 팬은 내 선물함 화면에서 단계와 [받았어요]를 보고, [받았어요]는 그 선물함에
  신청한 팬 본인만(로그인 토큰으로 DB 가 신청을 찾는다, 선물함 ID 외 인자 없음), 출고 뒤에만 남긴다. 크리에이터는 명세서 줄의 진행 칸에서 같은 단계를 본다.
  (강제 위치: DB 함수 revgift_box_fan_received · 팬이 보는 선물함 읽기)
  위반 시: 남의 신청에 받았어요가 남거나, 사무실에 있는 선물을 받았다고 표시한다.

### 배송 조회 서비스 연결 (결정 ⑦~⑩)

배송 조회 서비스(택배API)에 송장번호만 넘기고(주소·이름 없음), 서비스가 1시간마다 택배사를 조회해 웹훅으로 상태를 보낸다(밤 22~07시는 조회하지 않는다).
웹훅은 상태가 바뀌지 않아도 조회할 때마다 온다. 정해진 재전송 대기열은 없다 — 놓친 것은 다음 조회 때 최신 상태로 다시 온다.

- INV-DS7: 웹훅은 서명이 맞을 때만 받는다. 서명 = HMAC-SHA256(키 = 웹훅 서명 키, 대상 = 「요청 머리의 시각(유닉스 초)」 + 「.」 + 받은 본문 그대로의 바이트),
  머리 값은 `sha256=` + 16진수. 비교는 길이가 같을 때 시간이 일정한 비교로 한다. 시각이 지금과 5분(300초)보다 멀면(앞이든 뒤든) 서명이 맞아도 거부한다.
  본문은 받은 문자열 그대로로 검증하고, 검증이 끝난 그 문자열을 해석한다 — 해석한 뒤 다시 직렬화한 값으로 검증하지 않는다.
  서명 키가 서버 설정에 없으면 모든 웹훅을 거부한다(검증 없이 받는 길이 없다). 거부는 401, 내용은 비운다.
  (강제 위치: 웹훅 서명 검증 함수 · 웹훅 수신 라우트)
  위반 시: 누구나 「배달 완료」를 보내 팬 주소를 일찍 지우게 하거나 탈퇴 기준을 앞당기고, 받지 않은 선물을 받은 것처럼 보인다. 지난 요청을 다시 보내 상태를 되돌린다.
- INV-DS8: 같은 웹훅이 두 번 와도, 순서가 바뀌어 와도 결과가 같다. 택배사 단계(집하 < 배송 중 < 배달 완료)는 앞으로만 간다 — 뒤 단계를 받은 뒤 앞 단계가 와도 그대로다.
  배달 완료 시각은 처음 받은 때 한 번만 정해진다. 이력 줄은 (송장, 택배사 시각, 상태 코드)마다 하나만 남는다.
  (강제 위치: DB — 수신 처리 함수(조건부 갱신·고유 인덱스))
  위반 시: 다시 보낸 요청이 단계를 되돌리거나, 배달 완료 시각이 늦춰져 주소 삭제·탈퇴 기준이 흔들린다.
- INV-DS9: 팬꾹이 등록하지 않은 송장(택배사·송장번호 짝이 없는 것)은 무시한다 — 아무것도 저장하지 않고, 응답은 200(조회 서비스가 같은 것을 되풀이하지 않게).
  (강제 위치: DB — 수신 처리 함수)
  위반 시: 남의 송장 이력이 쌓이거나, 송장번호를 맞혀 보는 데 쓰인다.
- INV-DS10: 원본을 저장하지 않는다. 웹훅·수동 조회로 받은 것(택배사가 준 그대로 — 대리점·터미널·기사·지역·수령인·발송인 포함)은 받은 자리에서
  택배사·송장번호·상태 코드·이력의 (시각, 상태 코드)만 골라내고 나머지는 버린다 — DB 의 어느 표에도, 로그에도 남지 않는다.
  남는 것은 송장마다의 단계(집하·배송 중·배달 완료)·마지막 상태 코드·수신 시각·배달 완료 시각과 이력 줄(시각·상태 코드, 위치·설명·사람 칸 없음)뿐이다.
  이 단계·시각 기록은 대금 결제·재화 공급에 관한 기록이라 주문 기록과 같이 5년 보관한다(전자상거래법 제6조·시행령 제6조) —
  송장의 사무실 상자·선물함 신청이 지워질 때 함께 지워지고, 기간을 세는 주문의 「마지막 기록」에 배송 단계 수신 시각이 들어간다(my-account INV-A15·A16).
  화면·응답이 읽는 것은 단계와 배달 완료 시각뿐이다. 운영자 화면에도 송장번호 끝 네 자리·단계·마지막 수신 시각만 낸다.
  분쟁 때 택배사 기록이 필요하면 운영자 수동 조회(INV-DS14)로 다시 받는다 — 그 응답도 같은 수신 처리를 거쳐 단계·시각만 반영한다.
  (강제 위치: 앱 — 받은 본문을 정리하는 함수(정리한 꼴에 원본 칸 없음) · DB 로 넘기는 꼴 / DB — 수신 처리 함수(정해진 칸만 읽음) · 단계·이력 표의 칸 ·
  읽기 함수가 돌려주는 칸 · 운영자 읽기 응답 꼴 검사 · 자동 삭제 작업)
  위반 시: 받는 사람의 지역·이름이 화면에 드러나거나(INV-DS3 ③), 배송에 필요 없는 수령인·대리점 정보가 쌓여 처리방침의 약속(원본 미저장)을 어긴다.
  단계 기록을 5년 전에 지우면 공급 기록이 없어진다.
- INV-DS11: 단계 설정값(estimate | webhook)은 DB 의 설정값 하나다. webhook 일 때 「배달 완료」 수신으로 넷이 함께 바뀌고, estimate 이면 넷 다 출고 기준 그대로다(INV-DS5).
  ① 헤더 선물 아이콘의 체크 = 배달 완료(문구 「배송 완료」). estimate 이면 출고(문구 「발송 완료」).
  ② 선물함 신청의 delivered = 배달 완료 수신 때 shipped 에서 바뀐다. estimate 이면 바꾸지 않는다.
  ③ 팬 주소 사본 삭제 = 배달 완료 + 24시간. estimate 이면 출고 + 72시간.
  ④ 탈퇴 가능 = 배달 완료. estimate 이면 출고.
  webhook 인데 배달 완료가 오지 않으면(조회 서비스 장애·반송·택배사 분실) 출고 + 14일에 배달 완료로 본다 — ③④ 가 끝없이 미뤄지지 않게.
  화면 단계(INV-DS4)도 같은 값을 따른다. 앱 코드에 기본값을 두지 않는다 — 화면은 DB 에서 읽은 값을 넘겨받아 계산한다.
  (강제 위치: DB 설정 표·판정 함수 둘(배달 완료로 보는가 · 사본을 지울 때인가) · 단계 계산 함수의 필수 인자 · 헤더 아이콘 판정)
  위반 시: 한쪽만 바뀌어 배달 전에 주소를 지우거나(반송할 곳이 없다), 화면은 배달 완료인데 탈퇴가 막히거나 그 반대가 된다.
- INV-DS12: 조회 서비스는 꺼져 있어도 아무것도 막지 않는다. 송장번호를 저장하면 같은 처리에서 구독 대기 줄이 생기고(DB), 구독 요청(외부 호출)은 그 처리가 끝난 뒤
  따로 한다 — 실패해도 송장 저장·출고는 그대로다. 대기 줄은 정해진 때마다 다시 시도한다. 키가 서버 설정에 없으면 구독하지 않고(대기 줄만 남는다) 화면은 estimate 대로다.
  택배사 코드는 실제 운송사다 — 로지아이 경로 → cj, 우체국 → post. 그 밖의 경로(대리점)는 구독하지 않는다.
  (강제 위치: DB — 송장번호 저장 때 대기 줄 만드는 트리거 · 구독 어댑터 · 예약 작업)
  위반 시: 조회 서비스 장애가 출고를 막는다. 키 없이 띄운 서버가 시작하지 못한다.
- INV-DS13: 조회 서비스에 넘기는 것은 택배사 코드·송장번호·팬꾹 내부 번호(무작위 ID)뿐이다 — 주소·이름·전화·주문번호·닉네임은 넘기지 않는다.
  키·시크릿·서명 키는 서버 설정에만 있고 화면·응답·로그에 나오지 않는다.
  (강제 위치: 구독·조회 어댑터의 요청 본문 조립 · 서버 설정 읽기)
  위반 시: 위탁 없이 개인정보를 넘긴다(처리방침과 어긋난다).
- INV-DS14: 구독했는데 아직 배달 완료가 아닌 송장에서 웹훅이 24시간 오지 않으면 운영자 화면에 경고를 띄운다. 팬·크리에이터 화면은 마지막 단계를 그대로 둔다.
  운영자는 그 줄에서 수동 조회를 눌러 지금 상태를 받아 같은 수신 처리(INV-DS8~DS10)로 단계·시각만 반영한다(응답 원본은 저장하지 않는다). 수동 조회는 운영자만, 한 번에 50개까지.
  (강제 위치: 운영자 읽기 함수 · 수동 조회 라우트(운영자 판정은 DB))
  위반 시: 웹훅이 끊긴 것을 아무도 모르고 단계가 멈춘다.

## 시나리오

- S1 (INV-DS1): Given 서울 11월 9일 23시 59분 출고 / When 그날 23시 59분 · 10일 0시 · 12일 0시 직전 · 12일 0시에 본다 / Then 팬꾹에서 보냈어요 · 보통 1~2일 · 보통 1~2일 · 도착했어요(예상).
- S1b (INV-DS1, 실패경로): Given 검수 완료·출고 대기(송장 전) / Then 배송 단계 없음.
- S2 (INV-DS2): Given 출고한 날 / When 받는 쪽이 받았어요 / Then 도착했어요(확정), 흐리지 않음, 막대 끝까지.
- S2b (INV-DS2, 실패경로): Given 확인 없음 / When 30일 뒤 / Then 여전히 도착했어요(예상), 수령 칸은 끝나지 않음.
- S2c (INV-DS2, 실패경로): Given 출고 전 선물함 신청 / When 팬이 받았어요 / Then 거부, 기록 없음. 동시에 두 번 / Then 기록 하나.
- S3 (INV-DS3, 실패경로): Given 출고 송장번호가 있는 팬 선물 / When 팬 목록·팬 상자별 받았어요·크리에이터 받은 선물·선물 현황 읽기 / Then 어느 응답에도 그 번호가 없다(출고 날짜는 있다).
- S3b (INV-DS3, 실패경로): Given 팬행 송장번호가 있는 선물함 신청 / When 팬이 보는 선물함·크리에이터의 선물함 / Then 번호 없음. 팬 읽기 응답에 송장번호 칸이 섞여 오면 받지 않는다.
- S3c (INV-DS3, 실패경로): Given 크리에이터 선물 현황 · 팬 선물 상세 / Then 배송 조회 버튼·외부 조회 링크 없음.
- S4 (INV-DS4): Given webhook / Then 택배사 상태 없음 = 팬꾹에서 보냈어요, 집하·배송 중 = 보통 1~2일, 배달 완료 = 도착했어요. estimate 에서는 택배사 상태를 쓰지 않는다.
- S5 (INV-DS5): Given 출고된 팬 선물 / Then 헤더 아이콘 체크(발송 완료), 문구에 「배송 완료」 없음. 선물함 받았어요 뒤에도 신청 상태 shipped 그대로.
- S6 (INV-DS6): Given 선물함 신청 — 송장 전 · 송장만 · 출고 2일 / Then 팬 화면 준비 중 · 팬꾹에서 보냈어요(버튼 없음) · 단계 + [받았어요]. 신청하지 않은 팬·크리에이터·로그인 안 함은 남길 수 없다.

- S7 (INV-DS7): 맞는 서명 → 200·저장 / 서명 틀림 → 401 / 시각 301초 전·301초 뒤 → 401 / 본문 한 글자 바꿈 → 401 / 서명 키 없음 → 401.
- S8 (INV-DS8): 같은 본문 두 번 → 이력 줄 수 같음 · 배달 완료 뒤 배송 중 → 배달 완료 그대로, 배달 완료 시각 그대로.
- S9 (INV-DS9): 등록하지 않은 송장 → 저장 없음, 200.
- S10 (INV-DS10): 수령인·대리점이 든 본문(웹훅·수동 조회) → 팬·크리에이터 읽기 응답과 운영자 응답 어디에도 그 글자가 없고, DB 의 어느 표에도 없다. 단계·시각은 남는다.
- S10b (INV-DS10, my-account INV-A16): 둘 다 탈퇴한 5년 1일 된 주문인데 배송 단계 수신이 최근 → 주문·단계 기록 남음 / 배송 단계 수신도 5년 1일 전 → 주문과 함께 지워짐.
- S11 (INV-DS11): 같은 배달 완료를 estimate / webhook 에서 → estimate: 헤더 「발송 완료」·신청 shipped·사본 출고 + 72시간·출고 뒤 탈퇴 가능 /
  webhook: 헤더 배달 완료 전 체크 없음·신청 delivered·사본 배달 완료 + 24시간·배달 완료 전 탈퇴 거부. 14일 동안 배달 완료가 없으면 webhook 도 배달 완료로 본다.
- S12 (INV-DS12): 키 없음 → 구독 요청 없음, 송장 저장 성공 · 구독 요청 실패 → 송장 저장 성공, 대기 줄 남음.
- S14 (INV-DS14): 마지막 수신 25시간 전 → 경고 / 23시간 전 → 없음 / 배달 완료 → 없음.

## 신뢰 경계

- 웹훅 본문·머리: 서명이 맞기 전에는 아무것도 믿지 않는다. 서명이 맞아도 택배사 코드·송장번호는 팬꾹이 등록한 짝일 때만 쓰고, 상태 코드는 정해진 목록 밖이면 단계로 쓰지 않는다.

- 믿지 않는 값: 브라우저 시각(단계 경계는 서버가 그린 시각), 요청 본문의 신청·팬 ID(받았어요는 선물함 ID 하나만 받고 신청은 로그인 토큰으로 찾는다).
- 읽기 응답은 정해진 칸만 받는다 — 송장번호·이력 칸이 섞여 오면 화면 코드가 거부한다.

## 스스로 정한 것

- 「다음 날」·「출고 + 3일」은 서울 날짜로 센다(72시간이 아니라 날짜) — 「다음 날」과 같은 기준으로 맞췄다.
- 한 주문의 상자는 한 송장으로 함께 나가므로, 팬 선물 상세는 상자 중 하나라도 받았어요가 있으면 「도착했어요」로 본다.
- 크리에이터 받은 선물 목록은 받았어요를 남긴 상자의 글을 지금처럼 답장 상태(수령 확인·답장)로 두고, 아직 남기지 않은 상자에만 단계 문구를 붙인다.
- 팬 선물 상세의 단계 막대 여섯 칸은 그대로 두고, 「배송 중」·「수령」 칸만 단계에 맞춘다(보통 1~2일 → 배송 중 끝, 도착했어요 → 수령 끝, 예상 → 수령 칸 흐리게).
- 서명 시각 허용 오차 5분(300초): 조회 서비스 문서의 검증 예시가 300초를 쓰고, Stripe·Slack 웹훅 서명도 5분이 기본이다(업계 표준).
- 웹훅 24시간 경고: 웹훅은 상태가 그대로여도 조회 때마다(1시간) 온다. 가장 긴 정상 공백은 밤 조회 중단 22~07시 9시간 + 조회 간격 1시간 = 약 10시간이라,
  24시간이면 낮 조회를 열 번 넘게 놓친 것이다 — 밤 공백만으로는 경고가 뜨지 않는다. 그래서 밤 시간을 따로 빼지 않고 벽시계 24시간으로 센다.
  구독한 뒤 웹훅이 한 번도 오지 않았으면 구독한 때부터 센다.
- 신호 없음 상한 14일: 구독(recurring)이 14일 동안만 조회하므로 그 뒤에는 상태가 더 오지 않는다. 그때 배달 완료로 본다(주소 사본 삭제·탈퇴).
- 배달 완료 시각은 택배사 이력의 시각이 아니라 팬꾹이 처음 받은 시각이다 — 밤사이 배달은 아침에 들어오므로 주소 삭제가 그만큼 늦어지는 쪽(보수적)이다.
- 택배사 단계 대응: PICKED_UP → 집하, IN_TRANSIT·OUT_FOR_DELIVERY → 배송 중, DELIVERED → 배달 완료. 그 밖(PENDING·REGISTERED·PICKUP_READY·FAILED·RETURNED·CANCELLED·HOLD·UNKNOWN)은 단계를 바꾸지 않는다.
- 택배사 코드는 구독할 때의 기본 택배 경로로 정한다(로지아이 두 경로 → cj, 우체국 → post, 대리점 → 구독 안 함).
- 팬 선물은 주문의 상자가 모두 배달 완료일 때 주문을 배달 완료로 본다(그 전에 하나라도 집하 이후면 배송 중).
- 배송 단계 기록의 5년은 주문(팬 선물)·보내기(역조공)의 「마지막 기록」에 배송 단계 수신·배달 완료 시각을 넣어 센다(2026-11-09). 선물함(revgift-box)은 선물함이 끝난 때부터 센다 —
  끝난 뒤 들어온 배송 단계 수신은 아직 기간 계산에 넣지 않았다(BACKLOG).
- 재출력 창(출고 + 72시간)은 그대로 둔다 — webhook 에서 사본이 더 오래 남아도 출고 + 72시간 뒤에는 주소를 다시 열지 않는다(더 좁은 쪽).
