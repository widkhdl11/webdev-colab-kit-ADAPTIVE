# 크리에이터 본인 확인 스펙

크리에이터로 가입한 계정이 자기 채널의 주인인지 확인하는 기능이다. 방송인만이 아니라 크리에이터라면 누구나 받는다.
확인 방법은 그 플랫폼에 팬꾹이 쓸 수 있는 공식 API 가 있는지로 갈린다(INV-V2 표의 「API 확인」 칸). 공개 게시물로 코드를 올리게 하지 않는다 —
팔로워가 모두 보기 때문이다.

- **API 가 있는 플랫폼**(유튜브·치지직·인스타그램 프로페셔널 계정)
  - **플랫폼 로그인(기본)** — 그 플랫폼에 로그인해 「이 사람의 채널이 이것」이라는 답을 받으면 바로 확인된다. 아무것도 올리지 않는다(INV-V14).
  - **코드 자동 확인(보조)** — 로그인을 쓰기 어려우면 채널 주소로 **신청**해 **인증 코드**를 받고, 채널 **소개란**에 잠깐 붙인 뒤 「확인」을 누른다.
    서버가 그 플랫폼의 공식 API 로 공개 소개란을 읽어 코드를 찾으면 그 자리에서 승인된다. 승인 뒤 코드는 지워도 된다(INV-V16).
- **API 가 없는 플랫폼**(SOOP·인스타그램 개인 계정 등, 확인 전인 곳 포함) — **운영자 확인**. 신청해 받은 코드를 채널 소개란에 붙이거나
  팬꾹 공식 계정으로 DM 을 보내고 「확인 요청」을 누른다. 운영자가 채널이나 DM 을 열어 보고 **승인**하거나 **반려**한다.
  API 가 있는 플랫폼에서 자동 확인이 안 되는 경우(인스타그램 개인 계정 등)도 이 길로 온다.
- 한 계정이 같은 채널로 낼 수 있는 코드 신청은 3번까지다(INV-V15). 플랫폼 로그인과 실제 공식 API 연결은 외부 연결 때 붙인다 —
  그때까지 로컬에서는 가짜 창구(운영에서는 없음)로 흐름을 끝까지 돌린다. 승인 서명의 가짜 서명 창구와 같은 꼴이다.

승인되면 그 크리에이터는 크리에이터 찾기에 나오고 선물·팔로우를 받는다. 승인 **취소**는 이미 있는 기능이다(INV-K10).

어기면 생기는 사고는 넷이다.
- 남의 채널 주소로 확인을 받으면, 유명 크리에이터를 사칭한 계정이 팬의 선물을 받는다. 팬은 그 계정으로 선물을 보내고
  승인 서명이 끝나면 물건이 사칭한 사람에게 간다.
- 같은 채널로 두 계정이 승인되면, 팬이 찾기에서 같은 채널 둘을 보고 어느 쪽이 진짜인지 모른다.
- 인증 코드가 겹치거나 미리 짐작되면, 진짜 주인이 자기 신청을 위해 올린 코드로 다른 계정의 신청이 승인될 수 있다.
- 사칭하려는 계정이 같은 채널로 신청을 끝없이 되풀이하면, 한 채널 한 명 규칙(INV-V8) 때문에 진짜 주인이 계속 막힌다.

용어
- **신청**: 크리에이터 계정 하나가 채널 주소 하나로 확인을 요청한 기록. 상태는 다음과 같다.
  - **코드 받음**: 신청이 만들어져 코드가 나간 상태. 발급 뒤 7일이 지나면 **기간 지남**으로 본다(INV-V5).
  - **올림(확인 대기)**: 크리에이터가 「확인 요청」(운영자 확인 길 — 지난 판의 「코드 올렸어요」)을 누른 상태. 운영자 확인을 기다리고, 기한이 없다.
  - **승인됨** · **반려됨** · **거둠**(크리에이터가 신청을 거두거나 「코드 다시 받기」로 버린 것) ·
    **닫힘**(다른 계정이 플랫폼 로그인으로 같은 채널을 확인해 끝난 것, INV-V14).
  - **살아 있는 신청** = 기간이 지나지 않은 코드 받음, 또는 올림.
- **채널 키**: 서버가 채널 주소에서 뽑은 (플랫폼, 채널 식별자) 한 쌍. 주소 표기가 달라도 같은 채널이면 같은 키다(INV-V2).
- **채널 점유**: 한 채널 키를 지금 누가 쥐고 있는지. 살아 있는 신청이나 확인된 크리에이터가 쥔다(INV-V8).
- **확인됨**: 크리에이터 공개 정보의 본인 확인 칸이 참인 상태. 찾기·팔로우·선물 등록은 이미 이 칸으로 거른다.
- **운영자**: 관리자 화면에 들어오는 계정(대표·직원). admin-console 의 운영자 판정을 그대로 쓴다.

## 불변식

- INV-V1: 신청은 크리에이터 역할 계정이 자기 자신에 대해서만 한다. 요청에 담기는 것은 채널 주소 하나뿐이다 — 이름·채널 이름·분야 같은
  기본 공개 정보는 가입 때 받아 둔 것을 쓴다. 누구의 신청인지는 로그인 토큰이 확인한 사람(INV-L2)으로 서버가 정한다.
  브라우저가 계정·크리에이터 식별값을 보내도 쓰지 않는다. 팬·운영자·로그인하지 않은 사람의 신청은 거부한다.
  (강제 위치: DB 신청 함수 — 인자는 채널 주소 하나, 진입부에서 auth.uid() 의 역할이 크리에이터인지 확인)
  위반 시: 팬 계정이나 다른 크리에이터 계정 이름으로 신청이 생겨, 승인되면 엉뚱한 계정이 확인된 크리에이터가 된다.

- INV-V2: 채널 주소는 서버가 형식을 검사한다. 신청을 받는 플랫폼은 아래 표에서 「받음」인 것뿐이고, 플랫폼마다 받는 주소 꼴과 채널 키 규칙이 정해져 있다.
  공통 규칙: `https` 만 받는다. 쿼리(`?…`)·조각(`#…`)·끝의 `/` 는 버린다. `www.`·`m.` 이 붙거나 빠져도 같은 호스트로 본다.
  저장하는 주소는 **브라우저가 보낸 문자열이 아니라 서버가 채널 키로 다시 만든 주소**다. 목록 밖의 호스트, 아래 꼴이 아닌 경로는 거부한다.
  「받지 않음」 플랫폼과 목록 밖 플랫폼의 주소는 「1:1 문의로 알려 주세요」로 거부한다 — 운영자가 그 플랫폼의 규칙을 이 표에 더하기 전까지 신청할 수 없다.

  「API 확인」 칸: 로그인·자동 확인을 쓸 수 있으면 「있음」. 「있음」인 플랫폼만 INV-V14·V16 의 함수가 받는다. 확인 전이면 「없음」으로 두고,
  공식 API 를 확인하면 바꾼다(운영자가 아니라 이 표를 고치는 사람의 결정). 2026-10-06 조사: 유튜브는 로그인한 사람의 채널만 돌려주는 공식 기능과
  공개 채널 정보 조회가 있다. 치지직은 공식 개발자 센터에 로그인 연결이 있다(공개 소개란 조회는 연결 때 확인). 인스타그램은 프로페셔널 계정만
  로그인 연결과 다른 프로페셔널 계정의 소개란 조회(Business Discovery)가 된다. SOOP 은 공식 로그인 연결을 찾지 못했다.

- INV-V3: 인증 코드는 서버가 만든다. 신청 한 건에 코드 하나이고, 신청이 만들어질 때 정해져 그 뒤로 바뀌지 않는다.

- INV-V6: 인증 코드 신청의 승인과 반려는 운영자만 한다 — 예외는 API 가 있는 플랫폼의 코드 자동 확인(INV-V16)이 코드 받음 상태의 신청을 승인하는 것 하나다.

  위반 시: 남의 신청 코드를 읽어 그 코드를 자기 채널에 올리는 식으로 운영자를 헷갈리게 하거나, 신청 목록이 크리에이터 연락처를 모으는 통로가 된다.
  닫힘 사유에 상대 계정이 나오면 사칭자가 진짜 주인의 계정을 알게 된다.

- INV-V12: 확인된 크리에이터가 채널을 옮기려면 새 채널로 신청한다. 그 신청이 살아 있는 동안(코드 받음·올림):
  찾기에는 그대로 나오고 예전 채널이 보인다. 팔로우도 그대로 된다. **새 선물 등록은 막힌다** — 선물 보내기 화면에 「채널 이사 중」 안내가 뜨고,
  DB 등록 함수가 거부한다(크리에이터 → 크리에이터 선물도 같다). 이미 등록된 주문은 그대로 간다.
  새 신청이 승인되면(운영자 승인이든 로그인 확인이든) INV-V7 대로 새 채널로 바뀌고, 옛 채널 점유는 같은 처리에서 풀리고, 등록이 다시 열린다.
  반려·기간 지남·거둠·닫힘이면 예전 채널 그대로 등록이 다시 열린다(기간 지남은 계산값이라 따로 처리가 돌지 않아도 열린다).
  이사 신청과 선물 등록이 동시에 와도 「이사 신청이 끝난 뒤에 생긴 주문」은 없다.
  (강제 위치: DB 선물 등록 함수 — 받는 크리에이터의 살아 있는 신청 확인, 차단 확인(INV-D7)과 같은 자리 / DB 신청 함수 — 같은 크리에이터 잠금)
  위반 시: 채널을 옮기는 동안 들어온 선물이 확인되지 않은 새 채널 기준으로 승인돼 나간다. 등록 막기를 화면에만 두면 주소를 직접 부르는 등록이 지나간다.
  옛 채널 점유가 남아 그 채널의 다른 주인이 신청하지 못한다.

- INV-V13: 신청과 결정 기록에는 확인 방법 칸이 있다. 값은 「인증 코드」(운영자 확인)·「코드 자동 확인」·「플랫폼 로그인」 셋이다.
  크리에이터의 신청 함수는 언제나 「인증 코드」로 적고, 브라우저가 방법 값을 보내도 쓰지 않는다. 「코드 자동 확인」은 INV-V16 의 자동 확인 함수가
  승인 기록에만 적고, 「플랫폼 로그인」은 INV-V14 의 로그인 확인 함수만 적는다.
  (강제 위치: DB 제약 — 확인 방법 칸의 허용 값 / DB 신청 함수 — 방법 인자 없음 / 자동 확인·로그인 확인 함수만 그 값을 기록)
  위반 시: 어느 확인이 어느 방법으로 됐는지 기록에서 가릴 수 없다. 브라우저가 「플랫폼 로그인」을 적을 수 있으면 운영자 확인 없이
  확인됨이 되는 경로가 열린 것처럼 보이고, INV-V14 의 「로그인 확인이 이긴다」를 흉내 내 남의 신청을 닫을 수 있다.

- INV-V14: 플랫폼 로그인으로 채널 주인이 확인되면(유튜브·치지직·인스타그램 프로페셔널 계정) 그 계정은 바로 승인된다. 같은 채널 키에 **다른 계정의
  살아 있는 코드 신청**이 있으면 로그인 확인이 이긴다 — 한 처리 안에서 그 신청은 닫힘(사유 「다른 계정이 채널 주인 확인을 마쳤어요」)이 되고,
  점유는 로그인 확인한 계정으로 넘어가고, 그 계정의 신청 한 줄(확인 방법 「플랫폼 로그인」)이 승인된다(INV-V7). 로그인 확인한 계정에 다른 채널의
  살아 있는 신청이 있으면 같은 처리에서 거둔다(INV-V4). 같은 채널이 **다른 계정으로 이미 확인돼 있으면** 로그인 확인도 그 확인을 빼앗지 않는다 —
  「이미 등록한 채널이에요. 1:1 문의로 알려 주세요」로 거부하고, 운영자가 문의를 보고 승인을 취소한다(INV-K10).
  이 함수의 사람 값과 채널 키는 브라우저가 아니라 서버가 정한다 — 계정은 로그인 토큰이 확인한 사람(INV-L2), 채널 키는 서버가 플랫폼에서 직접 받은 답이다.
  함수는 서버의 관리자 키로만 부를 수 있고 로그인한 사용자 권한으로는 부를 수 없다. 플랫폼 로그인 연결 자체는 외부 연결 때 붙인다 —
  이 불변식의 시험은 그 DB 함수를 서버 권한으로 직접 불러 한다.
  운영자 승인과 로그인 확인이 같은 채널에 동시에 와도 하나만 반영된다 — 운영자 승인이 먼저 끝나면 그 채널은 확인된 채널이 되어 로그인 확인이 위의 「이미 등록한 채널」로
  거부되고, 로그인 확인이 먼저 끝나면 운영자 승인은 「이미 처리됨」이다.
  (강제 위치: DB 로그인 확인 함수 — 서버 관리자 키 전용 실행 권한, 채널 점유 행 잠금 뒤 다른 계정의 신청을 닫고 점유를 옮김)
  위반 시: 사칭자가 먼저 코드 신청을 내 두면 로그인으로 확인할 수 있는 진짜 주인도 「이미 확인중인 채널이에요」에 막힌다. 로그인한 사용자가
  이 함수를 직접 부를 수 있으면 아무 채널 키나 넣어 남의 신청을 닫고 자기 것으로 승인받는다.

- INV-V15: 인증 코드 신청은 한 계정이 같은 채널 키로 3번까지 낼 수 있다. 세는 것은 그 계정·그 채널 키의 코드 신청 가운데 **승인되지 않고 끝난 것**이다 —
  반려됨·기간 지남·거둠(「코드 다시 받기」로 버린 것 포함)·닫힘. 승인됐던 신청은 세지 않는다(승인 뒤 취소돼 다시 신청하는 것은 실패가 아니다).
  센 값이 3이면 그 채널로 새 코드 신청과 「코드 다시 받기」가 모두 거부되고 「이 채널로는 더 신청할 수 없어요. 1:1 문의로 알려 주세요」가 뜬다.
  센 값이 2이고 살아 있는 신청이 있으면 「코드 다시 받기」도 거부된다 — 지금 신청을 버리면 3이 되어 새 신청을 만들 수 없기 때문이다(지금 신청은 그대로 둔다).
  다른 채널 키의 횟수와는 따로 센다. 플랫폼 로그인 확인은 횟수와 상관없다.
  운영자는 문의를 보고 그 계정·그 채널 키의 횟수를 풀어 줄 수 있다 — 풀면 그 뒤에 끝난 신청만 다시 센다. 누가·언제·어느 계정·어느 채널을 풀었는지와
  메모를 지울 수 없는 기록으로 남긴다. 횟수는 칸에 저장하지 않고 신청 줄과 마지막 풀기 시각으로 계산한다.
  (강제 위치: DB 신청·다시 받기 함수 — 계정 잠금 안에서 계산 / DB 풀기 함수 — 진입부 운영자 판정 / 풀기 기록 표는 고치기·지우기 금지)
  위반 시: 거둠이나 다시 받기를 세지 않으면 사칭자가 7일마다 다시 받기로 같은 채널을 끝없이 쥐고 있는다. 승인됐던 신청까지 세면 취소 뒤 다시 확인받으려는
  진짜 주인이 막힌다. 크리에이터가 풀기를 부를 수 있으면 제한이 없는 것과 같다.

- INV-V16: 코드 자동 확인은 「API 확인」이 있는 플랫폼의 코드 받음 상태 신청에만 한다. 서버가 그 플랫폼의 공식 API 로 신청의 채널 키에 해당하는
  채널의 **공개 소개란**을 읽어, 그 신청의 인증 코드가 들어 있으면 그 자리에서 승인한다(INV-V7 — 운영자 승인과 같은 처리, 확인 방법 「코드 자동 확인」).
  읽을 채널과 찾을 코드는 신청 줄에서 서버가 정한다 — 브라우저가 보낸 소개란 글·채널 주소·코드는 쓰지 않는다. 코드가 없으면 신청은 그대로이고
  「아직 소개란에서 코드를 찾지 못했어요」를 돌려준다(실패로 세지 않는다 — 자동 확인은 발급 시각과 7일 기한을 다시 시작하지 않으므로, 못 찾은 신청은
  7일 뒤 기간 지남이 되어 INV-V15 횟수에 들어간다). 읽는 곳은 채널 주인만 고칠 수 있는 소개란 칸 하나다 — 댓글·커뮤니티 글·링크 칸은 읽지 않고,
  코드는 `FK-XXXX-NN` 꼴 그대로 일치해야 한다.
  한 신청의 자동 확인은 1분에 한 번까지다 — 플랫폼 API 의 호출 한도를 지키기 위해서다. 이 제한은 DB 의 「마지막 확인 시각」으로 지킨다
  (1분이 지났을 때만 갱신되는 한 번의 조건부 갱신 — 앱 서버가 여러 대이거나 다시 시작해도 풀리지 않는다). 전체 호출량 상한은 연결 때 플랫폼 한도를 보고 정한다.
  자동 확인 함수는 서버의 관리자 키로만 부를 수 있다(INV-V14 의 로그인 확인 함수와 같다). 운영자의 반려·크리에이터의 거두기와 동시에 와도 하나만 반영된다(INV-V6).
  공식 API 연결은 외부 연결 때 붙인다 — 그때까지 로컬에서는 가짜 소개란 창구가 그 신청의 코드를 담은 글을 돌려주고, 운영에서는 창구가 없어 자동 확인이 거부된다.
  (강제 위치: 앱 서버 — 플랫폼 API 호출, 소개란 칸만 읽기 / DB — 마지막 확인 시각 조건부 갱신으로 1분 제한 / DB 자동 확인 함수 — 서버 관리자 키 전용, 신청 행 잠금 뒤 상태·기한·플랫폼 「있음」 확인)
  위반 시: 브라우저가 보낸 소개란 글을 믿으면 누구나 코드를 적은 가짜 글로 남의 채널을 승인받는다. API 가 없는 플랫폼에서 공개 페이지를 긁어 확인하면
  약관 위반이고 페이지가 바뀔 때 조용히 틀린다. 횟수 제한이 없으면 버튼 연타가 플랫폼 API 한도를 다 써 다른 크리에이터의 확인이 막힌다.

## 시나리오

- S1 (INV-V1): Given 가입 때 이름·채널 이름·분야를 적은 크리에이터 꿀단지 / When 유튜브 주소로 신청 / Then 꿀단지의 코드 받음 신청 1건과 코드가 생긴다.
- S1b (INV-V1, 실패경로): Given 팬 계정 별빛 · 운영자 모아 · 로그인하지 않음 / When 신청 / Then 셋 다 거부, 신청 0건.
- S1c (INV-V1, 실패경로): Given 꿀단지 로그인 / When 요청에 하루의 계정 값을 붙여 신청 / Then 그 값은 무시되고 신청은 꿀단지의 것이다.
- S2 (INV-V2): Given 꿀단지 / When `https://m.youtube.com/@GgulDanji/videos?x=1` 로 신청 / Then 저장된 주소는 `https://www.youtube.com/@gguldanji` 이고 채널 키는 (유튜브, `gguldanji`).
- S2b (INV-V2): Given 여름밤 / When `https://instagram.com/Summer_Night_KO/` 로 신청 / Then 채널 키는 (인스타그램, `summer_night_ko`).
- S2c (INV-V2, 실패경로): Given 꿀단지 / When `http://` 주소 · 목록 밖 호스트(`https://evil.example/@a`, 틱톡 주소) · 유튜브 `/channel/UC…` 주소 · 정해진 꼴이 아닌 경로 / Then 거부, 신청 0건.
- S2d (INV-V2, 실패경로): Given 앱 서버의 형식 검사가 빠진 상태 / When 목록 밖 호스트 주소가 DB 신청 함수에 도달 / Then DB 가 거부한다.
- S2e (INV-V2, 실패경로): Given 꿀단지 / When `https://rplay.live/…` 주소로 신청 / Then 거부, 「1:1 문의로 알려 주세요」, 신청 0건.
- S3 (INV-V3): Given 신청 1000건 / When 코드를 모음 / Then 겹치는 코드 0개, 모두 `FK-XXXX-NN` 꼴.
- S3b (INV-V3, 실패경로): Given 살아 있는 신청 / When 요청에 원하는 코드를 붙여 신청 · 신청 행의 코드 칸을 고치려 함 / Then 보낸 코드는 무시되고, 고치기는 거부된다.
- S4 (INV-V4): Given 꿀단지의 코드 받음 신청(코드 A) / When 코드 다시 받기 / Then 코드 A 신청은 거둠, 새 신청(코드 B, 새 7일) 1건.
- S4b (INV-V4, 실패경로): Given 코드 A 신청이 다시 받기로 거둠 / When 꿀단지가 코드 A 신청에 「코드 올렸어요」 · 운영자가 승인 / Then 둘 다 거부, 확인됨 거짓 그대로.
- S4c (INV-V4, 동시): Given 살아 있는 신청 없는 꿀단지 / When 신청 두 개가 동시에 / Then 살아 있는 신청은 1건.
- S4d (INV-V4, 실패경로): Given 꿀단지의 올림 신청 / When 다른 채널로 새 신청 / Then 거부, 살아 있는 신청 1건 그대로.
- S4e (INV-V4): Given 꿀단지의 올림 신청 / When 꿀단지가 신청을 거둠 / Then 거둠, 채널 점유가 풀리고 새로 신청할 수 있다.
- S5 (INV-V5): Given 6일 23시간 전 발급된 코드 받음 신청 / When 「코드 올렸어요」 / Then 올림.
- S5b (INV-V5, 실패경로): Given 7일 1분 전 발급되고 올리지 않은 신청 / When 「코드 올렸어요」 / Then 거부, 크리에이터·운영자 화면에 「기간 지남」.
- S5c (INV-V5): Given 발급 6일 뒤 올림이 된 신청 / When 그로부터 30일 뒤 운영자가 승인 / Then 승인된다(운영자 확인에는 기한 없음).
- S5d (INV-V5): Given 기간이 지난 꿀단지의 신청 / When 꿀단지가 새로 신청 / Then 옛 신청은 기간 지남으로 닫히고 새 신청이 생긴다.

## 신뢰 경계

- 믿는 값: 로그인 토큰이 확인한 사람(INV-L2)과 그 계정의 역할 칸, DB 의 운영자 판정, 서버가 만든 인증 코드와 채널 키,
  서버 시각, 신청 표의 상태·발급 시각·올린 시각, 채널 점유 표, 횟수 풀기 기록, 서버가 플랫폼에서 직접 받은 「이 로그인의 채널」 답(INV-V14)
- 믿지 않는 값: 브라우저가 보내는 채널 주소 문자열(형식 검사 뒤 서버가 다시 만든 주소만 저장), 계정·크리에이터 식별값·코드·확인 방법(무시하거나 거부한다),
  화면이 들고 있는 신청 상태와 기한·남은 횟수 표시, 크리에이터의 「코드 올렸어요」 누름(올렸다는 사실의 증거가 아니라 운영자 확인을 부르는 신호일 뿐이다),
  브라우저가 넘겨주는 플랫폼 채널 식별값(로그인 확인에서도 서버가 플랫폼에 직접 물어 얻은 값만 쓴다)
- 사람이 판정하는 값: 인증 코드 방식에서 「채널에 코드가 올라와 있다」는 기계가 확인하지 않는다. 운영자가 저장된 주소를 열어 본다. 이 스펙이 지키는 것은
  운영자가 **맞는 주소에서 맞는 코드를** 보게 하는 것(INV-V2·V3)과 결정이 한 번만 반영되는 것(INV-V6)까지다.

## 비범위

- **플랫폼 계정 로그인 연결 자체** — 외부 연결이라 `external-connections.md` 때 붙인다. 이 스펙은 그 결과를 받는 DB 함수의 규칙(INV-V13·V14)만 정한다.
  지금 알고 있는 가능 여부(붙일 때 각 플랫폼 문서로 다시 확인한다):
  유튜브 — 채널 목록 API 를 `mine=true` 로 불러 로그인한 사람의 채널을 얻을 수 있다 / 치지직 — 공개 API 의 `/open/v1/users/me` 로 로그인한
  사람의 채널을 얻을 수 있다 / 인스타그램 — 프로페셔널 계정만 가능 / SOOP — 파트너 제휴가 있어야 한다 / 알플레이 — 공개 API 가 없다
- **다음에 정할 것 — API 가 없는 플랫폼에서 진짜 주인을 확인하는 방법.** 사용자 「api가 없는건 진짜 주인인지 확인 할 수 있는 방법을 모색하자.
  일단 1대1 문의로 받는건 맞아」. 지금은 인증 코드 + 3번 제한 + 1:1 문의로 받는다. 이 플랫폼(SOOP·알플레이, 비프로페셔널 인스타그램)에서는
