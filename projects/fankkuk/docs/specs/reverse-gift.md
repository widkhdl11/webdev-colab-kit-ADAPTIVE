# 역조공 스펙

역조공은 크리에이터가 자기 팬에게 선물을 보내는 기능이다. 방향이 거꾸로라 이번에는 **팬 주소**를 맡는다.
크리에이터는 사무실로 상자를 보내고, 팬은 「받기」를 누를 때 주소를 입력한다. 사무실은 검수 뒤 그 주소로
송장을 출력해 보낸다. 어기면 생기는 사고는 셋이다 — 크리에이터(또는 아무나)에게 팬 주소가 보이거나,
팔로우하지도 않은 사람에게 모르는 선물이 가거나, 팬 한 명이 안 받았을 때 결제 전체가 꼬인다.
크리에이터 주소 보호(`address-protection.md`)와 같은 보관 키·복호화 함수를 쓰고, 다른 점만 여기 적는다.

용어
- **보내기**: 크리에이터가 한 번에 하는 역조공. 결제 하나다.
- **몫**: 보내기 안에서 팬 한 명에게 가는 부분. 상자 하나와 주문번호 하나가 붙는다.

## 불변식

- INV-R1: 몫의 받는 사람은 **보내기를 등록하는 순간** 보내는 크리에이터를 팔로우하고 있는 팬 계정이다.
  크리에이터 계정·자기 자신·팔로우하지 않은 팬은 받는 사람이 될 수 없다. 등록 뒤에 팔로우를 끊어도 이미 만든 몫은
  그대로 가고, 팬은 「받지 않기」로 거절할 수 있다(INV-R10). 판정은 서버가 팔로우 표를 직접 읽어서 한다.
  (강제 위치: 서버 — 보내기 등록 / DB 등록 함수)
  위반 시: 팔로우하지 않은 사람에게 모르는 사람의 선물 소식이 간다 — 아이디만 알면 누구에게나 연락할 수 있게 된다.

- INV-R2: 받는 팬은 아이디를 **정확히** 입력해서만 찾는다. 부분 일치 검색이나 팔로워 목록은 보여 주지 않는다.
  없는 아이디, 팔로우하지 않은 아이디, 크리에이터 아이디에는 모두 **같은 응답**("보낼 수 없는 아이디예요")을 준다.
  (강제 위치: 서버 — 받는 팬 찾기)
  위반 시: 응답이 다르면 아무 아이디나 넣어 보며 가입 여부와 팔로우 관계를 알아낼 수 있다.

- INV-R3: 보내기 하나는 결제 하나이고, 몫은 1개 이상 10개 이하다. 몫마다 받는 팬 한 명·상자 하나·주문번호 하나가
  붙는다. 한 보내기 안에 같은 팬이 두 번 들어갈 수 없다. 결제 금액은 서버가 몫마다 고른 상자 구간 요금을 더해
  계산한다. 역조공 상자 요금은 팬 선물 요금에서 검수비를 뺀 금액이다 — 소형 5,400원(6,900 − 1,500) · 중형 6,900원(8,900 − 2,000).
  결제 기록에는 검수비 칸이 0 으로 남는다(`payment.md` INV-M7). 역조공 상자의 검수는 추적 장치 검사 없이 겉면·크기·무게와
  보낼 수 없는 물품(음식·위험물 등)만 확인한다 — 크리에이터가 팬에게 추적 장치를 달 이유가 적기 때문이다.
  (강제 위치: 서버 — 등록 검증 / DB 제약 — 보내기·팬 유일)
  위반 시: 한 몫의 상태(받음·안 받음·반송)가 다른 팬의 몫과 섞여, 한 명이 안 받았는데 모두 반송되거나 환불 금액이 틀린다.

- INV-R4: 몫의 주소는 **그 몫의 받는 팬 본인**이 「받기」를 할 때만 들어간다. 서버는 로그인으로 얻은 사람 ID
  (`session-login.md` INV-L2)가 몫의 받는 팬 ID 와 같은지 확인한다. 이미 받은 몫, 받지 않은 몫, 기한이 지난 몫,
  반송·취소된 몫에는 주소를 넣을 수 없다. 같은 몫에 「받기」 요청이 동시에 두 번 와도 주소는 하나만 저장된다.
  보내는 크리에이터와 관리자 화면에는 주소를 넣는 경로가 없다.
  (강제 위치: DB 함수 — 사람 확인·상태 확인·저장이 한 번에 일어나는 자리)
  위반 시: 다른 사람이 팬 대신 자기 주소를 넣어 선물을 가로채거나, 크리에이터가 엉뚱한 주소를 넣어 팬 행세를 한다.

- INV-R5: 팬 주소 평문은 팬 브라우저에서 암호화된 뒤에만 서버로 간다(`address-protection.md` INV-P1 과 같은 방식·같은
  보관 키). 받는 사람 이름과 전화번호도 주소와 같이 묶어 암호화한다(택배 라벨에 필요한 값이라 따로 두면 평문이 남는다). 암호화하는 내용에는 이 값들과 함께 **그 몫의 주문번호**가 들어간다. 서버는 암호문 형식이 아닌 입력을 거부한다.
  (강제 위치: 클라이언트 — 전송 전 암호화 / 서버 — 입력 형식 검증 / 복호화 함수 — INV-R7 (b))
  위반 시: 평문이 서버를 지나 로그·오류 보고에 남는다. 주문번호가 함께 묶여 있지 않으면 서버를 장악한 사람이 한 몫의
  암호문을 다른 몫에 옮겨 붙여, 팬 A 의 주소로 엉뚱한 상자를 보낼 수 있다.

- INV-R6: 팬 주소는 몫 하나에만 묶인다. 「내 정보」나 다른 몫에 저장되거나 다시 쓰이지 않고, 다음 역조공에서는
  처음부터 다시 입력한다. (강제 위치: 서버 — 몫 주소 저장 경로 외에 팬 주소를 저장하는 자리가 없다)
  위반 시: 팬 주소가 쌓인다 — 안 쌓아 두기로 한 결정(미리 저장 안 함)이 무너진다.

- INV-R7: 복호화 함수는 다음이 모두 참일 때만 몫의 주소를 연다. 하나라도 거짓이면 거부하고 거부 로그를 남긴다.
  (a) 그 몫에 팬이 넣은 주소 암호문이 있다(= 팬이 받기를 했다)
  (b) 암호문을 풀어 나온 주문번호가 요청한 몫의 주문번호와 같다 (INV-R5)
  (c) 몫이 검수 완료 상태이고 아직 출고 확정 전이며, 받지 않음·기한 지남·반송·취소가 아니다
  (d) 요청자가 대표 계정이다 (`address-protection.md` INV-P8 과 같은 판정)
  한 몫의 복호화는 최대 3회, 출고가 확정되면 더 열리지 않는다. 동시에 두 요청이 와도 상한을 넘지 않는다
  (INV-P5 와 같은 규칙). 응답에는 라벨 이미지와 운송장 번호만 있고 주소 문자열은 없다(INV-P6).
  (강제 위치: 복호화 함수 진입부, 복호화보다 먼저 / 횟수 확인과 증가가 한 번에 일어나는 자리)
  위반 시: 받지 않은 팬, 다른 몫의 주소가 열리거나 같은 주소를 몇 번이고 다시 꺼낼 수 있다.

- INV-R8: 보내는 크리에이터는 받는 팬의 주소·실명·휴대폰 번호를 어떤 경로로도 받지 못한다. 크리에이터에게 보이는 것은
  팬의 아이디·닉네임과 몫의 상태 셋 — 「받기 기다리는 중」「받았어요」「받지 않았어요」 — 뿐이다. 「받지 않았어요」는
  팬이 거절한 것과 기한이 지난 것을 구분하지 않는다. 팬에게 운송장 번호를 보여 주지 않는 기존 규칙과 같은 이유로
  크리에이터에게도 몫의 운송장 번호를 보여 주지 않는다.
  (강제 위치: 서버 — 크리에이터용 몫 읽기 함수의 반환 칸 / DB — 주소 암호문은 `pii` 구역, INV-P9)
  위반 시: 역조공이 크리에이터에게 팬 주소를 알아내는 통로가 된다. 운송장 번호로 택배사 조회를 하면 받는 곳 일부가 보인다.
  거절과 기한 지남을 구분해 보여 주면 팬이 거절한 사실이 크리에이터에게 드러난다.

- INV-R9: 몫의 주소 암호문은 다음 중 하나가 되는 순간 지워진다 — 출고 확정, 받지 않음, 반송, 취소. 지워진 뒤에는
  복호화가 거부된다(INV-R7 (a)). 지운 사실은 열람 기록처럼 남지만 주소 값은 남지 않는다.
  (강제 위치: DB — 상태를 바꾸는 함수가 같은 처리 안에서 암호문을 지운다)
  위반 시: 배송이 끝난 팬 주소가 계속 쌓여, 나중에 키가 털렸을 때 소급해서 열린다.

- INV-R10: 팬은 받기 전에 「받지 않기」를 할 수 있다. 결제 완료 시각부터 168시간(7일) 안에 받기도 받지 않기도 하지
  않으면 그 몫은 「받지 않음」이 된다. 받지 않음이 된 몫은 상자를 보낸 크리에이터에게 돌려보내고, 그 몫만 환불한다.
  기한 처리와 「받기」가 동시에 와도 둘 중 하나만 반영된다. 한 팬이 받지 않아도 다른 몫은 그대로 진행된다.
  (강제 위치: DB 함수 — 상태 확인과 변경이 한 번에 일어나는 자리 / 기한 판정은 서버 시각 기준)
  위반 시: 기한 처리 직후에 주소가 들어가 반송될 상자의 주소가 열리거나, 한 팬 때문에 보내기 전체가 멈춘다.

- INV-R11: 환불은 몫마다 따로 계산한다. 몫 하나의 환불은 그 몫 상자 요금을 넘지 않고, 금액은 `payment.md` INV-M8 의
  표를 몫에 적용해 서버가 정한다 — 입고 뒤 받지 않음·기한 지남 = 반송 택배비를 뺀 금액. 입고 전이면 크리에이터가 이미 상자를 보냈을 수 있어
  (결제 직후 받는 주소가 보인다) 그 몫의 6자리를 살려 두고 환불을 미룬다: 살려 둔 때부터 168시간 안에 오면 그 몫 상자로 입고돼 선불 반송, 환불은
  반송 택배비를 뺀 금액 / 안 오면 자동 처리가 6자리를 무효로 하고 그 몫 전액(2026-10-10, 팬 선물 payment INV-M18 과 같은 뜻 — 다만 몫마다 환불이
  하나라 먼저 일부를 돌려주지 않는다).
  한 보내기의 환불 합계는 결제 금액을 넘지 않고, 같은 몫의 환불이 두 번·동시에 와도 한 번만 나간다(INV-M9 와 같은 규칙).
  (강제 위치: 서버 — 환불 금액 계산 / DB — 몫별 환불 기록 유일)
  위반 시: 한 팬이 받지 않았는데 결제 전체가 환불되거나, 같은 몫이 두 번 환불된다.

- INV-R12: 팬 주소(평문·암호문)는 알림 본문·애플리케이션 로그·내부 QR·크리에이터 화면 어디에도 들어가지 않는다.
  팬에게 가는 알림에는 보낸 크리에이터 이름과 「받기」로 가는 링크만 있다. QR 에는 몫 주문번호만 들어간다.
  (강제 위치: 각 생성 함수 / 검사: 생성물에 주소 칸이 없다)
  위반 시: 암호화를 우회하는 평문 사본이 생긴다.

- INV-R13: 몫의 주소를 연 뒤 송장이 나오기 전에 출력이 실패하면(봉투 열기 실패·봉인 속 주문번호 대조 전 오류·송장 마무리 실패) 출력 함수는 그 「연 줄」을 돌려준다 —
  「돌려줌」 줄을 따로 남기고 원래 줄은 그대로 둔다. 몫의 횟수(INV-R7 의 3회) = 그 몫의 「연 줄」 수 − 그 가운데 돌려준 줄 수다. 조건은 모두 DB 가 몫을 잠근 자리에서 본다.
  (a) 돌려주기 함수로만 한다 — 복호화 전용 역할이 기록 표에 직접 넣을 수 있는 줄은 거부 줄뿐이다.
  (b) 「연 줄」 하나는 한 번만 돌려준다.
  (c) 그 몫의 가장 최근 「연 줄」이고, 그 줄을 연 요청자가 돌려받을 때만이다.
  (d) 몫이 아직 송장 출력 단계 전(검수 완료)일 때만이다 — 재출력의 실패는 돌려주지 않는다.
  (e) 한 몫에서 돌려줄 수 있는 것은 2번까지다.
  암호문 속 주문번호가 몫과 달라 거부된 경우(INV-R7 (b))는 실패가 아니라 거부라 돌려주지 않는다.
  역조공 송장 출력(몫 주소 읽기·몫별 횟수 칸·거부 기록)과 함께 만든다.
  (강제 위치: DB 돌려주기 함수 — 복호화 전용 역할만, 몫 잠금 뒤 (b)~(e) / DB 권한 — 기록 표 직접 넣기는 거부 줄만 / DB 제약 — 돌려줌 줄의 연 줄 유일)
  위반 시: 「열고 → 일부러 실패 → 돌려받기」를 되풀이해 팬 주소를 끝없이 연다. 반대로 돌려주지 않으면 일시 장애 세 번에 그 몫의 출고가 막힌다.

- INV-R14: 사무실 주소(2026-10-07부터 상자별 받는 주소 — 6자리 포함, inbound-address-code INV-C2·C3 를 역조공 상자에도 쓴다)는 결제가 끝난 보내기를 **보낸 크리에이터 본인**에게만 보여 준다. 팬의 「받기」는 기다리지 않는다 — 크리에이터는 결제 직후 상자를 보내고,
  받기는 출고 전에만 있으면 된다(INV-R7). 몫이 모두 받지 않음·반송·취소가 된 보내기에는 보여 주지 않는다. 주소 값은 팬 선물 안내와 같은 한 곳에서 읽는다.
  (강제 위치: 서버 — 보낸 역조공 읽기의 주소 안내 / DB — 보낸 역조공 읽기는 로그인한 보낸 사람 것만)
  위반 시: 결제하지 않은 보내기의 상자가 사무실로 와 미확인 입고가 생기거나, 모든 팬이 받지 않은 보내기의 상자가 계속 들어온다. 다른 크리에이터의 보내기에 주소 안내가 붙는다.

- INV-R15: 결제 대기로 만든 지 24시간이 지난 보내기는 자동 처리가 「실패」로 닫는다. 닫는 대상은 결제 대기뿐이다 — 「승인 중」(결제사 승인을 부른 뒤 결과를 기다리는 것)과
  결제 완료는 건드리지 않는다. 닫기는 「결제 대기인 줄만 실패로 바꾸기」 한 문장으로 하고, 같은 줄의 결제 확정 시작(결제 대기 → 승인 중)과 겹치면 둘 중 하나만 반영된다.
  닫힌 뒤 결제창에서 성공 주소로 돌아와도 결제사 승인을 부르지 않는다 — 승인을 부르지 않은 결제는 돈이 나가지 않는다. 닫힌 보내기는 지우지 않고 「실패」로 남긴다 —
  관리자 결제 목록과 맞출 수 있어야 한다. 닫힌 보내기의 몫은 팬·크리에이터 어느 화면에도 나오지 않는다. 같은 처리를 두 번 돌려도 결과는 같다.
  관리자 화면 「지금 돌리기」로도 부를 수 있다(office-workflow INV-W6 과 같은 자리). 정해진 시각에 부르는 장치가 생기기 전에는 「지금 돌리기」로만 닫힌다.
  팬 선물의 결제 대기도 같은 규칙이다(payment INV-M15).
  (강제 위치: DB 자동 처리 함수 — 조건부 갱신 한 문장 / DB 결제 확정 시작 함수 — 결제 대기일 때만 승인 중으로)
  위반 시: 「승인 중」을 닫으면 돈은 나갔는데 보내기가 사라진다. 닫힌 뒤에도 승인을 부르면 사라진 보내기에 돈이 나간다. 대기가 끝없이 쌓여 관리자 결제 목록을 가린다.

- INV-R16: 팬은 자기 몫 주소의 열람 기록을 본다 — 받은 역조공 상세에서 그 몫의 주소를 연 줄·거부된 줄(시각·몇 번째 출력·거부 사유)과 주소를 지운 줄(시각·까닭: 출고·반송·취소)을 전부.
  요청자는 계정·아이디·닉네임 없이 「대표」인지 아닌지만 보인다(크리에이터 열람 기록 INV-P7 과 같다). 주소 값·운송장 번호는 없다(INV-R7·R8).
  읽기 함수는 사람 ID 를 받지 않고 로그인 토큰의 계정이 받는 팬인 몫의 기록만 돌려준다 — 남의 몫·없는 몫은 빈 목록. 보낸 크리에이터·직원은 이 함수로 팬 몫의 기록을 읽지 못한다.
  (강제 위치: DB 읽기 함수 — 인자 없이 auth.uid() 로 몫의 팬 판정, 반환 칸)
  위반 시: 팬이 자기 주소가 언제 열렸는지 모른다 — 「열람 기록 전부 공개」가 크리에이터에게만 참이 된다. 다른 팬 몫의 기록이 보이면 그 팬이 역조공을 받았다는 사실이 새어 나간다.

## 시나리오

- S1 (INV-R1): Given 하루를 팔로우한 팬 별빛 / When 하루가 별빛에게 보내기 등록 / Then 몫 하나가 만들어진다.

- S3d (INV-R3, 실패경로): Given 브라우저가 금액을 1원으로 바꿔 보냄 / When 등록 / Then 금액은 서버 계산값이다.

- S5b (INV-R5, 실패경로): Given 누군가 평문 주소를 API 로 직접 보냄 / When 받기 / Then 형식 오류로 거부.

- S7d (INV-R7 c, 실패경로): Given 받지 않음이 된 몫 / When 출력 / Then 거부.
- S7e (INV-R7 d, 실패경로): Given 직원 계정 / When 출력 / Then 거부.
- S7f (INV-R7, 동시): Given 복호화가 상한 직전인 몫 / When 출력 요청 두 개가 동시에 / Then 복호화는 하나만.

- S8c (INV-R8, 실패경로): Given 크리에이터 로그인 토큰 / When 몫·주소 관련 모든 읽기 API 를 부름 / Then 응답에 주소·실명·전화번호 형태의 값이 없다.

- S9b (INV-R9): Given 받기를 한 뒤 반송·취소가 된 몫 / When 상태 변경 / Then 같은 처리 안에서 암호문이 지워진다.

- S15c (INV-R15, 동시): Given 기한 직전 결제 대기 / When 결제 확정 시작과 자동 처리가 동시에 / Then 하나만 반영.

- S16 (INV-R16): Given 별빛이 받기를 한 몫, 대표가 한 번 열고 직원 시도가 한 번 거부된 뒤 출고 확정 / When 별빛이 그 몫 상세를 봄 / Then 세 줄 — 연 줄(1번째, 대표) · 거부 줄(대표 아님) · 지운 줄(출고) — 이 시각 역순으로, 주소·운송장 번호 없이.
- S16b (INV-R16, 실패경로): Given 별빛의 몫 기록 / When 다른 팬·보낸 크리에이터·직원·익명이 읽음 / Then 0줄(익명은 거부). 별빛이 남의 몫 번호를 넣어도 0줄.

## 신뢰 경계

- 믿는 값: 서버가 로그인으로 얻은 사람 ID(INV-L2), DB 의 팔로우 표, 서버 시각, 복호화 함수가 스스로 풀어 본 주문번호와
  스스로 검증한 로그인 토큰, 복호화 함수 자신의 설정(대표 ID)
- 믿지 않는 값: 브라우저가 보내는 받는 팬 ID·금액·몫 개수·주소 형식, 앱 서버가 넘기는 몫 번호(복호화 함수가 암호문 속
  주문번호와 대조한다), DB 의 역할 칸
- 몫 상태(검수 완료·받지 않음 등)는 앱 서버가 쓰는 DB 값이라 앱 서버를 장악하면 위조할 수 있다. 그래도 (a)·(b)가
  따로 막으므로 위조로 얻는 것은 "팬이 받기를 한 몫을 검수 전에 여는 것"뿐이고, 그것도 열람 기록에 남는다.

## 비범위

- 팬 기기 해킹·피싱으로 받기를 빼앗기는 경우 — 로그인 보호는 `session-login.md` 의 관할
- 받기 때 카카오 서명 — 팬은 로그인 세션만으로 받는다. 서명은 크리에이터 주소에만 받는다(2026-10-09 카드 d56, 사용자 「팬까지 카카오 서명을 하게 되면 괜히 번거로울 것 같다」)
- 크리에이터가 사무실로 보내는 상자의 검수 기준 — 팬 선물과 같은 검수를 쓴다
- 7일 규칙 일반(크리에이터 승인 기한·미확인 입고) — 따로 쓸 시간 규칙 스펙. 여기서는 몫의 받기 기한만 다룬다
- 클라우드 KMS 연결 — `address-protection.md` 의 개발용 키 쌍 규칙(INV-P12)을 그대로 따른다
