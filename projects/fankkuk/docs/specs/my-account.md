# 내 정보 스펙

내 정보 화면은 팬이 자기 아이디·닉네임·이메일·휴대폰 번호·알림 설정을 보고, 닉네임·이메일·알림을 고치는 곳이다.
이메일과 휴대폰 번호는 연락처라 개인정보 구역(`pii`, 화면 쪽 API 로 열리지 않는 곳)에만 둔다(address-protection INV-P9).
화면이 그 값을 보려면 DB 함수 하나를 거쳐야 하고, **그 함수가 사람을 잘못 고르면 남의 번호가 그대로 보인다.**
그래서 읽기·고치기 모두 로그인 토큰이 확인한 사람 것만 다루고, 휴대폰 번호는 본인에게도 가운데를 가린 모양으로만 내보낸다.

용어
- **연락처 칸**: 이메일, 휴대폰 번호. 개인정보 구역의 계정 연락처 표에 계정당 한 줄.
- **확인된 이메일**: 확인 메일의 링크를 눌러 소유가 확인된 주소. 배송 소식은 이 주소로만 간다.
- **확인 대기 이메일**: 새로 입력했지만 아직 링크를 누르지 않은 주소. 확인되기 전까지 아무 메일도 받지 않는다(확인 메일 자신만 예외).
- **로그인 주소**: 로그인용으로 지어낸 `아이디@fankkuk.test`. 연락처 이메일과 별개이고, 연락처 이메일을 바꿔도 로그인은 그대로다.

## 불변식

- INV-A1: 이메일·휴대폰 번호는 개인정보 구역의 표에만 있다. public 표에는 연락처 칸이 없고, 화면 쪽 키(익명·로그인 사용자)로
  그 표를 직접 읽거나 쓸 수 없다. (강제 위치: DB — 개인정보 구역 권한 회수, 노출 스키마 목록에서 제외)
  위반 시: 표 하나가 실수로 열리면 전원의 연락처가 한 번에 나간다.

- INV-A2: 내 정보 읽기는 휴대폰 번호를 가운데 넷을 가린 모양(`010-****-5678`)으로만 돌려준다. 전체 번호는 어떤 읽기 함수의
  응답에도 없다. 번호가 없으면 빈 값이다. (강제 위치: DB 함수 — 가리기는 DB 안에서 한다)
  위반 시: 화면 응답·브라우저 캐시·오류 보고에 전체 번호가 남는다. 세션을 빼앗기면 번호까지 나간다.

- INV-A3: 내 정보 읽기·고치기 함수는 사람 ID 를 인자로 받지 않는다. 로그인 토큰이 확인한 사람(INV-L2)의 줄만 읽고 고친다.
  로그인하지 않았으면 거부한다. (강제 위치: DB 함수 — 인자 목록과 진입부 검사)
  위반 시: 본문에 다른 사람 ID 를 넣어 남의 이메일을 바꾸고, 비밀번호 재설정 같은 연락을 가로챈다.

  INV-A3·A5 를 지킨다 — 계정 ID 를 인자로 받지 않고 로그인 토큰의 크리에이터 계정만 고치며, 빈 값이면 아무 칸도 바꾸지 않고, 이메일·휴대폰은 건드리지 않는다.

  notifications INV-N6 의 종류별 표)은 두 칸이 모두 꺼져도 가므로 그것을 끄는 스위치는 없고, 팬·크리에이터 설정 화면 모두 「끌 수 없는 알림」 안내로 목록을 보여 준다. 알림 스펙에 없는 알림 종류의 스위치는 두지 않는다 — 설정 화면의 「자동 반려 하루 전」
  「주소가 열릴 때」 스위치는 카카오·이메일 두 스위치로 바꾸고, 그 두 알림을 둘지는 알림 구현 때 정한다.
  (강제 위치: DB 고치기 함수 — 알림 칸은 둘뿐 / 서버 보내는 일꾼 — INV-N6)
  위반 시: 화면 스위치를 꺼도 아무 일도 일어나지 않거나(저장할 칸이 없는 스위치), 승인 요청을 끌 수 있어 크리에이터가 요청을 모른 채 7일 자동 반려가 난다.

- INV-A12: 팬 프로필은 사진·배경 사진·자기소개 세 칸이고, 그 팬 본인만 바꾼다. 바꾸는 함수는 계정 ID 를 인자로 받지 않고 로그인 토큰이 확인한 계정 한 줄만 고친다.
  로그인하지 않았거나 팬 역할이 아니면 거부한다(크리에이터의 공개 정보는 INV-A9·creator-link INV-E1 경로다). 자기소개는 앞뒤 공백을 뺀 0~100자 한 줄이고
  태그·팬덤 이름과 같은 금칙어·연락처 필터(creator-tags INV-T7)를 거친다. 앱 서버가 먼저 검사하고 DB 함수가 다시 검사하며, 하나라도 틀리면 아무 칸도 바꾸지 않는다.
  같은 사이트의 JSON 요청만 받고 응답은 캐시되지 않는다(INV-A6). 프로필 수정 화면의 닉네임은 이 함수가 아니라 지금의 내 정보 고치기 경로(INV-A4·A5)로 바뀌고,
  계정마다 다른 닉네임·미리 확인 규칙(signup INV-U13·U14)을 그대로 따른다 — 닉네임 규칙을 새로 만들지 않는다.
  (강제 위치: DB 함수 — 인자 목록, 진입부 역할 확인, 고치는 칸이 정해져 있음 / 서버 입력 경계 / DB 제약 — 소개 길이)
  위반 시: 본문의 계정 ID 를 바꿔 남의 프로필을 고친다. 누구나 보는 소개에 연락처를 적어 크리에이터·다른 팬에게 사적으로 연락하는 길이 열린다. 닉네임 규칙이 두 군데서 따로 놀아 같은 닉네임 둘이 생긴다.

- INV-A13: 팬 프로필(사진·배경 사진·자기소개)은 공개 값이다 — 로그인하지 않은 사람·다른 팬·크리에이터·운영자(직원·대표) 누구나 본다(카드 d91).
  팬 전용 공개 페이지는 없고, 팬 닉네임이 보이는 자리에 같이 나온다. 프로필을 돌려주는 읽기는 닉네임·사진 주소·배경 사진 주소·자기소개 넷만 준다 —
  로그인 아이디·실명·이메일·휴대폰·주소·주문·팔로우 목록·차단 여부 같은 다른 칸을 같은 응답에 섞지 않는다. 크리에이터 역할 계정에는 팬 프로필이 없다.
  (강제 위치: DB 읽기 함수 — 돌려주는 칸이 정해져 있음 / 시험 — 로그인 안 함으로 읽은 응답에 그 네 칸 말고는 없는지)
  위반 시: 누구나 여는 읽기 하나로 팬의 로그인 아이디(비밀번호 대입의 절반)나 연락처·주문이 퍼진다.

- INV-A14: 팬 프로필 사진·배경 사진은 공개 저장소에 두되(공개 값이라 누구나 여는 주소로 보여 준다 — 업계 표준), 쓰기는 서버만 한다 — 화면에서 저장소로 바로 올리는 길이 없고,
  저장소에 화면 쪽 키(익명·로그인 사용자)의 쓰기·고치기·지우기 정책을 두지 않는다. 파일 자리는 서버가 로그인 토큰의 계정으로 정해서 본인 파일만 바뀐다.
  서버가 받아 실제 이미지인지 열어 보고(지금 사이트 공통 한도 — JPG·PNG·WebP, 10MB, 4천만 화소), 위치를 포함한 사진 정보(EXIF 등)를 모두 지우고
  정해진 크기로 다시 그려 WebP 로만 저장한다. 원본은 저장하지 않는다. 사진을 바꾸면 새 판 값의 파일 이름으로 저장하고 옛 파일을 지운다. 지우면 파일도 지운다.
  (강제 위치: 저장소 — 화면 쪽 쓰기 정책 없음, 서버의 비밀 키로만 씀 / 서버 — 사진 저장 경로 하나 / 시험 — 위치 정보가 든 사진을 올리고 저장된 파일에 사진 정보가 없는지)
  위반 시: 남이 저장소에 바로 올려 남의 프로필 사진을 바꾼다. 누구나 보는 사진에 팬 집 위치가 남는다. 바꾼 뒤에도 옛 사진이 주소로 계속 열린다.

## 시나리오

- S1 (INV-A1, 실패경로): Given 별빛으로 로그인 / When 개인정보 구역의 연락처 표를 직접 조회·수정 / Then 거부.
- S1b (INV-A1, 실패경로): Given 로그인 안 함 / When 같은 시도 / Then 거부.
- S2 (INV-A2): Given 별빛의 번호 01012345678 / When 내 정보 읽기 / Then `010-****-5678`, 응답 어디에도 `1234` 가 없다.
- S2b (INV-A2): Given 번호가 없는 계정 / When 내 정보 읽기 / Then 번호 칸은 빈 값.
- S3 (INV-A3): Given 별빛·달토끼 / When 각자 내 정보 읽기 / Then 각자 자기 이메일만 받는다.
- S3b (INV-A3, 실패경로): Given 별빛으로 로그인 / When 고치기 본문에 달토끼 ID 를 넣음 / Then 달토끼 정보는 그대로, 바뀐 것은 별빛 것뿐(또는 함수를 못 찾아 거부).
- S3c (INV-A3, 실패경로): Given 로그인 안 함 / When 읽기·고치기 / Then 거부.
- S4 (INV-A4, 실패경로): Given 별빛으로 로그인 / When 고치기 본문에 아이디·역할·휴대폰 번호를 넣음 / Then 셋 다 그대로.
- S5 (INV-A5, 실패경로): Given 닉네임 13자, 또는 이메일 `abc`, 또는 공백뿐인 닉네임 / When 저장 / Then 400, 아무 칸도 바뀌지 않음.
- S5b (INV-A5, 실패경로): Given 앱 서버를 거치지 않고 DB 함수를 직접 불러 닉네임 13자 / Then 거부, 변화 없음.
- S7 (INV-A7): Given 별빛의 확인된 이메일 A / When B 로 바꿔 저장 / Then 확인된 이메일은 A 그대로, 확인 대기 B, B 로 확인 메일 한 통.
- S7b (INV-A7): Given 확인 대기 B / When 메일의 링크를 엶 / Then 확인된 이메일이 B, 확인 대기 없음.
- S7c (INV-A7, 실패경로): Given 이미 쓴 링크, 24시간 지난 링크, 새 요청으로 무효가 된 링크, 다른 계정의 링크 / When 링크를 엶 / Then 거부, 변화 없음.
- S7d (INV-A7, 실패경로): Given 확인 대기 B / When 배송 소식 메일을 보낼 주소를 고름 / Then A(확인된 이메일).
- S7e (INV-A7): Given 링크 확인 기록 / When DB 를 직접 봄 / Then 링크 값 원문은 어디에도 없다.
- S8 (INV-A8, 실패경로): Given 한 시간에 다섯 통을 보냄 / When 여섯 번째 저장 / Then 429, 메일 안 보냄, 확인 대기도 안 바뀜.
- S8b (INV-A8): Given 확인 메일 / When 본문을 봄 / Then 휴대폰 번호·주소·선물 내용이 없다.
- S6 (INV-A6, 실패경로): Given 다른 사이트에서 온 요청 또는 JSON 이 아닌 본문 / When 저장 / Then 403, 변화 없음.
- S6b (INV-A6): Given 내 정보 저장 성공 / When 응답 헤더 / Then `Cache-Control: no-store`.
- S9 (INV-A9): Given 하루로 로그인 / When 공개 이름 「하루달」로 저장 / Then 하루의 공개 이름만 바뀌고 변경 기록 한 줄(언제·전·후).
- S9b (INV-A9, 실패경로): Given 하루로 로그인 / When 본문에 모모의 크리에이터 ID·채널 주소·본인 확인 참을 넣음 / Then 모모 그대로, 하루의 채널·확인 여부 그대로. 공개 이름 21자 → 400, 아무 칸도 안 바뀜. 팬 계정으로 부름 → 거부.
- S10 (INV-A10): 확인 전+켜짐 → 안 나옴 / 확인됨+꺼짐 → 안 나옴 / 확인됨+켜짐 → 나옴 / 켜짐인 채 승인 취소 → 안 나옴.
- S10b (INV-A10): Given 확인됨+꺼짐 / When 손님·팔로우 안 한 팬이 목록을 읽음 / Then 안 나옴. 팔로우한 팬·본인 / Then 나옴.
  When 누구든 한 명 읽기(그 크리에이터 ID) / Then 나옴. 확인 전이면 한 명 읽기도 빈 결과.
- S11 (INV-A11): Given 하루가 카카오·이메일 둘 다 끔 / When 입고 알림·승인 요청 알림이 생김 / Then 입고는 건너뜀, 승인 요청은 감.
- S12 (INV-A12): Given 별빛(팬)으로 로그인 / When 소개 「밤마다 방송 챙겨 보는 사람」 저장 / Then 별빛의 소개만 바뀐다. 닉네임 「별사탕」은 내 정보 고치기로 바뀌고 같은 닉네임이 이미 있으면 「이미 쓰는 닉네임」.
- S12b (INV-A12, 실패경로): Given 별빛으로 로그인 / When 본문에 달토끼의 계정 ID, 소개 101자, 소개에 전화번호 / Then 달토끼 그대로, 별빛도 아무 칸도 안 바뀜(400). 크리에이터 계정·로그인 안 함으로 부름 → 거부. DB 함수를 직접 불러 101자 → 거부.
- S13 (INV-A13): Given 별빛의 사진·소개 / When 로그인 안 함·달토끼(팬)·하루(크리에이터)·직원이 별빛 프로필 읽기 / Then 모두 닉네임·사진 주소·배경 사진 주소·소개가 나온다.
- S13b (INV-A13, 실패경로): Given 별빛의 휴대폰·이메일·주문·팔로우가 있음 / When 로그인 안 함으로 별빛 프로필 읽기 / Then 응답에 네 칸 말고는 없고, 로그인 아이디·휴대폰·이메일·주문번호가 어디에도 없다. 하루(크리에이터) 프로필 읽기 → 빈 결과.
- S14 (INV-A14): Given 위치 정보가 든 JPG / When 별빛이 프로필 사진으로 올림 / Then 저장된 파일은 WebP 이고 사진 정보가 없다. 사진을 바꾸면 주소의 판 값이 바뀌고 옛 파일이 저장소에 없다.
- S14b (INV-A14, 실패경로): Given 별빛·달토끼로 로그인 / When 화면 쪽 키로 저장소에 바로 파일을 올리거나 별빛의 파일을 덮어씀·지움 / Then 거부. 11MB 파일·이미지가 아닌 파일 → 400, 저장 없음.

## 신뢰 경계

- 믿는 값: Supabase Auth 가 검증한 사용자 ID, 개인정보 구역에 저장된 연락처
- 믿지 않는 값: 요청 본문의 모든 칸(사람 ID·아이디·역할·번호 포함), 화면이 보낸 닉네임·이메일 — 형식 검사 전까지
- 팬 프로필(INV-A12~A14): 믿는 값은 서버가 다시 그린 사진 파일. 믿지 않는 값은 화면이 보낸 소개 글, 올린 파일의 형식 표시·확장자·사진 정보

## 비범위

- 가입·카카오 본인 확인·실명 — signup 스펙. 휴대폰 번호 바꾸기 — signup INV-U12(카카오 재인증, PRODUCT)
- 가입할 때 처음 받는 이메일의 확인 — 계정 스펙(같은 확인 방식을 쓴다). 시험 계정은 확인된 이메일로 시작한다
- 운영용 메일 발송 서비스 선택 — 지금은 표준 메일 전송 방식(SMTP)으로 보내고, 로컬에서는 Supabase 로컬의 메일 확인 화면으로 받는다. 운영 서비스는 배포 전에 정한다
- 알림 실제 발송(카카오 알림톡·메일) — 설정 값만 저장한다
- 회원 탈퇴(비밀번호 바꾸기는 session-login INV-L12)
- 크리에이터 주소 — address-protection INV-P13. 크리에이터의 공개 이름·소개글·찾기 노출·알림은 이 스펙 INV-A9~A11
- 찾기 노출을 꺼도 비공개가 아니다 — 크리에이터 페이지 주소와 목록 읽기 함수(본인 확인을 마친 크리에이터 전체)로는 그대로 보인다
- 팬 전용 공개 페이지 — 만들지 않는다(카드 d91). 팬 프로필은 팬 닉네임이 보이는 자리에 같이 나온다
- 팬 프로필 비공개 설정·신고 기능 — 없다. 운영자는 누구나처럼 프로필을 볼 수 있다
- 회원 탈퇴 때 프로필 사진 지우기 — 탈퇴 기능과 같이 정한다
