# 관리자 화면 스펙

관리자 화면은 사무실 사람이 쓰는 화면이다. 요금을 바꾸고, 보낼 수 없는 물품 목록을 고치고, 크리에이터 본인 확인을
승인하고, 공지를 쓰고, 1:1 문의에 답하고, 결제·환불과 역조공을 처리한다. 어기면 생기는 사고는 셋이다 —
운영자가 아닌 사람이 이 쓰기를 하거나, 요금을 바꾸는 순간 이미 결제한 주문의 금액이 흔들리거나,
관리자 화면이 팬·크리에이터의 주소·실명·전화번호를 보여 주는 통로가 된다.

용어
- **운영자**: 계정 역할이 `operator` 인 사람(대표·직원). 역할은 화면·API 로 바꿀 수 없다(DB 에서만).
- **대표**: 운영자 중 한 사람. DB 의 대표 설정 표에 적힌 계정 하나다 — 역할 칸이 아니다.
- **요금표**: 상자 구간(소형·중형·대형)마다 받는 값, 택배 원가, 검수비. 기본 서비스료 = 받는 값 − 택배 원가 − 검수비.

## 불변식

- INV-K1: 관리자 화면의 모든 읽기·쓰기는 운영자만 한다. 판정은 DB 함수가 로그인 토큰의 사람 ID 로 계정 역할을 읽어서 한다.
  운영자가 아니면 쓰기는 거부되고 읽기는 빈 결과다. 계정 역할을 바꾸는 함수·API 는 없다.
  (강제 위치: DB 함수 진입부 / 화면 — 운영자가 아니면 관리자 주소에 들어오지 못한다(404))
  위반 시: 팬·크리에이터가 요금·공지·본인 확인을 바꾸거나, 남의 문의·결제 내역을 본다.

- INV-K2: 요금표를 바꾸는 사람은 대표 한 사람이다. 대표는 DB 의 대표 설정 표(행 하나)에 적힌 계정이고, 그 표를 바꾸는
  함수·API 는 없다(마이그레이션이나 DB 에서만). 직원 운영자가 요금을 바꾸려 하면 거부한다.
  환불 실행도 대표만 한다(INV-K7).
  (강제 위치: DB 요금 변경 함수 / 환불 기록 함수)
  위반 시: 직원 계정 하나가 털리면 요금을 0 원으로 바꾸거나 환불을 내보낼 수 있다.

- INV-K3: 결제 금액은 **등록하는 순간의** 요금표로 계산하고, 그 금액이 결제 기록에 남는다. 요금표를 바꿔도 이미 등록한
  주문(결제 대기 포함)·이미 결제한 주문의 금액·환불액은 바뀌지 않는다. 등록과 요금 변경이 겹치면 등록은 바뀌기 전이나
  바뀐 뒤 요금 중 하나로 온전히 계산된다(두 요금이 섞이지 않는다).
  (강제 위치: 서버 — 등록 때 요금표를 한 번 읽어 그 값으로만 계산 / DB — 결제 기록의 금액 칸)
  위반 시: 결제창에 뜬 금액과 승인할 금액이 달라져 결제가 실패하거나, 팬이 낸 것과 다른 금액이 환불된다.

- INV-K4: 요금표는 다음을 모두 지킬 때만 저장된다. 하나라도 어기면 통째로 거부한다.
  (a) 모든 값은 0 이상 정수, 받는 값은 1 원 이상
  (b) 구간마다 택배 원가 + 검수비 ≤ 받는 값 (기본 서비스료가 음수가 되지 않는다)
  (c) 받는 값·택배 원가·검수비 각각 소형 ≤ 중형 ≤ 대형 (도착 실측 차액이 음수가 되지 않는다 — payment INV-M11)
  역조공 요금은 저장하지 않고 늘 받는 값 − 검수비로 계산한다(reverse-gift INV-R3).
  (강제 위치: DB 요금 변경 함수 / 서버 — 화면 입력 검사)
  위반 시: 서비스료 칸이 음수인 결제 기록이 생기거나, 큰 상자로 바뀌었는데 차액이 마이너스가 된다.

- INV-K5: 요금 변경은 한 줄씩 기록된다 — 언제, 누가, 어느 구간의 무엇을, 얼마에서 얼마로. 이 기록은 고치거나 지울 수 없다.
  (강제 위치: DB — 요금 변경 함수가 같은 처리 안에서 기록 / 기록 표는 추가만)
  위반 시: 요금이 언제 왜 바뀌었는지 알 수 없어 분쟁 때 근거가 없다.

- INV-K6: 상자 구간은 셋이다 — 소형(세 변 합 100cm·5kg 이하) · 중형(100cm·10kg 이하) · 대형(160cm·20kg 이하).
  크기와 무게 중 큰 쪽 구간으로 정한다. 대형을 넘는 상자는 받지 않는다(검수 불합격 반송, payment INV-M8 의 그 줄).
  신고는 소형·중형·대형 중 하나다. 첫 요금은 대형 10,900 원(택배 원가 6,500 · 검수비 2,500)이다.
  (강제 위치: 서버 — 구간 판정 / DB — 신고 구간 칸 제약)
  위반 시: 택배사가 받지 않는 크기를 받아 반송비만 나가거나, 대형 상자를 중형 요금으로 보낸다.

- INV-K7: 환불은 대표가 화면에서 「환불」을 눌러 실행한다. 금액은 서버가 주문(몫) 상태로 정하고(payment INV-M8,
  reverse-gift INV-R11) 화면에는 금액 입력 칸이 없다. 같은 환불을 두 번 눌러도 결제사 취소는 한 번만 일어난다
  (멱등 키 = 환불 기록 ID). 결제사 취소가 실패하면 환불 기록은 「실패」로 남고 다시 시도할 수 있다.
  결제사 취소가 「실패」한 환불과, 결과를 모른 채 멈춘 「처리 중」 환불(누른 지 2분이 지난 것)은 대표가 팬꾹 밖에서 직접 돌려준 뒤
  「직접 환불함」으로 완료로 적을 수 있다(2026-10-24, 카드 d126). 누른 지 2분 안의 처리 중 환불은 적을 수 없고, 「다시 시도」와 동시에 눌려도 하나만 된다.
  메모(어떻게 돌려줬는지 — 결제사 관리 화면에서 취소·계좌 이체, 날짜, 취소 번호, 1~200자)는 반드시 쓰고, 숫자가 10자리 이상 이어진 메모는 받지 않는다
  (연락처·계좌번호를 남기지 않는다 — 빈칸·점·하이픈·괄호가 셋까지 끼어도 이어진 것으로 세고 전각 숫자도 센다. 쉼표·빗금은 끊는다.
  앞뒤에 숫자가 붙지 않은 날짜 2026-10-24·시각 13:05 는 빼고 센다 — 계좌번호 안의 날짜처럼 생긴 조각은 빼지 않는다). 누가·언제 적었는지 남고, 금액은 그 기록의 금액 그대로이며, 적은 뒤에는 고치거나 되돌릴 수 없다.
  확인 창은 결제사 관리 화면에서 이미 취소됐는지 먼저 확인하라고 알린다 — 결제사에 닿지 못해 실패한 기록은 실제로는 취소됐을 수 있다.
  (강제 위치: DB 환불 기록 함수 — 금액 계산·한 번만 / 서버 — 결제사 취소 호출에 멱등 키)
  위반 시: 같은 환불이 두 번 나가거나, 사람이 금액을 잘못 넣어 더 많이 돌려준다.

- INV-K8: 관리자 화면은 실명·주소·휴대폰 번호를 보여 주지 않는다. 사람은 아이디·닉네임으로만 보인다.
  예외: 6자리 없이 온 보류 상자의 원 송장 전화번호 뒤 4자리(inbound-address-code INV-C5) — 4자리로는 사람을 알 수 없고, 그 상자가 이어지거나 반송·처분되면 지운다.
  주소가 필요한 일(송장 출력)은 복호화 함수 한 곳에서만 한다(address-protection·reverse-gift INV-R7).
  (강제 위치: DB 관리자 읽기 함수의 반환 칸 / 서버 — 반환 줄을 정해진 칸으로만 받는다)
  위반 시: 직원 계정 하나로 전원의 연락처가 나간다 — 팬심 사고가 그대로 되풀이된다.

- INV-K9: 보낼 수 없는 물품 목록은 운영자가 더하고 고치고 지운다. 누구나 읽는다(크리에이터 페이지·선물 보내기 화면).
  항목은 이름 1~40자 · 설명 0~120자이고, 바뀐 기록(누가·언제·무엇)을 남긴다.
  (강제 위치: DB 함수 / 읽기는 공개 읽기 함수)
  위반 시: 아무나 목록을 바꿔 위험물을 「보낼 수 있는 것」처럼 보이게 한다.

- INV-K10: 크리에이터 본인 확인 승인·취소는 운영자만 하고, 누가 언제 했는지 남긴다. 취소하면 그 크리에이터는 찾기에서
  사라지고 새 선물 등록·팔로우가 막힌다(이미 등록된 주문은 그대로 간다).
  (강제 위치: DB 함수)
  위반 시: 크리에이터 사칭 계정이 승인돼 팬 선물을 받는다.

- INV-K11: 공지는 운영자만 쓰고 고친다. 1:1 문의는 쓴 사람 본인과 운영자만 읽고, 답은 운영자만 단다.
  답을 단 문의는 쓴 사람이 고칠 수 없다.
  (강제 위치: DB 함수·읽기 정책)
  위반 시: 남의 문의(개인 사정이 적혀 있다)가 다른 사람에게 보인다.

- INV-K12: 1:1 문의를 보내는 횟수에는 상한이 없다. 대신 대표가 계정 하나를 「문의 제한」으로 바꿀 수 있고, 제한된 계정이
  새 문의를 남기면 거부된다. 이미 남긴 문의를 읽는 것과 답이 달리기 전에 고치는 것은 그대로 된다. 제한된 사람의 고객센터에는
  양식 대신 「지금은 1:1 문의를 남길 수 없어요」가 보인다(제한됐다는 사실을 숨기지 않는다).
  제한과 풀기는 대표만 하고, 대상은 운영자 문의 목록의 문의로 고른다(그 문의를 쓴 계정 — 화면이 계정 ID 를 보내지 않는다).
  사유(1~200자)를 적어야 하고, 할 때마다 누가·언제·제한인지 풀기인지·사유가 한 줄 남는다. 이 기록은 고치거나 지울 수 없다.
  운영자 계정은 제한할 수 없다. 이미 그 상태면(제한된 계정을 다시 제한, 제한 안 된 계정을 풀기) 거부하고 기록도 남지 않는다.
  기한은 없다 — 대표가 풀 때까지다. 운영자 문의 목록(대표·직원)에는 쓴 사람이 지금 제한 중인지와 그 사유가 보인다
  (직원도 문의에 답하므로 왜 막혔는지 안다). 제한된 본인에게는 제한 여부만 알리고 사유는 보이지 않는다.
  (강제 위치: DB — 문의 남기기 함수가 제한 여부를 확인 / 제한 함수 진입부의 대표 판정 / 기록 표는 추가만)
  위반 시: 직원 계정 하나로 아무 팬의 문의를 막거나, 막은 이유가 남지 않아 「왜 막혔나」에 답할 수 없다.

## 시나리오

- S1 (INV-K1): Given 운영자 로그인 / When 요금표·문의·결제 내역 읽기 / Then 보인다.
- S1b (INV-K1, 실패경로): Given 팬·크리에이터 로그인 / When 관리자 쓰기 함수(공지 쓰기·본인 확인 승인 등)를 부름 / Then 거부, 변화 없음. 관리자 읽기는 빈 결과.
- S1c (INV-K1, 실패경로): Given 팬 / When 관리자 화면 주소로 들어감 / Then 404.
- S2 (INV-K2): Given 대표 / When 소형 받는 값을 7,400 으로 / Then 저장된다.
- S2b (INV-K2, 실패경로): Given 직원 운영자 / When 요금 변경 / Then 거부, 요금표 그대로.
- S3 (INV-K3): Given 소형 6,900 일 때 등록한 결제 대기 / When 대표가 7,400 으로 바꾼 뒤 그 결제를 확정 / Then 6,900 으로 확정된다.
- S3b (INV-K3): Given 바꾼 뒤 / When 새 등록 / Then 7,400.
- S3c (INV-K3, 동시): Given 등록과 요금 변경이 동시에 / When 둘 다 끝남 / Then 그 결제 기록의 네 칸은 한 요금표의 값과 맞는다.
- S4 (INV-K4, 실패경로): Given 대표 / When 택배 원가 + 검수비 > 받는 값, 또는 중형 받는 값 < 소형, 또는 음수 / Then 통째로 거부.
- S5 (INV-K5): Given 요금 변경 1회 / When 기록을 봄 / Then 한 줄(시각·대표·구간·칸·전·후). S5b: 기록 수정·삭제는 DB 가 거부.
- S6 (INV-K6): Given 세 변 합 150cm·18kg / When 구간 판정 / Then 대형. S6b: 170cm 또는 21kg → 받지 않음.
- S6c (INV-K6): Given 대형 신고 1개 / When 등록 / Then 10,900 원, 역조공이면 8,400 원.
- S7 (INV-K7): Given 입고 전 거절된 주문 / When 대표가 환불 / Then 전액, 결제사 취소 1회.
- S7b (INV-K7, 동시): Given 같은 환불을 두 번 동시에 / Then 결제사 취소는 한 번, 기록 하나.
- S7c (INV-K7, 실패경로): Given 직원 운영자 / When 환불 / Then 거부.
- S7d (INV-K7): Given 결제사 취소가 실패한 환불 / When 대표가 메모를 쓰고 「직접 환불함」 / Then 완료, 메모·적은 사람·시각이 남고 결제사 호출은 없다. 그 뒤 「환불」·「다시 시도」는 「이미 환불했다」로 거부.
- S7e (INV-K7, 실패경로): Given 누른 지 2분 안의 처리 중 환불 · 메모 없음 · 메모에 010-1234-5678·010.1234.5678·전각 숫자 · 직원 운영자 · 이미 완료된 환불 / When 「직접 환불함」 / Then 거부, 기록은 그대로. 「다시 시도」와 동시에 → 하나만.
- S8 (INV-K8): Given 운영자 / When 관리자 읽기 함수 전부를 부름 / Then 응답에 주소·실명·전화번호 칸이나 그 꼴의 값이 없다.
- S9 (INV-K9): Given 운영자 / When 금지 물품 하나 추가 / Then 크리에이터 페이지에 보인다. S9b: 크리에이터가 추가 → 거부.
- S10 (INV-K10): Given 승인 취소 / When 팬이 찾기 / Then 안 나오고 새 선물 등록은 거부.
- S11 (INV-K11): Given 별빛의 문의 / When 달토끼가 읽기 / Then 빈 결과. S11b: 답이 달린 문의를 별빛이 고치려 함 → 거부.
- S12 (INV-K12): Given 별빛의 문의 / When 대표가 그 문의로 제한(사유 적음) / Then 별빛의 새 문의는 거부, 지난 문의는 읽힘, 기록 1줄.
  When 대표가 풀기 / Then 다시 남길 수 있고 기록 2줄.
- S12b (INV-K12, 실패경로): 직원 운영자·팬이 제한 → 거부. 사유 빈칸·201자 → 거부. 운영자가 쓴 문의로 제한 → 거부. 이미 제한된 계정을 다시 제한 → 거부, 기록 그대로.
- S12c (INV-K12): 제한 기록은 고치거나 지울 수 없다. 운영자 문의 목록에 쓴 사람의 제한 여부가 보인다.

## 신뢰 경계

- 믿는 값: 로그인 토큰으로 확인한 사람 ID(session-login INV-L2), DB 의 계정 역할 칸(운영자 판정), DB 의 대표 설정 표,
  DB 요금표, 서버 시각
- 믿지 않는 값: 화면이 보내는 금액·환불액·사람 ID·역할, 결제사 응답(형식 검증 뒤 사용)
- 대표 설정 표는 DB 에서만 바뀐다. 앱 서버 관리자 키로는 DB 가 그 표를 바꾸는 함수를 내주지 않는다 — 다만 관리자 키는
  표를 직접 쓸 수 있으므로, 앱 서버를 장악하면 대표를 바꿀 수 있다. 그래도 주소 복호화의 대표 판정은 복호화 함수 자신의
  설정(address-protection INV-P8)이라 여기와 무관하다.
