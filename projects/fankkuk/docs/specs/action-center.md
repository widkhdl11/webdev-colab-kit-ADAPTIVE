# 처리할 일 스펙

처리할 일은 팬이 직접 무언가를 해야 선물이 계속 진행되는 일을 카드로 모은 페이지와, 사이드바 숫자·홈 한 줄이다.
따로 저장되는 기록이 아니라 **주문·상자·결제·역조공 몫의 지금 상태에서 그때 계산한 목록**이다.

어기면 생기는 사고는 두 가지다. 사이드바 숫자·홈 한 줄·페이지 목록이 서로 다른 수를 말하거나(시안에서도 사이드바는 1, 페이지 제목은 3건이었다),
이미 처리한 일이 남아 있거나 기한이 지나 처리할 수 없는 일이 버튼과 함께 보인다. 그리고 남의 주문이 섞이면 주문번호·금액·받는 크리에이터가 보인다.

카드가 되는 일 (지금 스펙에 실제로 있는 「사람이 해야 진행되는 상태」만)

| 종류 | 누가 | 원천 | 하는 일 | 미루면 |
|---|---|---|---|---|
| 추가 결제 | 그 주문을 보낸 계정 | 차액 결제 요청(payment INV-M11~M13, 알림 「추가 결제 요청」) | 차액 결제 | 7일 뒤 반송 대상 |
| 도착하지 않은 상자 | 그 주문을 보낸 계정 | 결제 완료 뒤 14일이 지나도 입고 전인 상자(office-workflow INV-W10, 알림 「아직 도착하지 않은 상자」) | 「받는 주소 없이 보냈어요」 찾기 — 송장번호·택배사·이름 앞 한 글자(inbound-address-code INV-C4 ②) | 30일에 그 상자가 닫히고 환불이 바뀜 |
| 역조공 받기 | 그 몫의 받는 팬 | 결제가 끝난 몫의 받기 대기(reverse-gift INV-R10) | 받기 / 받지 않기 | 7일 뒤 받지 않음 |

시안의 「받는 주소 없이 온 상자」(팬)는 따로 카드가 되지 않는다 — 주인을 모르는 상자는 누구에게도 보이지 않아야 하고(inbound-address-code INV-C10),
팬 쪽에서는 「도착하지 않은 상자」 카드의 찾기가 바로 그 일이다.
**넣지 않는 것**: 승인 대기(자기 메뉴와 숫자가 있다), 정보만 주는 알림(추적기 반송·돌려보낼 상자·거절 뒤 늦은 상자·전해지지 못한 선물·결제 취소 — 할 수 있는 일이 없다),
「제가 보낸 게 아니에요」(요청한 일이 아니다).

## 불변식

- INV-J1: 처리할 일 카드는 위 표의 세 종류뿐이고, 카드 하나는 상자(역조공은 몫) 하나의 일 하나다. 카드는 저장하지 않고 읽을 때마다 원천 상태에서 계산한다 — 처리할 일 표·숫자 칸·「읽음」 표시가 없다.
  각 종류의 「보이는 조건」은 그 일을 처리하는 기존 함수가 처리를 받아 주는 조건과 같은 판정에서 나온다: 추가 결제는 차액 결제를 시작할 수 있는 상태(미결제·요청 뒤 168시간 전·주문 진행 중)일 때만,
  도착하지 않은 상자는 결제 완료 뒤 336시간이 지났고 그 상자가 아직 입고 전이며 닫히지 않았고 주문이 진행 중일 때만, 역조공 받기는 몫의 결제가 끝났고 받기도 받지 않기도 하지 않았으며 결제 완료 뒤 168시간 전일 때만.
  시간은 서버 시각의 경과 시간으로 세고(office-workflow INV-W6 과 같다), 카드에 보이는 기한은 서울 시간으로 쓴다.
  (강제 위치: DB 읽기 함수 하나 — 종류별 조건을 기존 처리 함수와 같은 판정에서 / 시험 — 종류마다 조건 경계)
  위반 시: 이미 낸 차액이 「결제하기」로 남아 두 번 내려 하거나, 기한이 지나 처리할 수 없는 카드가 버튼과 함께 남는다. 저장된 숫자가 원천과 어긋나 「처리할 일 2」인데 목록이 빈다.

- INV-J2: 사이드바 숫자 뱃지·홈의 「처리할 일 N건」 한 줄·처리할 일 페이지 목록·선물 상세 맨 위 한 줄은 모두 INV-J1 의 같은 읽기 함수 하나의 결과에서 나온다 — 숫자는 그 결과의 줄 수이고, 따로 세는 함수가 없다.
  0건이면 뱃지와 홈 한 줄이 없고 페이지는 빈 상태다. 응답은 캐시하지 않는다.
  (강제 위치: 서버 — 화면들이 같은 읽기를 쓴다 / 시험 — 같은 상태에서 뱃지 수·홈 수·목록 길이가 같다)
  위반 시: 시안처럼 사이드바와 페이지가 다른 수를 말해 사람이 어느 쪽을 믿을지 모른다.

- INV-J3: 처리할 일 읽기 함수는 계정·크리에이터 ID 를 인자로 받지 않는다. 로그인 토큰의 계정이 보낸 주문의 차액 요청·상자와, 그 계정이 받는 팬인 역조공 몫만 돌려준다.
  직원·대표·로그인하지 않은 사람에게는 0줄이다. 카드의 칸은 그 사람이 기존 읽기 함수(선물 상세·역조공 받기)로 이미 받는 칸을 넘지 않는다 —
  크리에이터 주소·연락처는 없고, 나만 보는 메모(together INV-F8)는 들어가지 않는다.
  (강제 위치: DB 읽기 함수 — 인자 목록, 로그인 토큰의 계정 조건, 반환 칸)
  위반 시: 남의 주문번호·차액 금액·받는 크리에이터가 보인다.

- INV-J4: 카드의 버튼은 새 처리 함수를 만들지 않고 그 일의 기존 처리(차액 결제 준비, 「받는 주소 없이 보냈어요」 찾기, 역조공 받기·받지 않기)를 그대로 부른다. 처리가 끝나면 다음 읽기에서 그 카드는 없다.
  찾기의 세 값이 맞지 않아 이어지지 않으면 카드는 그대로 남는다 — 카드는 누른 기록이 아니라 상자 상태로 사라진다. 차액 결제가 「승인 중」인 동안은 결제를 다시 시작할 수 없으므로 카드가 없고, 결제가 실패하거나 취소되면 다시 생긴다.
  (강제 위치: 서버 — 버튼이 기존 처리 경로를 부름 / 시험 — 처리 전후로 같은 읽기의 줄 수)
  위반 시: 처리할 일 화면에만 있는 처리 길이 기존 규칙(차액 금액 계산·매칭 세 값·받기 기한)을 건너뛴다. 찾기를 눌렀다는 이유만으로 카드가 사라져 상자를 못 찾은 채 30일 닫힘을 맞는다.

## 시나리오

- S1 (INV-J1): Given 별빛의 주문에 차액 요청(미결제, 요청 뒤 2일), 결제 뒤 15일 된 입고 전 상자, 결제 뒤 13일 된 입고 전 상자 / When 처리할 일 읽기 / Then 추가 결제 1·도착하지 않은 상자 1(15일 된 것만).
- S1b (INV-J1, 실패경로): Given 차액 결제 완료, 요청 뒤 8일 미결제(반송 대상), 30일이 지나 닫힌 상자, 거절로 끝난 주문의 입고 전 상자 / When 읽기 / Then 카드 없음.
- S1c (INV-J1): Given 별빛이 받는 팬인 역조공 몫(결제 뒤 3일, 받기 전) / When 별빛으로 읽기 / Then 역조공 받기 1. 받은 뒤·받지 않은 뒤·결제 뒤 168시간이 지난 뒤 / Then 없음.
- S2 (INV-J2): Given 별빛에게 카드 2 / When 사이드바·홈·처리할 일 페이지를 봄 / Then 뱃지 2·「2건」·카드 2. 둘 다 처리한 뒤 / Then 뱃지 없음·홈 줄 없음·빈 상태.
- S2b (INV-J2, 실패경로): Given 사이드바 숫자를 따로 세는 경로를 하나 심음 / When 같은 상태에서 비교 시험 / Then 수가 달라 실패로 잡힌다.
- S3 (INV-J3, 실패경로): Given 별빛·달토끼 각자 카드 / When 별빛이 읽기, 본문·주소에 달토끼 ID / Then 별빛 것만. 직원·대표·로그인 안 함 / Then 0줄. 별빛의 카드 응답에 크리에이터 주소·메모가 없다.
- S3b (INV-J3): Given 하루(크리에이터)가 모모에게 보낸 선물에 차액 요청 / When 하루로 읽기 / Then 추가 결제 카드 1(보낸 사람이면 역할과 상관없다).
- S4 (INV-J4): Given 도착하지 않은 상자 카드 / When 세 값이 맞는 찾기 / Then 상자가 이어지고 카드가 사라진다.
- S4b (INV-J4, 실패경로): Given 같은 카드 / When 세 값이 틀린 찾기 / Then 카드가 남는다. Given 차액 결제가 승인 중 / Then 카드 없음, 실패로 끝나면 다시 있음.

## 신뢰 경계

- 믿는 값: Supabase Auth 가 검증한 사용자 ID, DB 의 주문·상자·결제·역조공 몫 상태, 서버 시각
- 믿지 않는 값: 요청 본문·주소의 ID, 화면이 기억하는 숫자, 브라우저 시각

## 비범위

- 크리에이터 쪽 처리할 일(확인할 선물, 시안의 크리에이터 카드 셋 — 받는 주소 없이 온 상자의 팬 고르기·대신 포장 상자값·크리에이터 몫 상자 늦은 도착) — 사용자가 시안을 보고 고른 뒤 추가한다(카드 d91). 그 전까지 크리에이터 화면에는 만들지 않는다
- 승인 대기 — 자기 메뉴와 숫자를 그대로 쓴다
- 처리할 일 알림 — 카드마다 원천 알림(추가 결제 요청·아직 도착하지 않은 상자·역조공 받기)이 이미 있다. 새 알림 종류는 만들지 않는다
