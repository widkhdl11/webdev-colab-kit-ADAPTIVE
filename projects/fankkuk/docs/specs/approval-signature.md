# 크리에이터 선물 승인 서명 스펙

승인은 "크리에이터가 이 주문 한 건의 수령을 허락했다"는 전자서명이다. 기본 수단은 카카오톡 인증서
서명이고, 예비 수단(패스키)은 첫 출시 뒤에 같은 틀에 끼운다. 승인이 주소를 여는 유일한 열쇠라서
(`address-protection.md` INV-P4), 승인이 위조되거나 한 번의 승인이 여러 주문에 쓰이면 주소 보호
전체가 무너진다.

흐름: 승인 요청 생성 → 본인 확인 결과 수신(방식별로 교체) → 승인 처리.

## 불변식

- INV-S1: 서명 원문은 `요청 ID + 주문번호 + 요청 생성 시각 + 팬 닉네임 해시`로만 이루어진다.
  주소·선물 내용·팬 실명은 들어가지 않는다. (강제 위치: 서버 — 승인 요청 생성)
  위반 시: 서명 원문은 카카오와 딜러사를 거치므로 원문에 든 개인정보가 우리 밖으로 나간다.

- INV-S2: 서버는 돌려받은 서명의 원문이 그 요청 ID로 서버가 저장해 둔 원문과 바이트 단위로 같을 때만
  승인한다. 원문이 다르면 거부한다. (강제 위치: 서버 — 본인 확인 결과 수신)
  위반 시: 다른 주문이나 다른 시각에 받은 서명을 이 요청에 붙여 승인시킬 수 있다.

- (INV-S3 — 외부 연결 때 확정할 약속이라 `external-connections.md` 로 옮겼다 — 내용은 그대로)

- INV-S4: 서명한 사람은 그 주문의 크리에이터 본인이다. 인증서에서 나온 본인 식별값이 크리에이터가
  가입 때 카카오 인증으로 등록한 값과 같을 때만 승인한다. 어떤 식별값을 쓰는지는 딜러사 계약 후 확정한다.
  (강제 위치: 서버 — 서명 검증 직후)
  위반 시: 카카오 인증서를 가진 아무나 남의 주문을 승인할 수 있다.

- INV-S5: 한 요청 ID는 한 번만 승인 처리된다. 같은 서명이 다시 와도, 동시에 두 번 와도 승인 기록은
  하나다. 두 번째부터는 아무것도 바꾸지 않고 처음 결과를 돌려준다. (강제 위치: DB 제약 — 요청 ID 유일)
  위반 시: 승인 기록이 중복되면 승인 횟수와 복호화 횟수의 대조가 틀어진다.

- INV-S6: 거절·반려(7일 자동 포함)·취소된 주문, 또는 팬이 차단된 주문에는 서명이 와도 승인하지 않는다.
  (강제 위치: 서버 — 승인 처리는 대기 중이고 승인 기록 없는 주문만 승인한다. 차단된 팬의 승인 전 주문은 차단하는 순간
  같은 처리 안에서 거절되므로(decline-block INV-D8) 승인 처리에 따로 차단 확인을 두지 않는다. 차단 때 거절하는 범위를
  줄이면 이 약속이 깨지니 승인 처리에 차단 확인을 먼저 넣는다.)
  위반 시: 크리에이터가 거절한 선물이 늦게 도착한 서명으로 되살아난다.

- INV-S7: 승인 상태를 바꾸는 경로는 서명 검증을 통과한 승인 처리 하나뿐이다. 링크를 여는 것(GET 요청)만으로
  상태가 바뀌는 경로, 관리자 화면에서 손으로 승인하는 경로, "전체 승인"은 없다. (강제 위치: 서버 — 상태 변경 함수가 하나)
  위반 시: 서명을 거치지 않는 두 번째 입구가 생기고 이 스펙의 다른 불변식은 그 입구를 모른다.

- (INV-S8 — 외부 연결 때 확정할 약속이라 `external-connections.md` 로 옮겼다 — 내용은 그대로)

- INV-S9: 사무실 주소(2026-10-07부터 상자별 받는 주소 — 사무실 주소 끝에 상자마다 다른 6자리, inbound-address-code INV-C2·C3)는 결제가 끝난 주문의 팬에게만 보여 준다. 거절·반려(7일 자동 포함)·취소된 주문에는 보여 주지 않는다.
  승인은 기다리지 않는다 — 팬은 결제 직후 보내고, 승인은 출고 전에만 있으면 된다(INV-P4).
  (강제 위치: 서버 — 주소 안내 조회)
  위반 시: 결제하지 않은 사람이 사무실로 상자를 보내 미확인 입고가 생기거나, 이미 거절된 선물이 계속 들어온다.
  거절·반려·취소가 되면 그 주문의 6자리는 같은 처리에서 무효가 된다(INV-C3). 결정 카드 fankkuk-20261001-1-d48(스펙 inbound-address-code 승인).
  (2026-10-02 개정 전: 승인 전에는 보여 주지 않았다. 거절될 선물의 반송 비용은 이제 환불에서 뺀다 — payment INV-M8)

- INV-S10: 카카오 인증 API 호출은 등록된 고정 IP 경로에서만 나간다. 앱 서버가 직접 호출하지 않는다.
  (강제 위치: 배포 구조 — 고정 IP 경로 / 검사: 앱 서버 코드에 카카오 인증 API 주소가 없음)
  위반 시: 카카오가 호출을 거부해 승인 전체가 멈춘다.

- INV-S11: 카카오 연결 전 로컬에서는 **가짜 서명 창구**가 「본인 확인 결과 수신」 칸을 대신한다. 가짜 창구는 로그인한 크리에이터가
  그 주문의 크리에이터일 때만 서명을 만들어 준다 — 원문은 서버가 저장한 원문 그대로, 서명자는 그 크리에이터의 가짜 식별값이다.
  그 뒤의 검증(INV-S2·S4·S5·S6)은 진짜 서명과 같은 코드를 지난다. 운영 환경에서는 창구가 없다 — 실제 카카오 창구가 붙기 전까지
  승인 요청은 거부되고, 운영에서 가짜를 켜는 설정은 두지 않는다. 창구를 고르는 곳은 하나다.
  (강제 위치: 서버 — 서명 창구 고르는 곳 하나 / 승인 라우트 — 로그인한 사람과 주문의 크리에이터 대조 /
  DB 승인 함수 — 가짜 서명은 로컬 seed 만 넣는 「가짜 서명 허용」 줄이 있는 DB 에서만 받는다. 로컬 앱이 운영 DB 키로 떠 있어도
  운영 DB 가 거부한다 — 2026-10-05 보안 리뷰 반영)
  위반 시: 운영 사이트에서 비밀번호만으로 승인돼 주소가 열린다. 로컬에서도 남의 주문을 승인할 수 있다.

- INV-S12: 승인 처리는 검증한 서명(서명된 원문·서명자 식별값·서명 방식 kakao|fake)을 승인과 **한 처리에서** 저장한다.
  저장한 서명은 고치거나 지울 수 없고, 복호화 함수가 INV-P4 (a) 에서 다시 검증하는 재료다. 서명 방식이 fake 인 승인은 기록에 그대로 남아
  나중에 섞여도 가려낼 수 있다.
  (강제 위치: DB 승인 함수 — 승인과 서명 저장을 한 처리에서 / 서명 표는 추가만)
  위반 시: 승인은 됐는데 서명이 없어 송장 출력이 영영 거부되거나, 서명 없는 승인이 생겨 복호화 함수가 「승인됨」 표시만 믿게 된다.

## 시나리오

- S1 (INV-S1): Given 주문 생성 / When 승인 요청 생성 / Then 원문은 정해진 네 값으로만 이루어지고 주소·실명·선물 내용이 없다.
- S1b (INV-S1, 실패경로): Given 원문 생성 함수에 주소 필드가 섞여 들어옴 / When 생성 / Then 생성이 실패한다.
- S2 (INV-S2, 실패경로): Given 주문 A의 서명 / When 주문 B의 요청 ID로 제출 / Then 원문 불일치로 거부.
- S4 (INV-S4, 실패경로): Given 다른 사람의 카카오 인증서로 만든 유효한 서명 / When 제출 / Then 본인 불일치로 거부.
- S5 (INV-S5): Given 이미 승인된 요청 / When 같은 서명을 다시 제출 / Then 승인 기록은 1개 그대로, 응답은 처음 결과.
- S5b (INV-S5, 동시): Given 승인 전 요청 / When 같은 서명이 동시에 두 번 제출 / Then 승인 기록 1개.
- S6 (INV-S6, 실패경로): Given 7일 자동 반려된 주문 / When 유효한 서명 도착 / Then 승인되지 않는다.
- S7 (INV-S7, 실패경로): Given 승인 요청 링크 / When 링크를 열기만 함 / Then 상태 변화 없음.
- S9 (INV-S9): Given 결제가 끝났고 아직 승인 전인 주문의 팬 / When 사무실 주소 조회 / Then 주소가 온다.
- S9b (INV-S9, 실패경로): Given 거절·7일 자동 반려·취소된 주문의 팬 / When 사무실 주소 조회 / Then 주소가 오지 않는다.
- S11 (INV-S11): Given 로컬, 크리에이터 하루의 승인 대기 주문 / When 하루가 승인 / Then 가짜 서명으로 승인되고 서명 방식은 fake.
- S11b (INV-S11, 실패경로): Given 하루의 주문 / When 모모가 그 요청으로 승인 · 팬이 승인 · 로그인하지 않고 승인 / Then 거부, 없는 요청과 같은 답, 아무것도 안 바뀜.
- S11c (INV-S11, 실패경로): Given 운영 환경 표시(가짜를 켜는 설정 포함) / When 서명 창구를 고름 / Then 창구 없음, 승인 요청 거부.
- S12 (INV-S12): Given 승인 / When 서명 표를 읽음 / Then 원문이 저장된 원문과 같고 서명자·방식이 있다. 고치기·지우기는 거부.
- S12b (INV-S12, 실패경로): Given 서명 저장이 실패하는 상태 / When 승인 / Then 승인도 남지 않는다.
- S10 (INV-S10): Given 앱 서버 코드 / When 카카오 인증 API 주소를 검색 / Then 고정 IP 경로 모듈 밖에서는 나오지 않는다.

## 신뢰 경계

- 믿는 값: 서버가 저장한 원문, 서버가 직접 검증한 서명과 인증서, 가입 때 등록된 본인 식별값
- 믿지 않는 값: 딜러사 응답의 성공 여부 필드, 브라우저가 보내는 요청 ID 외 모든 값, 알림 링크의 파라미터

## 비범위

- 크리에이터의 카카오 인증서 자체가 빼앗긴 경우 — 카카오의 재발급·폐기 절차에 맡긴다
- 패스키 예비 수단의 등록·복구 절차 — 도입 시 별도 스펙
- 거절 절차(서명 불필요, 로그인 세션으로 충분 — 거절은 주소를 여는 방향이 아니다)
- 고정 IP 경로를 무엇으로 만드는지(소형 VM·프록시) — 구현 선택
