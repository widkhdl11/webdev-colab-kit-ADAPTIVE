# 크리에이터 선물 승인 서명 스펙

승인은 "크리에이터가 이 주문 한 건의 수령을 허락했다"는 전자서명이다. 기본 수단은 카카오톡 인증서
서명이고, 예비 수단(패스키)은 첫 출시 뒤에 같은 틀에 끼운다. 승인이 주소를 여는 유일한 열쇠라서
(`address-protection.md` INV-P4), 승인이 위조되거나 한 번의 승인이 여러 주문에 쓰이면 주소 보호
전체가 무너진다.

흐름: 승인 요청 생성 → 본인 확인 결과 수신(방식별로 교체) → 승인 처리.

## 불변식

- INV-S1: 서명 원문은 `요청 ID + 주문번호 + 요청 생성 시각 + 팬 닉네임 해시`로만 이루어진다.
  주소·선물 내용·팬 실명은 들어가지 않는다. (강제 위치: 서버 — 승인 요청 생성)
  위반 시: 서명 원문은 카카오와 딜러사를 거치므로 원문에 든 개인정보가 우리 밖으로 나간다.

- INV-S2: 서버는 돌려받은 서명의 원문이 그 요청 ID로 서버가 저장해 둔 원문과 바이트 단위로 같을 때만
  승인한다. 원문이 다르면 거부한다. (강제 위치: 서버 — 본인 확인 결과 수신)
  위반 시: 다른 주문이나 다른 시각에 받은 서명을 이 요청에 붙여 승인시킬 수 있다.

- (INV-S3 — 외부 연결 때 확정할 약속이라 `external-connections.md` 로 옮겼다 — 내용은 그대로)

- INV-S4: 서명한 사람은 그 주문의 크리에이터 본인이다. 서명 요청은 그 크리에이터가 승인 서명 연결(INV-S16)에서 등록한
  이름·생년월일·휴대폰 번호로 대상을 지정해 보내고, 돌아온 서명의 서명자가 그 등록 정보와 맞을 때만 승인한다. 무엇으로 「맞다」를 판정하는지(인증서의 어느 값)는
  드림시큐리티 명세를 받은 뒤 확정한다.
  (강제 위치: 서버 — 서명 검증 직후)
  위반 시: 카카오 인증서를 가진 아무나 남의 주문을 승인할 수 있다.

- INV-S5: 한 요청 ID는 한 번만 승인 처리된다. 같은 서명이 다시 와도, 동시에 두 번 와도 승인 기록은
  하나다. 두 번째부터는 아무것도 바꾸지 않고 처음 결과를 돌려준다. (강제 위치: DB 제약 — 요청 ID 유일)
  위반 시: 승인 기록이 중복되면 승인 횟수와 복호화 횟수의 대조가 틀어진다.

- INV-S6: 거절·반려(7일 자동 포함)·취소된 주문, 또는 팬이 차단된 주문에는 서명이 와도 승인하지 않는다.
  결제 완료(등록 시각)부터 168시간이 지난 주문은 자동 처리가 아직 돌지 않았어도 승인하지 않고 「기한 지남」으로 따로 답한다 —
  화면은 「기간이 지나 자동으로 반려된 선물이에요」(decline-block INV-D2 와 같은 답).
  (강제 위치: 서버 — 승인 처리는 대기 중이고 승인 기록 없는 주문만 승인한다. 차단된 팬의 승인 전 주문은 차단하는 순간
  같은 처리 안에서 거절되므로(decline-block INV-D8) 승인 처리에 따로 차단 확인을 두지 않는다. 차단 때 거절하는 범위를
  줄이면 이 약속이 깨지니 승인 처리에 차단 확인을 먼저 넣는다.)
  위반 시: 크리에이터가 거절한 선물이 늦게 도착한 서명으로 되살아난다.

- INV-S7: 승인 상태를 바꾸는 경로는 서명 검증을 통과한 승인 처리 하나뿐이다. 링크를 여는 것(GET 요청)만으로
  상태가 바뀌는 경로, 관리자 화면에서 손으로 승인하는 경로, "전체 승인"은 없다. (강제 위치: 서버 — 상태 변경 함수가 하나)
  위반 시: 서명을 거치지 않는 두 번째 입구가 생기고 이 스펙의 다른 불변식은 그 입구를 모른다.

- (INV-S8 — 외부 연결 때 확정할 약속이라 `external-connections.md` 로 옮겼다 — 내용은 그대로)

- INV-S9: 사무실 주소(2026-10-07부터 상자별 받는 주소 — 사무실 주소 끝에 상자마다 다른 6자리, inbound-address-code INV-C2·C3)는 결제가 끝난 주문의 팬에게만 보여 준다. 거절·반려(7일 자동 포함)·취소된 주문에는 보여 주지 않는다.
  승인을 기다리지 않고 먼저 보낼 수 있지만, 크리에이터가 아직 승인하지 않은 주문은 팬이 「먼저 보내기」를 눌러야 받는 주소가 나온다(2026-10-08 사용자 지시).
  누르기 전 화면에는 「승인 기다리는 중」과 안내 — 먼저 보내면 배송 기간을 줄일 수 있지만 크리에이터가 거절하면 반송될 수 있고, 그때는 반송 택배비를 뺀 금액을
  돌려준다(payment INV-M8 「입고 뒤 거절」) — 가 보인다. 누른 시각은 주문에 한 번 기록되고(되돌리지 않는다), 서버는 그 기록이 있거나 승인이 끝난 주문에만 받는 주소를 준다.
  화면에서 가리기만 하지 않는다 — 안내를 보고 눌렀다는 근거가 거절 환불 다툼의 근거다. 누를 수 있는 사람은 그 주문을 보낸 사람뿐이다. 승인은 출고 전에만 있으면 된다(INV-P4).
  (강제 위치: 서버 — 주소 안내 조회 · 「먼저 보내기」 기록 함수)
  위반 시: 결제하지 않은 사람이 사무실로 상자를 보내 미확인 입고가 생기거나, 이미 거절된 선물이 계속 들어온다.
  거절·반려·취소가 되면 그 주문의 6자리는 같은 처리에서 무효가 된다(INV-C3). 결정 카드 fankkuk-20261001-1-d48(스펙 inbound-address-code 승인).
  (2026-10-02 개정 전: 승인 전에는 보여 주지 않았다. 거절될 선물의 반송 비용은 이제 환불에서 뺀다 — payment INV-M8)

- INV-S10: 카카오 인증 API 호출은 등록된 고정 IP 경로에서만 나간다. 앱 서버가 직접 호출하지 않는다.
  (강제 위치: 배포 구조 — 고정 IP 경로 / 검사: 앱 서버 코드에 카카오 인증 API 주소가 없음)
  위반 시: 카카오가 호출을 거부해 승인 전체가 멈춘다.

- INV-S11: 카카오 연결 전 로컬에서는 **가짜 서명 창구**가 「본인 확인 결과 수신」 칸을 대신한다. 가짜 창구는 로그인한 크리에이터가
  그 주문의 크리에이터일 때만 서명을 만들어 준다 — 원문은 서버가 저장한 원문 그대로, 서명자는 그 크리에이터의 가짜 식별값이다.
  그 뒤의 검증(INV-S2·S4·S5·S6)은 진짜 서명과 같은 코드를 지난다. 운영 환경에서는 창구가 없다 — 실제 카카오 창구가 붙기 전까지
  승인 요청은 거부되고, 운영에서 가짜를 켜는 길은 시험 사이트 판정(test-site INV-TS1) 하나뿐이다. 창구를 고르는 곳은 하나다.
  (강제 위치: 서버 — 서명 창구 고르는 곳 하나 / 승인 라우트 — 로그인한 사람과 주문의 크리에이터 대조 /
  DB 승인 함수 — 가짜 서명은 로컬 seed 만 넣는 「가짜 서명 허용」 줄이 있는 DB 에서만 받는다. 로컬 앱이 운영 DB 키로 떠 있어도
  운영 DB 가 거부한다 — 2026-10-05 보안 리뷰 반영)
  위반 시: 운영 사이트에서 비밀번호만으로 승인돼 주소가 열린다. 로컬에서도 남의 주문을 승인할 수 있다.

- INV-S12: 승인 처리는 검증한 서명(서명된 원문·서명자 식별값·서명 방식 kakao|fake)을 승인과 **한 처리에서** 저장한다.
  저장한 서명은 고치거나 지울 수 없고, 복호화 함수가 INV-P4 (a) 에서 다시 검증하는 재료다. 서명 방식이 fake 인 승인은 기록에 그대로 남아
  나중에 섞여도 가려낼 수 있다.
  (강제 위치: DB 승인 함수 — 승인과 서명 저장을 한 처리에서 / 서명 표는 추가만)
  위반 시: 승인은 됐는데 서명이 없어 송장 출력이 영영 거부되거나, 서명 없는 승인이 생겨 복호화 함수가 「승인됨」 표시만 믿게 된다.

- INV-S13: 받는 주소를 등록하지 않은 크리에이터의 승인은 거부된다. 화면은 승인 버튼을 누르면 주소가 없을 때 「주소를 입력해 주세요」를
  먼저 띄우고, 있으면 「주소를 확인해 주세요」로 이름표와 바꾼 날(address-protection INV-P16)을 보인 뒤 그 자리에서 바꿀 수 있게 한다.
  주소 등록과 승인은 서명을 따로 받는다(각각 INV-P13·INV-S11) — 한 번의 서명으로 둘을 묶지 않는다.
  (강제 위치: DB 승인 함수 — 그 크리에이터의 주소 칸이 없으면 「주소 없음」으로 답하고 아무것도 바꾸지 않는다)
  위반 시: 승인·검수까지 끝난 상자가 출고 단계에서야 「주소 없음」으로 멈추고, 그동안 7일 기한과 보관이 흘러간다.

- INV-S14: 탈퇴한 크리에이터의 승인 서명 기록은 거래 기록으로 **5년** 보관한다(전자상거래법 제6조 — 계약 기록). 남기는 칸은 서명값·서명 원문의 해시·주문번호·
  서명 시각·서명 방식, 그리고 계정 대신 넣는 **가명 식별자**(my-account INV-A15)다. 탈퇴 처리는 같은 처리 안에서 서명 기록의 계정 연결을 가명 식별자로 바꾸고,
  서명자 식별값과 인증서(이름이 들어 있다)·서명 원문을 지운다. 이름·채널·연락처는 계정 쪽에서 지운다(INV-A15).
  INV-S12 의 「고치거나 지울 수 없다」의 예외는 이 탈퇴 처리 함수 하나뿐이다 — 앱 서버·대표 화면·다른 함수는 여전히 서명 기록을 고치지 못한다.
  그 주문이 끝난 때(주문의 마지막 기록)부터 5년이 지나면 자동 삭제 작업이 지운다 — 주문이 회원 쪽 내역으로 남아 있어도 서명 기록은 지운다(my-account INV-A16, 카드 d125).
  (강제 위치: DB 탈퇴 처리 함수 — 운영자 전용, 서명 표의 계정 칸만 가명으로 바꾸고 서명값·해시·주문번호·시각은 건드리지 않는다)
  위반 시: 탈퇴한 사람을 서명 기록으로 다시 찾아낼 수 있거나(이름·인증서가 남음), 반대로 분쟁이 났을 때 그 주문이 승인됐다는 근거가 사라진다.

- INV-S15: 탈퇴한 크리에이터에게는 새 승인 요청이 생기지 않는다 — 그 크리에이터 앞의 새 주문(결제)이 거부되고, 크리에이터 페이지는 선물 보내기 없이
  「탈퇴한 크리에이터입니다.」로만 보인다. 탈퇴를 처리할 때 진행 중인 주문은 먼저 크리에이터 사정으로 취소(payment INV-M21, 카드 d100 — 환불은 INV-M8 의 「크리에이터 사정으로 취소」 줄)로 끝내고,
  그 뒤 같은 탈퇴 처리에서 그 크리에이터의 주소 암호문과 그 데이터 키(키 조각)를 지운다. 진행 중인 주문이 남아 있으면 탈퇴 처리는 거부된다.
  (강제 위치: DB 탈퇴 처리 함수 — 진행 중 주문이 있으면 거부 / 주문 생성·승인 요청 생성 함수 — 탈퇴한 크리에이터면 거부 / 크리에이터 페이지 읽기 — 탈퇴 표시)
  위반 시: 탈퇴한 크리에이터 앞으로 결제가 들어와 받을 사람 없는 상자가 사무실에 쌓이거나, 주문이 남은 채 주소를 지워 송장을 뽑을 수 없게 된다.

- INV-S16: 승인 서명 연결 — 크리에이터는 이름·생년월일·휴대폰 번호를 적고 그 정보로 대상을 지정한 **시험 서명** 한 번을 카카오톡에서 마쳐야 연결된다.
  시험 서명은 주문과 상관없는 고정 원문(연결 요청 ID + 요청 시각)이고, 검증(INV-S2·S3)을 통과해야 연결로 적는다. 시험 서명이 실패하거나 기한(요청부터 10분) 안에 끝나지 않으면 연결되지 않는다.
  세 값은 격리 구역(pii)에 **암호화해서만** 둔다 — 주소와 같은 봉투 방식으로, 앱 서버·DB 만으로는 풀 수 없고 서명 게이트웨이만 KMS 로 풀어 서명 요청을 만들 때 꺼낸다.
  앱 서버·화면·로그는 저장 뒤 세 값을 다시 보이지 않는다(설정 화면은 「연결됨」과 연결한 날만). CI 는 받지도 저장하지도 않는다.
  연결 전 크리에이터에게는 새 주문(결제)이 만들어지지 않는다 — 링크 페이지는 선물 보내기 대신 「승인 수단 등록 전」을 보인다(creator-link INV-E15).
  연결 요청은 크리에이터당 1시간 5번·하루 5번, 같은 접속 주소(IP 해시) 하루 20번까지다 — 요청마다 적은 번호로 카카오톡이 가므로 남의 번호로 퍼붓지 못하게.
  연결은 가입 5단계에서 「나중에 하기」로 미룰 수 있고, 크리에이터 설정에서 같은 단계로 다시 들어간다. 다시 연결하면 새 정보로 바꾸고 같은 시험 서명을 다시 받는다.
  드림시큐리티 명세가 오기 전에는 **시험 서명 창구**가 카카오톡을 대신한다 — 가짜 서명 창구(INV-S11)와 같이 운영에서는 창구가 없고, 시험 사이트 판정(test-site INV-TS1)만 연다.
  (강제 위치: 서버 — 연결 요청·결과 수신 / 서명 게이트웨이 — 세 값 풀기 / DB — 연결 표시는 검증된 시험 서명과 한 처리에서만, 주문 생성 함수가 미연결 크리에이터를 거부)
  위반 시: 남의 이름·번호로 연결해 그 사람에게 서명 요청이 가거나, 연결 정보가 DB 덤프로 새거나, 서명받을 수단이 없는 크리에이터에게 결제가 들어와 승인 기한 7일이 그냥 흐른다.

## 시나리오

- S1 (INV-S1): Given 주문 생성 / When 승인 요청 생성 / Then 원문은 정해진 네 값으로만 이루어지고 주소·실명·선물 내용이 없다.
- S1b (INV-S1, 실패경로): Given 원문 생성 함수에 주소 필드가 섞여 들어옴 / When 생성 / Then 생성이 실패한다.
- S2 (INV-S2, 실패경로): Given 주문 A의 서명 / When 주문 B의 요청 ID로 제출 / Then 원문 불일치로 거부.
- S4 (INV-S4, 실패경로): Given 다른 사람의 카카오 인증서로 만든 유효한 서명 / When 제출 / Then 본인 불일치로 거부.
- S5 (INV-S5): Given 이미 승인된 요청 / When 같은 서명을 다시 제출 / Then 승인 기록은 1개 그대로, 응답은 처음 결과.
- S5b (INV-S5, 동시): Given 승인 전 요청 / When 같은 서명이 동시에 두 번 제출 / Then 승인 기록 1개.
- S6 (INV-S6, 실패경로): Given 7일 자동 반려된 주문 / When 유효한 서명 도착 / Then 승인되지 않는다.
- S6c (INV-S6, 실패경로): Given 결제 뒤 168시간이 지났지만 자동 처리 전인 주문 / When 유효한 서명 도착 / Then 「기한 지남」, 승인되지 않는다.
- S7 (INV-S7, 실패경로): Given 승인 요청 링크 / When 링크를 열기만 함 / Then 상태 변화 없음.
- S9 (INV-S9): Given 결제가 끝났고 아직 승인 전인 주문의 팬 / When 「먼저 보내기」 없이 받는 주소 조회 / Then 주소가 오지 않고 「먼저 보내기 전」 표시가 온다. When 「먼저 보내기」 → 다시 조회 / Then 주소가 온다(두 번 눌러도 기록은 처음 시각).
- S9c (INV-S9): Given 크리에이터가 승인한 주문 / When 「먼저 보내기」 없이 조회 / Then 주소가 온다.
- S9d (INV-S9, 실패경로): Given 별빛의 주문 / When 다른 팬·크리에이터·익명이 「먼저 보내기」 / Then 거부, 기록 없음. 거절·반려·취소된 주문 / Then 거부.
- S9b (INV-S9, 실패경로): Given 거절·7일 자동 반려·취소된 주문의 팬 / When 사무실 주소 조회 / Then 주소가 오지 않는다.
- S11 (INV-S11): Given 로컬, 크리에이터 하루의 승인 대기 주문 / When 하루가 승인 / Then 가짜 서명으로 승인되고 서명 방식은 fake.
- S11b (INV-S11, 실패경로): Given 하루의 주문 / When 모모가 그 요청으로 승인 · 팬이 승인 · 로그인하지 않고 승인 / Then 거부, 없는 요청과 같은 답, 아무것도 안 바뀜.
- S11c (INV-S11, 실패경로): Given 운영 환경 표시(시험 사이트 아님) / When 서명 창구를 고름 / Then 창구 없음, 승인 요청 거부.
- S12 (INV-S12): Given 승인 / When 서명 표를 읽음 / Then 원문이 저장된 원문과 같고 서명자·방식이 있다. 고치기·지우기는 거부.
- S12b (INV-S12, 실패경로): Given 서명 저장이 실패하는 상태 / When 승인 / Then 승인도 남지 않는다.
- S10 (INV-S10): Given 앱 서버 코드 / When 카카오 인증 API 주소를 검색 / Then 고정 IP 경로 모듈 밖에서는 나오지 않는다.

- S13 (INV-S13, 실패경로): Given 주소를 등록하지 않은 하루의 승인 대기 주문 / When 유효한 서명으로 승인 / Then 「주소 없음」, 승인·서명 기록이 남지 않는다.
- S13b (INV-S13): Given 같은 주문 / When 하루가 주소를 등록한 뒤 승인 / Then 승인된다.

- S14 (INV-S14): Given 하루가 승인한 주문 A / When 하루의 탈퇴 처리 / Then A 의 서명 기록에 서명값·원문 해시·주문번호·시각이 그대로 있고, 계정 칸은 가명 식별자, 서명자 식별값·인증서·원문은 비어 있다.
- S14b (INV-S14, 실패경로): Given 탈퇴 처리된 서명 기록 / When 앱 서버·대표 계정이 그 줄을 고치거나 지움 / Then 거부. 탈퇴 처리 함수를 같은 계정에 다시 불러도 가명 식별자가 바뀌지 않는다.
- S14c (INV-S14): Given 크리에이터만 탈퇴했고 마지막 기록이 5년 1일 전인 주문의 가명 처리된 서명 기록 / When 자동 삭제 작업 / Then 서명 기록은 지워지고 주문은 남는다.
  서명은 5년 1일 전이어도 주문의 마지막 기록이 4년 364일 전이면 남는다(실패경로 — 서명한 때부터 세면 법정 보관 기간을 못 채운다). 탈퇴하지 않은 크리에이터의 서명은 남는다.
- S15 (INV-S15): Given 하루 앞으로 입고 전 주문 1건 / When 대표가 크리에이터 사정으로 취소한 뒤 탈퇴 처리 / Then 탈퇴되고 하루의 주소 암호문·데이터 키가 없다. 하루의 크리에이터 페이지는 「탈퇴한 크리에이터입니다.」, 선물 보내기 버튼이 없다.
- S15b (INV-S15, 실패경로): Given 하루 앞으로 진행 중 주문이 남음 / When 탈퇴 처리 / Then 거부, 주소·계정 그대로.
- S15c (INV-S15, 실패경로): Given 탈퇴한 하루 / When 팬이 하루 앞으로 결제를 만들거나 승인 요청 생성 함수를 직접 부름 / Then 거부, 주문·요청이 생기지 않는다.

- S16 (INV-S16): Given 채널 확인을 마친 하루 / When 이름·생년월일·휴대폰 번호를 적고 시험 서명을 마침 / Then 「연결됨」, 링크 페이지에 선물 보내기가 보인다. DB 의 세 값은 암호문뿐이다.
- S16b (INV-S16, 실패경로): Given 하루가 「나중에 하기」로 가입을 끝냄 / When 팬이 하루 앞으로 결제를 만들거나 주문 생성 함수를 직접 부름 / Then 거부. 링크 페이지는 「승인 수단 등록 전」.
- S16c (INV-S16, 실패경로): Given 연결 요청 / When 시험 서명이 실패하거나 10분이 지나거나, 브라우저가 「연결됨」만 꾸며 보냄 / Then 연결되지 않는다.
- S16d (INV-S16, 실패경로): Given 운영 환경(시험 사이트 아님), 드림시큐리티 연결 없음 / When 연결 요청 / Then 거부, 시험 창구로 넘어가지 않음.

## 신뢰 경계

- 믿는 값: 서버가 저장한 원문, 서버가 직접 검증한 서명과 인증서, 승인 서명 연결에서 시험 서명으로 확인된 등록 정보
- 믿지 않는 값: 딜러사 응답의 성공 여부 필드, 브라우저가 보내는 요청 ID 외 모든 값, 알림 링크의 파라미터

## 비범위

- 크리에이터의 카카오 인증서 자체가 빼앗긴 경우 — 카카오의 재발급·폐기 절차에 맡긴다
- 패스키 예비 수단의 등록·복구 절차 — 도입 시 별도 스펙
- 거절 절차(서명 불필요, 로그인 세션으로 충분 — 거절은 주소를 여는 방향이 아니다)
- 고정 IP 경로를 무엇으로 만드는지(소형 VM·프록시) — 구현 선택
