# 아이디 로그인과 로그인 유지 스펙

로그인은 Supabase Auth 의 이메일·비밀번호 로그인 위에 아이디를 얹는다 — 아이디 `byeolbit_fan` 은
내부적으로 `byeolbit_fan@fankkuk.test` 같은 주소로 바뀐다. DB 는 로그인 토큰에 든 사용자 ID 로
"팬은 자기 선물만" 같은 판정을 하므로, **앱 서버가 사용자를 잘못 정하면 DB 의 막음이 그대로 남에게 열린다.**
특히 돈과 상태를 바꾸는 쓰기는 앱 서버가 관리자 키로 대신 부르므로 DB 가 사람을 다시 확인하지 못한다 —
그 자리에서는 앱 서버의 판정이 유일한 판정이다.

## 불변식

- INV-L1: 로그인 토큰은 브라우저 스크립트가 읽을 수 없는 쿠키(httpOnly, SameSite=Lax, 운영에서는 Secure)에만 둔다.
  브라우저 코드는 Supabase 를 직접 부르지 않고 앱 서버만 부른다. (강제 위치: 서버 — 쿠키 설정)
  위반 시: 화면에 스크립트 하나만 끼어들어도 토큰을 가져가 그 사람으로 선물 목록을 읽는다.

- INV-L2: 서버는 쿠키 내용을 그대로 믿지 않는다. 요청마다 Supabase Auth 로 토큰을 검증해 얻은 사용자 ID 만 쓴다.
  검증에 실패하면 로그인하지 않은 것으로 본다. (강제 위치: 서버 — 현재 사용자 조회 함수 하나)
  위반 시: 쿠키 안의 사용자 ID 를 고쳐 다른 사람 행세를 한다.

- INV-L3: 관리자 키로 부르는 쓰기(선물 등록·결제)에 넘기는 사람 ID 는 INV-L2 로 얻은 ID 다.
  브라우저가 보낸 사용자 ID·닉네임은 쓰지 않는다. 로그인하지 않았거나 역할이 맞지 않으면 쓰기 전에 거부한다.
  선물 등록·결제의 맞는 역할은 **팬과 크리에이터**다. 운영자는 거부한다. 주문 표의 `fan_id` 칸은 이름은 그대로 두고
  「보내는 사람」으로 읽는다 — 보내는 사람이 크리에이터여도 같은 칸에 들어간다.
  (강제 위치: 서버 — 각 쓰기 경로 진입부. DB 등록 함수도 역할을 다시 확인한다)
  위반 시: 요청 본문의 팬 ID 를 바꿔 남의 이름으로 선물을 등록하거나 남의 결제를 진행한다.

- INV-L8: 크리에이터는 자기 자신에게 선물을 등록할 수 없다. 받는 크리에이터의 계정이 보내는 사람(INV-L2 로 얻은 ID)과
  같으면 거부한다. (강제 위치: 서버 — 선물 등록 진입부 + DB 등록 함수, 두 곳이 각각)
  위반 시: 자기 앞으로 주문을 만들어 자기 주소 열람 횟수와 승인 기록을 부풀린다 — 「열린 횟수 = 승인 횟수」 기록이 흐려진다.

- INV-L9: 선물을 등록하려면 보내는 사람(팬이든 크리에이터든)이 받는 크리에이터를 **팔로우하고 있어야** 한다.
  받는 쪽이 보내는 쪽을 팔로우한 것은 조건이 되지 않는다. 팔로우하지 않았으면 거부한다. 판정은 등록하는 순간의 팔로우로
  하고, 등록 뒤에 팔로우를 끊어도 이미 만든 주문은 그대로 간다. 크리에이터도 다른 크리에이터를 팔로우할 수 있어야 한다
  (자기 자신은 팔로우할 수 없다). (강제 위치: 서버 — 선물 등록 진입부 + DB 등록 함수, 두 곳이 각각)
  위반 시: 팔로우하지 않은 크리에이터에게 선물이 가 받는 쪽이 모르는 사람의 승인 요청을 받는다.

- INV-L4: 관리자 키(service_role)는 서버 전용 모듈에서만 읽는다. 공개 환경 변수(`NEXT_PUBLIC_` 접두어)에 없고,
  브라우저 번들에 들어가면 빌드가 실패한다. (강제 위치: 서버 설정 + 서버 전용 표시)
  위반 시: 누구나 모든 표를 읽고 쓴다 — RLS 가 통째로 꺼진 것과 같다.

- INV-L5: 로그인 실패 응답은 아이디가 없는 경우와 비밀번호가 틀린 경우를 구분하지 않는다. 같은 문구, 같은 상태 코드.
  (강제 위치: 서버 — 로그인 처리)
  위반 시: 응답 차이로 가입된 아이디 목록을 알아낸다.

- INV-L6: 시험 계정 주소(`@fankkuk.test`)는 운영 환경(`VERCEL_ENV=production` 또는 `NODE_ENV=production`)에서
  로그인할 수 없다. (강제 위치: 서버 — 로그인 처리)
  위반 시: 공개된 시험 비밀번호로 운영 사이트에 들어온다.

- INV-L7: 로그아웃은 서버에서 세션을 끝내고 쿠키를 지운다. 로그아웃 뒤 같은 쿠키로 온 요청은 로그인하지 않은 것으로 본다.
  (강제 위치: 서버 — 로그아웃 처리)
  위반 시: 공용 기기에서 로그아웃해도 다음 사람이 그대로 들어간다.

- INV-L10: 비밀번호 재설정 요청은 아이디와 이메일 둘 다 받는다(이메일은 계정마다 유일하지 않아 이메일만으로는 계정을 정할 수 없다).
  계정이 없을 때, 이메일이 맞지 않을 때, 확인된 이메일이 없을 때, 한도를 넘었을 때, 메일을 실제로 보냈을 때 모두 **같은 상태 코드·같은 문구**
  (「입력한 정보가 맞으면 메일을 보냈어요」)를 돌려준다. 메일은 입력한 이메일이 그 계정의 확인된 이메일과 같을 때만 그 주소로 보낸다 —
  확인 대기 이메일로는 보내지 않는다(my-account INV-A7). 한 계정에 한 시간 다섯 통까지(my-account INV-A8 과 같은 한도·같은 방식)이고,
  본문에는 링크와 닉네임만 있다. 운영 계정의 로그인 주소는 메일이 갈 수 없는 주소라(signup INV-U8) 재설정 메일은 확인 메일과 같은 우리 쪽 링크로 만든다.
  확인된 이메일이 없는 계정은 지금은 재설정할 수 없다 — 화면은 모든 경우에 같은 응답 아래 「메일이 오지 않으면 1:1 문의」를 안내하고,
  운영자가 손으로 비밀번호를 바꾸는 길은 만들지 않는다. 같은 사이트의 요청만 받고 응답은 캐시되지 않는다.
  (강제 위치: 서버 — 재설정 요청 처리, 응답 하나 / DB 함수 — 계정·이메일 대조, 보낸 기록과 개수 확인을 한 번에)
  위반 시: 응답 차이로 가입된 아이디와 그 이메일을 알아낸다(INV-L5 가 막은 것을 재설정 화면이 다시 연다). 확인 안 된 주소로 재설정 링크가 가서 남이 계정을 가져간다.

- INV-L11: 재설정 링크는 한 번만 쓰이고 발급 뒤 1시간에 만료되며, 그 계정 하나에 묶인다. 새 재설정을 요청하면 이전 링크는 무효다. DB 에는 링크 값이 아니라
  그 해시만 둔다(my-account INV-A7 과 같다). 새 비밀번호는 signup INV-U6 경계를 따른다. 재설정은 비밀번호만 바꾼다 — 주소·승인·휴대폰 번호에는 닿지 않는다.
  재설정이 끝나면 그 계정의 로그인 세션은 모두 끝나고 새 비밀번호로 다시 로그인한다.
  (강제 위치: DB 함수 — 링크 확인과 사용 표시를 한 처리에서, 행 잠금 / 서버 — 비밀번호 바꾸기와 세션 끝내기)
  위반 시: 메일함에 남은 옛 링크나 털린 DB 의 링크 값으로 비밀번호를 바꾼다. 계정을 빼앗은 사람의 세션이 재설정 뒤에도 살아 있다.

- INV-L12: 로그인한 사람의 비밀번호 바꾸기는 사람 ID 를 인자로 받지 않고 로그인 토큰이 확인한 사람(INV-L2)의 비밀번호만 바꾼다. 지금 비밀번호를 함께 받아
  맞을 때만 바꾸고, 틀리면 INV-L5 와 같은 하나의 실패 문구다. 새 비밀번호는 signup INV-U6 경계를 따른다. 바꾸면 지금 세션을 뺀 그 계정의 다른 세션은 모두 끝난다.
  같은 사이트의 JSON 요청만 받고 응답은 캐시되지 않는다.
  (강제 위치: 서버 — 비밀번호 바꾸기 처리 진입부)
  위반 시: 열린 세션 하나만 빼앗은 사람이 비밀번호를 바꿔 주인을 쫓아낸다. 다른 사이트가 로그인한 사람 몰래 비밀번호를 바꾼다.

- INV-L13: 로그인 뒤 돌아갈 주소는 같은 사이트의 경로만 받는다 — `/` 하나로 시작하고, `//`·`/\` 로 시작하지 않으며, 역슬래시·제어 문자·`://` 가 없어야 한다.
  조건에 맞지 않거나 비어 있으면 메인으로 간다. 서버는 이 값을 사이트 주소에 붙여 만들지 않고 경로 그대로 돌려준다(결제 확정 뒤 이동과 같은 방식, 2026-10-03).
  돌아갈 주소는 로그인 성공 뒤에만 쓰이고, 로그인 실패 응답(INV-L5)에는 영향이 없다.
  (강제 위치: 서버 — 로그인 처리의 돌아갈 주소 검사 하나 / 화면 — 로그인 링크에 경로만 싣는다)
  위반 시: 우리 로그인 화면이 다른 사이트로 보내는 데 쓰인다 — 로그인 직후 가짜 로그인 화면으로 보내 비밀번호를 다시 받아 간다.


- INV-L14: 비밀번호 확인(로그인 · 비밀번호 바꾸기와 번호 바꾸기의 지금 비밀번호 확인)은 아이디마다 센다 — 최근 10분 안에 5번 틀리면
  마지막으로 틀린 때부터 15분 동안 그 아이디의 비밀번호 확인을 하지 않고 거부한다(2026-10-08 결정, 정책 질문 ⑦).
  세 확인은 한 횟수를 함께 쓴다. 맞으면 그때까지 틀린 횟수는 지워진 것으로 본다. 비밀번호 재설정(INV-L10)은 이 확인을 거치지 않고,
  재설정이 끝나면 그 아이디의 막힘도 풀린다.
  가입되지 않은 아이디도 똑같이 세고 막는다 — 막혔다는 안내로 아이디가 있는지 알 수 없게(INV-L5).
  막혔을 때 안내는 「비밀번호를 여러 번 틀려 잠시 확인할 수 없어요. 15분 뒤 다시 하거나 비밀번호를 재설정해 주세요.」 하나다.
  동시에 들어온 확인도 한도를 넘지 않는다 — 결과가 나기 전의 시도도 틀린 것으로 센다.
  기록에는 아이디(소문자로 맞춘 값)·시각·결과만 있고 비밀번호·IP 는 없다. 기록 함수는 서버 전용 키로만 부른다.
  (강제 위치: DB — 시도 시작 함수가 아이디별 잠금 뒤 횟수 확인과 시도 줄 넣기를 한 처리로 / 서버 — 세 확인이 Auth 를 부르기 전에 시작 함수를 거침)
  위반 시: 계정 하나를 노린 비밀번호 짐작이 계정 단위로 막히지 않는다(Auth 의 제한은 IP 기준인데 요청이 모두 앱 서버 IP 에서 나간다).

- INV-L15: 「로그인 상태 유지」를 끄고 로그인하면 로그인 쿠키는 만료 시각이 없는 쿠키(브라우저를 닫으면 지워지는 쿠키)로만 쓴다.
  로그인할 때뿐 아니라 요청마다 토큰을 갱신하며 다시 쓸 때도 같다 — 그래서 끈 사람의 브라우저에는 만료 시각이 붙은 로그인 쿠키가 한 번도 남지 않는다.
  켜고 로그인하면 지금처럼 만료 시각이 붙은 쿠키로 쓴다(라이브러리 기본 400일, 토큰 갱신이 계속 연장). 화면의 체크 기본값은 꺼짐이다.
  어느 쪽으로 로그인했는지는 서버가 쓰는 표시 쿠키 하나로 기억한다 — 이 쿠키도 HttpOnly·SameSite=Lax·운영 Secure(INV-L1)이고,
  끈 사람에게만 만료 시각 없이 있고 켠 사람에게는 없다. 다시 로그인하면 그때 고른 값으로 바뀌고, 로그아웃하면 지운다(INV-L7).
  쿠키를 지우는 쓰기(만료 0)는 이 규칙과 상관없이 그대로 지운다. 이 표시는 쿠키를 어떻게 쓸지만 정하고 누가 로그인했는지 판정에는 쓰지 않는다(INV-L2).
  (강제 위치: 서버 — 로그인 쿠키를 쓰는 함수 하나가 표시를 보고 만료 시각을 뗀다. 로그인 처리·요청마다 갱신·화면 읽기가 모두 이 함수로 쓴다)
  위반 시: 공용 PC 에서 체크를 끄고 로그인한 사람이 창을 닫아도 다음 사람이 그 계정으로 들어간다. 토큰 갱신 때 한 번만 빠뜨려도 400일 쿠키가 생긴다.
## 시나리오

- S1 (INV-L1): Given 로그인 성공 / When 응답 쿠키를 봄 / Then 토큰 쿠키에 HttpOnly·SameSite=Lax 가 붙어 있다.
- S2 (INV-L2, 실패경로): Given 서명이 틀린(또는 만료된) 토큰 쿠키 / When 현재 사용자 조회 / Then 로그인 안 함으로 본다.
- S3 (INV-L3, 실패경로): Given 별빛으로 로그인, 본문에 달토끼의 ID 를 넣음 / When 선물 등록 / Then 주문의 팬은 별빛이다.
- S3b (INV-L3, 실패경로): Given 로그인 안 함 / When 선물 등록·결제 시작 / Then 거부, DB 쓰기 없음.
- S3c (INV-L3, 실패경로): Given 운영자 계정 / When 선물 등록 / Then 거부, DB 쓰기 없음.
- S3d (INV-L8, 실패경로): Given 크리에이터 별빛(계정) / When 별빛 자신의 크리에이터 페이지로 선물 등록 / Then 거부, DB 쓰기 없음.
- S3e (INV-L3·INV-L9): Given 크리에이터 별빛이 크리에이터 달토끼를 팔로우 / When 별빛이 달토끼에게 선물 등록 / Then 주문의 보내는 사람은 별빛, 받는 사람은 달토끼.
- S3f (INV-L9, 실패경로): Given 달토끼(계정)만 별빛을 팔로우, 별빛은 달토끼를 팔로우하지 않음 / When 별빛이 달토끼에게 선물 등록 / Then 거부, DB 쓰기 없음.
- S3g (INV-L9, 실패경로): Given 팬이 달토끼를 팔로우하지 않음 / When 그 팬이 달토끼에게 선물 등록 / Then 거부, DB 쓰기 없음. 팔로우한 뒤 다시 보내면 성공한다.
- S3h (INV-L9): Given 팬이 달토끼를 팔로우하고 선물 등록 / When 팔로우를 끊음 / Then 이미 만든 주문은 그대로 남는다.
- S4 (INV-L4): Given 서버 설정 / When 환경 변수 이름을 검사 / Then 관리자 키가 공개 접두어로 쓰이지 않는다.
- S5 (INV-L5, 실패경로): Given 없는 아이디 / 있는 아이디 + 틀린 비밀번호 / When 로그인 / Then 두 응답이 같다.
- S6 (INV-L6, 실패경로): Given 운영 환경 표시 / When `byeolbit_fan` 로그인 / Then 거부, 시험 계정 주소(`@fankkuk.test`)로는 Supabase Auth 를 부르지 않는다.
- S7 (INV-L7): Given 로그인 → 로그아웃 / When 지운 쿠키 값을 다시 붙여 요청 / Then 로그인 안 함.
- S8 (INV-L10, 실패경로): Given 없는 아이디 / 있는 아이디+틀린 이메일 / 확인된 이메일이 없는 계정 / 맞는 아이디+이메일 / When 재설정 요청 / Then 네 응답이 같고, 메일은 마지막 하나에만 한 통.
- S8b (INV-L10, 실패경로): Given 확인 대기 이메일 B 만 있는 계정 / When B 로 재설정 요청 / Then 같은 응답, 메일 없음. 한 시간 여섯 번째 요청 → 같은 응답, 메일 없음.
- S9 (INV-L11): Given 재설정 링크 / When 열어 새 비밀번호 저장 / Then 새 비밀번호로 로그인되고, 다른 기기 세션은 로그인 안 함으로 보인다.
- S9b (INV-L11, 실패경로): Given 이미 쓴 링크·1시간 지난 링크·새 요청으로 무효가 된 링크·다른 계정 링크 / When 저장 / Then 거부, 비밀번호 그대로. DB 에 링크 원문 없음.
- S10 (INV-L12, 실패경로): Given 별빛으로 로그인 / When 틀린 지금 비밀번호·9자 새 비밀번호·본문에 달토끼 ID / Then 각각 거부, 달토끼 비밀번호 그대로.
- S10b (INV-L12): Given 별빛이 두 기기에서 로그인 / When 한 기기에서 비밀번호 바꾸기 성공 / Then 그 기기는 로그인 그대로, 다른 기기는 로그인 안 함.
- S12 (INV-L14): Given 별빛 / When 10분 안에 비밀번호 5번 틀림 / Then 6번째는 맞는 비밀번호여도 거부(안내 문구), Auth 를 부르지 않음. 15분 뒤 → 맞으면 로그인.
- S12b (INV-L14): Given 별빛이 로그인에서 3번, 비밀번호 바꾸기에서 2번 틀림 / Then 막힘. 4번 틀린 뒤 맞으면 → 그 뒤 다시 5번까지.
- S12c (INV-L14): Given 없는 아이디 / When 5번 틀림 / Then 같은 안내로 막힘. Given 막힌 별빛 / When 재설정 완료 / Then 바로 로그인.
- S12d (INV-L14, 동시): Given 4번 틀린 별빛 / When 동시에 3번 확인 / Then 그중 1번만 Auth 까지 가고 나머지는 거부.
- S13 (INV-L15): Given 체크를 끄고 로그인 성공 / When 응답 쿠키를 봄 / Then 로그인 쿠키에 Max-Age·Expires 가 없고, 표시 쿠키가 HttpOnly 로 있다.
- S13b (INV-L15, 실패경로): Given S13 의 쿠키(표시 있음) / When 요청마다 갱신이 토큰을 다시 씀 / Then 다시 쓴 로그인 쿠키에도 Max-Age·Expires 가 없다.
- S13c (INV-L15): Given 체크를 켜고 로그인(전에 끄고 로그인한 표시가 남아 있어도) / When 응답 쿠키를 봄 / Then 로그인 쿠키에 Max-Age 가 있고 표시 쿠키는 지워진다.
- S13d (INV-L15·INV-L7): Given 끄고 로그인 / When 로그아웃 / Then 로그인 쿠키와 표시 쿠키가 모두 지워진다(만료 0 쓰기는 만료 시각을 떼지 않는다).
- S11 (INV-L13): `/help` → `/help` · `/gifts/FC-7K3M9` → 그대로 · `//evil.example` · `/\evil.example` · `https://evil.example` · `/a%0d%0a` 의 풀린 제어 문자 · 빈 값 → 메인.

- 믿는 값: Supabase Auth 가 검증해 돌려준 사용자 ID, DB 의 역할 칸(이 스펙 안에서 — 주소 복호화는 예외, address-protection INV-P8)
