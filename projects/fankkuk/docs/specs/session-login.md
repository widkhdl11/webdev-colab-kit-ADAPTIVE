# 아이디 로그인과 로그인 유지 스펙

로그인은 Supabase Auth 의 이메일·비밀번호 로그인 위에 아이디를 얹는다 — 아이디 `byeolbit_fan` 은
내부적으로 `byeolbit_fan@fankkuk.test` 같은 주소로 바뀐다. DB 는 로그인 토큰에 든 사용자 ID 로
"팬은 자기 선물만" 같은 판정을 하므로, **앱 서버가 사용자를 잘못 정하면 DB 의 막음이 그대로 남에게 열린다.**
특히 돈과 상태를 바꾸는 쓰기는 앱 서버가 관리자 키로 대신 부르므로 DB 가 사람을 다시 확인하지 못한다 —
그 자리에서는 앱 서버의 판정이 유일한 판정이다.

## 불변식

- INV-L1: 로그인 토큰은 브라우저 스크립트가 읽을 수 없는 쿠키(httpOnly, SameSite=Lax, 운영에서는 Secure)에만 둔다.
  브라우저 코드는 Supabase 를 직접 부르지 않고 앱 서버만 부른다. (강제 위치: 서버 — 쿠키 설정)
  위반 시: 화면에 스크립트 하나만 끼어들어도 토큰을 가져가 그 사람으로 선물 목록을 읽는다.

- INV-L2: 서버는 쿠키 내용을 그대로 믿지 않는다. 요청마다 Supabase Auth 로 토큰을 검증해 얻은 사용자 ID 만 쓴다.
  검증에 실패하면 로그인하지 않은 것으로 본다. (강제 위치: 서버 — 현재 사용자 조회 함수 하나)
  위반 시: 쿠키 안의 사용자 ID 를 고쳐 다른 사람 행세를 한다.

- INV-L3: 관리자 키로 부르는 쓰기(선물 등록·결제)에 넘기는 사람 ID 는 INV-L2 로 얻은 ID 다.
  브라우저가 보낸 사용자 ID·닉네임은 쓰지 않는다. 로그인하지 않았거나 역할이 맞지 않으면 쓰기 전에 거부한다.
  선물 등록·결제의 맞는 역할은 **팬과 크리에이터**다. 운영자는 거부한다. 주문 표의 `fan_id` 칸은 이름은 그대로 두고
  「보내는 사람」으로 읽는다 — 보내는 사람이 크리에이터여도 같은 칸에 들어간다.
  (강제 위치: 서버 — 각 쓰기 경로 진입부. DB 등록 함수도 역할을 다시 확인한다)
  위반 시: 요청 본문의 팬 ID 를 바꿔 남의 이름으로 선물을 등록하거나 남의 결제를 진행한다.

- INV-L8: 크리에이터는 자기 자신에게 선물을 등록할 수 없다. 받는 크리에이터의 계정이 보내는 사람(INV-L2 로 얻은 ID)과
  같으면 거부한다. (강제 위치: 서버 — 선물 등록 진입부 + DB 등록 함수, 두 곳이 각각)
  위반 시: 자기 앞으로 주문을 만들어 자기 주소 열람 횟수와 승인 기록을 부풀린다 — 「열린 횟수 = 승인 횟수」 기록이 흐려진다.

- INV-L9: 크리에이터가 다른 크리에이터에게 선물을 등록하려면 둘 사이에 팔로우가 **한쪽이라도** 있어야 한다 —
  보내는 쪽이 받는 크리에이터를 팔로우하고 있거나, 받는 크리에이터의 계정이 보내는 쪽 크리에이터를 팔로우하고 있거나.
  둘 다 없으면 거부한다. 팬이 보내는 선물에는 이 조건이 없다. 판정은 등록하는 순간의 팔로우로 하고, 등록 뒤에 팔로우를
  끊어도 이미 만든 주문은 그대로 간다. 이 조건이 뜻을 가지려면 크리에이터도 다른 크리에이터를 팔로우할 수 있어야 한다
  (자기 자신은 팔로우할 수 없다). (강제 위치: 서버 — 선물 등록 진입부 + DB 등록 함수, 두 곳이 각각)
  위반 시: 모르는 크리에이터끼리 선물이 오가 받는 쪽이 원치 않는 승인 요청을 받는다.

- INV-L4: 관리자 키(service_role)는 서버 전용 모듈에서만 읽는다. 공개 환경 변수(`NEXT_PUBLIC_` 접두어)에 없고,
  브라우저 번들에 들어가면 빌드가 실패한다. (강제 위치: 서버 설정 + 서버 전용 표시)
  위반 시: 누구나 모든 표를 읽고 쓴다 — RLS 가 통째로 꺼진 것과 같다.

- INV-L5: 로그인 실패 응답은 아이디가 없는 경우와 비밀번호가 틀린 경우를 구분하지 않는다. 같은 문구, 같은 상태 코드.
  (강제 위치: 서버 — 로그인 처리)
  위반 시: 응답 차이로 가입된 아이디 목록을 알아낸다.

- INV-L6: 시험 계정 주소(`@fankkuk.test`)는 운영 환경(`VERCEL_ENV=production` 또는 `NODE_ENV=production`)에서
  로그인할 수 없다. (강제 위치: 서버 — 로그인 처리)
  위반 시: 공개된 시험 비밀번호로 운영 사이트에 들어온다.

- INV-L7: 로그아웃은 서버에서 세션을 끝내고 쿠키를 지운다. 로그아웃 뒤 같은 쿠키로 온 요청은 로그인하지 않은 것으로 본다.
  (강제 위치: 서버 — 로그아웃 처리)
  위반 시: 공용 기기에서 로그아웃해도 다음 사람이 그대로 들어간다.

## 시나리오

- S1 (INV-L1): Given 로그인 성공 / When 응답 쿠키를 봄 / Then 토큰 쿠키에 HttpOnly·SameSite=Lax 가 붙어 있다.
- S2 (INV-L2, 실패경로): Given 서명이 틀린(또는 만료된) 토큰 쿠키 / When 현재 사용자 조회 / Then 로그인 안 함으로 본다.
- S3 (INV-L3, 실패경로): Given 별빛으로 로그인, 본문에 달토끼의 ID 를 넣음 / When 선물 등록 / Then 주문의 팬은 별빛이다.
- S3b (INV-L3, 실패경로): Given 로그인 안 함 / When 선물 등록·결제 시작 / Then 거부, DB 쓰기 없음.
- S3c (INV-L3, 실패경로): Given 운영자 계정 / When 선물 등록 / Then 거부, DB 쓰기 없음.
- S3d (INV-L8, 실패경로): Given 크리에이터 별빛(계정) / When 별빛 자신의 크리에이터 페이지로 선물 등록 / Then 거부, DB 쓰기 없음.
- S3e (INV-L3·INV-L9): Given 크리에이터 별빛이 크리에이터 달토끼를 팔로우 / When 별빛이 달토끼에게 선물 등록 / Then 주문의 보내는 사람은 별빛, 받는 사람은 달토끼.
- S3f (INV-L9): Given 달토끼(계정)만 별빛을 팔로우, 별빛은 달토끼를 팔로우하지 않음 / When 별빛이 달토끼에게 선물 등록 / Then 성공.
- S3g (INV-L9, 실패경로): Given 별빛과 달토끼 사이 팔로우 없음 / When 별빛이 달토끼에게 선물 등록 / Then 거부, DB 쓰기 없음. 팬이 같은 조건으로 달토끼에게 보내면 성공한다.
- S4 (INV-L4): Given 서버 설정 / When 환경 변수 이름을 검사 / Then 관리자 키가 공개 접두어로 쓰이지 않는다.
- S5 (INV-L5, 실패경로): Given 없는 아이디 / 있는 아이디 + 틀린 비밀번호 / When 로그인 / Then 두 응답이 같다.
- S6 (INV-L6, 실패경로): Given 운영 환경 표시 / When `byeolbit_fan` 로그인 / Then 거부, 시험 계정 주소(`@fankkuk.test`)로는 Supabase Auth 를 부르지 않는다.
- S7 (INV-L7): Given 로그인 → 로그아웃 / When 지운 쿠키 값을 다시 붙여 요청 / Then 로그인 안 함.

## 신뢰 경계

- 믿는 값: Supabase Auth 가 검증해 돌려준 사용자 ID, DB 의 역할 칸(이 스펙 안에서 — 주소 복호화는 예외, address-protection INV-P8)
- 믿지 않는 값: 요청 본문·주소창의 사용자 ID·닉네임·역할, 쿠키 안의 값을 직접 해석한 결과

## 비범위

- 가입·카카오 본인 확인·비밀번호 재설정·「로그인 상태 유지」 체크(지금은 항상 유지) — 계정 스펙
- 로그인 시도 횟수 제한 — Supabase Auth 기본 제한에 맡긴다. 운영 전에 계정 스펙에서 다시 정한다
