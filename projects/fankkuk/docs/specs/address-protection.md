# 크리에이터 주소 보호 스펙

팬꾹이 파는 것은 "크리에이터가 승인하지 않은 건은 우리 시스템도 주소를 열지 않는다"는 약속이다.
주소는 크리에이터 브라우저에서 암호화되어 들어오고, 송장을 출력하는 순간 한 건씩만 열린다.
어기면 사고가 한 번에 전원 규모로 난다 — 팬심 사고는 서버가 평문을 볼 수 있었고 화면 하나에
실명 컬럼이 섞여서 났다. 이 스펙의 목표는 **DB가 통째로 털려도, 앱 서버가 털려도, 승인된 적 없는
건의 주소는 열리지 않는 것**이다. 크리에이터 본인 기기가 털리는 경우는 막지 못한다(비범위).

용어
- **데이터 키**: 주소 한 건을 암호화하는 무작위 키. 브라우저에서 만든다.
- **보관 키**: 데이터 키를 감싸는 클라우드 KMS의 비대칭 키. 브라우저는 공개키로 감싸기만 하고,
  푸는 비밀키는 KMS 밖으로 나오지 않는다.
- **복호화 함수**: 주소를 여는 유일한 서버 코드. 앱 서버와 따로 배포되고 자기 자격 증명을 가진다.

## 불변식

- INV-P1: 주소 평문은 크리에이터 브라우저에서 암호화된 뒤에만 서버로 간다. 앱 서버와 DB가 받는
  주소 값은 암호문(감싼 데이터 키 + 암호화된 주소)뿐이다. 서버는 암호문 형식이 아닌 주소 입력을 거부한다.
  (강제 위치: 클라이언트 — 전송 전 암호화 / 서버 — 입력 형식 검증)
  위반 시: 평문이 한 번이라도 서버를 지나가면 로그·오류 보고·백업 어디에든 남을 수 있다.

- (INV-P2 — 외부 연결 때 확정할 약속이라 `external-connections.md` 로 옮겼다 — 내용은 그대로)

- (INV-P3 — 외부 연결 때 확정할 약속이라 `external-connections.md` 로 옮겼다 — 내용은 그대로)

- INV-P4: 복호화 함수는 다음이 모두 참일 때만 주소를 연다. 하나라도 거짓이면 거부하고 거부 로그를 남긴다.
  (a) 그 주문의 승인 서명을 복호화 함수가 **직접 다시 검증**해 유효하다 — 원문 일치·서명 값·인증서·본인 일치
      (`approval-signature.md` INV-S2~S4 와 같은 검증). DB의 "승인됨" 표시만으로는 열지 않는다
  (b) 서명 원문에 적힌 주문번호가 요청한 주문번호와 같다
  (c) 주문이 검수 완료 상태이고 **아직 출고 확정 전**이며, 거절·반려·차단되지 않았다
  (d) 요청자가 대표 계정이다 (INV-P8)
  (강제 위치: 복호화 함수 진입부, 복호화보다 먼저)
  위반 시: 승인 없는 건, 다른 주문의 승인으로 이 주문을 여는 경로가 생긴다.

- INV-P5: 한 주문의 복호화는 최대 3회다(첫 출력 + 재출력 2회 — 프린터 걸림·라벨 훼손용). 출고가 확정되면
  (송장 바코드 재스캔으로 짝 확인) 남은 횟수와 상관없이 그 주문은 더 열리지 않는다. 동시에 두 요청이 와도
  상한을 넘는 복호화는 일어나지 않는다. 2회째부터는 열람 기록에 「재출력」으로 표시된다.
  (강제 위치: 복호화 함수 — 횟수 확인과 증가가 한 번에 일어나는 자리 + INV-P4 (c))
  위반 시: 승인 한 번으로 주소를 몇 번이고 다시 열 수 있다. 쓰지 않은 횟수가 출고 뒤에도 남아 있으면
  배송이 끝난 주문의 주소를 나중에 다시 꺼낼 수 있다.

- (INV-P6 — 외부 연결 때 확정할 약속이라 `external-connections.md` 로 옮겼다 — 내용은 그대로)

- INV-P7: 복호화 시도는 성공·거부 모두 한 줄씩 기록된다 — 시각, 주문번호, 요청자 계정, 결과, 거부 사유.
  이 기록은 복호화 함수만 쓰고, 앱 서버는 고치거나 지울 수 없다. 크리에이터는 자기 주문의 기록 전부를 본다.
  (강제 위치: 복호화 함수 + DB 권한 — 앱 서버 역할에 수정·삭제 권한 없음)
  위반 시: 몰래 연 기록을 지울 수 있으면 "열람 기록 전부 공개"는 거짓 광고가 된다.

- INV-P8: 복호화를 요청할 수 있는 사람은 대표 계정 하나다. 복호화 함수는 요청에 실린 로그인 토큰을
  스스로 검증하고, 그 사용자 ID가 **복호화 함수 자신의 설정**에 적힌 대표 ID와 같을 때만 받는다.
  DB의 역할 컬럼은 판단 근거로 쓰지 않는다. (강제 위치: 복호화 함수 진입부)
  위반 시: 앱 서버를 장악하면 DB의 역할 컬럼을 고쳐 직원 계정을 대표로 만들 수 있다.

- INV-P9: 주소 암호문, 실명, 휴대폰 번호는 API로 노출되지 않는 별도 구역(`pii` 스키마)에만 있다.
  익명·일반 사용자 권한으로는 어떤 경로로도 조회되지 않는다. (강제 위치: DB — 노출 스키마 목록, RLS)
  위반 시: 암호문이라도 대량으로 나가면 나중에 키가 털렸을 때 소급해서 열린다. 실명·번호는 그 자체로 유출이다.

- INV-P10: 주소(평문·암호문), 데이터 키는 서명 원문·알림 본문·애플리케이션 로그·내부 QR 어디에도 들어가지 않는다.
  QR에는 주문번호 문자열만 들어간다. (강제 위치: 각 생성 함수 / 검사: 생성물에 주소 필드가 없음)
  위반 시: 암호화를 우회하는 평문 사본이 생긴다.

- (INV-P11 — 외부 연결 때 확정할 약속이라 `external-connections.md` 로 옮겼다 — 내용은 그대로)

- INV-P12: 클라우드 KMS 를 연결하기 전 임시 복호화(개발용 키 쌍)는 운영 환경에서 동작하지 않는다.
  운영 환경(`VERCEL_ENV=production` 또는 `NODE_ENV=production`)에서 임시 복호화를 만들려 하면 만드는 순간
  실패한다. 개발용 비밀키는 저장소에 커밋되지 않는다(환경 파일은 무시 목록에 있다).
  (강제 위치: 서버 — 임시 복호화 생성 시)
  위반 시: 개발용 비밀키가 운영 앱 서버에 있으면 INV-P2·P3 가 통째로 무너진다 — 앱 서버 하나로 전원 주소가 열린다.

## 시나리오

- S1 (INV-P1): Given 크리에이터가 주소를 입력 / When 저장 / Then 서버로 가는 요청 본문에 주소 평문 문자열이 없고, 저장된 값은 암호문 형식이다.
- S1b (INV-P1, 실패경로): Given 누군가 API로 평문 주소를 직접 보냄 / When 저장 요청 / Then 형식 오류로 거부되고 아무것도 저장되지 않는다.
- S4 (INV-P4 a): Given 승인 근거가 없는 검수 완료 주문 / When 대표가 송장 출력 / Then 거부, 거부 로그 1줄, 택배사 호출 없음.
- S4b (INV-P4 b): Given 주문 A의 승인 근거 / When 그것을 주문 B의 출력에 붙여 요청 / Then 거부.
- S4c (INV-P4 c): Given 승인됐지만 검수 미완료(또는 거절·반려된) 주문 / When 출력 / Then 거부.
- S5 (INV-P5): Given 상한까지 복호화된 주문 / When 한 번 더 출력 / Then 거부.
- S5c (INV-P5, 실패경로): Given 1회 출력 후 출고 확정된 주문 / When 재출력 요청 / Then 거부(남은 2회는 쓸 수 없다).
- S5d (INV-P5): Given 2회째 출력 / When 크리에이터가 열람 기록을 봄 / Then 그 줄에 「재출력」 표시가 있다.
- S5b (INV-P5, 동시): Given 복호화가 상한 직전인 주문 / When 출력 요청 두 개가 동시에 들어옴 / Then 복호화는 하나만 일어나고 나머지는 거부된다.
- S7 (INV-P7): Given 성공 1회, 거부 1회 / When 크리에이터가 열람 기록을 봄 / Then 두 줄 모두 보인다.
- S7b (INV-P7, 실패경로): Given 앱 서버 역할 / When 열람 기록 행을 수정·삭제 / Then DB가 거부한다.
- S8 (INV-P8, 실패경로): Given 직원 계정의 로그인 토큰 / When 복호화 요청 / Then 거부.
- S8b (INV-P8, 실패경로): Given DB에서 직원 계정의 역할을 '대표'로 바꿔 둠 / When 그 계정으로 복호화 요청 / Then 여전히 거부(복호화 함수 설정의 대표 ID와 다름).
- S9 (INV-P9, 실패경로): Given 익명 키와 일반 사용자 토큰 / When 모든 공개 API를 호출 / Then 응답에 주소·실명·전화번호 필드나 그 형태의 값이 없다.
- S10 (INV-P10): Given 승인 요청·알림·QR 생성 / When 각 생성물을 검사 / Then 주소 관련 값이 없고 QR 내용은 주문번호와 정확히 같다.

- S12 (INV-P12): Given 개발 환경과 개발용 키 쌍 / When 브라우저 방식으로 봉인한 주소를 임시 복호화로 엶 / Then 원래 주소가 나온다.
- S12b (INV-P12, 실패경로): Given 운영 환경 표시 / When 임시 복호화를 만들려 함 / Then 즉시 실패하고 키를 읽지 않는다.

## 신뢰 경계

- 믿는 값: 복호화 함수 자신의 설정(대표 ID, KMS 접근 자격), 복호화 함수가 스스로 검증한 로그인 토큰과 승인 서명
- 믿지 않는 값: 앱 서버가 넘기는 모든 값(주문 상태 제외 — 아래), 브라우저 입력, DB의 역할 컬럼,
  택배사 API 응답(형식 검증 후 사용)
- 주문 상태(검수 완료·거절 여부)는 앱 서버가 쓰는 DB 값이라 앱 서버를 장악하면 위조할 수 있다.
  그래도 (a)·(b)가 따로 막으므로 위조로 얻는 것은 "승인된 건을 검수 전에, 또는 상한 안에서 출고 뒤에 여는 것"뿐이고
  그것도 매번 열람 기록에 남아 크리에이터에게 보인다.

## 비범위

- 크리에이터 기기 해킹·피싱으로 승인을 빼앗기는 경우 — 피해는 그 크리에이터·그 건으로 한정된다
- 앱 서버를 장악한 공격자가 **승인된 건**의 라벨 이미지를 가로채는 것 — 원본 설계가 받아들인 남은 위험
- 팬의 반송 주소 처리 — 검수·반송 스펙에서 다룬다
- 로그인·재서명 절차 자체 — 계정 스펙
- 승인 서명의 생성·검증 절차 — `approval-signature.md`
