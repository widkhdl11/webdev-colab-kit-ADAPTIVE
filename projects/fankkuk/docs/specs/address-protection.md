# 크리에이터 주소 보호 스펙

팬꾹이 파는 것은 "크리에이터가 승인하지 않은 건은 우리 시스템도 주소를 열지 않는다"는 약속이다.
주소는 크리에이터 브라우저에서 암호화되어 들어오고, 송장을 출력하는 순간 한 건씩만 열린다.
어기면 사고가 한 번에 전원 규모로 난다 — 팬심 사고는 서버가 평문을 볼 수 있었고 화면 하나에
실명 컬럼이 섞여서 났다. 이 스펙의 목표는 **DB가 통째로 털려도, 앱 서버가 털려도, 승인된 적 없는
건의 주소는 열리지 않는 것**이다. 크리에이터 본인 기기가 털리는 경우는 막지 못한다(비범위).

용어
- **데이터 키**: 주소 한 건을 암호화하는 무작위 키. 브라우저에서 만든다.
- **보관 키**: 데이터 키를 감싸는 클라우드 KMS의 비대칭 키. 브라우저는 공개키로 감싸기만 하고,
  푸는 비밀키는 KMS 밖으로 나오지 않는다.
- **복호화 함수**: 주소를 여는 유일한 서버 코드. 앱 서버와 따로 배포되고 자기 자격 증명을 가진다.

## 불변식

- INV-P1: 주소 평문은 크리에이터 브라우저에서 암호화된 뒤에만 서버로 간다. 앱 서버와 DB가 받는
  주소 값은 암호문(감싼 데이터 키 + 암호화된 주소)뿐이다. 서버는 암호문 형식이 아닌 주소 입력을 거부한다.
  (강제 위치: 클라이언트 — 전송 전 암호화 / 서버 — 입력 형식 검증)
  위반 시: 평문이 한 번이라도 서버를 지나가면 로그·오류 보고·백업 어디에든 남을 수 있다.

- (INV-P2 — 외부 연결 때 확정할 약속이라 `external-connections.md` 로 옮겼다 — 내용은 그대로)

- (INV-P3 — 외부 연결 때 확정할 약속이라 `external-connections.md` 로 옮겼다 — 내용은 그대로)

- INV-P4: 복호화 함수는 다음이 모두 참일 때만 주소를 연다. 하나라도 거짓이면 거부하고 거부 로그를 남긴다.
  (a) 그 주문의 승인 서명을 복호화 함수가 **직접 다시 검증**해 유효하다 — 원문 일치·서명 값·인증서·본인 일치
      (`approval-signature.md` INV-S2~S4 와 같은 검증). DB의 "승인됨" 표시만으로는 열지 않는다
  (b) 서명 원문에 적힌 주문번호가 요청한 주문번호와 같다
  (c) 주문이 검수 완료 상태이고 **아직 출고 확정 전**이거나, 출고 확정된 상자의 **재출력**(INV-P5)이며, 거절·반려되지 않았다(차단은 승인 전 주문을 거절로 바꿀 뿐이고 승인된 주문은 차단돼도 출고한다 — decline-block INV-D8, 카드 d27)
  (d) 요청자가 대표 계정이다 (INV-P8)
  (강제 위치: 복호화 함수 진입부, 복호화보다 먼저)
  위반 시: 승인 없는 건, 다른 주문의 승인으로 이 주문을 여는 경로가 생긴다.

- INV-P5: 복호화는 **상자 하나에** 최대 3회다(첫 출력 + 재출력 2회 — 프린터 걸림·라벨 훼손용). 상자마다 송장이
  한 장씩 필요하므로 횟수도 상자마다 따로 센다 — 상자 4개짜리 주문은 네 상자 모두 송장을 뽑을 수 있다(카드 d30).
  상자의 출고가 확정돼도(송장 바코드 재스캔으로 짝 확인) 택배사가 상자를 가져갔다는 확인(집하) 전에는 남은 횟수 안에서
  재출력할 수 있다 — 기사가 오기 전에 라벨이 젖거나 망가지는 경우용. 택배사 연결 전에는 집하 확인이 없으므로 출고 확정 뒤에도
  남은 횟수가 그대로다(2026-10-10 사용자 결정). 재출력은 처음 송장번호를 그대로 쓰고 상자는 출고 확정 상태로 남는다.
  첫 출력은 검수 완료 상자에서만 한다.
  같은 상자에 동시에 두 요청이 와도 상한을 넘는 복호화는 일어나지 않는다. 열람 기록의 줄마다 어느 상자의 몇 번째
  출력인지 남고, 2회째부터는 「재출력」으로 표시된다. 어느 상자인지 없는 「연 줄」은 기록되지 않는다.
  횟수 = 그 상자의 「연 줄」 수 − 그 가운데 돌려준 줄 수(INV-P15).
  (강제 위치: 복호화 함수 — 횟수 확인과 증가가 한 번에 일어나는 자리 + INV-P4 (c))
  위반 시: 승인 한 번으로 주소를 몇 번이고 다시 열 수 있다. 반대로 주문 전체로 세면 상자가 넷 이상인 주문은 출고가 막힌다.
  (출고 뒤 남은 횟수로 주소를 다시 꺼낼 수 있는 것은 받아들인 위험이다 — 대표 계정만, 상자당 3번 안에서, 매번 열람 기록에 남는다.)

- (INV-P6 — 외부 연결 때 확정할 약속이라 `external-connections.md` 로 옮겼다 — 내용은 그대로)

- INV-P7: 복호화 시도는 성공·거부 모두 한 줄씩 기록된다 — 시각, 주문번호, 요청자 계정, 결과, 거부 사유.
  이 기록은 복호화 함수만 쓰고, 앱 서버는 고치거나 지울 수 없다. 크리에이터는 자기 주문의 기록 전부를 본다.
  직원이 송장 출력을 누른 시도도 앱 서버가 앞에서 끊지 않고 복호화 함수까지 보내, 그 함수가 「대표 아님」 거부 줄을 남긴다
  (2026-10-08 결정, 정책 질문 ⑨). 앱 서버는 그 결과와 상관없이 직원에게 라벨을 내주지 않는다.
  크리에이터 주소가 아직 등록되지 않았으면 열 주소가 없으므로 줄도 횟수도 남기지 않는다.
  (강제 위치: 복호화 함수 + DB 권한 — 앱 서버 역할에 수정·삭제 권한 없음)
  위반 시: 몰래 연 기록을 지울 수 있으면 "열람 기록 전부 공개"는 거짓 광고가 된다.

- INV-P15: 주소를 연 뒤 송장이 나오기 전에 출력이 실패하면(봉투 열기 실패·봉인 속 크리에이터 대조 전 오류·송장 마무리 실패) 출력 함수는 그 「연 줄」을
  돌려준다 — 「돌려줌」 줄을 따로 남기고 원래 줄은 그대로 둔다(INV-P7). 돌려준 줄은 횟수에서 빠지고, 크리에이터 열람 기록에는 그 줄이 「출력 실패」로 보인다.
  돌려주기의 조건은 모두 DB 가 상자를 잠근 자리에서 본다.
  (a) 돌려주기 함수로만 한다 — 복호화 전용 역할이 기록 표에 직접 넣을 수 있는 줄은 거부 줄뿐이다. 돌려줌 줄은 직접 넣을 수 없다.
  (b) 「연 줄」 하나는 한 번만 돌려준다.
  (c) 그 상자의 가장 최근 「연 줄」이고, 그 줄을 연 요청자가 돌려받을 때만이다.
  (d) 상자가 아직 송장 출력 단계 전(검수 완료)일 때만이다 — 재출력의 실패는 돌려주지 않는다.
  (e) 한 상자에서 돌려줄 수 있는 것은 2번까지다.
  (강제 위치: DB 돌려주기 함수 — 복호화 전용 역할만, 상자 잠금 뒤 (b)~(e) / DB 권한 — 기록 표 직접 넣기는 거부 줄만 / DB 제약 — 돌려줌 줄의 연 줄 유일)
  위반 시: 돌려줌 줄을 아무나·몇 번이고 넣을 수 있으면 상한이 사라진다 — 「열고 → 일부러 실패 → 돌려받기」를 되풀이해 주소를 끝없이 연다.
  반대로 돌려주지 않으면 일시 장애 세 번에 그 상자는 송장을 뽑을 수 없어 출고가 막힌다.

- INV-P8: 복호화를 요청할 수 있는 사람은 대표 계정 하나다. 복호화 함수는 요청에 실린 로그인 토큰을
  스스로 검증하고, 그 사용자 ID가 **복호화 함수 자신의 설정**에 적힌 대표 ID와 같을 때만 받는다.
  DB의 역할 컬럼은 판단 근거로 쓰지 않는다. (강제 위치: 복호화 함수 진입부)
  위반 시: 앱 서버를 장악하면 DB의 역할 컬럼을 고쳐 직원 계정을 대표로 만들 수 있다.

- INV-P9: 주소 암호문, 실명, 휴대폰 번호는 API로 노출되지 않는 별도 구역(`pii` 스키마)에만 있다.
  익명·일반 사용자 권한으로는 어떤 경로로도 조회되지 않는다. (강제 위치: DB — 노출 스키마 목록, RLS)
  위반 시: 암호문이라도 대량으로 나가면 나중에 키가 털렸을 때 소급해서 열린다. 실명·번호는 그 자체로 유출이다.

- INV-P10: 주소(평문·암호문), 데이터 키는 서명 원문·알림 본문·애플리케이션 로그·내부 QR 어디에도 들어가지 않는다.
  QR에는 주문번호 문자열만 들어간다. (강제 위치: 각 생성 함수 / 검사: 생성물에 주소 필드가 없음)
  위반 시: 암호화를 우회하는 평문 사본이 생긴다.

- (INV-P11 — 외부 연결 때 확정할 약속이라 `external-connections.md` 로 옮겼다 — 내용은 그대로)

- INV-P12: 클라우드 KMS 를 연결하기 전 임시 복호화(개발용 키 쌍)는 운영 환경에서 동작하지 않는다.
  운영 환경(`VERCEL_ENV=production` 또는 `NODE_ENV=production`)에서 임시 복호화를 만들려 하면 만드는 순간
  실패한다. 개발용 비밀키는 저장소에 커밋되지 않는다(환경 파일은 무시 목록에 있다).
  (강제 위치: 서버 — 임시 복호화 생성 시)
  위반 시: 개발용 비밀키가 운영 앱 서버에 있으면 INV-P2·P3 가 통째로 무너진다 — 앱 서버 하나로 전원 주소가 열린다.

- INV-P13: 크리에이터 주소 등록·변경은 로그인한 크리에이터 **본인의** 주소 칸에만 쓴다. 요청에 담기는 것은 봉인된 주소 하나뿐이고,
  누구의 주소인지는 서버가 세션에서 정한다. 봉인 내용에는 택배 라벨에 필요한 값(받는 사람 이름·전화번호·주소)과 그 크리에이터의
  식별값이 함께 들어간다. 크리에이터 한 명에 주소 하나 — 바꾸면 덮어쓴다. 등록·변경마다 누가·언제·어떤 서명 방식으로 했는지
  한 줄씩 남기고, 그 기록은 추가만 된다(주소 값은 기록에 없다). 카카오 재서명 자리는 로컬에서 가짜 서명 창구(approval-signature
  INV-S11 과 같은 창구)가 대신하고, 운영에서는 창구가 없어 등록·변경이 거부된다.
  (강제 위치: 앱 서버 — 세션의 크리에이터, 창구 고르는 곳 하나 / DB 함수 — 봉인 형식 검사, 크리에이터 역할 확인, 주소 칸과 기록을 한 처리에서)
  위반 시: 남의 주소 칸을 덮어써 그 크리에이터의 선물이 다른 곳으로 간다. 운영에서 비밀번호만으로 주소가 바뀐다.

- INV-P14: 봉인을 연 내용의 크리에이터 식별값이 그 주소 칸의 크리에이터와 다르면, 송장 출력은 그 주소를 쓰지 않는다.
  (강제 위치: 복호화 함수 — 연 뒤 대조) 위반 시: 서버를 장악한 사람이 한 크리에이터의 암호문을 다른 크리에이터 칸에 옮겨 붙여
  선물을 엉뚱한 주소로 보낸다(역조공 reverse-gift INV-R7 b 와 같은 이유).

## 시나리오

- S1 (INV-P1): Given 크리에이터가 주소를 입력 / When 저장 / Then 서버로 가는 요청 본문에 주소 평문 문자열이 없고, 저장된 값은 암호문 형식이다.
- S1b (INV-P1, 실패경로): Given 누군가 API로 평문 주소를 직접 보냄 / When 저장 요청 / Then 형식 오류로 거부되고 아무것도 저장되지 않는다.
- S4 (INV-P4 a): Given 승인 근거가 없는 검수 완료 주문 / When 대표가 송장 출력 / Then 거부, 거부 로그 1줄, 택배사 호출 없음.
- S4b (INV-P4 b): Given 주문 A의 승인 근거 / When 그것을 주문 B의 출력에 붙여 요청 / Then 거부.
- S4c (INV-P4 c): Given 승인됐지만 검수 미완료(또는 거절·반려된) 주문 / When 출력 / Then 거부.
- S5 (INV-P5): Given 상한까지 복호화된 상자 / When 한 번 더 출력 / Then 거부.
- S5c (INV-P5): Given 1회 출력 후 출고 확정된 상자 / When 대표가 재출력 / Then 열리고 「재출력」, 처음 송장번호 그대로, 상자는 출고 확정 그대로.
- S5h (INV-P5, 실패경로): Given 출고 확정 뒤 재출력을 두 번 해 3회를 다 쓴 상자 / When 한 번 더 / Then 거부(상한).
- S5e (INV-P5): Given 상자 4개짜리 주문, 네 상자 모두 검수 완료 / When 상자마다 한 번씩 출력 / Then 네 번 모두 열리고, 기록은 상자마다 첫 출력 한 줄씩.
- S5f (INV-P5, 실패경로): Given 상자 둘 / When 상자 1을 세 번 출력한 뒤 한 번 더, 그리고 상자 2를 출력 / Then 상자 1의 네 번째만 거부, 상자 2는 첫 출력으로 열린다.
- S5g (INV-P5): Given 상자 둘, 상자 1은 한 번 출력하고 출고 확정 / When 상자 1 재출력, 상자 2 출력 / Then 상자 1은 재출력(2번째), 상자 2는 첫 출력으로 열린다.
- S15 (INV-P15): Given 검수 완료 상자, 주소를 연 뒤 송장 마무리 실패 / When 출력 함수가 돌려줌 / Then 횟수 0 으로 돌아오고, 다음 출력은 첫 출력(재출력 아님), 열람 기록에 그 줄이 「출력 실패」.
- S15b (INV-P15, 실패경로 a): Given 복호화 전용 역할 / When 기록 표에 돌려줌 줄을 직접 넣음 / Then 거부.
- S15c (INV-P15, 실패경로 b): Given 이미 돌려준 연 줄 / When 다시 돌려주기 / Then 거부, 횟수 그대로.
- S15d (INV-P15, 실패경로 c): Given 연 줄 둘(앞 줄은 돌려주지 않음) / When 앞 줄을 돌려주기 / Then 거부. 다른 요청자가 돌려주기 / Then 거부.
- S15e (INV-P15, 실패경로 d): Given 송장 출력 단계 상자의 재출력 줄 / When 돌려주기 / Then 거부.
- S15f (INV-P15, 실패경로 e): Given 한 상자에서 두 번 돌려줌 / When 세 번째 돌려주기 / Then 거부 — 그 시도는 횟수에 남는다.
- S5d (INV-P5): Given 2회째 출력 / When 크리에이터가 열람 기록을 봄 / Then 그 줄에 「재출력」 표시가 있다.
- S5b (INV-P5, 동시): Given 복호화가 상한 직전인 상자 / When 출력 요청 두 개가 동시에 들어옴 / Then 복호화는 하나만 일어나고 나머지는 거부된다.
- S7 (INV-P7): Given 성공 1회, 거부 1회 / When 크리에이터가 열람 기록을 봄 / Then 두 줄 모두 보인다.
- S7b (INV-P7, 실패경로): Given 앱 서버 역할 / When 열람 기록 행을 수정·삭제 / Then DB가 거부한다.
- S7c (INV-P7): Given 직원 운영자 / When 출고 화면에서 송장 출력 / Then 403, 그 상자의 열람 기록에 「대표 아님」 거부 줄 1줄, 라벨 없음.
- S8 (INV-P8, 실패경로): Given 직원 계정의 로그인 토큰 / When 복호화 요청 / Then 거부.
- S8b (INV-P8, 실패경로): Given DB에서 직원 계정의 역할을 '대표'로 바꿔 둠 / When 그 계정으로 복호화 요청 / Then 여전히 거부(복호화 함수 설정의 대표 ID와 다름).
- S9 (INV-P9, 실패경로): Given 익명 키와 일반 사용자 토큰 / When 모든 공개 API를 호출 / Then 응답에 주소·실명·전화번호 필드나 그 형태의 값이 없다.
- S10 (INV-P10): Given 승인 요청·알림·QR 생성 / When 각 생성물을 검사 / Then 주소 관련 값이 없고 QR 내용은 주문번호와 정확히 같다.

- S12 (INV-P12): Given 개발 환경과 개발용 키 쌍 / When 브라우저 방식으로 봉인한 주소를 임시 복호화로 엶 / Then 원래 주소가 나온다.
- S12b (INV-P12, 실패경로): Given 운영 환경 표시 / When 임시 복호화를 만들려 함 / Then 즉시 실패하고 키를 읽지 않는다.

- S13 (INV-P13): Given 로컬, 크리에이터 하루 / When 주소를 등록 / Then 하루의 주소 칸에 봉인된 주소, 기록 한 줄(방식 fake), 설정 화면에 「등록됨」.
- S13b (INV-P13, 실패경로): Given 하루 / When 평문 주소·봉인 형식이 아닌 값을 보냄 / Then 거부, 아무것도 안 바뀜.
- S13c (INV-P13, 실패경로): Given 팬·운영자·로그인 안 함 / When 주소 등록 / Then 거부. 본문에 다른 크리에이터 값을 붙여도 하루의 칸에만 쓴다.
- S13d (INV-P13, 실패경로): Given 운영 환경 표시 / When 주소 등록 / Then 창구가 없어 거부.
- S13e (INV-P13): Given 주소가 등록된 하루 / When 다시 등록 / Then 주소 칸은 하나(새 값), 기록은 두 줄. 기록 고치기·지우기는 거부.
- S14 (INV-P14, 실패경로): Given 달빛의 봉인 주소를 하루의 칸에 옮겨 붙임 / When 하루 주문의 송장 출력 / Then 주소를 쓰지 않는다.

## 신뢰 경계

- 믿는 값: 복호화 함수 자신의 설정(대표 ID, KMS 접근 자격), 복호화 함수가 스스로 검증한 로그인 토큰과 승인 서명
- 믿지 않는 값: 앱 서버가 넘기는 모든 값(주문 상태 제외 — 아래), 브라우저 입력, DB의 역할 컬럼,
  택배사 API 응답(형식 검증 후 사용)
- 주문 상태(검수 완료·거절 여부)는 앱 서버가 쓰는 DB 값이라 앱 서버를 장악하면 위조할 수 있다.
  그래도 (a)·(b)가 따로 막으므로 위조로 얻는 것은 "승인된 건을 검수 전에, 또는 상한 안에서 출고 뒤에 여는 것"뿐이고
  그것도 매번 열람 기록에 남아 크리에이터에게 보인다.

## 비범위

- 크리에이터 기기 해킹·피싱으로 승인을 빼앗기는 경우 — 피해는 그 크리에이터·그 건으로 한정된다
- 앱 서버를 장악한 공격자가 **승인된 건**의 라벨 이미지를 가로채는 것 — 원본 설계가 받아들인 남은 위험
- 팬의 반송 주소 처리 — 검수·반송 스펙에서 다룬다
- 로그인·재서명 절차 자체 — 계정 스펙
- 승인 서명의 생성·검증 절차 — `approval-signature.md`
