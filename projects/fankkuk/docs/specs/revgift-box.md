# 팬에게 보내기 — 선물함 스펙

크리에이터가 선물함을 만들어 팔로워의 신청을 받고, 마감한 뒤 팬마다 닉네임을 적거나 번호 라벨을 붙인 선물을 **큰 상자 하나**(여러 개도 됨)에 담아
팬꾹으로 보낸다. 사무실은 상자를 열어 선물마다 실측하고, 크리에이터에게 명세서를 보내 **한 번** 결제받은 뒤 팬마다 송장을 출력해 보낸다.
지금 역조공(`reverse-gift.md`)과 다른 점은 셋이다 — 받는 팬을 크리에이터가 고르지 않고 팬이 신청하며, 결제가 등록 때가 아니라 실측 뒤이고,
사무실 주소 6자리가 팬 몫마다가 아니라 선물함마다 하나다.

어기면 생기는 사고는 다섯이다.
- 크리에이터(또는 아무나)에게 팬 주소·실명·번호가 보인다.
- 팔로우하지 않은 사람·초대받지 않은 사람이 신청하거나, 받을 인원보다 많은 신청이 들어간다.
- 결제하지 않은 선물이 나가거나, 같은 명세서가 두 번 결제·환불된다.
- 초기 크리에이터 51번째가 생기거나 한 달 31건째에 300원이 붙는다.
- 결제가 없는 선물함이 선반에 끝없이 쌓이거나, 반송할 선물함의 팬 주소가 남는다.

용어
- **선물함**: 크리에이터가 한 번에 하는 팬에게 보내기. 명세서 하나·결제 하나·사무실 주소 6자리 하나가 붙는다.
- **신청**: 선물함 안에서 팬 한 명 몫. 받을 주소 사본 하나·번호 라벨 하나·(결제 뒤) 송장 하나가 붙는다. 「선물」은 그 몫으로 들어온 물건이다.
- **큰 상자**: 크리에이터가 팬꾹으로 보내는 상자. 선물함 하나에 하나 이상.
- **명세서**: 실측이 끝난 뒤 서버가 만드는 결제 요청. 팬 줄마다 구간·택배비·서비스료·할증이 있다.

## 불변식

### 상태

- INV-GB1: 선물함의 상태는 아래 전환표의 한 칸씩만 움직인다. 표에 없는 전환은 거부한다. 상태를 직접 고르는 화면·API 는 없다.
  | 지금 | 일어난 일 | 다음 | 거부 조건 |
  |---|---|---|---|
  | (없음) | 크리에이터가 만들기(INV-GB3) | `open` 신청 받는 중 | 크리에이터 역할이 아님 · 입력 꼴이 틀림 |
  | `open` | 크리에이터가 마감(INV-GB8) | `closed` 마감 · 상자 고르기 | 제외 안 된 신청 0명 |
  | `open` | 크리에이터가 선물함 취소 | `cancelled` 취소(끝) | — |
  | `closed` | 크리에이터가 모든 신청에 구간을 고르고 「다음」 | `awaiting_box` 상자 보내 주세요 | 구간 없는 신청이 있음 |
  | `closed`·`awaiting_box` | 크리에이터가 선물함 취소(큰 상자가 하나도 입고되기 전) | `cancelled` | 큰 상자가 하나라도 입고됨 (추천안 — 정할 것 Q9) |
  | `awaiting_box` | 사무실이 이 선물함 6자리로 큰 상자 입고(INV-GB10) | `arrived` 도착 · 실측 중 | — |
  | `awaiting_box` | 큰 상자가 하나도 오지 않은 채 기한(추천안 — 정할 것 Q10) | `cancelled` | — |
  | `arrived` | 확인 필요 선물이 생김(INV-GB12) | `held` 확인 필요 | — |
  | `held` | 확인 필요 선물이 모두 풀림 | `arrived` | — |
  | `arrived` | 실측·도착 판정이 끝남(INV-GB11·GB12) | `invoiced` 결제 요청 | 확인 필요 선물이 남음 · 아직 올 큰 상자가 있고 7일이 안 지남 |
  | `invoiced` | 명세서 발행 + 72시간 | `overdue` 결제 기한 지남 | — |
  | `invoiced`·`overdue` | 결제 완료(INV-GB18) | `paid` 발송 중 | — |
  | `overdue` | 명세서 발행 + 168시간, 결제 없음(INV-GB19) | `returning` 착불 반송 | 결제 「승인 중」이 있음 |
  | `returning` | 반송 확정 | `returned` 반송됨(끝) | — |
  | `paid` | 모든 팬 줄이 출고·환불·도착 안 함 중 하나로 끝남 | `done` 끝 | — |
  1페이지 설명은 화면이지 상태가 아니다 — 저장되는 것이 없다. 모든 시각은 서버 시각, 시간은 경과 시간(시간대 무관, office-workflow INV-W6 과 같다).
  (강제 위치: DB 전환 함수 — 지금 상태 확인과 바꾸기가 한 처리 / 기한 전환은 DB 예약 작업, office-workflow INV-W11)
  위반 시: 결제 전 선물함이 발송 단계로 넘어가거나, 끝난 선물함에 다시 신청·입고가 붙는다.

- INV-GB2: 신청(팬 한 명 몫)의 상태는 다음 칸씩만 움직인다 —
  `applied` 신청 ⇄ `excluded` 제외(선물함이 `open` 일 때만 오감) → (마감) `selected` 담길 차례 → `measured` 실측됨 / `missing` 도착 안 함 / `rejected` 보낼 수 없음(금지 물품, 정할 것 Q12)
  → (결제) `paid` → `shipped` 출고 → `delivered` 배송 완료. 마감 때 `excluded` 는 그대로 끝난 상태가 되고, 선물함이 취소·반송되면 끝나지 않은 신청은 같은 처리에서 함께 끝난다.
  한 신청의 상태가 바뀌어도 같은 선물함의 다른 신청은 그대로다(도착 안 함·보낼 수 없음 한 줄이 명세서 전체를 막지 않는다).
  (강제 위치: DB 전환 함수 — 선물함 줄을 먼저 잠그고 신청 줄을 잠근 뒤 판정, office-workflow INV-W12 의 순서)
  위반 시: 한 팬의 선물이 오지 않았다고 선물함 전체가 멈추거나, 제외한 팬에게 선물이 나간다.

### 만들기·신청

- INV-GB3: 선물함은 크리에이터 역할 계정만 자기 이름으로 만든다(누구의 선물함인지는 로그인 토큰으로 정한다, session-login INV-L2).
  만들 때 받는 값은 셋뿐이다 — 이름(1~40자, 추천안 — 정할 것 Q3) · 받을 인원(1 이상 100 이하 정수) · 공개/비공개.
  비공개면 서버가 추측할 수 없는 초대 토큰을 만든다(6자리·주문번호와 다른 값). 받을 인원·공개 여부를 만든 뒤에 바꿀 수 있는지는 정할 것 Q3.
  (강제 위치: DB 만들기 함수 — 역할 판정·꼴 검사 / DB 제약 — 받을 인원 1~100)
  위반 시: 팬 계정이 선물함을 만들어 다른 팬의 주소를 모으거나, 101명 이상이 신청해 한 선물함의 실측·출고가 감당되지 않는다.

- INV-GB4: 신청은 **신청하는 순간** 그 선물함 크리에이터를 팔로우하고 있는 팬 계정만 한다. 크리에이터 계정·선물함 주인 자신·팔로우하지 않은 계정은 거부한다.
  공개 선물함은 크리에이터 상세 페이지의 입구로, 비공개 선물함은 유효한 초대 토큰이 있는 링크로만 신청한다 — 비공개 선물함은 토큰 없이 찾을 길이 없고,
  토큰이 틀리거나 없으면 「없음」과 같은 답이다. 팔로우하지 않은 사람이 열면 「팔로우한 팬만 신청할 수 있습니다」와 팔로우 버튼만 보인다(신청 폼은 열리지 않는다).
  한 선물함에 같은 팬의 신청은 하나다. 판정은 서버가 팔로우 표를 직접 읽어서 하고, 팔로우 끊기와 신청이 겹치면 팔로우 줄을 잠근 뒤 판정한다
  (reverse-gift INV-R1 과 같다). 신청한 뒤 팔로우를 끊어도 신청은 그대로다(추천안 — 정할 것 Q2).
  차단(`decline-block.md`)은 신청 자격에 영향이 없다(reverse-gift INV-R2 와 같은 판단 — 차단 사실을 드러내지 않는다, 정할 것 Q2).
  (강제 위치: DB 신청 함수 — 로그인 토큰으로 팬 판정, 팔로우 줄 잠금 뒤 판정, 토큰 대조 / DB 제약 — 선물함·팬 유일)
  위반 시: 팔로우하지 않은 사람이 크리에이터에게 닉네임을 드러내며 선물을 받아 가거나, 비공개 선물함이 링크 없이 열린다. 한 팬이 두 몫을 받는다.

- INV-GB5: 제외되지 않은 신청 수는 받을 인원을 넘지 않는다. 다 차면 새 신청과 「다시 넣기」를 거부하고(추천안 — 정할 것 Q1),
  제외된 신청은 자리를 차지하지 않는다. 마지막 한 자리에 신청 둘(또는 신청과 다시 넣기)이 동시에 와도 하나만 들어간다 — 선물함 줄을 잠근 뒤 센다.
  (강제 위치: DB 신청·다시 넣기 함수 — 선물함 줄 잠금 뒤 개수 확인과 넣기가 한 처리)
  위반 시: 받을 인원 30명 선물함에 31명이 들어가 크리에이터가 준비한 선물보다 신청이 많아진다.

- INV-GB6: 신청 폼은 받는 분 이름·휴대폰 번호·주소 세 가지를 신청할 때마다 입력한다(2026-11-08 사용자 「선물 신청마다 주소를 입력하게 해라」 —
  팬 등록 주소는 없다, address-protection INV-P17). 설정에 저장해 둔 주소에서 고르는 길도, 가입 번호를 쓰는 길도 없다(정할 것 Q4 는 없어짐).
  셋은 팬 브라우저에서 그 팬의 계정 식별값과 함께 봉인된 뒤에만 서버로 간다(address-protection INV-P1, reverse-gift INV-R5 와 같은 방식·같은 보관 키).
  할증 구분(「할증 없음 / 제주 / 도서」)은 address-protection INV-P20 ② 대로 브라우저가 계산해 봉인과 함께 보내고, 서버는 우편번호를 받지 않는다.
  봉인이 없거나 봉인 꼴이 아닌 신청은 거부한다. 신청한 순간의 봉인이 그 신청의 사본이 된다(업계 표준 — 주문 때 배송지를 고정한다).
  주소는 신청하는 팬 본인만 넣는다. 선물함 크리에이터·관리자 화면에는 신청의 주소를 넣거나 바꾸는 경로가 없다. 선물함이 `open` 이 아니면 주소를 넣을 수 없다.
  (강제 위치: 클라이언트 — 전송 전 봉인 / DB 신청 함수 — 본인 판정·봉인 꼴 검사(없으면 거부)·구분 꼴 검사·사본 저장이 한 처리 / 주소 사본은 `pii` 구역, INV-P9)
  위반 시: 주소 평문이 서버를 지나 로그에 남거나, 다른 사람이 팬 대신 주소를 넣어 선물을 가로챈다.

- INV-GB7: 신청 관리 창(목록·검색·초대 링크·마감·선물함 취소)은 선물함 주인 본인만 연다. 제외는 줄마다 체크 토글이고, 다시 누르면 다시 넣는다(INV-GB5 상한 안에서).
  제외·다시 넣기는 선물함이 `open` 일 때만 된다. 제외된 줄은 흐리게 목록에 남는다. 팬이 신청을 거둘 수 있는지는 정할 것 Q5.
  신청 사본의 주소는 제외해도 `open` 동안은 지우지 않고(다시 넣기 때 다시 받지 않으려고), 마감·선물함 취소 처리에서 제외된 신청의 사본을 지운다(추천안 — 정할 것 Q5).
  (강제 위치: DB 제외·다시 넣기 함수 — 로그인 토큰으로 주인 판정, 선물함 상태 확인)
  위반 시: 다른 크리에이터가 남의 선물함 신청을 빼거나 넣고, 마감 뒤에 제외가 바뀌어 담기지 않은 팬이 명세서에 오른다.

- INV-GB8: 마감은 선물함 주인이 `open` 일 때만, 제외 안 된 신청이 1명 이상일 때 한다. 마감과 신청이 겹치면 선물함 줄을 잠근 쪽이 먼저다 —
  마감보다 먼저 끝난 신청은 들어가고, 마감 뒤에 온 신청은 거부된다. 마감 뒤에는 새 신청·제외·다시 넣기가 없다.
  (강제 위치: DB 마감 함수 — 선물함 줄 잠금, 신청 함수와 같은 잠금)
  위반 시: 마감 직후 들어온 신청이 구간 고르기 목록에 없는데 명세서에는 올라, 선물 없는 팬 줄에 돈이 청구된다.

- INV-GB9: 크리에이터는 신청한 팬의 주소·받는 분 이름·전화번호·로그인 아이디를 어떤 경로로도 받지 못한다. 크리에이터에게 보이는 팬 정보는
  닉네임·신청 시각·신청 상태, 그리고 명세서의 팬 줄마다 할증 구분(「제주」「도서」 — 지역 이름보다 넓지 않음, 사용자 결정 2026-11-07)뿐이다.
  팬 몫의 운송장 번호도 보이지 않는다(reverse-gift INV-R8 과 같은 이유). 번호 라벨 PDF 에는 닉네임과 바코드만 있다.
  팬에게는 다른 신청자의 존재·수·닉네임이 보이지 않는다(추천안 — 정할 것 Q6).
  팬 주소(평문·암호문)·6자리는 알림 본문·애플리케이션 로그·바코드·크리에이터 화면 어디에도 들어가지 않는다 — 바코드에는 신청 번호만 있다(reverse-gift INV-R12 와 같다).
  (강제 위치: DB — 크리에이터용 선물함·신청·명세서 읽기 함수의 반환 칸 / 주소 사본은 `pii` 구역 / 라벨 생성 함수 / 알림 본문 틀)
  위반 시: 선물함이 크리에이터가 팬 주소를 모으는 통로가 된다. 운송장 번호로 택배사 조회를 하면 받는 곳 일부가 보인다.

### 큰 상자·실측

- INV-GB10: 사무실 주소 6자리는 선물함마다 하나다. `closed` → `awaiting_box` 처리에서 inbound-address-code INV-C1 의 글자·확인 문자·겹침 규칙으로 발급하고,
  선물함 주인 본인에게만 보인다(INV-C2 — 기본은 가리고 눌러야 보임, 「주소 한 번에 복사」는 6자리 포함). 결제 전에 발급하는 유일한 6자리다(팬 선물·옛 역조공은 결제 뒤).
  같은 6자리로 큰 상자를 몇 개든 입고한다. 6자리가 무효가 되는 때는 선물함 취소·명세서 발행·반송(추천안 — 정할 것 Q7)이고, 무효가 된 뒤 온 상자는 보류(INV-C6)로 간다.
  번호 라벨 PDF 는 `awaiting_box` 부터 주인 본인만 받고, 선택된 신청마다 라벨 하나(닉네임 + 신청 번호 바코드)다. 사무실은 선물마다 바코드를 스캔해 신청을 찾고, 그 라벨을
  사무실 내부 라벨로 그대로 쓴다. 손글씨 닉네임 선물에만 사무실이 라벨을 출력한다(손글씨는 선택된 신청 목록에서 닉네임으로 찾는다).
  (강제 위치: DB — 6자리 발급이 상태 전환과 같은 처리, 6자리 칸 꼴·겹침 / 읽기 함수 — 주인일 때만 6자리·라벨)
  위반 시: 6자리를 본 사람이 같은 주소로 상자를 보내 남의 선물함에 이어 붙이거나, 다른 선물함의 바코드로 선물이 엉뚱한 팬 줄에 실측된다.

- INV-GB11: 여러 상자 — 크리에이터는 3페이지에서 「보낸 상자 수」(1 이상 정수)를 적는다. 적은 수만큼 큰 상자가 입고되고 선택된 신청이 모두 실측되면 명세서를 만든다.
  첫 큰 상자 입고 시각부터 168시간 안에 실측되지 않은 신청은 `missing` 도착 안 함으로 빼고 나머지만으로 명세서를 만든다(사용자 결정 ⓓ). 선택된 신청이 모두 `missing`·`rejected`
  이면 명세서를 만들지 않는다(그 뒤 처리는 정할 것 Q12). `missing` 이 된 신청의 주소 사본은 같은 처리에서 지운다. 보낸 상자 수를 고칠 수 있는지는 정할 것 Q8.
  (강제 위치: DB 예약 작업 — 168시간 판정과 명세서 생성이 한 처리, 선물함 줄 잠금)
  위반 시: 오지 않을 선물 하나 때문에 선물함 전체가 결제·발송되지 않거나, 오지 않은 선물에 택배비가 청구된다.

- INV-GB12: 실측은 선물(신청)마다 한다 — 세 변 합과 무게 중 큰 쪽으로 구간을 정한다(극소형 80cm·2kg · 소형 100cm·5kg · 중형 120cm·10kg · 대형 140cm·15kg, admin-console INV-K15 의 구간).
  명세서에는 크리에이터가 고른 구간이 아니라 실측 구간을 적는다 — 고른 구간보다 작아도 크게 적지 않는다. 대형을 넘으면 개인접수(INV-GB16).
  닉네임·바코드가 선택된 신청과 맞지 않는 선물은 「확인 필요」로 두고, 크리에이터 처리할 일에 카드 한 장(선물함 이름 · 선물 사진 · 작성한 닉네임 · 팬 선택하기 · 확인)이 생긴다.
  「빼기」는 없다. 크리에이터가 고를 수 있는 팬은 그 선물함의 선택된 신청뿐이고, 고르면 그 신청의 선물로 실측된다. 이미 선물이 있는 신청을 고를 때와 확인 필요의 기한은 정할 것 Q11.
  확인 필요 선물이 남은 동안에는 명세서를 만들지 않는다.
  (강제 위치: DB 실측 기록 함수 — 구간 판정 / DB 팬 선택 함수 — 로그인 토큰으로 주인 판정, 같은 선물함의 선택된 신청만)
  위반 시: 작은 구간 값으로 큰 선물이 나가 택배비만큼 손해가 나거나, 크리에이터가 다른 선물함의 팬(또는 신청하지 않은 팬)을 골라 그 팬 주소로 선물이 간다.

### 금액

- INV-GB13: 명세서 금액은 서버가 **명세서를 만드는 순간의** 설정값으로 계산해 저장하고, 그 뒤 설정값이 바뀌어도 다시 계산하지 않는다(admin-console INV-K3 과 같은 원칙).
  2페이지의 예상 금액은 표시일 뿐 판단 근거가 아니다. 명세서 = 팬 줄마다 [실측 구간 택배비(INV-K15 의 팬에게 보내기 택배비) 또는 개인접수 실비(INV-GB16)]
  + [서비스료(INV-GB14·GB15 — 정가 700원, 초기 크리에이터 300원)] + [할증(INV-GB17)] 의 합 + 착불로 받은 큰 상자 택배비의 합.
  착불 큰 상자 택배비는 입고 때 운영자가 그 상자의 착불 금액(원)을 넣고, 0 이상 정수만 받는다(상한은 정할 것 Q13). 선불로 온 상자는 0 이다.
  결제 기록은 칸을 나눠 저장한다 — 배송비 칸(택배비·개인접수 실비·할증·착불 큰 상자 택배비) · 기본 서비스료 칸(서비스료) · 검수비 칸 0 · 상품 대금 칸 0, 네 칸의 합 = 결제 금액
  (payment INV-M7 과 같은 꼴, 착불 큰 상자 택배비를 배송비 칸에 넣는 것은 추천안 — 정할 것 Q13). 팬 줄마다 같은 칸을 저장하고 줄 칸의 합(+ 착불 큰 상자 택배비) = 명세서의 같은 칸이다.
  크리에이터에게는 팬 줄의 구간·택배비·서비스료·할증과 합계만 보이고, 택배사 계약 원가는 보이지 않는다(확정 17).
  (강제 위치: DB 명세서 생성 함수 — 계산·저장 한 처리 / DB 제약 — 칸 합 일치 / 서버 — 운영자 입력 검사)
  위반 시: 브라우저나 운영자가 고친 금액이 청구되거나, 요금표를 바꾼 뒤 낸 돈과 다른 금액이 보여 다툼이 생긴다.

- INV-GB14: 초기 크리에이터는 채널 확인을 마친 순서로 앞선 50명이다(사용자 결정 2026-11-07 ③). 순번은 채널 확인 승인 처리(creator-verification INV-V7 — 운영자 승인·로그인 확인 모두)
  안에서 매기고, 한 번 매긴 순번은 바뀌지 않는다. 50번째 자리에 승인 둘이 동시에 와도 순번 1~50 은 계정마다 하나씩, 50 을 넘는 순번은 초기 크리에이터가 아니다 —
  순번 카운터 줄을 잠근 뒤 매긴다. 승인 취소·재승인 때 순번을 다시 주거나 빈 자리를 채우는지는 정할 것 Q14(추천안: 다시 주지 않고 채우지 않는다).
  이 기능을 켜기 전에 이미 채널 확인을 마친 크리에이터는 승인 기록의 시각 순으로 같은 규칙에 따라 순번을 받는다(동시각은 승인 기록 순서).
  초기 크리에이터 혜택 기간은 채널 확인일(순번을 받은 승인 시각)부터 3개월이다(달력 3개월인지 90일인지는 정할 것 Q14). 기간 안인지는 명세서를 만드는 순간으로 본다.
  출시 기념 요금(F-25) 자체는 여전히 적용하지 않는다 — 50명·3개월 기준만 가져왔다.
  (강제 위치: DB — 승인 처리 안에서 카운터 잠금·순번 저장, 순번 칸 유일·1~50 / 명세서 생성 함수가 순번·기간을 읽음)
  위반 시: 51번째 크리에이터에게 300원이 붙어 건마다 400원씩 덜 받거나, 같은 순번을 두 명이 쥔다.

- INV-GB15: 초기 크리에이터의 300원 서비스료는 한 달 30건까지다. 1건 = 명세서의 팬 줄 하나다. 명세서를 만드는 순간 그 달 남은 건수만큼의 팬 줄에 300원을,
  나머지 팬 줄에 700원을 적고, 적은 건수를 그 달 사용으로 센다(추천안 — 「달」의 기준(KST 달력 달)·결제 없이 반송된 명세서의 건수를 돌려주는지는 정할 것 Q15).
  한 크리에이터의 명세서 둘이 동시에 만들어져도 그 달 300원 줄의 합은 30 을 넘지 않는다 — 그 크리에이터의 월 사용 줄을 잠근 뒤 센다.
  (강제 위치: DB 명세서 생성 함수 — 월 사용 줄 잠금, 세기와 적기가 한 처리 / DB 제약 — 월 사용 ≤ 30)
  위반 시: 두 선물함의 실측이 같은 때 끝나 31건째에도 300원이 붙는다.

- INV-GB16: 개인접수 — 선물의 실측이 대형(140cm·15kg)을 넘으면 운영자가 그 선물의 우체국 실비(원)를 넣고, 그 팬 줄의 금액은 실비 + 서비스료(INV-GB14·GB15)다
  (요금 11-07 최종 ②). 실비는 대형 팬에게 보내기 택배비 이상, 100,000원 이하 정수만 받는다(payment INV-M23 ① 과 같은 범위 — 추천안, 정할 것 Q13). 실비 없이 대형 초과를 기록하면 거부한다.
  크리에이터 명세서에는 그 줄을 「개인접수」로 보여 준다.
  (강제 위치: DB 실측 기록 함수 — 판정·실비 검사 / 서버 — 운영자 입력 검사)
  위반 시: 받을 수 없는 크기의 선물이 대형 요금으로 나가 택배비만큼 손해가 나거나, 운영자가 잘못 넣은 금액이 그대로 청구된다.

- INV-GB17: 제주·도서 할증은 팬 줄마다 따로다 — 명세서를 만드는 순간 그 신청에 복사된 주소의 할증 구분(INV-GB6)을 읽어, 「제주」면 제주 할증, 「도서」면 도서 할증
  (설정값 — 첫 값 제주 4,000 · 도서 5,000, payment INV-M24 와 같은 설정)을 그 줄에 더한다. 실비와의 차이는 정산하지 않는다. 신청의 주소는 신청 때 고정되므로 결제 뒤 다시 받거나 돌려주지 않는다.
  송장 출력 때 다시 판정한 구분이 저장값과 다르면 출력은 그대로 하고 운영자 화면에 「할증 지역 불일치」만 남긴다(address-protection INV-P20 ③).
  구분 읽기는 명세서 생성 함수 안에서만 하고, 크리에이터에게는 명세서 줄의 구분 표시로만 나간다(INV-GB9).
  (강제 위치: DB 명세서 생성 함수(공개 구역)가 `pii` 의 구분 읽기 함수를 부름)
  위반 시: 제주·도서 팬에게 가는 상자마다 택배비가 모자라거나, 크리에이터가 아무 팬의 지역을 알아내는 함수가 생긴다.

### 결제·반송·발송

- INV-GB18: 명세서 하나에 결제 완료는 하나다. 결제는 `invoiced`·`overdue` 일 때 선물함 주인 본인만 시작하고, 금액은 저장된 명세서 금액이다(payment INV-M2·M3·M5 와 같은 검증).
  미리 결제하는 길은 없다 — 명세서 전에는 결제를 시작할 수 없다. 결제 기한은 명세서 발행 + 72시간이고, 지나도 168시간 전까지는 결제할 수 있다(`overdue`).
  결제 대기는 만든 지 24시간이 지나면 닫히지만(payment INV-M15 와 같은 규칙) 명세서는 그대로 남아 다시 결제할 수 있다.
  같은 명세서의 결제 확정이 두 번·동시에 와도 결제 완료는 하나다.
  (강제 위치: DB 결제 대기 생성·확정 함수 — 명세서 상태 확인, 명세서마다 결제 완료 유일 / 서버 — 결제사 응답 대조)
  위반 시: 같은 명세서에 돈이 두 번 나가거나, 실측 전 금액으로 결제돼 차액이 생긴다.

- INV-GB19: 명세서 발행 + 168시간까지 결제가 없으면 자동 처리가 선물함을 `returning` 으로 바꾸고 큰 상자의 선물을 크리에이터에게 착불로 돌려보낸다(확정 14).
  결제 「승인 중」(결제사 승인을 부른 뒤 결과를 기다리는 것)이 있으면 바꾸지 않는다 — 결과가 정해진 뒤 다시 본다(payment INV-M19 와 같은 이유).
  반송 전환과 결제 확정 시작이 겹치면 선물함 줄을 잠근 쪽 하나만 반영된다 — 반송이 먼저면 결제 시작은 거부되고, 결제 시작이 먼저면 반송하지 않는다.
  같은 처리에서 모든 신청의 주소 사본을 지우고(지운 기록은 남고 값은 없음) 6자리를 무효로 한다. 반송 주소를 어디로 할지(원 송장 주소·등록 주소·확인 받기)는 정할 것 Q16.
  (강제 위치: DB 예약 작업 — 조건부 갱신 한 문장, 선물함 줄 잠금 / DB 결제 확정 시작 함수 — 같은 잠금)
  위반 시: 돈은 나갔는데 선물이 크리에이터에게 돌아가거나, 결제 없는 선물이 선반에 끝없이 쌓인다. 반송될 선물함의 팬 주소가 남는다.

- INV-GB20: 팬 주소는 결제가 끝난 선물함의 `paid` 신청에서만, 출고 스캔 때 송장 한 장마다 연다(사용자 결정 ⓒ — 주소 열기 1회). 복호화 함수의 조건은 reverse-gift INV-R7 과 같다 —
  (a) 그 신청에 주소 사본이 있다 (b) 봉인 속 계정 식별값이 그 신청의 팬과 같다 (c) 신청이 `paid` 이거나 출고 확정 뒤 사본이 남은 재출력이다
  (d) 요청자가 대표 계정이다. 한 신청에 최대 3회, 돌려주기·기록·팬 열람 기록은 reverse-gift INV-R13·R16 과 같다. 응답에는 라벨 이미지와 운송장 번호만 있다.
  사본은 그 신청의 선물이 끝나면 지운다(2026-11-08 사용자 「선물이 완전히 끝나면 주소는 파기」). 「끝남」은 옛 역조공 몫 사본을 지우는 판정(reverse-gift INV-R9)을 그대로 쓴다 —
  출고된 신청은 택배사 집하 확인 때, 연결 전에는 출고 확정 + 72시간(팬꾹에는 배송 완료 기록이 없어 이것을 배송이 끝난 때로 본다). 신청 취소·제외 확정(마감)·선물함 취소·반송·처분·
  도착 안 함·환불된 신청은 그 처리에서 지운다. 팬 등록 주소는 없다(address-protection INV-P17).
  (강제 위치: 복호화 함수 진입부, 복호화보다 먼저 / 상태를 바꾸는 함수가 같은 처리에서 사본 삭제)
  위반 시: 결제하지 않은 선물함, 다른 신청의 주소가 열리거나 같은 주소를 몇 번이고 다시 꺼낸다. 배송이 끝난 주소가 쌓여 키가 털렸을 때 소급해 열린다.

- INV-GB21: 환불·취소 — 환불 금액은 서버가 신청(팬 줄) 상태로 정하고, 브라우저나 관리자가 금액을 넣지 않는다(payment INV-M8 과 같은 원칙).
  ① 결제 전(만들기~명세서~반송)은 결제가 없어 환불이 없다. 결제 전 취소는 INV-GB1 표의 선물함 취소뿐이다.
  ② 결제 뒤 출고 전에 그 팬 줄을 보낼 수 없게 되면(어떤 경우인지는 정할 것 Q17) 그 줄 금액(택배비·서비스료·할증)을 돌려준다. 착불 큰 상자 택배비는 돌려주지 않는다.
  ③ 출고 뒤에는 환불하지 않는다(payment INV-M8 「출고 뒤」 줄과 같다).
  한 명세서의 환불 합계는 결제 금액을 넘지 않고, 같은 줄의 환불이 두 번·동시에 와도 한 번만 나간다(payment INV-M9 — 줄마다 환불 하나, 환불마다 멱등 키).
  초기 크리에이터 건수(INV-GB15)를 환불된 줄만큼 돌려주는지는 정할 것 Q15.
  (강제 위치: 서버 — 환불 금액 계산 / DB 제약 — 줄마다 환불 하나·환불 합계)
  위반 시: 한 팬 줄이 두 번 환불되거나, 출고된 선물까지 돌려줘 돈이 샌다.

### 옛 흐름

- INV-GB22: 이 스펙이 승인되면 옛 보내기 화면(팔로워 체크로 고르기·몫마다 등록 때 결제, reverse-gift INV-R2·R3·R15)과 「합포장」 메뉴를 닫는다 — 새 보내기를 만드는 길이 선물함 하나뿐이다.
  닫기 전에 결제된 옛 보내기는 끝날 때까지 reverse-gift 스펙 그대로 진행한다(받기 기한·몫 6자리·환불 모두 — 이미 낸 주문은 낸 때의 규칙, 업계 표준).
  (강제 위치: 서버 — 옛 보내기 등록 함수가 새 등록을 거부 / 화면 — 사이드바 「팬에게 보내기」 한 줄)
  위반 시: 같은 크리에이터에게 등록 때 결제와 실측 뒤 결제가 섞여 금액·환불 규칙이 엇갈린다.

- INV-GB23: 취소한 선물함의 6자리로 상자가 오면 — 그 상자는 보류(inbound-address-code INV-C6)로 들어가되, 6자리로 선물함을 알 수 있으므로 같은 처리에서 그 크리에이터에게
  처리할 일 카드 「취소한 선물함의 상자가 도착했어요」를 띄운다. 고르는 것은 둘 — 「선물함 다시 열기」(취소 전 마감 상태·같은 신청자로 돌아가고, 취소 때 지운 주소는 신청자가
  다시 입력해야 그 줄이 발송 대상이 된다) · 「돌려받기」(원 송장 보내는 사람 주소로 착불 반송). 카드를 띄운 때부터 7일(168시간) 안에 고르지 않으면 「돌려받기」와 같다.
  30일 보관(INV-C6)을 기다리지 않는다. 다시 열기는 선물함 주인 본인만, 한 번만.
  (강제 위치: DB — 입고 함수가 취소 선물함의 6자리를 알아보고 카드 생성 / 선택 함수 / 자동 처리)
  위반 시: 주인이 분명한 상자를 30일 동안 사무실에 쌓아 두거나, 취소한 선물함이 크리에이터 모르게 다시 진행된다.

## 시나리오

- S1 (INV-GB1): Given 하루의 선물함 `open` / When 마감 → 구간 다 고르고 다음 → 큰 상자 입고 → 실측 끝 / Then `closed` → `awaiting_box` → `arrived` → `invoiced` 순서로만 바뀐다.
- S1b (INV-GB1, 실패경로): Given `open` 선물함 / When API 로 `paid` 로 바꾸려 함 / Then 그런 길이 없다. `awaiting_box` 에서 결제 시작 / Then 거부(명세서 없음).
- S1c (INV-GB1, 실패경로): Given `closed` 선물함, 구간 없는 신청 하나 / When 다음 / Then 거부, 그대로 `closed`.
- S2 (INV-GB2): Given 신청 셋 중 별빛이 `missing` / When 명세서 생성 / Then 나머지 둘만 명세서에 오르고 별빛 줄은 없다.
- S2b (INV-GB2, 실패경로): Given 마감된 선물함의 제외된 달토끼 / When 다시 넣기 / Then 거부.
- S3 (INV-GB3): Given 크리에이터 하루 / When 이름 「겨울 선물」·받을 인원 30·비공개로 만들기 / Then `open`, 초대 토큰이 생긴다.
- S3b (INV-GB3, 실패경로): Given 하루 / When 받을 인원 0 또는 101 / Then 거부. 팬 별빛이 만들기 / Then 거부.
- S4 (INV-GB4): Given 하루를 팔로우한 별빛, 하루의 공개 선물함 / When 하루 상세의 입구로 신청 / Then 신청 하나.
- S4b (INV-GB4, 실패경로): Given 팔로우하지 않은 달토끼 / When 신청 API 를 직접 부름 / Then 거부. 화면은 「팔로우한 팬만 신청할 수 있습니다」와 팔로우 버튼만.
- S4c (INV-GB4, 실패경로): Given 비공개 선물함 / When 팔로워 별빛이 토큰 없이 또는 틀린 토큰으로 엶 / Then 「없음」과 같은 답, 신청 거부.
- S4d (INV-GB4, 실패경로): Given 별빛이 이미 신청함 / When 다시 신청 / Then 거부. 하루 자신·크리에이터 모모가 신청 / Then 거부.
- S4e (INV-GB4, 동시): Given 달토끼의 팔로우 끊기가 아직 끝나지 않음 / When 그 사이 신청 / Then 끊기가 끝날 때까지 기다렸다가 거부.
- S5 (INV-GB5, 동시): Given 받을 인원 2, 신청 1 / When 별빛·구름빵 신청이 동시에 / Then 하나만 들어가고 다른 하나는 「다 찼어요」로 거부.
- S5b (INV-GB5): Given 받을 인원 2, 신청 2 중 하나 제외 / When 새 신청 / Then 들어간다. 그 뒤 제외한 줄 다시 넣기 / Then 거부(다 참).
- S6 (INV-GB6): Given 별빛 / When 신청 폼에 받는 분 이름·휴대폰 번호·주소를 입력해 신청 / Then 요청 본문에 주소 평문·우편번호가 없고, 신청에 암호문 사본과 구분이 저장된다.
  봉인 없이 신청(옛 「등록 주소 쓰기」 요청) / Then 거부, 신청이 생기지 않는다.
- S6b (INV-GB6, 실패경로): Given 누군가 평문 주소를 신청 API 로 보냄 / When 신청 / Then 형식 오류로 거부. 하루가 별빛 신청의 주소를 바꾸려 함 / Then 그런 길이 없다.
- S6c (INV-GB6, 실패경로): Given 마감된 선물함 / When 별빛이 주소를 바꾸려 함 / Then 거부.
- S7 (INV-GB7): Given `open` 선물함의 별빛 신청 / When 하루가 체크로 제외 → 다시 누름 / Then 제외 → 다시 들어감, 주소 사본은 그대로.
- S7b (INV-GB7, 실패경로): Given 하루의 선물함 / When 모모가 제외 API 를 부름 / Then 거부, 변화 없음.
- S7c (INV-GB7): Given 제외된 달토끼 / When 하루가 마감 / Then 달토끼 신청의 주소 사본이 같은 처리에서 지워지고 지운 기록 한 줄.
- S8 (INV-GB8, 동시): Given `open` 선물함 / When 마감과 별빛의 신청이 동시에 / Then 신청이 먼저면 별빛은 구간 고르기 목록에 있고, 마감이 먼저면 별빛 신청은 거부된다 — 목록과 명세서가 어긋나는 경우는 없다.
- S8b (INV-GB8, 실패경로): Given 신청이 모두 제외된 선물함 / When 마감 / Then 거부.
- S9 (INV-GB9): Given 신청 셋 / When 하루가 신청 관리 창·명세서·라벨 PDF 를 봄 / Then 닉네임·신청 시각·상태·(명세서) 할증 구분만 있고 주소·받는 분 이름·전화·아이디·운송장 번호 칸이 없다.
- S9b (INV-GB9, 실패경로): Given 크리에이터 로그인 토큰 / When 선물함 관련 모든 읽기 API 를 부름 / Then 응답에 주소·실명·전화번호 형태의 값이 없다. 바코드를 풀면 신청 번호뿐이다.
- S9c (INV-GB9, 실패경로): Given 별빛 / When 자기 신청 화면을 봄 / Then 다른 신청자의 수·닉네임이 없다(추천안 Q6).
- S10 (INV-GB10): Given `closed` → 다음 / When 하루가 3페이지를 봄 / Then 6자리 하나가 가려진 채 보이고, 라벨 PDF 는 선택된 신청마다 한 장(닉네임 + 바코드).
- S10b (INV-GB10, 실패경로): Given 하루의 선물함 6자리 / When 모모·별빛이 읽음 / Then 6자리 칸 없음. 명세서 발행 뒤 그 6자리로 온 상자 / Then 보류(추천안 Q7).
- S10c (INV-GB10, 실패경로): Given 선물함 A 의 바코드 라벨을 붙인 선물이 선물함 B 의 큰 상자에 있음 / When 사무실이 스캔 / Then B 의 신청으로 잇지 않고 「확인 필요」.
- S11 (INV-GB11): Given 보낸 상자 수 2, 첫 상자 입고 / When 168시간 안에 둘째 상자가 와 모두 실측 / Then 명세서 생성.
- S11b (INV-GB11): Given 첫 상자 입고 뒤 168시간, 구름빵 선물 없음 / When 자동 처리 / Then 구름빵 `missing`·주소 사본 삭제, 나머지로 명세서. 167시간 59분이면 그대로.
- S12 (INV-GB12): Given 하루가 별빛을 소형으로 고름 / When 실측 110cm·3kg / Then 명세서 별빛 줄은 중형 4,400원.

- 믿는 값: 서버가 로그인으로 얻은 사람 ID(INV-L2), DB 의 팔로우 표, 서버 시각, DB 의 요금 설정값·초기 크리에이터 순번·월 사용 줄, 사무실 스캔으로 기록한 실측 값,
