# 여러 선물을 골라 서명 한 번으로 승인

승인은 「크리에이터가 이 주문의 수령을 허락했다」는 전자서명이고, 주소를 여는 유일한 열쇠다(address-protection INV-P4).
지금은 주문 하나에 서명 하나라서 선물이 많은 크리에이터는 카카오톡 서명을 건마다 해야 한다.

이 스펙은 **서명 원문 한 장에 고른 주문을 줄마다 적어 서명 한 번으로 승인**하는 길을 더한다.
지키는 원칙은 그대로다 — 원문에 적히지 않은 주문은 어떤 서명으로도 승인되지 않고, 어떤 주소도 열리지 않는다.
업체(드림시큐리티) 쪽에서 보면 원문이 긴 서명 한 건이므로 「다건 서명」 기능은 필요 없다. 확인할 것은 원문 길이 한도뿐이다(아래 「확인할 것」).

## 바뀌는 기존 조항

| 조항 | 지금 | 바뀐 뒤 |
|---|---|---|
| approval-signature INV-S1 | 원문 = 한 주문의 네 값 | 원문 = 한 주문 이상, 주문마다 네 값을 한 줄씩(INV-B1) |
| approval-signature INV-S7 | 「"전체 승인"은 없다」 | 서명 원문에 줄로 적힌 주문만 승인한다. 원문에 없는 주문을 승인하는 길(목록 전체 승인·관리자 승인)은 여전히 없다(INV-B3) |
| approval-signature INV-S12 | 승인마다 서명 저장 | 묶음이면 승인한 주문마다 같은 서명값·원문 해시를 각각 저장(INV-B5) |
| approval-signature INV-S13 | 승인 버튼마다 주소 확인 | 묶음 서명 전에 주소 확인을 한 번(INV-B6) |
| approval-signature INV-S17 | 한 주문에 기다리는 요청 하나 | 한 주문은 기다리는 요청(한 건이든 묶음이든) 하나에만 들어간다(INV-B4) |
| address-protection INV-P4 (b) | 원문의 주문번호가 요청한 주문번호와 같다 | 원문의 **주문 줄 가운데 하나**의 주문번호가 요청한 주문번호와 정확히 같다(INV-B7) |

## 불변식

- INV-B1: 묶음 서명 원문은 요청 구분 「팬꾹 선물 수령 승인」 아래에 고른 주문을 **한 줄에 하나씩**, 줄마다 주문번호 · 보낸 팬 닉네임 · 선물 종류 · 개수 네 값만 적는다.
  줄 순서는 주문번호 순이고, 맨 위에 「N건」을 적는다. 팬이 쓴 글·사진·주소·실명·연락처는 들어가지 않는다(INV-S1 과 같은 제한).
  원문은 서버가 고른 주문번호로 주문을 다시 읽어 만든다 — 화면이 보낸 닉네임·종류·개수를 쓰지 않는다. 한 번에 고를 수 있는 주문은 **최대 20건**이다.
  (강제 위치: 서버 — 원문 만드는 함수 하나가 주문번호 목록만 받는다)
  위반 시: 원문에 개인정보가 섞여 업체를 거쳐 밖으로 나가거나, 크리에이터가 무엇을 승인하는지 원문에서 알 수 없다.

- INV-B2: 묶음에 넣을 수 있는 주문은 **그 크리에이터 앞의, 아직 승인 기록이 없는 승인 대기 주문**뿐이다. 하나라도 아니면 요청 전체를 만들지 않는다
  (다른 크리에이터의 주문, 이미 승인·거절·반려·취소된 주문, 168시간이 지난 주문 — INV-S6).
  (강제 위치: 서버 — 묶음 서명 요청 만들기, 로그인한 크리에이터와 주문마다 대조)
  위반 시: 남의 주문을 자기 묶음에 끼워 승인하거나, 끝난 주문이 묶음 서명으로 되살아난다.

- INV-B3: 서명 결과가 오면 서버는 원문을 저장한 원문과 바이트 단위로 대조하고(INV-S2), 서명자를 본인 대조하고(INV-S4), 그다음 **원문에 적힌 주문만** 하나씩 승인한다.
  그사이 상태가 바뀐 주문(팬 취소·차단으로 거절·168시간 지남)은 그 주문만 승인하지 않고 나머지는 승인한다 — 결과는 주문마다 「승인됨 / 기한 지남 / 이미 끝난 선물」로 돌려준다.
  묶음 서명으로도 원문에 없는 주문의 상태는 바뀌지 않는다. 화면이 「전체 선택」을 제공하더라도 서버는 원문에 적힌 주문번호만 본다.
  (강제 위치: DB 승인 함수 — 묶음 요청의 원문 줄 목록을 돌며 INV-S6 판정을 주문마다)
  위반 시: 서명하지 않은 주문이 승인돼 주소가 열리거나, 한 건이 그사이 끝났다는 이유로 나머지 정상 주문까지 승인이 안 된다.

- INV-B4: 한 주문은 동시에 **기다리는 서명 요청 하나에만** 들어간다 — 한 건 요청이든 묶음 요청이든. 기다리는 요청에 이미 든 주문을 다른 묶음에 넣으려 하면 새 요청을 만들지 않고 「이미 서명을 기다리는 선물이 있습니다」로 답한다.
  요청은 만든 때부터 5분 동안만 결과를 받는다(INV-S17 과 같음). 묶음 요청도 카카오톡이 한 번 가므로 **크리에이터당 하루 묶음 요청 10번**까지다(주문당 하루 5번은 그대로).
  같은 묶음 서명이 두 번 오거나 동시에 와도 주문마다 승인 기록은 하나다(INV-S5).
  (강제 위치: DB — 주문마다 기다리는 요청 하나(유일 제약), 묶음 요청 하루 횟수, 승인 기록 주문당 하나)
  위반 시: 같은 주문이 두 요청에 걸려 어느 서명으로 승인됐는지 엇갈리거나, 크리에이터 카카오톡에 요청이 쏟아진다.

- INV-B5: 묶음으로 승인한 주문마다 서명값·원문 해시·서명 시각·서명 방식을 **각각** 저장한다(같은 값이 여러 주문에 들어간다). 묶음 원문 자체는 묶음 요청 줄에 남는다.
  주문마다 따로 저장하므로 5년 보관·탈퇴 처리·자동 삭제(INV-S14)는 지금처럼 주문 단위로 돈다.
  (강제 위치: DB 승인 함수 — 승인과 서명 저장을 주문마다 한 처리에서)
  위반 시: 한 주문이 끝나 서명 기록을 지울 때 같은 묶음의 다른 주문 근거까지 사라지거나, 반대로 남아야 할 기록이 지워지지 않는다.

- INV-B6: 받는 주소가 없는 크리에이터는 묶음 승인도 거부된다(INV-S13). 화면은 묶음 서명 요청 전에 주소 확인(이름표·바꾼 날)을 **한 번** 보인다.
  주소 확인과 승인 서명은 여전히 따로다 — 한 서명으로 묶지 않는다.
  (강제 위치: DB 승인 함수 — 주소 칸 확인)
  위반 시: 묶음으로 승인한 상자 여럿이 출고 단계에서 한꺼번에 「주소 없음」으로 멈춘다.

- INV-B7: 복호화 함수는 그 주문의 서명을 다시 검증할 때, 원문을 **줄 단위로 나눠** 주문번호 칸이 요청한 주문번호와 **정확히 같은 줄**이 있어야 연다.
  글자열 포함으로 찾지 않는다(FC-AB12C 가 FC-AB12CD 줄에 걸리지 않게). 원문 해시·서명값·본인 대조(INV-P4 (a))는 지금과 같다.
  (강제 위치: 복호화 함수 진입부 — address-protection INV-P4 (b) 를 이 문장으로 바꾼다)
  위반 시: 한 묶음 서명으로 원문에 없는 다른 주문의 주소가 열린다.

## 시나리오

- B1 (INV-B1): Given 하루에게 승인 대기 3건(별빛 편지 1·달토끼 인형 2·구름빵 편지 1) / When 셋을 골라 「선택한 3건 승인」 / Then 원문 맨 위 「팬꾹 선물 수령 승인」·「3건」, 그 아래 주문번호 순 세 줄, 줄마다 네 값뿐.
- B1b (INV-B1): 화면이 닉네임을 바꿔 보내도 원문은 주문에서 읽은 닉네임이다. 21건을 보내면 요청을 만들지 않는다.
- B2 (INV-B2): 하루의 묶음에 모모 앞 주문 하나를 끼워 보내면 요청 전체를 만들지 않는다. 이미 승인된 주문·168시간 지난 주문도 같다.
- B3 (INV-B3): 3건 묶음을 서명하는 사이 1건을 팬이 취소 → 서명 결과로 2건만 승인, 취소된 건은 「이미 끝난 선물」, 원문에 없는 네 번째 대기 주문은 그대로 대기.
- B3b (INV-B3): 원문을 한 글자 바꾼 서명은 3건 모두 승인하지 않는다.
- B4 (INV-B4): 주문 A 가 기다리는 한 건 요청에 있을 때 A 를 넣은 묶음 → 새 요청 없음. 같은 묶음 서명을 동시에 두 번 → 주문마다 승인 기록 하나. 하루 열한 번째 묶음 요청은 거부.
- B5 (INV-B5): 묶음으로 승인한 2건의 서명 기록이 주문마다 하나씩, 같은 서명값·같은 원문 해시. 한 주문이 끝나 5년 뒤 지워져도 다른 주문의 기록은 남는다.
- B6 (INV-B6): 주소 없는 크리에이터의 묶음 승인 → 「주소 없음」, 아무 주문도 승인 안 됨.
- B7 (INV-B7): 원문에 FC-AB12CD 줄만 있는 서명으로 FC-AB12C 주소를 열려 하면 거부·거부 로그.

## 확인할 것 (구현 전에)

- **원문 길이 한도**: 드림시큐리티(카카오톡 인증서) 서명 원문의 최대 길이. 한 줄이 약 40바이트라 20건이면 약 1KB. 한도가 더 작으면 최대 건수를 한도에 맞춰 줄인다. 한도를 모르는 채 구현하지 않는다.
- 카카오 지갑에서 크리에이터가 보는 화면에 원문 여러 줄이 그대로 보이는지(서명하는 사람이 무엇에 서명하는지 볼 수 있어야 한다).

## 판단 근거 (표준인지 판단인지)

- 원문을 나열하고 서명 한 번: 공동인증서 다건 이체·전자세금계산서 일괄 발행과 같은 방식 — **업계 표준에 가깝다**.
- 최대 20건: 판단 — 지갑 화면에서 한눈에 읽을 수 있는 길이와 원문 약 1KB. 업체 한도 확인 뒤 확정.
- 크리에이터당 하루 묶음 10번: 판단 — 주문당 하루 5번과 같은 목적(카카오톡 퍼붓기 방지), 묶음은 여러 건을 한 번에 처리하니 그보다 넉넉하게.
- 일부 주문이 그사이 끝났을 때 나머지는 승인: 판단 — 한 건 때문에 전부 다시 서명하게 하면 묶음의 의미가 없다. 서명 원문에 적힌 주문만 대상이라 안전 조건은 그대로다.
