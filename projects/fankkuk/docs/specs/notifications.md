# 알림 스펙

선물이 한 단계 움직일 때마다 팬이나 크리에이터에게 카카오 알림톡이 간다. 카카오가 템플릿을 승인하기 전에는 같은 본문을
이메일로 보낸다. 알림은 잠금 화면·메일함·대행사 서버처럼 **우리가 지킬 수 없는 곳**에 남는다. 그래서 본문에는 「무슨 일이
있었다」는 사실과 우리 사이트로 가는 링크만 넣고, 누가 무엇을 누구에게 보냈는지는 링크를 열고 로그인한 뒤에만 보이게 한다.

어기면 생기는 사고는 다섯 가지다.
- 본문에 주소·실명·선물 내용·보낸 사람·운송장 번호가 들어가 잠금 화면이나 남의 메일함에 남는다.
- 다른 계정의 번호, 확인 안 된 이메일로 간다 — 선물 소식이 남에게 간다.
- 같은 사건에 두 번 가거나, 사건은 났는데 발송 실패를 잃어서 영영 안 간다 — 승인 요청이 안 가면 7일 뒤 자동 반려된다.
- 끈 설정을 무시하고 보낸다.
- 링크의 값을 믿고 처리하거나, 운영에서 가짜 발송 창구가 켜져 알림이 「보냄」으로 처리되고 실제로는 아무에게도 안 간다.

용어
- **알림 종류**: 승인 요청 · 입고 · 검수 · 출고 · 배송중 · 수령 (PRODUCT 6종) + 추적기 반송(위치 추적기로 확인된 상자를 돌려보냄, INV-N13 — 종류 코드는 처음 이름 그대로 hold·hold_fan) 과 그 뒤에 더한 종류들.
  전체 목록과 끌 수 있는지는 아래 「알림 종류와 끌 수 있는지」 표가 정본이다. 승인 요청에는 재알림 차례(INV-N8)가 있다.
- **꼭 가는 알림**: 받는 사람이 알림 설정을 꺼도 가는 종류. 조치가 필요하거나 돈·상자가 걸린 알림이다(INV-N6).
- **사건**: 알림을 일으키는 DB 의 상태 변화 한 번. 예: 첫 결제가 끝나 승인 요청 줄이 생김, 주문 상태가 입고로 바뀜.
- **발송 대기 줄**: 사건 하나·받는 계정 하나·통로 하나에 한 줄. 보내야 할 알림을 잃지 않으려고 사건과 같은 처리에서 DB 에 남긴다.
- **통로**: 카카오(알림톡) 또는 이메일.
- **보내는 일꾼**: 발송 대기 줄을 꺼내 대행사·메일 서버로 보내는 앱 서버 쪽 처리. 앱 서버 키로만 돈다.

## 불변식

- INV-N1: 알림 본문(제목·본문·버튼 문구·링크)에 들어갈 수 있는 값은 **알림 종류, 받는 사람 자신의 닉네임, 주문번호, 고정된 사이트
  경로** 넷과, 승인 요청 종류에 한해 **자동 반려 예정 시각** 하나뿐이다(누구의 것인지 드러내지 않는 시각이라 넣는다 — 결정 2026-10-06
  「기한을 세는 방법」). 역조공 받기 알림(INV-N20)에 한해 **보낸 크리에이터의 이름** 하나가 더 들어간다(reverse-gift INV-R12 — 팬이 누가 보냈는지 모르면 받을지 정할 수 없다).
  거절 알림(gift_undelivered)에 한해 **문구 갈래**(거절 / 기간 반려) 하나가 더 들어간다 — 받는 팬이 화면(decline-block INV-D5)에서
  이미 보는 구분이고, 앱이 넘기는 값이 아니라 알림을 꺼낼 때 DB 가 주문 상태로 정한 값이다(INV-N2, 2026-10-12 (2) D11). 갈래 값이 없는 거절 알림은 만들지 않고 건너뛴다.
  주소(평문·암호문)·실명·휴대폰 번호·이메일·선물 내용(품목·사진·메모)·상대방(보낸 팬, 받는 크리에이터)의 이름이나
  아이디·운송장 번호·검수 결과의 세부는 들어가지 않는다. 본문을 만드는 함수는 이 값들만 인자로 받는다(다른 값이 섞일 자리가 없다).
  (강제 위치: 서버 — 종류별 본문 틀 하나, 인자 목록 / 카카오 템플릿 자체도 같은 틀로 심사받는다)
  위반 시: 잠금 화면·메일함·대행사 서버에 「누가 누구에게 무엇을」이 남는다. address-protection INV-P10 이 깨진다.

- INV-N2: 팬이 받는 알림은 차단을 드러내지 않는다 — 크리에이터 거절·7일 자동 반려·차단에 따른 거절이 알림의 종류·발송 여부에서 구분되지 않고,
  크리에이터 거절과 차단에 따른 거절은 문구에서도 구분되지 않는다. 문구는 화면(decline-block INV-D5)과 같은 두 갈래다 — 직접 거절·차단 거절은
  「크리에이터가 선물을 원하지 않아요」, 7일 자동 반려는 「기간이 지나 반려됐어요」(2026-10-12 (2) 문제집 D11 — 그 전에는 셋이 같은 문구였다).
  이 갈래는 거절 알림(INV-N17 ②)에만 있고, 아직 안 온 상자 안내(INV-N17 ①)는 셋 모두 같은 문구다.
  거절·반려된 주문의 팬 알림(INV-N17)은 셋 모두 같은 처리에서 같은 규칙으로 고르고, 무엇을 보낼지는
  상자 사정(받는 주소를 본 적이 있는가·아직 안 온 상자가 있는가)으로만 정한다 — 거절한 사람·차단 여부는 그 판단에 들어가지 않는다.
  문구 갈래는 알림을 꺼낼 때 DB 가 주문 상태로만 정한다 — 거절(rejected)이면 거절, 기간 지남(expired)이면 기간 반려. 차단 표시는 읽지 않으므로
  차단 거절·차단 뒤 결제도 직접 거절과 같은 값이다.
  승인 자체(크리에이터가 승인했다는 사실)도 팬 알림으로 따로 보내지 않는다.
  차단 때 결제 대기였다가 뒤늦게 결제가 끝난 주문(전액 환불 대상, decline-block S8b)도 결제가 끝나는 그 처리에서 같은 거절 알림을 받는다 —
  이것이 빠지면 차단만 「알림이 오는가」로 구분된다.
  알림 시각은 숨기지 않는다 — 차단으로 함께 거절된 주문은 같은 때 알림이 간다. 같은 때 여러 건이 오는 것으로 「피한다」는 짐작은 할 수 있지만
  사용자 C2 「크리에이터가 나를 피한다는 정보 정도는 괜찮아」(DECISIONS 2026-10-10)에 따라 받아들인다.
  (강제 위치: DB — 주문이 거절·반려로 바뀌는 순간의 처리 하나가 팬 알림 줄을 고른다. 알림을 꺼내는 함수가 주문 상태로 문구 갈래를 정한다. 둘 다 차단 표시 칸을 읽지 않는다)
  위반 시: 알림이 오고 안 오는 것이나 문구로 팬이 「차단됐다」를 알아낸다(decline-block INV-D5 가 깨진다).

- INV-N3: 받는 계정은 DB 가 사건의 주문에서 고른다 — 승인 요청(재알림 포함)·추적기 반송(hold)은 그 주문의 크리에이터에 연결된 계정, 입고·검수·출고·

  위반 시: 다른 계정의 번호·오타 이메일로 선물 소식이 간다. 발송 기록 하나가 털리면 연락처 목록이 같이 나간다.

- INV-N4: 사건 하나에 받는 계정·통로마다 발송 대기 줄은 정확히 하나다 — 같은 사건이 다시 처리되거나(재시도·같은 스캔 두 번) 동시에

  줄도 남는다. 줄의 이름(멱등 키)은 알림 종류 + 대상(주문 또는 승인 요청, 역조공 받기는 몫) + 재알림 차례 + 받는 계정 + 통로로 정해지고, DB 가 겹침을 막는다.

  위반 시: 팬이 받기 대기를 모른 채 7일이 지나 선물이 받지 않음으로 돌아간다. 이미 받은 팬에게 「받아 주세요」가 또 간다. 본문에 선물 내용이 들어가면 잠금 화면에 남는다.

- INV-N21: 받는 주소 없이 보낸 상자 안내 — 6자리 없이 온 상자가 입고 때 어느 계정의 닉네임과 맞고(inbound-address-code INV-C5·C12 ①) 그 계정에 결제가 끝났고 입고 전인 팬 선물 주문이나 역조공 몫이 있으면, 같은 처리에서 그 계정에 한 번 간다(2026-10-16 카드 d94, 크리에이터는 카드 d96 ③).

- INV-N22: 반송 주소 알림 — 주문에 이어진 상자(팬 선물 상자·역조공 몫 상자)가 반송 대기가 되는 처리마다, 그 주문을 보낸 사람(팬 선물은 팬, 역조공은 보낸 크리에이터)에게
  주문 단위로 한 번 간다(return_address, office-workflow INV-W15, 2026-10-17 카드 d100). 같은 처리에서 hold_fan(INV-N13)이 가면 그 본문이 같은 말을 담고 있어 따로 보내지 않는다.
  본문은 「돌려보낼 상자가 있어요」·「돌려받을 주소를 정해 주세요. 30일 안에 정하지 않으면 상자를 처분해요」와 선물 상세 링크뿐이다 — 반송 이유·주소·크리에이터 이름은 쓰지 않는다(INV-N1).
  반송 대기가 된 때부터 14일(336시간)이 지나도 고르지 않은 상자가 있으면 같은 사람에게 상자마다 한 번 재알림(return_address_reminder)이 간다. 본문은 「돌려받을 주소를 아직 정하지 않았어요」·
  「○월 ○일까지 정하지 않으면 상자를 처분해요」(날짜는 반송 대기 + 30일, 서울 시간)와 링크뿐이다. 이미 고른 상자에는 가지 않는다. 둘 다 꼭 가는 알림이다(아래 표).
  어느 주문에도 이어지지 않은 상자(보류·미확인)는 받을 사람이 없어 이 알림이 없다.
  (강제 위치: DB — 반송 대기로 바꾸는 처리 안에서 줄 추가(hold_fan 이 같은 처리에 있으면 넣지 않음) / 자동 처리 함수 안에서 재알림 줄, 상자마다 같은 이름의 줄은 넣지 않음)
  위반 시: 보낸 사람이 반송 주소를 정해야 하는 줄 모른 채 30일이 지나 상자가 처분된다. 재알림이 두 번 가거나 이미 고른 사람에게 간다.

## 알림 종류와 끌 수 있는지 (INV-N6 — 2026-10-12 문제집 D7)

「끌 수 없음」은 받는 사람이 카카오·이메일 두 칸을 모두 꺼도 쓸 수 있는 통로로 간다. 「끌 수 있음」은 칸을 따른다.
새 종류를 더할 때는 이 표에 먼저 한 줄을 넣는다 — 표에 없는 종류는 만들지 않는다.

1. 받는 사람: 승인 요청(+재알림)·보관(2026-10-12 부터 추적기 반송) → 크리에이터 / 입고·검수·출고·배송중·수령 → 팬 / 배송중·수령은 크리에이터에게도. 주문 단위로 한 번 (INV-N3).

5. 결과를 모르는 발송: 대행사 발송 조회로 확인한 뒤 안 갔을 때만 다시. 조회가 없는 통로는 다시 보낸다 (INV-N5).
6. 6종 밖: 보관(추적 장치) 알림만 넣는다(2026-10-12 부터 추적기 반송 알림). 역조공 받기·자동 반려 하루 전은 각 기능 때 (INV-N13).
