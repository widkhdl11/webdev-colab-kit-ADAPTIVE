# 알림 스펙

선물이 한 단계 움직일 때마다 팬이나 크리에이터에게 카카오 알림톡이 간다. 카카오가 템플릿을 승인하기 전에는 같은 본문을
이메일로 보낸다. 알림은 잠금 화면·메일함·대행사 서버처럼 **우리가 지킬 수 없는 곳**에 남는다. 그래서 본문에는 「무슨 일이
있었다」는 사실과 우리 사이트로 가는 링크만 넣고, 누가 무엇을 누구에게 보냈는지는 링크를 열고 로그인한 뒤에만 보이게 한다.

어기면 생기는 사고는 다섯 가지다.
- 본문에 주소·실명·선물 내용·보낸 사람·운송장 번호가 들어가 잠금 화면이나 남의 메일함에 남는다.
- 다른 계정의 번호, 확인 안 된 이메일로 간다 — 선물 소식이 남에게 간다.
- 같은 사건에 두 번 가거나, 사건은 났는데 발송 실패를 잃어서 영영 안 간다 — 승인 요청이 안 가면 7일 뒤 자동 반려된다.
- 끈 설정을 무시하고 보낸다.
- 링크의 값을 믿고 처리하거나, 운영에서 가짜 발송 창구가 켜져 알림이 「보냄」으로 처리되고 실제로는 아무에게도 안 간다.

용어
- **알림 종류**: 승인 요청 · 입고 · 검수 · 출고 · 배송중 · 수령 (PRODUCT 6종). 승인 요청에는 재알림 차례(INV-N8)가 있다.
- **사건**: 알림을 일으키는 DB 의 상태 변화 한 번. 예: 첫 결제가 끝나 승인 요청 줄이 생김, 주문 상태가 입고로 바뀜.
- **발송 대기 줄**: 사건 하나·받는 계정 하나·통로 하나에 한 줄. 보내야 할 알림을 잃지 않으려고 사건과 같은 처리에서 DB 에 남긴다.
- **통로**: 카카오(알림톡) 또는 이메일.
- **보내는 일꾼**: 발송 대기 줄을 꺼내 대행사·메일 서버로 보내는 앱 서버 쪽 처리. 앱 서버 키로만 돈다.

## 불변식

- INV-N1: 알림 본문(제목·본문·버튼 문구·링크)에 들어갈 수 있는 값은 **알림 종류, 받는 사람 자신의 닉네임, 주문번호, 고정된 사이트
  경로** 넷뿐이다. 주소(평문·암호문)·실명·휴대폰 번호·이메일·선물 내용(품목·사진·메모)·상대방(보낸 팬, 받는 크리에이터)의 이름이나
  아이디·운송장 번호·검수 결과의 세부는 들어가지 않는다. 본문을 만드는 함수는 이 넷만 인자로 받는다(다른 값이 섞일 자리가 없다).
  (강제 위치: 서버 — 종류별 본문 틀 하나, 인자 목록 / 카카오 템플릿 자체도 같은 틀로 심사받는다)
  위반 시: 잠금 화면·메일함·대행사 서버에 「누가 누구에게 무엇을」이 남는다. address-protection INV-P10 이 깨진다.

- INV-N2: 팬이 받는 알림은 거절의 종류를 드러내지 않는다 — 크리에이터 거절·7일 자동 반려·차단에 따른 거절이 알림의 종류·발송 여부·
  문구 어디에서도 구분되지 않는다. 승인 자체(크리에이터가 승인했다는 사실)도 팬 알림으로 따로 보내지 않는다.
  (강제 위치: 서버 — 팬에게 가는 종류 목록에 승인·거절 종류가 없다)
  위반 시: 알림이 오고 안 오는 것으로 팬이 「직접 거절당했다」·「차단됐다」를 알아낸다(decline-block INV-D5 가 깨진다).

- INV-N3: 받는 계정은 DB 가 사건의 주문에서 고른다 — 승인 요청은 그 주문의 크리에이터에 연결된 계정, 팬 쪽 종류는 그 주문의 팬 계정.
  발송 대기 줄에는 **계정 ID 만** 있고 휴대폰 번호·이메일은 없다. 번호와 이메일은 보내는 순간에 앱 서버 키 전용 DB 함수로 그 계정
  ID 의 것을 읽는다. 이메일은 확인된 이메일만 쓰고 확인 대기 이메일은 어떤 알림에도 쓰지 않는다(my-account INV-A7). 계정이 없는
  크리에이터(가입 전 예시)에게는 줄을 만들지 않는다. 화면·요청 본문에서 받는 사람을 고르는 길은 없다.
  (강제 위치: DB — 줄을 만드는 처리 안에서 주문을 읽어 고름 / 연락처를 읽는 함수는 앱 서버 키만 실행 가능, 로그인 사용자·익명은 거부)
  위반 시: 다른 계정의 번호·오타 이메일로 선물 소식이 간다. 발송 기록 하나가 털리면 연락처 목록이 같이 나간다.

- INV-N4: 사건 하나에 받는 계정·통로마다 발송 대기 줄은 정확히 하나다 — 같은 사건이 다시 처리되거나(재시도·같은 스캔 두 번) 동시에
  와도 줄이 늘지 않는다. 줄은 사건을 일으킨 상태 변화와 **같은 처리**에서 생긴다 — 상태 변화가 취소되면 줄도 없고, 상태 변화가 남으면
  줄도 남는다. 줄의 이름(멱등 키)은 알림 종류 + 대상(주문 또는 승인 요청) + 재알림 차례 + 받는 계정 + 통로로 정해지고, DB 가 겹침을 막는다.
  (강제 위치: DB — 상태를 바꾸는 함수 안에서 줄 추가, 멱등 키 유일 제약)
  위반 시: 같은 알림이 두 번 가거나, 상태는 「입고」인데 알림 줄이 없어 알림이 영영 안 간다.

- INV-N5: 발송 대기 줄의 상태는 대기 → 보내는 중 → 보냄 / 실패 / 건너뜀 으로만 움직이고, 보냄·실패·건너뜀은 끝이다. 보내는 일꾼 둘이
  같은 줄을 동시에 꺼낼 수 없다 — 꺼내기는 「대기인 줄만 보내는 중으로 바꾸기」 한 번으로 하고, 진 쪽은 그 줄을 보내지 않는다.
  보내기에 실패하면(대행사 오류·연결 끊김) 줄은 대기로 돌아가 간격을 늘려 다시 보내고, 다섯 번 실패하거나 사건 뒤 24시간이 지나면
  실패로 끝나 운영자 목록에 남는다. 결과를 모르는 채 「보내는 중」에 멈춘 줄은 열린 질문 ⑤ 의 답대로 다룬다.
  (강제 위치: DB — 조건부 갱신 한 문장으로 꺼내기, 끝 상태에서 바꾸는 갱신 거부 / 서버 — 보내는 일꾼)
  위반 시: 두 일꾼이 같은 알림을 두 번 보내거나, 한 번 실패한 알림이 조용히 사라진다.

- INV-N6: 보내는 순간에 받는 계정의 알림 설정을 읽어 따른다 — 카카오 칸이 꺼져 있으면 카카오 줄은 보내지 않고 건너뜀으로 끝내고,
  이메일 칸이 꺼져 있으면 이메일 줄도 같다. 예외는 열린 질문 ② 의 「꼭 가는 알림」뿐이다(추천: 승인 요청과 그 재알림). 꼭 가는 알림이
  아닌 종류에서 설정을 무시하는 길은 없다.
  (강제 위치: 서버 보내는 일꾼 — 설정 읽기와 보내기 사이에 다른 판단 없음 / DB — 연락처 함수가 꺼진 통로의 연락처를 돌려주지 않음)
  위반 시: 끈 사람에게 알림이 간다. 반대로 꼭 가는 알림까지 끌 수 있으면 크리에이터가 요청을 모른 채 7일 자동 반려가 난다.

- INV-N7: 카카오 통로를 쓸지는 **종류마다 「승인된 템플릿 코드」가 설정에 있는가** 하나로 정한다. 코드가 없는 종류는 카카오 줄을
  만들지 않고, 그 종류는 이메일 통로로만 나간다(이메일 본문은 카카오 템플릿과 같은 틀, INV-N1). 대행사가 돌려준 오류를 보고 그때그때
  이메일로 갈아타지 않는다. 대체 기간에 이메일 설정이 꺼진 사람을 어떻게 할지는 열린 질문 ③.
  (강제 위치: 서버 — 통로를 고르는 곳 하나, 설정 값만 읽음)
  위반 시: 같은 사건이 카카오와 이메일로 한 번씩 가거나(오류를 보고 갈아탐), 승인 안 된 템플릿으로 보내다 대행사가 계속 거부해 아무것도 안 간다.

- INV-N8: 승인 요청 알림은 차례가 셋이다 — 첫 결제가 끝나 승인 요청이 생길 때, 상자가 처음 입고될 때, 열린 질문 ④ 의 기준 시각부터
  72시간 뒤. 재알림 차례는 보내는 순간에 승인 요청이 아직 「대기」일 때만 보내고, 승인·거절·반려됐으면 건너뜀으로 끝낸다.
  차례마다 줄은 하나다(INV-N4 의 재알림 차례). 7일 자동 반려 기준(결제 완료 시각부터 168시간, office-workflow 정한 것 1)은 알림 때문에
  늘지 않는다.
  (강제 위치: DB 자동 처리 함수 — 기한이 된 대기 요청에 줄 추가, 차례 유일 / 서버 보내는 일꾼 — 보내기 직전 요청 상태 확인)
  위반 시: 이미 승인한 크리에이터에게 「승인해 주세요」가 계속 가거나, 같은 재알림이 매번 자동 처리 때마다 새로 생긴다.

- INV-N9: 알림 링크는 고정된 사이트 경로(필요하면 주문번호 하나)만 담고, 그 자체로는 아무것도 처리하지 않는다. 링크를 연 화면은 로그인
  세션으로 사람을 다시 확인하고, 그 사람이 그 주문의 팬·크리에이터가 아니면 아무것도 보여 주지 않는다. 승인·거절·받기 같은 쓰기는
  링크의 값이 아니라 화면에서 다시 고른 동작과 서명으로만 일어난다(「링크 클릭만으로 승인되는 경로」는 PRODUCT 비범위).
  링크의 사이트 주소는 설정 값에서 만들고 요청 헤더에서 만들지 않는다.
  (강제 위치: 서버 — 본문 틀의 링크 생성, 각 화면의 세션·소유 확인)
  위반 시: 링크를 가로챈 사람이 남의 선물 정보를 보거나, 주문번호만 바꾼 링크로 남의 주문을 연다. Host 를 바꾼 요청이 남의 사이트 링크를 알림에 넣는다.

- INV-N10: 발송 기록(발송 대기 줄)·애플리케이션 로그·오류 보고에는 휴대폰 번호·이메일·알림 본문·대행사 키가 남지 않는다. 줄에 남는 것은
  종류·대상·차례·받는 계정 ID·통로·상태·시도 횟수·시각·대행사 발송 번호·오류 **코드**뿐이다(대행사 오류 문장은 번호를 되풀이할 수 있어
  저장하지 않는다). 줄은 화면 쪽 키(익명·로그인 사용자)로 읽거나 쓸 수 없고, 운영자는 관리자 화면에서 실패·건너뜀 줄을 종류·주문번호·
  시도 횟수·오류 코드로만 본다. 대행사 키와 메일 서버 비밀번호는 앱 서버 환경 설정에만 있고 오류 메시지에는 설정 이름만 쓴다.
  (강제 위치: DB — 표에 그 칸이 없음, 화면 쪽 키 권한 회수 / 서버 — 로그에 넘기는 값)
  위반 시: 발송 기록이 연락처 목록이 된다. 로그 수집 서비스에 번호가 쌓인다.

- INV-N11: 가짜 발송 창구(로컬에서 알림톡 대신 화면·메일 확인 화면으로 보내는 것)는 운영에서 켜질 수 없다. 운영 환경에서 카카오 템플릿
  코드가 설정돼 있는데 실제 대행사 설정이 없으면 시작하지 않는다(조용히 가짜로 넘어가지 않는다). 메일도 운영에서 설정이 빠지면 시작하지
  않는다(지금 메일 설정과 같다). 가짜 창구로 처리한 줄은 통로 기록에 가짜로 남고, 가짜 표시는 로컬 seed 만 넣는 「가짜 발송 허용」 줄이
  있는 DB 에서만 받는다 — 로컬 앱이 운영 DB 키로 떠 있어도 운영 DB 가 거부한다(approval-signature INV-S11 과 같은 방식). 창구를 고르는 곳은 하나다.
  (강제 위치: 서버 — 발송 창구 고르는 곳 하나 / DB — 가짜 표시 줄 거부)
  위반 시: 운영 알림이 「보냄」으로 기록되지만 실제로는 아무에게도 안 간다. 승인 요청을 못 받은 크리에이터의 선물이 7일 뒤 반송된다.

- INV-N12: 배송중·수령 알림은 주문의 배송 칸이 「배송중」·「수령」으로 바뀌는 사건에서만 생긴다. 그 칸은 택배사 연결이 쓰고, 화면·운영자가
  손으로 바꾸는 길은 없다. 택배사 연결 전에는 이 두 종류의 줄이 생기지 않는다(빈 사건을 지어내지 않는다).
  (강제 위치: DB — 배송 칸을 바꾸는 함수 안에서 줄 추가 / 그 함수는 앱 서버 키 전용)
  위반 시: 실제로 배달되지 않았는데 「수령」 알림이 가서 크리에이터가 받지 못한 선물을 못 찾는다.

## 시나리오

- S1 (INV-N1): Given 주문 FC-7K3M9, 품목 「향수」, 팬 별빛, 크리에이터 하루, 송장 출력 끝남 / When 6종 본문을 각각 만듦 / Then 본문에 주문번호·받는 사람 닉네임·경로만 있고 「향수」·「별빛」·운송장 번호·주소·전화 꼴의 값이 없다.
- S1b (INV-N1, 실패경로): Given 본문 틀 / When 품목이나 상대방 이름을 인자로 넘기려 함 / Then 그 인자 자리가 없다(타입 오류). 
- S2 (INV-N2): Given 별빛의 주문 셋 — 크리에이터 거절·7일 반려·차단 거절 / When 각 사건 뒤 팬 쪽 발송 대기 줄을 봄 / Then 세 주문 모두 같은 줄(또는 셋 다 없음), 종류·문구가 같다.
- S2b (INV-N2, 실패경로): Given 크리에이터가 승인 / When 팬 쪽 줄을 봄 / Then 승인 사실을 알리는 줄이 없다.
- S3 (INV-N3): Given 하루(계정 있음)에게 간 별빛의 주문 / When 결제 완료 / Then 승인 요청 줄의 받는 계정은 하루, 줄에 번호·이메일 칸이 없다.
- S3b (INV-N3, 실패경로): Given 로그인한 별빛 / When 연락처를 읽는 함수를 직접 부름(자기 ID·남의 ID) / Then 둘 다 거부.
- S3c (INV-N3, 실패경로): Given 확인된 이메일 A, 확인 대기 이메일 B / When 이메일 줄을 보냄 / Then A 로 간다. 확인된 이메일이 없으면 건너뜀.
- S3d (INV-N3): Given 계정이 없는 예시 크리에이터에게 간 주문 / When 결제 완료 / Then 승인 요청 줄이 생기지 않는다.
- S4 (INV-N4, 동시): Given 검수 완료 상자 / When 출고 확정 스캔 두 개가 동시에 / Then 상태 전환 1번, 출고 알림 줄 1개.
- S4b (INV-N4, 실패경로): Given 입고 처리 도중 DB 오류로 상태 변화가 취소됨 / Then 입고 알림 줄도 없다.
- S4c (INV-N4): Given 이미 입고 줄이 있는 주문 / When 같은 사건 처리를 다시 돌림 / Then 줄은 그대로 1개.
- S5 (INV-N5, 동시): Given 대기 줄 하나 / When 보내는 일꾼 둘이 동시에 꺼냄 / Then 한쪽만 「보내는 중」으로 바꾸고, 대행사 호출은 1번.
- S5b (INV-N5, 실패경로): Given 대행사가 다섯 번 오류 / Then 줄은 실패로 끝나고 운영자 실패 목록에 1줄, 더 보내지 않는다.
- S5c (INV-N5, 실패경로): Given 보냄 줄 / When 대기로 되돌리는 갱신 / Then DB 거부.
- S6 (INV-N6): Given 별빛의 카카오 칸 꺼짐, 이메일 칸 켜짐 / When 입고 사건 / Then 카카오 줄은 건너뜀, 이메일 줄은 보냄.
- S6b (INV-N6, 실패경로): Given 별빛 두 칸 모두 꺼짐 / When 검수 사건 / Then 아무것도 보내지 않음.
- S6c (INV-N6): Given 하루 두 칸 모두 꺼짐 / When 승인 요청 사건 / Then 열린 질문 ② 의 답대로(추천: 확인된 통로로 보냄).
- S7 (INV-N7): Given 입고 종류만 템플릿 코드가 있음 / When 입고·검수 사건 / Then 입고는 카카오, 검수는 이메일로만. 
- S7b (INV-N7, 실패경로): Given 템플릿 코드가 있는 종류에서 대행사가 오류 / When 다시 보냄 / Then 같은 카카오 줄을 다시 보낼 뿐 이메일 줄을 새로 만들지 않는다.
- S8 (INV-N8): Given 결제 완료 + 72시간, 승인 요청 대기 / When 자동 처리 / Then 3차 재알림 줄 1개. 자동 처리를 두 번 돌려도 1개.
- S8b (INV-N8, 실패경로): Given 3차 줄이 대기인 사이에 하루가 승인 / When 일꾼이 꺼냄 / Then 건너뜀, 보내지 않음.
- S8c (INV-N8): Given 결제 완료 + 71시간 59분 / When 자동 처리 / Then 3차 줄 없음.
- S9 (INV-N9, 실패경로): Given 별빛의 주문번호가 든 알림 링크 / When 달토끼로 로그인해 엶 / Then 그 주문 정보가 보이지 않는다.
- S9b (INV-N9, 실패경로): Given 승인 요청 알림 링크 / When 로그인한 하루가 엶 / Then 승인 화면이 열릴 뿐 승인되지 않는다(서명 전).
- S9c (INV-N9, 실패경로): Given Host 헤더를 바꾼 요청이 사건을 일으킴 / When 본문 링크를 봄 / Then 설정의 사이트 주소다.
- S10 (INV-N10): Given 보냄·실패 줄 / When 표와 그 처리의 앱 로그를 검사 / Then 휴대폰·이메일 꼴의 값과 본문 문장이 없다.
- S10b (INV-N10, 실패경로): Given 익명·로그인 사용자 키 / When 발송 대기 줄을 읽거나 씀 / Then 거부.
- S11 (INV-N11, 실패경로): Given 운영 환경, 템플릿 코드 있음, 대행사 설정 없음 / When 시작 / Then 시작하지 않고 설정 이름만 알린다.
- S11b (INV-N11, 실패경로): Given 「가짜 발송 허용」 줄이 없는 DB / When 줄을 가짜 통로로 보냄 표시 / Then DB 거부, 줄은 대기 그대로.
- S12 (INV-N12, 실패경로): Given 출고된 주문 / When 로그인 사용자·운영자가 배송 칸을 바꾸려 함 / Then 그런 함수가 없다(권한 거부), 수령 줄 없음.

## 신뢰 경계

- 믿는 값: DB 의 주문·승인 요청·상자 상태, 주문에 묶인 팬·크리에이터 계정, 개인정보 구역의 확인된 이메일과 휴대폰 번호, 알림 설정,
  서버 시각, 서버 설정의 템플릿 코드·사이트 주소
- 믿지 않는 값: 알림 링크의 모든 값(주문번호 포함 — 화면이 세션으로 다시 확인), 요청 헤더의 Host, 화면이 보내는 받는 사람·연락처
  (그 칸이 없다), 대행사 응답의 오류 문장(코드만 쓴다), 확인 대기 이메일

## 비범위

- 6종과 승인 재알림 밖의 알림 — 거절·반송·환불·차액 결제 요청·크리에이터 본인 확인 결과(creator-verification 비범위)·역조공 받기(reverse-gift INV-R12)·
  보관(추적 장치) 알림은 열린 질문 ⑥ 의 답에 따라 이 스펙에 더하거나 따로 둔다
- 웹 푸시(PRODUCT 선택 항목)
- 알림톡 대행사 고르기·계약·템플릿 심사 — 사람이 할 일. 대행사가 정해지면 실제 연결 약속은 외부 연결 스펙(external-connections)에 더한다
- 운영 메일 서비스와 TLS 설정 — 배포 전(BACKLOG)
- 보내는 일꾼을 정해진 시각마다 부르는 장치 — 7일 자동 처리와 같이 배포 방식을 정할 때(BACKLOG 「매일 새벽 자동 처리」)
- 반송된 메일·수신 거부 처리, 알림 문구 자체(문구는 카피 조정이라 이 스펙의 약속이 아니다 — 들어갈 수 있는 값만 INV-N1 이 정한다)

## 열린 질문 — 답이 오면 해당 INV 를 고치고 이 칸을 「정한 것」으로 바꾼다

1. **어느 종류가 누구에게 가나** (INV-N3)
   - 가: 승인 요청(+재알림) → 크리에이터 / 입고·검수·출고·배송중·수령 → 팬. 크리에이터는 상태 화면에서 본다
   - 나: 가 + 크리에이터에게도 배송중·수령(받을 상자가 오고 있다는 것을 알면 놓치지 않는다). 알림톡 건수가 늘어난다
   - 다: 6종 모두 양쪽에. 건수가 두 배이고 크리에이터에게 검수 소식은 쓸모가 적다
   - **추천: 나** — 크리에이터가 실제로 행동할 일(승인, 상자 받기)만 알린다. 주문 단위로 한 번(상자마다가 아니라)도 같이 정한다.
2. **꺼도 가는 알림이 있나** (INV-N6)
   - 가: 승인 요청과 그 재알림은 끌 수 없다. 설정 화면에 「승인 요청은 꺼도 갑니다」라고 적는다
   - 나: 모두 설정을 따른다. 크리에이터가 다 끄면 요청을 모른 채 7일 반려가 날 수 있다
   - 다: 카카오·이메일 중 하나는 반드시 켜져 있게 막는다
   - **추천: 가** — 승인 요청을 못 받으면 팬의 선물이 반송되고 반송비가 빠진다. 끄는 칸을 남기면 그 사고를 사용자 실수로 만든다.
3. **템플릿 승인 전, 이메일을 꺼 둔 사람** (INV-N7)
   - 가: 이메일 칸을 따른다 — 꺼 두었으면 그 기간에는 아무것도 안 간다(꼭 가는 알림은 ② 대로)
   - 나: 카카오 칸이 켜져 있으면 「카카오 대신」 이메일로 보낸다(이메일 칸이 꺼져 있어도)
   - **추천: 가** — 칸 둘이 각자 자기 통로만 뜻해야 사용자가 설정을 읽고 결과를 예측한다. 기본값이 둘 다 켜짐이라 영향받는 사람은 직접 끈 사람뿐이다.
4. **3일 재알림의 기준 시각** (INV-N8)
   - 가: 결제 완료 시각 + 72시간 — 7일 반려와 같은 기준이라 「반려까지 4일 남음」이 늘 맞다
   - 나: 첫 입고 시각 + 72시간 — PRODUCT 의 「도착 시·3일 후」를 글자대로. 상자가 늦게 오면 반려 직전이나 뒤로 밀린다
   - **추천: 가** — 기한과 같은 시계를 써야 재알림이 반려 뒤에 가는 일이 없다.
5. **결과를 모르는 발송** — 대행사에 보냈는데 응답 전에 일꾼이 멈춘 줄 (INV-N5)
   - 가: 다시 보낸다 — 두 번 갈 수 있다
   - 나: 다시 보내지 않고 운영자 목록에 「확인 필요」로 띄운다 — 실제로 안 갔으면 놓친다
   - 다: 대행사의 발송 조회(우리 발송 번호로 조회)로 확인한 뒤 안 갔을 때만 다시 보낸다. 조회가 없는 대행사면 가
   - **추천: 다** — 두 번 가는 것은 불편이고 안 가는 것은 반려 사고다. 대행사를 고를 때 발송 조회 기능을 조건에 넣는다.
6. **6종 밖의 알림을 이번에 넣나** (비범위)
   - 가: 넣지 않는다. 보관(추적 장치) 알림·역조공 받기·자동 반려 하루 전(BACKLOG) 은 각 기능 때
   - 나: 보관 알림만 넣는다 — 이미 기록 표(`office_hold_alerts`)가 있고, 크리에이터 안전에 닿는 소식이다. 본문은 「확인할 선물이 있어요」 + 링크
   - 다: 셋 다 넣는다. 역조공 받기 알림은 reverse-gift INV-R12 가 크리에이터 이름을 허용해 INV-N1 의 예외가 된다
   - **추천: 나** — 추적 장치가 나왔는데 크리에이터가 모르는 것이 남은 알림 중 가장 비싼 누락이다. 역조공은 INV-N1 예외를 따로 정해야 해서 그 기능 때 묶는다.
