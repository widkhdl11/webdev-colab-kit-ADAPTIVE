# 외부 연결 때 확정할 약속

클라우드 KMS·복호화 함수·택배사 연동·카카오 인증서·딜러사 서명 검증·패스키가 붙어야 시험할 수 있는
약속을 모아 둔 곳이다. 지금 코드에는 이 약속을 지킬 대상이 아직 없다 — 주소는 개발용 키 쌍으로만
열리고 운영에서는 막혀 있으며(`address-protection.md` INV-P12), 승인 함수는 서버 비밀 키로만 부를 수 있고
그것을 부르는 화면이 없다.

용어(데이터 키·보관 키·복호화 함수)는 `address-protection.md` 를, 서명 원문·딜러사는
`approval-signature.md` 를 따른다.

## 불변식

- INV-P2: 데이터 키를 풀 수 있는 키는 앱 서버·DB·브라우저 어디에도 없다. 앱 서버의 환경 변수와
  DB에는 감싸지 않은 데이터 키도, 보관 키의 비밀 부분도 존재하지 않는다.
  (강제 위치: KMS — 비밀키가 KMS 밖으로 나오지 않음 / 검사: 앱 서버 환경 변수 목록에 KMS 복호화 자격 증명이 없음)
  위반 시: DB 덤프나 앱 서버 하나로 전원의 주소가 열린다.

- INV-P3: 보관 키로 데이터 키를 푸는 권한은 복호화 함수의 자격 증명 하나에만 있다. 앱 서버의
  자격 증명으로 푸는 요청은 거부된다. (강제 위치: 보관 키 쪽 권한 정책)
  위반 시: 앱 서버를 장악한 공격자가 복호화 함수를 거치지 않고 직접 연다.

- INV-P6: 복호화 함수는 평문 주소를 응답으로 돌려주지 않는다. 택배사 API를 직접 호출하고,
  송장 라벨 이미지와 운송장 번호만 돌려준다. 평문은 그 호출 동안 메모리에서만 쓰고 저장하거나
  로그에 쓰지 않는다. (강제 위치: 복호화 함수의 응답 형식)
  위반 시: 앱 서버가 평문을 받아 그 뒤 어디로든 흘릴 수 있다.

- INV-P11: 크리에이터가 주소를 바꾸면 새 암호문이 이전 것을 대체한다. 아직 출력 전인 주문은
  출력 시점의 주소로 나간다. 주소 변경 자체는 카카오 인증서 재서명이 있어야 한다(계정 스펙).
  (강제 위치: 서버 — 주소 저장 경로)
  위반 시: 비밀번호만 턴 공격자가 주소를 자기 것으로 바꿔 선물을 가로챈다.

- INV-S3: 서명 값 검증(인증서 체인, 서명 알고리즘, 인증서 유효 기간과 폐기 여부)은 서버가 직접 한다.
  딜러사 응답의 "성공" 표시만으로 승인하지 않는다. (강제 위치: 서버 — 본인 확인 결과 수신)
  드림시큐리티 간편인증-API 에서는: 결과(hubToken)를 연동 모듈로 복호화한 뒤 그 안의 전자서명문(PKCS#7 SignedData)을 게이트웨이가 직접 연다 —
  서명값을 서명 인증서의 공개키로 검증하고, 인증서가 설정한 카카오 인증기관 인증서로 이어지는지·지금 유효 기간 안인지·폐기되지 않았는지(인증서에 적힌 OCSP 주소가
  허용 목록 안일 때만 묻고, 묻지 못하면 거부)를 본다. 카카오는 원문을 `{"txId":…,"data":…}` 로 감싸 서명하므로, 감싼 틀을 벗긴 원문이 요청 원문과 바이트 단위로 같아야 한다.
  결과의 발급 시각이 10분 넘게 지났으면 거부한다(딜러사 권고). 감싼 틀의 정확한 꼴은 테스트 키로 첫 서명을 받아 확인한다.
  위반 시: 딜러사 응답을 위조하거나 중간에서 바꾸면 서명 없이 승인된다.

- INV-S8: 예비 수단(패스키)을 붙일 때도 INV-S2~S7이 그대로 적용된다. 이보다 약한 승인 경로는 추가하지 않는다.
  (강제 위치: 승인 모듈 구조 — 바뀌는 것은 가운데 단계뿐)
  위반 시: 가장 약한 경로가 전체 보안 수준이 된다.

- INV-X1: 택배사에 보내는 송장의 「보내는 사람」은 항상 팬꾹 사무실 이름·주소·전화다. 팬의 이름·주소·연락처는
  송장·라벨·택배사 API 요청 어디에도 들어가지 않는다. (강제 위치: 송장 요청 조립부 / 검사: 택배사 요청 본문에 팬 정보 0건)
  위반 시: 택배사의 배송 문자·반송이 팬에게 가고, 그 과정에서 배송지가 드러난다.

- INV-X2: 송장 품목 칸·라벨·알림톡 본문에는 정해진 목록 값과 고정 문구만 들어간다. 팬이 직접 쓴 글(한마디 등)은
  들어가지 않는다. (강제 위치: 송장·알림 조립부)
  위반 시: 긴 글이나 특수 문자로 라벨이 깨지거나, 팬의 글이 택배 기사·크리에이터 가족에게 그대로 보인다.

- INV-X3: 팬꾹은 크리에이터에게 알림톡·메일·채팅으로 주소 입력 링크를 보내지 않는다. 배송 실패로 주소 확인이 필요해도
  「설정에서 주소를 다시 확인해 주세요」만 보내고 링크를 넣지 않는다. (강제 위치: 알림 템플릿)
  위반 시: 팬꾹을 사칭한 링크로 주소를 받아 가는 피싱이 진짜 안내와 구별되지 않는다.

- INV-X4: 서버가 밖으로 보내는 요청은 허용 도메인 목록(지원 플랫폼·택배사·카카오·결제·알림 발송)으로만 나간다.
  리다이렉트를 따라갈 때도 목록을 다시 검사하고, 내부 주소(127.0.0.1·169.254.169.254·사설 대역)는 막는다.
  사용자가 준 주소로 서버가 데이터를 보내는 기능은 없다. (강제 위치: 외부 요청 공통 창구 / 검사: 목록 밖·내부 주소 요청이 거부됨)
  서명 게이트웨이(sign.fankkuk.com)의 목록은 딜러사(dreamsecurity.com·ez-iok.com 아래 — 간편인증-API 는 개발 scert-dir.ez-iok.com · 운영 cert-dir.ez-iok.com)·카카오(kakao.com 아래)·서울 리전 KMS·이 프로젝트의 DB 주소
  (<프로젝트>.supabase.co 하나)뿐이다. 딜러사·카카오·KMS 는 코드에 박혀 있고 설정 파일로는 좁히기만 할 수 있다. DB 주소는 설정 파일에서 오지만
  `https://<20자 프로젝트 이름>.supabase.co` 꼴 하나만 받는다. 서비스 설정으로 인스턴스 메타데이터 주소도 막는다.
  위반 시: 채널 주소 칸에 내부 주소를 넣어 서버가 내부망을 읽게 만든다.

## 시나리오

- S1 (INV-P2): Given 앱 서버 배포 설정 / When 환경 변수 목록을 검사 / Then 보관 키의 비밀 부분이나 복호화 자격 증명이 없다.  (원래 주소 스펙 S2)
- S2 (INV-P2, 실패경로): Given DB 전체 덤프 / When 덤프만으로 데이터 키를 풀려 함 / Then 풀 수 있는 키가 덤프 안에 없다.  (원래 주소 스펙 S2b)
- S3 (INV-P3, 실패경로): Given 앱 서버의 자격 증명 / When 보관 키에 데이터 키 풀기를 요청 / Then 권한 거부.  (원래 주소 스펙 S3)
- S4 (INV-P6): Given 정상 출력 / When 복호화 함수의 응답을 검사 / Then 라벨 이미지와 운송장 번호만 있고 주소 문자열 필드가 없다. 함수 로그에도 주소가 없다.  (원래 주소 스펙 S6)
- S5 (INV-P11): Given 출력 전 주문이 있는 크리에이터 / When 재서명 후 주소 변경 / Then 그 주문은 새 주소로 출력된다.  (원래 주소 스펙 S11)
- S6 (INV-P11, 실패경로): Given 로그인 세션만 있고 재서명 없음 / When 주소 변경 / Then 거부.  (원래 주소 스펙 S11b)
- S7 (INV-S3, 실패경로): Given 딜러사 응답은 "성공"이지만 서명 값이 원문과 맞지 않음 / When 수신 / Then 거부.  (원래 승인 스펙 S3)
- S8 (INV-S3, 실패경로): Given 폐기되었거나 만료된 인증서의 서명 / When 수신 / Then 거부.  (원래 승인 스펙 S3b)
