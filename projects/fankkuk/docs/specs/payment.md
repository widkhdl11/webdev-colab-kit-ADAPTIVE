# 팬 결제와 환불 스펙

팬은 선물을 등록할 때 상자마다 구간 요금(배송비 포함, 소형 6,900원·중형 8,900원)을 낸다.
구간은 세 변 합과 무게 중 큰 쪽으로 정한다 — 소형 = 세 변 합 100cm 이하·5kg 이하, 중형 = 세 변 합 100cm 이하·10kg 이하.
중형을 넘는 상자는 받지 않는다. 도착 뒤 실측 구간이 신고보다 크면 차액을 따로 결제 요청한다. 결제가 끝나야
크리에이터에게 승인 요청이 간다. 결제는 브라우저가 PG 화면에서 인증하고, **서버가 PG 승인 API 를
호출해야 끝난다.** 브라우저가 보내는 금액과 "결제 성공" 이동은 위조할 수 있으므로 판단 근거가 아니다.
어기면 생기는 사고는 셋이다 — 덜 낸 금액으로 주문이 완료되거나, 한 결제가 두 번 반영되거나, 환불이
결제보다 많이 나간다.

## 불변식

- INV-M1: 결제 금액은 서버가 계산한다 — `상자별 신고 구간 요금의 합 (+ 상품 대금, 지금은 0)`.
  구간 요금은 서버 설정표에서만 읽는다. 결제 대기 기록을 만들 때 서버가 계산한 금액을 저장하고,
  브라우저가 보낸 금액은 쓰지 않는다. 상자가 0개이거나 중형을 넘는 구간이 있으면 결제 대기를 만들지 않는다.
  (강제 위치: 서버 — 결제 대기 기록 생성)
  위반 시: 팬이 금액을 고쳐 100원만 내고 주문을 완료한다.

- INV-M2: 결제 승인 API 를 부르기 전에, 성공 주소로 돌아온 `orderId`·`amount` 를 서버의 결제 대기 기록과
  대조한다. 기록이 없거나 금액이 다르면 승인 API 를 부르지 않고 그 결제 대기를 실패로 닫는다.
  (강제 위치: 서버 — 승인 처리 진입부)
  위반 시: 브라우저에서 금액을 바꾼 결제가 바뀐 금액으로 승인된다.

- INV-M3: 결제 완료는 서버가 부른 승인 API 응답의 상태가 `DONE` 이고, 응답의 `orderId`·`totalAmount` 가
  결제 대기 기록과 같을 때만 기록된다. 성공 주소에 도착한 것만으로는 완료가 아니다.
  (강제 위치: 서버 — 승인 응답 처리)
  위반 시: 승인되지 않은 결제(실패·만료·중단)가 완료로 기록된다.

- INV-M4: PG 비밀 키는 서버에서만 읽는다. 브라우저 번들과 공개 환경 변수(`NEXT_PUBLIC_` 접두어)에 없다.
  (강제 위치: 서버 설정 / 검사: 비밀 키 이름이 공개 접두어로 쓰이지 않음)
  위반 시: 누구나 우리 가맹점 이름으로 결제를 승인·취소한다.

- INV-M5: 한 주문의 결제 완료 기록은 하나다. 같은 결제의 승인 처리가 두 번·동시에 와도 결제 완료는
  한 번만 기록되고, 두 번째는 처음 결과를 돌려준다. 승인 API 호출에는 멱등 키를 붙인다.
  (강제 위치: DB 제약 — 주문당 결제 완료 1건 / 서버 — 멱등 키)
  위반 시: 새로고침 한 번에 결제 기록이 둘이 되고 정산·환불 계산이 틀어진다.

- INV-M6: 결제 완료 전에는 크리에이터에게 승인 요청을 만들지 않는다. (강제 위치: 서버 — 승인 요청 생성)
  위반 시: 돈을 안 낸 선물이 승인되고 사무실 주소가 공개된다.

- INV-M7: 결제 기록은 상품 대금·기본 서비스료·검수비·배송비를 서로 다른 칸에 저장하고, 네 칸의 합은 결제 금액과 같다.
  화면에는 구간 요금 한 금액만 보이지만, 기록의 배송비 칸 = 그 구간의 택배 원가(설정값), 검수비 칸 = 그 구간의 검수비
  (소형 1,500 · 중형 2,000), 기본 서비스료 칸 = 나머지다. 아래 INV-M8 의 「서비스료 칸」은 기본 서비스료 + 검수비를 뜻한다.
  차액 결제도 같은 방식으로 나눈다.
  (강제 위치: 서버 — 결제 기록 생성 / DB 제약 — 합계 일치)
  위반 시: 대행 수수료와 상품 대금이 섞여 매출·부가세 신고가 틀어진다(결정 D-03).

- INV-M8: 환불 금액은 서버가 주문 상태로 정한다. 브라우저나 관리자가 금액을 입력하지 않는다.
  | 주문 상태 | 환불 |
  |---|---|
  | 입고 전에 거절·7일 자동 반려·팬 취소 | 전액 |
  | 입고 뒤 검수 불합격 반송 (추적 장치 등·중형 초과 실측 포함 — 팬의 위반) | 상품 대금 칸만 — 검수비(서비스료)·반송비(배송비 칸) 차감 (2026-10-02 사용자 결정) |
  | 입고 뒤 거절·7일 자동 반려 (반송) | 반송 택배비를 뺀 금액 = 서비스료 칸 + 상품 대금 칸 (2026-10-02 사용자 결정) |
  | 차액 요청 뒤 7일 미납 반송 | 상품 대금 칸만 — 배송비 칸은 선불 반송에 쓰인다 (2026-10-08 정책 ③) |
  같은 표가 차액 결제에도 결제 건마다 적용된다. 실측 구간이 신고보다 작아도 환불하지 않는다.
  | 출고 뒤 | 없음 |
  반송은 팬꾹이 선불로 보내고 위 표대로 환불에서 배송비 칸(택배 원가)을 뺀다 — 착불로 보내지 않는다(팬이 반송비를 두 번 내지 않게, 2026-10-08 정책 ③).
  (강제 위치: 서버 — 환불 금액 계산)
  위반 시: 사람마다 다른 금액을 돌려주거나, 받은 것보다 많이 돌려준다.

- INV-M9: 한 결제의 환불 합계는 결제 금액을 넘지 않는다. 같은 환불이 두 번·동시에 와도 한 번만 나간다.
  환불 API 호출에는 환불마다 고유한 멱등 키를 붙인다. (강제 위치: 서버 + DB 제약 — 환불 합계·환불 ID 유일)
  위반 시: 같은 환불이 두 번 나가 돈이 샌다.

- INV-M11: 차액은 서버가 상자마다 `실측 구간 요금 − 신고 구간 요금` 으로 계산한다(배송비·서비스료 칸도 각각의 차).
  실측 구간이 신고 이하이면 차액 요청을 만들지 않는다. 실측이 중형을 넘으면 차액이 아니라 검수 불합격이다.
  한 상자에 차액 요청은 하나다. (강제 위치: 서버 — 실측 기록 / DB 제약 — 상자당 차액 요청 1건)
  위반 시: 팬이 작은 구간으로 신고해 차액 없이 큰 상자를 보내거나, 같은 차액을 두 번 낸다.

- INV-M12: 차액 요청이 있는 주문은 차액 결제가 끝나기 전에 송장을 출력하지 않는다(= 주소를 열지 않는다).
  (강제 위치: 복호화 함수 진입부 판정)
  위반 시: 돈을 덜 낸 상자가 출고된다.

- INV-M13: 차액 요청 뒤 7일(서울 시간, 요청 시각부터 168시간)이 지나도록 결제되지 않으면 그 주문은 반송 대상이 된다.
  (강제 위치: 서버 — 자동 처리)
  위반 시: 미납 상자가 보관 선반에 무기한 쌓인다.

- INV-M10: 운영 환경에서 테스트 키(`test_` 로 시작)를 쓰면 결제 모듈이 만드는 순간 실패한다.
  (강제 위치: 서버 — 결제 클라이언트 생성)
  위반 시: 운영 사이트에서 가상 승인이 일어나 돈을 안 받은 주문이 완료된다.

- INV-M14: 팬의 결제 내역 읽기 함수는 사람 ID 를 인자로 받지 않고, 로그인 토큰이 확인한 계정이 보낸 사람인 주문만 돌려준다(보낸 사람이 크리에이터여도 같다 — session-login INV-L3).
  금액은 **결제할 때 저장한 값만** 쓴다 — 첫 결제 금액, 상자마다 등록 때 저장한 신고 구간과 그 순간의 요금으로 정한 그 상자의 금액, 상자별 차액 결제(구간·금액·결제 여부),
  환불 금액과 상태. 지금 요금표를 읽어 다시 계산하지 않는다. 상자 금액은 등록할 때 결제 대기 기록과 함께 저장하고, 상자 금액의 합은 첫 결제 금액과 같다(DB 가 검사한다).
  환불 금액은 서버가 정한 값(INV-M8)만 보여 준다 — 반송·거절 뒤 얼마를 돌려받는지 문의 없이 알 수 있게 한다.
  기본 서비스료·검수비·배송비·상품 대금의 칸 나눔은 돌려주지 않는다. 결제가 끝나지 않은 결제 줄은 돌려주지 않는다.
  (강제 위치: DB 읽기 함수 — 인자 목록·반환 칸 / DB 제약 — 상자 금액의 합 = 첫 결제 금액 / 서버 — 등록 때 상자 금액 저장)
  위반 시: 요금을 바꾼 뒤 팬 화면에 낸 돈과 다른 금액이 보여 환불 다툼이 생긴다. 칸 나눔이 나가면 택배 원가·수수료 구조가 그대로 공개된다.

- INV-M15: 결제 대기로 만든 지 24시간이 지난 팬 선물 주문은 자동 처리가 「실패」로 닫는다(역조공 INV-R15 와 같은 규칙).
  닫는 대상은 결제 대기뿐이다 — 결제사 승인을 부른 뒤 결과를 기다리는 결제와 결제 완료는 건드리지 않는다. 닫기는 「결제 대기인 줄만 실패로 바꾸기」
  한 문장으로 하고, 같은 줄의 결제 확정 시작과 겹치면 둘 중 하나만 반영된다. 닫힌 뒤 성공 주소로 돌아와도 승인 API 를 부르지 않는다(INV-M2).
  닫힌 주문은 지우지 않고 「실패」로 남긴다 — 관리자 결제 목록과 맞출 수 있어야 한다. 같은 처리를 두 번 돌려도 결과는 같고, 관리자 화면 「지금 돌리기」로도
  부를 수 있다(office-workflow INV-W6 과 같은 자리). 정해진 시각에 부르는 장치가 생기기 전에는 「지금 돌리기」로만 닫힌다.
  (강제 위치: DB 자동 처리 함수 — 조건부 갱신 한 문장 / DB 결제 확정 시작 — 결제 대기일 때만)
  위반 시: 결과를 기다리는 결제를 닫으면 돈은 나갔는데 주문이 사라진다. 닫힌 뒤에도 승인을 부르면 사라진 주문에 돈이 나간다. 대기가 끝없이 쌓여 관리자 결제 목록을 가린다.

## 시나리오

- S1 (INV-M1): Given 소형 2·중형 1 / When 팬이 등록 / Then 결제 대기 금액은 6,900×2 + 8,900 = 22,700원이다.
- S1b (INV-M1, 실패경로): Given 브라우저가 금액 100원을 같이 보냄 / When 결제 대기 생성 / Then 저장 금액은 여전히 구간 요금의 합.
- S1c (INV-M1, 실패경로): Given 상자 0개 또는 중형 초과 구간 / When 결제 대기 생성 / Then 만들지 않는다.
- S2 (INV-M2, 실패경로): Given 결제 대기 9,000원 / When 성공 주소의 amount 가 100 / Then 승인 API 를 부르지 않고 결제 대기를 실패로 닫는다.
- S2b (INV-M2, 실패경로): Given 없는 orderId / When 성공 주소 도착 / Then 승인 API 를 부르지 않는다.

- S3b (INV-M3, 실패경로): Given 승인 응답 ABORTED(또는 EXPIRED) / When 응답 처리 / Then 완료로 기록하지 않는다.
- S3c (INV-M3, 실패경로): Given 응답 상태 DONE 이지만 totalAmount 가 기록과 다름 / When 응답 처리 / Then 완료로 기록하지 않는다.
- S4 (INV-M4): Given 서버 설정 / When 환경 변수 이름을 검사 / Then 비밀 키가 공개 접두어로 노출되지 않는다.

- S5b (INV-M5, 동시): Given 결제 대기 / When 승인 처리 두 개가 동시에 / Then 결제 완료 기록 1개.
- S6 (INV-M6, 실패경로): Given 결제 대기 상태의 주문 / When 승인 요청 생성 시도 / Then 거부.
- S7 (INV-M7): Given 소형 1 결제 / When 기록을 봄 / Then 상품 대금 0 · 서비스료 + 배송비 원가 = 6,900, 배송비 칸은 소형 원가 설정값.
- S7b (INV-M7, 실패경로): Given 세 칸의 합이 결제 금액과 다른 기록 / When 저장 / Then 거부.

- S9 (INV-M9, 실패경로): Given 이미 전액 환불된 결제 / When 환불 다시 요청 / Then 아무것도 나가지 않는다.

## 신뢰 경계

- 믿는 값: 서버가 계산·저장한 결제 대기 금액, 서버가 부른 PG 승인·취소 API 의 응답
- 믿지 않는 값: 브라우저가 보내는 금액, 성공·실패 주소의 쿼리 값(대조용으로만 쓴다), 결제 화면의 표시 금액

## 비범위

- 가상계좌 입금 대기(`WAITING_FOR_DEPOSIT`) — 첫 출시는 즉시 결제 수단만. 가상계좌를 열면 입금 알림 처리와 함께 다시 정한다
- PG 웹훅 — 첫 출시는 승인 API 응답만으로 확정한다. 웹훅을 붙이면 서명 검증과 함께 이 스펙에 추가한다
- 부분 취소 외의 정산·세금계산서 — 세무사 확인 후
- 구간별 택배 원가의 실제 값 — 택배 계약 전에는 설정값 소형 4,000원·중형 5,000원(가정). 요금(6,900·8,900)은 확정, 원가는 기록의 칸 나눔에만 쓰인다
