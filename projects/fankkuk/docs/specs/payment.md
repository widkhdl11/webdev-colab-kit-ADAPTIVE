# 팬 결제와 환불 스펙

팬은 선물을 등록할 때 단일 요금(배송비 실비 + 검수·전달 서비스료 5,000원)을 낸다. 결제가 끝나야
크리에이터에게 승인 요청이 간다. 결제는 브라우저가 PG 화면에서 인증하고, **서버가 PG 승인 API 를
호출해야 끝난다.** 브라우저가 보내는 금액과 "결제 성공" 이동은 위조할 수 있으므로 판단 근거가 아니다.
어기면 생기는 사고는 셋이다 — 덜 낸 금액으로 주문이 완료되거나, 한 결제가 두 번 반영되거나, 환불이
결제보다 많이 나간다.

## 불변식

- INV-M1: 결제 금액은 서버가 계산한다 — `배송비 실비 + 서비스료 5,000원 (+ 상품 대금, 지금은 0)`.
  결제 대기 기록을 만들 때 서버가 계산한 금액을 저장하고, 브라우저가 보낸 금액은 쓰지 않는다.
  (강제 위치: 서버 — 결제 대기 기록 생성)
  위반 시: 팬이 금액을 고쳐 100원만 내고 주문을 완료한다.

- INV-M2: 결제 승인 API 를 부르기 전에, 성공 주소로 돌아온 `orderId`·`amount` 를 서버의 결제 대기 기록과
  대조한다. 기록이 없거나 금액이 다르면 승인 API 를 부르지 않고 그 결제 대기를 실패로 닫는다.
  (강제 위치: 서버 — 승인 처리 진입부)
  위반 시: 브라우저에서 금액을 바꾼 결제가 바뀐 금액으로 승인된다.

- INV-M3: 결제 완료는 서버가 부른 승인 API 응답의 상태가 `DONE` 이고, 응답의 `orderId`·`totalAmount` 가
  결제 대기 기록과 같을 때만 기록된다. 성공 주소에 도착한 것만으로는 완료가 아니다.
  (강제 위치: 서버 — 승인 응답 처리)
  위반 시: 승인되지 않은 결제(실패·만료·중단)가 완료로 기록된다.

- INV-M4: PG 비밀 키는 서버에서만 읽는다. 브라우저 번들과 공개 환경 변수(`NEXT_PUBLIC_` 접두어)에 없다.
  (강제 위치: 서버 설정 / 검사: 비밀 키 이름이 공개 접두어로 쓰이지 않음)
  위반 시: 누구나 우리 가맹점 이름으로 결제를 승인·취소한다.

- INV-M5: 한 주문의 결제 완료 기록은 하나다. 같은 결제의 승인 처리가 두 번·동시에 와도 결제 완료는
  한 번만 기록되고, 두 번째는 처음 결과를 돌려준다. 승인 API 호출에는 멱등 키를 붙인다.
  (강제 위치: DB 제약 — 주문당 결제 완료 1건 / 서버 — 멱등 키)
  위반 시: 새로고침 한 번에 결제 기록이 둘이 되고 정산·환불 계산이 틀어진다.

- INV-M6: 결제 완료 전에는 크리에이터에게 승인 요청을 만들지 않는다. (강제 위치: 서버 — 승인 요청 생성)
  위반 시: 돈을 안 낸 선물이 승인되고 사무실 주소가 공개된다.

- INV-M7: 결제 기록은 상품 대금·서비스료·배송비를 서로 다른 칸에 저장하고, 세 칸의 합은 결제 금액과 같다.
  (강제 위치: 서버 — 결제 기록 생성 / DB 제약 — 합계 일치)
  위반 시: 대행 수수료와 상품 대금이 섞여 매출·부가세 신고가 틀어진다(결정 D-03).

- INV-M8: 환불 금액은 서버가 주문 상태로 정한다. 브라우저나 관리자가 금액을 입력하지 않는다.
  | 주문 상태 | 환불 |
  |---|---|
  | 입고 전에 거절·7일 자동 반려·팬 취소 | 전액 |
  | 입고 뒤 검수 불합격 반송 | 배송비 실비만 |
  | 입고 뒤 거절·반려 (가정 — 검수 불합격과 같게 본다) | 배송비 실비만 |
  | 출고 뒤 | 없음 |
  (강제 위치: 서버 — 환불 금액 계산)
  위반 시: 사람마다 다른 금액을 돌려주거나, 받은 것보다 많이 돌려준다.

- INV-M9: 한 결제의 환불 합계는 결제 금액을 넘지 않는다. 같은 환불이 두 번·동시에 와도 한 번만 나간다.
  환불 API 호출에는 환불마다 고유한 멱등 키를 붙인다. (강제 위치: 서버 + DB 제약 — 환불 합계·환불 ID 유일)
  위반 시: 같은 환불이 두 번 나가 돈이 샌다.

- INV-M10: 운영 환경에서 테스트 키(`test_` 로 시작)를 쓰면 결제 모듈이 만드는 순간 실패한다.
  (강제 위치: 서버 — 결제 클라이언트 생성)
  위반 시: 운영 사이트에서 가상 승인이 일어나 돈을 안 받은 주문이 완료된다.

## 시나리오

- S1 (INV-M1): Given 배송비 4,000원 설정 / When 팬이 등록 / Then 결제 대기 금액은 9,000원이다.
- S1b (INV-M1, 실패경로): Given 브라우저가 금액 100원을 같이 보냄 / When 결제 대기 생성 / Then 저장 금액은 여전히 9,000원.
- S2 (INV-M2, 실패경로): Given 결제 대기 9,000원 / When 성공 주소의 amount 가 100 / Then 승인 API 를 부르지 않고 결제 대기를 실패로 닫는다.
- S2b (INV-M2, 실패경로): Given 없는 orderId / When 성공 주소 도착 / Then 승인 API 를 부르지 않는다.
- S3 (INV-M3): Given 승인 응답 DONE·금액 일치 / When 응답 처리 / Then 결제 완료가 기록된다.
- S3b (INV-M3, 실패경로): Given 승인 응답 ABORTED(또는 EXPIRED) / When 응답 처리 / Then 완료로 기록하지 않는다.
- S3c (INV-M3, 실패경로): Given 응답 상태 DONE 이지만 totalAmount 가 기록과 다름 / When 응답 처리 / Then 완료로 기록하지 않는다.
- S4 (INV-M4): Given 서버 설정 / When 환경 변수 이름을 검사 / Then 비밀 키가 공개 접두어로 노출되지 않는다.
- S5 (INV-M5): Given 승인 처리 하나가 끝난 주문 / When 같은 성공 주소를 새로고침 / Then 결제 완료 기록 1개, 승인 API 재호출 없음.
- S5b (INV-M5, 동시): Given 결제 대기 / When 승인 처리 두 개가 동시에 / Then 결제 완료 기록 1개.
- S6 (INV-M6, 실패경로): Given 결제 대기 상태의 주문 / When 승인 요청 생성 시도 / Then 거부.
- S7 (INV-M7): Given 결제 완료 / When 기록을 봄 / Then 상품 대금 0 · 서비스료 5,000 · 배송비 4,000, 합 9,000.
- S7b (INV-M7, 실패경로): Given 세 칸의 합이 결제 금액과 다른 기록 / When 저장 / Then 거부.
- S8 (INV-M8): 상태별 환불액 — 입고 전 거절 9,000 / 검수 불합격 4,000 / 입고 뒤 반려 4,000 / 출고 뒤 0.
- S9 (INV-M9, 실패경로): Given 이미 전액 환불된 결제 / When 환불 다시 요청 / Then 아무것도 나가지 않는다.
- S9b (INV-M9, 동시): Given 같은 환불 요청 두 개가 동시에 / Then 환불은 한 번만.
- S10 (INV-M10, 실패경로): Given 운영 환경 + `test_` 키 / When 결제 모듈 생성 / Then 즉시 실패.

## 신뢰 경계

- 믿는 값: 서버가 계산·저장한 결제 대기 금액, 서버가 부른 PG 승인·취소 API 의 응답
- 믿지 않는 값: 브라우저가 보내는 금액, 성공·실패 주소의 쿼리 값(대조용으로만 쓴다), 결제 화면의 표시 금액

## 비범위

- 가상계좌 입금 대기(`WAITING_FOR_DEPOSIT`) — 첫 출시는 즉시 결제 수단만. 가상계좌를 열면 입금 알림 처리와 함께 다시 정한다
- PG 웹훅 — 첫 출시는 승인 API 응답만으로 확정한다. 웹훅을 붙이면 서명 검증과 함께 이 스펙에 추가한다
- 부분 취소 외의 정산·세금계산서 — 세무사 확인 후
- 배송비 실비의 실제 값 — 택배 계약 전에는 설정값 4,000원(가정)
