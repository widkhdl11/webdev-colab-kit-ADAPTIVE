## 1. 크리에이터가 받은 선물의 진행 단계 읽기 → `office-workflow.md`

지금은 크리에이터용 받은 선물 읽기가 승인 대기 건만 돌려줘서, 크리에이터 메인이 등록·입고까지만 칠한다(BACKLOG 「크리에이터 메인에서 비어 있는 것」).
열람 기록 읽기(인자 없이 로그인한 크리에이터 것만), 본인 확인 신청 읽기(INV-V11), 내 정보 읽기(INV-A3)와 같은 꼴로 쓴다.

**INV-W9**: 크리에이터가 받은 선물의 진행 단계 읽기 함수는 계정·크리에이터 ID 를 인자로 받지 않는다. 로그인 토큰이 확인한 계정이
받는 크리에이터인 주문만 돌려주고, 결제가 끝나지 않은 주문은 돌려주지 않는다(payment INV-M6 — 돈을 내지 않은 등록은 크리에이터에게 오지 않은 것이다).
한 줄의 칸은 주문번호 · 보낸 사람 닉네임 · 상자 수 · 지금 단계 · 단계마다 처리된 시각(결제 완료·입고·검수·출고) · 검수 결과(통과·보관·반송 중 하나) ·
배송 칸(배송중·수령)뿐이다. 실명·주소·전화번호, 보낸 사람의 계정 ID·아이디, 팬이 쓴 원 송장번호, 검수 장비별 세부, 처리한 운영자는 없다
(INV-W7, admin-console INV-K8 — 열람 기록 읽기도 처리한 사람을 「대표인지 아닌지」로만 돌려준다). 크리에이터행 출고 송장번호도 넣지 않는다 `(질문 Q1)`.
팬·운영자·로그인하지 않은 사람에게는 0줄이다.
(강제 위치: DB 읽기 함수 — 인자 목록, `auth.uid()` 로 크리에이터를 고르는 조건, 반환 칸)
위반 시: 앱이 크리에이터 ID 를 넘기면 그 값을 바꿔 다른 크리에이터가 받은 선물과 보낸 팬 목록을 본다. 원 송장번호를 내주면 택배사 조회로 팬 주소 일부가 크리에이터에게 보인다.

- 참고: 배송중·수령의 **시각** 칸은 지금 주문에 없다(배송 칸 값만 있다). 택배사 연결 때 그 칸이 생기면 이 줄에 더한다(notifications INV-N12 와 같은 때).
- 시나리오 **S9** (INV-W9): Given 하루에게 온 주문 셋(입고·검수 완료·출고), 모모에게 온 주문 하나 / When 하루로 읽기 / Then 하루 주문 셋만, 각 줄에 단계 시각이 맞게.
- 시나리오 **S9b** (INV-W9, 실패경로): Given 하루에게 온 결제 대기 주문 / When 하루로 읽기 / Then 그 주문은 없다. 팬·운영자·익명으로 읽기 / Then 0줄.
- **시험 한 줄**: DB 통합 시험 — 하루·모모 주문을 만들고 하루 토큰으로 부르면 하루 주문만 나오고, 응답 JSON 에 `fan_id`·원 송장번호·출고 송장번호 키와 전화·주소 꼴 문자열이 없으며, 팬·운영자 토큰은 0줄인지 본다.

## 2. 팬이 자기 선물의 결제 금액 읽기 → `payment.md`

선물 상세의 결제 내역이 비어 있다(BACKLOG 「선물 상세의 결제 내역」). 지금 요금표로 다시 계산하면 대표가 요금을 바꾼 뒤에는 틀린 금액이 보인다.
이미 정해진 것: 결제한 금액은 등록 순간의 요금으로 고정된다(admin-console INV-K3) · 팬에게는 금액만 보내고 칸 나눔은 보내지 않는다(칸 나눔은 영업 정보, BACKLOG 「세 화면을 실제 데이터로」).

**INV-M14**: 팬의 결제 내역 읽기 함수는 사람 ID 를 인자로 받지 않고, 로그인 토큰이 확인한 계정이 보낸 사람인 주문만 돌려준다(보낸 사람이 크리에이터여도 같다 — session-login INV-L3).
금액은 **결제할 때 저장한 값만** 쓴다 — 첫 결제 금액, 상자마다 등록 때 저장한 신고 구간과 그 상자의 금액 `(질문 Q2)`, 상자별 차액 결제(구간·금액·결제 여부),
환불 금액과 상태 `(질문 Q3)`. 지금 요금표를 읽어 다시 계산하지 않는다. 상자 금액의 합은 첫 결제 금액과 같다.
기본 서비스료·검수비·배송비·상품 대금의 칸 나눔은 돌려주지 않는다. 결제가 끝나지 않은 결제 줄은 돌려주지 않는다.
(강제 위치: DB 읽기 함수 — 인자 목록·반환 칸 / DB 제약 — 상자 금액의 합 = 첫 결제 금액)
위반 시: 요금을 바꾼 뒤 팬 화면에 낸 돈과 다른 금액이 보여 환불 다툼이 생긴다. 칸 나눔이 나가면 택배 원가·수수료 구조가 그대로 공개된다.

- 시나리오 **S14** (INV-M14): Given 소형 요금 6,900 일 때 소형 1·중형 1 결제(15,800원) / When 대표가 소형을 7,400 으로 바꾼 뒤 팬이 읽음 / Then 상자 금액 6,900·8,900, 합계 15,800.
- 시나리오 **S14b** (INV-M14, 실패경로): Given 별빛의 주문 / When 달토끼로 읽기 / Then 0줄. 응답 어디에도 서비스료·검수비·배송비 칸이 없다.
- **시험 한 줄**: DB 통합 시험 — 결제 뒤 요금표를 바꾸고 읽어 금액이 결제 때 값 그대로인지, 다른 팬 토큰은 0줄인지, 응답 키에 `service_fee`·`inspection_fee`·`shipping_fee` 가 없는지 본다. 상자 금액 합이 결제 금액과 다른 줄은 DB 가 거부하는지 함께.

## 3. 크리에이터 설정 — 공개 이름·찾기 노출·알림 → `my-account.md`

지금 「주소와 설정」의 프로필·알림 칸은 예시 크리에이터 값을 보여 주고 저장이 DB 에 닿지 않는다(BACKLOG 「크리에이터 설정의 … 예시 데이터」).
이미 정해진 것: 기본 공개 정보는 가입 때 받고 소개글은 「내 팬꾹」에서 고친다(DECISIONS 2026-10-05 본인 확인) · 플랫폼·채널 주소는 본인 확인 승인으로만 바뀐다(INV-V7) ·
승인 요청과 그 재알림은 꺼도 간다(INV-N6) · 본인 확인 전 크리에이터는 찾기에 나오지 않는다(INV-U5).

**INV-A9**: 크리에이터 공개 정보 고치기 함수는 계정·크리에이터 ID 를 인자로 받지 않고, 로그인 토큰이 확인한 계정에 연결된 크리에이터 한 줄만 고친다.
크리에이터 역할이 아니거나 로그인하지 않았으면 거부한다. 고칠 수 있는 칸은 공개 이름 · 소개글 · 찾기 노출 셋뿐이다 — 플랫폼·채널 주소·채널 이름·분야·본인 확인 여부·
페이지 주소 이름·평균 승인 시간은 이 경로로 바뀌지 않는다(INV-V7). 입력 경계: 공개 이름은 앞뒤 공백을 뺀 1~20자(가입과 같다), 소개글은 0~200자, 노출은 참·거짓.
앱 서버가 먼저 검사하고 DB 함수가 다시 검사하며, 하나라도 틀리면 아무 칸도 바꾸지 않는다. 공개 이름이 바뀌면 언제·전·후를 한 줄씩 남기고 그 기록은 추가만 된다 `(질문 Q4)`.
같은 사이트의 JSON 요청만 받고 응답은 캐시되지 않는다(INV-A6 과 같다).
(강제 위치: DB 함수 — 인자 목록, 진입부 역할 확인, 고치는 칸이 정해져 있음 / 서버 입력 경계)
위반 시: 본문의 크리에이터 ID 를 바꿔 남의 공개 이름을 고치거나, 설정 저장으로 채널 주소를 바꿔 확인받지 않은 채널이 확인된 채널로 나온다.

**INV-A10**: 크리에이터 찾기 목록에 나오는 조건은 「본인 확인됨」 **그리고** 「찾기 노출 켜짐」 둘 다다. 노출 스위치는 본인 확인을 대신하지 못한다 —
확인 전 크리에이터가 노출을 켜도 나오지 않고, 승인이 취소되면 노출 값과 상관없이 사라진다(admin-console INV-K10). 노출의 처음 값은 켜짐이다.
노출을 끈 동안에는 찾기 목록에서만 빠지고, 크리에이터 페이지·팔로우·새 선물 등록은 그대로 된다 `(질문 Q5)`.
(강제 위치: DB 찾기 읽기 함수의 조건 — 두 칸을 함께 본다)
위반 시: 노출만 켜면 확인 전 계정이 찾기에 나와 사칭 계정이 선물을 받는다(INV-U5 가 깨진다). 끈 크리에이터가 계속 검색된다.

**INV-A11**: 크리에이터의 알림 설정은 팬과 같은 두 칸(카카오·이메일)이고, INV-A3~A6 과 같은 고치기 경로로만 바뀐다. 승인 요청과 그 재알림은 두 칸이 모두 꺼져도
가므로(notifications INV-N6) 그것을 끄는 스위치는 없다. 알림 스펙에 없는 알림 종류의 스위치는 두지 않는다 `(질문 Q6)`.
(강제 위치: DB 고치기 함수 — 알림 칸은 둘뿐 / 서버 보내는 일꾼 — INV-N6)
위반 시: 화면 스위치를 꺼도 아무 일도 일어나지 않거나(저장할 칸이 없는 스위치), 승인 요청을 끌 수 있어 크리에이터가 요청을 모른 채 7일 자동 반려가 난다.

- 시나리오 **S9** (INV-A9): Given 하루로 로그인 / When 공개 이름 「하루달」로 저장 / Then 하루의 공개 이름만 바뀌고 변경 기록 한 줄.
- 시나리오 **S9b** (INV-A9, 실패경로): Given 하루로 로그인 / When 본문에 모모의 크리에이터 ID·채널 주소·본인 확인 참을 넣음 / Then 모모 그대로, 하루의 채널·확인 여부 그대로. 공개 이름 21자 → 400, 아무 칸도 안 바뀜. 팬 계정으로 부름 → 거부.
- 시나리오 **S10** (INV-A10): 확인 전+켜짐 → 안 나옴 / 확인됨+꺼짐 → 안 나옴 / 확인됨+켜짐 → 나옴 / 켜짐인 채 승인 취소 → 안 나옴.
- 시나리오 **S11** (INV-A11): Given 하루가 카카오·이메일 둘 다 끔 / When 입고 알림·승인 요청 알림이 생김 / Then 입고는 건너뜀, 승인 요청은 감.
- **시험 한 줄**: A9 — DB 통합 시험으로 다른 크리에이터 ID·채널 칸을 넣어 불러도 바뀌지 않는지, 21자·팬 계정이 거부되는지. A10 — 네 가지 조합을 만들어 찾기 함수 결과를 본다(노출 조건을 빼면 「확인됨+꺼짐」 시험이 깨진다). A11 — 크리에이터 계정으로 내 정보 고치기를 불러 알림 두 칸이 저장되는지, 알림 일꾼 시험에 크리에이터 계정 줄을 더해 승인 요청만 꺼도 가는지.

## 4. 계정 보안 — 비밀번호 재설정·변경, 휴대폰 번호 변경, 로그인 뒤 돌아갈 주소

이미 정해진 것: 로그인은 아이디+비밀번호, **이메일은 비밀번호 재설정용**(PRODUCT) · 확인된 이메일로만 메일을 보낸다(INV-A7) · 메일 한도와 본문 규칙(INV-A8) ·
비밀번호 경계 10~72자·아이디와 다름(INV-U6) · **휴대폰 번호 변경은 카카오 인증 재확인**(PRODUCT 내 정보) · 가짜 본인 확인은 운영에서 켜지지 않는다(INV-U9) ·
돌아갈 주소는 같은 사이트의 경로만(BACKLOG 「로그인한 뒤 원래 보던 화면으로」) · 비밀번호만으로 열리는 범위는 목록·상태 보기(PRODUCT).

알아 둘 사실: 운영 계정의 로그인 주소는 메일이 갈 수 없는 `<아이디>@login.fankkuk.invalid` 다(INV-U8). 그래서 Supabase Auth 가 로그인 주소로 보내는
기본 재설정 메일은 쓸 수 없고, 확인 메일(INV-A7)과 같은 우리 쪽 링크로 만든다.

### `session-login.md` — INV-L10 ~ L13

**INV-L10**: 비밀번호 재설정 요청은 아이디와 이메일을 받는다 `(질문 Q7)`. 계정이 없을 때, 이메일이 맞지 않을 때, 확인된 이메일이 없을 때, 한도를 넘었을 때,
메일을 실제로 보냈을 때 모두 **같은 상태 코드·같은 문구**(「입력한 정보가 맞으면 메일을 보냈어요」)를 돌려준다. 메일은 입력한 이메일이 그 계정의
확인된 이메일과 같을 때만 그 주소로 보낸다 — 확인 대기 이메일로는 보내지 않는다(INV-A7). 한 계정에 한 시간 다섯 통까지(INV-A8 과 같은 한도·같은 방식)이고,
본문에는 링크와 닉네임만 있다. 같은 사이트의 요청만 받고 응답은 캐시되지 않는다.
(강제 위치: 서버 — 재설정 요청 처리, 응답 하나 / DB 함수 — 계정·이메일 대조, 보낸 기록과 개수 확인을 한 번에)
위반 시: 응답 차이로 가입된 아이디와 그 이메일을 알아낸다(INV-L5 가 막은 것을 재설정 화면이 다시 연다). 확인 안 된 주소로 재설정 링크가 가서 남이 계정을 가져간다.

**INV-L11**: 재설정 링크는 한 번만 쓰이고 발급 뒤 1시간에 만료되며 `(질문 Q8)`, 그 계정 하나에 묶인다. 새 재설정을 요청하면 이전 링크는 무효다. DB 에는 링크 값이 아니라
그 해시만 둔다(INV-A7 과 같다). 새 비밀번호는 INV-U6 경계를 따른다. 재설정은 비밀번호만 바꾼다 — 주소·승인·휴대폰 번호에는 닿지 않는다.
재설정이 끝나면 그 계정의 로그인 세션은 모두 끝나고 새 비밀번호로 다시 로그인한다 `(질문 Q9)`.
(강제 위치: DB 함수 — 링크 확인과 사용 표시를 한 처리에서, 행 잠금 / 서버 — 비밀번호 바꾸기와 세션 끝내기)
위반 시: 메일함에 남은 옛 링크나 털린 DB 의 링크 값으로 비밀번호를 바꾼다. 계정을 빼앗은 사람의 세션이 재설정 뒤에도 살아 있다.

**INV-L12**: 로그인한 사람의 비밀번호 바꾸기는 사람 ID 를 인자로 받지 않고 로그인 토큰이 확인한 사람(INV-L2)의 비밀번호만 바꾼다. 지금 비밀번호를 함께 받아
맞을 때만 바꾸고 `(질문 Q10)`, 틀리면 INV-L5 와 같은 하나의 실패 문구다. 새 비밀번호는 INV-U6 경계를 따른다. 바꾸면 지금 세션을 뺀 그 계정의 다른 세션은 모두 끝난다 `(질문 Q9)`.
같은 사이트의 JSON 요청만 받고 응답은 캐시되지 않는다.
(강제 위치: 서버 — 비밀번호 바꾸기 처리 진입부)
위반 시: 열린 세션 하나만 빼앗은 사람이 비밀번호를 바꿔 주인을 쫓아낸다. 다른 사이트가 로그인한 사람 몰래 비밀번호를 바꾼다.

**INV-L13**: 로그인 뒤 돌아갈 주소는 같은 사이트의 경로만 받는다 — `/` 하나로 시작하고, `//`·`/\` 로 시작하지 않으며, 역슬래시·제어 문자·`://` 가 없어야 한다.
조건에 맞지 않거나 비어 있으면 메인으로 간다. 서버는 이 값을 사이트 주소에 붙여 만들지 않고 경로 그대로 돌려준다(결제 확정 뒤 이동과 같은 방식, 2026-10-03).
돌아갈 주소는 로그인 성공 뒤에만 쓰이고, 로그인 실패 응답(INV-L5)에는 영향이 없다.
(강제 위치: 서버 — 로그인 처리의 돌아갈 주소 검사 하나 / 화면 — 로그인 링크에 경로만 싣는다)
위반 시: 우리 로그인 화면이 다른 사이트로 보내는 데 쓰인다 — 로그인 직후 가짜 로그인 화면으로 보내 비밀번호를 다시 받아 간다.

- 시나리오 **S8** (INV-L10, 실패경로): Given 없는 아이디 / 있는 아이디+틀린 이메일 / 확인된 이메일이 없는 계정 / 맞는 아이디+이메일 / When 재설정 요청 / Then 네 응답이 같고, 메일은 마지막 하나에만 한 통.
- 시나리오 **S8b** (INV-L10, 실패경로): Given 확인 대기 이메일 B 만 있는 계정 / When B 로 재설정 요청 / Then 같은 응답, 메일 없음. 한 시간 여섯 번째 요청 → 같은 응답, 메일 없음.

- 시나리오 **S9b** (INV-L11, 실패경로): Given 이미 쓴 링크·1시간 지난 링크·새 요청으로 무효가 된 링크·다른 계정 링크 / When 저장 / Then 거부, 비밀번호 그대로. DB 에 링크 원문 없음.
- 시나리오 **S10** (INV-L12, 실패경로): Given 별빛으로 로그인 / When 틀린 지금 비밀번호·9자 새 비밀번호·본문에 달토끼 ID / Then 각각 거부, 달토끼 비밀번호 그대로.
- 시나리오 **S11** (INV-L13): `/help` → `/help` · `/gifts/FC-7K3M9` → 그대로 · `//evil.example` · `/\evil.example` · `https://evil.example` · `/a%0d%0a` 의 풀린 제어 문자 · 빈 값 → 메인.

### `signup.md` — INV-U12

**INV-U12**: 휴대폰 번호 바꾸기는 로그인한 사람(INV-L2) 자신의 번호만 바꾸고, 새 번호에 대한 카카오 본인 확인을 다시 받아야 한다. 가입과 같은 규칙을 쓴다 —
서버가 직접 확인한 번호만(INV-U1), 확인 한 건은 한 번·10분 안에만(INV-U2), 번호 하나에 계정 하나(INV-U3), 요청 횟수 한도(INV-U10), 운영에서 카카오 연결 전에는 거부(INV-U9).
확인 결과의 번호와 바꿀 번호가 다르면 거부한다. 다른 계정이 쓰는 번호면 본인 확인을 마친 뒤에만 「이미 가입된 번호」라고 알려 준다(INV-U11).
지금 비밀번호도 함께 받아 맞을 때만 바꾼다 `(질문 Q11)`. 바뀌는 것은 연락처 줄의 번호 하나이고, 바꿀 때마다 누가·언제 바꿨는지 한 줄 남기며 그 기록에는 번호 값이 없다.
(강제 위치: 서버 — 번호 바꾸기 처리, 본인 확인 제공자 고르는 곳 하나 / DB 함수 — 확인 줄 잠금·사용 표시·번호 바꾸기를 한 처리에서, 번호 유일 제약)
위반 시: 세션만 빼앗은 사람이 번호를 자기 것으로 바꿔 알림톡을 가로챈다. 같은 번호가 두 계정에 붙어 알림이 섞인다.

- 시나리오 **S12** (INV-U12): Given 별빛이 010-2222-3333 으로 본인 확인 / When 그 번호로 바꾸기 / Then 연락처 줄의 번호가 바뀌고 기록 한 줄(번호 값 없음).
- 시나리오 **S12b** (INV-U12, 실패경로): Given 010-2222-3333 으로 확인 / When 바꿀 번호를 010-9999-0000 으로 보냄 / Then 거부. 이미 쓴 확인·11분 지난 확인 → 거부. 달토끼 번호로 확인받고 바꾸기 → 「이미 가입된 번호」, 둘 다 그대로. 같은 번호로 두 계정이 동시에 → 하나만.
- **시험 한 줄**: DB 통합 시험 — 확인 줄의 번호와 다른 번호·쓴 확인·만료 확인·남의 번호·동시 두 요청을 넣어 연락처 줄과 기록 줄 수를 본다. 운영 환경 표시로는 서버가 거부하는지 단위 시험.

### INV-R13 — 송장이 안 나온 출력은 연 줄을 돌려준다 (주소 보호 INV-P15 대응)

역조공 몫도 한 몫에 최대 3회(INV-R7)라, 일시 장애 세 번이면 그 몫은 송장을 뽑을 수 없다. 팬 선물 쪽은 카드 d31 에서 보안 리뷰 조건 넷을 붙여 「돌려주기」를 정했다 — 같은 조건을 몫에 그대로 쓴다.

**INV-R13**: 몫의 주소를 연 뒤 송장이 나오기 전에 출력이 실패하면(봉투 열기 실패·봉인 속 주문번호 대조 전 오류·송장 마무리 실패) 출력 함수는 그 「연 줄」을 돌려준다 —
「돌려줌」 줄을 따로 남기고 원래 줄은 그대로 둔다. 몫의 횟수 = 그 몫의 「연 줄」 수 − 그 가운데 돌려준 줄 수다. 조건은 모두 DB 가 몫을 잠근 자리에서 본다.
(a) 돌려주기 함수로만 한다 — 복호화 전용 역할이 기록 표에 직접 넣을 수 있는 줄은 거부 줄뿐이다.
(b) 「연 줄」 하나는 한 번만 돌려준다.
(c) 그 몫의 가장 최근 「연 줄」이고, 그 줄을 연 요청자가 돌려받을 때만이다.
(d) 몫이 아직 송장 출력 단계 전(검수 완료)일 때만이다 — 재출력의 실패는 돌려주지 않는다.
(e) 한 몫에서 돌려줄 수 있는 것은 2번까지다.
암호문 속 주문번호가 몫과 달라 거부된 경우(INV-R7 (b))는 실패가 아니라 거부라 돌려주지 않는다.
(강제 위치: DB 돌려주기 함수 — 복호화 전용 역할만, 몫 잠금 뒤 (b)~(e) / DB 권한 — 기록 표 직접 넣기는 거부 줄만 / DB 제약 — 돌려줌 줄의 연 줄 유일)
위반 시: 「열고 → 일부러 실패 → 돌려받기」를 되풀이해 팬 주소를 끝없이 연다. 반대로 돌려주지 않으면 일시 장애 세 번에 그 몫의 출고가 막힌다.

- 참고: 역조공 송장 출력 자체(몫 주소 읽기·몫별 횟수 칸·거부 기록)가 아직 없다(BACKLOG 「역조공 송장 출력 연결」). 그것과 함께 만든다.
- 시나리오 **S13** (INV-R13): Given 받기를 한 검수 완료 몫, 주소를 연 뒤 송장 마무리 실패 / When 돌려줌 / Then 횟수 0, 다음 출력은 첫 출력.
- 시나리오 **S13b** (INV-R13, 실패경로): 직접 넣은 돌려줌 줄 → 거부 / 이미 돌려준 줄 → 거부 / 앞 줄·다른 요청자 → 거부 / 재출력 줄 → 거부 / 세 번째 돌려주기 → 거부, 그 시도는 횟수에 남음.
- **시험 한 줄**: 주소 보호 S15~S15f 의 DB 시험을 몫 기준으로 옮겨 다섯 조건 각각을 하나씩 어기는 시험을 둔다.

### INV-R14 — 결제한 크리에이터에게 사무실 주소 안내 (승인 서명 INV-S9 대응)

보내기 화면이 「결제하면 사무실 주소가 안내돼요」라고 약속하지만 주소를 보여 주는 곳이 없다(BACKLOG 「역조공 결제 뒤 사무실 주소 안내」). 팬 선물과 같은 규칙이다 — 팬의 받기를 기다리지 않는다.

**INV-R14**: 사무실 주소는 결제가 끝난 보내기를 **보낸 크리에이터 본인**에게만 보여 준다. 팬의 「받기」는 기다리지 않는다 — 크리에이터는 결제 직후 상자를 보내고, 받기는 출고 전에만 있으면 된다(INV-R7).
몫이 모두 받지 않음·반송·취소가 된 보내기에는 보여 주지 않는다. 주소 값은 팬 선물 안내와 같은 한 곳에서 읽는다.
(강제 위치: 서버 — 보낸 역조공 읽기의 주소 안내 / DB — 보낸 역조공 읽기는 로그인한 보낸 사람 것만)
위반 시: 결제하지 않은 보내기의 상자가 사무실로 와 미확인 입고가 생기거나, 모든 팬이 받지 않은 보내기의 상자가 계속 들어온다. 다른 크리에이터의 보내기에 주소 안내가 붙는다.

- 시나리오 **S14** (INV-R14): Given 결제가 끝난 하루의 보내기 / When 하루가 보낸 역조공을 봄 / Then 사무실 주소가 보인다.
- 시나리오 **S14b** (INV-R14, 실패경로): Given 결제 대기 보내기 / 몫이 모두 받지 않음인 보내기 / When 하루가 봄 / Then 주소 없음. 모모가 하루 보내기를 읽음 → 0줄.
- **시험 한 줄**: 보낸 역조공 화면 모양을 만드는 단위 시험에서 결제 대기·전부 받지 않음·진행 중 세 경우의 주소 칸을 보고, DB 시험으로 다른 크리에이터 토큰은 0줄인지 본다.

### INV-R15 — 결제창에서 이탈한 결제 대기 정리

결제창을 닫거나 실패한 보내기가 결제 대기로 남고, 다시 결제하면 새 보내기가 생긴다(BACKLOG 「결제창에서 이탈한 역조공 보내기 정리」). 결과를 모르는 「승인 중」은 돈이 나갔을 수 있어 건드리면 안 된다(BACKLOG 「결과를 모르는 결제 확정」).

**INV-R15**: 결제 대기로 만든 지 24시간이 지난 보내기는 자동 처리가 「실패」로 닫는다 `(질문 Q13)`. 닫는 대상은 결제 대기뿐이다 — 「승인 중」(결제사 승인을 부른 뒤 결과를 기다리는 것)과
결제 완료는 건드리지 않는다. 닫기는 「결제 대기인 줄만 실패로 바꾸기」 한 문장으로 하고, 같은 줄의 결제 확정 시작(결제 대기 → 승인 중)과 겹치면 둘 중 하나만 반영된다.
닫힌 뒤 결제창에서 성공 주소로 돌아와도 결제사 승인을 부르지 않는다 — 승인을 부르지 않은 결제는 돈이 나가지 않는다. 닫힌 보내기의 몫은 팬·크리에이터 어느 화면에도 나오지 않는다.
같은 처리를 두 번 돌려도 결과는 같다. 관리자 화면 「지금 돌리기」로도 부를 수 있다(office-workflow INV-W6 과 같은 자리).
(강제 위치: DB 자동 처리 함수 — 조건부 갱신 한 문장 / DB 결제 확정 시작 함수 — 결제 대기일 때만 승인 중으로)
위반 시: 「승인 중」을 닫으면 돈은 나갔는데 보내기가 사라진다. 닫힌 뒤에도 승인을 부르면 사라진 보내기에 돈이 나간다. 대기가 끝없이 쌓여 관리자 결제 목록을 가린다.

- 시나리오 **S15** (INV-R15): Given 결제 대기 25시간 / When 자동 처리 / Then 실패. 23시간이면 그대로. 두 번 돌려도 실패 한 번.
- 시나리오 **S15b** (INV-R15, 실패경로): Given 승인 중 25시간 / When 자동 처리 / Then 그대로. 닫힌 보내기의 성공 주소 도착 → 결제사 승인 호출 없음.
- 시나리오 **S15c** (INV-R15, 동시): Given 기한 직전 결제 대기 / When 결제 확정 시작과 자동 처리가 동시에 / Then 하나만 반영.
- **시험 한 줄**: DB 통합 시험 — 만든 시각을 25시간·23시간 전으로 둔 대기와 25시간 전 승인 중을 넣고 자동 처리를 두 번 돌려 상태를 보고, 닫힌 줄에 결제 확정 시작이 거부되는지 본다.
