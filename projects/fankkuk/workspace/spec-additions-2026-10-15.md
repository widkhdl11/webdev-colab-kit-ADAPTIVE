## 1. 팬 프로필 → `my-account.md` (INV-A12 ~ A14)

지금 팬에게는 닉네임 말고 프로필이 없다(`profiles` 표 칸: 아이디·닉네임·역할·만든 시각). 표는 행 보안이 켜져 있고 정책이 없어 DB 함수로만 읽힌다.
크리에이터가 팬을 보는 곳은 승인 요청 카드(`my_approval_requests`)·승인 내역·받은 선물(INV-W9)·확인할 선물(`my_creator_checks`)이고, 모두 닉네임만 준다.
역조공의 팔로워 고르기(`my_revgift_followers`)도 닉네임만 준다 — 결정 ④에 따라 여기에는 프로필을 넣지 않는다.

**INV-A12**: 팬 프로필은 사진·배경 사진·자기소개 세 칸이고, 그 팬 본인만 바꾼다. 바꾸는 함수는 계정 ID 를 인자로 받지 않고 로그인 토큰이 확인한 계정 한 줄만 고친다.
로그인하지 않았거나 팬 역할이 아니면 거부한다(크리에이터의 공개 정보는 INV-A9·creator-link INV-E1 경로다). 자기소개는 앞뒤 공백을 뺀 0~100자 한 줄이고 태그·팬덤 이름과 같은 금칙어·연락처 필터를 거친다.
앱 서버가 먼저 검사하고 DB 함수가 다시 검사하며, 하나라도 틀리면 아무 칸도 바꾸지 않는다. 같은 사이트의 JSON 요청만 받고 응답은 캐시되지 않는다(INV-A6).
프로필 수정 화면의 닉네임은 이 함수가 아니라 지금의 내 정보 고치기 경로(INV-A4·A5)로 바뀌고, 계정마다 다른 닉네임·미리 확인 규칙(signup INV-U13·U14)을 그대로 따른다 — 닉네임 규칙을 새로 만들지 않는다.
(강제 위치: DB 함수 — 인자 목록, 진입부 역할 확인, 고치는 칸이 정해져 있음 / 서버 입력 경계 / DB 제약 — 소개 길이)
위반 시: 본문의 계정 ID 를 바꿔 남의 프로필을 고친다. 소개에 연락처를 적어 크리에이터에게 사적으로 연락하는 길이 열린다. 닉네임 규칙이 두 군데서 따로 놀아 같은 닉네임 둘이 생긴다.

**INV-A13**: 팬 프로필(사진·배경 사진·자기소개)을 돌려주는 읽기는 둘뿐이다 — ① 본인 것 읽기(인자 없음) ② 크리에이터가 자기에게 승인 요청을 보낸 팬의 프로필 읽기.
②는 크리에이터 ID 를 인자로 받지 않고, 로그인 토큰의 크리에이터와 그 팬 사이에 승인 요청이 하나라도 있을 때만 돌려준다 — 상태(대기·승인·거절·반려·취소)와 차단 여부는 따지지 않는다 `(정할 것 Q1)`.
결제가 끝나지 않아 승인 요청이 없는 주문만 있는 팬, 팔로워일 뿐인 팬은 빈 결과다. 다른 팬·다른 크리에이터·운영자(직원·대표) `(정할 것 Q2)`·로그인하지 않은 사람에게는 빈 결과다.
팬 프로필은 공개 화면(크리에이터 페이지·답장 모음·공유 카드·미리보기 이미지), 역조공 팔로워 고르기, 차단 목록(INV-D9), 알림 본문 어디에도 들어가지 않는다.
(강제 위치: DB 읽기 함수 — 인자 목록, 승인 요청 존재 조건 / 서버 — 공개 화면용 읽기에 프로필 칸 없음)
위반 시: 팬을 팔로우만 한 사람이나 남이 팬의 얼굴 사진·소개를 본다. 결정 ④(본인과 승인 요청을 받은 크리에이터만)가 깨진다.

**INV-A14**: 팬 프로필 사진·배경 사진은 비공개 저장소에 두고 서버만 쓴다 — 화면에서 저장소로 바로 올리는 길이 없고, 저장소에 읽기·쓰기 정책을 두지 않는다.
서버가 받아 실제 이미지인지 열어 보고(JPG·PNG·WebP, 10MB, 4천만 화소), 위치를 포함한 사진 정보(EXIF 등)를 모두 지우고 정해진 크기로 줄여 WebP 로만 저장한다. 원본은 저장하지 않는다.
보여 줄 때는 서버가 INV-A13 의 조건을 확인한 뒤 그 파일 하나에 60초짜리 서명 주소를 만들어 준다 — 영구 주소·공개 주소는 없다. 사진을 바꾸거나 지우면 옛 파일도 지운다.
(강제 위치: 저장소 — 비공개, 정책 없음 / 서버 — 사진 저장 경로 하나, 서명 주소는 A13 읽기 함수가 결과를 준 파일에만 / 시험 — 위치 정보가 든 사진을 올리고 저장된 파일에 사진 정보가 없는지)
위반 시: 사진 주소 하나가 퍼지면 승인 요청과 상관없이 누구나 연다. 팬 집 위치가 담긴 사진이 크리에이터에게 간다.

시나리오 (my-account 의 마지막 S11 다음)

## 2. 나만 보는 선물 메모 → `together.md` (INV-F7 · F8)

선물 정보 단계에 「나만 보는 메모」(선물 이름 20자·내용 200자, 둘 다 선택)가 생긴다. 보낸 팬 본인만 보고, 선물 상세·보낸 선물 목록에 나온다(결정 ②).
함께한 시간 스펙은 「팬 본인만 보는 기록」을 다루고 팬이 올린 선물 사진(INV-F2)도 같은 이유로 여기 있어서 이 파일에 붙인다.

**코드에서 확인한 지금의 길** — 새 칸이 이 길로 새면 안 된다.
- 주문 표(`orders`)·상자 표는 행 보안이 켜져 있고 정책이 하나도 없다. 앱 서버 코드도 이 표를 직접 읽지 않는다. 밖으로 나가는 길은 DB 함수뿐이다.
- 그 함수들은 안에서 주문 줄 전체(`select o.*`)를 잡기도 하지만(크리에이터 받은 선물 읽기, 추적기 반송 읽기, 차액·확인할 선물 처리 등) 돌려주는 칸은 하나씩 적혀 있다. 그래서 **메모를 주문 표의 칸으로 두면, 앞으로 누가 함수를 고치며 칸 하나를 더 적는 순간 바로 샌다.**
- 크리에이터·사무실·운영자에게 주문이 나가는 길: 승인 요청 목록·승인 내역·서명할 원문(`approval_payload_of` — 서명된 원문은 고칠 수 없다)·받은 선물·확인할 선물·추적기 반송·사무실 QR 조회·송장 출력 원문·관리자 결제 목록·알림 본문.
- **팬이 쓴 글이 이미 크리에이터에게 가는 칸이 있다**: 「물품 이름」(`item_kind`, 종류가 「기타」면 팬이 쓴 1~30자 글). 승인 요청 카드·승인 내역·확인할 선물·답장에 그대로 나간다. 메모의 「선물 이름」과 이름이 비슷해 섞이기 쉽다.
- 결제사로 가는 주문 이름은 고정 문구(「팬꾹 선물 전달 {주문번호}」)라 메모가 들어갈 자리가 없다.

**INV-F7**: 메모는 선물 이름(앞뒤 공백을 뺀 0~20자, 한 줄)과 내용(앞뒤 공백을 뺀 0~200자, 줄바꿈 허용) 두 칸이고 둘 다 선택이다. 둘 다 비면 저장하지 않는다.
메모는 주문 표가 아니라 **메모만 담는 따로 된 표**에 주문당 한 줄로 두고, 그 표는 행 보안을 켜고 정책을 두지 않으며 화면 쪽 키(익명·로그인 사용자)에 권한이 없다.
메모는 등록과 같은 처리에서 저장되고, 메모 주인은 서버가 세션에서 확인한 보낸 사람이다(등록 함수의 보낸 사람과 같다). 메모는 물품 이름(`item_kind`)을 채우지 않고, 물품 이름은 메모를 채우지 않는다.
등록 화면은 「기타」 물품 이름 칸에 「크리에이터에게 보여요」를, 메모 칸에 「나만 볼 수 있어요」를 붙여 둘을 구분한다.
(강제 위치: DB — 따로 된 표, 권한 회수, 길이 제약 / 서버 입력 경계 / 등록 처리)
위반 시: 메모가 주문 칸이면 크리에이터·운영자용 함수를 고치다 한 칸만 더 적어도 샌다. 팬이 「기타」 글을 나만 보는 줄 알고 개인적인 내용을 적어 크리에이터에게 간다.

**INV-F8**: 메모 표를 읽거나 쓰는 DB 함수는 정해진 셋뿐이다 — 등록 때 저장, 보낸 팬 본인의 선물 상세 읽기, 보낸 팬 본인의 보낸 선물 목록 읽기. 읽기 둘은 계정 ID 를 인자로 받지 않고 로그인 토큰의 계정이 그 주문의 보낸 사람일 때만 메모를 준다.
크리에이터·직원·대표 권한으로 부를 수 있는 어떤 함수의 응답에도, 승인 요청의 서명 원문, 알림 본문, 결제사로 가는 주문 이름, 공유 카드·미리보기·공지 이미지, 함께한 시간의 답장 카드 공유(gift-reply INV-G9)에도 메모는 없다.
(강제 위치: DB — 메모 표를 참조하는 함수 허용 목록 / 시험 — ① 구조: DB 함수 본문 전체에서 메모 표 이름을 참조하는 함수가 허용 목록 셋뿐인지 ② 응답: 알아볼 수 있는 표시 값을 메모로 심고, 크리에이터·직원·대표로 로그인해 열린 표·함수를 모두 불러 그 값이 한 번도 나오지 않는지, 보낸 팬으로는 선물 상세에 나오는지)
위반 시: 팬이 「나만 본다」고 믿고 쓴 글(예: 「고백 편지 들어 있음」)이 크리에이터나 운영자 화면에 나간다. 결정 ②가 깨진다.

**개인정보 노출 검사와의 관계** — 지금 배포 전 개인정보 노출 검사(address-protection INV-P9)는 익명·팬·크리에이터·직원·대표로 열린 표·함수를 모두 불러 **이름·전화번호·주소 꼴**의 칸 이름과 값을 찾는다. 메모는 자유 글이라 칸 이름(`memo` 등)도 값도 그 꼴에 걸리지 않는다 — 메모가 크리에이터 응답에 새도 그 검사는 0건이다.
그래서 INV-F8 의 시험 ①②가 따로 필요하다. 구현은 그 검사가 이미 가진 「모두 부르기」와 「pii 에 닿는 함수는 허용 목록에만」 구조 검사에 메모 표와 심은 값을 더하는 것으로 한다. 반대 방향 주의: 팬이 메모에 전화번호를 적으면 본인 선물 상세 응답에 전화번호 꼴이 나온다 — 시험 계정 메모에는 전화번호 꼴을 넣지 않는다(넣으면 그 검사가 본인 응답을 잡는다).

시나리오 (together 의 마지막 S6 다음)
- **S7** (INV-F7): Given 별빛이 등록하며 선물 이름 「생일 편지와 인형」, 내용 3줄 / When 별빛이 선물 상세·보낸 선물 목록을 봄 / Then 메모가 나온다. 주문의 물품 이름은 고른 종류 이름 그대로다.
- **S7b** (INV-F7, 실패경로): Given 선물 이름 21자 또는 내용 201자 / When 등록 / Then 400, 주문·메모 모두 생기지 않는다. 별빛 세션으로 메모 표를 직접 읽기·쓰기 / Then 거부.
- **S8** (INV-F8, 실패경로): Given 별빛의 주문에 표시 값 메모 / When 하루(받는 크리에이터)·직원·대표로 승인 요청 목록·승인 내역·서명 원문·받은 선물·확인할 선물·QR 조회·송장 출력 원문·관리자 결제 목록을 포함해 열린 함수를 모두 부름 / Then 그 값이 0번. 그 주문의 알림 줄 본문에도 없다.
- **S8b** (INV-F8, 실패경로): Given 메모 표 이름을 본문에 쓴 함수를 하나 심음 / When 구조 검사 / Then 허용 목록 밖이라 실패로 잡힌다(심은 위반이 잡히는지 보는 시험).

신뢰 경계
- 믿는 값: 세션에서 확인한 보낸 사람 ID, DB 함수가 돌려주는 칸 목록
- 믿지 않는 값: 화면이 보낸 메모 글(길이 검사 전), 요청 본문의 계정 ID

비범위

- 등록 뒤 메모 고치기·지우기
- 메모 안 글의 필터 — 본인만 보는 글이라 거르지 않는다

## 3. 크리에이터 팬덤 색 → `creator-link.md` (INV-E13 · E14)

**팬마크는 이미 있는 「팬덤 심볼」이다** — 시안 상세 설정의 「팬마크 올리기(정사각, JPG·PNG, 뱃지에 작게)」는 creator-link INV-E1·E9·E12 의 팬덤 심볼(정사각 자르기, 권리 확인 체크 필수)과 같은 것이라 새 INV 를 만들지 않는다.
다만 시안의 상세 설정 화면에는 **권리 확인 체크가 없다** — INV-E12 에 따라 구현 화면에는 「내가 만들었거나 쓸 권리가 있는 이미지예요」 체크를 넣어야 한다(체크 없이 올리면 서버가 거부한다).
**팬덤 이름은 지금 크리에이터 공개 정보 고치기 함수(`update_my_creator_profile`)의 칸이다**(마이그레이션 20261014000002 가 기본값이 「그대로 둠」인 인자로 더했다, my-account INV-A9). 두 색도 같은 함수에 같은 방식으로 더한다 — 상세 설정의 이름·색을 한 번에 저장하고, 색을 보내지 않는 지금의 호출은 색을 건드리지 않는다.

**INV-E13**: 크리에이터 색은 퍼스널 컬러와 팬컬러 두 칸이고, 각각 비어 있음(사이트 기본 모양) 또는 `#RRGGBB`(16진수 여섯 자리, 대문자로 저장)다. 그 크리에이터 본인만 바꾼다 —
크리에이터 공개 정보 고치기 함수(INV-A9 와 같은 경로, 크리에이터 ID 를 인자로 받지 않음)에 두 칸을 더하고, 보내지 않으면 그대로·빈 값이면 기본으로 되돌린다. 앱 서버가 먼저, DB 가 다시 형식을 검사하고 틀리면 아무 칸도 바꾸지 않는다.
두 색은 공개 값이다. 퍼스널 컬러는 크리에이터 페이지 맨 위 띠와 프로필 사진 테두리에만, 팬컬러는 팬덤 뱃지의 면에만 쓴다. 사이트의 버튼·링크·글자·선택·초점 표시와 미리보기·공지 이미지(INV-E10)에는 쓰지 않는다.
화면은 색을 스타일에 넣기 직전에 형식을 한 번 더 확인하고, 형식이 아니면 기본 모양으로 그린다.
(강제 위치: DB 함수 — 인자 목록·본인 계정 / DB 제약 — 두 칸의 형식 / 서버 입력 경계 / 화면 — 그리기 직전 형식 확인)
위반 시: 남의 페이지 색을 바꾼다. 형식 검사 없이 스타일에 넣으면 색 칸에 스타일 문장을 끼워 페이지 모양을 망가뜨리거나 가짜 버튼을 덮는다. 색이 버튼에 번지면 하늘색 규칙(design-rules 000절)이 깨진다.

**INV-E14**: 색 위의 글자색은 저장하지 않고 배경색에서 그때 계산한다 — 흰색과 #111827 가운데 그 배경과의 대비(WCAG 상대 휘도)가 큰 쪽이다. 크리에이터 페이지 띠·팬덤 뱃지·상세 설정 미리보기가 모두 같은 계산 하나를 쓴다.
두 글자색 어느 쪽으로도 대비가 4.5:1 에 못 미치는 색은 저장하지 않고 「글자가 잘 안 보여요 — 조금 밝게나 어둡게 골라 주세요」로 답한다 `(정할 것 Q3)`.
(강제 위치: 공용 계산 함수 하나 + 단위 시험(경계 색 포함) / 서버 입력 경계 — 대비 하한 / DB 제약은 형식만)
위반 시: 미리보기와 실제 페이지의 글자색이 달라진다. 밝은 팬컬러 위에 흰 글자가 얹혀 팬덤 이름이 안 읽힌다.

목록 고칠 문장 (승인된 문장이라 같이 승인받는다)
- my-account INV-A9: 「고칠 수 있는 칸은 공개 이름 · 소개글 · 팬덤 이름 · 찾기 노출 넷뿐이다」 → 「… 팬덤 이름 · 찾기 노출 · 퍼스널 컬러 · 팬컬러 여섯뿐이다(색의 규칙은 creator-link INV-E13·E14)」
- creator-link INV-E1 의 「본인만 바꾼다」 목록과 INV-E7 의 「공개 화면에 나가는 것」 목록에 퍼스널 컬러·팬컬러를 더한다.

시나리오 (creator-link 의 마지막 S11 다음)
- **S12** (INV-E13): Given 하루로 로그인 / When 퍼스널 컬러 `#1e3a8a`, 팬컬러 `#FFF59D` 저장 / Then `#1E3A8A`·`#FFF59D` 로 저장, 하루 페이지 띠·사진 테두리·뱃지 면에 쓰이고 버튼 색은 그대로. 팬덤 이름만 보내는 저장은 색을 건드리지 않는다.
- **S12b** (INV-E13, 실패경로): Given 하루로 로그인 / When 본문에 모모의 크리에이터 ID, 색 `red`·`#12345`·`#123456; background:url(x)` / Then 모모 그대로, 하루도 아무 칸도 안 바뀜(400). DB 함수를 직접 불러 형식 밖 값 → 거부. 팬 계정으로 부름 → 거부.
- **S13** (INV-E14): Given 팬컬러 `#FFF59D` / Then 뱃지 글자 #111827. `#1E3A8A` / Then 흰색. 같은 색으로 페이지 띠·뱃지·미리보기의 글자색이 같다.
- **S13b** (INV-E14, 실패경로): Given 두 글자색 모두 4.5:1 에 못 미치는 중간 회색(예: `#777777` 근처 경계 색) / When 저장 / Then 400, 저장되지 않음.

신뢰 경계
- 믿는 값: 로그인 토큰의 크리에이터, DB 제약을 통과해 저장된 색
- 믿지 않는 값: 화면이 보낸 색 문자열, 요청 본문의 크리에이터 ID

비범위
- 무늬·글꼴 고르기, 사이트 전체 테마 색(design-rules 10절 「테마 색·무늬·글꼴 고르기는 없다」 그대로)
- 미리보기·공지 이미지의 색(INV-E10 그대로 — 토큰 값만)

## 4. 해야 할 일 → 새 스펙 `action-center.md` (INV-J1 ~ J4)

```
feature: 해야 할 일 — 팬꾹이 요청한 조치를 모은 목록과 숫자 (action center)
status: draft
surfaces: [authz]
# authz: 해야 할 일은 그 사람 본인의 주문·상자에서만 만든다. 틀리면 남의 주문번호·금액·크리에이터가 보인다.
```

해야 할 일은 따로 저장되는 기록이 아니라 **다른 상태에서 파생된 목록**이다. 그래서 사고는 두 가지로 난다 — 사이드바 숫자·홈 한 줄·페이지 목록이 서로 다른 수를 말하거나(시안에서도 크리에이터 사이드바는 1, 페이지 제목은 3건이었다), 이미 처리한 일이 남아 있거나 처리할 수 없는 일이 버튼과 함께 보인다.

**지금 코드·스펙에 실제로 있는 「사람이 해야 진행되는 상태」** (지어낸 것 없음)

| 종류 | 누가 | 원천 | 하는 일 | 미루면 |
|---|---|---|---|---|
| 추가 결제 | 그 주문을 보낸 계정 | 차액 결제 요청(payment INV-M11~M13, 결제 표의 차액 줄, 알림 「추가 결제 요청」) | 차액 결제 | 7일 뒤 반송 대상 |
| 도착하지 않은 상자 | 그 주문을 보낸 계정 | 결제 완료 뒤 14일이 지나도 입고 전인 상자(office-workflow INV-W10, 알림 「아직 도착하지 않은 상자」) | 「받는 주소 없이 보냈어요」 찾기 — 송장번호·택배사·이름 앞 한 글자(inbound-address-code INV-C4 ②) | 30일에 그 상자가 닫히고 환불이 바뀜 |
| 확인할 선물 | 받는 크리에이터 | 블루투스·RF 가 나온 상자의 크리에이터 확인 대기(`my_creator_checks`, 알림 「확인할 선물」) | 받기 / 돌려보내기 | 7일 뒤 반송 |
| 역조공 받기 `(정할 것 Q4)` | 몫의 받는 팬 | 결제가 끝난 몫의 받기 대기(reverse-gift INV-R10) | 받기 / 받지 않기 | 7일 뒤 받지 않음 |

시안의 「받는 주소 없이 온 상자」(팬)는 따로 카드가 되지 않는다 — 주인을 모르는 상자는 누구에게도 보이지 않아야 하고(INV-C10), 팬 쪽에서는 「도착하지 않은 상자」 카드의 찾기가 바로 그 일이다.
**넣지 않는 것**: 승인 대기(자기 메뉴와 숫자가 있다), 정보만 주는 알림(추적기 반송·돌려보낼 상자·거절 뒤 늦은 상자·전해지지 못한 선물·결제 취소 — 할 수 있는 일이 없다), 「제가 보낸 게 아니에요」(요청한 일이 아니다), 시안의 크리에이터 카드 셋 `(정할 것 Q5)`.

**INV-J1**: 해야 할 일 카드는 위 표의 종류뿐이고, 카드 하나는 상자(역조공은 몫) 하나의 일 하나다. 카드는 저장하지 않고 읽을 때마다 원천 상태에서 계산한다 — 할 일 표·숫자 칸·「읽음」 표시가 없다.
각 종류의 「보이는 조건」은 그 일을 처리하는 기존 함수가 처리를 받아 주는 조건과 같은 판정에서 나온다: 추가 결제는 차액 결제를 시작할 수 있는 상태(미결제·요청 뒤 168시간 전·주문 진행 중)일 때만, 도착하지 않은 상자는 결제 완료 뒤 336시간이 지났고 그 상자가 아직 입고 전이며 닫히지 않았고 주문이 진행 중일 때만, 확인할 선물은 답이 없고 기한 전이며 주문이 진행 중일 때만.
시간은 서버 시각의 경과 시간으로 세고(INV-W6 과 같다), 카드에 보이는 기한은 서울 시간으로 쓴다.
(강제 위치: DB 읽기 함수 하나 — 종류별 조건을 기존 처리 함수와 같은 판정에서 / 시험 — 종류마다 조건 경계)
위반 시: 이미 낸 차액이 「결제하기」로 남아 두 번 내려 하거나, 기한이 지나 처리할 수 없는 카드가 버튼과 함께 남는다. 저장된 숫자가 원천과 어긋나 「해야 할 일 2」인데 목록이 빈다.

**INV-J2**: 사이드바 숫자 뱃지·홈의 「해야 할 일 N건」 한 줄·해야 할 일 페이지 목록·선물 상세 맨 위 한 줄은 모두 INV-J1 의 같은 읽기 함수 하나의 결과에서 나온다 — 숫자는 그 결과의 줄 수이고, 따로 세는 함수가 없다.
0건이면 뱃지와 홈 한 줄이 없고 페이지는 빈 상태다. 응답은 캐시하지 않는다.
(강제 위치: 서버 — 화면들이 같은 읽기를 쓴다 / 시험 — 같은 상태에서 뱃지 수·홈 수·목록 길이가 같다)
위반 시: 시안처럼 사이드바와 페이지가 다른 수를 말해 사람이 어느 쪽을 믿을지 모른다.

**INV-J3**: 해야 할 일 읽기 함수는 계정·크리에이터 ID 를 인자로 받지 않는다. 로그인 토큰의 계정이 보낸 주문(역할과 상관없이 — 크리에이터가 다른 크리에이터에게 보낸 선물도), 그 계정이 받는 팬인 역조공 몫, 그 계정의 크리에이터가 받는 상자의 확인 대기만 돌려준다.
직원·대표·로그인하지 않은 사람에게는 0줄이다. 카드의 칸은 그 사람이 기존 읽기 함수로 이미 받는 칸을 넘지 않는다 — 크리에이터 카드에는 팬 실명·주소·연락처·원 송장번호가 없고(INV-W7·W9), 팬 카드에는 크리에이터 주소가 없다. 메모(together INV-F8)는 들어가지 않는다.
(강제 위치: DB 읽기 함수 — 인자 목록, `auth.uid()` 조건, 반환 칸)
위반 시: 남의 주문번호·차액 금액·받는 크리에이터가 보인다. 크리에이터가 카드로 팬 정보를 더 얻는다.

**INV-J4**: 카드의 버튼은 새 처리 함수를 만들지 않고 그 일의 기존 처리(차액 결제 준비, 「받는 주소 없이 보냈어요」 찾기, 확인할 선물 답, 역조공 받기)를 그대로 부른다. 처리가 끝나면 다음 읽기에서 그 카드는 없다.
찾기의 세 값이 맞지 않아 이어지지 않으면 카드는 그대로 남는다 — 카드는 누른 기록이 아니라 상자 상태로 사라진다. 차액 결제가 「승인 중」인 동안은 결제를 다시 시작할 수 없으므로 카드가 없고, 결제가 실패하거나 취소되면 다시 생긴다.
(강제 위치: 서버 — 버튼이 기존 처리 경로를 부름 / 시험 — 처리 전후로 같은 읽기의 줄 수)
위반 시: 해야 할 일 화면에만 있는 처리 길이 기존 규칙(차액 금액 계산·매칭 세 값·확인 기한)을 건너뛴다. 찾기를 눌렀다는 이유만으로 카드가 사라져 상자를 못 찾은 채 30일 닫힘을 맞는다.

시나리오
- **S1** (INV-J1): Given 별빛의 주문에 차액 요청(미결제, 요청 뒤 2일), 결제 뒤 15일 된 입고 전 상자, 결제 뒤 13일 된 입고 전 상자 / When 해야 할 일 읽기 / Then 추가 결제 1·도착하지 않은 상자 1(15일 된 것만).
- **S1b** (INV-J1, 실패경로): Given 차액 결제 완료, 요청 뒤 8일 미결제(반송 대상), 30일이 지나 닫힌 상자, 거절로 끝난 주문의 입고 전 상자 / When 읽기 / Then 카드 없음.
- **S1c** (INV-J1): Given 하루에게 확인 대기 상자 하나(답 없음) / When 하루로 읽기 / Then 확인할 선물 1. 답한 뒤·기한이 지난 뒤 / Then 없음.
- **S2** (INV-J2): Given 별빛에게 카드 2 / When 사이드바·홈·해야 할 일 페이지를 봄 / Then 뱃지 2·「2건」·카드 2. 둘 다 처리한 뒤 / Then 뱃지 없음·홈 줄 없음·빈 상태.
- **S2b** (INV-J2, 실패경로): Given 사이드바 숫자를 따로 세는 경로를 하나 심음 / When 같은 상태에서 비교 시험 / Then 수가 달라 실패로 잡힌다.
- **S3** (INV-J3, 실패경로): Given 별빛·달토끼 각자 카드 / When 별빛이 읽기, 본문·주소에 달토끼 ID / Then 별빛 것만. 직원·대표·로그인 안 함 / Then 0줄. 하루의 확인할 선물 카드 응답에 팬 실명·주소·연락처·원 송장번호·메모가 없다.
- **S3b** (INV-J3): Given 하루(크리에이터)가 모모에게 보낸 선물에 차액 요청 / When 하루로 읽기 / Then 추가 결제 카드 1(확인할 선물 카드와 함께).
- **S4** (INV-J4): Given 도착하지 않은 상자 카드 / When 세 값이 맞는 찾기 / Then 상자가 이어지고 카드가 사라진다.
- **S4b** (INV-J4, 실패경로): Given 같은 카드 / When 세 값이 틀린 찾기 / Then 카드가 남는다. Given 차액 결제가 승인 중 / Then 카드 없음, 실패로 끝나면 다시 있음.

신뢰 경계
- 믿는 값: Supabase Auth 가 검증한 사용자 ID, DB 의 주문·상자·결제·확인 대기 상태, 서버 시각
- 믿지 않는 값: 요청 본문·주소의 ID, 화면이 기억하는 숫자, 브라우저 시각

비범위
- 승인 대기 — 자기 메뉴와 숫자를 그대로 쓴다
- 시안의 크리에이터 카드 셋(받는 주소 없이 온 상자의 팬 고르기·대신 포장 상자값·크리에이터 몫 상자 늦은 도착) `(정할 것 Q5)`
- 해야 할 일 알림 — 카드마다 원천 알림(추가 결제 요청·아직 도착하지 않은 상자·확인할 선물)이 이미 있다. 새 알림 종류는 만들지 않는다
