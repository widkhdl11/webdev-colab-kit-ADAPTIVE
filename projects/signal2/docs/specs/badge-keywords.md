# 뱃지 키워드 — 뽑기와 저장

글마다 모델이 키워드를 만들어 붙이고, 그것이 피드 위 뱃지 줄의 재료가 된다.

**어기면 사고인 핵심 위험은 하나다: 같은 뜻이 여러 표기로 갈리는 것.** 갈리면  
"프론트엔드 3건"이 되어야 할 것이 "프론트엔드 1 / 웹 프론트엔드 1 / 프론트엔드 개발 1"이 되고,  
뱃지가 고를 수 없을 만큼 잘게 늘어난다. 반대 방향의 실패도 있다 — 너무 세게 합치면  
새로 생긴 분야가 기존 이름에 흡수돼 **지금 고정 5개 태그와 똑같은 상태로 돌아간다.**  
이 스펙은 그 사이를 잡는다.

> 아래 본문은 `keywords-and-kinds.md` 쪽 조항을 접두 없이 `K5 조항` 처럼 가리킨다.  
> 예전에는 본문에서 `INV-` 를 한 번 적기만 해도 그 불변식의 테스트가 요구돼서 그렇게 썼다.  
> 2026-08-31 부터는 줄 맨 앞의 정의 앵커(`- INV-X:`)만 세므로 인용해도 요구가 생기지 않는다.  
> 표기는 굳이 되돌리지 않고 둔다.

## 불변식

- INV-B1: 뱃지 키워드는 **글마다 모델이 만든다.** 어느 축도 목록에서 고르게 하지 않는다.  
**축은 둘이다** — `분야`(무엇에 대한 글인가, 1~~3개)와~~ `사건종류`~~(무슨 일이 일어났나, 0~~2개).  
(강제 위치: 서버 — 프롬프트가 두 질문을 따로 하고 어디에도 "다음 목록에서만 고른다"가 없다  
/ DB — 축을 가르는 칸)  
위반 시(목록에서 고르게 하면): **지금 고정 5개와 똑같은 상태가 된다.** 새로 생긴 분야가  
비슷한 기존 이름으로 흡수된다.
  - **축을 나눈 근거는 실측이다** (2026-08-15, 690건). "이 글이 다루는 것"만 물었더니  
  **107종이 전부 분야였고 사건종류가 한 건도 안 나왔다** — `출시`·`규제`·`사건사고` 류가 0개다.  
  **안 물으면 안 만든다.** 그래서 질문을 둘로 나눴다.
  - 앵커 목록은 **축마다 따로** 준다. 한 목록으로 합치면 모델이 사건종류 자리에 분야를 쓴다.
- INV-B2: **표기 기준**을 지킨다. 여섯은 모델이, 마지막 하나는 코드가 강제한다.  
① 한국어 기본, 제품·회사 이름과 널리 원어로 쓰는 기술 용어는 원어(MCP·RAG·LLM) — INV-K4 와 같은 규칙  
② 수식어를 안 붙인다(`웹 프론트엔드` → `프론트엔드`) ③ 버전·숫자를 뺀다(`Next.js 16` → `Next.js`)  
④ 꼬리말을 안 붙인다(`투자 소식`·`보안 관련` → `투자`·`보안`) ⑤ 명사형, 조사·복수 없이  
⑥ 아래 INV-B3 ⑦ **코드**: 소문자화·공백/하이픈 통일·양끝 공백 제거  
(강제 위치: 서버 — 프롬프트 지시 / DB — `normalized_name` unique, INV-T2 를 그대로 쓴다)  
위반 시: 같은 뜻이 여러 표기로 갈려 **뱃지가 쪼개진다.**
  - **기준 문장 자체는 불변식이 아니라 설정이다** → "열린 값". `TOPIC_SCOPE` 와 같은 성격이라  
  유닛 테스트가 옳고 그름을 못 잡는다. 확인은 실제로 돌려 나온 목록을 보고 한다.
  - 갈림은 세 층인데 잡히는 정도가 다르다: **글자 모양**(`Next.js`/`NextJS`)은 ⑦ 이 완전히 잡고,  
  **언어**(`프론트엔드`/`frontend`)는 ① 이 잡고, **입도·동의어**(`웹 프론트엔드`)는  
  규칙만으로는 부분적이라 INV-B3 가 필요하다.
- INV-B3: 이미 쓰인 키워드 목록을 프롬프트에 함께 주고, **같은 뜻이 목록에 있으면 그것을 쓴다**(합친다).  
(강제 위치: 서버 — 프롬프트 지시 + 같은 뜻의 다른 표기가 새 행을 만들지 않는지 보는 테스트)  
위반 시: 규칙 문장은 모델이 매번 해석해야 하지만 **목록은 대조만 하면 된다.** 목록을 안 주면  
② ~ ⑤ 가 날마다 다르게 적용돼 입도 갈림이 그대로 남는다.
  - **빈 목록은 아예 안 싣는다.** 빈 채로 실으면 모델이 그걸 제약("이 중에서 골라라")으로 읽는다.
  - 목록에는 상한이 있다(INV-K6).
  - planned 문서의 **K5 조항과 정반대 규칙이다.** 그쪽은 "목록에 없는 새 개념이면 반드시 새로  
  만든다"인데, 새 개념(`루프 엔지니어링`)이 기존 것에 흡수돼 **새로 생겼다는 사실 자체가**  
  **사라지는 것**을 막으려는 조항이다. 뱃지 키워드는 반대로 **합쳐져야** 한다.  
  한 규칙을 둘 다에 걸 수 없다 — **지금은 새 개념 키워드를 안 만들므로 합치는 쪽으로 간다**(비범위).
- INV-K1: 키워드는 글마다 생성하고 **누적한다.** 같은 이름이 다시 나오면 새 행을 만들지 않고  
기존 행에 항목을 연결한다. (강제 위치: DB — unique(`normalized_name`), INV-T2 를 그대로 쓴다)  
위반 시: 같은 말이 여러 행으로 갈려 세는 것도 필터도 쪼개진다.
  - **한 글에 같은 키워드를 두 번 연결하면 안 된다.** `item_tag` 는 `(item_id, tag_id)` 가  
  기본키라, 두 번 연결하려 들면 **그 글의 키워드가 하나도 안 붙는다.** 그래서 응답을 읽는  
  단계에서 이미 접어야 하고, **접는 기준이 저장 유일성 기준과 같아야** 한다 —  
  다른 기준으로 접으면 여기서 통과한 두 값이 저장 단계에서 한 행으로 합쳐진다.
- INV-K4: 표기는 **한국어가 기본이되 고유명사와 널리 원어로 쓰는 기술 용어는 원어**로 둔다  
(제품·회사 이름, MCP·RAG·LLM 등). (강제 위치: 서버 — 프롬프트 지시)  
위반 시: 같은 개념이 영어·한국어로 갈리면 누적이 쪼개진다. 반대로 전부 한국어로 옮기면  
"모델 컨텍스트 프로토콜" 같은 표기가 나와 오히려 못 알아본다.
- INV-K6: 프롬프트에 싣는 목록에는 상한이 있다. (강제 위치: 서버 — **부르는 쪽**이 자른다)  
위반 시: 목록이 항목마다 통째로 실리므로 키워드가 늘수록 비용이 선형으로 는다.  
실측(2026-08-10): 100개가 898 입력 토큰.
  - **자를 때 자주 나온 것부터 남긴다** — 표기를 맞출 값은 흔한 말이지 한 번 나온 말이 아니다.
  - 지시문 조립은 **하나도 안 자른다.** 자르는 자리가 둘이면 상한이 두 번 걸려 실제로 실리는  
  개수가 상한보다 적어진다.

## 시나리오

- BK1 (INV-B1): Given 글 하나 / When 지시문 조립 / Then `분야` 와 `사건종류` 를 **따로** 묻는다.
- BK2 (INV-B1, 실패경로): Given 지시문 / When 전문을 훑는다 /  
Then 두 축 어디에도 "다음 목록에서만 고른다"에 해당하는 문장이 없다.
- BK3 (INV-B1): Given 기존 목록에 없는 분야의 글 / When 키워드 생성 /  
Then 기존 키워드로 흡수되지 않고 **새 키워드가 생긴다.**
- BK4 (INV-B2): Given 표기 기준 / When 지시문 조립 / Then 기준 문장이 **비어 있지 않은 채로 전부** 실린다.
- BK5 (INV-B2, 실패경로): Given 모델이 `Next.js 16` · `투자 소식` · `에이전트들` 을 돌려줌 /  
When 저장 / Then 각각 `Next.js` · `투자` · `에이전트` 로 남는다.
- BK6 (INV-B3): Given 키워드 "프론트엔드" 가 이미 있고 다른 글이 "웹 프론트엔드" 를 다룸 /  
When 키워드 생성 / Then 새 행이 생기지 않고 "프론트엔드" 에 연결된다.
- BK7 (INV-B3, 실패경로): Given 한 축의 앵커 목록이 비어 있음 / When 지시문 조립 /  
Then **그 축의 목록 문장 자체가 안 실린다** (빈 목록을 제약으로 읽지 않게).
- BK8 (INV-B3): Given 두 축의 앵커 목록 / When 지시문 조립 / Then 축마다 따로 실려 서로 안 섞인다.
- BK9 (INV-K1): Given 키워드 "MCP" 가 이미 있음 / When 다른 글에서 "mcp" 가 나옴 /  
Then 새 행이 생기지 않고 기존 행에 연결된다.
- BK10 (INV-K1, 실패경로): Given 한 글의 응답에 `온-디바이스` 와 `온_디바이스` 가 같이 옴 /  
When 저장 / Then 하나만 남는다 — 둘 다 살아남으면 같은 글에 같은 `tag_id` 를 두 번 연결해  
**그 글의 키워드가 전부 안 붙는다.**
- BK11 (INV-K4): Given 제품명 `DeepSearcher` 가 나오는 글 / When 키워드 추출 /  
Then 그 이름은 번역되지 않는다.
- BK12 (INV-K4, 실패경로): Given 지시문 / When 전문을 훑는다 /  
Then "전부 한국어로 옮겨라"에 해당하는 문장이 없고, 원어를 유지하라는 예외가 실려 있다.
- BK13 (INV-K6): Given 키워드가 상한보다 많이 쌓인 상태 / When 목록을 만든다 /  
Then 실리는 목록이 상한을 넘지 않고 **자주 나온 것부터** 남는다.
- BK14 (INV-K6, 실패경로): Given 상한보다 많은 목록 / When 지시문 조립 /  
Then 조립은 **하나도 안 자른다** — 자르는 자리는 부르는 쪽 하나뿐이다.

## 신뢰 경계

- **믿는 값**: `normalized_name` 의 유일성(DB 제약) · `item_tag` 의 기본키 ·  
우리가 조립한 지시문 · 우리가 센 건수.
- **믿지 않는 값**: **모델 응답 전체.** 이것은 남의 글을 읽은 모델의 출력이다.
  - 배열이 아닌 값·빈 문자열·너무 긴 값(문장을 돌려주면 뱃지 줄이 통째로 깨진다)·  
  제어문자가 든 값은 버린다. 제어문자는 **잘라 쓰지 않고 통째로 버린다** —  
  그 값이 다음 호출의 지시문에 실리는데(INV-B3), 개행 하나면 우리 규칙 줄과 똑같이 생긴  
  줄을 만들 수 있다.
  - **잘린 응답(**`stop_reason: "max_tokens"`**)은 읽히더라도 답이 아니다.** 키워드는 누적되고  
  쌓인 목록이 다음 호출의 표기 기준이 되므로(INV-B3), 잘린 목록을 한 번 저장하면  
  그 뒤로 모든 글이 그 표기에 맞춰진다.
  - **"못 읽었다"와 "짚이는 게 없다"를 구별한다.** 실패를 빈 값으로 뭉개면 파싱이 통째로  
  깨진 주기가 "이 글들엔 키워드가 없었다"로 보인다 — 리포트가 정상처럼 읽히고 뱃지 줄만 비어 간다.

## 비범위

- **새 개념 키워드** — 처음 나온 개념을 기존 것에 흡수시키지 않고 새로 세우는 것  
(planned 문서의 K2·K3·K5 조항). INV-B3 와 정반대 규칙이라 한 호출에 둘 다 걸 수 없다.  
켤 때는 두 종류를 가르든지 프롬프트에서 두 질문으로 나눈다.
- **화면** — 뱃지 줄의 창 길이·두 축 색·카드 표시. 시각 기준은  
`docs/design/design-rules.md` 2026-08-27 블록에 승인돼 있고, 조항은 planned 에 남아 있다.  
화면을 만들 때 여기로 옮긴다.
- **갈래 판정과 소식 배치** — 핫이슈 문턱·문 배정·이슈성. planned 에 그대로 있다.
- **의미 검색(임베딩)으로 같은 뜻 합치기.** 키워드가 0개인 상태에서는 "얼마나 비슷하면 같은  
것인가"의 기준을 정할 근거가 없다. 다시 볼 조건: 같은 개념이 다른 이름으로 갈린 것이  
**실제로 관찰됐을 때.**
- **기존 고정 5개 태그와 그에 붙은** `item_tag` **연결의 정리** — 지우지 않고 둔다.  
지금 지우면 피드의 필터 칩 5개가 빈 결과를 내는데 대체할 뱃지 줄이 아직 없다.  
**뱃지 줄이 화면에 붙을 때 칩과 함께 정리한다.**
  - 마이그레이션 `0006_tag_axis` 가 이 다섯 행을 `axis = 'legacy'` 로 갈라 뒀다(2026-08-27 적용 확인:  
  `tag` 5행 전부 legacy · `item_tag` **701건**). 그래야 뱃지 줄이 켜지는 날 옛 태그가  
  분야 뱃지로 섞여 나오지 않고 한 줄로 걸러진다.
  - 건수는 계속 는다 — 8/15 에 475건이던 것이 재수집으로 701건이 됐다. **정리 시점의 값을**  
  **다시 재고 지운다**(이 숫자를 근거로 쓰지 마라).
