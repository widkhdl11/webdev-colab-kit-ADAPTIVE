# DECISIONS — signal

트레이드오프가 있던 결정만 한 줄씩. 이유의 상세는 PRODUCT.md / 스펙.

- **수집 구조 = 런타임 + Supabase** (정적 빌드타임 아님): 랭킹·상태 저장 등 기능 우선. 정적보다 무겁고 유지비 있음.
- **신호 선별 = 랭킹까지 포함** (단순 최신순 아님): '뜨는 것' 정렬이 핵심 가치. 점수가 시변·파생 → /spec 예정.
- **상세 = 원문 전문 표시** (링크아웃 아님): 사이트 안에서 바로 읽기 우선. 본문 추출 난이도 + 저작권 표면 감수. _(2026-08-09 단서: "전문"은 **얻어졌을 때**다. 봇을 막는 사이트에서는 추출이 실패하고(OpenAI 403 실측), 그때 상세는 없다고 밝히고 출처로 보낸다 — 아래 INV-S5 항목)_
- **읽음·북마크 = MVP 제외, 후순위**: 범위를 좁혀 수집·랭킹·필터에 집중.
- **페이지 = 피드 + 상세 2개** (소스 관리 화면 없음): 소스 목록은 설정파일로.
- **프레임워크 = Next.js (App Router)** (Vite/SPA 아님): 웹 노출(SSR/SEO) + 기존 Next+FSD 경험. Vite→Next 전환은 signal 한정, 전역 게이트 불변. 프로파일 nextjs-fsd(pages 제거·app 통일, provider는 shared).
- **원문 표시 방식 = sanitize 후 렌더** (2026-08-02 spec): 화이트리스트 sanitize + html-react-parser. iframe 격리는 X-Frame-Options·높이제어 문제로 탈락. dangerouslySetInnerHTML 금지(게이트). → content-safety.md
- **요약 = AI 생성(Claude)** (2026-08-02 spec): RSS 요약 품질 편차 회피, 한국어 통일. 실패 시 null 적재 후 재시도, summary IS NULL만 재생성(비용). 요약은 신뢰경계 밖—원문이 진실. @anthropic-ai/sdk는 요약 구현 시 설치.
- **랭킹 = 시간감쇠 × 소스 weight(설정파일)** (2026-08-02 spec): 최신성만이면 랭킹=최신순이 돼 '뜨는 것' 가치 소멸 → 정적 소스 weight를 곱함. 앵커 패턴(점수 저장 안 함, 조회 시 계산 → 배치 사고·낡음 원천봉쇄). 외부 인기신호(HN points 등)는 시변 외부값이라 재수집 부담 → MVP 제외. → ingestion-ranking.md
- **중복제거 = 정규화 원문 URL** (2026-08-02 spec): utm_*·fbclid 등 추적파라미터·fragment 제거, 소문자화. 재수집은 upsert(중복 안 쌓임).
- **시각 방향 = 톤 a 인디고 + 밝은 회색 페이지 위 밝은 카드** (2026-08-02 checkpoint 1차): 레퍼런스 biko 는 흰 페이지+회색 카드였으나 "너무 하얘서 눈이 아프다" 피드백으로 명암을 뒤집음. 매일 훑는 리더라 눈부심이 비용. 부수효과로 카드 분리가 뚜렷해짐. 메타색은 그만큼 한 단계 낮춰 대비 재확보(#6A6F77→#656A72).
- **읽음 표시 = MVP로 승격** (2026-08-02, 위 "MVP 제외" 결정을 뒤집음): 사용자 요청. 로그인이 없어 브라우저 로컬에만 저장 → 서버·스키마 변경 없음, 기기 간 동기화 없음. 값이 싸서 승격이 가능했던 것. 흐릿하게 하되 대비 4.5:1 유지·호버 복원(읽은 글도 다시 찾을 수 있어야).
- **피드 = 날짜 그룹 1차, 정렬 2차** (2026-08-02): 수집이 매일 아침 1회 배치라 "오늘 뭐 왔지"가 기본 질문. 점수가 날짜를 가로지르면 하루 단위로 훑을 수 없음. 대안(정렬 1차·평면 목록)은 '뜨는순'에서 날짜가 뒤섞여 탈락. 갱신 주기가 바뀌면 이 결정도 다시 본다.
- **읽음 기록 시점 = 상세 화면 마운트** (2026-08-06, 목록 클릭 아님): 클릭 시점에 찍으면 이동이 실패했을 때(라우트 부재·네트워크) 읽지도 않은 글이 흐릿하게 굳고 localStorage라 새로고침해도 안 풀린다. PRODUCT의 "이미 **연** 소식" 정의와 어긋남. 대가는 상세를 열자마자 읽음이 된다는 것(스크롤 여부·체류 시간은 안 본다) — 개인용이라 그 정밀도가 필요 없다.
- **랭킹 점수·'뜨는 중'은 화면이 만들지 않는다** (2026-08-06): 계산식이 ingestion-ranking.md 에 파킹된 상태라, 더미 데이터가 `score`·`isTrending` 을 들고 오고 화면은 표시만 한다. 대가는 지금 값이 가짜라는 것. 대신 스펙을 켤 때 화면을 안 고쳐도 된다. (열린 질문이었던 '그룹 안 상위'의 기준은 2026-08-09 에 정해짐 — 아래)
- **'뜨는 중' 판정 = 필터·정렬을 걸기 전 목록 기준, 날짜 그룹 안 상위 `TRENDING_TOP_N`개(기본 3)** (2026-08-09, INV-R5 신설): 대안은 필터 결과 안에서 다시 상위를 뽑는 것이었는데, 그러면 **같은 글이 필터에 따라 뱃지가 붙었다 떨어져** 뱃지가 무슨 뜻인지 알 수 없게 된다. 대가는 태그 필터를 걸면 결과 상단에 뱃지가 하나도 없을 수 있다는 것 — "지금 전체에서 뜨는 것"이라는 뜻을 지키는 쪽을 택했다. 개수는 어느 문서에도 없었다(design-rules 는 "그룹 안에서의 상위"까지만 정함). 참/거짓을 판정하려면 수가 필요해서 설정값으로 뒀다.
- **카드 밀도 = A(숨 쉴 곳) + B(출처 표식)** (2026-08-06 비교 시안 승인): "너무 글자글자글자~" 피드백. 요약 3→2줄로 정보량을 줄이고 여백을 키웠다 — 훑는 속도가 목적이라 요약 한 줄보다 밀도가 비싸다는 판단. 출처 이니셜 원은 요소를 하나 늘리는 대가로 훑을 기준점을 얻는다(색은 안 씀 — 포인트색은 "아직 안 본 것" 전용 규칙 유지). C안(제목 17px·요약 연하게)은 효과는 있으나 타이포 단계를 하나 더 늘려 보류.
- **아웃바운드 URL 스킴 = 허용 목록, 본문과 출처를 나눔** (2026-08-06 INV-D6 신설): sanitize 는 본문만 훑으므로 본문 밖 필드인 `sourceUrl` 은 방벽 밖이었다. 본문 링크는 `http·https·mailto`(원문에 이메일 링크가 온다), 출처 링크는 `http·https` 만 — 출처는 웹 주소라 mailto 를 받을 이유가 없고, 넓게 잡으면 나중에 왜 넓은지 아무도 설명 못 한다. 스킴 목록의 정본은 한 곳(`features/content-render/lib/url-safety.ts`). **URL 정리(제어문자·공백 제거)는 보안 장치가 아니다** — 문자를 지우기만 하므로 허용 범위를 넓히는 방향으로만 작동한다. 실제 역할은 멀쩡한 URL 을 잃지 않는 것과 "검사한 문자열 = 렌더할 문자열"을 맞추는 것.
- **AI 요약 박스 = 16px** (2026-08-06 checkpoint, 15px 에서 올림): `ui-layers` 의 "본문 16px 이상" 하한을 요약도 지킨다. 하한 예외의 근거가 "목록 미리보기는 본문이 아니다"인데 상세의 요약은 실제로 읽는 여러 문장이라 예외에 해당하지 않는다. 대가는 원문(17px)과 1px 차이밖에 안 남는다는 것 — 위계를 면·색·왼쪽 포인트선·줄높이 네 축으로 옮겨서 갚았다. 함께 "하한이 걸리는 자리(본문)와 안 걸리는 자리(문장에 딸린 부속: small·figcaption·첨자)"를 문서에 명시했다. 예외 목록이 짧았던 것이 이 혼란의 원인이었다.
- **원문 제목 h1~h6 = 크기 두 값(20/17) + 굵기·색·여백** (2026-08-06 checkpoint): 스펙이 허용하는 태그에 시각 기준이 없어 구현이 값을 발명할 수 없었다. "단계를 늘리지 말고 굵기로" 규칙을 지키려면 17px 아래로 못 내려간다(제목이 본문보다 작아지면 위계가 뒤집힌다). 그래서 h4~h6 은 굵기를 600 으로 고정하고 색 사다리(`--text→--text2→--meta`)로 나눴다. 원문 h1 은 페이지 제목(28px)과 경쟁하지 않게 20px 로 누르고 점선 밑선으로 구획만 표시. (h1 이 둘이 되는 문제는 2026-08-08 에 결론 — 아래)
- **`h1` 이 둘인 것을 그대로 두고, 색과 레이아웃으로 가른다** (2026-08-08, 2026-08-06 미결 해소): 파서에서 원문 제목을 한 단계 강등(h1→h2)하는 안을 검토했으나 채택 안 함 — HTML5 에서 h1 이 여럿인 건 위반이 아니고, 강등은 문서 개요를 위해 **원문 마크업을 우리가 고쳐 쓰는 일**이다. 대신 눈으로 갈리게 했다: 우리가 붙인 페이지 제목은 포인트색(`--accent`), 출처가 쓴 제목은 먹색 + 왼쪽 세로선. **대가는 스크린리더**다 — 색과 선은 시각 신호라 제목 목록에는 안 나타나고, 거기서는 두 h1 이 여전히 같은 층으로 보인다. 이 대가를 알고 고른 것이다. 부수적으로 design-rules 의 "포인트색은 면적을 최소로" 규칙이 페이지 제목까지 넓어졌다(전면 배경 금지는 유지).
- **원문 이미지의 `width`·`height` 를 허용한다 — 조건 넷을 다 만족할 때만** (2026-08-08, INV-D2 확장): 자리를 미리 비워 이미지가 뜰 때 아래 글이 밀리는 것을 막는다. 조건은 ① 둘 다 있음 ② 둘 다 양의 정수 ③ 비율 10:1 이내 ④ 각 값 20000 이하. 하나라도 어긋나면 **둘 다** 버린다(하나로는 비율을 못 구한다). ③·④ 가 필요한 이유는 정수 검사만으로는 `width="1" height="99999"` 같은 거짓 치수를 못 막기 때문 — 믿고 자리를 비우면 높이 0 에서 튀어오르는 것보다 나쁜 빈 공간이 생긴다. **대가는 화이트리스트에 "값도 보는" 규칙이 처음 생긴 것**이고, 그래서 경계(이 둘뿐)를 스펙·코드 양쪽에 못 박았다. 치수 없는 이미지는 CSS 가 16:9 로 대신 예약한다. 함께 **`src` 를 잃은 이미지는 태그째 버린다**(빈 상자가 "여기 그림이 있다"고 거짓말하지 않게).
- **INV-D6 스킴 목록의 정본은 `shared` 가 아니라 `features/content-render`** (2026-08-08, 스펙 문구를 코드에 맞춤): 스펙이 "shared 의 공용 URL 가드"라고 적었지만 구현은 features 에 있었고 **구현 쪽이 맞다.** 두 목록을 가르는 근거("출처는 웹 주소라 mailto 를 받을 이유가 없다")가 도메인 판단이라 shared 규칙(도메인 지식 금지)과 어긋난다. 도메인 없는 조각(문자열 정리·스킴 추출)만 `shared/lib/url.ts` 에 남았다 — 경계는 이미 옳았고 문서만 낡아 있었다.
- **포커스 아웃라인에 라운드를 주지 않는다** (2026-08-06, 기존 규칙 정정): `a:focus-visible` 의 명시도가 컴포넌트 클래스를 이겨서, 키보드 포커스가 닿는 순간 카드가 12px→6px, 알약 버튼이 999px→6px 로 각지게 변하고 있었다. "호버·포커스에서 완전 복구"와 정면으로 어긋난다. `--r-focus` 토큰도 없앴다 — 남겨두면 다음 화면이 되살린다.
- **소스 식별자를 표시 이름과 분리(`sourceId`)** (2026-08-09, INV-R4 구현 중): weight 조회 키를 표시 이름으로 두면 "Anthropic 블로그"를 "Anthropic"으로 다듬는 순간 그 소스의 모든 글이 기본 배수로 떨어져 순위가 조용히 바뀐다. 대가는 항목마다 필드가 하나 늘고 더미·테스트 픽스처를 전부 고쳐야 했던 것. 함께 **모르는 소스의 weight 를 0 이 아니라 1 로** 정했다 — 0 이면 점수가 0 이 되어 그 소스 글이 피드에서 사라지고, 소스 id 오타 하나의 증상이 "글이 안 보인다"가 되어 원인을 못 찾는다.
- **저장 모양과 조회 모양을 타입으로 가름(`StoredArticle`)** (2026-08-09, INV-R1): `score`·`isTrending` 을 뺀 타입에 `never` 자리를 둬서 조회 결과를 그대로 저장하는 코드가 컴파일되지 않게 했다. 규칙을 주석으로만 두면 언젠가 한 줄이 조용히 통과한다 — `ArticleListItem` 이 본문에 대해 쓰는 것과 같은 장치다. 더미 데이터도 이 모양으로 바꿔, 화면이 실제로 `rankFeed` 를 거치게 됐다.
- **DB 강제 불변식은 두 층으로 검증** (2026-08-09, INV-C1·R1·T1·T2): SQL 텍스트 검사(오프라인, 기본 `npm test`) + 실제 DB 검사(`test:integration`, 별도 config). 가짜 저장소만 쓰면 "우리 fake 가 unique 를 흉내낸다"를 검증하게 되고, DB 만 보면 왜 그렇게 생겼는지가 코드에 안 남는다. 통합 테스트는 환경변수가 없으면 **건너뛰지 않고 실패한다** — 조용히 건너뛰면 "통과했다"로 읽힌다.
- **타임존 없는 발행시각은 UTC 로 읽는다** (2026-08-09, 같은 날 뒤집은 결정): 처음엔 "존을 모르면 추측하지 말자"며 수집시각으로 대체하게 만들었다. 사용자가 필요한 정밀도를 밝히자("대략적인 날짜만 — 언제 나온 소식인지") 그 판단이 뒤집혔다 — **대체하면 일주일 전 글이 오늘 날짜 묶음에 들어간다.** UTC 로 읽으면 최악이 하루 어긋나는데, 목적이 "언제 나온 소식인지"라면 완전히 틀리는 쪽이 훨씬 나쁘다. 대가는 KST 자정 근처 글의 날짜 묶음이 하루 밀릴 수 있다는 것. **정밀도 요구를 모른 채 안전해 보이는 쪽을 고르면 틀릴 수 있다** — "모르면 버린다"가 늘 보수적인 선택은 아니다. 함께 `Date.parse` 에 맡기지 않는 것도 정했다: 존 없는 값을 로컬로 읽어 서버와 브라우저가 갈린다.
- **요약 표시 = AI 요약 → 출처 요약글 → 없음, 라벨은 값에 맞춘다** (2026-08-09, INV-S2 확장): "요약은 거의 무조건 나와야 한다"는 요구를 받았는데, 그대로 하면 본문 없는 항목에서 모델이 제목만 보고 지어낸다(INV-S1 위반). 그래서 요구를 **근거 확보 → 요약**으로 갈랐다. 출처가 준 요약글은 `summary` 가 아니라 `source_excerpt` 라는 **다른 칸**에 넣는다 — 같은 칸이면 "요약이 없다"는 신호가 사라져 AI 요약이 영영 안 생긴다(INV-S3 의 재시도 조건이 무력화). 화면은 어느 쪽인지 함께 알린다: 출처 글을 "AI 요약"이라 부르면 표시가 거짓이 된다.
- **근거 없으면 요약을 시도하지 않는다** (2026-08-09, INV-S3 조건 추가): 근거는 본문 또는 출처 요약글. 없으면 호출 자체를 건너뛰고 `skippedNoEvidence` 로 **실패와 따로 센다** — 재시도해도 소용없는 것과 다시 해볼 만한 것은 다른 이야기고, 섞으면 실패 건수가 계속 쌓여 진짜 문제를 가린다.
- **본문 추출을 수집 단계에 넣는다 (INV-S5 신설)** (2026-08-09): 왜 필요한지는 실측이 정했다 — HN 은 링크 모음이라 본문을 가진 적이 없고(요약글도 링크뿐), OpenAI 는 요약글은 주지만 원문이 403 이다. **소스마다 되는 길이 달라서** 요약글과 추출이 둘 다 필요하다. `@mozilla/readability` + `jsdom`, 브라우저 UA. 실패(403·타임아웃·본문 없음)는 항목 단위로 격리한다 — 봇 차단은 정상 경로지 예외가 아니다. 추출 결과는 신뢰 경계 밖이라 화면에서 sanitize 를 거친다. **추출을 요약보다 먼저** 돌려 이번 주기에 채운 본문이 곧 근거가 되게 했다.
- **태그 = 제목 키워드 규칙 + AI 분류의 합집합** (2026-08-09, INV-T3 신설): 규칙만 쓰면 표현이 다른 글을 놓치고, AI 만 쓰면 **요약이 실패한 항목에 태그가 하나도 안 붙는다**(요약과 분류를 한 번에 부르므로). 규칙은 적재 때, AI 는 요약 때 붙고 `item_tag` 기본키가 중복을 막는다. 목록 밖 태그는 버린다 — AI 가 새 태그를 만들면 필터가 늘어난다. 낱말 경계로 찾아 `toolbar`→'툴' 같은 오분류를 막되 영어 복수형은 잡는다. 태그 목록 자체는 아직 임시다.
- **RSS 가 본문을 안 주는 건 AI 차단이 아니다** (2026-08-09 실측): robots.txt 에 AI 크롤러 규칙이 없다(OpenAI·HN 둘 다 `User-agent: *` 뿐). HN 은 애초에 링크 모음이고, OpenAI 는 요약만 주는 피드다(AI 이전부터 흔한 트래픽 유도 방식). 원문 403 은 Cloudflare 의 봇 차단으로 브라우저 아닌 요청 전반에 걸린다. **추측하지 않고 확인한 덕에** 소스별로 다른 처방(요약글 vs 추출)이 나왔다.
- **제목을 한국어로 옮긴다. 본문 전문 번역은 지금 안 한다** (2026-08-10, INV-S6 신설): 사용자가 영어를 읽지 못한다는 것이 계기였다. 요구는 "본문 번역"이었는데 숫자가 답을 바꿨다 — **원문 본문이 있는 항목이 101건 중 42건뿐**이고(수집 당시엔 11%), 출력 토큰이 본문 길이만큼 나와 요약의 5~6배가 든다. 반면 제목은 훑을 때 제일 먼저 걸리는 자리인데 요약만 한국어라 시선이 언어를 두 번 건너뛰고 있었고, **이미 부르는 요약 호출의 응답에 필드 하나를 더하는 것**이라 추가 비용이 거의 0이다. 대가는 본문이 여전히 영어라는 것 — 본문을 읽는 일이 잦아지면 그때 다시 본다. 원문 제목은 덮지 않고 다른 칸(`title_ko`)에 넣는다: 원문이 진실이라는 규칙(INV-S1)을 지키려면 번역이 틀렸을 때 대조할 것이 있어야 한다.
- **번역의 근거는 제목 자신이라 요약과 조건이 갈린다** (2026-08-10, INV-S6): 요약은 근거(본문·출처 요약글)가 있을 때만 만들지만(INV-S3), 번역은 근거가 없어도 한다. 둘을 같은 조건으로 묶으면 본문도 요약글도 없는 항목이 **영어 제목으로 영영 남아 그 카드는 통째로 못 읽는 상태**가 된다. 실행이 이 결정을 확인해 줬다 — 첫 바퀴에서 번역 10건, 요약 7건으로 갈렸다.
- **핵심 항목(`summary_points`)은 AI 요약의 부속** (2026-08-10, INV-S7 신설): 컬럼·조회·화면이 다 있는데 **수집이 채우지 않아 비어 있던 필드**였다. 요약과 같은 호출·같은 근거에서 받아 채운다. 출처가 준 글을 보여줄 때는 항목을 딸려 보내지 않는다 — 우리가 뽑은 항목이 출처 글 옆에 붙으면 누가 쓴 것인지가 섞인다(INV-S2 의 라벨 규칙과 같은 계열). 화면이 `isAi && points.length` 를 각자 판단하던 것을 `displaySummary` 한 곳으로 내렸다.
- **마이그레이션 파일에는 재실행해도 같은 결과가 나오는 것만 담는다** (2026-08-10, 리뷰에서 발견): 요약 기준이 바뀌어 기존 요약을 비우는 `update public.item set summary = null` 을 `0003` 에 넣었는데, `apply-migrations.mjs` 는 **이름을 안 주면 폴더의 `.sql` 을 전부 다시 적용한다.** 다음에 `0004` 를 추가하고 습관대로 전부 돌리는 순간 그동안 만든 요약이 통째로 날아가고 전액 재과금된다. 파괴적 문장은 파일에서 빼고 "언제 무엇을 한 번 실행했는지"만 주석으로 남겼다. `add column if not exists` 류는 그대로 둔다. **"한 번만 도는 것"과 "여러 번 돌아도 되는 것"을 한 파일에 섞지 않는다**가 규칙이다.
- **주제 밖 판정을 요약 앞으로, 제목만으로** (2026-08-10, INV-F1 신설): 실측이 순서를 정했다 — 칵테일 레시피 항목 하나가 **13,099 입력 토큰**으로 나머지 7건 평균(2,496)의 5배였다. 요약을 만든 뒤 버리면 그 돈을 이미 쓴 뒤다. 제목만 보는 판정은 약 270 토큰. 대가는 제목만으로 판정하므로 오판 여지가 커진다는 것 — 그래서 **판정이 실패하면 거르지 않고 통과**시키고(INV-F3), 걸러진 건수와 제목을 리포트에 남긴다(INV-F2). 잘못 거르는 쪽이 잘못 통과시키는 쪽보다 비싸다: 걸러진 글은 화면에 없으니 사용자가 알아챌 방법이 없다.
- **출처 표시 = 수집 소스가 아니라 실제 발행처** (2026-08-10, INV-O1): 사용자가 "이런 건 보통 공식 발표니까"라며 출처를 신뢰 판단에 쓴다고 밝혔는데, 지금 화면은 HN 을 거친 글을 발행처와 무관하게 전부 "Hacker News" 로 보여주고 있었다. 판단 재료는 이미 DB 에 있다(`original_url`). 대가는 발행처를 못 뽑는 경우가 생긴다는 것 — 그때는 빈칸을 만들지 않고 수집 소스 이름으로 되돌아간다.
- **공식 여부는 근거를 구분해 남긴다** (2026-08-10, INV-O2·O3): `byUrl`(원문 주소가 그 주체의 도메인 — 도메인 비교뿐, 모델을 안 거친다) / `byContent`(모델 판단) / `none`. 하나로 합치면 모델 판단이 주소 근거와 같은 확실성으로 보이고, 모델이 틀리면 사용자가 잘못 믿는다. 대가는 화면에 표시가 두 종류가 되는 것 — design-rules 에 없는 요소라 시안이 한 바퀴 필요하다.
- **소스는 두 층으로 나누되 화면에는 안 드러낸다** (2026-08-10, INV-L1·L2): `daily`(화제성)/`deep`(전문적)은 weight 로만 반영한다. 사용자가 말한 두 가지 쓰임("매일 이슈 숙지" / "시간 날 때 전문적인 것")은 **읽는 방식**의 축이고, 처음 말한 갈래(뉴스/정보/스킬툴)는 **무엇에 관한 글**의 축이라 서로 다르다. 둘 다 화면의 1차 기준이 될 수는 없어서 화면은 갈래로 가르고 층은 순서로만 반영한다. HN 은 1번 쓰임에는 맞지만 2번에는 **구조적으로 못 쓴다** — 투표 상위에 뜬다는 건 이미 이슈가 됐다는 뜻이고, 검색 피드로 표 조건을 피하려면 **찾을 낱말을 미리 알아야 한다**(모르는 새 개념에는 못 쓴다).
- **태그(고정 분류)와 키워드(생성·누적)를 가른다** (2026-08-10, keywords-and-kinds.md): 사용자가 태그를 키워드로 이해하고 있었고, 지금 구현은 고정 5개였다. 성질이 반대다 — 분류는 안 변해야 필터 버튼이 쓸모 있고, 키워드는 변해야 새 개념을 담는다. 한 칸에 두면 둘 다 나빠진다. **스키마는 이미 자유롭다**(`tag.normalized_name` unique + 다대다) — 고정한 것은 코드의 결정이었다. 키워드는 대상("루프 엔지니어링")과 사건("보안 이슈")을 **섞는다**: 나중에 가르는 건 가능하지만 합치는 건 이미 붙인 것을 다시 손봐야 한다.
- **키워드는 빈도가 아니라 "그 글이 다루는 것"** (2026-08-10, INV-K2): 사용자가 든 예가 반례였다 — 새 개념("벡터 엔지니어링") 발표 글에는 기존 용어가 훨씬 많이 나온다. 새 개념은 한 번 정의되고 그 뒤로는 지칭될 뿐이다. 빈도로 뽑으면 **정작 그 글이 다루는 것이 안 뽑힌다.** 같은 이유로 화면 신호도 둘로 갈랐다: **처음 보는 말**(공식 발표 첫날 1건)과 **요즘 자주 보이는 말**(급증). 급증만 보면 사용자가 원하는 순간을 못 잡는다.
- **키워드 통일은 목록을 프롬프트에 주는 것으로, 임베딩은 안 쓴다** (2026-08-10): `normalized_name` unique 는 **글자가 같을 때만** 합친다. 표기를 맞추는 건 "이미 쓰인 키워드 목록"을 함께 주는 것이 한다. 다만 목록은 **표기를 맞추라고 주는 것이지 범위를 제한하는 게 아니다** — 이걸 명시하지 않으면 지금 고정 5개 태그와 똑같은 상태가 된다. 의미 검색은 **지금 안 한다**: 키워드가 0개인 상태에서는 "얼마나 비슷하면 같은 것인가"를 정할 근거가 없고, 느슨하게 잡으면 새 개념이 기존 것에 흡수돼 목적과 정반대로 실패한다.
- **프롬프트 문장은 파일로 빼되 출력 형식 줄은 코드에 남긴다** (2026-08-10): 사용자가 말투·요약 방식을 자주 고치고 싶어 했다. 말투는 `model/prompt-text.ts` 로 옮겼고, **출력 JSON 의 키 이름·형식 지시는 옮기지 않았다** — 그 줄이 깨지면 파싱이 전부 실패하고 그 실패는 조용하다(빈 결과로 돌아가 매 주기 재시도만 반복). 진짜 `.md` 로 빼는 안은 로더 설정(next.config)이나 배포 시 파일 누락 위험을 새로 만들어 탈락. **프롬프트 변경의 진짜 비용은 파일 위치가 아니라 검증**이다 — 말투가 좋아졌는지는 테스트가 못 잡고 실제로 몇 건 돌려 읽어야 한다.
- **토큰 계측은 실패한 호출도 센다** (2026-08-10, `IngestReport.usage`): 성공 분기에서만 세면 "요약은 하나도 안 늘었는데 요금만 나간 주기"가 보고서에서 멀쩡해 보인다. 파싱 실패·응답 잘림으로 빈 결과를 돌려줄 때도 usage 를 담는 이유가 이것이다. 한 건의 최대 입력 토큰을 따로 남기는 것도 같은 계열 — 합계만 보면 "한 항목의 근거가 비정상적으로 컸다"와 "고르게 늘었다"가 구분되지 않는다. 호출이 아예 던진 경우는 세지 않는다(받은 적 없는 토큰을 지어내지 않는다).

- **수집 한 바퀴에 시간 예산을 둔다** (2026-08-13, `INGEST_BUDGET_MS = 240_000`): 단계가 전부 순차라 최악치가 Vercel 상한(300초)을 넘는데 예산이 코드 어디에도 없었다. 2026-08-13 실행이 안 넘긴 건 요약 10건이 크레딧 소진으로 즉시 실패했기 때문이고, 크레딧을 채우니 158.9초가 됐다. **넘겼을 때의 증상이 이 파이프라인이 하려던 것과 정면으로 어긋난다** — Vercel 이 함수를 죽이면 응답 본문이 없어서 `failureReasons`·`notChecked`·토큰 계측이 제일 필요한 날 하나도 안 남고 요금만 나간다. 그래서 300 이 아니라 240 이다: 남은 60초는 리포트를 만들어 돌려주는 몫이다. 예산이 떨어지면 그 단계를 **멈추고 리포트를 정상 반환**하고, 건너뛴 것을 `budget` 칸에 남겨 터미널에 찍는다 — 안 남기면 "뒤쪽 소스가 매일 0건"이 *그 소스에 새 글이 없다*로 보인다(`notChecked`·`alreadyKnown` 을 따로 세는 이유와 같다). 시계는 주입받는다: 논리 시각 `now` 는 발행시각 계산용 고정값이라 흐르지 않고, 테스트가 실제로 4분을 기다릴 수도 없다.
- **예산 상수를 `server-only` 밖으로 내렸다** (2026-08-13, `lib/budgets.ts`): `BATCH`·`ENRICH_POOL` 이 `api/ports.ts` 안에 있었는데 그 파일은 `server-only` 라 **유닛 테스트가 한 번도 로드하지 않는다.** 그래서 `ENRICH_POOL` 을 100 → 10 으로 바꿔도 450개가 전부 green 이었다 — 그렇게 바꾸면 "점수로 고른다"가 항등 함수가 되어 방금 고친 버그로 그대로 돌아간다. 값을 못 박는 테스트에 **관계 단언도 같이 둔다**(`ENRICH_POOL >= ENRICH_BATCH * 20`) — 값만 못 박으면 다음 사람이 숫자만 고치고 지나간다. 7세션의 `MAX_RATIO` 10→100 과 같은 자리다.
- **자료 경계는 감싸는 것만으로 부족하다** (2026-08-13, 보안 리뷰, `data-fence.ts`): 외부 글을 `<자료>` 로 감쌌지만 안쪽을 무해화하지 않아 **자료가 자기 경계를 닫을 수 있었다.** 닫히면 그 뒤 문장이 지시가 된다. 도달 경로가 짧다 — 투고형 소스에 글을 올리면 본문 추출이 페이지 HTML 을 통째로 저장하고, weight 가 높으면 그 주기 요약 1순위로 배정된다. XSS 가 아니라 **내용 위조**다: 요약·핵심 항목·한국어 제목이 남의 문장이 되고 "공식 발표라고 함" 표시까지 붙어 피드 상단에 앉는다. 실행마다 다른 nonce 를 쓰는 방법도 있으나 **함수가 순수해야 조립 결과를 테스트가 직접 보고 "자료 밖에 남는 글이 없다"를 단언할 수 있어서** 결정론적 무해화(`<자료`·`</자료` → `‹자료`)를 골랐다.
- **외부 응답에 바이트 상한을 둔다** (2026-08-13, `MAX_FETCH_BYTES = 2_000_000`): 타임아웃 15초만으로는 부족하다 — 그 15초 동안 수백 MB 를 흘려보내면 함수가 메모리로 죽고, 그다음 JSDOM 파싱은 동기라 더 나쁘다. 공격이 필요한 것도 아니고 소스 14곳 중 하나가 큰 파일을 주기만 해도 같은 일이 난다. 게다가 실패한 항목은 `content_html` 이 빈 채 남아 다음 주기에도 같은 자리에서 다시 잡힌다(백오프 컬럼이 아직 없다). **넘치면 잘라 쓰지 않고 던진다** — 깨진 HTML 에서 나온 엉뚱한 결과가 조용히 본문으로 저장되는 것보다 "실패했다"가 낫다.
- **선별 기준을 소재 한 축에서 소재 + 쓸모 두 축으로** (2026-08-13, **구현됨**, INV-F1): 사용자가 실제 피드를 보고 "심심할 때 볼 정보글이 대부분이다, 내가 원하는 건 트렌드·성능·방향성"이라고 지적했다. 소재 축만으로는 **절대 못 가른다**는 게 실측으로 확인됐다 — 걸러 달라고 한 세 글("알트먼 사망 해프닝"·"AI 로 스피루리나 재배"·"삼성SDS 중앙부처 공급")이 **소재로는 셋 다 AI** 다. 반대 증거도 있다: "세계 전력 10% 태양광"은 읽을 만하다고 했는데 소재로는 탈락한다(태양광류는 나중에 "IT 그외" 갈래를 열어 담기로 하고 지금은 탈락시킨다). 기준 문장은 불변식이 아니라 설정이라 `prompt-text.ts` 의 `TOPIC_SCOPE` 에 두고, 유닛 테스트가 못 잡는 자리를 `npm run check:topic` 이 메운다 — 사용자가 직접 판정한 제목 11건을 정답으로 박고 실제 모델에 물어 확인한다. 소재 축만일 때 10건 중 7건, 쓸모 축을 더해 11/11. 건당 입력 427 → 826 토큰.
- **선별 판정을 전 소스로 켰다** (2026-08-13, **구현됨**, INV-F4): 프롬프트만 고쳤을 때 **효과가 거의 없었다** — 판정이 `geeknews`·`hn-frontpage` 두 곳에만 걸려 있어서, 문제가 된 세 글이 온 한국어 뉴스 소스(aitimes·etnews)는 판정을 아예 안 거치고 있었다. 전에 두 곳뿐이던 근거("AI 전용 피드에 '이게 AI 글인가'를 묻는 건 답이 정해진 질문")는 **판정이 소재만 물을 때만 성립한다.** 쓸모 축이 붙는 순간 AI 전용 피드에서도 답이 안 정해진 질문이 생긴다. 비용은 실측으로 확인했다 — 하루 신규 68건(612→680건), 이미 적재된 항목은 판정을 건너뛰므로 동시 8건 기준 약 32초로 예산 240초 안이다. 전에 적혀 있던 "29분"은 **첫 수집 450건을 순차로** 돌렸을 때의 값이라 정상 주기의 비용이 아니었다. 실행 확인: `판정 안 거는 소스 387건 → 0건`, 147.9초.
- **탭 셋은 한 축이 아니다 — 종류(뉴스/툴) × 문턱(핫이슈)** (2026-08-15, **설계만**): 핫이슈와 소식은 *나와의 거리*로 갈렸고 스킬·툴은 *종류*로 갈렸다. 서로 다른 자로 잰 것을 한 줄에 세우면 겹치는 칸이 생긴다(내가 쓰는 스택의 새 툴). 사용자 결정은 **기본은 안 겹치게, 문턱을 넘은 툴만 핫이슈에도**다. 이유가 중요하다 — 툴이 핫이슈에 있으면 "써 봐야 할 것 같고 알아야 할 것 같아" 피로해지고, 스킬·툴 탭은 걸어 들어가는 자리라 그 부담이 없다. **피로감을 만드는 건 툴이 아니라 "핫이슈에 있다"는 사실**이다. 소식은 뉴스만, 스킬·툴은 툴만 — 소식에도 툴이 섞이면 같은 피로가 거기서 생긴다. 공식 발표 여부는 문턱에서 **뺐다**: 그걸 문턱으로 쓰면 빅테크 발표는 다 올라가고 좋은 개인 툴은 다 밀린다(원하는 것과 반대). 공식 표시는 카드 표시로만 남는다(INV-O2).
- **핫이슈는 "중요한가" 대신 답이 갈리는 질문 셋으로 판정한다** (2026-08-15, **설계만**): 처음엔 "나와의 거리" 한 축으로 재려 했는데 두 번 물렸다. ① 내 스택만 잡으면 다른 프레임워크 소식을 영영 못 듣고, 다 잡으면 정보 과다가 된다 — 내 스택 안팎에 **던지는 질문 자체가 달라야** 한다는 뜻이다. ② 대안으로 낸 "판이 바뀌나"는 **스스로 물렸다**: AI 에게 물으면 큰 회사 발표를 판이 바뀌는 걸로 착각해 빅테크 발표만 쌓이는 지금 상태로 되돌아가고, 판이 바뀌었는지는 시간이 지나야 안다. 최종 형태는 흐릿한 질문이 하나도 없는 셋이다 — **① 내가 쓰는 것에 변화가 있나**(새 기능·가격·지원 중단·취약점) **② 지금까지의 방향을 뒤집나**("이 소식이 없었다면 반대로 예상했을까") **③ 놓치면 기회가 닫히나**(마감·베타·행사). 하나라도 걸리면 핫이슈다. 대가는 **핫이슈가 꽤 적어진다**는 것 — 모델 순위·빅테크 신모델 발표는 셋 다 아니라 소식으로 간다. 이진 판정이라 양 조절이 안 되므로(사용자 선택) 문턱을 높게 잡고 시작해 며칠 보고 푼다. 부수효과로 **어느 질문에 걸려 올라왔는지가 남아** 오판의 원인을 그 줄만 보고 고칠 수 있다.
- **판정은 2단계, 두 단계의 기울기가 반대다** (2026-08-15, **설계만**): 제목으로 전부 1차 판정하고 **핫이슈 후보만** 본문을 읽어 요약·정밀 판정한다. 전부 본문까지 읽히면 월 35달러선이고 제목만 쓰면 월 1~2달러인데, 2단계는 중간(월 15달러선)이면서 **아침에 볼 글부터 요약이 채워진다**(지금 요약이 붙은 건 700건 중 161건뿐이다). 여기서 따라 나오는 게 있다 — **1차에서 떨어진 글은 두 번째 기회가 없다.** 2단계의 효과는 통과한 것의 정확도를 높이는 것이지 놓친 것을 구해내는 게 아니다. 그래서 **1차는 후하게(애매하면 후보에), 2차는 엄격하게(애매하면 핫이슈에 안 올림)**. 같은 파이프라인 안에서 두 판정이 반대로 기울어야 한다. 2차에서 떨어진 후보는 소식으로 가고 요약은 그대로 쓰인다.
- **"나와의 거리"를 재려면 프로필이 필요하고, 판정에 그 버전을 남긴다** (2026-08-15, **설계만**): 지금 프롬프트에 읽는 사람 정보는 "영어를 읽지 못한다" 한 줄뿐이라, 기준을 아무리 다듬어도 "나한테 걸리나"는 잴 수 없다 — AI 는 **일반적으로 중요해 보이는 것**(빅테크 발표)만 올린다. 프로필은 기준(규칙)과 다른 것이다: 기준은 "무엇을 버릴지", 프로필은 "누구 기준으로 볼지". 프로필을 고치면 그 전 판정이 낡으므로 **어느 프로필로 내렸는지를 같이 저장**한다(review.md 의 basis 해시와 같은 방식). 다시 돌리는 값이 싸서(1차는 700건 전부 다시 해도 2달러 미만) **한 번에 완벽히 쓸 필요가 없다** — 대충 쓰고 결과 보고 고치는 방식이 가능해진다. 비싼 2차는 후보만이라 건수가 적다.
- **같은 사건이 여러 매체에서 오는 것을 핫이슈에서 거른다** (2026-08-15, **설계만**): 중복 제거가 정규화 원문 주소 기준이라 **같은 사건을 여러 매체가 쓰면 주소가 달라 다 남는다.** 셋 다 핫이슈 조건에 걸리면 아침 5분의 30%가 같은 얘기가 되고, **큰 사건일수록 많이 겹치니 제일 중요한 날에 제일 심해진다.** 핫이슈 판정 때 그날 이미 뽑힌 제목 목록을 같이 주고 "같은 사건이면 빼라"고 한다(keywords-and-kinds INV-K5 가 키워드 목록을 주는 것과 같은 형태). 점수순으로 판정하면 신뢰도 높은 매체 것이 자연히 대표가 된다. 한계는 제목만 보고 같은 사건인지 판단하므로 표현이 많이 다르면 놓친다는 것.
- **요약은 요점 먼저, 표를 허용한다** (2026-08-15, **설계만**): 사용자 요구는 요점 → 내용 요약 → 원문 순서인데 **데이터는 이미 그 모양이다**(`summary` + `points`). 화면이 summary 를 먼저, points 를 아래에 그리고 있어 **순서가 정확히 반대**였다 — 뒤집는 건 화면만 고치면 되고 데이터도 프롬프트도 안 건드린다. 가독성(줄바꿈·표)은 별개 문제이고 **content-safety 에 닿는다**: 요약은 신뢰 경계 밖이라 지금 순수 텍스트로만 그린다(근거가 남의 웹페이지에서 온 글이라 거기 심은 문장이 "AI 요약" 자리에 앉을 수 있다). 마크업을 그리려면 무엇을 허용하고 무엇을 지울지 정해야 한다 — **아직 안 정했다.**
- **소식은 주제 뱃지 줄로 들어간다 — 개수는 화면에 안 보여준다** (2026-08-15, **설계만**): 사용자가 소식 탭을 "부담없이, 그때그때" 본다고 했다. 부담이 없다는 건 **다 본 상태가 없어야 한다**는 뜻이라 두 가지가 자동으로 탈락한다 — 하루 총 개수 표시("오늘 8건"은 곧 할당량이 된다. 3건 보면 5건 남은 게 된다)와 안 읽은 개수 배지. 그런데 "골고루"는 남는다. **평평한 목록은 점수순이라 위에서 끊어 읽으면 매일 같은 주제만 보게 된다** — 넓어지는 게 아니라 좁아진다. 주제 뱃지 줄이면 **펼치지 않아도 오늘 뭐가 왔는지는 남으므로** 안 봐도 골고루가 성립한다. 부담 없이 보는 사람에게는 이게 유일한 방법이다. 뱃지 줄은 오늘부터 3~4일 창(미끄러지는 창 — 내일이 되면 제일 오래된 날의 뱃지가 빠진다)으로 계산하되 **글은 안 지운다**: 창 밖 글은 날짜 그룹으로 그대로 남는다(사라지면 "며칠 못 봤더니 없어졌다"가 되어 부담 없음과 정면으로 부딪힌다). 핫이슈는 **반대 규칙**이다 — 꼭 알아야 하는 것이라 다 봤다는 표시가 의미를 갖는다. 아직 안 정한 것: 뱃지에 건수를 붙일지(붙이면 "프론트엔드 (3)"이 다시 할당량이 된다. 안 붙이면 눌러보기 전엔 뭐가 있는지 모른다 → 시안에서 나란히 본다).
- **분류를 두 축으로 넓히고, 새 개념 키워드와 가른다** (2026-08-15, **설계만**, INV-K3 재검토): 사용자가 뱃지 예시로 든 말들이 실은 세 종류였다 — **분야**(프론트엔드·투자·정책, 안 변함) · **사건종류**(업데이트·보안이슈·사건사고, 안 변함) · **새 개념**(MCP·Next.js 15.6, 계속 생김). 앞의 둘은 뱃지로 완벽하다(3~4일 만에 열어도 어제 눌렀던 뱃지가 그대로 있다). **세 번째를 같은 줄에 넣으면 뱃지 줄이 무너진다** — 창 기간이면 수십 개가 쌓여 "끌리는 걸 고른다"가 "뭘 고를지 고민한다"가 되고 그게 피하려던 부담이다. 그래서 지금 필요한 건 새 설계가 아니라 **분류(고정 5개)를 넓히는 것**이고, 넓히는 방향이 하나가 아니라 둘이다(한 글이 "프론트엔드 + 보안이슈"를 동시에 갖는다). 여기서 INV-K3("대상과 사건을 섞는다, 층을 가르지 않는다")를 다시 봐야 한다 — 그 조항 아래에 "나중에 가르는 건 가능하지만 합치는 건 어렵다"고 적어뒀고, 뱃지 줄이 가를 이유다. 분야 목록은 곧 **소스 쇼핑 목록**이다(칸을 두면 그 소스를 구해야 하고, 안 두면 안 구해도 된다). 2026-08-13 에 "태양광류는 나중에 'IT 그외' 갈래를 열어 담는다"고 미뤄둔 것이 이 목록으로 돌아온다.
- **들여오는 규칙은 덧셈이 아니라 문 셋이다** (2026-08-15, **설계만**): 사용자가 "이슈+중요성+관련성으로 기본 점수"라고 했다가 다음 문장에서 스스로 덧셈을 깼다 — "관련성이 낮아도 아예 없는 게 아니면 이슈+중요성으로 가져올 수도 있다". **덧셈이면 이게 안 된다**: 중요도 3 + 관련성 0 과 중요도 1 + 관련성 2 가 같은 점수인데 앞엣것은 반드시 봐야 하고 뒤엣것은 안 봐도 된다. 그래서 문을 셋으로 나눈다 — **1번(중요도 ≥ 1, 관련성 안 봄) / 2번(중요도 0 + 관련성 높음) / 3번(중요도 0 + 관련성 낮음 = "이것도 한번 맛볼래?") / 관련성 없음 + 중요도 0 은 안 들임**. 연속 점수(이슈성)는 문을 고르는 데 안 쓰고 **문 안에서의 순서에만** 쓴다. 이러면 어느 문으로 들어왔는지가 남아 **문마다 하루 상한을 다르게 걸 수 있다**(1번은 없거나 아주 넉넉히, 2번은 넉넉히, 3번은 작게 — 부담의 원천이 3번이다). 관련성은 100점 척도가 아니라 **높음/낮음/없음 3단계**다(사용자 문장 자체가 3단계였다). 상한은 기준을 대체하지 않는다: **기준을 넘은 것을 다 들이되 넉넉한 상한에 부딪히면 그때만 이슈성 낮은 것부터 자르고, 부딪혔다는 것을 수집 리포트에 남긴다**(매일 부딪히면 기준이 느슨한 것이고 한 번도 안 부딪히면 상한이 있으나 마나라는 신호다 — INV-F2 와 같은 형태). 대안이었던 "상위 N개 고정"은 탈락: **조용한 날에 별로인 글이 자리를 채운다.** 이 배정은 2단계 판정의 1차에 붙는다(위 2026-08-15 항목) — 1번 문에 든 것만 2차로 본문을 읽는다.
- **이슈성은 모델에게 묻지 않는다** (2026-08-15, **설계만**): "이 글 중요도 몇 점"이라고 물으면 숫자는 나오지만 같은 글을 다시 물으면 다른 점수가 나오고 날마다 기준이 흔들린다. 이 레포는 이미 그 실패를 겪었다(위 "핫이슈는 '중요한가' 대신 질문 셋"). 그래서 **모델은 참/거짓만 답하고 숫자는 우리가 만든다** — 중요도는 질문 셋 중 몇 개가 참인가(0~3), 이슈성은 **교차 발행처 수 × 소스 weight × 시간감쇠**로 우리가 센다(전부 이미 DB 에 있는 값이라 공짜고 재현된다). 교차 발행처 수는 INV-G4 의 사건 묶기에서 나온다 — 그날 뽑힌 제목을 주고 "같은 사건이면 빼라"를 "같은 사건이면 어느 것과 같은지 돌려줘라"로 바꾸면 묶음이 그 호출에서 함께 나온다. **다만 이슈성 단독으로는 글을 들여오지 않는다**: 교차 발행처 수는 중요도가 아니라 보도량이고, 보도량은 발표 주체의 크기를 따라간다(국내 4곳이 OpenAI 발표를 다 받아쓰면 5가 되고 Anthropic 엔지니어링 글은 1이 된다). 순서에만 쓴다.
- **관심도 학습은 지금 만들지 않는다** (2026-08-15, 사용자가 "만들기도 전에 너무 멀리 봤다"고 판단): 안 본 글의 점수를 내리고 계속 언급되면 올려 되살리는 설계를 검토했으나 세 가지로 막힌다. ① **"안 봤다"가 관심 없다는 뜻이 아니다** — 뱃지로 골라 보는 구조에서는 안 누른 뱃지의 글이 전부 "안 봄"이 된다. 그날 안 끌렸을 뿐인데 점수가 내려가고, 몇 주면 관심사가 두세 개로 쪼그라든다(피하려던 것의 정반대). ② **재등장 조건이 소스 편향을 그대로 먹는다** — "계속 언급되면 오른다"의 언급 횟수는 우리 소스가 그 주제를 얼마나 많이 다루느냐일 뿐이라 큰 회사 소식만 되살아난다. ③ 사용자 1명, 소식 탭을 며칠에 한 번, 클릭 몇 건 — 점수를 움직일 표본이 없다. 더 중요한 건 **뱃지가 있으면 학습이 거의 필요 없다**는 것이다: 학습은 고르는 수고를 대신하는 것인데 사용자는 고르고 싶다고 했다("끌리는 뱃지를 클릭해서 보는 거야"). **넓히는 일은 프로필도 학습도 아니라 3번 문이 한다** — 프로필이 1년 동안 그대로여도 3번 문이 매일 몇 건씩 프로필 밖을 들여오고, 학습과 달리 내가 클릭한 것 근처가 아니라 아예 안 보던 쪽도 들어온다. 나중에 다시 볼 조건: **뱃지 클릭 기록만 남겨** 두고, 몇 주 뒤 한 번도 안 눌린 뱃지가 실제로 관찰되면 그때 규칙을 정한다(뱃지 클릭은 사용자가 명시적으로 "이거 볼래"라고 한 것이라 글 단위 클릭보다 신호가 깨끗하다).
- **프로필은 설정 파일에 둔다, 갱신은 손으로, 재판정은 창 안만** (2026-08-15, **설계만**): 두는 자리는 `sources.ts` 옆 설정 파일이다 — 소스 목록도 설정 파일이고 같은 이유다. 화면에서 고치는 안은 프로필 편집 화면이 필요해 후순위로 미룬다(PRODUCT 의 "소스 관리 화면 → 후순위"와 같은 계열). 고치려면 파일 한 줄 바꾸고 push 하면 Vercel 이 배포한다. **자주 바뀌는 값이 아니고, 바뀌는 순간은 본인이 안다**(새 프로젝트를 시작하거나 새 기술을 쓰기 시작할 때). 고쳤을 때 과거 판정이 낡는 문제는 **창 안만 다시 판정**해서 끊는다 — 뱃지 줄이 3~4일 창이라 화면에 실제로 영향을 주는 건 그만큼(약 200건)이고, 창 밖은 그대로 둔다(기존 680건을 옛 기준으로 두기로 한 것과 같은 결정). 낡은 것을 알아채는 방법은 **항목에 프로필 해시를 같이 저장**하는 것이다(review.md 의 `basis` 해시와 같은 장치) — 현재 해시와 다른 창 안 항목이 재판정 대상이라 "프로필 고쳤는데 재판정 깜빡함"이 안 생긴다. 결과적으로 **프로필을 한 번에 잘 쓸 필요가 없다**: 틀리면 고치고, 고치는 값이 창 안 재판정뿐이다.
- **소스 선정 기준에 "내용을 주는가"를 넣는다** (2026-08-15, 사용자 결정): 판정 재료가 없는 문제를 두 겹으로 푼다 — **1차로 내용을 최대한 주는 소스를 고르고, 2차로 제목 + 출처 요약글만으로도 판정이 되게 만든다.** 실측(2026-08-15, `npm run ingest:status`, 690건)으로 셋이 서로 다른 값임을 확인했다: **출처 요약글 464건(67%)** — 피드 XML 안에 이미 들어 있어 원문 페이지를 안 열어도 얻어진다(OpenAI 는 원문이 403 인데 요약글은 줘서 62건 중 60건이 요약됐다) / **본문 249건(36%)** — 원문 페이지를 실제로 열어 추출한 것 / **AI 요약 171건(25%)**. 앞서 "77% 에 내용이 없다"고 본 것은 세 번째 숫자로 말한 오독이었다 — **AI 요약이 없는 이유는 근거가 없어서가 아니라 하루 예산(`ENRICH_BATCH = 10`)** 이다(theverge 14건 중 본문 14건인데 요약 0, arstechnica 25/25 인데 요약 0 — 차례가 안 온 것). 그래서 문 배정은 AI 요약을 기다릴 필요 없이 **제목 + 출처 요약글 + (있으면) 본문**으로 한다. 남은 구멍: **제목밖에 없는 소스가 셋**이다(google-ai-blog 20건 요약 0 본문 0 · huggingface-blog 51건 본문 2 · deepmind-blog 50건 본문 1). 셋 다 weight 1.3~1.5 로 제일 쳐주는 공식 발표 소스인데 중요도 질문("방향을 뒤집나")을 제목만으로 답해야 한다. 그리고 "출처 요약글 **또는** 본문이 있는 항목"의 합집합은 아직 안 센다 — 문 배정 대상이 몇 %인지 알려면 `ingest-status.mjs` 에 한 줄 더해야 한다.
- **뱃지 키워드 목록을 미리 정하지 않는다 — 표기 기준을 두고 데이터가 정하게 한다** (2026-08-15, **설계만**, 같은 날 한 번 뒤집음): 처음엔 "사람이 목록을 정하고 모델은 그 안에서 고르기만 한다"로 정했다. 근거는 ① 뱃지가 안 변해야 다시 누를 수 있고 ② 표기가 안 갈리고 ③ **빈 칸이 곧 소스 쇼핑 목록**이 된다는 것이었다. 사용자가 **"표기 기준을 두어 같은 의미가 다양하게 표기되지 않게 하자"** 고 했고 그쪽이 맞다 — **지금 목록을 손으로 정하면 그건 추측이고, 고정 5개가 실패한 이유가 정확히 그 추측이다.** 대신 갈림을 세 층으로 갈라 각각 다른 장치로 잡는다: **글자 모양**(`Next.js`/`NextJS`)은 기계 정규화(`normalized_name` unique, 이미 있다) · **언어**(`프론트엔드`/`frontend`)는 프롬프트 지시(INV-K4 와 같은 규칙) · **입도·동의어**(`웹 프론트엔드`)는 규칙만으로 부분적이라 **이미 쓰인 목록을 프롬프트에 같이 주고 같은 뜻이면 그것을 쓰게** 한다. 규칙 문장은 모델이 매번 해석해야 하지만 목록은 대조만 하면 된다 — **제일 강한 표기 기준은 규칙이 아니라 목록**이다. 대가가 하나 있다: 고정 목록의 "빈 칸이 보인다"는 성질을 잃는다(백엔드 소식이 안 온 날, 없는 건지 소스가 없는 건지 구별이 안 된다). 되찾는 방법은 나중에 목록을 만드는 것이고, **만들지 말지는 690건에 한 번 돌려 실제로 어떤 키워드가 나오는지 보고 정한다.** 두 축(분야/사건종류)으로 가르려던 것도 같이 뺐다 — 목록을 안 정하면 축을 강제할 자리가 없다.
- **새 개념 키워드는 뒤로, 뱃지 키워드부터** (2026-08-15, 사용자 확인): 두 종류에 필요한 규칙이 **정반대**라 한 번에 못 만든다. `웹 프론트엔드` 는 `프론트엔드` 로 **합쳐져야** 하지만, `루프 엔지니어링` 이 `에이전트` 로 합쳐지면 **새로 생겼다는 사실 자체가 사라진다**(INV-K5 가 막으려던 것). 새 개념 = **작년에는 목록에 적을 수 없었던 말**이다(MCP·RAG·루프 엔지니어링·Claude Code). 뱃지용 말(프론트엔드·투자·보안)은 10년 전에도 있었고 10년 뒤에도 있다. 이 구분이 값을 하는 자리는 명확하다 — MCP 가 처음 나온 날, 뱃지만 있으면 "AI 도구 칸에 뭔가 왔네"까지만 보이고 새 개념 키워드가 있어야 "**MCP 라는 처음 보는 말이 오늘 생겼다**"가 보인다(INV-KD2 가 "처음 보는 말"과 "급증하는 말"을 가른 이유). PRODUCT 한 줄 정의에 MCP 가 예시로 이름까지 박혀 있는 만큼 뺄 기능이 아니다 — **취소가 아니라 순서다.** 뱃지 줄은 새 개념 없이 완전히 돌아간다. 켤 때 INV-B3 ↔ INV-K5 충돌을 먼저 처리한다(두 종류를 가르든지, 프롬프트에서 두 질문으로 나누든지).
- **뱃지 키워드는 목록을 고정하지 않는다 — 690건 실측으로 확정** (2026-08-15, **실측 근거 있음**): 자유 생성 + 표기 기준 + 앵커 목록으로 690건을 한 번 돌렸다(107종 · 4분 8초 · $2.24 · 실패 1.2% · 건당 입력 1,407토큰). **5건 샘플에서 건당 2.2종이라 690건이면 수백 종을 걱정했는데 107종이었다** — 이미 쓴 키워드를 프롬프트에 같이 주는 장치(INV-B3)가 실제로 수렴시킨다는 첫 증거다. **표기 갈림은 `기상예보`/`기상예측` 한 쌍뿐**이고, 걱정했던 `프론트엔드`/`웹 프론트엔드` 류는 하나도 안 나왔다. 분포도 뱃지에 맞다 — 상위 20종이 부여의 약 80%, 1~2건짜리가 42종으로 꼬리에 깔려서 3일 창이면 10~20개가 뜬다. 부수적으로 확인된 것 둘: **`AI` 는 5건 샘플에서 3/5에 붙어 뱃지로 못 쓴다**(이 사이트는 AI·IT만 모은다)는 것을 690건 전에 규칙으로 막았고 실제로 목록에 없다 / **고정 태그 5개 중 `에이전트`(95건)·`MCP`(3건)는 고정 목록 없이 스스로 되살아났고 `툴` 은 690건에서 한 번도 안 나왔다.**
- **사건종류 축을 되살렸다 — 안 물으면 안 만든다** (2026-08-15, **실측이 뒤집음**): 같은 날 오전에 "두 축(분야/사건종류)으로 가르려던 것도 뺀다"고 정했는데, 690건 결과가 그걸 뒤집었다 — **107종이 전부 분야였고 사건종류(`출시`·`규제`·`사건사고` 류)가 한 건도 안 나왔다.** "이 글이 다루는 것"만 물었으니 소재만 답한 것이다. 그래서 같은 호출에서 질문을 둘로 나눈다(분야 1~3개 · 사건종류 0~2개). **사건종류를 고정 목록으로 두려다 접었다** — 동의어가 갈릴 것(`출시`/`공개`/`발표`/`런칭`)을 걱정했는데 그건 재지 않은 예측이었고, 분야도 갈릴 줄 알았지만 한 쌍뿐이었다. 사용자 판단으로 분야와 같은 방식(자유 생성 + 축별 앵커)으로 간다. **앵커 목록은 축마다 따로** 준다 — 합치면 모델이 사건종류 자리에 분야를 쓴다(변이로 확인).
- **뱃지는 분야와 사건종류를 색으로 구분한다** (2026-08-15, 사용자 결정, **설계만**): 한 줄에 섞여 있으면 `보안`(분야)과 `사건사고`(사건종류)가 같은 것으로 읽힌다. **design-rules 와 부딪히는 자리가 있다** — 승인된 규칙이 포인트색(인디고 `#4F46E5`)을 **"아직 안 본 것" 전용**으로 쓰고 면적을 최소로 둔다. 뱃지 두 색을 거기서 가져오면 그 신호가 흐려지므로 새 토큰이 필요하고, **읽음/안읽음 × 호버까지 대비 4.5:1 을 실측**해야 한다(조합이 늘어난다). 시안에서 정한다 — keywords-and-kinds INV-B5.
- **프롬프트 캐싱은 매일 도는 경로를 만들 때 넣는다** (2026-08-15): 확인해 보니 **`cache_control` 이 프로젝트 전체에 한 줄도 없다.** `api/ports.ts` 가 `cache_read_input_tokens` 를 리포트에 담고 주석에 "계속 0이면 캐싱이 안 걸리고 있다"고 적어뒀는데, 거는 쪽이 없어서 **걸린 적이 없다.** 지금 넣어도 값을 안 하는 이유 둘: 백필 스크립트는 앵커 목록이 청크마다 자라 프리픽스가 매번 달라지고, 한 청크의 8건이 동시에 나가 서로의 캐시를 못 읽는다. 넣을 때의 조건 셋 — ① **목록을 실행 중 고정**한다(매일 68건뿐이라 고정해도 잃는 게 없다. 백필과 반대 방향이다) ② 지시문이 **1,024 토큰**(Sonnet 5 최소 캐시 길이)을 넘어야 한다 — 지금 지시문이 1,000 언저리라 앵커가 차야 겨우 넘는다 ③ 캐시 수명 5분 안에 끝난다(68건 × 동시 8 = 약 35초). 같은 문제가 **주제 판정에도 있다**: `buildTopicPrompt` 는 완전히 고정된 문자열이라 캐싱에 제일 좋은 대상인데 826토큰이라 최소 길이에 못 미친다. 추정 효과는 매일 경로에서 월 $7 → 약 $2.2.
- **개발자용 파이프라인 대시보드(`/dev/ingest`)는 시안 절차를 건너뛴다** (2026-08-17, 사용자 지시): design-drafting.md 는 "대시보드"를 새 레이아웃 언어의 예로 들지만, 이 화면은 사용자가 소스별 통계를 빨리 보고 싶다고 명시적으로 "일단 정보를 가져오게 하는 것"부터 요청했다 — 기능 우선, 시안은 나중(그래프·소스 관리가 붙을 때). 그래서 design-interview→시안→checkpoint 없이 기존 토큰만으로 표/리스트를 바로 구현했다. 대가로 색 재사용에서 실수가 하나 났다(`--accent`를 오류 표시에 썼다가 리뷰에서 잡힘 — "아직 안 본 것/링크" 전용이라는 기존 규칙과 충돌) — 색 없이 굵기로만 강조하는 쪽으로 고쳤다. 이 페이지는 로컬 전용(`NODE_ENV=production`이면 404)이라 사용자에게 노출되는 화면이 아니고, 나중에 배포하며 관리자 로그인을 붙일 때 디자인도 다시 본다.

- **뱃지 줄의 상한을 화면에서 뺀다 — 개수는 그날 뉴스 양이 정한다** (2026-08-30, 사용자 결정): `BADGE_LIMIT` 24 → 60. **실측이 문제를 다시 정의했다** — 문턱 2 vs 3 을 정하려고 창 3일(176건·42종)을 세어 보니 2건 이상 29종 / 3건 이상 27종인데 **둘 다 상한 24에 잘려 그려지는 줄이 완전히 같았다.** 즉 노출을 정하고 있던 것은 문턱이 아니라 상한이었고, 그래서 **뉴스가 몰린 날과 한산한 날이 화면에서 똑같이 24개로 보였다.** 사용자 문장: "상한을 없애고 이슈성과 중요도에 따라 나오게 하는거 어때? 그때그때 어떨때는 5개, 어떤날은 20개가 나올 수 있는거". **완전히 없애지 않은 이유**는 하나뿐이다 — 뱃지 줄이 클라이언트 컴포넌트라 담긴 것이 그대로 브라우저로 직렬화된다. 60은 평소에 닿지 않는 **사고 방지선**이다(실측 최대 29종). 문턱은 2로 확정(2와 3이 같은 줄을 그리므로 낮은 쪽). 화면 뱃지 24 → 29개. **예상 하나가 틀렸다**: 상한을 풀면 넓은 화면에서도 접힘이 일해 `더 보기` 죽은 버튼이 같이 풀릴 줄 알았는데, 29개도 1280px 두 줄에 다 들어갔다(1168px 에서 40px 남음) — 늘어난 다섯이 전부 짧은 말이었다.
- **이슈성·중요도로 뱃지를 고르는 것은 나중 — 지금 문턱은 임시 기준이다** (2026-08-30): 사용자가 쓴 두 단어가 스펙 용어와 정확히 같은데(`docs/specs/keywords-and-kinds.md` INV-N3 이슈성 = 교차 발행처 수 × 소스 weight × 시간감쇠 / INV-G2 중요도 = 핫이슈 문턱 질문 셋) **둘 다 코드에도 스키마에도 없다**(grep 0건). 교차 발행처 수는 "같은 사건 묶기"가 먼저 필요하다 — 지금 중복 제거가 정규화 원문 주소 기준이라 **같은 사건을 다른 매체가 쓰면 서로 다른 글**이다. 중요도는 글마다 모델 판정 단계가 새로 필요하고 요금이 는다(키워드 80건에 입력 14만 토큰인데 비슷한 규모가 하나 더). 그래서 planned 스펙 승격부터 가는 정식 경로로 따로 둔다. **지금 쓰는 문턱 2건은 "몇 건이나 나왔나"만 본다** — 한 매체가 시시한 것을 여러 번 써도 뜨고 중요한 발표가 한 번만 실리면 안 뜬다. 붙는 날 이 상수를 조정하는 게 아니라 **고르는 기준 자체가 바뀐다**(사용자에게 미리 알리고 진행).
- **피드 조회를 창 안과 창 밖 둘로 가른다 — 상한 숫자를 올리는 안을 접었다** (2026-08-31, 사용자 결정): 조회가 "최신 200건" 하나였고 **그 200칸을 성격이 다른 둘이 나눠 쓰고 있었다** — 뱃지 줄은 *시간* 기준(최근 3일, INV-B4)이고 목록은 *건수* 기준이라 단위가 다른데 한 칸에서 서로를 민다. 3일치가 200건을 넘으면 집계가 있는 글을 다 못 세서 **뱃지 숫자가 작아지는데 화면에는 아무 표시도 안 난다.** 실측이 급한 것을 알려 줬다: 창 안이 **185건(상한의 92%)** 이라 다음 수집에서 넘고, **지금까지의 최악은 424건**이라 이미 자른 날이 있었다. 덤으로 200칸 중 185칸을 창이 먹어서 **날짜 그룹을 내려가는 길이 15건뿐**이었다. **상한만 600으로 올리는 안(B)과 올리고 로그로 경고하는 안(C)을 접었다** — 숫자를 잘 고르는 문제로 두면 같은 모양이 다시 오고, 최악 424를 보면 600도 언젠가 닿는다. 대신 **창 안은 건수 제한 없이 전부, 창 밖은 `FEED_TAIL = 120`** 으로 갈랐다(왕복 하나가 는다). 경계는 `badgeWindowStartIso` **한 함수**가 정한다 — 세는 쪽과 가져오는 쪽이 따로 계산하면 사이에 낀 글이 생기고, 그것도 "뱃지 숫자가 좀 작다"로만 보인다. 창 밖 120은 한 페이지 12건 기준 열 번쯤 더 볼 분량이고, 실측상 몰린 날은 1~2일치·한산할 때는 일주일 넘게 내려간다. **PostgREST 기본 1000행에 닿으면 서버 로그에 경고를 남긴다** — 그때는 창을 좁히거나 집계를 DB 로 내릴 때다(지금은 185/1000). 실측 검증: 화면 카드 **305건 = 185 + 120**, 날짜 그룹이 8/27 까지 내려가고, 읽음 기록을 비운 뒤 뱃지 숫자가 DB 집계와 **정확히 일치**(출시 30 · AI 모델 29 · 오픈소스 25 · 정책 21 · 연구개발 20 · 논쟁 19).
- **요금 상수를 그날 갈지 않고 실행 시각으로 단가를 고른다** (2026-08-31, 사용자 결정): `estimate-cost.ts` 주석이 "이 상수를 2026-08-31 이후에 손보지 않으면 대시보드가 실제보다 싸게 보여준다"고 예고해 둔 자리다. 상수만 $2/$10 → $3/$15 로 바꾸는 안(A)은 10줄이면 끝나지만 **배포 시점을 손으로 맞춰야 한다** — 오늘 배포하면 오늘 실행분이 실제보다 50% 비싸게, 내일 넘겨 배포하면 그 사이 실행분이 싸게 보인다. 그래서 `ratesFor(startedAt)` 을 두고 `estimateCostUsd`·`estimateCostBreakdown` 이 `startedAt` 을 **필수 인자**로 받게 했다(기본값을 두면 날짜를 안 넘긴 호출이 조용히 한쪽 단가로 계산된다). **표시 차이는 실제로는 거의 없다** — 대시보드는 `fetchLatestIngestRun()` 으로 최신 실행 **하나만** 보여주므로 두 안이 갈리는 것은 오늘~내일 사이의 한 건뿐이다. 그래도 B 를 고른 이유는 값이 아니라 **"그날 상수를 고친다"는 숙제 자체를 없애는 것**이다. **안 잰 것: 프로모션 종료의 시간대.** 앤트로픽 문서는 날짜(2026-08-31)만 밝히고 시간대를 안 적어 **UTC 자정으로 가정**했고 코드 주석에 추정임을 남겼다 — 경계 몇 시간 안에 돌린 실행은 단가가 어긋날 수 있다. 읽을 수 없는 `startedAt` 은 정가로 떨어뜨린다(싼 쪽으로 틀리면 화면이 "생각보다 안 썼네"로 보여 이 화면을 만든 이유를 깬다). `scripts/count-prompt-tokens.ts` 는 이미 도입가·정가를 둘 다 출력하므로 손대지 않았다. 캐시 배수(쓰기 1.25 · 읽기 0.1)는 그대로다. 테스트는 **값 못 박기와 동작을 갈랐고**(rules/tdd.md), 캐시 배수는 단가와 무관하게 `쓰기/입력 = 1.25` 비율로 붙든다 — 단가가 또 바뀌어도 배수 테스트는 안 깨진다. 표적 변이 6종(경계일 한 달 이동 · 무효 시각 폴백 뒤집기 · 정가 3.0→2.0 · 날짜 분기 제거 · 배수 1.25→2 · 판정 비용만 옛 상수) 전부 빨간불 확인.
- **상세 뱃지 높이는 토큰이 정한다 — 패딩+줄높이로 재던 것을 되돌렸다** (2026-08-31, 리뷰 이관분 처리): 승인 시안(`docs/design/mockups/badge-row.html` 의 `.detailKwChip`)은 `height: var(--kw-detail-chip-h)`(24px) + `white-space: nowrap` 이고 컨테이너 `.detailKw` 는 `flex-wrap: wrap` 인데, 구현은 `padding: 4px 12px` 만 줬다. **브라우저 실측이 리뷰의 산술을 그대로 확인했다** — 옛 규칙을 재현하니 알약 높이가 정확히 **27.2px**(`4 + 12px×1.6 + 4`), 새 규칙은 **24px**. 패딩으로 높이를 만들면 글자 크기가 바뀔 때 조용히 또 어긋나므로 토큰으로 못 박는다. **`flex-wrap` 은 관찰된 결함이 아니라 방벽이다** — 지금 데이터로는 최대 4개(305px 에서도 한 줄)라 접힘이 안 일어난다. 그래서 **최악 케이스를 만들어 쟀다**: 실제 키워드 43종 중 가장 긴 5개(`소프트웨어 개발`·`정부 지원사업`·`AI 서비스`·`동영상 편집`·`에지 컴퓨팅` — design-rules 의 상세 최대 5 = 분야 3 + 사건종류 2)를 305px 에 넣으면, 고친 뒤는 **2줄 · 전부 24px · 가로 스크롤 없음**이고 옛 규칙은 **한 줄에 욱여넣어 알약 높이 142.39px**(한글이 글자 단위로 세로로 쪼개짐) **+ 가로 스크롤 발생**이다. 즉 이 결함은 잠복해 있었고 뱃지가 5개 붙는 날 드러났을 것이다.
- **컨트롤 줄 `padding-bottom` 을 시안의 12px 로 되돌렸다** (2026-08-31, 리뷰 이관분 처리): 구현이 18px 로 가져왔던 자리다. 시안이 일부러 좁힌 값인 이유는 컨트롤 줄과 뱃지 줄이 **같은 "고르는 도구" 묶음**이기 때문이다 — 벌려 두면 뱃지 줄이 카드 쪽 묶음으로 읽힌다. 실측: 세그먼트 알약 아래 → 첫 뱃지 위 **12px**(`.kwRow` 의 -4px 마진과 4px 패딩이 상쇄돼 계산값과 같다). **`.kwBlock` 의 18px 은 안 건드렸다** — 시안에는 `.kwBlock` 규칙이 아예 없어(뱃지 줄과 카드 사이 0) 그대로 가져오면 뱃지가 카드에 붙는다. 리뷰가 지적한 것도 컨트롤 줄 하나뿐이라 범위를 넓히지 않았다.
- **상세 뱃지 위치가 승인 시안과 다르다 — 이번엔 안 고치고 알린다** (2026-08-31, 발견): 시안(`badge-row.html:2482`)은 `.detailMeta`(출처·시각·원문 제목, 점선 아래선) **다음에** `.detailKw` 를 별도 줄로 두는데, 구현은 `.tags` 를 `.metaRow` **안에** 인라인으로 넣어 뱃지가 점선 위 출처 옆에 붙는다. 6세션의 "승인된 시안의 정정을 안 가져온 자리 4곳"과 같은 계열이다. 이번 범위(리뷰 이관 2건)를 넘어 화면이 눈에 띄게 바뀌는 변경이라 **고치지 않고 결정을 남긴다** — 고치면 마크업 이동 + `role="group" aria-label="이 소식의 키워드"` 추가가 따라온다.
- **상세 뱃지를 승인 시안 자리(점선 아래 별도 줄)로 옮겼다** (2026-08-31, 사용자 결정): 위 항목에서 "고치지 않고 알린다"로 남겼던 것을 닫는다. `.tags` 를 `.metaRow` 밖 `.keywords` 로 빼고 `role="group" aria-label="이 소식의 키워드"` 를 붙였다. **왜 갈렸는지가 더 중요하다** — `design-rules.md` 의 「카드와 상세」 절이 상세에 대해 "전부 보여준다"만 적고 **자리는 안 적었다.** 자리는 시안 HTML 에만 있었고, 개수·색·높이 테스트는 인라인 상태에서도 전부 통과했다. 그래서 두 곳을 같이 막았다: 문서에 자리를 적고, `article-view.test.tsx` 에 자리 테스트를 넣었다(메타 줄 밖 · 메타 줄의 바로 다음 형제 · `role`/`aria-label` · 칩이 전부 그 줄 안). 변이 2종으로 빨간불 확인. **옮기면서 잠복 결함 하나가 드러났다** — 요약이 없는 글에서 원문 점선이 알약 바닥에 붙어 있었다(위 14px / 아래 **0px**). 알약에 margin 이 없고 원문 점선은 자기 위쪽 테두리라 사이를 벌리는 것이 없다. 요약 박스가 있는 글에서는 그 박스의 `margin-top: 24px` 이 가려서 안 보였다(요약 생성이 실패한 글에서만 나온다). `.keywords + .prose { margin-top: var(--space-14) }` 로 14/14 대칭. **긴 키워드는 안 막았다** — 380px 에서 30자부터 알약이 넘치고 60자면 페이지가 가로로 스크롤되지만, 실제 키워드 57종의 최장이 8자(`소프트웨어 개발`)라 승인된 `white-space: nowrap` 을 유지했다. 다시 볼 조건: 20자 넘는 키워드가 실제로 나올 때.

- **비용 라벨이 어느 단가를 썼는지 말한다** (2026-08-31, 사용자 결정, 리뷰 지적 반영): 같은 토큰 수가 09-01 전후로 다른 금액으로 찍히는데 화면에 근거가 없었다. `estimateCostBreakdown` 이 `rateTier: "promo" | "standard"` 를 같이 돌려주고 위젯은 문구만 고른다 — **날짜 판단을 UI 로 올리지 않는다.** 위젯에서 `new Date(run.startedAt) < ...` 를 다시 계산하면 경계가 두 군데로 갈려 조용히 어긋난다. 실측 확인: 실행 2026-08-31 13:20 KST → "추정 비용 (claude-sonnet-5 **프로모션가** 기준)".
- **`Date.parse` 는 오프셋 없는 시각을 로컬 시간으로 읽는다 — 단가 경계가 시간대만큼 밀렸다** (2026-08-31, 리뷰 지적 반영): `Date.parse("2026-09-01T00:00:00")` 은 ES 규정상 **로컬 시간**이라 KST 에서 `2026-08-31T15:00Z` 가 된다. 즉 **정가여야 할 실행이 프로모션가**로 계산되고, NaN 이 아니라 폴백에도 안 걸려 조용히 싼 쪽으로 틀린다. 프로덕션 경로는 `started_at timestamptz` + `toISOString()` 이라 항상 오프셋이 붙어 안전했지만 **그 전제가 코드에도 테스트에도 없었고** 인자 타입이 `string` 이라 다른 호출자는 아무 문자열이나 넘길 수 있었다. 오프셋 검사를 넣어 없으면 정가로 떨어뜨리고(기존 폴백과 같은 방향) 테스트로 못 박았다. 같은 리뷰에서 **`scripts/count-prompt-tokens.ts` 가 같은 요금 숫자 넷을 손으로 쥐고 있던 것**도 이었다 — "상수를 손으로 갈지 않겠다"는 이번 변경의 이유가 정작 두 번째 자리에서 깨져 있었다. 안내 날짜도 `STANDARD_FROM_MS` 에서 파생시켜 세 번째 복제를 막았다.
