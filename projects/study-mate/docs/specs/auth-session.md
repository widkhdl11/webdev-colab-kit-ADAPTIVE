# 인증과 세션 스펙

> **2026-09-04 승인.** 아래 불변식은 코드에서 역산한 관찰로 시작했지만, 사람이 하나씩
> 확인해 계약으로 삼았다. 이제 "지금 이렇게 동작한다"가 아니라 **"이렇게 동작해야 한다"** 다.
> 다시 짓는 코드는 이 불변식을 만족해야 하고, 불변식마다 그것을 참조하는 테스트가 요구된다.

세션은 Supabase 인증을 쿠키로 유지하고, 요청마다 프록시 계층에서 갱신·검증된다.
어기면 사고가 나는 자리는 둘이다 — 로그인하지 않은 사람이 보호된 화면에 들어가는 것,
그리고 토큰을 검증하지 않고 신뢰하는 것.

## 불변식

- INV-A1: 보호된 경로에 세션 없이 들어오면 화면을 그리기 전에 로그인 페이지로 보낸다.
  (강제 위치: 서버 — 요청 프록시) 위반 시: 비로그인 사용자가 남의 스터디·프로필·채팅
  화면에 도달한다.

  보호되는 것 — `docs/IA.md` 의 화면 목록에서 "로그인 필요"인 화면 전부다:

  | 경로 | 덮는 화면 |
  |---|---|
  | `/posts/create` | 모집글 작성 |
  | `/posts/*/edit` | 모집글 수정 |
  | `/studies` 전체 | 스터디 개설·상세·수정 |
  | `/profile` 전체 | 프로필 조회·수정·비밀번호 변경 |
  | `/chats` 전체 | 채팅방 목록·그룹 채팅 |

  **`/posts` 목록과 `/posts/[id]` 상세는 보호하지 않는다.** 제품 원칙 1이 요구하는
  "발견"이 로그인 앞에 있어야 하고, 판단에 필요한 정보를 로그인 뒤에 숨기면 발견이
  시작되지 못한다. 로그인 벽이 처음 나타나는 자리는 참가 신청이다.

  **2026-09-05 에 `/posts/*/edit` 를 더했다.** 원래 목록은 모집글 수정 화면을 안 덮고
  있었고, 리뷰에서 security-reviewer 와 code-reviewer 가 독립적으로 같은 지적을 했다.
  화면 목록(`docs/IA.md`)이 생기기 전에는 무엇이 빠졌는지 셀 근거가 없어 열어 두었다.
- INV-A2: 이미 로그인한 사용자가 로그인·회원가입 페이지로 오면 홈으로 보낸다.
  (강제 위치: 서버 — 요청 프록시)
  위반 시: 로그인 상태에서 로그인 폼이 보인다(사고는 아니고 흐름의 단절).
- INV-A3: 세션 판정은 클라이언트가 보낸 값이 아니라 **검증된 토큰의 클레임**으로 한다.
  (강제 위치: 서버) 위반 시: 위조된 쿠키로 로그인 상태를 흉내 낼 수 있다.
  구현 시 주의: 세션을 읽는 함수가 여럿이고 **그중 토큰을 검증하지 않는 것이 있다.**
  어느 것을 쓰는지가 이 불변식의 참·거짓을 가르므로, 고른 함수가 검증한다는 근거를 두고
  고른다(원본 프로젝트에서 주석과 실제 호출이 어긋나 있던 자리다).
- INV-A4: 서버 액션은 시작할 때 세션을 확인하고, 없으면 아무 일도 하지 않고 실패를 반환한다.
  (강제 위치: 서버 — 각 액션의 첫 단계)
  위반 시: 비로그인 요청이 쓰기 경로에 들어간다.

## 시나리오

- S1 (INV-A1): Given 세션이 없다 / When `/studies/123` 을 연다 / Then 로그인 페이지로 보낸다.
- S1b (INV-A1, 실패경로): Given 세션이 없다 / When 보호 목록에 없는 `/posts` 목록을 연다 /
  Then 그대로 보여준다(보호 대상이 아니다).
- S2 (INV-A4, 실패경로): Given 세션이 없다 / When 스터디 삭제 액션을 직접 호출한다 /
  Then 아무것도 지우지 않고 "유저 정보를 찾을 수 없습니다"를 반환한다.

## 신뢰 경계

- 믿는 값: 서버에서 검증된 토큰의 사용자 식별자.
- 믿지 않는 값: 클라이언트가 보낸 사용자 식별자, 폼에 담겨 온 작성자 필드, URL 의 id.

## 비범위

- 비밀번호 정책·계정 잠금·다중 기기 세션 관리는 이 스펙이 다루지 않는다.
  Supabase 인증의 기본 동작에 맡겨져 있다.
- **라우트 핸들러(`app/api/**`)는 아직 이 스펙이 다루지 않는다.** INV-A1(페이지 경로)과
  INV-A4(서버 액션) 사이에 비어 있다 — 리뷰에서 지적받았다. 여기에 INV-A1 을 그대로 걸 수
  없는 이유는 **응답의 모양이 다르기 때문**이다. 페이지는 로그인 화면으로 보내면 되지만,
  API 요청을 로그인 HTML 로 리다이렉트하면 부르는 쪽이 그 HTML 을 데이터로 파싱한다.
  거기 맞는 응답은 401 이다. 지금 이 프로젝트에 라우트 핸들러가 하나도 없어서 불변식을
  쓰면 테스트가 가리킬 코드가 없다 — 첫 핸들러가 생길 때 INV-A5 로 추가한다(백로그에 있다).
- 데이터베이스 수준의 접근 통제는 `write-authorization` 스펙이 다룬다.
