# 모집글 좋아요 스펙

한 사람이 모집글 하나에 좋아요를 누르거나 취소한다. 화면에는 **지금까지 몇 명이 눌렀는지**와
**내가 눌렀는지**가 보인다.

**이 기능이 위험 표면에 닿는 이유는 개수 때문이다.** 개수는 사람이 입력하는 값이 아니라
누른 행들에서 **파생되는 값**이고, 파생 상태는 원본과 어긋나도 화면이 멀쩡해 보인다 —
"좋아요 12개"는 그것이 맞는 숫자인지 틀린 숫자인지 화면만 봐서는 알 수 없다. 사고는
나중에 조용히 난다. 그래서 개수의 출처를 먼저 못박는다.

그리고 **누가 누를 수 있고 누구의 좋아요를 지울 수 있는지**가 쓰기 정책이다. 이 제품의
다른 쓰기 경로와 같은 모양으로 둔다(`write-authorization.md`).

## 정해야 할 것 — 개수를 어디서 얻는가

두 갈래가 있고 실패하는 모양이 다르다.

| | 세어서 얻는다 (`count(*)`) | 열에 쌓아 둔다 (`posts.likes_count`) |
|---|---|---|
| 맞음 | 항상 맞는다. 원본이 곧 답이다 | 갱신을 한 번 놓치면 영구히 틀린다 |
| 비용 | 목록 한 화면에 글 20개면 집계가 20번 | 읽기는 열 하나 |
| 어긋나는 모양 | 없음 | 조용함 — 화면은 멀쩡하다 |

**이 스펙은 세는 쪽을 고른다.** 지금 이 제품의 목록은 한 화면에 스무 개 남짓이고,
`post_likes (post_id)` 인덱스가 있으면 그 집계는 인덱스만 읽는다. 쌓아 두는 쪽은
**틀렸을 때 알아차릴 방법이 없다**는 비용이 크고, 그 비용은 데이터가 늘수록 커진다.
나중에 느려지면 그때 쌓아 두는 열을 더하되, **원본에서 다시 세어 대조하는 검사와 같이**
넣는다 — 그 검사가 없는 파생 열은 이 스펙이 금지한다(INV-L5).

## 불변식

- INV-L1: **한 사람은 한 모집글에 좋아요를 하나만 가진다.**
  (강제 위치: DB — `post_likes (post_id, user_id)` 기본 키 또는 유일 제약)

  위반 시: 같은 사람이 두 번 세어져 개수가 사람 수보다 커진다. 두 번 눌러서 늘리는 것이
  가능해지면 개수는 아무 뜻도 없는 숫자가 된다.

  **두 번 눌러도 에러가 아니다.** 같은 사람이 같은 글에 다시 누르면 취소이고, 경합으로
  같은 요청이 두 번 도착하면 결과는 한 번 누른 것과 같다(멱등).

- INV-L2: **개수는 좋아요 행에서 파생된다. 따로 저장된 숫자를 화면이 읽지 않는다.**
  (강제 위치: 읽기 경로 하나 — `src/entities/post/api/*` 의 조회가 `post_likes` 를 세고,
  `posts` 에는 개수 열을 두지 않는다)

  위반 시: 원본과 화면이 갈라진 채로 아무도 모른다.

- INV-L3: **좋아요를 만들 수 있는 것은 로그인한 자신뿐이고, 남의 좋아요를 지울 수 없다.**
  (강제 위치: DB — `post_likes` 의 RLS. insert 는 `user_id = auth.uid()`,
  delete 는 자기 행만)

  위반 시: 남의 이름으로 좋아요가 눌리거나 지워진다. 개수가 여론처럼 읽히는 자리라
  조작이 그대로 화면에 반영된다.

- INV-L4: **좋아요는 모집글이 사라지면 같이 사라진다.**
  (강제 위치: DB — `post_id` 외래 키 `on delete cascade`)

  위반 시: 없는 글을 가리키는 좋아요가 남아 집계에 섞인다.

- INV-L5: **파생된 개수를 열에 쌓아 두려면, 원본에서 다시 세어 대조하는 검사가 같이 있어야
  한다.** 지금은 쌓아 두지 않으므로 이 불변식이 금지하는 것은 「검사 없는 파생 열의 추가」다.
  (강제 위치: 이 스펙과 리뷰. 열이 생기는 순간 대조 테스트가 없으면 거부한다)

  위반 시: 위 표의 「어긋나는 모양: 조용함」이 그대로 실현된다.

## 시나리오

- **S1 (INV-L1, 멱등)**: Given 로그인한 사용자 / When 같은 글에 좋아요를 두 번 보낸다 /
  Then 행은 하나고 개수는 1 이다.
- **S1b (INV-L1, 반대 절반)**: Given 서로 다른 두 사용자 / When 같은 글에 각각 누른다 /
  Then 개수는 2 다 — 유일 제약을 `(post_id)` 로 잘못 걸면 여기서 빨간불이 난다.
- **S2 (INV-L1, 취소)**: Given 이미 누른 사용자 / When 다시 누른다 / Then 행이 없어지고
  개수는 0 이다.
- **S3 (INV-L2)**: Given 좋아요 세 개가 있는 글 / When 행 하나를 DB 에서 직접 지운다 /
  Then 다음 조회의 개수는 2 다 — 어딘가에 숫자를 쌓아 두는 구현이면 3 이 나온다.
- **S4 (INV-L3, 실패경로)**: Given 사용자 A 의 공개 키 연결 / When `user_id` 를 B 로 적어
  좋아요를 넣는다 / Then 거부된다.
- **S4b (INV-L3, 실패경로)**: Given 같은 연결 / When B 의 좋아요 행을 지운다 /
  Then 지워지지 않는다.
- **S4c (INV-L3, 반대 절반)**: Given 같은 연결 / When 자기 좋아요를 넣고 지운다 /
  Then 둘 다 된다 — 정책을 「전부 거부」로 바꿔도 S4·S4b 는 통과한다.
- **S4d (INV-L3, 비로그인)**: Given 익명 연결 / When 좋아요를 넣는다 / Then 거부된다.
- **S5 (INV-L4)**: Given 좋아요가 달린 모집글 / When 그 글을 지운다 / Then 좋아요 행도
  없어진다.
- **S6 (INV-L1, 경합)**: Given 같은 사용자의 동시 요청 둘 / When 같은 글에 동시에 누른다 /
  Then 한쪽이 유일 제약에 걸리고 최종 상태는 행 하나다 — 그 실패가 사용자에게 에러로
  나가면 안 된다.

## 비범위

- **좋아요 알림은 안 만든다.** `notifications.md` 가 다루는 사건 종류를 늘리는 일이고,
  좋아요는 참가 신청과 달리 받는 사람이 할 일이 없다.
- **누가 눌렀는지의 목록은 화면에 안 낸다.** 개수와 내 상태만 보인다. 목록을 내면 그것이
  또 하나의 「사람이 쓴 글자가 남의 화면에 나가는 자리」가 되고
  (`text-display-integrity.md`), 지금 정할 일이 아니다.
- **정렬·인기순은 이 스펙 밖이다.** 개수를 세는 자리가 정해지면 그 위에서 정하면 된다.
