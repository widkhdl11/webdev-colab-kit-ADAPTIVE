# 모집글 좋아요 스펙

한 사람이 모집글 하나에 좋아요를 누르거나 취소한다. 화면에는 **지금까지 몇 명이 눌렀는지**와
**내가 눌렀는지**가 보인다.

## 이 스펙이 하는 일 — 새로 만드는 것이 아니다

**2026-09-16 에 기존 구현을 읽고 다시 썼다.** 처음 쓸 때는 코드를 안 보고 「새로 만드는
기능」으로 적었는데, 데이터베이스 쪽은 `0001_init.sql` 부터 이미 다 있었다. 없는 것은
**누르는 자리 하나**였다 — `likes` 에 쓰는 코드가 앱 어디에도 없어서 개수는 보이는데
영원히 0 이다.

그래서 이 스펙이 하는 일은 둘이다.

1. **이미 있는 계약을 문장으로 고정하고 테스트를 붙인다.** 아래 다섯 가지는 전부 구현돼
   있는데 **그것을 확인하는 테스트가 하나도 없었다.** 구현이 있다는 것과 그것이 계약이라는
   것은 다르다 — 검사가 없으면 다음 사람이 「좋아요순 정렬이 느리다」 같은 이유로
   `posts.likes_count` 열을 더해도 아무것도 빨갛게 되지 않는다.
2. **누르는 자리를 만든다.** 토글 서버 액션과 상세 화면의 버튼.

## 개수를 어디서 얻는가 — 이미 정해져 있다

`0001_init.sql:129` 의 주석이 결정을 들고 있다.

> `likes_count` 를 두지 않는다 — `likes` 를 세면 나온다. `comments_count` 도 두지 않는다:
> 제품에 댓글이 없다. `views_count` 는 남긴다 — 원천 테이블이 없는 진짜 카운터다.

실제 구현은 `likes_count(public.posts)` 라는 **계산 함수**다(`0002_review_fixes.sql:148`).
PostgREST 가 이것을 계산된 열로 노출하므로, 목록 조회는 카드 열 목록에 `likes_count` 를
끼워 **한 번의 질의**로 가져온다(`src/entities/post/api/post-query.ts:26`) — 글 스무 개에
집계 스무 번이 아니다.

- **단일 질의 — 확인됨.** 별도의 집계 왕복이 없다.
- **읽기 공개 — 확인됨.** `likes_read on public.likes for select using (true)`
  (`0001_init.sql:533`). 개수는 누구나 세고, 내 것인지는 `user_id` 로 걸러서 본다
  (`src/entities/post/api/read-post-detail.ts:111`).

쌓아 두는 열로 바꾸려면 **원본에서 다시 세어 대조하는 검사와 같이** 와야 한다 —
그 검사가 없는 파생 열은 INV-L5 가 금지한다.

## 불변식

- INV-L1: **한 사람은 한 모집글에 좋아요를 하나만 가진다.**
  (강제 위치: DB — `constraint likes_unique unique (post_id, user_id)`,
  `0001_init.sql:153`. **이미 있다**)

  위반 시: 같은 사람이 두 번 세어져 개수가 사람 수보다 커진다. 두 번 눌러서 늘리는 것이
  가능해지면 개수는 아무 뜻도 없는 숫자가 된다.

  **두 번 눌러도 에러가 아니다.** 같은 사람이 같은 글에 다시 누르면 취소이고, 경합으로
  같은 요청이 두 번 도착하면 결과는 한 번 누른 것과 같다(멱등).

- INV-L2: **개수는 좋아요 행에서 파생된다. 따로 저장된 숫자를 화면이 읽지 않는다.**
  (강제 위치: DB — 계산 함수 `likes_count(public.posts)` 가 `count(*)` 한다,
  `0002_review_fixes.sql:148`. `posts` 에는 개수 열이 없다. **이미 있다**)

  위반 시: 원본과 화면이 갈라진 채로 아무도 모른다.

- INV-L3: **좋아요를 만들 수 있는 것은 로그인한 자신뿐이고, 남의 좋아요를 지울 수 없다.**
  (강제 위치: DB — `likes_write_self`(insert, `user_id = auth.uid()`) ·
  `likes_del_self`(delete, 같은 조건) · `likes_read`(select, 공개),
  `0001_init.sql:533`. **이미 있다**)

  위반 시: 남의 이름으로 좋아요가 눌리거나 지워진다. 개수가 여론처럼 읽히는 자리라
  조작이 그대로 화면에 반영된다.

- INV-L4: **좋아요는 모집글이 사라지면 같이 사라진다.**
  (강제 위치: DB — `post_id uuid not null references public.posts (id) on delete cascade`,
  `0001_init.sql:150`. **이미 있다**)

  위반 시: 없는 글을 가리키는 좋아요가 남아 집계에 섞인다.

- INV-L5: **파생된 개수를 열에 쌓아 두려면, 원본에서 다시 세어 대조하는 검사가 같이 있어야
  한다.** 지금은 쌓아 두지 않으므로 이 불변식이 금지하는 것은 「검사 없는 파생 열의 추가」다.
  (강제 위치: `tests/integration/post-likes.test.ts` 가 `posts` 에 `like` 가 든 열이
  없다는 것을 본다. 열이 생기는 순간 그 검사가 빨개지고, 대조 테스트를 같이 들고 오게 한다)

  위반 시: 위 표의 「어긋나는 모양: 조용함」이 그대로 실현된다.

## 새로 만드는 것

- **토글 서버 액션** — 누른 적이 없으면 넣고, 있으면 지운다. 같은 요청이 두 번 도착해도
  결과는 한 번 누른 것과 같다(INV-L1 의 멱등).
- **상세 화면의 버튼** — 개수와 내 상태를 보여 주고 누르면 토글한다. 지금 그 자리는
  글자만 있다(`src/widgets/post-detail/ui/PostDetailView.tsx:185`).

## 시나리오

- **S1 (INV-L1, 멱등)**: Given 로그인한 사용자 / When 같은 글에 좋아요를 두 번 보낸다 /
  Then 행은 하나고 개수는 1 이다.
- **S1b (INV-L1, 반대 절반)**: Given 서로 다른 두 사용자 / When 같은 글에 각각 누른다 /
  Then 개수는 2 다 — 유일 제약을 `(post_id)` 로 잘못 걸면 여기서 빨간불이 난다.
- **S2 (INV-L1, 취소)**: Given 이미 누른 사용자 / When 다시 누른다 / Then 행이 없어지고
  개수는 0 이다.
- **S3 (INV-L2)**: Given 좋아요 세 개가 있는 글 / When 행 하나를 DB 에서 직접 지운다 /
  Then 다음 조회의 개수는 2 다 — 어딘가에 숫자를 쌓아 두는 구현이면 3 이 나온다.
- **S4 (INV-L3, 실패경로)**: Given 사용자 A 의 공개 키 연결 / When `user_id` 를 B 로 적어
  좋아요를 넣는다 / Then 거부된다.
- **S4b (INV-L3, 실패경로)**: Given 같은 연결 / When B 의 좋아요 행을 지운다 /
  Then 지워지지 않는다.
- **S4c (INV-L3, 반대 절반)**: Given 같은 연결 / When 자기 좋아요를 넣고 지운다 /
  Then 둘 다 된다 — 정책을 「전부 거부」로 바꿔도 S4·S4b 는 통과한다.
- **S4d (INV-L3, 비로그인)**: Given 익명 연결 / When 좋아요를 넣는다 / Then 거부된다.
- **S5 (INV-L4)**: Given 좋아요가 달린 모집글 / When 그 글을 지운다 / Then 좋아요 행도
  없어진다.
- **S6 (INV-L1, 경합)**: Given 같은 사용자의 동시 요청 둘 / When 같은 글에 동시에 누른다 /
  Then 한쪽이 유일 제약에 걸리고 최종 상태는 행 하나다 — 그 실패가 사용자에게 에러로
  나가면 안 된다.

## 비범위

- **좋아요 알림은 안 만든다.** `notifications.md` 가 다루는 사건 종류를 늘리는 일이고,
  좋아요는 참가 신청과 달리 받는 사람이 할 일이 없다.
- **누가 눌렀는지의 목록은 화면에 안 낸다.** 개수와 내 상태만 보인다. 목록을 내면 그것이
  또 하나의 「사람이 쓴 글자가 남의 화면에 나가는 자리」가 되고
  (`text-display-integrity.md`), 지금 정할 일이 아니다.
- **정렬·인기순은 이 스펙 밖이다.** 개수를 세는 자리가 정해지면 그 위에서 정하면 된다.
