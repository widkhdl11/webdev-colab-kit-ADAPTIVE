# 참가·정원·모집 상태 스펙

> **이 스펙은 코드에서 역산했다.** 아래 불변식은 관찰이지 합의가 아니고, 지금 동작이
> 버그일 수도 있다. 항목마다 확인 필요 표시를 달았고 `status` 는 `draft` 다.

참가 신청이 수락되면 스터디의 현재 인원이 올라가고, 정원이 차면 모집 상태가 바뀐다.
현재 인원과 모집 상태는 **다른 값에서 파생되는 값**이고, 동시에 들어온 수락 요청이
정원을 넘길 수 있다. 어기면 사고가 나는 자리가 여기다.

## 관찰된 사실 — 불변식보다 먼저 읽을 것

- 현재 인원과 모집 상태를 실제로 갱신하는 것은 **데이터베이스 트리거**다. 참여자 행이
  들어오고 나가고 바뀔 때마다 수락된 참여자를 세어 스터디 행에 쓴다. `[문서에서 확인]`
- 그런데 도메인 모델에도 모집 상태의 전이 규칙이 있다. 같은 값의 주인이 둘이다.
  기존 문서는 이 상태를 "누가 주인인지 정리 대상"이라고 적어 두었다. `[문서에서 확인]`
- 참여자 상태 값은 데이터베이스 제약이 `pending` · `accepted` · `rejected` 셋만 허용한다.
  도메인에는 강퇴·탈퇴 결과가 따로 있어서, 저장할 때 이 셋으로 옮겨지지 않으면 제약에
  걸린다. `[문서에서 확인]`

## 불변식

- INV-P1: 수락된 참여자 수는 스터디의 정원을 넘지 않는다. (강제 위치: 데이터베이스 —
  제약과 트리거) 위반 시: 정원 초과 스터디가 생기고 좌석 표시가 거짓이 된다.
  `[추정 — 확인 필요]`
- INV-P2: 스터디의 현재 인원은 저장된 값이 아니라 **수락된 참여자 수에서 파생된 값**이며,
  참여자 행이 바뀔 때마다 다시 계산된다. (강제 위치: 데이터베이스 트리거)
  위반 시: 화면의 인원수와 실제 멤버 수가 어긋난다. `[추정 — 확인 필요]`
- INV-P3: 정원을 현재 인원보다 작게 줄일 수 없다. (강제 위치: 데이터베이스 트리거)
  위반 시: 이미 들어온 멤버가 정원 밖으로 밀려난 채 남는다. `[추정 — 확인 필요]`
- INV-P4: 참가 신청을 수락할 수 있는 것은 신청이 아직 대기 상태이고 스터디가 모집 중일
  때뿐이다. (강제 위치: 서버 — 액션과 도메인 규칙)
  위반 시: 마감된 스터디에 멤버가 들어오거나 같은 신청이 두 번 수락된다.
  `[추정 — 확인 필요]`
- INV-P5: 참가가 수락되면 그 사람은 스터디의 그룹 채팅방 참여자가 된다. 같은 사람이 두 번
  들어가지 않는다. (강제 위치: 데이터베이스 트리거)
  위반 시: 승인됐는데 대화를 시작할 수 없다 — 제품의 핵심 흐름이 여기서 끊긴다.
  `[추정 — 확인 필요]`
- INV-P6: 모집 상태 값을 바꾸는 주인은 하나다. (강제 위치: **정해져 있지 않다**)
  위반 시: 두 곳이 서로 다른 규칙으로 같은 값을 써서, 화면과 데이터베이스가 어긋난다.
  `[추정 — 확인 필요]` — 이 불변식은 지금 지켜지지 않는다고 기존 문서가 스스로 적고 있다.

## 시나리오

- S1 (INV-P1, 실패경로): Given 정원이 4명이고 수락된 멤버가 4명 / When 호스트가 다섯 번째
  신청을 수락한다 / Then 거부한다.
- S2 (INV-P2): Given 수락된 멤버가 3명 / When 한 명을 강퇴한다 / Then 현재 인원이 2가 된다.
- S3 (INV-P3, 실패경로): Given 현재 인원이 3명 / When 정원을 2로 줄인다 / Then 거부한다.
- S4 (INV-P5): Given 대기 중인 신청 / When 호스트가 수락한다 / Then 그 사람이 그룹 채팅방
  참여자 목록에 정확히 한 번 나타난다.
- S5 (INV-P1, 경합): Given 남은 자리가 하나 / When 두 수락이 동시에 들어온다 /
  Then 하나만 성공한다. **지금 그렇게 되는지 아무도 확인하지 않았다.**

## 신뢰 경계

- 믿는 값: 데이터베이스가 세어 넣은 현재 인원, 참여자 행의 상태 값.
- 믿지 않는 값: 화면이 들고 있던 인원수(캐시), 클라이언트가 보낸 정원·상태 값.
