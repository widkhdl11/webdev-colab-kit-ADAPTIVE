# 참가·정원·모집 상태 스펙

> **2026-09-04 승인, 2026-09-05 모델링 개정.** 아래 불변식은 사람이 확인해 계약으로 삼았다 —
> "지금 이렇게 동작한다"가 아니라 **"이렇게 동작해야 한다"** 다.
>
> **2026-09-05 활성 계약이 됐다.** 불변식 일곱을 참조하는 테스트가
> `tests/integration/participation-capacity.test.ts` 에 있고, 실제 로컬 Postgres 에 붙어서 돈다.
> 흉내 낸 객체로는 "제약과 트리거가 실제로 거부하는가"를 물을 수 없어서다.
> 강제 장치를 하나씩 무력화해 전부 빨간불이 되는 것을 확인했다(결정 로그의 변이 표).
>
> **2026-09-05 (2) 리뷰 개정 — 불변식 둘을 더한다.** 그 변이 표에도 구멍이 있었다.
> 검사가 전부 **슈퍼유저 직결**로 돌아서 행 수준 접근 정책을 안 탔고, 그래서 파생값을 내는
> 함수가 **묻는 사람마다 다른 답을 준다는 것**을 아무도 못 봤다(INV-P9). 그리고 INV-P5 는
> 채팅방에 들어가는 쪽만 정하고 나오는 쪽을 안 정해서, 강퇴가 대화에서 아무 일도 하지
> 않는 상태가 코드에 그대로 있었다(INV-P8).

참가 신청이 수락되면 스터디의 인원이 늘고, 정원이 차면 더 못 들어온다. 어기면 사고가 나는
자리는 둘이다 — 정원을 넘겨 들어오는 것, 그리고 화면에 보이는 인원수가 거짓이 되는 것.

## 2026-09-05 모델링 개정 — 무엇이 바뀌었나

승인된 시안 3장과 데이터 모델링 체크리스트를 들여온 스키마에 대고 훑었다. 두 가지가 바뀐다.

**① 인원수를 저장하지 않는다.** 들여온 스키마는 `studies.current_participants` 라는 컬럼에
수락된 인원을 세어 넣고 트리거로 갱신했다. 체크리스트 2번(파생값)에 정면으로 걸린다 —
파생값을 저장하면 원천과 어긋날 여지가 생기고, 그 어긋남은 조용하다. **수락된 참여자 행을
세면 언제나 정확한 값이 나오므로 저장할 이유가 없다.**

정원 초과는 컬럼이 아니라 **참여자 행이 들어올 때 세어서** 막는다(INV-P1). 값을 저장하지
않아도 강제 위치는 그대로 데이터베이스다.

**② 모집 상태의 주인 싸움을 없앤다(INV-P6).** 들여온 스키마의 `status` 는 세 값
(`recruiting`·`closed`·`completed`)이었고, 트리거와 도메인 규칙이 같은 값을 각자 관리해서
원본 문서가 스스로 "정리 대상"이라고 적어 두었다.

원인은 **한 컬럼이 성격이 다른 두 가지를 담고 있었다는 것**이다.

| | 무엇 | 성격 |
|---|---|---|
| `closed` | 호스트가 직접 모집을 닫았다 | **사람의 행위** — 어디서도 파생되지 않는다 |
| `completed` | 정원이 찼다 | **파생값** — 수락 인원과 정원에서 나온다 |

그래서 **사람의 행위만 저장하고 나머지는 파생시킨다.** `closed_at`(호스트가 닫은 시각,
안 닫았으면 비어 있음) 하나만 저장하고, "모집 중인가"는 그때그때 계산한다.

```
모집 중 = closed_at 이 비어 있다  그리고  수락된 인원 < 정원
```

**주인이 둘일 수가 없어진다 — 다툴 값 자체가 사라지기 때문이다.** 이게 체크리스트의
권장 패턴("파생값을 저장하지 말고 앵커를 저장하라")을 이 도메인에 적용한 것이다.

## 관찰된 사실 — 불변식보다 먼저 읽을 것

- 참여자 상태 값은 들여온 데이터베이스가 `pending` · `accepted` · `rejected` 셋만 허용했다.
  그런데 제품에는 **강퇴와 탈퇴**가 있다. 도메인에는 그 결과가 따로 있는데 저장할 자리가
  없어서, 저장할 때 셋 중 하나로 뭉개지 않으면 제약에 걸렸다. `[문서에서 확인]`
  → 체크리스트 5번(상태 전이). 아래 INV-P7 로 닫는다.
- 참여자 행에 이름·이메일·사진이 복사돼 있었다(조회 효율용 사본). `[문서에서 확인]`
  → 체크리스트 2번. 사본은 원본이 바뀌어도 안 따라간다. **없앤다.** 신뢰 경계에도 이미
  "복사본은 믿지 않는다"고 적혀 있었다.
- 포인트 컬럼과 이력 테이블·트리거가 남아 있었다. 제품 정의의 비범위다. **없앤다.**

## 불변식

- INV-P1: 수락된 참여자 수는 스터디의 정원을 넘지 않는다. **동시에 들어온 수락 요청에도
  넘지 않는다** — 남은 자리가 하나일 때 두 수락이 동시에 오면 하나만 성공한다.
  (강제 위치: 데이터베이스 — 참여자 행이 수락 상태로 들어오거나 바뀔 때, 스터디 행을 잠그고
  수락 인원을 세어 정원을 넘기면 거부한다)
  위반 시: 정원 초과 스터디가 생기고 화면의 좌석 표시가 거짓이 된다.

- INV-P2: 스터디의 현재 인원은 **저장된 값이 아니라 수락된 참여자 행을 세어 얻는 값**이다.
  인원수를 담는 컬럼은 존재하지 않는다. (강제 위치: 스키마 — 그런 컬럼을 두지 않는다)
  위반 시: 저장된 수와 실제 참여자 수가 어긋나고, 어느 쪽이 맞는지 판정할 방법이 없다.

- INV-P3: 정원을 현재 수락 인원보다 작게 줄일 수 없다.
  (강제 위치: 데이터베이스 — 스터디 정원이 바뀔 때 검사)
  위반 시: 이미 들어온 멤버가 정원 밖으로 밀려난 채 남는다.

- INV-P4: 참가 신청을 수락할 수 있는 것은 **신청이 아직 대기 상태이고 그 스터디가 모집
  중일 때**뿐이다. (강제 위치: **데이터베이스** — 수락될 때 스터디가 닫혔는지 확인하고,
  대기 상태였는지는 INV-P7 의 전이 검사가 함께 막는다. 서버에도 같은 판정을 두지만 그것은
  화면에 이유를 보여주기 위한 것이고, 계약을 지키는 것은 데이터베이스다 — 공개 키로
  접근하는 구조에서 서버 판정은 우회 가능하다)
  위반 시: 마감된 스터디에 멤버가 들어오거나 같은 신청이 두 번 수락된다.

- INV-P5: 참가가 수락되면 그 사람은 스터디의 그룹 채팅방 참여자가 된다. 같은 사람이 두 번
  들어가지 않는다. (강제 위치: 데이터베이스 — 수락될 때 채팅 참여자를 넣고, 같은 방·같은
  사람 조합에 유일성을 건다)
  위반 시: 승인됐는데 대화를 시작할 수 없다 — 제품의 핵심 흐름이 여기서 끊긴다.

- INV-P6: 모집 상태는 **저장되지 않고 파생된다.** 저장하는 것은 호스트가 모집을 닫은
  시각 하나뿐이고, "모집 중인가"는 **호스트가 닫지 않았다 · 수락 인원이 정원보다 적다 ·
  스터디가 지워지지 않았다** 셋이 모두 참일 때다.
  (강제 위치: 스키마 — 모집 상태를 담는 컬럼을 두지 않는다)
  위반 시: 두 곳이 서로 다른 규칙으로 같은 값을 써서 화면과 데이터베이스가 어긋난다.
  — **들여온 구조에서는 이것이 지켜지지 않았고**, 원본 문서가 스스로 그렇게 적고 있었다.

  **삭제 조건은 2026-09-05 에 더했다.** 계산 컬럼은 처음부터 지워진 스터디를 걸렀는데
  계약에는 그 조건이 없어서, 그 가지를 붙드는 검사가 INV-P9(누가 묻든 같은 답)의 이름표를
  달고 있었다. 성질이 다른 검사에 같은 이름표가 붙으면 빨간불이 무엇을 잡았는지 못 가른다.

  **모집 마감일은 여기 들어가지 않는다**(2026-09-05 결정). 마감일은 호스트가 적어 둔 목표이고
  모집을 닫는 것은 호스트다 — 마감일이 지난 스터디도 그대로 모집 중이고, 목록에서 뒤로 갈
  뿐이다(그 순서는 `docs/IA.md` 가 정한다).

- INV-P7: 참여자 상태는 신청 이후에 일어날 수 있는 결과를 **전부** 표현한다 —
  대기 · 수락 · 거절 · 탈퇴 · 강퇴. 그리고 끝난 상태에서 되돌아가지 않는다.
  (강제 위치: 데이터베이스 — 허용값 제약 + 서버 — 도메인의 전이 함수)
  위반 시: 강퇴와 탈퇴를 저장할 자리가 없어 다른 상태로 뭉개지고, 그러면 "왜 나갔는지"를
  화면도 호스트도 알 수 없다.

- INV-P8: **채팅방의 구성원은 참가 상태에서 파생된다 — 양쪽 방향으로.** 수락되면 들어가고,
  끝난 상태(거절·탈퇴·강퇴)가 되면 **나간다.** 구성원 자리는 참가 상태와 독립적으로 바뀌지
  않는다. 나간 뒤에도 그 사람이 남긴 메시지는 그대로 남는다(INV-Z6 과 같은 결).
  (강제 위치: 데이터베이스 — 참가 상태가 바뀔 때 채팅 구성원을 넣고 빼는 트리거)
  위반 시: **강퇴가 아무 일도 하지 않는다.** 내보낸 사람이 대화를 계속 읽고 계속 쓴다 —
  호스트가 문제 있는 멤버를 내보내는 것이 제품에서 실제로 의미하는 자리가 대화이기 때문이다.
  INV-P5 는 들어가는 쪽만 정하고 나오는 쪽을 정하지 않았다. 그 빈칸이 그대로 코드의 빈칸이었다.

- INV-P9: 수락 인원과 모집 상태는 **누가 묻든 같은 답**을 준다. 묻는 사람의 권한에 따라
  달라지지 않는다. (강제 위치: 데이터베이스 — 파생값을 내는 함수가 호출자의 시야가 아니라
  정의된 권한으로 센다. 내보내는 것은 **수**와 **참/거짓**뿐이고 참여자 행 자체는 아니다)
  위반 시: 로그인하지 않은 방문자에게 좌석이 언제나 `0 / 정원` 으로 보이고 정원이 꽉 찬
  스터디도 "모집중"으로 보인다. **오류가 아니라 그럴듯한 숫자로 틀리기 때문에 화면을 봐도
  모른다** — 신청 버튼을 누른 뒤에야 거부당한다. 발견 화면 셋이 전부 비로그인 공개라
  이 값이 틀리면 제품의 첫 화면부터 거짓말이 된다.

## 시나리오

- S1 (INV-P1, 실패경로): Given 정원이 4명이고 수락된 멤버가 4명 / When 호스트가 다섯 번째
  신청을 수락한다 / Then 거부한다.
- S2 (INV-P2): Given 수락된 멤버가 3명 / When 한 명을 강퇴한다 / Then 인원을 물었을 때 2가
  나온다. 어디에도 3이 저장돼 있지 않다.
- S3 (INV-P3, 실패경로): Given 수락 인원이 3명 / When 정원을 2로 줄인다 / Then 거부한다.
- S4 (INV-P5): Given 대기 중인 신청 / When 호스트가 수락한다 / Then 그 사람이 그룹 채팅방
  참여자 목록에 정확히 한 번 나타난다.
- S5 (INV-P1, 경합): Given 남은 자리가 하나 / When 두 수락이 **동시에** 들어온다 /
  Then 하나만 성공하고 다른 하나는 거부된다.
- S6 (INV-P6): Given 정원 5명에 수락 3명이고 호스트가 닫지 않았다 / When 모집 상태를 묻는다 /
  Then "모집 중". 그다음 호스트가 닫으면 인원이 그대로여도 "마감".
- S7 (INV-P6, 반대 절반): Given 호스트가 닫지 않았고 수락 인원이 정원과 같다 /
  When 모집 상태를 묻는다 / Then "마감" — 사람이 아무것도 안 해도 그렇다.
- S7-1 (INV-P6, 삭제): Given 자리가 남았고 호스트가 닫지도 않은 스터디 / When 호스트가 그것을
  지운 뒤 모집 상태를 묻는다 / Then "마감" — 인원도 닫은 시각도 그대로인데 답이 바뀐다.
- S8 (INV-P7, 실패경로): Given 이미 거절된 신청 / When 그것을 수락으로 바꾼다 /
  Then 거부한다. 끝난 상태에서 되돌아가지 않는다.
- S9 (INV-P8, 실패경로): Given 수락돼 채팅방에 들어간 멤버 / When 호스트가 그를 강퇴한다 /
  Then 그는 채팅 구성원에서 빠지고, 그 방의 메시지를 더는 읽지도 쓰지도 못한다. 이미 보낸
  메시지는 남아 있다.
- S10 (INV-P8, 본인 탈퇴): Given 수락된 멤버 / When 스스로 탈퇴한다 / Then 같은 결과가 된다.
- S11 (INV-P9): Given 정원이 꽉 찬 스터디 / When **로그인하지 않은 연결**로 수락 인원과
  모집 상태를 묻는다 / Then 호스트가 물었을 때와 같은 답(정원만큼 · 모집 아님)이 나온다.
- S12 (INV-P9, 반대 절반): Given 같은 연결 / When 참여자 행 자체를 읽으려 한다 /
  Then 여전히 보이지 않는다. 파생값을 열었다고 명단이 열린 것은 아님을 보인다.

## 신뢰 경계

- 믿는 값: 참여자 행의 상태, 스터디 행의 정원과 닫은 시각.
- 믿지 않는 값: 화면이 들고 있던 인원수(캐시), 클라이언트가 보낸 정원·상태 값,
  그리고 **저장된 인원수** — 이 스펙 이후로 그런 값은 존재하지 않는다.

## 비범위

- 포인트 적립은 제품에 없다. 관련 컬럼·테이블·트리거를 새 스키마에 만들지 않는다.
- 알림 전달의 신뢰성(빠짐 없이 도착하는가)은 이 스펙이 다루지 않는다.
- 누가 수락할 수 있는지(호스트만)는 `write-authorization` 스펙이 다룬다. 여기는 **언제**
  수락할 수 있는지만 다룬다.
