# 알림 스펙

> **2026-09-08 승인.** 불변식 여덟을 사람이 하나씩 보고 계약으로 삼았다 — "지금 이렇게
> 동작한다"가 아니라 **"이렇게 동작해야 한다"** 다.
>
> 승인 시점에 여덟 중 하나(INV-N5)가 안 지켜지고 있었다 — 알림 표의 갱신 권한이 열 단위로
> 좁혀져 있지 않아 자기 알림의 종류·제목을 고칠 수 있었다. **마이그레이션 `0019` 가 그날
> 닫았다**(`revoke update … / grant update (read_at)`). 여덟이 전부 강제 장치를 갖고 있다.

알림은 참가 사건(신청·수락·거절·강퇴·탈퇴)에서 자동으로 생기는 기록이고, 헤더 종 아이콘에
달린 패널에서만 보인다(별도 페이지 없음 — `docs/IA.md` 「화면이 아닌 것」).

**어기면 사고인 것은 셋이다.**

**① 남의 알림이 보이는 것.** 알림의 `type` 에는 `participation_rejected` 와
`participation_kicked` 가 있다. 남의 알림 한 줄이 보이면 **"누가 어느 스터디에 신청했다가
거절당했는지"**가 그대로 나온다 — 쓰기 인가 스펙이 INV-Z11 로 참여자 명단을 좁힌 것과 같은
값이고, 알림은 그 값을 **문장으로 만들어 둔 것**이라 명단보다 더 직접적이다.

**② 사람이 알림을 만들 수 있는 것.** 알림은 "이런 일이 있었다"는 사실 기록이다. 사람이 넣을
수 있으면 **자기에게 「○○ 스터디에 수락되었습니다」를 만들어 넣을 수 있고**, 그 순간 알림은
사실이 아니라 주장이 된다. 지금 이 테이블에 삽입 정책이 없는 것은 빠뜨린 것이 아니라
그 결론이다(`0002` 가 그렇게 적어 두었다).

**③ 알림이 엉뚱한 사람에게 가는 것.** 거절 알림이 신청자가 아닌 다른 사람에게 만들어지면
①과 같은 유출이 **정책을 하나도 어기지 않은 채로** 일어난다. 그 사람은 자기 알림을 볼
권한이 있고, 그 안에 남의 일이 들어 있을 뿐이다.

## 관찰된 사실 — 불변식보다 먼저 읽을 것

- `notifications` 표에는 조회·갱신·삭제 정책만 있고 **삽입 정책이 없다.** 정책이 없으면
  아무도 못 넣는다 — 트리거가 `security definer` 로 만드는 것이 유일한 경로다.
  `[코드에서 확인: 0001_init.sql:556-564, 0002_review_fixes.sql:326-336]`
- 알림을 만드는 것은 `participants` 표의 삽입·상태 갱신에 붙은 트리거
  `participants_notify` 하나뿐이다. 받는 사람은 사건마다 다르다 — 신청과 탈퇴는 호스트에게,
  수락·거절·강퇴는 그 사람에게. `[코드에서 확인: 0002_review_fixes.sql:348-396]`
- 트리거는 두 경우를 **일부러 건너뛴다**: 스터디를 만들 때 호스트 자신이 `accepted` 로
  들어오는 행(알릴 일이 아니다)과, 호스트가 자기 스터디에서 스스로 나가는 경우(자기에게
  자기 소식을 보내지 않는다). `[코드에서 확인: 0002_review_fixes.sql:362-364, 383-386]`
- 알림 행은 참조 대상에 외래 키를 걸지 않는다. 원본이 사라져도 문장이 남아야 하기 때문이고,
  **"링크가 죽을 수 있다는 것은 화면이 처리한다"고 적혀 있다** — 그런데 그 화면이 아직
  없어서 무엇을 하는지 아무 데도 안 적혀 있다. `[코드에서 확인: 0001_init.sql:190-204]`
- 저장되는 `title` 은 알림 문장이 아니라 **그때의 스터디 제목**이다. 화면에 나갈 문장은
  `type` 과 이 제목으로 조립된다. `[코드에서 확인: 0002_review_fixes.sql:386-387]`
- `notifications` 의 갱신 권한은 **표 전체에 열려 있었다.** 같은 마이그레이션이
  `participants`(상태만) · `chat_participants`(마지막 읽은 시각만) · `posts`(제목·요약·본문만)
  에는 열 단위로 좁혀 두었는데 알림만 그 목록에 없었다.
  `[코드에서 확인: 0002_review_fixes.sql:168-175]`
  **2026-09-08 에 `0019` 가 `read_at` 한 열로 좁혔다** — 이 스펙이 승인되면서 닫힌 자리다.
- 앱에 있는 것은 안 읽은 수를 세는 판독기 하나뿐이고, 그것은 조건을 `read_at is null` 로만
  적는다 — 누구 것인지는 접근 정책이 정한다.
  `[코드에서 확인: src/entities/notification/api/read-unread-count.ts]`
- 종 옆 숫자는 화면마다 서버에서 다시 세어 넘긴다. 저장된 값이 아니라 **매 요청 파생되는
  값**이다. `[코드에서 확인: src/app/**/page.tsx 의 readUnreadNotificationCount 호출]`

## 불변식

- INV-N1: 알림은 **받는 사람 본인에게만 보인다.** 다른 누구도, 스터디의 호스트도, 그 사건의
  상대방도 남의 알림 행을 읽을 수 없다.
  (강제 위치: 데이터베이스 — 조회 정책 `notifications_read_own`)
  위반 시: 누가 어느 스터디에서 거절·강퇴당했는지가 남에게 보인다. INV-Z11 이 명단에서 막은
  값이 문장으로 새어 나간다.

- INV-N2: 알림을 **사람이 만들 수 없다.** 로그인한 사용자는 자기 앞으로도 알림을 넣을 수 없고,
  알림이 생기는 경로는 참가 사건에 붙은 트리거뿐이다.
  (강제 위치: 데이터베이스 — `notifications` 에 삽입 정책을 두지 않는 것 + `security definer`
  트리거)
  위반 시: 알림이 사실 기록이 아니라 주장이 된다. 수락되지도 않은 사람이 자기 화면에
  「수락되었습니다」를 만들어 두고, 화면은 그것을 사실처럼 그린다.

- INV-N3: 알림의 **받는 사람은 사건의 상대방이다.** 신청이 들어오면 호스트에게, 수락·거절·
  강퇴는 그 신청을 한 사람에게, 탈퇴는 호스트에게 간다. 스터디를 만들며 호스트가 스스로
  `accepted` 로 들어오는 행과, 호스트가 자기 스터디에서 스스로 나가는 경우에는 알림이 생기지
  않는다.
  (강제 위치: 데이터베이스 — 트리거 `participants_notify`)
  위반 시: 정책을 하나도 어기지 않고 INV-N1 의 유출이 일어난다 — 받은 사람은 자기 알림을 볼
  권한이 있고, 그 안에 남의 일이 들어 있을 뿐이다.

- INV-N4: **읽음 처리와 삭제는 자기 알림만 대상이다.** 「전체 읽음」도 자기 알림 밖으로
  나가지 않는다.
  (강제 위치: 데이터베이스 — `notifications_update_own` · `notifications_delete_own`.
  앱이 붙이는 조건은 보조다)
  위반 시: 남이 아직 못 본 알림이 읽은 것으로 바뀌거나 사라진다. 삭제는 되돌릴 수 없다 —
  알림에는 지운 것으로 표시하는 열이 없다.

  **벽이 둘이고, 하나만 보면 다른 하나가 열린 것을 아무도 모른다.** 조건이 붙은 갱신
  (`where id = …`)은 그 조건을 계산하느라 조회 정책이 같이 걸리므로, 갱신 정책을 통째로
  열어 놔도 조회 정책이 대신 막는다. **조건도 `returning` 도 없는 문장**(`update
  notifications set read_at = now()`)은 조회 정책을 안 거치고 갱신 정책 혼자 판정한다 —
  그 경로로 남의 알림이 전부 읽음이 될 수 있다. 그래서 시나리오 S4·S4b 는 조건 없는
  문장으로도 확인한다. (2026-09-08 변이 검증에서 실제로 드러났다)

- INV-N5: **만들어진 알림의 내용은 바뀌지 않는다.** 갱신으로 바뀔 수 있는 열은 `read_at`
  하나뿐이고, 받는 사람·종류·제목·참조·만들어진 시각은 자기 알림이라도 못 고친다.
  (강제 위치: 데이터베이스 — 열 단위 갱신 권한. 접근 정책의 `with check` 로는 부족하다:
  그 조건은 받는 사람만 보므로 나머지 열은 요청이 보낸 값 그대로 들어간다 — INV-Z8 과 같은 자리)
  위반 시: 사실 기록이 사실이 아니게 된다. 「거절되었습니다」를 「수락되었습니다」로 고쳐 두고
  화면에 그렇게 그려 놓을 수 있다. 남이 못 보는 자리라 티도 안 난다.

- INV-N6: 화면에 나가는 **알림 문장은 저장된 값(`type` · `title`)만으로 만든다.** 지금의
  원본을 다시 읽어 문장을 짓지 않는다.
  (강제 위치: 서버 — 알림 판독기)
  위반 시: 스터디 이름이 바뀌면 **지난 알림의 문장까지 같이 바뀐다.** 그때 그런 일이 있었다는
  기록이 지금의 이름으로 다시 쓰이고, 원본이 사라진 알림은 문장 자체를 잃는다.

- INV-N7: 알림이 가리키는 대상이 **지금 그 사람에게 보이지 않으면 링크를 걸지 않는다.**
  문장은 그대로 남고 누를 수 없게만 한다.
  (강제 위치: 서버 — 알림 판독기가 참조 대상의 현재 가시성을 확인해 링크 여부를 정한다)
  위반 시: 지워진 스터디를 가리키는 알림이 누르면 없는 화면으로 간다. 링크가 화면 안에 있으면
  누르지 않아도 미리 가져오기가 404 를 만든다 — 2026-09-07 에 `/about` 에서 실제로 났던 것과
  같은 모양이다.

- INV-N8: 종 옆의 **안 읽은 수는 패널이 안 읽음으로 그리는 줄 수와 같다.** 읽음 처리·전체
  읽음·삭제 뒤에도 사용자가 새로 고치지 않고 같아진다.
  (강제 위치: 서버 — 세는 조건과 그리는 조건이 같은 값(`read_at is null`)이고, 알림을 바꾸는
  액션이 헤더를 그리는 경로를 다시 그리게 한다)
  위반 시: 숫자는 3인데 패널은 비어 있다. 사용자는 못 본 알림이 어딘가 있다고 믿고 계속 연다.

## 시나리오

- S1 (INV-N1, 실패경로): Given 알림을 받은 사람이 아닌 로그인 사용자 / When 그 알림 행을
  id 로 읽는다 / Then 0행이다. 그 사람이 그 스터디의 호스트여도 같다.
- S1b (INV-N1, 반대 절반): Given 알림을 받은 본인 / When 자기 알림을 읽는다 / Then 보인다.
  정책이 조회를 통째로 막아 버려서 통과한 것이 아님을 보인다.
- S1c (INV-N1, 실패경로): Given 비로그인 / When 알림 표를 읽는다 / Then 0행이다.

- S2 (INV-N2, 실패경로): Given 로그인한 사용자 / When 자기 앞으로 알림을 직접 넣는다 /
  Then 거부된다. 넣을 정책이 없다.
- S2b (INV-N2, 실패경로): Given 같은 사용자 / When 남 앞으로 알림을 넣는다 / Then 거부된다.
- S2c (INV-N2, 반대 절반): Given 모집 중인 스터디 / When 다른 사람이 참가를 신청한다 /
  Then 호스트 앞으로 알림 행이 **생긴다**. 삽입이 통째로 죽은 상태도 위 둘만으로는 초록불이다.

- S3 (INV-N3): Given 모집 중인 스터디 / When 신청이 들어온다 / Then 알림은 **호스트**에게
  가고 신청자에게는 안 간다.
- S3b (INV-N3): Given 대기 중인 신청 / When 호스트가 수락한다 / Then 알림은 **신청자**에게
  가고 호스트에게는 안 간다. 거절·강퇴도 같다.
- S3c (INV-N3): Given 수락된 멤버 / When 스스로 나간다 / Then 알림은 **호스트**에게 간다.
- S3d (INV-N3, 건너뛰는 갈래): Given 스터디를 새로 만든다 / When 호스트 자신의 참여 행이
  `accepted` 로 들어간다 / Then 알림이 생기지 않는다.
- S3e (INV-N3, 건너뛰는 갈래): Given 호스트가 자기 스터디의 자기 참여 행 / When 스스로
  `withdrawn` 으로 바꾼다 / Then 알림이 생기지 않는다. 자기에게 자기 소식이 가지 않는다.

- S4 (INV-N4, 실패경로): Given 남의 알림 / When 그 행의 `read_at` 을 채운다 / Then
  아무것도 안 바뀐다.
- S4b (INV-N4, 실패경로): Given 남의 알림 / When 그 행을 지운다 / Then 아무것도 안 사라진다.
- S4c (INV-N4, 반대 절반): Given 자기 알림 / When 읽음 처리하고 지운다 / Then 둘 다 된다.
  정책이 갱신·삭제를 통째로 막아 버려서 통과한 것이 아님을 보인다.
- S4d (INV-N4): Given 두 사람이 각각 안 읽은 알림을 가진 상태 / When 한 사람이 「전체 읽음」을
  실행한다 / Then 그 사람 것만 읽음이 되고 다른 사람의 알림은 그대로 안 읽음이다.

- S5 (INV-N5, 실패경로): Given 자기 알림 / When `type` 을 `participation_accepted` 로
  바꾼다 / Then 거부된다. 열 권한이 정책보다 앞에서 막으므로 요청이 통째로 떨어진다.
- S5b (INV-N5, 실패경로): Given 자기 알림 / When `title` 이나 `reference_id` 를 바꾼다 /
  Then 거부된다.
- S5c (INV-N5, 반대 절반): Given 자기 알림 / When `read_at` 만 채운다 / Then 성공한다.
  이 절반이 없으면 갱신을 통째로 막아 버린 상태(= 아무도 읽음 처리를 못 한다)도 초록불이다.

- S6 (INV-N6): Given 「○○ 스터디」로 만들어진 알림 / When 호스트가 스터디 제목을 「△△」로
  고친 뒤 그 사람이 패널을 연다 / Then 알림 문장은 여전히 「○○」이다.
- S6b (INV-N6): Given 호스트가 지운 스터디를 가리키는 알림 / When 패널을 연다 /
  Then 문장이 그대로 보인다. 사라지지도, 빈칸이 되지도 않는다.

- S7 (INV-N7): Given 호스트가 지운 스터디를 가리키는 알림 / When 패널을 연다 /
  Then 그 줄에 링크가 없다. 화면 어디에도 그 주소가 나가지 않는다.
- S7b (INV-N7, 반대 절반): Given 살아 있는 스터디를 가리키는 알림 / When 패널을 연다 /
  Then 그 줄이 스터디 상세로 가는 링크다. 링크를 통째로 없앤 상태도 위 하나만으로는 초록불이다.

- S8 (INV-N8): Given 안 읽은 알림 3건 / When 패널을 연다 / Then 종 옆 숫자와 안 읽음으로
  그려진 줄 수가 둘 다 3이다.
- S8b (INV-N8): Given 같은 상태 / When 한 줄을 읽음 처리한다 / Then 새로 고치지 않아도 종 옆
  숫자가 2가 된다.
- S8c (INV-N8): Given 안 읽은 알림이 있는 상태 / When 그 알림을 **지운다** / Then 숫자가
  같이 줄어든다. 읽음 처리만 헤더를 다시 그리게 하고 삭제를 빠뜨리면 여기서만 어긋난다.

## 신뢰 경계

- 믿는 값: 데이터베이스가 스스로 아는 현재 사용자, 트리거가 `participants`·`studies` 에서
  직접 읽은 호스트와 제목.
- 믿지 않는 값: 클라이언트가 보낸 알림 id 목록(자기 것인지는 정책이 판정한다), 요청이 들고 온
  `user_id`, 그리고 **앱 코드의 판정만으로 지켜지는 것** — 서버도 공개 키로 붙으므로
  (INV-Z5) 앱을 우회한 요청이 같은 문을 두드린다.

## 비범위

- 알림의 종류를 늘리는 것(채팅 새 메시지·모집 마감 임박 등)은 여기서 다루지 않는다. 지금
  종류는 참가 사건 다섯이고 데이터베이스의 검사 제약이 그 다섯으로 묶어 둔다.
- 알림을 브라우저 밖으로 보내는 것(이메일·푸시)은 제품 정의의 범위가 아니다.
- 오래된 알림을 자동으로 지우는 보관 정책은 정하지 않는다. 지금은 사람이 지우는 것뿐이다.
- 실시간 밀어내기(새 알림이 도착하면 열려 있는 패널이 스스로 갱신되는 것)는 이 스펙 밖이다.
  INV-N8 이 요구하는 것은 **그 사람이 한 행동 뒤에** 숫자와 목록이 어긋나지 않는 것까지다.
