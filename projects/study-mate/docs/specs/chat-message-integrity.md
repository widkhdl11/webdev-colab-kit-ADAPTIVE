# 채팅 메시지의 기록 스펙

메시지는 방 멤버가 쓰는 것이지만, **그 메시지가 언제 왔는지는 멤버가 정하는 값이 아니다.**
2026-09-10 까지는 정할 수 있었다. `chat_messages` 에 열 단위 삽입 권한이 없어서, 방 멤버는
공개 키로 테이블에 직접 붙어 `created_at` 을 아무 값으로나 실을 수 있었다. 삽입 정책
(`0010:238-242`)이 보는 것은 `sender_id` 가 나인가와 이 방의 멤버인가 둘뿐이고,
**정책의 조건에 없는 열은 요청이 보낸 값 그대로 들어간다** — 0002 의 4절이 갱신에 대해
이미 같은 판정을 내렸는데 삽입 쪽은 그때 안 좁혔다.

그 값이 가는 곳이 셋이다. 날짜 구분선과 시각(`ChatRoomView.tsx:173,199`), 채팅방 목록의
정렬(`read-chats.ts:145`), 안 읽은 수(`read-chats.ts:132` 의 `.gt("created_at", last_read_at)`).
같은 경로로 본문 길이 상한도 우회됐다 — `src/features/chat/model/limits.ts` 가 스스로
「스키마에 제약이 없어 서버의 이 값이 유일한 강제 위치」라고 적어 놨는데, 직접 삽입은
그 액션을 지나지 않는다.

**0021 이 이 다섯 불변식을 전부 걸었다.** 아래 「강제 위치」는 지금 실제로 도는 것을 말한다.

이 스펙이 정하는 것은 하나다: **메시지 행에서 어느 열을 사람이 정하고 어느 열을
데이터베이스가 정하는가.**

## 불변식

- INV-M1: **메시지를 넣는 요청이 이름 붙일 수 있는 열은 `chat_id` · `sender_id` · `content`
  셋뿐이다.** `id` 와 `created_at` 은 요청이 못 정하고 데이터베이스 기본값에서만 나온다.
  (강제 위치: DB 열 단위 삽입 권한 — `revoke insert on public.chat_messages from anon,
  authenticated;` 뒤에 `grant insert (chat_id, sender_id, content) to authenticated;`.
  열 단위 권한은 정책보다 **앞에서** 판정하므로, 허용되지 않은 열이 요청에 들어오면
  정책을 보기도 전에 거부된다 — 0002 의 4절과 같은 손짓이다)

  위반 시 둘로 갈린다. **과거 시각**이면 그 문장이 남이 이미 나눈 대화의 중간에 끼어들고,
  `.gt("created_at", last_read_at)` 에 안 걸려 **안 읽음 배지에도 안 뜬다** — 받은 사람은
  새 메시지가 왔다는 신호를 못 받고, 스크롤을 올려야만 만난다. **미래 시각**이면 그 방이
  채팅방 목록 맨 위에 고정되고, 읽어도 배지가 안 꺼진다(읽음 시각이 그 미래를 못 넘는다).
  `id` 는 손해가 작지만 같은 권한 한 줄로 같이 닫힌다.

- INV-M2: **안 읽은 수를 가르는 두 값은 같은 시계에서 나온다.**
  `chat_messages.created_at` 과 `chat_participants.last_read_at` 은 둘 다 데이터베이스가
  찍는다. (강제 위치: DB — `created_at` 은 `default now()`, `last_read_at` 은 갱신을
  받는 자리에서 `now()` 로 덮어쓴다)

  2026-09-10 까지는 두 값의 출처가 달랐다. `created_at` 은 데이터베이스 시계이고
  `last_read_at` 은 **앱 서버의 시계**였다(`mark-read.ts` 의 `new Date().toISOString()`).
  지금 앱은 시각을 안 만들고 자리 표시(`STAMPED_BY_DB = null`)만 보낸다.
  위반 시: 앱 서버 시계가 데이터베이스보다 **빠르면** 읽음 시각이 미래로 찍혀 그 차이만큼
  뒤에 온 메시지가 영원히 안 읽음으로 안 뜬다. **느리면** 이미 읽은 메시지가 다시 안 읽음으로
  올라온다. 둘 다 오류를 안 내고, 화면은 그냥 틀린 숫자를 그린다.

- INV-M3: **저장되는 메시지 본문은 공백을 뺀 내용이 있고 2000자 이하다.**
  (강제 위치: DB 제약 `chat_messages_content_length` + 서버 액션 `insertMessage`.
  두 자리의 숫자는 `src/features/chat/model/limits.ts` 의 `MESSAGE_MAX` 하나에서 나온다)

  **「공백」은 `btrim` 이 아니다.** 인자 하나짜리 `btrim` 은 U+0020 하나만 자르므로,
  전각 공백(U+3000)이나 줄바꿈 없는 공백(U+00A0)으로만 된 본문이 「내용이 있다」를
  통과한다 — 0010 이 사용자 이름에서 실측해 적어 둔 함정이고, 이 스펙의 첫 구현도 같은
  자리에 빠졌다(2026-09-10 security-reviewer). 판정은 `[[:space:]]` 와 BOM(U+FEFF)을
  지운 나머지가 비어 있는가다.

  **두 자리가 세는 단위도 같아야 한다.** 앱은 `[...content].length`(코드 포인트)로 센다 —
  `content.length` 는 UTF-16 코드 단위라 이모지 하나가 2로 세지고, 그러면 스키마가 받아 줄
  메시지를 앱만 막는다.

  위반 시: 폼을 안 지나는 삽입으로 상한 없는 문단이 방에 들어간다. 그 값은 방 안 화면에만
  머물지 않는다 — 채팅방 목록의 미리보기 줄(`src/app/chats/page.tsx`)로도 나가므로 **보낸
  사람이 아닌 다른 멤버의 목록 화면이 무너진다.** 공백만으로 된 본문은 빈 말풍선이 되고,
  그 방의 마지막 메시지 자리를 차지해 목록에서 「아직 대화가 없습니다」와 구별되지 않는다.

- INV-M4: **메시지 본문에 제어문자가 들어가지 않는다.**
  (강제 위치: DB 제약 `chat_messages_content_no_control` — `content !~ '[[:cntrl:]]'`.
  서버 액션도 같은 범위를 먼저 본다 — `hasControlChars`. **강제 위치는 데이터베이스이고
  앱 쪽은 문구를 위해서다**: 제약이 거부하면 나오는 것이 영어 원문이라 화면에 못 내보내고,
  덮어쓴 문구가 「잠시 뒤 다시 시도해 주세요」라서 절대 성공하지 않는 요청에 기다리라고
  말하게 된다. 두 판정의 범위가 갈라지면 그 틈으로 들어온 값이 다시 그 반복되는 오류가
  되므로, 앱 쪽도 U+0000–1F · U+007F · U+0080–9F 로 맞춘다)

  0015 가 사용자 이름에, 0020 이 스터디 제목에 세운 것과 같은 규칙이고 근거도 같다.
  위반 시: 말풍선은 `white-space: pre-wrap` 으로 그리므로
  (`src/features/chat/ui/chat-room.module.css:97`)
  줄바꿈이 그대로 산다 — 2000자를 전부 줄바꿈으로 채우면 말풍선 하나가 화면 수십 개
  높이가 되고, 그 방을 연 사람은 다른 대화를 못 찾는다. **지금 입력창은 한 줄짜리
  `<input>` 이라 줄바꿈을 만들 수 없다**(`ChatRoomView.tsx:214`) — 즉 이 제약이 막는 것은
  폼이 만들 수 없는 값뿐이고, 폼을 지나는 메시지는 하나도 안 막힌다.

- INV-M5: **저장된 메시지는 수정되지도 삭제되지도 않는다.**
  (강제 위치: DB 두 층 — ① `chat_messages` 에 갱신·삭제 **정책이 하나도 없다**. 행 수준
  보안이 켜진 테이블에서 정책이 없는 동작은 전부 거부된다 ② 0021 이 `anon`·`authenticated`
  에서 갱신·삭제 **권한**도 거뒀다)

  **②는 오늘 아무것도 안 바꾼다** — ①이 이미 막는다. ②가 막는 것은 나중이다:
  「내 메시지 수정」 정책 한 줄(`for update using (sender_id = auth.uid())`)을 더하는 순간,
  권한이 남아 있으면 같은 요청이 `content` 만이 아니라 `chat_id`·`created_at`·`sender_id`
  까지 SET 에 실을 수 있다. 그 정책을 만드는 날 열 단위 `grant update (content)` 를 같이
  적게 만드는 것이 ②다. (2026-09-10 security-reviewer)

  위반 시: 남이 읽은 뒤에 자기 말을 다른 말로 바꿀 수 있다. 대화 기록이 「그때 이런 말이
  오갔다」를 더 이상 뜻하지 않게 된다.

  **이 불변식은 지금 지켜지고 있지만, 지키는 것이 「없음」이라 눈에 안 보인다.** 나중에
  누군가 메시지 수정 기능을 만들면서 정책 한 줄을 더하면 이 규칙이 소리 없이 사라진다.
  검사가 있어야 그때 깨진다.

## 시나리오

- **S1 (INV-M1, 실패경로)**: Given 방 멤버로 공개 키에 로그인한 연결 / When
  `insert into chat_messages` 에 `created_at` 을 하루 전으로 실어 보낸다 / Then 거부된다
  (열 단위 권한 없음). 행이 생기지 않는다.
- **S1b (INV-M1, 실패경로)**: Given 같은 연결 / When `id` 를 직접 지정해 보낸다 / Then 거부된다.
- **S1c (INV-M1, 정상경로)**: Given 같은 연결 / When `chat_id` · `sender_id` · `content`
  셋만 보낸다 / Then 행이 생기고, `created_at` 이 데이터베이스의 지금이다.
- **S1d (INV-M1, 반대 절반)**: Given 방 멤버가 아닌 연결 / When 셋만 보낸다 / Then 거부된다
  — 열을 좁히면서 기존 정책이 죽지 않았는지 본다.
- **S1e (INV-M1, 권한 층 직접)**: Given 데이터베이스 연결 / When 이 표의 삽입 권한 목록을 묻는다 /
  Then `authenticated` 는 정확히 셋이고 `anon` 은 하나도 없다. **행동으로는 `anon` 쪽을 못
  잰다** — 삽입 정책이 `sender_id = auth.uid()` 를 보고 비로그인은 그 값이 null 이라 정책이
  대신 거부하므로, 권한이 열려 있어도 삽입은 실패한다.

- **S2 (INV-M2)**: Given 한 번도 안 읽은 방(`last_read_at` 이 null)의 멤버 / When 앱이 보내는
  모양 그대로(`last_read_at: null`) 읽음 표시를 한다 / Then 저장된 값이 데이터베이스의 지금이고,
  그 전에 온 메시지는 안 읽은 수에서 빠진다.
- **S2b (INV-M2, 실패경로)**: Given 방 멤버 / When 읽음 표시 요청에 미래 시각을 실어 보낸다 /
  Then 그 값이 저장되지 않는다(데이터베이스가 자기 시각으로 덮는다).
- **S2c (INV-M2)**: Given 이미 한 번 읽은 방 / When 다시 읽음 표시를 한다 / Then 저장된 시각이
  앞으로 나아간다 — 「이미 값이 있으면 그대로 둔다」로 쓴 트리거를 여기서 잡는다.
- **S2d (INV-M2, 실패경로)**: Given 미래 시각을 실어 누른 뒤 / When 새 메시지가 온다 /
  Then 안 읽은 수가 1이다.

- **S3 (INV-M3, 실패경로)**: Given 방 멤버의 공개 키 연결 / When 본문 2001자로 직접 삽입한다 /
  Then 제약 위반으로 거부된다.
- **S3b (INV-M3, 정상경로)**: Given 같은 연결 / When 본문 2000자로 직접 삽입한다 / Then 들어간다
  — 상한을 좁히는 변이도 잡기 위해 경계를 양쪽에서 민다. **S3 과 다른 검사로 나눈다**:
  하나로 묶으면 앞 단언이 실패할 때 뒤 갈래를 아예 안 재고, 넓히는 변이와 좁히는 변이가 같은
  이름의 검사 하나를 깨뜨려 어느 갈래가 붙들린 것인지 못 가른다.
- **S3c (INV-M3, 실패경로)**: Given 같은 연결 / When 본문을 공백 세 칸으로 직접 삽입한다 /
  Then 거부된다. `char_length` 만 보는 제약은 여기서 통과한다.
- **S3d (INV-M3, 실패경로)**: Given 같은 연결 / When 전각 공백(U+3000)·줄바꿈 없는
  공백(U+00A0)·BOM(U+FEFF)으로만 된 본문을 직접 삽입한다 / Then 셋 다 거부된다.
  `btrim` 으로 판정하면 셋 다 통과한다.

- **S4 (INV-M4, 실패경로)**: Given 같은 연결 / When 본문에 줄바꿈을 넣어 직접 삽입한다 /
  Then 거부된다.
- **S4b (INV-M4, 반대 절반)**: Given 같은 연결 / When 평범한 한 줄 메시지를 보낸다 /
  Then 성공한다 — 제약이 정상 입력을 막고 있지 않은지 본다.
- **S4c (INV-M4, 실패경로)**: Given 같은 연결 / When 줄바꿈이 아닌 제어문자(U+0007)를 넣어
  직접 삽입한다 / Then 거부된다. 제약을 「줄바꿈만 막는다」로 좁히는 변경을 여기서 잡는다.
  널 문자(U+0000)를 안 쓰는 이유는 PostgreSQL 이 그것을 `text` 에 아예 못 담아서 제약이
  없어도 거부되기 때문이다 — 그러면 이 시나리오가 제약을 안 재고도 통과한다.

- **S5 (INV-M5, 실패경로)**: Given 자기가 보낸 메시지가 있는 방 멤버의 공개 키 연결 / When 그
  행의 `content` 를 갱신한다 / Then **거부되거나 0행이 바뀌고**, 원본이 그대로다.
  거부되는 **방식**을 단언하지 않는다 — 방벽을 하나 더 세우면 거부 방식이 바뀌는데,
  방식을 고정해 두면 불변식을 강하게 만드는 변경이 검사를 깨뜨린다.
- **S5b (INV-M5, 실패경로)**: Given 같은 연결 / When 그 행을 삭제한다 / Then 같은 방식으로
  아무것도 안 지워지고 원본이 남는다.
- **S5c (INV-M5, 정책 층 직접)**: Given 데이터베이스 연결 / When 이 표의 정책 목록을 묻는다 /
  Then 읽기와 넣기 둘뿐이다. **S5·S5b 는 직접 경로만 본다** — 나중에 `security definer`
  함수로 수정 기능이 들어오면 그 함수는 정책을 우회하므로 그 둘은 통과한 채 INV-M5 가 깨진다.
- **S5d (INV-M5, 권한 층 직접)**: Given 데이터베이스 연결 / When 이 표의 갱신·삭제 권한을
  묻는다 / Then `anon`·`authenticated` 에 하나도 없다. 이 방벽은 오늘 동작을 안 바꾸므로
  행동으로는 못 잰다.

## 신뢰 경계

- **믿는 값**: 세션이 확인해 준 사용자 id(`requireSession` 이 넘겨주는 `user.id`) ·
  데이터베이스가 찍은 `now()` · 접근 정책이 판정한 「이 방의 멤버인가」.
- **믿지 않는 값**: 요청이 보낸 모든 열. `created_at` · `id` 는 아예 받지 않고,
  `last_read_at` 은 받되 데이터베이스가 자기 시각으로 덮고,
  `content` 는 받되 길이와 모양을 데이터베이스가 다시 잰다. `sender_id` 는 정책이
  세션 값과 같은지 확인한다. 폼의 `maxLength` 와 서버 액션의 길이·제어문자 판정은
  읽을 수 있는 문구를 주기 위한 자리이지 강제가 아니다.

## 비범위

- **누가 이 방에 쓸 수 있는가**는 여기서 안 정한다 — `write-authorization.md`(INV-Z4) 와
  `participation-capacity.md`(INV-P8) 가 이미 덮는다. 이 스펙은 「쓸 수 있는 사람이
  **무엇을** 쓸 수 있는가」만 좁힌다.
- **눈에 안 보이는 글자 중 줄을 안 바꾸는 것은 여기서 안 막는다** — 양방향 제어
  문자(U+202A–202E 등) · 폭 없는 공백(U+200B) · **줄 구분자(U+2028)와 문단
  구분자(U+2029)** · 결합 부호 쌓기. 이름·알림 쪽에 같은 질문이 열려 있어 한 자리에서 같이
  정한다 (`docs/BACKLOG.md` 의 「양방향 제어 문자가 알림의 낫표 경계를 깰 수 있다」).

  **U+2028·U+2029 는 한 번 막았다가 되돌렸다(2026-09-10).** 막은 근거가 「줄바꿈 규칙에서
  강제 줄바꿈이라 `pre-wrap` 말풍선에서 U+000A 와 같은 일을 한다」였는데, 재 보니 아니었다 —
  Chromium 에서 `<p>` 높이: U+000A·pre-wrap **51px**(두 줄, 대조군) · U+2028·pre-wrap
  **26px** · U+2029 **26px** · U+000B **26px** · U+0085 **26px**. **CSS 에서 줄을 바꾸는 것은
  U+000A 하나뿐이다** — 유니코드 줄바꿈 규칙(UAX #14)의 「강제 줄바꿈」과 CSS 의
  「segment break」가 같은 집합이 아니다. 다른 렌더링 엔진은 안 쟀다.
  **가르는 기준은 「이 불변식이 이름 붙인 손해(세로 도배)를 내는가」이고, 이 둘은 안 낸다.**
  막는 값이 0이라는 것만으로 막으면 폭 없는 공백·양방향 제어와 기준이 갈린다.
- **메시지 신고·숨김·관리자 삭제**는 제품에 없다. INV-M5 는 「수정·삭제 경로가 없다」를
  고정하는 것이지, 그런 경로를 만들면 안 된다는 뜻이 아니다 — 만들 때 이 스펙을 고친다.
- **이미 저장된 행의 정정**은 마이그레이션에 안 넣는다. 0020 이 정한 절차와 같다:
  제약을 걸기 전에 위반 행을 세어 보고, 0이 아니면 정정을 손으로 한 번 돌린다.
