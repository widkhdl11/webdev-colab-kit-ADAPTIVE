# 저장되는 글자의 표시 무결성 스펙

이 제품에서 **한 사람이 쓴 글자가 다른 사람의 화면에 나가는 자리는 다섯**이다 — 사용자 이름
(`profiles.username`) · 스터디 제목(`studies.title`) · 채팅 본문(`chat_messages.content`) ·
알림에 복사된 제목(`notifications.title`) · 모집글 제목(`posts.title`). 다섯 자리는 전부
**제품이 쓴 글자 옆에** 놓인다. 이름은 멤버 목록의 다른 이름들 사이에, 제목은 알림 문장의
낫표 안에, 본문은 다른 사람의 말풍선 위아래에, 모집글 제목은 브라우저 탭 제목에서 제품
이름과 한 문자열 안에.

**모집글 제목이 다섯 번째로 들어온 경위**(2026-09-15, P17 결정). 이 스펙을 승인할 때
`posts.title` 은 빠져 있었다. 그런데 `src/app/posts/[id]/page.tsx` 의 `generateMetadata` 가
`` `${post.title} — Study Mate` `` 를 탭 제목으로 만든다 — INV-T2 가 막으려는 모양 그대로고,
거기엔 `<bdi>` 를 걸 요소조차 없다(탭 제목은 요소가 아니라 문자열이다). 그리고 `posts` 에는
앱에도 데이터베이스에도 이 부류의 판정이 하나도 없어서, 제목에 제어문자가 섞이면
「잠시 뒤 다시 시도해 주세요」가 뜨고 다시 시도해도 절대 성공하지 않는다.

**그래서 어기면 사고가 나는 규칙은 「길이」가 아니라 「제 자리에 머무는가」다.** 지금까지
세운 제약(길이 · 제어문자 · 공백)은 전부 이 규칙의 한 조각이었는데, 조각마다 따로 정해져서
같은 종류의 값이 열마다 다르게 처리된다. 이 스펙은 그 판정을 **한 자리로 모은다.**

여기서 정하는 것은 **저장 여부**이고, 이미 저장된 값이 화면에서 어디까지 번지는가는
INV-T3 가 따로 맡는다. 둘 다 필요한 이유는 알림의 제목이 **사건이 일어난 순간의 사본**이기
때문이다 — 원본에 제약을 걸어도 그 전에 복사돼 나간 행은 안 바뀐다(0020 이 같은 이유로
`notifications.title` 에도 길이 제약을 걸었다).

## 근거 — 2026-09-11 실측

**목록으로 정하지 않고 쟀다.** 직전 사이클에서 줄 구분자(U+2028·U+2029)를 「강제 줄바꿈
이니까」라는 이유로 막았다가, Chromium 에서 줄을 안 바꾼다는 측정에 근거가 뒤집혀 되돌린
적이 있다. 같은 실수를 반대 방향으로도 하지 않으려고 네 부류를 전부 이 앱의 DOM 모양으로
재현해 쟀다.

### ① 지금 무엇이 통과하나 (로컬 Postgres 17, 문자 37개)

| 부류 | 이름 | 제목 | 본문 |
|---|---|---|---|
| 제어문자 U+0000–1F · 7F · 80–9F | 막힘 | 막힘 | 막힘 |
| 공백류 U+00A0 · 1680 · 2000–200A · 2028 · 2029 · 202F · 205F · 3000 | **통과** | **통과** | 막힘 |
| 폭 없는 것 U+180E · 200B · 200C · 200D · 2060 · FEFF | **통과** | **통과** | **통과**(FEFF 만 막힘) |
| 양방향 서식 U+200E · 200F · 202A–202E · 2066–2069 | **통과** | **통과** | **통과** |
| 결합 부호 U+0300–036F · 0489 | **통과** | **통과** | **통과** |

- **`btrim(title) <> ''` 는 U+0020 하나만 자른다.** 전각 공백(U+3000) 한 자로 된 제목이
  「내용이 있다」를 통과한다. 0010 이 이름에서 실측해 적어 뒀고 0021 이 본문에서 고친
  그 함정이, 제목에는 그대로 남아 있었다.
- **이름에는 「비어 있지 않다」 조건이 아예 없다** — 길이 1–20 과 제어문자 금지뿐이다.
  줄바꿈 없는 공백(U+00A0) 한 글자짜리 이름이 통과한다.
- **U+180E 는 이 Postgres 에서 `[[:space:]]` 가 아니다** — 유니코드 6.3 에서 공백 부류
  (Zs)에서 서식 부류(Cf)로 옮겨 갔다. 본문의 공백 판정이 이것 하나를 놓치는 이유다.

### ② 눈에 어떻게 보이나 (Chromium, 멤버 목록의 이름 자리)

| 값 | 그려진 폭 |
|---|---|
| `김하늘`(대조군) | 42px |
| U+00A0 한 자 | 4.9px |
| U+3000 한 자 | 14px |
| U+3000 스무 자 | 280px |
| U+200B · U+FEFF · U+2060 · U+180E · U+0300 각 한 자 | **0px** |

폭 0 은 이름이 통째로 안 보인다는 뜻이다. 이것이 0010 이 「멤버 목록에 빈 줄로 뜨는
사용자」라고 적어 둔 그것이고, **같은 값으로 남과 구별되지 않는 이름을 만들 수도 있다** —
`김하늘` 과 `김하늘‌`(뒤에 U+200C)는 화면에서 같은 글자다.

### ③ 알림 줄의 낫표 경계 — 무엇이 깨나 (Chromium)

알림 한 줄은 `「` + `<b>제목</b>` + `」` + 제품 꼬리말이 **한 문단 안**에 있다. 제목에
양방향 서식 문자를 하나 넣고, 네 토막의 가로 위치로 시각 순서를 읽었다.

**제목이 한글일 때는 U+202E(RLO) 하나만 깼다.** `「제목」꼬리말` 이 `「꼬리말」제목` 으로
뒤집힌다. 나머지 아홉(LRO · RLE · LRE · RLI · LRI · FSI · RLM · LRM · PDF)은 순서를 안 바꿨다.

**그런데 그것은 내 시험 데이터의 성질이었다.** 제목을 히브리어(`לימוד`)로 바꿔 다시 재니
**RLE · RLI · FSI 도 똑같이 뒤집었다.** 어느 문자가 깨느냐는 그 문자의 성질이 아니라
**제목 안에 방향 토막이 몇 개인가**로 갈리고, 그 값은 제품이 안 정한다.

> 이것이 이 스펙이 **부류 전체를 막는 근거**다. 「실측에서 깬 것만 막는다」로 갔으면
> U+202E 한 자만 막고 RLE 를 열어 뒀을 것이고, 그 구멍은 히브리어 제목 하나로 열린다.

**제어 문자가 하나도 없는 아랍어·히브리어 제목은 경계를 안 깼다.** 정상적인 오른쪽-왼쪽
이름은 무고하고, 막는 것은 서식 문자뿐이다.

**`<b>` 를 `<bdi>` 로 바꾸면 U+202E 를 넣어도 안 깨진다** — 격리가 문단 안에서 그 토막의
방향 계산을 닫는다. 이것이 INV-T3 다.

### ④ 결합 부호는 다른 종류였다 (Chromium)

| 바탕 + U+0303 개수 | 잉크가 기준선 위로 |
|---|---|
| 0개 | 7px |
| 2개 | 13px |
| 6개 | 22px (줄 높이 21px 를 처음 넘는다) |
| 30개 | **81px** |

**줄 높이는 21px 에서 안 변한다.** 레이아웃은 그대로인 채 잉크만 위로 뻗어서, 말풍선 목록
에서 **위쪽 말풍선 둘을 덮는다** — 화면을 찍어 눈으로 확인했다. 덮인 글자는 읽을 수 없다.

그런데 이 부류는 앞의 셋과 **성질이 다르다.** 백로그는 넷 다 「폼으로는 못 만들고 붙여
넣기로만 들어오며 막는 값이 0」이라고 적었는데, 결합 부호는 그렇지 않다 — `café` 를
`cafe` + U+0301 로 보내는 입력기가 흔하고(macOS 의 NFD), 그것을 막으면 **정상적인 글자가
막힌다.** 한글 바탕에서는 애초에 안 쌓인다(30개를 붙여도 잉크가 12px 그대로).

그래서 결합 부호는 이 스펙의 비범위다. 고치는 자리도 다르다 — 잉크가 상자를 넘는 것은
표시 층의 일이고, 말풍선 상자에 「넘치는 것은 안 그린다」를 걸면 실제로 잘린다(두 방식으로
확인했다). 시각 기준에 걸리는 결정이라 백로그로 넘긴다.

## 불변식

- INV-T1: **저장되는 사람의 글자에는 보이는 내용이 하나는 있어야 한다.**
  공백류와 폭 없는 글자를 전부 지운 나머지가 비어 있으면 안 된다.
  (강제 위치: DB 제약 — `profiles_username_visible` · `studies_title_visible` ·
  `chat_messages_content_visible` · `notifications_title_visible` · `posts_title_visible`.
  앱 쪽은 문구를 위한 자리이고 판정은 `src/shared/lib/text.ts` 하나에서 나온다)

  지우는 집합은 `[[:space:]]` + U+180E + U+200B–U+200D + U+2060 + U+FEFF 다.
  `[[:space:]]` 에 U+2028·U+2029 가 들어 있으므로 줄 구분자만으로 된 값도 여기서 걸린다 —
  **직전 사이클이 되돌린 판단과 어긋나지 않는다.** 그때 되돌린 것은 「줄을 바꾸니까
  금지」였고, 여기서 거는 것은 「보이는 내용이 없으니까 거부」다. 줄 구분자가 **섞인**
  값은 여전히 통과한다.

  **`btrim` 으로 쓰지 않는다.** 인자 하나짜리 `btrim` 은 U+0020 하나만 자른다(위 실측 ①).

  위반 시: 멤버 목록에 이름이 안 보이는 사람이 생기고(폭 0px), 채팅방 목록의 마지막 메시지
  자리가 빈 칸으로 차서 「아직 대화가 없습니다」와 구별되지 않는다. 제목이 빈 칸이면 알림
  줄이 `「」에 새 참가 신청이 왔습니다` 가 된다 — 어느 스터디인지 읽을 방법이 없다.

- INV-T2: **양방향 서식 문자는 저장되지 않는다.**
  U+200E · U+200F · U+202A–U+202E · U+2066–U+2069 열 자다.
  (강제 위치: DB 제약 — `profiles_username_no_bidi` · `studies_title_no_bidi` ·
  `chat_messages_content_no_bidi` · `notifications_title_no_bidi` · `posts_title_no_bidi`.
  앱 쪽은 같은 판정을 `src/shared/lib/text.ts` 에서 먼저 본다)

  **부류 전체를 막는 근거는 실측 ③ 이다** — 어느 한 자가 경계를 깨는지는 그 문자가 아니라
  값의 내용이 정하고, 값의 내용은 쓰는 사람이 정한다.

  **글자의 방향 자체는 안 막는다.** 아랍어·히브리어로 된 이름과 제목은 그대로 통과하고,
  실측에서 경계도 안 깼다. 막는 것은 **주변 글자의 순서를 바꾸는 서식 문자**뿐이다.

  **U+200D(ZWJ)는 여기 없다.** 가족 이모지(👨‍👩‍👧)가 ZWJ 로 이어 붙인 글자라서, 금지하면
  정상적인 메시지가 막힌다. ZWJ 는 INV-T1 의 「지우고 나면 남는 게 있나」에서만 쓰인다 —
  ZWJ 만으로 된 값은 거부되고, 이모지 안에 든 ZWJ 는 통과한다.

  위반 시: 알림 줄에서 제품이 쓴 꼬리말과 사람이 쓴 제목의 시각 순서가 뒤집힌다(실측 ③).
  낫표가 그리려던 경계 — 「여기까지가 남이 쓴 글자다」 — 가 그 줄에서 뜻을 잃는다.

- INV-T3: **제품이 쓴 글자와 사람이 쓴 글자가 한 문단에 있으면, 사람이 쓴 쪽은 방향 격리
  안에 있다.**
  (강제 위치 둘 — ① 알림 줄의 제목을 `<bdi>` 로 감싼다:
  `src/widgets/site-header/ui/NotificationBell.tsx` ② 모집글 탭 제목은 사람이 쓴 제목을
  U+2068(FSI)과 U+2069(PDI) 사이에 둔다: `src/app/posts/[id]/page.tsx` 의 `generateMetadata`)

  **탭 제목에 `<bdi>` 를 못 쓰는 이유는 그것이 요소가 아니라 문자열이기 때문이다.** 브라우저가
  탭에 그리는 것은 `<title>` 안의 글자뿐이라 감쌀 자리가 없다. 같은 일을 하는 문자가
  FSI–PDI 한 쌍이고, 이것은 **제품이 쓰는 글자**다 — INV-T2 가 막는 것은 사람이 쓴 값에
  그 문자가 **저장되는** 것이지 제품이 경계를 그리려고 쓰는 것이 아니다.

  **INV-T2 가 있는데도 이것이 따로 필요한 이유는 알림의 제목이 사본이기 때문이다.**
  참가 사건의 트리거가 그때의 제목을 `notifications` 행으로 복사하므로, 제약이 생기기
  전에 복사된 행은 원본을 고쳐도 안 바뀐다. INV-T2 는 앞으로 저장될 값을 맡고, INV-T3 는
  이미 저장된 값이 그 문단에서 할 수 있는 일을 맡는다.

  **이 격리는 시각을 안 바꾼다** — 실측 ③ 에서 한글·아랍어·히브리어 제목의 시각 순서가
  `<b>` 일 때와 `<bdi>` 일 때 같았다.

  위반 시: INV-T2 가 막기 전에 저장된 제목 하나가 알림 줄의 순서를 계속 뒤집는다.

## 시나리오

- **S1 (INV-T1, 실패경로)**: Given 로그인한 공개 키 연결 / When 자기 이름을 전각 공백
  (U+3000) 한 자로 직접 갱신한다 / Then 제약이 거부한다.
- **S1b (INV-T1, 실패경로)**: Given 같은 연결 / When 이름을 U+00A0 한 자로 갱신한다 /
  Then 거부된다. **줄바꿈 없는 공백은 `[[:space:]]` 라 ①에서 같이 걸린다.**
- **S1c (INV-T1, 실패경로)**: Given 같은 연결 / When 이름을 U+200B 한 자로 갱신한다 /
  Then 거부된다.
- **S1d (INV-T1, 반대 절반)**: Given 같은 연결 / When 이름을 `김하늘` 로 갱신한다 /
  Then 들어간다 — 이 검사가 없으면 제약을 「항상 거부」로 바꿔도 위 셋이 다 통과한다.
- **S1e (INV-T1, 반대 절반)**: Given 같은 연결 / When 이름에 가족 이모지(ZWJ 둘)를 쓴다 /
  Then 들어간다.
- **S2 (INV-T1, 제목)**: Given 호스트의 공개 키 연결 / When 제목을 U+3000 한 자로 직접
  갱신한다 / Then 거부된다.
- **S2b (INV-T1, 제목, 반대 절반)**: Given 같은 연결 / When 제목을 `토익 900` 으로
  갱신한다 / Then 들어간다.
- **S3 (INV-T1, 본문)**: Given 방 멤버의 공개 키 연결 / When 본문을 U+200B 한 자로 직접
  삽입한다 / Then 거부된다. **0021 의 판정은 이것을 통과시켰다**(U+200B 가
  `[[:space:]]` 가 아니다).
- **S3b (INV-T1, 본문, 반대 절반)**: Given 같은 연결 / When 본문에 가족 이모지를 보낸다 /
  Then 들어간다 — ZWJ 를 금지하는 구현이면 여기서 빨간불이 난다.
- **S4 (INV-T2, 실패경로)**: Given 호스트의 공개 키 연결 / When 제목 앞에 U+202E 를 붙여
  갱신한다 / Then 거부된다.
- **S4b (INV-T2, 실패경로)**: Given 같은 연결 / When 제목 앞에 U+202B(RLE)를 붙인다 /
  Then 거부된다. **한글 제목에서는 화면이 안 깨지는 문자다** — 그런데도 막는 이유가
  실측 ③ 이므로, 이 검사가 없으면 「안 깨는 것은 열어 두자」는 되돌림을 아무도 못 막는다.
- **S4c (INV-T2, 반대 절반)**: Given 같은 연결 / When 제목을 아랍어 `دراسة` 로 갱신한다 /
  Then 들어간다 — 오른쪽-왼쪽 글자 자체를 막는 구현이면 여기서 빨간불이 난다.
- **S4d (INV-T2, 이름·본문)**: Given 각 열의 공개 키 연결 / When U+2066 을 섞은 값을
  넣는다 / Then 네 열 모두 거부된다.
- **S5 (INV-T1·T2, 알림 행)**: Given 데이터베이스 연결 / When `notifications` 에 보이는
  내용이 없는 제목, 또는 서식 문자가 든 제목을 직접 넣는다 / Then 거부된다.
  **원본이 이미 좁으므로 트리거가 이 제약에 걸릴 경로는 없다** — 이 제약이 막는 것은
  사람이 직접 넣는 경우와, 나중에 원본 제약이 느슨해지는 경우다.
- **S6 (INV-T2, 앱 층)**: Given 이름 수정 폼 / When 서식 문자가 든 이름을 제출한다 /

  「잠시 뒤 다시 시도해 주세요」로 덮인다. 다시 시도해도 절대 성공하지 않는다.
- **S6b (INV-T2, 앱 층, 범위 일치)**: Given 앱의 판정과 데이터베이스 제약 / When 같은

## 비범위

- **결합 부호만으로 된 값은 INV-T1 을 통과한다** — 지우는 집합에 결합 부호가 없기 때문이다.
  그런 값은 화면에서 폭 0px 로 그려지므로 INV-T1 이 이름 붙인 손해가 그대로 난다.
  안 막는 이유는 아래와 같다(막는 값이 0 이 아니다). 바탕 글자가 없는 경우만 따로 막는 것은
  가능하지만 결합 부호의 집합이 넓어 어떤 목록을 써도 일부만 덮는다 — 백로그로 넘긴다.
- **결합 부호 쌓기**(U+0300–036F 등)는 여기서 안 막는다. 근거는 실측 ④ 다 — 손해는
  실재하지만(잉크 81px, 위 말풍선 둘을 덮는다) **막는 값이 0 이 아니다**(`cafe`+U+0301).
  고치는 자리도 표시 층이다. 백로그로 넘긴다.
- **폭 없는 글자가 섞인 값**은 안 막는다. `김하늘‌`(뒤에 U+200C)은 INV-T1 을 통과한다 —
  「지우고 나면 남는 게 있나」이지 「그 글자가 있나」가 아니다. 이름 흉내를 정말 막으려면
  유일성 판정을 **정규화한 값**으로 해야 하는데, 그건 이 스펙이 아니라 이름의 유일성
  규칙이 다룰 일이고 지금 이 제품에는 이름 유일성 자체가 없다.
- **길이 상한**은 각 열의 기존 제약이 그대로 맡는다(이름 20 · 제목 60 · 본문 2000).
- **제어문자**(U+0000–1F · 7F · 80–9F)도 기존 제약이 맡는다. 이 스펙은 그것이 안 잡는
  나머지만 다룬다.
