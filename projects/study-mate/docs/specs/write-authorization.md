# 쓰기 인가 스펙

> **2026-09-04 승인, 2026-09-05 모델링 개정.** 아래 불변식은 사람이 확인해 계약으로 삼았다 —
> "지금 이렇게 동작한다"가 아니라 **"이렇게 동작해야 한다"** 다.
>
> **2026-09-05 활성 계약이 됐다.** 불변식 일곱을 참조하는 테스트가
> `tests/integration/write-authorization.test.ts` 에 있고, **공개 키로** 실제 데이터베이스에
> 붙어서 돈다 — 그 키는 브라우저에도 들어가는 값이라, 그 연결로 할 수 있는 일이 곧
> "아무나 할 수 있는 일"이다.
>
> 검증 중에 하나를 배웠다. **"요청이 거부됐다"만 보는 검사로는 부족하다** — 정책을 활짝 열어도
> 행동 검사가 전부 초록불인 상태가 실제로 나왔다. 거부는 정책 말고 다른 이유로도 일어나기
> 때문이다. 그래서 정책 표현식 자체를 읽어 "조건이 아무나인 쓰기 정책이 없다"를 따로 붙든다.

누가 무엇을 바꿀 수 있는지를 정하는 곳이 어디인가가 이 스펙의 주제다. 어기면 사고가 나는
자리는 그 판정을 우회하는 경로가 있느냐다.

## 2026-09-05 모델링 개정 — 무엇이 바뀌었나

**① INV-Z5 에 강제되는 자리가 생긴다.** 들여온 구조에서는 이 불변식이 지켜지는 자리가
**아예 없었다.** 새로 짓는 스키마는 모든 테이블에 행 수준 접근 정책을 켠 상태로 시작한다.

**이것이 이번 데이터 모델 작업의 가장 큰 값어치다.** 아래 「관찰된 사실」이 말하는 대로,
이 애플리케이션은 서버에서도 공개 키로 데이터베이스에 접근한다. 그 키는 브라우저에도
들어간다. 그러면 **앱을 거치지 않고 데이터베이스를 직접 부르는 것을 아무도 막지 못한다** —
행 수준 접근 정책 말고는.

즉 INV-Z1~Z4 를 서버 코드에 아무리 잘 써 놔도, 정책이 없으면 그 넷은 **우회 가능한
권고사항**이다. 정책이 있어야 계약이 된다.

**② 스터디 삭제를 소프트 삭제로 바꾼다(INV-Z6).** 들여온 스키마는 스터디를 지우면
참여자·모집글·채팅방·메시지까지 연쇄로 지웠다. 체크리스트 4번(삭제되면 어떻게 되는가)에
걸린다 — **호스트 한 사람의 삭제가 다른 사람들의 대화 기록을 없앤다.** 참조가 전혀 없는
것만 하드 삭제하고, 사람이 남긴 것이 딸려 있으면 소프트 삭제한다.

## 관찰된 사실 — 불변식보다 먼저 읽을 것

- 들여온 마이그레이션 스냅샷에서 공개 테이블(스터디·참여자·모집글·채팅·프로필 등)에 행 수준
  접근 정책이 **하나도 없었다.** 거기 있던 정책 11개는 전부 파일 저장소 객체에 대한
  것이었다. `[코드에서 확인]`
- 애플리케이션은 서버에서도 **공개 키**로 데이터베이스에 접근한다. 서버 전용 비밀 키를 쓰는
  코드가 없다. `[코드에서 확인]` → 이것이 위 ①의 전제다.
- 파일 저장소 정책 중 하나는 삭제를 모두에게 허용했다(`for delete` · `to public` ·
  조건 `true`). 이름은 "모든 사용자에게 읽기 허용"인데 실제 동작은 삭제 허용이라, 이름과
  동작이 어긋나 있었다. `[코드에서 확인]` → 새 스키마에서 반복하지 않는다(INV-Z7).
- 관리자·운영자 역할은 제품에 없다. 인가의 축은 **작성자인가 / 그 스터디의 호스트인가**
  둘뿐이다. `[코드에서 확인]`

## 불변식

- INV-Z1: 스터디를 지우는 것은 그 스터디의 호스트만 할 수 있다.
  (강제 위치: 데이터베이스 — 행 수준 접근 정책 · 그리고 서버 — 도메인 모델의 호스트 판정)
  위반 시: 남의 스터디가 사라지고 거기 딸린 것들이 같이 사라진다.

- INV-Z2: 참가 신청을 수락·거절·강퇴하는 것은 그 스터디의 호스트만 할 수 있다.
  (강제 위치: 데이터베이스 — 접근 정책 · 서버 — 액션)
  위반 시: 아무나 남의 스터디 멤버를 들이고 내보낼 수 있다.

- INV-Z3: 모집글을 고치거나 지우는 것은 작성자만 할 수 있다.
  (강제 위치: 데이터베이스 — 접근 정책 · 서버)
  위반 시: 남의 글이 바뀌거나 사라진다.

- INV-Z4: 인가 판정의 근거가 되는 사용자 식별자는 **검증된 세션에서 꺼낸 값**이고, 요청
  본문이나 URL 에서 온 값이 아니다. 데이터베이스 정책도 요청이 들고 온 값이 아니라
  데이터베이스가 스스로 아는 현재 사용자로 판정한다. (강제 위치: 서버 + 데이터베이스)
  위반 시: 요청을 조작해 남의 권한으로 행동할 수 있다.

- INV-Z5: **애플리케이션을 우회한 직접 접근에도 위 넷이 그대로 유지된다.**
  모든 테이블에 행 수준 접근 정책이 켜져 있고, 정책이 허용하지 않는 동작은 거부된다.
  (강제 위치: 데이터베이스)
  위반 시: 위 넷이 전부 무의미해진다 — 공개 키를 가진 누구나 정책 판정을 건너뛴다.

- INV-Z6: 사람이 남긴 것이 딸려 있는 스터디는 **지워도 행이 사라지지 않는다.** 호스트의
  삭제는 "지워진 것으로 표시"이고, 멤버들의 참여 기록과 대화는 그대로 남는다.
  목록·검색에는 나타나지 않는다. (강제 위치: 데이터베이스 — 삭제 표시 컬럼 + 조회 정책)
  위반 시: 호스트 한 사람의 행동이 다른 사람들의 기록을 지운다. 되돌릴 수 없다.

- INV-Z7: 파일 저장소의 삭제·수정은 **그 파일을 올린 사람만** 할 수 있다.
  (강제 위치: 데이터베이스 — 저장소 접근 정책)
  위반 시: 아무나 남의 프로필 사진을 지운다. 들여온 구조에 실제로 그런 정책이 있었다.

## 시나리오

- S1 (INV-Z1, 실패경로): Given 호스트가 아닌 로그인 사용자 / When 스터디 삭제를 요청한다 /
  Then 아무것도 바뀌지 않고 "스터디 호스트만 삭제할 수 있습니다"를 반환한다.
- S2 (INV-Z2, 실패경로): Given 호스트가 아닌 로그인 사용자 / When 대기 중인 신청을 수락한다 /
  Then 거부한다.
- S3 (INV-Z5, 실패경로): Given 공개 키를 가진 아무나 / When 데이터베이스를 직접 불러 남의
  스터디 행을 지운다 / Then **거부된다.** 앱을 거치지 않았어도 그렇다.
- S4 (INV-Z5, 반대 절반): Given 그 스터디의 호스트 / When 같은 방법으로 자기 스터디를
  지운다 / Then 성공한다. 정책이 전부를 막아 버려서 통과한 것이 아님을 보인다.
- S5 (INV-Z6): Given 수락된 멤버 2명과 대화가 있는 스터디 / When 호스트가 삭제한다 /
  Then 목록에서 사라지지만 멤버의 참여 기록과 메시지는 그대로 조회된다.
- S6 (INV-Z7, 실패경로): Given 다른 사람이 올린 프로필 사진 / When 그것을 지우려 한다 /
  Then 거부한다.

## 신뢰 경계

- 믿는 값: 데이터베이스가 스스로 아는 현재 사용자, 데이터베이스에서 다시 읽은 행의
  소유자 필드.
- 믿지 않는 값: 클라이언트가 보낸 소유자·역할 필드, URL 의 id, 그리고 **서버 코드의
  판정만으로 지켜지는 것** — 공개 키로 접근하는 구조에서 서버 판정은 우회 가능하다.

## 비범위

- 관리자·운영자 역할은 제품에 없다.
- 읽기 권한의 세부(누가 어떤 모집글을 볼 수 있는가)는 여기서 다루지 않는다. 발견은
  공개라는 것이 제품 원칙이고, 화면 목록(`docs/IA.md`)이 어디까지 공개인지 정한다.
