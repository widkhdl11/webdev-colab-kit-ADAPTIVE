# 쓰기 인가 스펙

> **이 스펙은 코드에서 역산했다.** 아래 불변식은 관찰이지 합의가 아니고, 지금 동작이
> 버그일 수도 있다. 항목마다 확인 필요 표시를 달았고 `status` 는 `draft` 다.

누가 무엇을 바꿀 수 있는지는 지금 **애플리케이션 계층에서만** 정해진다. 서버 액션이 세션을
확인하고, 도메인 모델이 "호스트인가"를 판정해 아니면 거부한다. 어기면 사고가 나는 자리는
그 판정을 우회하는 경로가 있느냐다.

## 관찰된 사실 — 불변식보다 먼저 읽을 것

- 공개 테이블(스터디·참여자·모집글·채팅·프로필 등)에 행 수준 접근 정책이 **하나도 없다.**
  마이그레이션 스냅샷에 있는 정책 11개는 전부 파일 저장소 객체에 대한 것이다.
  `[코드에서 확인]`
- 애플리케이션은 서버에서도 **공개 키**로 데이터베이스에 접근한다. 서버 전용 비밀 키를 쓰는
  코드가 없다. `[코드에서 확인]`
- 이 둘을 합치면: 애플리케이션을 거치지 않고 데이터베이스 API 를 직접 부르는 경로가 열려
  있는지가 **이 프로젝트에서 가장 먼저 확인해야 할 것**이다. 스냅샷이 실제 데이터베이스의
  현재 설정과 같은지도 함께 봐야 한다. `[추정 — 확인 필요]`
- 파일 저장소 정책 중 하나는 삭제를 모두에게 허용한다(`for delete` · `to public` ·
  조건 `true`). 의도인지 실수인지는 질문 목록에 있다. `[코드에서 확인]`

## 불변식

- INV-Z1: 스터디를 지우는 것은 그 스터디의 호스트만 할 수 있다. (강제 위치: 서버 —
  도메인 모델이 호스트 여부를 판정하고 아니면 `NotHost` 로 거부)
  위반 시: 남의 스터디가 사라지고, 딸린 참여자·모집글·채팅·메시지까지 연쇄로 지워진다.
  `[추정 — 확인 필요]`
- INV-Z2: 참가 신청을 수락·거절·강퇴하는 것은 그 스터디의 호스트만 할 수 있다.
  (강제 위치: 서버 — 액션이 호스트 여부를 확인)
  위반 시: 아무나 남의 스터디 멤버를 들이고 내보낼 수 있다. `[추정 — 확인 필요]`
- INV-Z3: 모집글을 고치거나 지우는 것은 작성자만 할 수 있다. (강제 위치: 서버)
  위반 시: 남의 글이 바뀌거나 사라진다. `[추정 — 확인 필요]`
- INV-Z4: 인가 판정의 근거가 되는 사용자 식별자는 **세션에서 꺼낸 값**이고, 요청 본문이나
  URL 에서 온 값이 아니다. (강제 위치: 서버)
  위반 시: 요청을 조작해 남의 권한으로 행동할 수 있다. `[추정 — 확인 필요]`
- INV-Z5: 애플리케이션을 우회한 직접 접근에도 위 판정이 유지된다. (강제 위치: 데이터베이스)
  **이 불변식은 지금 강제되는 자리가 없다** — 위의 관찰된 사실 참고.
  위반 시: 위 넷이 전부 무의미해진다. `[추정 — 확인 필요]`

## 시나리오

- S1 (INV-Z1, 실패경로): Given 호스트가 아닌 로그인 사용자 / When 스터디 삭제를 요청한다 /
  Then 아무것도 지우지 않고 "스터디 호스트만 삭제할 수 있습니다"를 반환한다.
- S2 (INV-Z2, 실패경로): Given 호스트가 아닌 로그인 사용자 / When 대기 중인 신청을 수락한다 /
  Then 거부한다.
- S3 (INV-Z5, 실패경로): Given 공개 키를 가진 아무나 / When 데이터베이스 API 로 남의 스터디
  행을 직접 지운다 / Then 거부되어야 한다. **지금 그렇게 되는지 아무도 확인하지 않았다.**

## 신뢰 경계

- 믿는 값: 세션에서 꺼낸 사용자 식별자, 데이터베이스에서 다시 읽은 행의 소유자 필드.
- 믿지 않는 값: 클라이언트가 보낸 소유자·역할 필드, URL 의 id, 참여자 행에 복사돼 있는
  이름·이메일·사진(조회 효율용 사본이라 원본은 프로필이다).
