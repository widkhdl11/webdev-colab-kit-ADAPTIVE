## 이 리뷰에서 가장 크게 드러난 것

### ① INV-Z10 의 「새 모집글」 갈래에 강제 위치가 없었다 (리뷰어 셋이 독립적으로)

스펙은 이렇게 적어 두었다 — "지워진 것으로 표시된 스터디는 새로운 쓰기를 받지 않는다 —
새 신청도, 새 수락도, **새 모집글도.** (강제 위치: 데이터베이스)". 신청에는
`private.study_accepts_applications` 가 붙어 있고 수락에는 트리거 검사가 있는데,
**모집글 삽입 경로만 비어 있었다.**

```sql
create policy posts_insert_author on public.posts for insert
with check (
  author_id = (select auth.uid())
  and private.is_study_host(study_id, (select auth.uid()))
);
```

`private.is_study_host` 는 `select exists (... where id = ? and host_id = ?)` 라서
`deleted_at` 을 아예 안 본다. **호스트가 자기가 지운 스터디의 id 를 폼에 넣으면 삽입이
성공했다.** 공개 키로 PostgREST 를 직접 불러도 같다.

**새는 값은 없었다** — 그렇게 만들어진 행은 `posts_read` 의 `study_is_visible` 이 감춰서
호스트 본인 말고는 목록에도 상세에도 안 나온다. 깨져 있던 것은 계약이고, 삭제 취소 경로가
생기거나 `study_is_visible` 이 넓어지는 날 값이 샌다.

**이번 사이클이 쓴 주석이 그것을 지켜진다고 적고 있었다** — `read-my-studies.ts` 가
"고르게 두면 고른 뒤에 거부당한다"고. 거부는 일어나지 않았고, INV-Z10 을 지키는 것은 화면의
셀렉트 박스 하나뿐이었는데 같은 파일이 스스로 "이 목록은 인가가 아니다"라고 적어 두었다.

`0014` 로 닫았다. `private.study_is_live` 를 만들고 정책에 조건을 하나 더 걸었다.
`study_accepts_applications` 를 재사용하지 않은 이유는 그 함수가 `closed_at` 도 보기 때문이다 —
「마감된 스터디에 새 모집글」은 아무도 안 정한 제품 결정이라, 함께 막으면 그 결정이
마이그레이션에 숨는다(보류 P12 로 올렸다).

### ② 브라우저에서 온 본문은 문단이 안 나뉘었다

HTML 폼은 textarea 의 줄바꿈을 전부 CRLF 로 보낸다. 그런데 본문을 문단으로 나누는 쪽은
`content.split(/\n{2,}/)` 로 **`\n` 이 연달아 두 번** 오는 것을 찾는다 — `\r\n\r\n` 은
CR·LF·CR·LF 라 한 번도 안 맞고, **본문 전체가 한 문단으로 렌더된다.**

지금까지 안 드러난 이유는 `posts` 의 본문이 전부 SQL 로 넣은 시드였기 때문이다. 브라우저
textarea 에서 본문이 들어오는 경로는 이번 사이클이 처음 만들었다. 같은 모양이 스터디 설명
(`create-study` 의 textarea)에도 있었다 — 원인이 같아서 `shared/lib/form-text.ts` 한 자리로
모으고 두 폼을 같이 갈아끼웠다. 브라우저에서 실측했다(아래 실행 근거).

### ③ 배포되는 액션 파일을 부르는 검사가 0개였다

유닛 검사는 조립 함수(`makeCreatePost`)를 직접 불렀다. 그래서 **액션 파일이 그 조립을 안
거치도록 바뀌어도 전부 초록불**이었다 — 세션 가드가 프로덕션 경로에서만 빠지는 상태가
만점으로 나온다. 리다이렉트 목적지를 폼 값에서 받게 바꾸는 변이도 같은 이유로 안 잡혔다.

`create-post.test.ts` 를 따로 만들어 액션을 직접 부른다. 세 가지를 붙든다 — 가드를 거치는가 ·
세션이 없으면 데이터베이스에 손도 안 대는가 · 목적지가 **데이터베이스가 돌려준 id** 인가.

### ④ 검사를 쓰자마자 결함이 하나 드러났다

행도 오류도 없는 갈래(`data: null, error: null`)에서 `dbErrorMessage(…, null)` 이
**TypeError 를 던졌다.** `ActionResult` 가 아니라 서버 액션 밖으로 나가는 예외라, 사용자는
폼 오류 대신 500 을 보고 적은 것을 잃는다. `.single()` 조합에서는 잘 안 나지만 누군가
`.maybeSingle()` 로 바꾸는 순간 정상 경로가 된다.

### ⑤ 상한 검사가 상한을 고정하지 못했다

검사가 구현과 **같은 상수를 import** 해서 상대적으로만 확인했다 — `TITLE_MAX = 80` 을
800000 으로 바꿔도 전부 초록불이다. 문구에 숫자를 박아 고정했다. 같은 결로, 보내는 페이로드를
값 하나씩만 보면 컬럼 이름 오타나 `content` 누락이 전부 초록불인데(가짜는 무엇을 보내든 성공을
돌려준다) 실제 스키마는 `content not null` 이라 그러면 기능이 100% 죽는다 — 다섯 칸을 통째로
단언한다.
