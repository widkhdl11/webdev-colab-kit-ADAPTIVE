## 이 리뷰에서 가장 크게 드러난 것

### ① 새로 쓴 검사 둘 중 하나가 알리바이였다

INV-Z12 의 「판정 함수 일곱이 API 에 없다」가 빈 본문 `{}` 로 RPC 를 두드리고 있었다.
**PostgREST 는 함수가 없을 때와 본문의 키로 인자를 못 맞출 때 둘 다 404 를 낸다.**
그래서 함수가 노출된 상태에서도 404 였다 — 실측으로 확인했다:

```
변이를 심어 public.is_study_member 를 다시 연 상태에서
  {} 로 두드림                          → 404
  {"p_study_id":…,"p_user_id":…} 로     → 200 + false
```

이 검사는 노출을 감지하지 못하면서 언제나 초록불이었다. `z12-expose-helper` 가 잡힌 것은
옆의 구조 검사 덕이었고, 숫자만 보면 둘 다 일하는 것처럼 보였다.

고친 방향은 셋이다. 인자 이름을 **데이터베이스에서 읽어** 실어 보내고, 이름 목록도
`pg_proc` 에서 뽑고(손으로 적으면 오타가 404 를 받아 통과한다), **반대 절반**을 넣었다 —
열려 있다고 알고 있는 함수 하나(`increment_post_views`)를 같은 방법으로 두드려 404 가
아닌 것을 확인한다. 그것이 실패하면 위 검사가 알리바이라는 뜻이다.

### ② 스키마를 옮겨도 껍데기 함수 하나면 문이 다시 열린다

정책이 `private` 함수를 부르려면 anon·authenticated 에게 실행 권한이 있어야 한다
(**권한을 뺏어 확인했다: `permission denied for function study_is_visible` — 정책이 죽는다**).
그 권한이 있으므로 `security definer` 가 **아닌** 껍데기 함수를 `public` 에 하나 만들면
안쪽 판정 함수를 그대로 대신 불러 준다. 실측했다 — 비로그인 호출이 200 + 판정값을 받았다.

구조 검사가 `prosecdef` 만 보고 있어서 이걸 못 봤다. 조건을 넓혔다:
**definer 이거나, 본문이 `private.` 을 부르거나.** 그리고 계산 컬럼 면제를
「인자가 하나이고 그것이 공개 테이블의 행 타입일 때」로 좁혔다 — 지어낸 복합 타입은
읽을 행이 없어서 JSON 으로 만들어 보내면 그만이기 때문이다.

### ③ 복구가 죽으면 S4 구멍이 그대로 열린 채 남았다

복구는 옛 마이그레이션을 다시 트는데, **0002 가 판정 함수들을 진짜 본문으로 `public` 에
다시 만든다.** 0002 가 지나간 뒤에 죽으면 그 함수 다섯이 그대로 남는다 — 껍데기가 연 것이
아니라 0002 가 연 것이라, 껍데기를 아무리 안전하게 만들어도 못 막는 상태였다.

**데이터베이스 쪽 복구를 트랜잭션 하나로 묶었다.** 어디서 죽든 아무것도 안 남는다.
그리고 껍데기를 일곱에서 **하나로** 줄였다 — 나머지 여섯은 복구 목록 안에서 진짜 본문으로
다시 만들어지거나(0002·0004) 아무도 안 부른다(`is_chat_member`).

### ④ 순서 의존이 주석에만 있었고, 지문 대조로는 절대 안 잡혔다

`RESTORE_MIGRATIONS` 에서 0010 이 맨 뒤여야 한다는 것이 주석에만 있었다. 그런데
**mutation-run 은 기준선 지문을 뜨기 전에 복구를 먼저 돌린다** — 순서가 틀린 복구는 매번
같은(틀린) 상태를 만들고 그 상태가 기준선이 되므로, 이후 모든 복구가 「일치」로 나온다.

복구가 끝난 자리를 **복구 자신이 확인**하게 했다. 일부러 어겨서 잡히는 것을 봤다:

```
0010 을 목록에서 빼고 --restore
→ Error: 복구가 끝났는데 판정 함수가 public 에 남아 있다: is_study_host, is_study_member,
  study_accepted_count, study_accepts_applications, study_is_recruiting, study_is_visible
  (종료코드 1)
그 뒤 데이터베이스를 세어 보니 남은 것 0건 — 트랜잭션이 되감았다
```

### ⑤ 강제 위치를 옮긴 것이 「빈 이름」의 정의를 갈라 놓았다

폼의 `trim()` 은 전각 공백까지 지우는데 데이터베이스의 기본 `btrim` 은 U+0020 하나만
자른다. 그래서 전각 공백 한 글자짜리 이름이 길이 1 로 제약을 통과했다 —
**멤버 목록에 빈 줄로 뜨는 사용자.** 이건 옮기기 전에는 없던 자리다.

무엇이 공백인지는 데이터베이스에 물어서 정했다(`chr(12288) ~ '[[:space:]]'` → 참).
그리고 패턴에서 백슬래시 이스케이프를 걷어내고 `chr()` 로 바꿨다 — 이 파일이 도구를
거치는 동안 유니코드 이스케이프가 실제 문자로 바뀌어 들어간 적이 있고, 그때 규칙이
조용히 달라진다.
