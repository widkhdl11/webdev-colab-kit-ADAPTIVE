## 게이트가 잡은 것

마이그레이션을 저장하자마자 편집 훅이 6건을 냈고, 둘 다 실제 문제였다.

- **`security definer` 함수 넷의 `search_path`** — `= public` 으로 뒀는데 빈 문자열이어야
  한다. 그래야 임시 스키마에 같은 이름의 객체를 만들어 함수 안의 이름을 가로채는 것을
  막는다. 빈 문자열로 고정하면 모든 이름을 스키마까지 적어야 하는데, 본문이 이미 그렇게
  돼 있어서 값만 바꾸면 됐다.
- **위험 표면 미커버** — 인가·동시성 표면에 들어갔는데 스펙 둘이 아직 보류였다. 예상한
  대로였고, 아래 테스트를 쓰고 활성화해서 풀었다.

## 변이로 확인한 것 (테스트가 실제로 붙들고 있는가)

강제 장치를 하나씩 무력화하고 실제 데이터베이스에 테스트를 돌렸다. 전부 복원했다.

| 무력화한 것 | 결과 |
|---|---|
| 정원 검사의 **행 잠금**(`for update`) 제거 | 1 failed — 경합 검사만 빨간불 |
| `studies` 의 행 수준 보안 끄기 | 10 failed |
| 스터디 수정 정책을 `아무나`로 열기 | 2 failed |
| 참여자 상태 전이 검사 제거 | 2 failed |
| 정원 하한 검사 제거 | 1 failed |
| 수락 시 채팅방 참여 제거 | 3 failed |
| `studies` 에 `status` 컬럼 추가 | 1 failed |
| 저장소 삭제 정책을 `아무나`로 열기 | 2 failed |
| 신청 정책을 `아무나`로 열기 | 3 failed |

**여기서 검사의 구멍이 두 번 나왔다.**

**① 경합 검사가 경합을 안 만들고 있었다.** 처음 쓴 판은 A 를 커밋한 **뒤에** B 를 돌리는
순서였다. 그러면 B 는 A 의 결과를 보고 스스로 거부하므로, **행 잠금을 통째로 빼도
초록불이었다.** 두 트랜잭션을 실제로 겹쳐 놓고 "A 가 열려 있는 동안 B 가 멈춰 있는가"를
직접 단언하도록 고친 뒤에야 변이가 빨간불이 됐다.

**② "요청이 거부됐다"만 보는 검사로는 정책을 못 붙든다.** 스터디 수정 정책을 `true` 로
활짝 열었는데 **행동 검사 35개가 전부 통과했다** — 거부가 정책 말고 다른 이유로도
일어나기 때문이다. 정책 표현식 자체를 읽어 "조건이 아무나인 쓰기 정책이 하나도 없다"를
따로 단언하고 나서야 잡혔다.

두 번 다 초록불이었다. **초록불은 그 자체로 검증의 증거가 아니라는 것이 또 확인됐다.**
